# DEC-005：准备输入摘要里是否保留「用例 ID ↔ 修订」的配对

状态：**待裁定**

提出日期：2026-10-01

提出方：B 包（项目与计划）

受影响方：A、B、C

裁定方：袁（项目负责人）

期望裁定日期：待定

影响合同：`AB-001`；`BC-001` 的 `PreparedRun.case_revisions` 字段本身不变

## 1. 待裁定问题

`prepare_run` 的业务输入摘要（决定"同一 `prepare_request_id` 的再次到达是复用、冲突还是需重新准备"）
**要不要包含"哪个用例对应哪个修订"的配对关系**。

两条现行要求指向相反的结论：一条要求配对进摘要，另一条要求观察到的依据事实**不进**摘要。

## 2. 冲突依据（逐字引用）

| 来源 | 原文 |
| --- | --- |
| `docs/一期工程检查-B包.md` 第 3.2 节 B-09 | "规范载荷保留 ID/修订/摘要的完整关联，区分有序序列与集合，仅按字段语义规范化；**同请求换修订映射必须识别异输入**，单纯无意义重排应保持一致。" |
| `docs/项目文档/一期/架构文档/01-项目与计划.md` 第 11 节（经 `docs/一期工程检查-B包.md` B-02 复述） | "按主责合同区分请求意图与来源事实；同键异请求冲突，来源漂移 `needs_reprepare`" |
| 同上，B-02 原文 | "反而纳入观察到的源码 content_identity，来源变化抛 `PreparationConflictError`" |
| 现行实现 `src/aitest/application/planning/preparation.py` | `PAYLOAD_FIELDS` 只含 `case_revision_ids` / `rule_version_ids` / `template_version_ids`（**标识，不含修订号**） |
| 现行实现 `src/aitest/application/planning/preparation.py` 的 `decide_preparation()` | 判定次序为硬性："摘要冲突 > 来源变化 > 幂等复用" |
| 同上，`_INVALIDATION_DESCRIPTIONS` | `"plan_revision": "plan republished"` —— 计划重发布对应 `needs_reprepare` |

## 3. 冲突点

`PreparationInputs.case_revisions` 来自**已发布的计划**，属**观察结果**而非请求内容。

- 若按 B-09 把配对放进摘要：计划一重发布，摘要随之变化，判定在第一步就命中"摘要冲突"，
  结果报 `CONFLICTED` —— 而 `_INVALIDATION_DESCRIPTIONS` 明确规定该情况应走 `needs_reprepare`。
- 若按架构第 11 节把观察结果排除在摘要之外：配对关系不参与判定，
  B-09 的反例（`case-1@1/case-2@2` 换成 `case-1@2/case-2@1` 得到同一摘要）依然成立。

两条要求**同时满足不了**。

## 4. 选项与代价

### 选项甲：按 B-09，把 ID／修订／摘要三元组放进摘要载荷

- 代价：计划重发布被判成"同键异输入冲突"，与架构第 11 节的失效规则矛盾；
  B-02 那类"观察结果混进摘要"的问题以另一种形式回来。

### 选项乙：摘要仍只放标识；把「ID ↔ 修订」映射移到**观察侧**比对

- 做法：给 `PreparationRequest` 增加一个观察字段（如按用例排序的 `(case_id, revision)` 序列），
  在 `decide_preparation()` 中与 `InputRevisions` 一起比对；变化即 `needs_reprepare`，
  并列入 `changed_inputs`。
- 效果：B-09 的"换配对要识别为不同输入"满足；"计划重发布走 `needs_reprepare`"也满足；
  单纯无意义重排因规范排序而保持一致。
- 代价：`PreparationRequest` 增加字段，属准备身份合同的变更，
  需 C 知悉（`PreparedRun` 的外部字段不变）；`tests/unit/test_prepare_run.py` 需补反例。

## 5. B 侧倾向（**仅为建议，不作为结论**）

B 倾向于**选项乙**：它同时满足两条要求的字面结论，代价只是增加一个观察字段。

## 6. 阻塞影响

- 不裁定则检查文档 B-09 一直挂账；
- 擅自按某一种实现，另一种口径下要重写 `prepare_run.py`、`preparation.py` 与相关测试。

## 7. 裁定结论

- **结论：采用选项乙。** 摘要仍只放标识；「用例 ID ↔ 修订」的配对作为**观察事实**
  参与 `decide_preparation()` 的比对，变化即 `needs_reprepare` 并列入 `changed_inputs`。
- **裁定方式**：项目负责人于 2026-10-01 指示由 B 侧按现有文档证据自行裁定并回写本节。
- 判定日期：2026-10-01
- 确认人：待项目负责人确认（本节已回写，合同同步见下）
- **选乙的理由**：它是唯一**同时满足两条原文**的方案——
  B-09 要求"同请求换修订映射必须识别异输入"，乙通过观察比对识别；
  架构第 11 节要求"计划重发布走 `needs_reprepare`"，乙因配对不进摘要而保持该结论。
  选项甲会让计划重发布先撞 `CONFLICTED`，与 `_INVALIDATION_DESCRIPTIONS` 直接矛盾。
- **规范形式**：观察字段按 `case_id` 排序存放 `(case_id, revision)` 序列，
  因此"单纯无意义重排"得到同一结论，满足 B-09 的后半句。
- 需同步的合同／Schema／夹具／测试：
  - `src/aitest/application/planning/preparation.py`：`PreparationRequest` 增观察字段，
    它随准备记录一起落盘并可重建（否则重启后比对会失真），`decide_preparation()` 加比对；
  - `src/aitest/application/planning/prepare_run.py`：从 `PreparationInputs.case_revisions` 构造该字段；
  - `tests/unit/test_prepare_run.py`、`tests/unit/test_preparation.py`：补 B-09 反例
    （`case-1@1/case-2@2` → `case-1@2/case-2@1` 必须判为不同输入；同集合重排必须判为相同）；
  - `PreparedRun` 的外部字段与字节夹具**不变**，`BC-001` 无需变更。
