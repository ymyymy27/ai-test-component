# DEC-004：`publish_rules()` 发布结果落到哪个记录类别

提出方：B 包（项目与计划）

受影响方：A、B、C、D

裁定方：袁（项目负责人）

期望裁定日期：待定

影响合同：`AB-001`；并影响 `CORE-001` 的索引与查询面

## 1. 待裁定问题

"规则发布"这个动作落盘后应当产生哪一类记录：

- 是产生一条**规则版本**记录（`rule_version`），与"规则草稿"（`rule_draft`）分开；
- 还是沿用**同一条草稿记录族的下一修订**，即发布只是给草稿加一版？

现状是后者，但 `AggregateKind` 里声明了 `rule_version`，全仓却**没有任何一处写入它**。

## 2. 冲突依据（逐字引用）

| 来源 | 原文 |
| --- | --- |
| `docs/项目文档/一期/架构文档/01-项目与计划.md` 第 57 行 | `RuleDraft`发布`RuleVersion`不可变。 |
| 同上，第 77 行（记录字段与模块归属表） | \| `RuleDraft` → `RuleVersion` \| 规则编号、版本、适用范围、步骤、证据要求、启用状态 \| |
| 同上，第 154 行（记录字段表） | \| RuleDraft/RuleVersion \| 稳定规则ID、适用范围、步骤/断言/证据规范、版本、发布状态及来源 \| `domain/planning/rules.py` \| |
| `docs/接口对接/进行中/AB-001-端口与保存/contract.md` 第 3.1 节（B 向 A 提的端口需求） | `save_rule_draft / publish_rule_version -> RevisionRef` |
| 同上，第 8.3 节（B 提供的 `RecordRepository` 草案） | `def read_rule_version(self, rule_id: str, revision: int) -> Mapping[str, object]: ...` |
| 现行实现 `src/aitest/application/planning/publish.py` | `unit_of_work.stage_record(aggregate_kind="rule_draft", record_id=draft.rule_id, ...)` |
| `tests/unit/test_publish_orchestration.py` | 读的是 `reader.read(aggregate_kind="rule_draft", record_id="rule-1", revision=1)` |

第 154 行把该记录写作「RuleDraft/RuleVersion」并含"发布状态"，因此"一个记录家族、
发布只是加修订"这一读法也有原文依据；两种解释都成立，需要唯一结论。

## 3. 选项与代价

### 选项甲：发布产生 `rule_version` 记录

- 做法：`publish_rules()` 改为 `stage_record(aggregate_kind="rule_version", record_id=draft.rule_id, ...)`；
  `read_rule_version()` 按该类别读；`rule_draft` 只留草稿。
- 代价：
  - C、D 若已按 `rule_draft` 读取，需要改；
  - `tests/unit/test_publish_orchestration.py` 的读取断言要改（改取值、不删除）；
  - 已落盘的 `rule_draft` 发布记录需要迁移口径。

### 选项乙：维持 `rule_draft` 同族，改需求文档

- 做法：承认发布=给草稿记录加一版；把 `AB-001` 第 3.1／8.3 节的 `publish_rule_version` /
  `read_rule_version` 改写为草稿族的读写；`AggregateKind` 里的 `rule_version` 删除或说明用途。
- 代价：
  - 架构分册第 57、77 行需要修订；
  - "已发布的规则版本不可变"这一约束要改由"修订号不可覆盖"表达，需确认语义等价。

## 4. B 侧倾向（**仅为建议，不作为结论**）

B 倾向于**选项甲**：

- 架构分册第 57 行"`RuleDraft` 发布 `RuleVersion` 不可变"把两者描述为**发布前后两个对象**；
- B 向 A 提的端口需求本来就区分 `save_rule_draft` 与 `publish_rule_version`；
- `AggregateKind` 已声明 `rule_version`，若最终不用，需要显式说明它的用途。

但第 154 行的记录表写法支持选项乙，因此**必须由裁定方定唯一结论**。

## 5. 阻塞影响

- 不裁定则 B-04／FR05 的"规则发布可被 C/D 按准确修订读到"无法闭合；
- 擅自按某一种实现，另一种口径下要重写实现、测试与已落盘记录的迁移。

## 6. 裁定结论

- **结论：采用选项甲。** `publish_rules()` 产生 `rule_version` 记录
  （`aggregate_kind="rule_version"`）；`rule_draft` 只承载草稿；
  按准确修订读回走 `read_rule_version(rule_id, revision)` 语义。
- **裁定方式**：项目负责人于 2026-10-01 指示由 B 侧按现有文档证据自行裁定并回写本节；
  结论已按第 2 节的逐字原文选择，未另立口径。
- 判定日期：2026-10-01
- 确认人：待项目负责人确认（本节已回写，合同同步见下）
- **选甲的理由（逐条对应第 2 节原文）**：
  1. 架构《01-项目与计划》第 57 行"`RuleDraft`发布`RuleVersion`不可变"把两者描述为
     **发布前后两个对象**——不可变的是"版本"，草稿本身按第 154 行的"发布状态"承载状态；
  2. `AB-001` 第 3.1、8.3 节是 B 向 A 提的**正式端口需求**，本就区分
     `save_rule_draft` 与 `publish_rule_version` 并给出 `read_rule_version`；
  3. `AggregateKind` 已声明 `rule_version`，不采用它就需要另行说明该取值的用途。
- **对第 154 行"RuleDraft/RuleVersion"的解释**：该行是**记录字段与模块归属表**，
  把同一主责模块下的两个记录并列书写，不表示它们是同一个 `record_id` 的修订序列。
- **迁移影响（实测）**：全仓读取 `rule_draft` 的只有
  `src/aitest/application/planning/publish.py` 与 B 自己的
  `tests/unit/test_publish_orchestration.py`，**没有 B 包之外的消费方**，
  因此迁移成本限于 B 侧。
- 需同步的合同／Schema／夹具／测试：
  - `src/aitest/application/planning/publish.py`：`aggregate_kind` 改为 `rule_version`，
    payload 增加发布状态；
  - `tests/unit/test_publish_orchestration.py`：读取断言改取值、不删除；
  - `AB-001` 第 3.1／8.3 节的签名需求**保持原样**（本就按甲书写）。
