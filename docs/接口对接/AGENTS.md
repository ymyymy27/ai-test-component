# 接口对接目录协作规则

> 本文件是仓库根 [`AGENTS.md`](../../AGENTS.md) 的目录补充，冲突时以根文件为准。当前规则只有根 `AGENTS.md`、本文件和[文档总览](../README.md)中的约定；`docs/归档/` 下的作者 AGENTS 是历史材料。

本文件适用于 `docs/接口对接/` 及其全部子目录。进入本目录工作前，必须先读同目录 `README.md`，再读仓库根 `AGENTS.md` 及任务涉及的现行主责合同：需求看 [`../01-准备阶段/02-需求规格.md`](../项目文档/一期/02-需求/02-需求规格.md)，功能与判定看 [`../01-准备阶段/03-功能清单.md`](../项目文档/一期/02-需求/03-功能清单.md)，字段与接口看 [`../02-开发阶段/`](../项目文档/一期/README.md) 对应分册，界面看 [`../01-准备阶段/04-产品方案与界面设计.md`](../项目文档/一期/03-设计/01-产品方案与界面设计.md)。

## 1. 唯一入口

- `README.md` 是目录规则、状态定义和总台账的唯一入口；现行状态以合同 frontmatter 与本页第 10 节为准，不另建状态副本。
- `contract.md` 是一个对接主题的唯一现行合同正文。
- 评审意见、交付说明、修改日志、聊天记录和 `归档/` 材料不得覆盖现行合同。
- 相同字段、枚举、身份、状态或公式不得在多个合同中另起定义；引用主责合同条款和版本。

## 2. 放置规则

- 草案、评审中、待确认和接入中的合同统一放在 `进行中/<合同编号-主题>/`，不按双方增加目录层级。`进行中/` 当前只有 `.gitkeep`；没有在办主题时保持空目录，不删除目录本身。
- 同时面向三个及以上包的基础合同使用 `CORE-*` 编号，也直接放在 `进行中/`。
- 只有满足 `README.md`「移入已完成的条件」的整个主题目录才能进入 `已完成/`。
- 尚未完全闭合的跨合同决定一项一文件放入 `待裁定/DEC-*.md`。该目录包括两类：提出后尚未裁定的冲突，以及**已裁定、已实现但仍有真实验收等未闭合项**的决定；后者必须写清剩余闭合条件，不能伪装成未定冲突。
- 跨合同决定不得修改准备阶段与开发阶段合同正文：接口侧只读引用，发现字段、枚举或判定口径与合同不一致时开 `DEC-*.md` 写明差异，由合同 owner 在对应分册修订；接口侧同步受影响的合同、Schema、夹具和测试，完成后把 DEC 移入 `归档/裁定/`，未完成实现转记合同状态与下一动作。
- 已裁定、失效或被替代材料放入 `归档/`，并在文件顶部标明不再生效及现行入口。
- 不在 `docs/接口对接/` 根目录散放业务合同。

## 3. 命名和责任

- 使用稳定合同编号，如 `AB-001`、`CD-001`、`CORE-001`；目录名不使用成员姓名。
- 双方编号不表示方向，提供方和消费方写在合同元数据中。
- 每个能独立确认、独立变更或拥有不同阻塞项的主题使用独立合同目录。
- 交付说明统一命名为 `delivery*.md`：单份用 `delivery.md`，按包拆分用 `delivery-<A|B|C|D>.md`；不得使用其他名称或按成员命名。
- 每项待确认问题必须有编号、责任方、下一动作和阻塞影响。裁定编号单调递增、不复用；无原记录的历史引用登记为「记录缺失」，不补造结论。

## 4. 状态不得混写

每份合同必须分别维护：

- `contract_status`；
- `provider_implementation`；
- `consumer_implementation`；
- `verification_status`；
- `last_verified_commit`；
- `blockers`、`next_owner`、`next_action`。

禁止用一个「已完成」同时表示文档确认、提供方实现、消费方接入和真实环境验收。提供方完成不等于双方对接完成；契约或单元测试通过不等于真实 Trae、其他宿主、文件系统故障恢复或平台对拍通过。`frozen + done + fixture_passed` 只表示跨包接口关闭，不表示产品验收通过。

## 5. 修改流程

1. 从 `README.md` 总台账和各合同 frontmatter 找到现行合同与主责合同条款。
2. 检查工作区现有改动，保留他人的未提交成果。
3. 先改 `contract.md` 或新建待裁定记录，再修改代码、Schema、夹具和消费方。
4. 双方确认必须回写合同；聊天和单方评审不能作为最终确认。
5. 已冻结合同发生变更时更新版本、影响和迁移说明，破坏性变更提升主版本。
6. 文件移动或重命名后，全仓更新文档、代码注释和测试中的路径引用。
7. 同步更新 `README.md` 总台账和对应修改日志；新增裁定只在本页与第 10.4 节台账登记一次，不在文件顶部追加平行状态段落。

## 6. 验证要求

- 运行受影响的 Schema、夹具、合同和集成检查。
- 接口验证批次写入 `docs/validation/`；历史证据在 `docs/归档/validation/`，不向归档追加新结论。
- 逐个检查本目录 Markdown 相对链接的目标存在（断链必须为 0），并确认没有指向文档重构前的旧目录前缀。
- 确认历史状态表述已随历史快照显式标注，没有被写成现行状态。
- 运行 `git diff --check`。
- 在 `delivery*.md` 中分别列出已实现、静态/单元/合同检查、真实环境验收和未验证项。
- 失败检查必须如实记录，不能因为与本次改动无关就写成全部通过。

## 7. 禁止事项

- 不按成员姓名新建目录。
- 不创建第二份并行生效的合同正文。
- 不把多个无关裁定问题重新合并成一个汇总文件。
- 不手工编辑生成 Schema 或生成夹具。
- 不把未知状态静默解释为成功、通过、空结果或无需处理。
- 不删除历史确认记录；被替代内容进入归档并指向现行入口。
- 不在 `docs/归档/` 新增现行合同、评审或验证批次。
- 不在本目录修改准备阶段或开发阶段合同正文；需要改口径时按第 2 节开 DEC 卡。
