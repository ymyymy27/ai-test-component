# 跨包接口对接规则与总台账

版本：2.2

更新日期：2026-10-02

适用范围：A、B、C、D 包之间的合同、交付、评审、裁定与验证材料

## 1. 目录职责

本目录只管理**跨包协作材料**。产品范围、字段语义和业务规则仍以
`docs/项目文档/阅读索引.md` 指定的现行需求、功能和架构分册为主责来源。
接口对接文档负责把主责合同落实为双方可以实施、验证和演进的具体边界，不能另起一套业务定义。

```text
docs/接口对接/
├── AGENTS.md                         # 本目录对自动化工具生效的强制协作规则
├── README.md                         # 本规则与唯一总台账
├── 进行中/                           # 草案、评审中、待确认或接入中的合同
├── 已完成/                           # 双方接入和最低验证均已完成的现行合同
├── 待裁定/                           # 跨合同冲突，等待有权责任人裁定
└── 归档/                             # 已裁定、已废弃、被替代或仅供追溯的历史材料
```

目录含义不得混用：

- `进行中/` 中的文档仍有后续动作，不能因为提供方写完代码就移入 `已完成/`。
- `已完成/` 中的合同仍然有效；需要变更时重新进入评审流程，不能直接静默修改。
- `待裁定/` 中的文件只解释冲突和候选方案，不是接口合同。
- `归档/` 中的材料不再作为现行接口定义；已裁定记录只保留“为什么这样决定”，正式字段和接口必须已经同步回对应合同。

## 2. 稳定编号和目录命名

### 2.1 对接合同

合同编号采用 `<双方包名>-<三位序号>`，双方字母按固定顺序排列，不表示提出方向：

- `AB-001`：A 与 B 的第一个独立对接主题；
- `BC-001`：B 与 C 的第一个独立对接主题；
- `CORE-001`：同时面向三个及以上包的公共合同。

每个可独立确认、独立变更或具有不同阻塞条件的主题使用一个目录：

```text
进行中/AB-001-端口与保存/
├── contract.md                       # 唯一现行合同正文
├── review-A.md                       # 评审过程材料，可有多份
├── delivery.md                       # 实现交付状态，可选
└── fixtures/                         # 该合同的公开夹具，可选
```

不得在路径中写成员姓名。人员变化不应导致合同路径变化；提供方、调用方和确认人写在正文元数据中。

### 2.2 裁定记录

裁定编号采用 `DEC-<三位序号>`。一个文件只处理一个可以单独作出结论的问题，不再维护把多个问题混在一起的“待办汇总”。

## 3. 文档角色

| 文件 | 只负责什么 | 不负责什么 |
| --- | --- | --- |
| `contract.md` | 双方当前生效的字段、接口、时序、错误、兼容与确认 | 施工日志、个人方案汇总 |
| `review-*.md` | 某次评审的问题、意见和建议 | 代替双方确认后的合同正文 |
| `delivery*.md` | 提供方与消费方的实现、接入、验证和缺口 | 新定义字段或改变合同语义 |
| `fixtures/` | 可执行、可校验的跨包样例 | 代替 Schema 或主责业务规则 |
| `DEC-*.md` | 跨合同冲突、选项、裁定与同步范围 | 长期承载正式接口定义 |

同一字段或枚举只能有一个主责来源。其他文档使用链接和版本引用，不复制一份可独立演进的定义。

## 4. 每份合同的固定元数据

`contract.md` 顶部必须维护以下字段；状态值使用本节规定的枚举，不能自由造词：

```yaml
contract_id: BC-001
title: PreparedRun
provider: B
consumer: C
contract_version: 1.0
contract_status: draft
provider_implementation: partial
consumer_implementation: not_started
verification_status: not_run
last_verified_commit: null
blockers: []
next_owner: B
next_action: 补齐字段映射并请求 C 评审
```

### 4.1 合同状态

`contract_status` 只允许：

- `draft`：提出方正在编写，尚未请求正式评审；
- `reviewing`：已请求对方评审，存在待回复项；
- `agreed`：双方已确认，尚未合并到 `develop`；
- `frozen`：双方确认且已合并到 `develop`；
- `superseded`：已被明确的新合同或新主版本替代。

### 4.2 实现状态

`provider_implementation` 和 `consumer_implementation` 分开记录，只允许：

- `not_started`；
- `partial`；
- `done`。

提供方完成 Schema、代码或夹具，不代表消费方已经接入。

### 4.3 验证状态

`verification_status` 只记录已取得证据的最高层级：

- `not_run`；
- `schema_passed`；
- `fixture_passed`；
- `integration_passed`；
- `real_environment_passed`。

文档审阅、模拟器、内存假实现和单元测试不能登记为真实宿主、真实文件系统或真实平台验收通过。

## 5. 对接流程

1. 从最新 `develop` 建立合同分支。
2. 在 `进行中/` 下创建 `<合同编号>-<主题>/contract.md`，状态为 `draft`。
3. 明确主责分册、FR/AC、提供方、消费方、输入、输出、异常、兼容和验证方式。
4. 提交 PR，指定对方评审；此时状态改为 `reviewing`。
5. 评审意见写入同一合同目录，结论必须回写 `contract.md`，不能只留在聊天或个人目录。
6. 双方逐项确认后标记 `agreed`；合并到 `develop` 后标记 `frozen`。
7. 双方分别实现，更新各自实现状态；不得把一方完成写成“对接完成”。
8. 使用双方真实产物做 Schema、夹具或集成对拍，登记命令、版本、提交号和证据位置。
9. 满足第 6 节条件后，整个主题目录从 `进行中/` 移入 `已完成/`，并同步本总台账。
10. 后续接口变更重新走第 1—9 步。破坏性变更提升合同主版本，并保留旧版追溯入口。

聊天只用于通知；合并到 `develop` 的合同、确认记录和可复核证据才构成正式对接材料。

## 6. 移入“已完成”的条件

同时满足以下条件才能移入 `已完成/`：

1. 合同状态为 `frozen`；
2. 提供方实现状态为 `done`；
3. 消费方实现状态为 `done`；
4. 至少达到 `fixture_passed`，且该夹具同时经过提供方生成或校验、消费方读取或校验；
5. 没有阻塞性未决项；
6. `last_verified_commit` 指向可复核提交；
7. `delivery.md` 如实区分已实现、静态/单元/合同检查、真实环境验收和未验证项。

合同冻结但尚未接线，或只有一方实现完成，仍留在 `进行中/`。

## 7. 裁定流程

当一个问题同时影响多个合同、主责分册互相冲突或没有唯一所有者时：

1. 在 `待裁定/` 新建一个 `DEC-*.md`；
2. 逐字引用冲突来源，列出受影响合同、选项、代价和推荐方，不把推荐写成既定结论；
3. 记录唯一裁定人或裁定角色及期望日期；
4. 裁定后记录结论、日期和确认人；
5. 项目文档只作为裁定依据，不在接口对接工作中修改；把结论及其项目文档依据同步到所有受影响的接口合同、Schema、夹具和测试；
6. 完成裁定结论的接口合同同步后移入 `归档/`，并在文件顶部标明裁定结论、依据和已同步的现行合同；尚未完成的代码、Schema、夹具或真实验证转记到对应合同的实现状态、阻塞项或下一动作，不能继续伪装成“待裁定”。裁定若实际改变现行字段或 Schema，则必须同步相应 Schema、夹具和测试后才能归档。

裁定记录本身不成为第二套接口合同。未同步正式合同的裁定不得标记“已裁定完成”。

## 8. 变更和兼容规则

- 已确认内容不静默覆盖；在变更记录中写明版本、原因、影响和迁移方式。
- 新增可选字段必须说明旧消费方行为，并补成功、失败和未知样例。
- 删除、改名、改变枚举或错误语义必须提升主版本并由双方重新确认。
- 未知枚举、未知状态和未知错误不得静默当成成功或空数据。
- 生成的 Schema 和夹具由其声明的所有者生成，不手工改生成物。
- 文件移动或重命名必须全仓更新引用，并运行断链检查和相关契约测试。
- 评审意见、个人设计和修改日志只能作为历史或输入，不能覆盖 `contract.md`。

## 9. PR 合并前检查清单

- [ ] 合同编号和目录唯一；路径中没有成员姓名。
- [ ] 已链接主责需求、功能或架构条款及相关 FR/AC。
- [ ] 提供方、消费方、字段所有者和 Schema/夹具所有者明确。
- [ ] 合同、双方实现、验证三个状态维度分别填写。
- [ ] 所有待确认问题都有编号、责任方和下一动作。
- [ ] 跨合同冲突已进入独立 `DEC-*.md`。
- [ ] 旧路径引用、相对链接、代码注释和测试夹具路径已更新。
- [ ] 已运行适当的 Schema、夹具或集成检查，并登记实际结果。
- [ ] 未把模拟或单元结果写成真实环境验收通过。
- [ ] 本页总台账已同步。
