# DEC-009：源码快照的修订语义（`InputRevisions.snapshot_revision` 到底该是什么）

状态：**已裁定并归档；候选方案不再生效**

提出日期：2026-10-03

提出方：B 包（项目与计划）

受影响方：A（快照端口与记录）、C（快照消费与运行事实）、D（"依据需重新准备"的展示）

裁定方：袁（项目负责人）

裁定日期：2026-10-03

影响合同：`AB-001` 第 11 节（`SourceSnapshot` 字段口径，含其第 11.5 节 **Q4**）；`BC-001`

## 1. 待裁定问题

`prepare_run` 的输入摘要比对里有一项 **`snapshot_revision`**，其失效提示写的是
"**source bytes changed**"。问题是：**这个修订号到底指什么？**

- 若指**快照记录的仓储修订**，实测**恒为 1**，于是"源码变了"**永远检测不到**；
- 若指**内容变化序号**，则它需要一套派生规则（谁递增、依据什么），目前**不存在**；
- 若不指修订号，则应改成比对**内容身份**（与 `case_revisions` 的观察比对同类）。

**三条路只能选一条**，否则该判定项要么恒不触发、要么语义含混。

## 2. 冲突依据（逐字引用，均可从仓库核实）

| 来源 | 原文 |
| --- | --- |
| `src/aitest/application/planning/prepare_run.py` 第 69 行 | `"snapshot_revision": "source bytes changed"` —— 该项的失效语义是"源码字节变了" |
| `src/aitest/application/planning/preparation.py` 第 392—400 行 | `changed_inputs()` 按**字段值**逐项比对：`getattr(previous, name) != getattr(current, name)` |
| `src/aitest/application/planning/preparation.py` 第 67 行 | `snapshot_revision: int`，且第 61—62 行要求"每一项都必须 `>= 1`" |
| `src/aitest/infrastructure/adapters/source_snapshot.py`（**A 的端口实现**） | 元数据字段为 `schema`／`snapshot_id`／`purpose`／`canonical_path`／`selected_paths`／`exclusion_rules`／`files` —— **没有 `revision`**；且注释写明"**内容寻址快照幂等：既有清单不可变，重复 pin 不覆盖**" |
| B 侧实现 `application/project/persistence.py` 的 `save_source_snapshot()` | 每次固定（pin）产生**新 `snapshot_id`**，其**记录仓储修订为 `@1`** |
| `tests/support/prepared_run_factory.py` 第 454 行 | 夹具用 `source_revision = 9` 表示"源码已变"，即现行测试**假定该值会随源码变化** |

## 3. 冲突点

`changed_inputs()` 比较的是**修订号的值**。而实测：

- A 的端口**不产生修订号**（内容寻址，同一 `snapshot_id` 不可变）；
- B 的快照记录**每次都是 `@1`**。

**因此**：同一逻辑源码发生变化 → 产生**新的 `snapshot_id`** → 但 `InputRevisions.snapshot_revision`
**仍是 1**，与上一次相等 → `changed_inputs()` **不报变化** → 第 3 步不判 `NEEDS_REPREPARE`。

**"源码变化须重新准备"这条要求在现行实现下无法触发**，而夹具里的 `source_revision=9` 只是**测试自己造的值**，
不代表真实链路会产生这个值。

**注意**：`PreparedRun.snapshot`（`SnapshotRef`）**已经带 `content_identity`**——
`AB-001` 第 11.3 节的算法使它**随源码内容变化而变化**。也就是说，
**"源码变了"这件事已经有可用的判据，只是没用在摘要比对里。**

## 4. 选项与代价

### 选项甲：`snapshot_revision` = 快照记录的仓储修订

- 做法：`prepare_run` 用 `save_source_snapshot()` 的返回值（当前恒为 `1`）填入 `InputRevisions.snapshot_revision`。
- 效果：字段值真实、可核对；**但"源码变了"永远检测不到**——与第 69 行的失效语义直接矛盾。
- 代价：必须在文档里把 `_INVALIDATION_DESCRIPTIONS` 的 `"source bytes changed"`
  改成别的说法（例如"快照记录被替换"），**等于承认这一项不覆盖源码变化**。

### 选项乙：`snapshot_revision` = 内容变化序号（**B 侧倾向**）

- 做法：保留 `snapshot_revision` 字段名与 `>= 1` 约束，但**把其值定义为"内容身份的观察序号"**：
  以项目内**该 `input_revisions` 组合首次出现**为 1，**每次 `content_identity` 变化即递增**；
  实现上可直接用"已记录的准备记录里该来源身份出现的次序"派生（与 B-11 的"按已记录条数派生"同一手法）。
- 效果：`changed_inputs()` **无需改结构**即可检出源码变化；第 69 行的失效语义**成立**。
- 代价：① 需要一条明确的派生规则与实现；② 该值不再是"记录修订"，
  容易与 `PreparedRun.snapshot` 的标识混淆，必须在合同里写清；
  ③ 属**准备身份语义变更**，C 需知悉（`PreparedRun` 外部字段不变）。

### 选项丙：**不再用修订号，改比对 `content_identity`**（与 `DEC-005` 同类手法）

- 做法：把该来源的"变化判据"从修订号改为**内容身份字符串**，作为**观察事实**参与
  `decide_preparation()` 的比对（`DEC-005` 已有先例：观察字段随记录落盘、可重建）；
  `changed_inputs()` 仍报 `snapshot_revision` 这个名字，便于既有提示不变。
- 效果：判据**直接就是内容**，最准确；与 `DEC-005` 的既有口径一致（观察结果不进摘要、只参与比对）。
- 代价：① `InputRevisions` 的**类型**要变（`int` → 内容身份字符串），或新增一个观察字段；
  ② 触及 `DEC-005` 刚定下的结构，需一并说明；③ 需要迁移既有记录。

## 5. B 侧倾向（**仅为建议，不作为结论**）

**倾向选项乙**：它**不改 `InputRevisions` 的结构与类型**，只固定一个派生规则，
就能让第 69 行的失效语义**真正生效**；代价最小、迁移量最小。

若裁定者更看重"判据必须就是内容本身"，则选项丙在语义上更干净，
但它要改 `DEC-005` 刚定的结构，需一并评估。

## 6. 阻塞影响

- **不裁定则**：`snapshot_revision` 的取值无从确定，B 侧无法把
  `prepare_run` 的该入参接真实来源（现在只有夹具自己在造值）；
- 若 B 与 C 各按一种理解实现，**"源码变化须重新准备"这一条在一边生效、另一边不生效**，
  会造成同一准备请求在两个入口得到不同判定——属跨包可复现的错误，不是风格问题。

## 7. 裁定结论

- 结论：直接比较快照 content_identity；snapshot_revision 保留为仓储读取修订。新增 observed_snapshot_content_identity 随准备意图保存和重建，不进入请求摘要；旧观察字段缺失不得当作相同内容。
