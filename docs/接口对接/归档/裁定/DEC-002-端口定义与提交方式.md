# DEC-002：端口定义归属与提交方式

状态：**已裁定并同步，归档记录**

提出日期：2026-09-28

整理日期：2026-09-30

提出方：B 包（项目与计划）

受影响方：A、B、C、D

裁定方：袁（项目负责人）

影响合同：`CORE-001`、`AB-001`、`AC-001`

## 1. 待裁定问题

`application/ports.py` 是外部能力端口的唯一归属文件，但业务分册又把
`SourceSnapshotPort`、`SourceControlPort`、`ModelProvider` 等端口列为 B 的端口。
目前形成“业务定义责任”和“文件提交责任”分离，需要确定谁写入、谁确认以及如何避免并行 PR 冲突。

附带需要明确：`Clock` 在项目与计划、存储与恢复两册重复列出；`ProjectionPort` 缺少明确主责位置。

## 2. 当前事实

- `application/ports.py` 当前由 A 维护公共端口文件。
- `WorkspaceUnitOfWork`、`RecordRepository` 已有基础签名，但 B 所需的准备登记语义尚未完全进入公共文件后端。
- `SourceSnapshotPort`、`SourceControlPort`、`ModelProvider`、`ProjectionPort` 仍缺完整方法合同。
- B 已在 `AB-001/contract.md` 提供签名与并发语义草案。
- A 在 `AB-001/review-A.md` 表示愿意采用部分草案，但主张继续由 A 独占写入 `ports.py`。

## 3. 备选方案

| 选项 | 做法 | 影响 |
| --- | --- | --- |
| 甲（B 原推荐） | B 按“只追加本包段落、不重排”方式修改 `ports.py`，A 评审 | 推进快，但需修改 B 的现行协作规则，且多人写同一文件仍有冲突风险 |
| 乙（A 当前建议） | 各包在合同中提需求，由 A 统一写入 `ports.py`，业务包评审签名 | 文件所有者唯一，但必须明确响应时限，避免调用方长期阻塞 |
| 丙 | 指定独立公共合同维护人，统一处理端口 PR | 权责清楚，但需要明确长期责任人和交接机制 |

## 4. 需要裁定的结论

1. `application/ports.py` 的唯一写入责任采用甲、乙还是丙。
2. 业务包如何提交签名草案、由谁确认业务语义、由谁确认基础设施可实现性。
3. 多包同时改端口时的合并顺序和冲突责任。
4. `Clock` 的唯一主责分册。
5. `ProjectionPort` 的唯一主责方。
6. `stage_preparation`、结构化冲突详情等能力属于一期还是后续迭代。

## 5. 裁定前约束

- 不在多个文件复制同名 Protocol。
- 业务包可以在合同中提交完整签名草案，但不得将草案描述为已生效端口。
- 应用用例不直接导入基础设施实现绕过端口。
- 已发布字段和语义的修改仍需合同版本与双方确认。

## 6. 裁定记录

裁定：**采用方案乙并增加阻塞升级机制。** `application/ports.py` 由 A 维护物理文件和合并冲突；业务包负责提交完整业务语义、签名草案、错误与兼容要求并评审最终签名，A 负责基础设施可实现性。属于当期的端口必须在当期冻结；A 无法及时维护时由项目负责人显式指定代维护人，不允许另建同名 Protocol。

补充结论：`Clock` 与 `ProjectionPort` 的唯一技术主责为总体架构第 12 节和 `application/ports.py`，业务分册只定义使用场景或策略；准备意图的同键同摘要复用、同键异摘要冲突以及 `intent_id` 与记录同次提交属于一期，允许由通用工作单元原语实现，不强制同名专用方法；结构化冲突至少必须提供机器可判定类别和当前修订，一期完成。
