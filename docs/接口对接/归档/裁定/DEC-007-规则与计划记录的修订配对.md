# DEC-007：`rule_draft` / `plan` 记录的「正文修订」与「仓储修订」是否必须一致

状态：**已裁定并归档；候选方案不再生效**

提出日期：2026-10-03

提出方：B 包（项目与计划）

受影响方：A（存储与索引）、C（消费用例与规则修订）

裁定方：袁（项目负责人）

裁定日期：2026-10-03

影响合同：`AB-001`（保存语义）；`BC-001`（`PreparedRun.case_revisions` / `rule_versions` 的引用方式）

## 1. 待裁定问题

`case` 与 `acceptance_scope` 两类记录已按检查项 **B-11** 强制一条不变量：

```
正文里的 revision == 这次分配的仓储修订 == (expected_revision or 0) + 1
```

**`rule_draft` 与 `plan` 要不要适用同一条不变量？**

## 2. 冲突依据（逐字引用）

| 来源 | 原文 |
| --- | --- |
| `docs/一期工程检查-B包.md` 第 3.1 节 B-11 | "合法Case.revision=9被保存为仓储修订1、2；准确读取@1/@2均返回Case@9，正文与记录修订不一致……**补新建/更新/重复旧修订及Scope/规则同类路径验证**" |
| 同上 B-11 完成条件 | "B保存时核对或分配权威新正文修订，准确读回验证内容身份；**拒绝旧修订/跳号错配**" |
| `src/aitest/application/planning/portable.py` 第 158—163 行（现行实现） | `import_rule_payloads()` 按文件里的 `revision` **原样还原**草稿修订号（`revision = payload.get("revision")`，只校验 `>= 1`） |
| `docs/文档-feix-a/B包/02-B包施工检查项清单.md` 第 35.2 节（现行口径） | "**无法逐字节往返**：`unknown_extension_fields`……在 Markdown 里没有约定的转义规则，导出再导入会丢信息"——即可携带格式的设计目标是**保真** |
| 检查文档 B-14 完成条件（现行实现） | 发布核对的是**调用方声明的 `rule_version` 仓储修订**，与 `draft.revision` 无强制相等关系 |

## 3. 冲突点（**已实测，不是推断**）

**实测（2026-10-03，真实文件存储）**：

```
save_rule_draft(RuleDraft(revision=9), expected_revision=None)
  → 记录仓储修订 = 1，payload 里 revision = 9
```

即 `rule_draft` 存在与 B-11 反例**完全相同的现象**。但同一份证据里存在两条相反的要求：

- **要求甲**（检查文档 B-11 完成条件）：拒绝"旧修订/跳号错配"，则 `rule_draft` 也应强制不变量；
- **要求乙**（可携带格式的设计目标 + 现行导入实现）：导入应**保真外部规则包里的修订号**。
  外部包写 `revision: 9` 时，若强制"仓储修订 1 ⇒ 正文必须是 1"，
  要么拒绝导入该包，要么把外部编号改写成 1——**两者都破坏了保真**。

**同时满足不了**：`rule_draft.revision` 既是"草稿的第几版"（本地编排语义），
又被当作"外部规则包的版本号"（导入保真语义），两个语义共用一个字段。

`plan` 记录同类：`publish_plan` 的 payload 修订来自计划对象，仓储修订是独立序号。

## 4. 选项与代价

### 选项甲：`rule_draft` / `plan` 也强制不变量；导入时**显式映射**外部修订号

- 做法：`save_rule_draft` / `publish_plan` 加同一条不变量校验；
  导入路径增加"外部规则修订号 → 本地编排修订"的映射规则（例如按导入顺序重排为 1..n，
  并把外部原编号存入一个**新字段**如 `source_revision`）。
- 代价：① 需要**新增字段**（跨包字段变更，走完整流程）；
  ② 同一份外部包在不同工作空间导入会得到不同本地修订号，
  "同一规则在两个实例是否同一版"需要靠新字段比对；
  ③ 与"可携带格式保真"的表述需要重新解释。

### 选项乙：保持现状，只在**文档与边界**上收紧（**B 侧倾向**）

- 做法：
  1. `rule_draft` / `plan` **不适用** B-11 不变量，理由写进文档（本节与检查项清单第 38 节）；
  2. 明确**"按什么读回"的口径**：这两类的读取以**仓储修订**为准（`record_id + revision`），
     payload 里的 `revision` 是**草稿/计划的版本号**，不承诺与仓储修订相等；
  3. 在 `save_rule_draft` / `publish_plan` 的 docstring 里写明这一区别，
     避免调用方按"正文修订"去读记录（这正是 B-11 反例里发生的事）；
  4. 补一条回归测试：**锁定"仓储修订 ≠ 正文修订"在这两类上是可预期的行为**，
     使将来任何人改这两处的语义时都会先撞到这条测试。
- 代价：① 两类记录仍存在"记录 `@N` 里是正文 `@M`"的形态，
  靠文档与测试说明而不是靠不变量拦住；② 检查文档 B-11 的"规则同类路径验证"只能
  以"已验证并如实登记差异"结项，而不是"已统一"。

## 5. B 侧倾向（**仅为建议，不作为结论**）

**倾向选项乙**，理由是它不动字段、不破坏导入保真，且**把真实差异写成了可执行的约束**
（测试 + docstring），而不是留一个说不清的状态。

若裁定选甲，B 侧需要先得到"外部规则修订号如何映射到本地编排修订"的明确规则，
否则无法实现——这也是把本项提交裁定的原因。

## 6. 阻塞影响

- 不裁定则：`rule_draft` / `plan` 的修订语义一直无法在文档中写死，
  检查文档 B-11 的"规则同类路径"只能挂着；
- 若两边（B 与 C）各按一种理解实现，`PreparedRun.rule_versions` 引用的修订号会与
  实际记录对不上——**这是跨包可复现的错误**，不是风格问题。

## 7. 裁定结论

- 结论：保留正文版本与仓储修订的区别；读取、乐观锁及冻结引用使用仓储修订。发布结果明确携带 record_revision，正文 revision 不被重写。
