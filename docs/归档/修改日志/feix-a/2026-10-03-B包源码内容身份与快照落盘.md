## 3 两条关键设计决定

### 3.1 `content_identity` **不包含**什么（§11.3 第 3 条，逐条落到测试）

| 不参与计算的字段 | 理由 |
| --- | --- |
| `mtime_hint` | 只作变化提示，永不参与身份（§11.3 明文） |
| `source_scope`、`exclusion_rules` | 它们是**范围声明**，其影响已体现在"哪些文件在清单里"；若算进身份，同一批文件只因范围描述不同就会得到两个身份，与"内容身份"的语义不符 |
| `refetch_dependencies`、`refetch_scope` | 描述"能不能再取到"，不是"内容是什么" |
| `snapshot_id`、`purpose` | 同一内容的两次固定应得到同一**内容**身份 |

### 3.2 读回时**重算并核对**内容身份

`load_source_snapshot()` 用读回的 payload 重算身份，与记录里存的比对，不一致即报错。
这样"记录里的身份"与"记录的字节"不可能长期分叉——调用方不会拿一份自相矛盾的依据去做核对。

### 3.3 漂移核对为什么不用 `query()`

`RecordReader` 协议虽有 `query`，但其可用性取决于实现（查询走索引，需先建索引；
内存替身与真实存储行为不同）。核对链要能在任何合规的 `read()` 实现上工作，
因此"取最高存在的修订"用 `read()` 从 1 逐个探测（记录只追加，读到第一次读不到即止，
并有上限保护）。
