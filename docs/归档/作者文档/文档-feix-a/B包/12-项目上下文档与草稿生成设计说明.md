## 2 缺口：本模块最重要的一条

需求 P1-AC17 原文：

> 上下文缺失时**列出缺什么并保持阻塞，不编造依赖和结论**。

因此本模块**没有"猜一个默认值"的分支**。缺口分为两级，**不可混同**：

| 级别 | 取值 | 含义 | 典型场景 |
| --- | --- | --- | --- |
| **阻塞** | `blocking=True` | 上下文不完整，**不得继续准备或执行** | 无模块、无依赖登记、无环境、环境缺载体 |
| **提示** | `blocking=False` | 可在报告中声明，**不阻塞** | 盘符类型无法核实（`DriveKind.UNKNOWN`） |

**为什么必须分两级**：需求 P1-FR07 明说"未执行"不等于"不适用"，
架构文档第 1 节又说 `DriveKind.UNKNOWN` 由调用方决定是否阻塞。
把"无法核实"一律当阻塞会误伤可用场景；一律放行又会漏掉真实缺口。

### 2.1 一条容易搞反的规则

> **有模块但没有登记任何依赖边 → 阻塞缺口。**

需求 P1-FR03 异常分支原文：**"映射缺失不能解释为没有影响"**。
即："没登记依赖"**不等于**"没有依赖"，不能据此判定"无影响"。
因此这是**阻塞**缺口，而不是"无依赖、可继续"。

### 2.2 `ContextGap` 的构造期不变量

`kind` / `subject` / `detail` 非空；**阻塞级 `kind` 不得把自己声明为非阻塞**
（`blocking=False` 直接 `ValueError`）——防止下游用一句 `blocking=False` 绕过阻塞。

## 3 三处硬约束的落点

| 约束 | 落点 | 测试 |
| --- | --- | --- |
| **非 Git 目录不构成拒绝理由**（P1-AC25） | `create_project()` 与绑定形态无关；`plain` 是**一等绑定** | `test_project_without_a_git_repository_is_accepted`、`test_plain_binding_is_a_first_class_binding` |
| **同步盘/网络盘拒绝建立并说明原因** | `create_binding()` 返回 `BindingResult(rejection=...)`，**不是布尔** | `test_network_drive_is_rejected_with_a_reason`、`test_sync_folder_is_rejected_with_a_reason` |
| **模板只生成草稿** | `GeneratedContent.status` 恒为 `draft`，构造期拒绝其它取值；本模块无发布路径 | `test_generated_content_cannot_be_published` |

### 3.1 路径判定必须用 `PureWindowsPath`

`path_is_canonical_absolute()` 用 `PureWindowsPath` 而**不是** `pathlib.Path`：
后者在 Linux 上是 `PosixPath`，会把 ``C:\work`` 判成相对路径，
**同一份代码在 Windows 与 Linux 上结论不一致，且 Windows 本地测不出来**（只有 CI 能抓）。

**实测发现的一个细节**（已写进测试）：`PureWindowsPath` 会把单独的 `.` 段**规范化掉**，
因此 ``C:\work\.\here`` 与 ``C:\work\here`` 是同一个规范路径，**不是**非法路径。
`..` 段则保留，因此仍被拒绝。

## 4 草稿生成与定向失效

### 4.1 `RevisionContext`：记录**实际依赖**的修订集合

架构文档第 9 节要求生成内容"按实际依赖修订集合与生成策略版本，依赖变化**定向失效**"。

| 字段 | 说明 |
| --- | --- |
| `project_revision` / `binding_revision` | 必填 |
| `template_revision` | 必填（模板版本是字符串，如 `1.0.0`） |
| `environment_revision` / `source_revision` / `rules_revision` | **可选**；`None` 表示该类来源**不适用** |

**`None` 是"不适用"，不是"未知"**：`draft_expiry()` 对 `None` 的来源**不做比较**。
把"不适用"记成"未知"会让每次来源变化都误判为过期。

### 4.2 `apply_template()` 的三条行为

1. **缺口非空 → 不生成草稿**，原样返回缺口（不编造检查内容）。
2. **成功 → 产出 `GeneratedContent`**，`status` 恒为 `draft`。
3. **不提供覆盖既有草稿的入口**：再次生成须传入递增的 `content_revision`，
   得到**新对象**；人工修订过的旧草稿按原修订保留（架构文档第 3 节）。

### 4.3 `draft_expiry()`：只列**实际变化**的那几项

返回变化来源名的元组，**未变化的来源不出现**，因此未变部分仍可复用
（架构文档第 9 节："仅重新生成受影响草稿；未变部分可复用"）。

### 4.4 模板读取走 `importlib.resources`

`load_template()` **按准确版本**读取 `<template_id>/<version>.json`，不返回"最新版本"。
`list_templates()` 列出安装后的全部版本，按 `(template_id, version)` 排序。

> 发布布局是单文件而非架构文档第 3 节描述的 `manifest.json` + 子目录，
> 该不一致早已登记为 D-01（以代码为准），本次沿用既有布局，**未改目录结构**。

`cli.py` 里原本有一段等价的模板列表逻辑（属 D 的 `interfaces/` 目录），
**本次未改它**；`list_templates()` 是它可改用的公共实现。是否改由 D 决定。
