## 一、测试范围与环境

### 1.1 环境

| 项 | 值 |
| --- | --- |
| 操作系统 | Windows 11 x64 |
| 宿主 | TraeCode CN 3.3.102 |
| 插件 | `aitest-trae.vsix` 0.4.10（本地构建） |
| 核心解释器 | Python 3.13.3（仓库开发虚拟环境，可编辑安装） |
| 被测项目 | 自建最小纯函数样例 `py-lib-sample/main.py` |

### 1.2 覆盖的链路

按《可用版本交付路径》所列主线逐项执行：

1. 安装扩展、打开工作区、配置解释器与用户数据工作空间；
2. 新手向导：选择项目与测试入口、填写测试目标、登记测试环境、核对四项检查、发布计划、分析源码、准备并登记运行；
3. 逐用例执行：解析操作、受控授权、执行、独立核验；
4. 保存报告、读取报告修订、导出 Markdown 摘要与证据包；
5. 完全退出宿主后重新打开，读取已保存的运行与报告。

### 1.3 关于被测样例

仓库内 `examples/python_library/sample.py` 仅含被调用的函数定义，无测试入口、无 JSON 输出，不能直接用于向导。本次另建样例，仅依赖标准库，向标准输出打印一个 JSON 对象，字段与向导四项检查一一对应：

```json
{"loaded": true, "normal": 5, "boundary": 0, "error": "TypeError"}
```

## 二、总体结论

主链路可以跑通。项目建立、计划发布、受控执行、证据采集、独立核验、报告生成与导出均能完成，并经数据侧复核确认。

但在首次使用与重启恢复两个环节存在阻断性问题，另有若干影响可理解性与可操作性的缺陷。共记录 10 项问题，按影响程度分为三级：

| 级别 | 数量 | 说明 |
| --- | --- | --- |
| 阻断 | 1 | 新环境首次保存项目必然失败，无界面提示可循 |
| 严重 | 2 | 重启后问题与报告查询失败；报告重存产生独立文档而非新修订 |
| 一般 | 7 | 默认配置过期、界面不可读、失败后无法重来等 |

## 三、问题清单

### 问题 1（阻断）向导工作空间路径过深，首次保存项目必然失败

**现象**
向导完成环境准备后，执行"保存项目并继续"，面板提示"这一步尚未完成"，真实报错为：

```
[Errno 2] No such file or directory:
...\globalStorage\aitest-local.aitest-trae\projects\guided-<uuid>\workspace\indexes\business\...
```

**根因**
向导将项目根目录固定在扩展全局存储下，路径本身已达 228 字符；索引目录在其下再增加 `business/<64 位十六进制>/<64 位十六进制>.json` 两级，单文件完整路径达 298 字符，超过 Windows 默认 `MAX_PATH`（260）。本机 `LongPathsEnabled` 为 0，故文件无法创建，上层报 `ENOENT`。

| 度量 | 值 |
| --- | --- |
| `indexes/business` 目录路径长度 | 228 字符 |
| 索引叶文件完整路径长度 | 298 字符 |
| Windows 默认上限 | 260 字符 |
| `HKLM\SYSTEM\CurrentControlSet\Control\FileSystem\LongPathsEnabled` | 0 |

**影响**
开启长路径支持前，任何新用户首次保存项目均失败；错误信息不含路径超限提示，用户无法自行判断原因。

**建议**
将项目根目录改置于较短路径（如 `%LOCALAPPDATA%\aitest\<短标识>`）或允许用户指定；缩短索引目录层级；在路径超限时给出明确提示而非 `ENOENT`。

**备注**
本次将 `LongPathsEnabled` 置为 1 并完全重启宿主后，同一流程一次通过。该结论可复现、可对照。

---

### 问题 2（严重）重启后问题与报告查询失败，且无重建入口

**现象**
完全退出宿主并重新打开后，运行概览、结论与四个用例均可正常恢复；但在"问题与报告"页读取报告修订时返回：

```
B_INDEX_MAINTENANCE_REQUIRED: the query index is missing or stale; rebuild it before querying
```

**根因**
各查询索引目录的提交进度不一致：

| 索引目录 | commit_id |
| --- | --- |
| `records-*`、`reports`、`reports-byid`、`latest-keys` | 227（与当前提交一致） |
| `issues` | **0**（自建立后从未推进） |

问题（issues）索引停留在初始状态，与查询根不一致，查询被判为"索引缺失或过期"。空索引族未被正确初始化，导致"没有问题时本应返回空列表"的情形变为报错。

**影响**
交付主线第 6 步"退出并重开，继续读取与受控恢复"部分失败：运行事实可读，问题与报告不可读。

**缺失**
界面与 CLI 均未提供"重建索引"入口（`aitest` 仅有 `doctor`、`dispatch`、`templates`、`python-carrier`、`ensure-core`、`mcp-relay` 六个子命令），用户无法自行恢复。

**建议**
修正空索引族的初始化与推进逻辑；在界面提供受限的索引维护操作；至少应返回空结果而非报错。

---

### 问题 3（严重）同一运行重复保存报告，产生独立文档而非递增修订

**现象**
补做核验后重新保存报告，报告中出现两个并列条目，内容修订号均为 1：

| 报告标识 | 业务结论 | 已执行 | 有效验证 | 内容修订 |
| --- | --- | --- | --- | --- |
| `report-e87cbb85…` | 未完成 | 4 | 3 | 1 |
| `report-e0909970…` | 通过 | 4 | 4 | 1 |

**根因**
报告标识由业务意图派生（`report-<intent>`），每次新意图产生新的报告实体，正文修订号始终为 1。

**影响**
"报告为不可变快照、其历史以修订递增"的设计未真正落地。用户无法从列表判断哪一份为最新，也无法看出同一运行从"未完成"到"通过"的演进。

**建议**
报告标识按运行标识固定，正文变化时递增内容修订；意图去重键与业务标识分离。

---

### 问题 4（一般）模型名称默认值已停用

**现象**
向导与设置页的模型名称默认值均为 `deepseek-chat`。

**依据**
DeepSeek 官方公告（2026-04-24）载明：`deepseek-chat` 与 `deepseek-reasoner` 两个模型名自 2026-07-24 起停止使用。官方现行模型为 `deepseek-flash` 与 `deepseek-v4-pro`。

**影响**
采用默认值将导致模型调用失败；该问题无法从代码审阅中发现，仅在真实调用时暴露。

**建议**
更新默认值，并考虑在模型不可用时不阻断人工填写路径。

---

### 问题 5（一般）报告显示"未完成"但不给出原因与缺口

**现象**
业务结论为"未完成"时，报告页的"未完成原因"为空白，"首要缺口"显示"未提供"。

**依据**
同快照数据中，缺口列表为空、决定性失败为空、首要缺口为 null，而有效验证数为 3、必测数为 4。即"未完成"仅由计数差值产生，未转化为可读原因。

**影响**
报告的核心价值在于说明"为何未通过、应补什么"。当前仅给出结论，用户无法定位待补项。

**建议**
将"必测但未取得有效验证"的用例列入缺口，并在报告中指名。

---

### 问题 6（一般）工作台不展示核验结论

**现象**
点击"核验这次执行结果"后，界面仅提示"核验请求已返回"，刷新后仍不显示核验结论。

**依据**
工作台仅渲染三项：步骤状态、本次尝试、依据。核验结论（匹配 / 不匹配 / 无结果）只存在于核心记录中。

**影响**
用户完成核验后无法从界面确认是否通过，只能借助报告间接判断。

**建议**
在"依据"之下增加"核验结论"一项，不匹配时列出差异字段。

---

### 问题 7（一般）用例列表仅有编号，无名称

**现象**
工作台左下角列表显示为"用例 1 · 必测""用例 2 · 必测"等，不显示用例目标。

**影响**
四个用例对应加载与语法、正常输入、边界输入、异常输入，预期结果各不相同。用户在补做核验时无法判断应操作哪一个。本次定位缺失用例须依靠核心记录反查。

**建议**
显示用例目标或检查类型，如"用例 4 · 加载与语法 · 必测"。

---

### 问题 8（一般）向导失败后无法重新开始

**现象**
向导失败后再次点击"开始第一次测试"，界面回到同一失败状态。

**根因**
向导对象在面板脚本加载时创建一次，按钮仅切换视图，不重建向导；界面亦未提供"放弃当前向导"入口。

**影响**
用户须完全重启宿主才能重新开始，且残留的半初始化工件不会被清理。

**建议**
提供"重新开始"与"清理失败现场"入口，或在新一次选择项目时自动重置。

---

### 问题 9（一般）重启后不自动恢复上次运行

**现象**
重启后进入面板，概览全部显示"尚未读取"，须依次点击"刷新本次视图""读取运行详情""打开本次工作台"方可见内容。

**影响**
"继续上次测试"场景下，用户易误判为数据丢失。

**建议**
检测到既有运行时自动读取一次，或在概览直接显示最近一次运行摘要。

---

### 问题 10（一般）导出后不指明产物位置

**现象**
导出成功后提示"可在诊断中查看制品位置"，但面板内未发现可到达"诊断"的入口。

**实际位置**
```
<用户数据工作空间>\artifacts\reports\<report_id>\
    markdown_summary-<摘要>.md
    evidence_bundle-<摘要>.zip
```

**建议**
在导出完成提示中直接给出可点击的绝对路径，或提供"打开所在文件夹"。

## 五、使用体验

### 5.1 确认次数与节奏

每个用例需经历"查看操作—确认授权—执行—刷新—核验"五步，其中"查看将执行的操作"属只读语义，仍会触发核心原生确认窗口。四个用例合计约 16 次点击、8 次以上确认窗口，每次确认限时两分钟。

对首次使用者，确认频次本身可以接受（符合"每个副作用单独授权"的设计），但以下两点增加负担：

- 只读的"查看"动作也要求确认，与"一次确认对应一次副作用授权"的心理预期不一致；
- 确认窗口正文为完整命令 JSON，中文摘要位于首行，信息密度过高，普通用户难以据此判断操作影响。

### 5.2 界面可理解性

向导阶段的引导文字清晰，四项检查的填写说明含示例，可用。主要困难集中在核验之后：

- 核验结论不可见（问题 6）；
- 用例无名称（问题 7）；
- 报告"未完成"无原因（问题 5）；
- 报告查看为两步操作，但界面未提示第二步；修订条目以纯文本呈现，不易识别为可点击元素。

### 5.3 失败后的可恢复性

向导失败时，界面提示为固定文案，不区分超时取消、参数错误与被拒绝；真实错误显示在另一处状态行，两者分离。加之无法重来（问题 8），首次使用者容易停留在无从下手的状态。

### 5.4 值得肯定的部分

- 全链路可在不依赖模型的情况下完成，人工填写路径可用；
- 计划、依据确认、动作授权、执行、独立核验为不同事实，界面上分列清晰；
- 证据链完整可回溯：从报告可逐项追到核验记录、标准输出与来源证据，且导出产物与记录一致；
- 重启后运行事实与判定可正确恢复，未出现重放或伪造结论。

## 七、建议的处理顺序

1. 问题 1（路径过深）：影响全部新用户，优先处理；
2. 问题 2（索引未推进）：影响重启后的可用性，与既有 issue #101 同类；
3. 问题 3（报告标识）：影响报告历史与演进追溯；
4. 问题 5、6、7（可理解性）：影响用户能否独立完成与自查；
5. 问题 4（默认模型名）：改动小，建议一并更新；
6. 问题 8、9、10（可用性）：可随后续面板优化统一处理。
