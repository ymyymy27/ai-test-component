### D1 能力快照形状

**冻结值**：只保留一套完整形状，采用方案 §3.8，不采用 §10 的短形状。

```json
{
  "backend": ["django"],
  "router": ["drf"],
  "auth": ["jwt"],
  "frontend_calls": ["axios-template"],
  "services": ["backend", "frontend"],
  "dependencies": [
    {"type": "redis", "level": "D1", "source": "docker-compose", "status": "detected"}
  ],
  "external_systems": [
    {"type": "smtp", "level": "D3", "source": "config", "status": "unknown"}
  ],
  "hosts": ["browser"],
  "level": "T1",
  "unknowns": ["frontend_wrapper"],
  "unsupported": ["drf_custom_action"],
  "source": "runtime",
  "evidence": ["GET /openapi.json", "tasks/urls.py:7"],
  "fingerprint": "sha256:...",
  "generated_at": "2026-11-26T12:00:00+08:00"
}
```

- `level`：`T1|T2|T3|T4`。T1 = 运行时路由/schema + 认证 + 不变量 + fixture；T2 = 有 OpenAPI/Swagger 可导入；T3 = 只有静态事实；T4 = 明确不支持。
- `dependencies[].level` / `external_systems[].level`：`D1|D2|D3|D4`。
- `source`：`static|runtime|mixed`。
- `fingerprint`、`generated_at` 可选；其余字段必填，空值用 `[]`。
- 新写入必须写 `fingerprint`；旧计划缺失时按 canonical JSON 计算临时值，不写回。
- `fingerprint` 只覆盖稳定字段（backend/router/auth/frontend_calls/services/dependencies/external_systems/hosts/level/unknowns/unsupported/source/evidence）与 `DiscoveryResult.facts` 的稳定键（routes/api_routes/services/auth/framework/frontend_calls），不含 `generated_at`、`fingerprint` 自身、测试摘要或源码片段；同一事实重复发现不触发重新确认。
- `project.discover` 返回的 `capabilities`/`facts` 在落盘或传给 `plan.generate` 前脱敏；不写凭据正文、Token、Cookie。
- `unknowns`、`unsupported` 不允许当“已覆盖/已通过”。
- 画像随计划保存到 `Plan.capabilities`；不建独立画像服务、数据库、常驻缓存进程。

**影响**：`models.py`、`models` 关联的 schema、面板 `dto.ts/map.ts`、报告、`tests/contract/`。

### D4 AI 决策写回路径

**冻结值**：AI 预期/评审决策放进 `run.start` 的 payload，原子写入 `Confirmation.ai_decisions` 与 `Run.ai_decisions`；不新增 `plan.decide`，不改计划 revision，不在确认页先写计划。

```json
{
  "expectations": [
    {"expectation_id": "aie_...", "decision": "confirmed|rejected", "reason": ""}
  ],
  "reviews": [
    {"review_id": "air_...", "decision": "accepted|rejected", "reason": ""}
  ]
}
```

- `plan.ai_expectations[].status` 在 `plan.generate` 时只写 `suggested`；`confirmed/rejected` 是保留值，当前主流程不写回计划。
- `plan.ai_reviews[].status` 在 `plan.generate` 时只写 `pending`；`accepted/rejected` 是保留值，当前主流程不写回计划。
- 本次运行的有效状态 = `Run.ai_decisions` 优先，计划字段只作生成时快照。
- `run.start` 只接受计划中存在的 `expectation_id`/`review_id`；未知 ID、重复 ID、非法 decision 返回 `INVALID_REQUEST`，不创建确认/运行记录。
- `plan.generate` 在用例生成后按 `item_id` 绑定 `case_id`；只有该验收项恰好一条可绑定用例时才写，多个候选保持 `null`，只展示不执行。
- `run.start` 生成运行快照时，把 `decision=confirmed` 且 `case_id` 非空的 AI 预期写入快照 Case 的 `frozen_expectation`，同时把 `expectation_verified` 置为 `true`、`expectation_source` 追加“用户确认 AI 建议”；`rejected` 或 `case_id=null` 不写。计划文件不变，运行快照是本次执行依据。
- 决策不是启动前置：未决策的 AI 建议保持 `suggested/pending`，对应用例只能“预期未证实”，不进入通过。
- 评审决策只记录采纳/驳回与理由，不自动改计划或用例；需要改计划时走 `plan.update` 生成新 revision，再重新确认。
- `plan.update` 改 cases 时：重算 `coverage_ledger`，清空 `ai_expectations`/`ai_reviews`（避免悬空引用），`recipes` 保留为生成历史；新 revision 必须重新确认。
- `run.start` 确认指纹加入 `ai_decisions` 的 sha256；决策变化必须重新确认；复用确认记录时，`Run.ai_decisions` 取复用记录，不重新决策。
- 报告从 `Run.ai_decisions` 汇总，不重新解释计划字段。
- 面板计划页展示 `suggested/pending`，确认页做可选决策，结果/报告展示本次决策。
- 不提供用户可见的 `ai.mode` 开关；`legacy|assist|off` 只允许作为后端内部配置，默认 `assist`。

### D5 服务启动与依赖安装范围

**冻结值**：事实采集阶段默认不启动服务；执行阶段只有显式许可才启动/安装。

- `project.discover`：
  - `allow_service_start` 默认 `false`；为 `false` 时只读静态 + 探测并复用已健康服务，不启动新服务。
  - 为 `true` 时在没有健康服务的情况下临时启动，采集后停止；停止放在 `finally`，取消/超时也执行；只停止本次启动的服务，复用服务不停止。
  - `keep_running` 默认 `false`；只有显式 `true` 才保留。
  - 不在发现阶段安装依赖；缺依赖记 `unknown`。
  - 启动/读取失败不回错误码，回退静态并返回 `degraded=true`、`degrade_reason`；只有参数非法返回 `INVALID_REQUEST`。
  - 复用现有服务启动/健康检查/停止实现；为避免命令层反向依赖 worker，S2a 先把该实现抽到 `runners/service_lifecycle.py`，worker 与发现共用。
- `run.start`：
  - `allow_service_start` 默认 `false`。
  - `allow_dependency_install` 默认 `false`。
  - 两个标志和 `plan.capabilities.fingerprint` 都进入确认指纹。
  - 指纹算法变化后，旧确认记录不可复用；首次升级需要重新确认一次，旧记录保留只读。
- worker：
  - 不再默认自动检测/安装依赖、不再默认启动服务。
  - 已有健康服务可复用，`service_started=false`；复用/未启动用 `preflight.reused_services` 区分。
  - `service_name` 仍列出本次配置涉及的服务名，不表示已启动。
  - 配置了服务但未许可启动时：依赖服务的用例进入 `incomplete`（原因 `blocked`），不判产品失败。
  - 未许可安装且依赖缺失时：`dependency_install_ok=false`，依赖用例进入 `incomplete`（原因 `blocked`），不判产品失败。
  - `services.reset` / 重启只对“本次运行启动且许可启动”的服务执行。
- 现有真实服务测试必须显式传许可；默认路径测试断言“不启动”。

### D6 AI 假设与旧失败分析的关系

**冻结值**：`Run.ai_hypotheses` 是新结构化字段；`Analysis.candidate_causes` 只读兼容。

```json
[
  {
    "case_id": "c_...",
    "hypothesis": "可能是脚本未等待异步任务完成",
    "evidence": ["output_tail"],
    "confidence": "high|medium|low",
    "next_check": "增加等待后重跑"
  }
]
```

- `judge_failure` 返回 `{hypotheses, rationale, confidence}`，不再返回 `verdict`；`hypotheses` 元素符合 `AIOutput(kind=hypothesis)`。
- `RunCase.judgement` 保留 `verdict`，但由 `core/judge.py` 确定性规则计算；形状为 `{verdict, reason, evidence_basis, hypothesis_refs}`，`hypothesis_refs` 指向 `Run.ai_hypotheses` 下标或 id。
- `inconclusive` 映射为 `incomplete`（原因 `unknown`），不再映射为 `blocked`。
- `RunCase.result` 保持执行事实 `failed`，`confidence_tier=suspected`；`core/verdict.py` 的验收项/业务结论把 `failed+suspected` 收敛为 `incomplete`（unknown），不写 `blocked`，报告用例明细仍显示 failed/suspected。
- `coverage.failed` 只计 confirmed 失败；suspected 计入 `incomplete`，避免把未证实失败算成产品失败。
- `blocked` 只用于环境、服务、依赖、前置未满足。
- 可信度只在 `core/judge.py:compute_case_confidence` 计算一次；worker 和报告只读取。
- 旧运行有 `analysis.candidate_causes` 时只读展示；新运行不再写入该字段。

### 1.3 状态与四值

| 细状态 | 业务四值 | 触发条件 |
|---|---|---|
| `blocked` | `incomplete` | 服务/依赖/前置未就绪 |
| `unsupported` | `incomplete` | 插件没有该能力，但验收项适用 |
| `uncovered` | `incomplete` | 有能力但本次未覆盖 |
| `unknown` | `incomplete` | 证据不足，无法判定 |
| `error` | `incomplete` | 脚本/执行错误，可修 |
| 断言失败且确定性成立 | `failed` | 断言与验收项一致，无环境/脚本/依赖异常 |
| 执行完成且断言通过 | `passed` | 证据齐全、预期已证实 |
| 验收项本身不适用 | `not_applicable` | 只能用于“不适用”，不能掩盖能力缺口 |

`inconclusive` 不再作为业务状态；只作为 AI 假设的置信描述。
