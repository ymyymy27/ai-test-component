## 第 0 节：目标分层、代码实测基线与已落地能力对账

### 0.1 核心目标、优先级分层与两种“新问题”分离

> **总目标**：在声明支持的能力与本次验收范围内，给出**可信、可核对、不夸大**的结论，并实现开箱顺畅的高效体验。

| 层级 | 目标 | 可验收定义 |
| :--- | :--- | :--- |
| **核心结果（P0）** | **不误测** | 声明支持范围内 `false_pass = 0`；环境/前置问题不判产品失败；弱断言与未核对预期不发布 |
| **结果质量（P1）** | **覆盖透明** | 每个验收项有确定性覆盖账本；未覆盖/不支持显式列出；不承诺绝对“不漏” |
| **默认路径约束（P1）** | **插件级** | 发现与概览体检默认严格只读（不启动服务、不装浏览器、不跑容器、不新增后台守护进程）；运行期仅经人显式确认后启声明服务 |
| **实现策略（P2）** | **复用经济** | 协议/成熟引擎/项目自带测试优先复用；重型依赖不进默认包 |

优先级原则：**不误测 > 覆盖透明 > 插件级（默认路径约束） > 多复用**。每条通过结论必须同时具备四要素：**证据**（请求/响应/日志/截图）、**范围**（`S/M` 与未覆盖清单）、**来源**（`invariant`/`recipe`/`model`/`explicit` 与事实来源）、**未知**（`unknowns`/`unsupported`）。

#### 两种“新问题”严格分离与停止收敛规则

| 类型 | 含义 | 处理策略 |
| :--- | :--- | :--- |
| **被测项目的新缺陷** | 插件在真实施测中发现的目标产品真实 Bug | **产品核心价值**，召回越准越好 |
| **插件自身的新缺陷（C1 / C2 / C3）** | `C1 correctness`（假通过/误失败/误阻塞/结论错）、`C2 coverage`（未识别/未覆盖）、`C3 UX`（面板/报告交互摩擦） | **本方案收敛对象** |

- **类级沉淀与停止规则**：所有新发现遵循 `发现 → 归类（C1/C2/C3） → 最小 fixture 复现 → 类级修复（adapter / 红线 / 不变量） → 固化进 Fixture Zoo → Portfolio 回归`；连续 **3–5 个新项目**不再产生新的 `C1` 类、只出现 `C2`（新栈未覆盖）时，说明体系已收敛，停止为单个项目改动核心判定逻辑。

### 2.1 五层架构蓝图（事实、生成、约束、验证、复用解耦）

```text
1. 事实层（确定性主导，不猜）
   ├─ 默认只读：代码图 + 路由/契约静态提取 + Git diff + 复用已运行服务 + 体检快照
   └─ 显式升级：运行时内省（OpenAPI / DRF resolver / Flask url_map / Express router）+ 可选流量探针
2. 生成层（确定性不变量生成器打底 + AI 补业务与增强）
   ├─ 确定性不变量与场景生成器（纯 Python 模块，10 条规则 + 5 类场景，与检查模板完全隔离）
   └─ 模型（缺口必补 + 非重复业务增强 + 权限矩阵补漏，经去重签名与门禁验收）
3. 约束层（不可突破的护栏）
   ├─ 五条红线（plan_validation.py + lifecycle.py）
   ├─ 断言强度 lint（script_linter.py + http 字段级断言校验）
   └─ 基线 Smoke Gate + 写隔离（自建资源优先，共享种子后置 + 重启/reset 兜底）
4. 验证层（可核对与长期不退化）
   ├─ 12 维覆盖账本（advisory，未要求不扣分）+ 按需只读人工核对（禁止自动重跑自带写测试）
   └─ 本地 Seeded Bug 基准 + Fixture Zoo（static/integration）+ 5 项目 Portfolio
5. 复用层（不重复造轮子）
   └─ OpenAPI/Swagger 协议复用 + 可选 Schemathesis 薄封装，结果统一经五条红线归一化
```

- **默认不设用户可见的“模式开关”**：UI 不出现 `ai.mode` 或“简单/完整”切换；深层能力（如运行时内省）作为受确认的按需动作存在。

### 2.2 四个概念严格分清与业务四值映射

| 概念 | 精确含义 | 是否算通过 | 映射到业务四值结论 | 展示位置 |
| :--- | :--- | :--- | :--- | :--- |
| **`failed`** | 执行完成且断言失败 | 否 | `failed` | 结果页 / 问题页 / 报告 |
| **`blocked`** | 前置、环境、基线 Smoke 或服务未就绪 | 否 | `incomplete`（原因 `blocked`） | 结果页 / 报告 |
| **`unsupported`** | 插件当前不具备该能力（如特定协议/宿主） | 否 | `incomplete`（原因 `unsupported`） | 概览 / 确认页 / 报告 |
| **`uncovered`** | 插件有能力，但本次未生成或未选中该验收项 | 否 | `incomplete`（原因 `uncovered`） | 计划页 / 报告未覆盖清单 |
| **不适用项** | 验收项本身明确不适用于当前项目 | 不计分母 | `not_applicable` | 范围页 / 报告说明 |

> **铁律**：`blocked / unsupported / uncovered` 是原因分类，不是第五种业务结论；**`not_applicable` 只能用于“验收项本身不适用”，严禁用来掩盖“插件没能力（`unsupported`）”**。

| **T4 明确不支持** | 透明亮牌，不假装具备能力 | **协议类**：`GraphQL`、`gRPC / Protobuf`、`WebSocket / SSE 实时推送`、`MQTT / AMQP`、`SOAP`（在对应 fixture 落地前）<br>**端侧/设施类**：原生/跨端移动端（`iOS / Android / Flutter / React Native`）、桌面客户端（`Electron / Tauri / WinUI`）、嵌入式硬件、云厂商专有 Serverless 触发器 | 报告明确列为 `unsupported`（原因分类，绝不偷标为 `not_applicable`） |

> **晋升与扩栈铁律**：新增任意技术栈只能增加协议/启动/认证适配器与对应 `zoo` fixture，**严禁修改四值裁决、五条红线和 `S/M` 核心逻辑**。

#### 依赖与基础设施分级 D1–D4 及控制面（按优先级收敛）

| 级别 | 能力 | 适配清单与隔离承诺边界 |
| :--- | :--- | :--- |
| **D1 完整** | 识别 + 启动/健康 + 复位/隔离 + 状态探针 + fixture | **首批落地**：`SQLite`、`Redis`（清表 / `FLUSHDB` / 唯一前缀隔离与状态探针，缓存场景验证创建读回源、更新失效、删除防脏读、TTL）<br>**次批按需晋升**：`PostgreSQL`、`MySQL / MariaDB`（独立测试库/schema + 迁移清表） |
| **D2 基本** | 识别 + 启动/健康 + 复位 | **次批实验性**（待对应 `zoo/integration` fixture 落地）：`MongoDB`、`MinIO / S3`、`Mailpit / MailHog`、`WireMock / Prism`（本地第三方 HTTP 桩），可复位隔离但暂不深探内部状态 |
| **D3 只识别** | 识别 + 连接，不可自动复位 | 托管云数据库/缓存、外部第三方 SaaS API（支付 Stripe/支付宝、短信/邮件、第三方 LLM、OAuth 外部登录），仅依赖唯一前缀测试数据并在报告标“隔离受限” |
| **D4 不支持** | 不识别或不接管 | 专有云 PaaS 控制面、Kubernetes 全集群编排、真实生产外部资金/风控接口、硬件外设；报告列为 `unsupported`，依赖不可用时相关用例记 `blocked`，不判产品失败 |

- **控制面分批收敛纪律**：先做通 `SQLite` 与 `Redis` 控制面及 `zoo/integration` 夹具，再按实际项目需要逐个推进次批 `PostgreSQL/MySQL/S3/Mailpit`，不做大而空的适配壳子。

## 第 4 节：生成层——10 条不变量、5 类确定性场景与非重复 AI 业务增强

### 4.1 10 条零模型确定性不变量（直接从路由 + Schema 推导）

| # | 不变量场景 | 确定性预期 |
| :--- | :--- | :--- |
| 1 | 创建 → 读取 | 响应字段与返回 `id` 完全一致 |
| 2 | 更新 → 读取 | `id` 不变，目标字段已持久化更新 |
| 3 | 删除 → 读取 | 返回 `404` |
| 4 | 对不存在资源执行 PUT / DELETE | 返回 `404` |
| 5 | 缺少必填字段提交写请求 | 返回 `400` / `422`（依栈规范） |
| 6 | 未带凭证访问受保护接口 | 返回 `401` |
| 7 | 越权/无权限角色操作受保护资源 | 返回 `403` |
| 8 | 创建后查询列表接口 | 列表中包含新建对象 |
| 9 | 响应 `Content-Type` 校验 | 符合 API 契约（如 `application/json`） |
| 10 | 状态化全链路序列 | 同一对象执行 `create → update → delete` 闭环 |

### 4.2 纯 Python 确定性场景生成器（与检查模板物理分离、拒绝脆弱 JSON DSL）

- **架构取舍与字段隔离硬规则**：
  - 放弃编写脆弱的 JSON 声明式配方 DSL 解析器，**首期直接用纯 Python 确定性生成器模块（`src/aitest/core/invariants.py` 拟新增）直接产出标准 `http:` 请求序列**（可灵活适配不同项目的响应包装层、`id`/`uuid` 字段与认证头，具备完整类型检查且易调试）；命中记录存放在 `Plan.recipes`；
  - 现有咨询性检查模板继续只存 `plan.templates`，**绝不共用 schema、不共用字段、不共用 `S/M` 分母语义**。
- **首期 5 类确定性覆盖场景**：
  1. `rest-crud`：资源列表 / 详情 / 创建 / 更新 / 删除及写后读回 + 404；
  2. `rest-validation`：缺必填字段 / 非法参数类型边界验证；
  3. `jwt-login`：登录取 token、凭证注入与非法/过期 token 401；
  4. `negative-auth`：未带凭证 401、跨角色/跨租户无权限 403/404（强制先建/验资源存在）；
  5. `multi-service`：前后端分离角色探针目标与健康路由匹配。
- 生成器匹配仅依据 `capabilities` 事实；匹配不上记 `skipped` 并进未覆盖清单，禁止猜测生成。

### 4.3 模型补充边界：缺口必补 + 非重复业务增强（去重签名）

- **模型只做确定性规则覆盖不到的事**：业务语义特有规则（如库存扣减、优惠计算、多步骤审批状态机）、复杂前置构造、对已覆盖验收项的**高价值非重复增强**（并发竞争、重复提交幂等、跨租户边界、状态组合）。
- **确定性去重签名**：每条生成用例计算签名 `item_id + scenario_type + assertion_target + data_shape`，`exact duplicate` 率必须为 **0**，禁止模型重复输出不变量/配方已覆盖的常规 CRUD 用例凑数。
- **预期来源优先级（严防 AI 替人定真相）**：
  1. 用户提供的可执行输入/输出样例；
  2. 验收项原文（`expectation_source`）；
  3. 用户经双盲对比确认后更新进计划的预期；
  4. 仅模型猜测且无法锚定验收项原文的用例，一律标“预期未证实”，执行后最多算阻塞/未完成，不能判通过。

## 第 5 节：AI 后端治理基建与分批能力清单（去元框架、留真基建）

### 5.1 AI 方法统一入口防重复与单向分层规则（原 §2.3 工程纪律）

1. **唯一调用口与单向分层**：所有 AI 调用收口到 `src/aitest/adapters/model.py` 的公开方法，同时严守 `core/` 不反向依赖 `adapters/` 的分层边界；针对 `src/aitest/core/templates.py`（现行 L197 通过 `JsonModel` 协议直调 `complete_json`），**R2 将实际模型调用及缓存/统计能力收口至 `adapters/model.py` 的 `dispose_template_items()`，由 `command_handlers/` 调用后再把模型原始结构交回 `core/templates.py` 做确定性归一化**。
2. **一任务一入口**：新增前核对既有方法表，禁止并存两套实现；旧实现与新实现冲突时在同一切片删除旧路径。

### 5.2 AI 输出硬契约与安全权限等级

- **输出硬约束**：每条 AI 建议/假设/评审补丁必须引用原文或源码/日志证据；**严禁出现结论词（`passed`/`failed`/`全部通过`/`建议上线` 等）及 `S/M`、通过率**；检测到结论词整段作废，无证据引用降级为 `unknown`；进 prompt 前及落盘前强制执行凭据脱敏。
- **风险分级授权**：`R0 只读分析`（读代码/日志/路由，AI 自动）→ `R1 项目内可逆/脚本局部调整`（经静态守卫 + 人确认、可回滚）→ `R2 服务启动与受控执行`（显式确认、超时、独立证据）→ `R3 系统级/外部生产操作`（严禁 AI 执行）→ `R4 结论与关闭`（仅确定性核心与人类裁定）。所有外部输入（代码、README、日志、GitHub 返回）一律视作不可信数据，防止提示注入。

### 5.3 AI 工程治理基建（省成本、可离线测试、可安全降级）

1. **按 `input_hash` 缓存（R2 提前落地）**：相同上下文与 prompt 版本不重复调模型，立刻降低日常调试与复测延迟；
2. **模型成本分级（`model.ai.model_tier=auto`）**：摘要/映射/分类可用轻量模型，复杂业务用例与失败深度诊断用强模型；
3. **单任务 Token 预算兜底**：超预算自动降级为纯确定性路径，不阻塞主流程；
4. **Golden Set 录制回放评测**：CI 默认完全离线，使用录制响应回放验证 schema 合法率 100%、结论词过滤率 100%、证据引用率 100%；真实大模型调用留给手动或发布前 smoke；
5. **内部回退开关 `model.ai.mode=assist|off`**：仅后端配置可见，不暴露到面板 UI；置为 `off` 时确定性发现、场景生成、红线校验、执行、四值裁决与报告生成仍可端到端完整运行。

### 5.4 第一批核心 AI 能力 vs 第二批后置扩展能力

| 批次 | 能力与方法 | AI 职责 | 确定性验收与门禁 |
| :--- | :--- | :--- | :--- |

## 第 6 节：约束层与验证层——五条红线、12 维账本、Fixture Zoo 与 Portfolio

### 6.1 五条不可突破红线（`plan_validation.py` + `lifecycle.py` + `judge.py`）

1. **负向鉴权不补认证**：验收项要求 `401/403` 时，`assert` 阶段严禁自动补凭证改写成通过。
2. **setup 只能期望成功**：`setup` 阶段请求不得设置 `4xx/5xx` 期望或放入负向断言。
3. **状态码必须断言**：验收项写明 `400/401/403/404` 等状态码时，`assert` 阶段必须显式包含 `path=status` 校验。
4. **结果与可信度分离（同步 D4）**：执行完成的断言失败保持 `failed`；AI 只产出假设，最终可信度由确定性规则计算；裁判不确定不把执行失败改成 `blocked`，且**绝不把 `PATCH/PUT/DELETE` 等单次写操作真实失败降级吞成 `incomplete`**。
5. **未知/未覆盖/弱断言不判通过**：空 `http:`、`unknowns`、`unsupported`、未覆盖项与空 `S` 严禁汇总成通过或启动运行；HTTP 断言强度 lint 要求状态码 + 至少一个业务字段/状态校验（禁止“只要 200 就算通过”）。

### 6.2 基线 Smoke Gate

- 启动正式业务用例前，先核验项目可读/可配置，且已声明并确认启动的服务健康、认证登录/关键只读入口可用；
- **基线门禁失败直接判为 `incomplete`（原因 `blocked`）**，立即止损，绝不继续执行业务用例造成大规模环境假失败或误判产品缺陷。

### 6.3 12 维覆盖账本（`Plan.coverage_ledger`，advisory）

按验收项文本与已有用例覆盖情况确定性映射所需维度：**正向、负向、权限、边界、状态流转、UI、跨服务、缓存/异步、依赖状态、安全、性能、可靠性**。文本未涉及的维度标为“未要求”且不扣分；明确要求但当前计划未覆盖的进入缺口提醒。

### 6.4 与项目自带测试的按需核对边界（移出自动运行主线）

- **严禁在运行主线中对已绑定 `test_nodes` 的失败用例自动重跑**：若一条用例执行的就是项目自带的 `test_nodes`，再跑一次只是重跑自己而非交叉校验，且对写状态用例会直接破坏隔离、违反“写用例禁止防抖重跑”的红线；
- **定位降级为按需只读对比**：仅在后续有明确隔离条件、且插件跑的是独立自建 HTTP 用例时，才由人工按需对比项目既有测试结果作线索参考，不进入自动执行主路径，也不自动改判。

### 6.5 Fixture Zoo 两层结构与 5 项目 Portfolio 回归基线

#### Fixture Zoo 两层目录（`tests/fixtures/zoo/`）

1. **`zoo/static/`（11 个离线快速夹具，每次提交在默认 `pytest` 中运行，不启服务、不调真实模型）**：
   - **首批既有/T1 核心 + 前端封装 + OpenAPI（7 个）**：`flask_decorator/`、`fastapi_router/`、`django_drf_router/`、`express_router/`、`axios_template_base/`、`fetch_wrapper/`、`openapi_generic/`（仓库内置 OpenAPI spec，验证通用 T2 协议导入）；
   - **增补多栈静态路由与 T1 次批演进护航（4 个）**：`nextjs_app_router/`、`nestjs_controller/`、`spring_boot_controller/`、`go_gin_router/`。
2. **`zoo/integration/`（3 个本地进程集成夹具，验证真实隔离与协议联调，不访问外网、模型用录制回放）**：
   - `jwt_negative_401/`、`multi_service/`（Flask/FastAPI + Vite 前后端角色探针）、`redis_cache/`（缓存失效与 `FLUSHDB`/前缀隔离）。

| 项目 | 测试角色定位 | 技术栈 | 目标基线（核心不退化标准） |

## 第 7 节：复用经济与依赖边界

- **协议优先，不重复造轮子**：不自建 API fuzzer、浏览器录制器、流量代理、单元测试生成器、容器编排或自愈 locator；自研只聚焦在**验收映射与 `S/M`、四值裁决、五条红线、证据链、插件工程体验**。
- **可选薄封装引入顺序**：已有 OpenAPI 规范时支持后续按需可选接入 **Schemathesis**（Apache/MIT 许可）做边界与状态码生成；借鉴 **RESTler** 的 `create→update→delete` 状态序列构造配方，不重写复杂引擎抽象层（接入第三个外部引擎时再考虑抽统一接口）。
- **结果归一化**：任何外部工具输出一律不能直接算业务结论，必须经**路由/用例映射 → 验收项绑定 → 五条红线 → 去重签名 → 证据落盘**。
- **依赖打包纪律**：核心保持轻量（Python 标准库 + 现有核心依赖）；重型或可选工具仅在用户明确触发按需加载，不进默认发布安装包。
