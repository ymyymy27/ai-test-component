# 轻量 Trae 测试插件修改计划

日期：2026-11-16
范围：一期插件 MVP；不含产品设计稿与界面细化。
状态：执行计划；完成情况以提交、测试与真实 Trae 验收为准。

## 1 目标

把当前“系统级本地测试平台”收敛为轻量 Trae 插件：

```text
Trae 扩展（薄 UI）
  → 本地 Python CLI（按命令调用，无常驻核心）
    → 少量核心模块
    → 简单文件：JSON / Markdown / 证据文件 / zip 备份
```

不是系统：

- 无常驻核心、命名管道、后台守护服务（每次运行的一次性 worker 不算，见 §5.4）；
- 无数据库、提交根、manifest、分片、索引、事件日志；
- 无格式迁移/回滚/注册表；
- 无计划许可账本、逐动作授权、A—D 等级、功能×维度覆盖契约；
- 账号、上传、共享审核不进入插件内核。

参考规模（用来判断是否又长回去了，不作为验收指标）：

| 项 | 大致量级 |
| --- | ---: |
| Python 核心 | 一万行上下 |
| Trae 扩展/面板 | 几千行 |
| 测试 | 与实现相当 |
| 模块 | 二三十个 |
| 默认快测 | 十几秒到半分钟 |
| 全量测试 | 几分钟 |

这些数字只是防止再次膨胀的参照。实现更小、拆得更少都没问题；超出很多时再回头看看是不是又在做系统。

### 1.1 约束分级

计划里的条款分两档，读的时候按档对待，不要一把尺子量到底。

**硬约束**：变了就不是这个产品，或者会让用户拿到假结论。要改必须明确否决，不能顺手放宽。

| # | 硬约束 | 为什么不能松 |
| --- | --- | --- |
| H1 | 无常驻核心、命名管道、后台守护 | 一进来就回到系统级，装卸载都会变重 |
| H2 | 无数据库、提交引擎、迁移/回滚、许可账本、A—D 等级、账号/上传内核 | 这些正是从简单产品膨胀成系统的主因 |
| H3 | 扩展只通过 CLI 的 JSON 协议取数据；命令名与对外字段单一来源 | 两套协议必然漂移，面板和 AI 会给出不同结论 |
| H4 | 运行/报告的业务结论只有 `passed / failed / incomplete / not_applicable`；未执行、未知、阻塞不得汇总成通过 | 测试工具的全部价值在结论可信。步骤与断言可以有 `blocked / error / not_run` 等更细的执行状态，但只能向这四值收敛，不能反过来把四值拆成别的通过口径 |
| H5 | 空分母不显示 100%；模型/GitHub/链路失败不写成通过 | 同上，属于伪造结果 |
| H6 | 业务文件（项目/任务/计划/问题/报告）同时只有一个 CLI 在写，写入原子；`runs/<run_id>/` 由该次执行进程独占，CLI 只读。锁用 PID + 心跳，进程消失后下一次命令可接管 | 防半截文件和数据丢失。执行进程与 CLI 各写各的目录，互不抢锁；锁不能留成永久的 |
| H7 | 旧格式只提示转换或重建，不静默迁移、不覆盖用户记录 | 用户数据被改写不可撤回 |
| H8 | 凭据落盘前过滤，不进日志、导出、面板 | 泄露不可撤回 |
| H9 | Runner/适配器只返回结果；结论由 core 派生，面板只展示 | 防出现第二个判定口径 |

**软约定**：默认这么做，遇到更合适的做法可以改，改的时候在提交说明里留一句。

- 目录与文件怎么切、哪些小模块合并；
- 内部函数、类、变量的命名；
- 依赖方向（`core` 不碰 IO 是习惯，不是架构测试拦人）；
- 行数、模块数、测试条数、文档份数；
- 快测与全量的耗时；
- 数据文件字段的增减（H3 里的 CLI 对外字段除外）；
- 工作包的先后顺序与拆分粒度；
- 注释密度、日志措辞、错误提示文案。

## 2 已确认决策

| 主题 | 决策 |
| --- | --- |
| 宿主 | 一期 Trae；其他编辑器后置 |
| 运行形态 | 扩展调用 Python CLI；无常驻核心 |
| 长任务 | 每次运行启一个 detached worker 子进程，写 `runs/<id>/`；关编辑器不中断，取消用标志文件 |
| 模型 API | **必需**（AI 主导测试）；DeepSeek 兼容 HTTP API |
| 模型密钥 | 环境变量优先，其次 `%APPDATA%itest\config.json`；工作空间不存密钥 |
| AI 分析 | 失败后生成结构化说明；只展示，不做人工审批、不改结论 |
| GitHub | **一期必需薄适配器**：只读提交/PR/检查/部署版本 |
| GitHub 认证 | 复用 `gh` CLI 登录态，插件不存 token；gh 缺失或未登录由人处理 |
| 链路 | **一期必需薄适配器**：请求→日志→模块→DB→断言 |
| 链路数据 | 读配置的日志文件（JSON lines 或正则）+ 执行只读查询命令；不接 APM、不内置数据库驱动 |
| 存储 | 项目目录 JSON/Markdown/证据文件 + 原子写 + zip 备份 |
| 数据升级 | 只支持当前格式；备份后转换或拒绝/重建 |
| 账号/上传/共享审核 | 不做，后续外部集成 |
| 目标输入 | AI 给 3—5 条候选目标（无信号给通用目标），可选、可改、可自定义 |
| 计划发布 | AI 生成后自动发布为初版 |
| 执行确认 | 发布后执行前确认一次；改范围/环境/凭据或明显副作用时重新确认 |
| 测试范围 | 按验收项选：全部适用 / 自选（先模块、可选再层级）；不按用例挑拣 |
| 执行驱动 | 不做 planned/stepwise 驱动；按计划顺序执行，取消在用例边界生效 |
| 重跑 | 按验收项新建运行，旧运行保留 |
| L3 载体 | 前端 UI 与接口/命令；AI 生成可重放脚本；智能体入口后置 |
| 测试文件 | AI 生成到 `runs/<id>/generated/`，不进仓库；缺依赖确认后安装 |
| 服务与数据 | 按配置启动、只接管自己启动的；数据不自动清理，显式命令 + dry-run |
| L1 定位 | 项目级检查，单独列、不计验收项覆盖；用例标 depends_on 精确阻塞 |
| 问题去重 | 按失败签名合并，同一问题追加发生记录；不自动重试，结果不同标疑似不稳定 |
| 模块关系 | 可选；AI 可起草，确认后生效，不扫全仓 |
| 验收意见 | 报告附自由文本 + 手填署名与时间；无通过/驳回、无流转；AI 不代填 |
| 变更回归 | 一期只列涉及模块与未选提示；自动影响分析后置二期 |
| 报告计数 | 主表按验收项取最差结果；用例明细附表；L1/L2/L3 按用例单独统计 |
| Mock 真实性 | AI 按需读业务代码判定并附依据；不填清单、不可手改；默认 40 文件/3 层，可配置 |
| 覆盖与等级 | 显示状态与计数；不做 A—D 等级 |
| 模板 | 保留为规则预设清单，不做模板子系统 |
| 保留期 | 文件永久保留；用户自行清理，插件不做自动清理 |
| Python | 3.11+；验证 3.11/3.13，3.14 未验证 |
| 运行环境 | 优先复用已有合格 Python；缺失时下载便携 Python 到 `%APPDATA%itest
untime`，用自带 wheel 安装 |
| 本地边界 | 模型/GitHub/链路是必需外部依赖，不是严格“纯本地” |

## 3 MVP 功能

| 编号 | 功能 | 最小内容 |
| --- | --- | --- |
| FR01 | 项目与模块 | 目录、目标、模块、依赖、负责人、实现状态 |
| FR02 | 任务与验收项 | AI 目标候选与验收项提取；范围、验收条件、执行/验收人 |
| FR03 | 交付说明 | AI 从提交与脚本起草；变更、运行方式、Mock、自测证据 |
| FR04 | 规则与模板预设 | 规则版本、预设清单、Markdown 导入导出 |
| FR05 | 计划与用例 | AI 按所选验收项生成并发布初版；验收项关联、预期、Mock 许可 |
| FR06 | L1 源码可运行性 | 项目级检查：语法、构建、入口加载/最小启动 |
| FR07 | L2 函数与模块 | pytest/命令、断言、输出、日志、Mock |
| FR08 | L2 接口与集成 | HTTP 串联、业务断言、存储核验 |
| FR09 | L3 用户场景 | 前端 UI 与接口/命令两种载体；AI 生成可重放脚本；`manual_pending` 兜底 |
| FR10 | Mock 与证据 | AI 判定真实/Mock/混合/未知并附依据；证据文件引用 |
| FR11 | 问题与回归 | AI 自动生成问题并按失败签名去重；分级、修复版本、复测 |
| FR12 | 报告与导出 | AI 摘要说明；Markdown、范围与覆盖、涉及模块、按验收项计数与用例明细、证据索引、验收意见 |
| FR13 | Trae 接入 | 面板/命令、项目绑定、运行状态、导出、环境自检与修复 |
| FR14 | GitHub 变更与检查 | 只读提交/PR/检查/合并状态/部署版本 |
| FR15 | 链路采集 | 请求标识、日志、模块调用、DB 结果、节点顺序、缺口 |
| FR16 | 链路断言与定位 | 节点断言、首个异常、上下游、代码位置或未知范围 |
| FR17 | 工作空间备份与恢复 | zip 备份、可校验、恢复核对、缺口如实显示 |
| FR18 | AI 失败分析 | 失败/阻塞后生成：事实、证据引用、候选原因、未验证、下一步；只展示，不审批、不改结论 |

FR18 的边界：

- 触发：运行结束且存在失败、阻塞或执行异常时自动生成；全部通过不分析。生成是异步的，不改运行状态、不拖慢运行结束；
- 手动 `analysis.run` 只用于重跑或换模型重试，不是必需的日常操作；
- 输出固定四段（事实、证据、候选原因含把握程度、未验证 + 下一步），缺“未验证”视为不合格输出；不合格时整条标“分析不合格”，不展示半截内容，也不截取部分段落充数；
- 分析只是说明材料：不参与 `passed/failed` 判定，不自动建问题，不关闭问题，不提供采纳、备注或审批入口，也没有状态流转；
- 模型不可用、无配置或调用失败时，该次运行标“分析未生成”，运行结果、证据、报告照常可用；
- 面板展示，导出报告时附在对应失败段落；报告里与断言结果分列，不带状态字段。

### 3.1 范围与覆盖

主流程不变：项目 → 模块 → 任务 → 验收项 → 用例 → 执行/证据 → 问题 → 回归 → 报告。

- **选择单位是验收项**，不直接挑用例；用例由计划按验收项生成或关联，不能脱离验收项存在。
- 两个预设：**全部适用**（当前任务下全部适用验收项）、**自选范围**（先按模块筛，可选再按层级筛，最后勾验收项）。
- `M` = 当前任务适用的验收项；`S` = 本次所选。空 `S` 不允许发布计划或启动运行。
- 覆盖固定展示 `|S|/|M|` 和未覆盖清单；`|S| < |M|` 时只说“本范围通过”，不出现“全部通过 / 完整通过”。
- 范围在 `plan.publish` 固定；`run.start` 可再收窄到 `S` 的子集。运行中改范围必须新建运行。
- 结论只描述本次运行的 `S`，不描述整个项目。

### 3.2 重跑

- 重跑按**验收项**发起，不按单条用例挑拣；
- 新建一次运行，范围只含该验收项（可加上它依赖的验收项），旧运行完整保留，旧结果不被覆盖；
- 问题关闭仍以新运行的实际证据为准。

### 3.3 L3 业务场景

L3 是业务闭环验证，不限于前端，一期支持两种载体：

| 载体 | 做法 | 例子 |
| --- | --- | --- |
| 前端 UI | AI 生成 Playwright 脚本并执行，脚本落盘可重放 | 打开订单列表，看到新订单 |
| 接口/命令 | AI 生成请求或命令序列，跑完核对最终持久化 | 调下单接口，再查库确认订单与库存 |

- 能自动化的由 AI 生成脚本或步骤并执行；
- 脚本生成失败、场景不可自动化（验证码、真人判断、主观评价）→ 标 `manual_pending` 转人工；
- 人工兜底按用例现场逐条记录，结果、时间、截图/请求引用立即落盘；未记录计入未完成；
- 智能体入口后置，一期不做；
- 不做 AI 临场自主操作页面，也不做 `stepwise` 驱动。

### 3.4 验收意见

- 报告可附一段自由文本验收意见，记录署名、时间、正文；署名手填，不依赖账号体系；
- 没有“接受/不接受”枚举，没有状态流转，不影响运行结论与报告结论；
- 可以不填；不填时导出显示“未填写验收意见”；
- 只能由人通过 `report.opinion` 写入；AI 不生成、不代填、不修改。

### 3.5 变更与回归

一期只做提示，不做推荐：

- 报告列出“本次涉及模块”：由计划范围与 GitHub 变更文件映射到已登记模块得到；映射不上的标“未映射文件”，不猜；
- 选范围时提示“相关模块还有 N 条验收项未选”，数据来自已登记的模块归属，不做推断；
- 不自动加入范围、不排序、不打分；增删由人决定；
- 模块关系或目录规则缺失时，明确提示“数据不足”，不生成建议。

### 3.6 计数口径

- 主表按**验收项**统计：每条验收项的结论取它所有用例中最差的结果，顺序为 `失败 > 阻塞/未知/未执行 > 通过`；
- 覆盖、通过率、运行结论都从验收项口径派生；
- 用例明细作为附表：层级、所属验收项、结果、证据引用，导出也带；
- 一条用例覆盖多条验收项时，在各验收项下各计一次；用例总数只计一次；
- L1/L2/L3 的数量按用例单独统计，不与验收项混算；
- 全部验收项不适用时显示“不适用”，不显示 100%。

二期方向（变更影响分析，不在一期实现）：

- 信号：变更文件、文件→模块映射、模块依赖、接口 diff、依赖清单、历史链路、历史问题；
- 过程：文件映射到模块 → 沿依赖扩散 1—2 层 → 与验收项/用例取交集 → 按直接/间接、重要度、历史失败排序；
- 输出：候选回归清单，每条带依据与高/中/低/未知置信度，另列“未知影响”；
- 前置条件：模块目录规则齐全、调用图可用、至少一个试点项目跑过若干轮；
- 明确不做：全语言静态分析器、跨仓库影响分析、自动修改范围。

### 3.7 Mock 真实性（AI 判定）

- 不要求用户填写 Mock 清单，也不提供结果修改入口；
- 每次运行后由 AI 按需读代码判定每个外部依赖：从测试配置和测试代码出发，沿调用链追客户端初始化与地址来源，再与本次的请求、响应、日志、DB 结果对照；
- 每条结论必须带文件路径与行号或证据引用；给不出依据只能判 `unknown`；
- 读取预算：默认最多 40 个文件、调用链 3 层，可在项目配置调整；超出即停，标 `unknown` 并注明“达到读取上限”；
- 结果按项目修订 + 文件哈希缓存，文件变化才重判；
- 读过的文件清单写入运行证据，报告可查；
- AI 不可用 → 全部 `unknown`，报告写“真实性未判定”，测试与证据不受影响；
- `unknown` 或含未识别 Mock 的用例不能获得“真实链路通过”。

### 3.8 目标候选

进入项目后不要求人先写目标：

- AI 依据上次运行以来的提交与变更、未关闭问题、模块与依赖、README/需求文档、历史任务五项，给 3—5 条候选目标，每条带一句依据；
- 没有任何信号的新项目，给一条通用目标“验证项目能否启动并跑通主流程”；
- 人可以选一条、改一句，或完全自定义输入；自定义入口始终可见；
- 候选只是建议，不选也不输入则不建任务；
- AI 不可用时直接进入自定义输入。

### 3.9 执行前确认

- 计划发布后不自动执行；面板展示范围（已选/适用、未覆盖清单）、用例数与层级分布、环境、凭据边界与明显副作用、将安装的依赖、预计耗时；
- 人确认一次后启动，确认记录写入 `run.json`（`confirmed_by`、`confirmed_at`、范围摘要）；
- 改范围、换环境、用新凭据、执行明显副作用动作时需重新确认；同一范围同一环境重复运行不重复确认；
- CLI 调 `run.start` 必须显式 `--confirm`，否则拒绝；
- AI 不能代替确认。

### 3.10 人工剩余动作

这些事永远由人做，不交给 AI：

| 动作 | 为什么必须是人 |
| --- | --- |
| 选项目目录 | 只有人知道要测哪个项目 |
| 首次配置模型密钥 | 凭据不能由 AI 生成或代填 |
| 执行前确认一次 | 范围、环境、副作用需要人认可 |
| 处理无法自动化的 L3 | 验证码、真人判断、主观评价，脚本做不了 |
| 处理坏掉的环境 | 代理、证书、权限，AI 只能给建议 |
| 纠正明显错误的 AI 判定 | 通过改范围或重跑纠正，不直接改运行结果 |

下面两件不算人工动作：

- 看报告：可选，不看也能交付；
- 填写验收意见：可选，空着合法。

### 3.11 环境诊断与修复

`doctor` 先采集事实：Python 版本、能否导入 aitest、模型连通性、GitHub 认证、目录权限、代理设置。失败时 AI 解释原因并给出修复方案，按风险分三档：

| 档 | 包括什么 | 怎么做 |
| --- | --- | --- |
| 低风险 | 重建插件运行时、重装 wheel、清临时目录、修复工作空间权限 | AI 自动修，记动作日志 |
| 中风险 | 项目 venv 装依赖、`npm ci`、补测试依赖 | 跟随执行前确认一起授权，记录命令与输出 |
| 高风险 | 改系统代理、装根证书、改 PATH、装系统级 Python/Node/gh | AI 只给命令与风险说明，由人执行 |

- 每次修复记录命令、输出、结果与时间，写进动作日志；失败只记录原因，不循环重试；
- 不关闭 TLS 校验，不静默改系统环境变量，不要求管理员权限；
- AI 不可用时退回原始错误与检查项清单，人自行处理；
- 修复只针对环境，不改被测代码、不改项目配置。

### 3.12 AI 生成测试文件与运行

- 按用例生成对应文件：pytest、HTTP 请求脚本、Playwright spec、SQL 核对语句；
- 全部放在 `runs/<run_id>/generated/`，不写进被测仓库，不覆盖、不提交、不改项目配置；
- 用项目自己的解释器和依赖运行（仓库里的 `.venv`、`node_modules`），pytest 用显式文件路径，不扫全仓；
- 脚本内容、摘要、生成模型、时间与输出一起写进运行证据，可复查、可重放；
- 缺项目依赖时，在执行前确认页列出将安装的依赖；确认后随运行安装，未确认标 `blocked`；
- 脚本自身写错（语法、导入）标 `blocked` 或 `error`，不算产品失败；
- 用户要保留脚本进项目时自行复制，插件不代做。

### 3.13 服务与数据生命周期

服务按项目配置管理：

```json
"services": {
  "start": "docker compose up -d",
  "stop": "docker compose down",
  "health": "http://localhost:8080/health",
  "timeout_seconds": 120,
  "keep_on_failure": false
}
```

- 先探测健康地址；已通就不接管，直接用；
- 未通则执行启动命令并轮询健康检查，超时标 `blocked`，保留启动日志；
- 只停止自己启动的服务，用户原本在跑的不动；
- 端口冲突、启动失败如实报告，不强行杀进程；
- 运行结束默认停止；`keep_on_failure` 打开时失败后保留现场。

测试数据：

- 插件生成的数据带运行标记（如 `aitest_<run_id>_` 前缀）或记录下业务 ID；
- 默认**不自动清理**；
- `data.cleanup` 默认 dry-run，列出将删除的条数与条件；加 `--yes` 才执行；
- 只删带标记或记录在案 ID 的数据，不按时间或整表删除；
- 清理动作写入动作日志。

### 3.14 L1 与覆盖

- L1 是项目级检查，结果单独展示，不进 `S/M` 覆盖，不计入验收项计数；
- L1 用例可以不关联验收项；
- 每条用例记录 `depends_on`：`build`、`service` 或空；
- L1 构建/入口加载失败 → 依赖 `build` 的用例标 `blocked`；
- 服务启动失败 → 依赖 `service` 的用例标 `blocked`，单元测试等无依赖用例继续；
- 阻塞原因写进报告“项目级检查”区，不归到某条验收项。

### 3.15 问题去重与稳定性

- 失败签名 = 用例 ID + 错误类型 + 关键堆栈或断言标识；
- 同一签名只建一个问题，后续失败追加“发生记录”（运行、时间、证据），不新建；
- 不同签名分别建问题；报告显示“问题数 / 失败次数”，不把重复失败算成多个问题；
- 不自动重试；
- 人可手动重跑某条验收项（新建运行）；两次结果不一致时标“疑似不稳定”，两次结果都保留，不互相覆盖；
- 第二次通过不回写成第一次通过。

## 4 项目结构

下面是**起点参考**，不是必须逐字照搬的目录合同。实现时按实际需要增删文件、合并小模块；先不建空的包和占位文件。判断标准是：读代码的人能在几秒内找到某个功能的入口，而不是目录长得多整齐。

### 4.2 模块职责

下表的“不做什么”是防止职责串味的提醒，不是逐条检查的禁令。小的越界（例如某个读取顺手做了字段校验）不值得为它再造一层。

| 模块 | 主要职责 | 尽量不放在这里 |
| --- | --- | --- |
| `cli.py` | 解析命令、调用 core/storage/runners/adapters、输出 JSON | 业务判定 |
| `models.py` | 数据模型、枚举、字段校验 | 文件/网络 I/O |
| `storage/workspace.py` | 目录布局、原子写、锁、zip 备份 | 业务规则 |
| `storage/files.py` | 单文件 JSON/Markdown 读写 | 业务查询 |
| `storage/evidence_store.py` | 保存证据文件、摘要、引用 | 判断证据有效性 |
| `core/*` | 项目、计划、执行、证据、问题、报告的规则 | 文件读写、网络调用 |
| `runners/*` | 执行外部命令/请求，返回统一结果 | 写业务记录 |
| `adapters/model.py` | 调模型 API、解析结构化输出 | 发布计划、改判定 |
| `adapters/github.py` | 读 GitHub，返回 change/check 引用 | 写 GitHub |
| `adapters/link.py` | 导入日志/DB 结果，返回节点/断言 | 自动追踪 |
| `integrations/trae` | UI、命令、参数收集、展示 | 重算结论 |

### 4.3 依赖方向

大致方向：

```text
扩展 → cli → core / storage / runners / adapters
core / storage / runners / adapters → models / errors / security
```

- `core` 尽量不依赖 `storage`、`runners`、`adapters`，这样规则可以脱离文件和网络单独测；
- 适配器之间不互相调用，避免一个外部依赖坏了牵动另一个；
- 整体避免环。

方向是为了好改、好测，不用加架构测试去卡死。真需要反向引用时在提交说明里写一句原因即可，不必绕一大圈造抽象来维持形式上的分层。

## 5 CLI 协议

### 5.1 入口

```bash
python -m aitest.cli <command> --workspace <dir> --input <json-file>
```

- 支持 `--input` 文件或 stdin JSON，两者行为一致；
- 输出一行 JSON 到 stdout；
- 日志写 stderr，不混入 JSON；
- 退出码：0 成功，1 业务拒绝，2 参数/环境错误。

### 5.2 请求/响应

请求：

```json
{
  "command": "project.add",
  "request_id": "uuid",
  "payload": {}
}
```

成功：

```json
{"ok": true, "request_id": "uuid", "data": {}}
```

失败：

```json
{"ok": false, "request_id": "uuid",
 "error": {"code": "INVALID_PROJECT", "message": "...", "next_step": "..."}}
```

### 5.3 命令清单

| 命令 | 作用 |
| --- | --- |
| `doctor` | 检查工作空间、Python、模型、GitHub、权限、代理；失败时解释并可修复低风险项 |
| `project.add/list/show/update` | 项目 |
| `module.add/update/list` | 模块、依赖、负责人 |
| `task.suggest/add/list/show` | AI 目标候选；任务与验收项 |
| `delivery.save/show` | 交付说明 |
| `rules.list/show/import/export/bind` | 规则与模板预设、项目绑定 |
| `plan.generate/show/publish` | 计划与用例 |
| `run.start/status/list/cancel` | 执行、状态、中断接管；`run.start` 可把范围收窄到计划范围的子集 |
| `run.manual` | 记录 L3 人工步骤结果与证据；只改该用例状态 |
| `data.cleanup` | 按运行标记清理测试数据；默认 dry-run，`--yes` 才执行 |
| `evidence.add/list` | 证据引用、人工补证 |
| `issue.add/list/update/close` | 问题与回归 |
| `report.generate/export/opinion` | 报告、导出、验收意见记录 |
| `github.read` | 只读变更/检查 |
| `link.import/assert` | 链路证据与断言 |
| `analysis.run` | 对一次运行生成 AI 失败分析；只写分析，不改状态 |
| `backup.create/restore` | zip 备份与恢复 |

命令名和对外字段在 `models.py` 里定义一次（H3），扩展只调用不复制。新增命令先看现有命令能不能覆盖，避免同一件事有两个名字。

H3 不要求生成 TypeScript 类型，也不要求共享 Schema 文件：扩展手写自己展示用到的字段即可，字段对不上时以 CLI 实际输出为准。做代码生成会把插件重新拖回工程化老路。

### 5.4 执行模型：一次运行一个子进程

长任务不能占用 CLI，也不能等扩展托管（关掉 Trae 就断）。选定的做法是**每次运行起一个用完即退的子进程**，它只服务这一次运行，不是常驻核心：

```text
run.start
  → 校验计划、创建 runs/<run_id>/
  → 写 run.json（status=running, pid, started_at, heartbeat_at）
  → 以 detached 方式启动 python -m aitest.worker --workspace .. --run ..
  → 立即返回 run_id
```

- worker 独占 `runs/<run_id>/`，按计划顺序执行并持续刷新 `heartbeat_at`；不写项目/任务/计划等业务文件；
- 遇到 L3 用例标 `manual_pending` 后继续后面的用例，不等待人工；
- `run.cancel` 只写 `runs/<run_id>/cancel.requested`；worker 在步骤边界看到后停止，写 `cancelled`；没停下来就写 `execution_error` 并说明；
- `run.status` 读 `run.json`，不主动改状态；
- `run.start` 必须有确认记录或显式 `--confirm`，否则拒绝；
- 进程间只通过文件通信，不引入队列、调度器、socket、命名管道；
- 关闭 Trae 不影响 worker；重开后 `run.list` 仍能看到这次运行；
- 面板轮询 `run.json`：运行中 2 秒、空闲 10 秒；只读，不触发状态变更。

**中断接管**：发现 `status=running` 但心跳超过阈值、且 pid 不在时，标为 `interrupted`，保留已有证据和步骤记录，不自动重跑、不补造结果。接管发生在 `doctor`、`run.status`、`run.list` 读取时，由 CLI 做一次幂等检查。

### 5.5 配置与密钥

模型密钥的来源按顺序解析：

1. 环境变量 `AITEST_MODEL_KEY`；
2. 用户级配置 `%APPDATA%\aitest\config.json`；
3. 都没有 → `doctor` 报“未配置”，AI 步骤标不可用。

- 工作空间只存 `model.base_url`、`model.name`、`timeout` 等非敏感项，不存密钥；
- 密钥不写入日志、证据、导出、错误信息，进入输出前统一脱敏；
- `doctor` 显示密钥来源（环境变量/用户配置/未配置），不显示密钥本身；
- 模型调用失败时只报状态码与脱敏后的地址，不回显请求头；
- 后续可换系统凭据库，解析顺序与调用方接口不变。

### 5.6 运行环境准备

扩展首次使用时按顺序找可用的 Python，任一步成功即停：

1. Trae 设置里的 `aitest.pythonPath`；
2. 机器上已有的合格 Python（版本 ≥3.11，能 `import aitest`，能执行 `aitest --version`）；
3. 都没有 → 自动准备：
   - 下载便携版 Python 到 `%APPDATA%\aitest\runtime\<版本>\`；
   - 在其中创建 venv；
   - 用 VSIX 自带的 wheel 执行 `pip install --no-index`，不依赖 PyPI；
   - 校验 SHA256，失败即停。

规则：

- 准备过程显示进度和失败原因（网络、磁盘、权限、校验），不假装完成；
- 准备完成后后续启动不再联网；
- 插件升级时校验 wheel 版本与已安装版本，不一致才重建；
- 已有合格 Python 的用户完全跳过下载；
- 不自动降级到旧版本，不静默改用其他解释器。

## 6 数据文件

### 6.1 工作空间布局

```text
workspace/
  workspace.json
  projects/<project_id>/
    project.json
    tasks/<task_id>.json
    plans/<plan_id>.json
    runs/<run_id>/run.json
    runs/<run_id>/evidence/<files>
    runs/<run_id>/cancel.requested   # 取消时出现，worker 轮询
    issues/<issue_id>.json
    reports/<report_id>.json
  backups/<timestamp>.zip
```

目录可以按实现微调，用户能一眼找到项目、运行和证据即可。

### 6.2 文件规则

- 每个文件一个对象，带 `schema_version`；
- UTF-8、缩进 2、键排序，方便 diff 和手改；
- 写入用临时文件 + `os.replace`，失败不留下半个 JSON；
- 证据只存相对路径、摘要、大小、media type；
- 日志/截图正文放证据目录，不塞进业务 JSON；
- 旧 `schema_version` 拒绝并提示转换或重建，不写自动迁移（H7）。

### 6.3 起步字段

下表是够用的起点，不是最终 Schema。字段可以按实际功能增补；删改字段时同步 CLI、面板和报告，别留两套。

| 文件 | 起步字段 |
| --- | --- |
| `workspace.json` | schema_version、workspace_id、created_at |
| `project.json` | project_id、name、root、goal、modules[]、revision |
| `task.json` | task_id、project_id、title、goal、acceptance_items[]、revision |
| `plan.json` | plan_id、task_id、scope（preset、module_ids、acceptance_item_ids）、rules_version、cases[]、status、revision |
| `run.json` | run_id、plan_id、scope（preset、module_ids、acceptance_item_ids、frozen_at）、confirmed_by、confirmed_at、status、pid、heartbeat_at、attempts[]、evidence_refs[]、analysis[] |
| `issue.json` | issue_id、project_id、status、severity、evidence_refs[]、revision |
| `report.json` | report_id、run_id、outcome、counts、changed_modules[]、unmapped_files[]、evidence_refs[]、opinion（by/at/text）、revision |

字段以 `models.py` 为准；文档不复制全部枚举。

## 7 Runner 与适配器接口

三者只需要一个统一的返回形状，方便 cli/core 汇总、面板展示。下面的字段够用即可，实现时可以增减，不必做成完整协议。

### 7.1 Runner

```text
RunnerRequest:
  project_root, workdir, command/script, env_refs, timeout_seconds

RunnerResult:
  status: passed|failed|blocked|error
  exit_code, stdout_ref, stderr_ref, artifacts[], assertions[], error
```

- Runner 返回结果，不直接写 `run.json`；由 cli/core 合并；
- 大输出写 `runs/<run_id>/evidence/`，结果只存引用；
- 超时/缺依赖/不可达分别标 `blocked`/`error`，不写成 passed。

### 7.2 GitHub

```text
read(repo, ref) →
  change: {repo, branch, commit, prs[], checks[], deployment, fetched_at}
```

- 认证复用 `gh` CLI：通过 `gh api` 读取，插件不保存、不读取 token；
- 只发 GET；不写 GitHub、不接 Webhook；写权限即使存在也不使用；
- `doctor` 检查 `gh` 是否存在、是否已登录、能否读取目标仓库；缺失或未登录时给安装/登录指引，由人执行；
- 记录本次使用的账号与主机，写进证据；
- 失败返回结构化错误，不返回缓存冒充最新。

### 7.3 链路

```text
import(run_id, request_id, logs[], db_results[]) →
  nodes[]: {node_id, parent_id, type, status, duration, input_ref, output_ref, evidence_ref}
  assertions[]: {node_id, expected, actual, result}
  gaps[]: {node_id, reason}
```

- 只导入已有证据；不自动捕获、不插桩；
- 缺请求 ID/日志/DB 结果时写 gaps；
- 首错不一定是根因；定位只给已观测事实与未知范围。

### 7.4 链路数据来源

项目配置里声明数据在哪，插件只读不猜：

```json
{
  "link": {
    "request_id_header": "X-Request-Id",
    "log_paths": ["logs/app-*.jsonl"],
    "log_format": "jsonl",
    "log_fields": {"request_id": "trace_id", "module": "logger", "status": "level", "message": "msg"},
    "db_query": "psql -h ... -c \"SELECT * FROM orders WHERE request_id='{request_id}'\""
  }
}
```

- 日志只支持两种：JSON lines（按字段名取值）、文本 + 正则（按捕获组取值）；不做格式自动识别；
- 数据库只执行配置好的只读命令，命令和连接串从环境或用户配置取，不存密码；有超时和输出上限；
- 请求标识：HTTP runner 发请求时注入配置的 header；后端不回显时，允许用响应体正则提取；
- 两者都拿不到 → 标“无法可靠关联”，不拼接、不猜测；
- 不接 APM/日志平台，不内置数据库驱动，不解析 SQL。

解析默认值：

| 项 | 默认 | 说明 |
| --- | --- | --- |
| 时间窗口 | 运行前后各 5 分钟 | 可配置，避免扫整份日志 |
| 行数上限 | 5000 行 | 超出截断并标注“已截断” |
| 文件匹配 | 支持通配符，按修改时间从新到旧 | 如 `logs/app-*.log` |
| 编码 | UTF-8 优先，失败回退 GBK | 可配置覆盖 |
| 请求 ID | 精确匹配 | 不做模糊匹配，避免串请求 |
| 多文件命中 | 全部保留，按时间排序 | 同一请求跨文件时可拼接 |

匹配不到时标“未找到该请求的日志”，不用相邻请求替代。

## 8 大型项目与多框架支持

| 层 | 插件做法 | 项目需提供 |
| --- | --- | --- |
| L1 | 调构建/启动命令 | 入口、依赖、环境 |
| 前端测试 | 调 npm test/vitest/jest，导入 JUnit/JSON | 测试命令 |
| 前端 L3 | Playwright 适配器或人工步骤 | 前端、账号、选择器 |
| 后端测试 | pytest/Maven/Gradle/npm test + JUnit | 命令、环境、数据 |
| 接口/集成 | HTTP 串联 + 独立 DB 查询 | 地址、鉴权、DB 只读入口 |
| 链路 | 导入请求 ID、日志、DB 结果 | 请求标识与结构化日志 |
| 证据 | 保存日志/JUnit/截图/请求引用 | 文件或查询结果 |

大型项目一般需要这些信息（由项目自身提供，插件不猜）：

- 构建/测试/启动命令；
- 前端/后端地址；
- 测试账号与凭据引用；
- DB 查询入口；
- 模块/目录映射与忽略规则；
- 单次用例数、证据体积上限。

范围与性能：

- 按模块/目录/变更文件/验收项选范围；
- 不默认全仓扫描、不逐文件语义分析；
- 长任务后台执行 + `run.json` 状态；
- 结果流式写、证据按文件引用；
- 超边界明确提示，不假装能测。

一期支持一个试点组合：一种前端 + Playwright、一种后端 + 测试命令/JUnit、一种数据库只读查询。

不承诺：任意框架零配置适配、任意前端自动操作、自动插桩/跨服务追踪、自动准备测试数据、自动解决登录/验证码/权限、全仓全量语义分析。

## 11 实现约定（给 AI/开发者）

这些是经验约定，不是逐条卡人的门禁。遇到具体情况可以按“事实优先、改动最小、留痕”处理。

1. 一个文件尽量只承担一件事；太长、名词太多时再拆，不为了行数拆。
2. 不为单一实现预建 Protocol/Factory/Adapter；第二个真实实现出现再抽接口。
3. 不做常驻核心、数据库、提交引擎、迁移、索引、事件日志（H1/H2）。
4. 不写 `except Exception: pass`；捕获明确的、能处理的异常，其余上抛。
5. 不伪造成功、不把未知写成通过、不把未执行写成不适用（H4/H5）。
6. 业务 JSON 带 `schema_version`，写入尽量原子。
7. 证据存引用与摘要，正文放证据目录。
8. 大输出/长任务写文件或后台状态，别把 CLI/面板卡住。
9. 模型/GitHub/链路失败时，本地项目/计划/证据/问题/报告仍可用。
10. 新增功能先看能否只加 runner/adapter；改核心时在提交说明写一句原因。
11. 测试断言行为/状态/证据为主，不数内部调用；有实际风险的审计问题补回归。
12. 同一件事别起两个命令名/字段/状态；扩展调用 CLI，不复制业务规则。

## 12 验证与门禁

每个工作包大致按这个节奏走，按改动大小取舍（这是工作习惯，不设合并门禁；真正不能破的是 §1.1 的硬约束）：

1. `ruff`、`mypy`；
2. 受影响的行为测试；
3. 涉及文件/备份的路径跑真实文件测试；
4. 快测保持顺手；全量按批次跑，结果如实记录；
5. 文档链接与状态同步。

验收：

- 真实 Trae 安装/绑定/执行/导出；
- 试点业务 L1/L2/L3 闭环；
- GitHub 只读关联与链路证据；
- 备份恢复；
- 模型/GitHub/链路不可用时明确降级。

不以全量测试通过、文档一致或模拟器通过代替真实 Trae 验收。

## 13 风险

| 风险 | 控制 |
| --- | --- |
| 删除系统级代码影响旧数据 | 只支持当前格式；备份后重建；旧格式拒绝 |
| 轻量存储查询变慢 | 数据量小，按目录直接列；真到瓶颈先做分页/缓存，不引入数据库（H2） |
| GitHub/链路重新变重 | 固定薄适配器；禁止 Webhook/自动追踪/平台化；失败不阻塞本地 |
| 模型 API 不可用 | AI 步骤失败/阻塞；人工、证据、导出继续 |
| AI 分析被当成结论 | 分析段不带状态字段，不自动建问题；报告里与断言结果分列 |
| 分析拖慢运行结束 | 异步生成，运行状态先落 `failed/blocked`，分析后续补写 |
| 大项目性能 | 范围选择、后台执行、结果流式写、证据文件引用 |
| worker 崩溃或被系统杀掉 | 心跳 + PID 检查标 `interrupted`，保留证据，不自动重跑 |
| 测试删得过多 | 质量检查：变异/覆盖/审计回归；关键路径不删 |
| AI 自动发布范围选错 | 报告固定显示已选/适用与未覆盖清单；改范围重跑 |
| AI 目标候选不贴切 | 候选附依据；始终保留自定义输入 |
| 需求再次膨胀 | MVP 18 FR 冻结；新增功能走适配器，不改核心 |

## 14 形态底线

下面几条就是 §1.1 的 H1/H2，单独列出来是为了在实现时一眼看到。确实遇到非做不可的场景，先提出来讨论，不要顺手实现。

1. 常驻核心进程、命名管道、后台守护服务；
2. 数据库或自建提交根、manifest、分片、索引、事件日志；
3. 格式迁移/回滚/注册表框架；
4. 多入口并发写同一业务文件、自建单写引擎、跨进程会话框架（§5.4 的一次性 worker 不算：它只写自己那次运行的目录）；
5. 计划许可账本、逐动作授权、A—D 证据等级、功能×维度覆盖契约；
6. 账号、上传、共享审核、平台接收端进入插件内核；
7. MCP 多协议、自动浏览器捕获、跨服务/函数级追踪。

外部依赖：

- 模型 API：必需；
- GitHub：一期必需薄适配器（只读）；
- 链路：一期必需薄证据导入（不做自动追踪）；
- 失败时降级，不阻塞本地核心。

## 15 完成定义

1. 插件只依赖 Trae 扩展 + Python CLI + 文件工作空间；
2. 无常驻核心、数据库、提交引擎、迁移框架、许可账本、证据等级；
3. MVP 18 FR 可用，核心闭环、GitHub 关联与链路证据在真实 Trae 中跑通；
4. 快测保持顺手，全量测试能在一次工作间隙内跑完，关键路径的质量门禁通过；
5. 旧系统级文档与代码归档，不再出现在现行路径；
6. 未完成/未验证项明确标注，不写成通过。
