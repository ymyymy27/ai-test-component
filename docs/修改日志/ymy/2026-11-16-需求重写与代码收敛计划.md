日期：2026-11-16

状态：执行计划；完成情况以提交记录、测试结果与验收台账为准。

## 1 目标

把仓库从“旧 17 FR + 多次 AI 扩写”收敛到已确认的一期基线：

- **21 FR / 26 条验收草案**（旧 35 AC 仅历史）；

- GitHub 与链路工具纳入一期；

- 一次范围确认 + 动作日志；
- 保留覆盖、删除 A—D 证据等级；
- 只支持当前存储格式 + 备份；
- 模板保留为规则预设。

完成标准：

1. 需求、架构、设计、验收、代码使用同一套 FR/状态/字段；
2. 旧设计（许可账本、证据等级、迁移框架、账号/上传一期范围）不再出现在现行合同与代码路径；
3. GitHub 与链路有一期最小实现与验收场景；
4. 每阶段有可复核的验证记录，不用“文档一致”代替真实执行。

### WP6 功能分层与模块化单体（P1，新增）

目标：按功能组织源码，但不做微服务、不按功能复制存储/合同/事务。采用“共享内核 + 平台层 + 功能包 + 单一装配入口”。

| ID | 任务 | 涉及范围 | 完成标准 |
| --- | --- | --- | --- |
| WP6-01 | 固定共享内核 | `shared/`：ID、错误、canonical JSON、时间、安全/脱敏 | 只放稳定、无业务语义代码；业务规则不得进入 |
| WP6-02 | 固定平台层 | `platform/file_store`、`platform/model`、`platform/github`、`platform/link` | 多功能共用的技术能力只在这里；不被单个功能独占 |
| WP6-03 | 划分功能包 | `features/{project,planning,execution,evidence,review}` | 每个功能拥有规则、用例、功能端口/适配器、只读 DTO |
| WP6-04 | 单向依赖规则 | features 之间、features→platform、interfaces→bootstrap | 禁止循环；只允许 planning → execution → review/evidence 等已登记方向 |
| WP6-05 | 架构测试 | `tests/architecture` | 禁止功能互相 import 内部模块；禁止 shared 出现业务规则；禁止 platform import feature |
| WP6-06 | 单一事务入口 | 工作单元/提交协调器留在共享层 | 功能只 stage，不各自提交；跨功能用例仍走同一提交边界 |
| WP6-07 | 跨功能只读投影 | 报告/面板查询端口 | 报告不 import 功能内部对象，只读 DTO/查询端口 |
| WP6-08 | 测试组织 | 功能内单测 + 跨功能集成/验收 | 功能测试不替代跨功能验收；测试目录跟随功能边界 |

约束：

- 不做大爆炸式目录重排；先完成 WP3 删除，再移动仍然存活的代码。
- 每次移动保持行为不变，移动与逻辑修改分开提交。
- 不按功能拆数据库/文件存储；存储仍是单一平台层。
- 不按功能复制规则；覆盖、状态、证据、问题关闭只保留一份。
- 不允许 `shared/` 变成第二个单体；只放稳定无业务语义内容。

执行时机：WP3 删除完成后、WP4 新增 GitHub/链路之前。新能力直接按目标结构落地，避免先写进旧层再搬。


### WP7 测试重构与有效性（P0，新增）

问题：当前 5,238 节点、约 9.4 万行测试，全量约 1.5 小时，但审计发现的真实问题几乎都不是全量测试先发现的。说明测试数量大、方向和断言强度不对：大量测试覆盖死实现、实现细节和防御分支，缺少需求级行为、故障注入和真实宿主验证。

目标：

- 默认开发回路 ≤2—3 分钟；
- 存储/恢复分层 ≤5 分钟；
- 全量 nightly ≤10—15 分钟，硬上限 20 分钟；
- 节点数不是目标；以分支覆盖、变异得分、注入缺陷发现率、真实验收通过数为目标。

| ID | 任务 | 完成标准 |
| --- | --- | --- |
| WP7-01 | 测试分层 marker | `unit`／`contract`／`storage`／`host`／`slow`／`acceptance`；默认只跑快层 |
| WP7-02 | 命令与 CI 分层 | PR 跑受影响模块 + 快层；storage/host 单独任务；全量 nightly |
| WP7-03 | 删除死代码测试 | 死模块删除后对应测试同步删；不保留“测试死实现”的绿色 |
| WP7-04 | 去重与行为化 | 同一规则只留一个行为测试；断言业务结果/状态/证据，不数内部调用 |
| WP7-05 | 加速夹具 | 内存底座用于应用层；工作空间模板复用；非耐久测试跳过 fsync/全量核验 |
| WP7-06 | 故障注入 | 提交中断、fsync 失败、材料损坏、断连、恢复各保留少量真实文件测试 |
| WP7-07 | 变异测试 | 对领域判定/覆盖/状态迁移跑变异测试，领域规则变异得分目标 ≥70% |
| WP7-08 | 需求级验收 | 21 FR/26 AC 中一期必测项有可执行端到端脚本；真实 Trae/GitHub/链路单独标记 |
| WP7-09 | 审计回归 | 每个已确认审计问题至少一条回归测试；修复提交必须带对应用例 |
| WP7-10 | 指标门禁 | 记录默认层耗时、storage 层耗时、分支覆盖、变异得分、注入缺陷发现率；禁止用节点数代替质量 |
| WP7-11 | 测试预算硬门禁 | fast >3 分钟、storage >5 分钟、全量 >15 分钟即失败并定位最慢用例；禁止靠加机器掩盖 |
| WP7-12 | 真实文件测试预算 | 真实文件/迁移/恢复用例控制在约 60—100 条；其余应用层用内存底座或模板工作空间 |

原则：

- 不追求“每个函数一个测试”；按风险和需求组织。
- 不 mock 被测对象；只在端口用 fake，存储/恢复用真实文件。
- 不为不可能状态和防御分支写测试；删掉对应代码后再删测试。
- 每个测试必须能回答“失败时说明哪个需求/不变量被破坏”。
- 节点数下降不自动等于质量提升；必须同时看变异得分和真实验收。

执行时机：WP7-01/02 可立即开始；WP7-03/04 跟随 WP3；WP7-06/07 跟随 WP6；WP7-08 跟随 WP4。


## 5 执行顺序

1. **WP1**：先冻结需求与验收，避免后面继续按旧 AC 改。
2. **WP2**：先改架构合同，再改代码；设计只改对象/状态部分。
3. **WP3**：按“许可 → 等级 → 迁移 → 死代码 → 统一/性能”顺序，每步独立提交。
4. **WP7-01/02**：先建立测试分层与默认快测命令，后续所有改动都走快层。
5. **WP6**：删除完成后，按功能边界重排存活代码；移动与逻辑修改分开提交。
6. **WP4**：GitHub 与链路按新功能结构实现，避免先写进旧层再搬。
7. **WP7**：随 WP3 删死测试、随 WP6 做行为化/故障注入、随 WP4 补需求级验收；全量 nightly。
8. **WP5**：最后压台账、折叠规划、收敛文档与测试。

依赖关系：

- WP3-01/02/03 依赖 WP2-01/02/03 的合同先定。
- WP1-03/04 依赖 WP1-01。
- WP4-01/02 依赖 WP2-04/05。
- WP5-05 可在任何阶段并行准备，但不阻塞功能。

## 6 验证门禁

每个工作包完成时必须：

1. `ruff check .`、`mypy` 通过；
2. 受改动路径的既有测试通过；
3. 合同/架构/恢复测试按影响范围通过；
4. 文档链接、`check_docs_facts --full` 通过；
5. 删除类改动额外验证：无生产引用、启动/恢复路径可用；
6. 新增能力：至少有组件级真实进程/文件测试，并明确未做真实 Trae/真实仓库验收。

全量 `pytest tests` 只在 nightly 或明确验证批次执行；不以分块结果冒充全量。

## 9 完成定义

一期收敛完成需同时满足：

1. 21 FR 在需求、架构、设计（非界面部分）、功能清单中编号与语义一致；
2. 新 26 条验收场景全部有明确状态；`verified` 必须有真实环境证据；
3. 代码中不再存在许可账本、证据等级、迁移框架的现行路径；
4. GitHub 与链路有一期最小实现和验证记录；
5. 模板保留但不再形成第二套发布门禁；
6. `ruff`、`mypy`、合同/架构/恢复测试、文档检查通过；
7. 真实 Trae、GitHub、链路试点中未完成的部分明确标“未验证”，不写成通过；
8. 功能包边界由架构测试强制：无循环依赖、无 shared 业务规则、无 platform 反向依赖、无功能各自提交事务；
9. 默认测试层在开发机 ≤3 分钟；全量 nightly ≤15 分钟；有耗时、分支覆盖、变异得分与验收结果记录，不只报节点数。
