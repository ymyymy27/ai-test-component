## 一、已拍板的核心原则与架构分工铁律

### 1.1 核心分工铁律

| 角色 | 唯一职责（重构后绝不越界） | 绝对禁止事项 |
| --- | --- | --- |
| **确定性硬代码** | **当眼睛**（单遍仓索引、完整运行态 OpenAPI、真实环境探测）；<br>**当手脚**（隔离拉起与 Job Object 回收服务、Cookie/表单/上传 HTTP 执行、上下文精准脱敏、工作空间短锁原子读写）；<br>**当算盘**（AST 拦截水脚本、四态结论与 `S/M` 覆盖核算、稳定问题指纹、客观三分类裁判）。 | 禁止用关键词胡猜业务接口造假用例；禁止盲目按文本正则给产品定罪；禁止运行中偷偷篡改冻结计划；禁止删掉被测项目业务环境变量；禁止长锁里调 LLM 或网络。 |
| **AI（大模型）** | **理解项目与出题**（归纳业务测试地图、按完整 OpenAPI 与相关代码编写 `http:` / `script:` / `playwright:` / `manual` 用例）；<br>**诊断与排因辅助**（分析失败文本、产出四段式排因、在 `setup` 写错测试数据时通过修订草稿提出修复、判定复杂 IO 边界是否真实）。 | 禁止直接汇总最终四态结论或计算覆盖率；禁止改动 `verify` 阶段业务断言；禁止替代人类做执行前确认或填写验收意见。 |
| **人类（研发/测试）** | 核对配置草稿 → 选定范围 `S` 与验收准绳 `M` → 审阅确认计划与新修订 → 录入 L3 人工结果与最终验收意见。 | — |

   - 运行期间一旦脚本因测试数据格式错误（例如保留域名邮箱、缺必填关联字段报 400/422）在 `setup` 阶段失败，Worker 如实记录错误与阻塞状态；
   - 改造并复用现有 `plan.repair_case`（支持批量模式一次修复多条 `setup` 错因），生成**仅修改 `setup` 准备数据的新计划修订草稿**（经硬代码 AST 核对确认 `verify` 业务断言与预期零变动），交由人审阅 diff 确认后基于新修订**定向重跑失败/阻塞项**，无需新造冗余命令。
3. **补齐“多角色测试凭据引用”标准入口**：
   - 在项目配置中提供轻量的测试角色环境变量引用（仅存角色名与环境变量名，如 `admin -> AITEST_ADMIN_USER / AITEST_ADMIN_PASS`、`employee -> ...`，**严禁落盘明文密码**），供规划喂给 AI、`preflight` 校齐、脱敏系统纳入打码集，填补多角色 RBAC 测试的长期空白。

   - 先完成“阶段 1A：全栈删干净 `FR04`”，再进行“阶段 1B：纯后端大减法止血”，随后依次推进阶段 2、3、4；**上一阶段全量门禁全绿前，禁止开启下一阶段**。
5. **旧工作空间兼容性红线**：
   - 遵循 `AGENTS.md` “拒绝并提示转换或重建，不做静默迁移”原则，读取旧版不兼容记录时给出明确提示，不做隐晦静默迁移。
