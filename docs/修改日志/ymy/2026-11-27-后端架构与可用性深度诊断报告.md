# 后端架构与可用性深度诊断报告（2026-11-27）

> **审计范围**：`src/aitest/` 全部 **82 个 Python 模块（35,458 行代码）**、现行一期合同文档（18 FR / 32 AC），以及 `AgentSwarm-RBAC` 真实 Docker + 后端运行态两轮实测证据（修复前 `run_458bb4d2eb27` 与修复后 `run_0a05b7dc5cc7`）。
>
> **总定性**：当前产品底线工程（工作空间写锁、原子写、报告格式收敛、基础命令骨架）已经具备，**但核心“项目理解 → 测试规划 → 运行执行 → 失败裁判 → 问题沉淀”主链路存在系统性架构错位与大量致命缺陷，现阶段确实无法投入真实中大型项目生产使用。**

## 一、总评与核心追问直答

### 1. 为什么每次测真实大项目就露馅，感觉越修越多？

当前后端代码之所以不断在真实项目上“爆新缺陷”，不是因为漏了几行判断逻辑，而是同时踩中了两个结构性错误：

1. **职责彻底颠倒：硬代码在“猜业务、代做决策”，真正该守的底座却千疮百孔**
   - 代码里堆了数千行号称“免 AI 确定性”的正则猜测与模板规则（多语言正则抠路由、词表猜业务场景、死模板拼 HTTP 用例、正则猜前后端契约冲突、文本匹配改判失败原因）；
   - 这些规则在 555 个“自造极简温室单测”上表现完美，一旦遭遇真实大项目（多登录端点、表单/Query 传参、统一响应包装 `{code, data}`、多角色 RBAC、独立运行环境、Monorepo、`@pytest.mark.parametrize` 等），立刻集体失灵；
   - 与此同时，真正必须靠确定性代码打牢的基础能力（完整 OpenAPI 契约解析、安全与状态维持的 HTTP 执行器、精准凭据脱敏、问题签名去重、并发读写锁分层）却要么残缺、要么互相打架。

2. **两个关键追问的坦诚回答（不迎合、按事实定性）**

#### 追问 ①：“原因是不是插件太不相信 AI 了？”

**只说对了一半，而且把两半搞反了：**

- **确实过度不信任 AI 的地方（应该信、但硬代码一直在抢活）**：
  - 理解非标接口与业务流程、按完整 OpenAPI 写测试数据与请求参数、在 `setup` 准备数据写错时看懂 422 报错改对重试、分析失败到底是不是脚本自己发错了参数——这些事**本来必须由 AI 动脑完成**。
  - 现在的做法是：一边只喂给 AI 被截断、被去除了参数位置与约束的残缺信息，一边用死规则（`invariants.py`）和硬过滤（`_apply_suggested_tests`、`judge.py` 强制覆写 `http:` 错误假设）把 AI 写对的东西盖掉或压死。
- **绝不能信任 AI 的地方（必须由确定性硬代码死守，目前反而有漏洞）**：
  - 业务四态结论与 `S/M` 覆盖率统计、不许 AI 在 `verify` 阶段把失败断言改松凑通过、密码脱敏边界、人工执行前确认与防线守卫。
  - **真实现状的反讽**：当 AI 顺从地写了空断言或水脚本，或者遇到测试环境缺包时，部分护栏还能兜住；但当 AI 真的帮测试定位到问题时，死规则反手一巴掌否决 AI。**总结：硬代码应该只当“眼睛（采集完整真事实）、手脚（隔离安全执行）和算盘（守住底线与统计）”，把思考和写用例交还给 AI。**

#### 追问 ②：“我设计的 FR04 模板体系，是不是有问题、应该直接删掉？”

**结论：你的初衷完全对，但落地成的“模板审批子系统”确实应该直接砍掉。**

1. **先分清锅不是你背**：在 `AgentSwarm-RBAC` 里直接制造假缺陷单的，是后来新增的 `invariants.py`（写死逻辑自动造 HTTP 请求），不是你写入 `FR04` 的 `core/templates.py`。
2. **为什么仍建议直接砍掉 `FR04` 现有模板体系**：
   - **名存实亡（在核心主链里纯空转）**：核查测试计划生成核心 `src/aitest/runtime/plan_commands.py`（2,094 行），**全程零引用 `templates`**。`cmd_template_apply` 花掉一次大模型调用把 6 份公文式内置 JSON 逐条标记为 `applicable / not_applicable / unsupported / unknown`，存进任务目录并挂在报告末尾作附注——**AI 真正在生成测试用例时根本看不到它**，完全没有实现“提醒 AI 某类项目别忘事”的初衷；
   - **没有技术栈上下文的盲评**：`build_template_payload`（`src/aitest/core/templates.py:173-193`）只给模型传项目名、目标和验收项文本，连技术栈、路由和源码都没给，模型根本无法准确判断适用性；
   - **架构过重且与 `rules` 撞车**：为“提醒几条注意事项”建了 2 个 CLI 命令、6 份长篇官僚公文 JSON（含具体业务示例 `ticket-workflow`）、独立任务文件、独立计划版本变更逻辑与前端独立页签，与同一 `FR04` 下已有 `rules`（含 `ai_rules`、`steps_md`、`evidence_requirements`）功能严重重叠；
   - **正确替代方案**：删掉独立 `template.list / template.apply` 逐项审批流程，保留“提醒 AI 防漏测”的初衷——将其压缩为按技术栈自动注入 `plan.generate` 提示词的极简检查要点，或统一并入 `rules` 规则预设。

## 二、P0 致命架构缺陷全清单（16 项）

> 这一级的问题只要命中就会**直接毁掉结果可信度、破坏工作数据、锁死流程或使产品在真实项目上无法启动**，必须彻底重做或直接砍掉。

### A. 项目感知与契约层（4 项 P0）

#### [P0-1] 2,500+ 行“全语言正则静态路由与契约解析”属于伪编译幻觉，真实项目漏报/误报齐爆
- **大白话**：不用运行服务也不用语言 AST/编译器，纯靠几千行正则跨语言“硬抠”路由和前端调用，结果全仓库同名常量、同名 Schema 互相覆盖，主流多中间件写法全漏，再把残缺结果当成“100% 完整契约”拿去判失败。
- **精确位置**：
  - `src/aitest/core/context/py_routes.py:127-168, 217-330, 663-734, 760-959`
  - `src/aitest/core/context/contracts.py:144-256, 313-338, 388-403, 655-994, 1200-1452`
  - `src/aitest/core/project_context.py:541-629`
- **真实触发场景与破坏**：
  1. **全局命名碰撞**：`py_routes.py:139-140` 用全局扁平 `global_consts` 先到先得，多服务各自定义 `API_PREFIX` 会互相窜前缀；`242, 250` 硬猜子模块导出路由名一定是 `"router"`；`263-330` 与 `contracts.py:388-403` 按短类名覆盖 Pydantic/Zod 模型并草率标 `fields_complete=True`；`py_routes.py:663-734` 甚至塞了针对特定框架的 `_plugin_toml_prefix_for_file`。
  2. **多语言框架匹配极脆弱**：Express 带中间件 `app.use('/api', authMiddleware, router)` 直接失配丢前缀；NestJS 忽略全局前缀与版本；Go 嵌套 `Group`/跨文件路由丢失；Spring `@GetMapping` 带 `produces/consumes` 参数全部漏扫。
  3. **OpenAPI 解析双套分裂且丢弃核心字段**：静态 `_openapi_routes`（`contracts.py:187-256`）不支持 `.yaml/.yml`、忽略 `servers/basePath` 与全局 `security`；运行态 `_extract_runtime_openapi_routes`（`project_context.py:575-629`）**丢弃全部 `parameters`（query/path 参数位置）、非 JSON 媒体类型（form-urlencoded/multipart）、`required` 列表及字段 `format`**，且与静态输出格式不兼容（`auth="authenticated"` vs `"user"`、`fields` 为 `list` vs 逗号串）。
  4. **前端提取在真实包装下失效**：`contracts.py:1286` 仅支持同文件 `axios.create`，全仓通用的 `src/utils/request.ts` 跨文件调用 100% 丢前缀；`_balanced_group`（313-338）未跳过 JS `//` 注释导致单引号注释搅乱语法状态机；超过 1500 个 `.py` 文件按字母序直接 `break` 丢弃后面路由。
- **处置建议**：**推倒重做**——砍掉全语言正则强契约推断；将运行态/显式 OpenAPI（完整补齐 YAML、OAS2/3、`servers`、全局 `security`、参数位置、媒体类型与校验格式）作为唯一权威契约；静态扫描降级为弱提示，禁止产出 `severity="error"` 的阻断结论。

#### [P0-2] 服务探测硬编码单一模板仓库，多服务在 `detect` 与运行态内省中被静默截断
- **大白话**：没问清楚项目怎么启动，就套特定 GitHub 模板仓库的命令去猜（硬用 `uv run bash` + `18000` 端口 + `bunx vite` + `/api/v1/utils/health-check/`）；更离谱的是碰到多服务时只留第一个，直接把真正后端扔掉。
- **精确位置**：
  - `src/aitest/core/context/services.py:198-248, 250-326, 329-408`
  - `src/aitest/command_handlers/project_commands.py:310-327`
  - `src/aitest/core/project_context.py:646-657, 922-927`
- **真实触发场景与破坏**：
  1. `services.py:372-405` 为符合特定结构（`backend/app/main.py` + `frontend/package.json`）的仓库强生成模板专属命令（Windows 下 `uv run bash ...` 与未装 `bun` 的 `bunx vite` 直接报错）；`216` 行正则还容易把 `DB_PORT=5432`、`REDIS_PORT=6379` 误抓成 HTTP 健康端口；
  2. `project_commands.py:312-315` 处理多服务检测结果时只 `next(...)` 取第一个服务（常常是 `db`），把后端与前端全部丢弃；
  3. `project_context.py:646-657, 922-927` 在存在多个服务 URL 时，一旦先遇到前端 Vite 地址或邮件服务即 `break`，导致永远拿不到后端 OpenAPI。
- **处置建议**：**推倒重做**——彻底删除模板硬编码，无法从配置文件/Compose 确定的启动与健康地址必须留空交由用户确认；完整保留多服务配置并遍历/按 `role=backend` 优先探测 OpenAPI。

#### [P0-3] 无统一文件索引层，单次面板刷新引发 8~12 遍全仓遍历 + 20+ 次 `git` 子进程 + 过期缓存投毒
- **大白话**：多个模块各自扫自己的硬盘和 Git，互不共用结果，大型仓库打开项目或刷地图会瞬间卡死，更严重的是“改了代码却继续命中旧缓存”。
- **精确位置**：
  - `src/aitest/runtime/snapshot.py:146-175, 245, 351-368`
  - `src/aitest/core/code_graph.py:132-170, 927-934, 1260`
  - `src/aitest/core/project_context.py:143-242, 270-501`
  - `src/aitest/core/context/manifests.py:294-331, 418-696`
  - `src/aitest/core/git_engine.py:137-340`
- **真实触发场景与破坏**：
  1. `snapshot.py:157-166` 检查 `local_git.get("since_commit")`，但 `inspect_local_git` 返回体里根本无此字段，导致每次 `snapshot` 重跑两遍 10~15 次 `git` 子进程；
  2. 紧接着依次触发 `code_graph` 全仓扫 + 7 遍路由/前端 `os.walk` + 嵌套正则扫描，紧跟着 `cached_project_context` 不共享索引再重扫一遍 + 4~6 遍测试文件重复 `ast.parse`，最后 `build_capabilities_snapshot` 无缓存再扫一遍；Mock 判定还直接调无缓存的 `build_code_graph`；

- **处置建议**：**架构重做**——建立唯一只读仓库索引与带版本淘汰的共享缓存（记录脏文件 `mtime_ns + size`），修复 `since_commit` 丢失与 git 失败容错。

#### [P0-4] 跨模块字段名契约割裂，甚至公然用 `test_dependencies` 伪造 `missing_packages`
- **大白话**：上游输出的字典键名，下游换了个名字去读，导致核心大图裁剪全部按字母表乱裁、动态插件告警静默失效；更荒唐的是把“项目依赖清单”直接当成“缺少的包”报红灯。
- **精确位置**：
  - `src/aitest/runtime/snapshot.py:177-235` vs `src/aitest/core/code_graph.py:723-855, 968-976`
  - `src/aitest/core/project_context.py:889, 993-1010` vs `src/aitest/core/context/py_routes.py:948, 959`
  - `src/aitest/command_handlers/map_task_commands.py:387-399`
- **真实触发场景与破坏**：
  1. `snapshot.py:196, 205-212` 去 `code_graph` 读取不存在的 `node_id`/`path`/`api_route`/`backend_route`（实际是 `node_ids`/`file`/`layer`/`kind`），导致 300+ 节点裁剪完全失效并丢弃冲突高危节点；

- **处置建议**：**立即修复并清理伪指标**——对齐字段契约，删掉伪造的 `missing_packages` 映射。

### B. 测试规划、盲写与 AI 链路（4 项 P0）

#### [P0-5] `invariants.py` 确定性模板乱配验收项与假载荷，直接成为系统头号“假缺陷制造机”
- **大白话**：硬代码靠中文关键词瞎猜对应接口，往任意接口发硬编码假字段、拿错密码 401 冒充登录验收、不带账号请求接口去断言 403、只 ping `/health` 就标端到端联调通过，强塞进计划制造海量误报与假通过。
- **精确位置**：`src/aitest/core/invariants.py:217-968`、`src/aitest/runtime/plan_commands.py:1064-1097, 1287-1346`

## 六、分阶段重构建议（供决策执行）

1. **阶段 1：大减法止血与合同同步**

2. **阶段 2：重塑“眼睛与手脚”（感知、HTTP 执行器、环境与服务进程管理）**
   - 重做统一仓库索引与完整 OpenAPI 解析（补齐 YAML/参数位置/表单/格式）；

3. **阶段 3：重塑“算盘与大脑”（脱敏、锁模型、裁判、问题单与 AI 链路）**
   - 重做 `security.py` 边界脱敏、`judge.py` 三分类归责、`issues.py` 稳定签名、`workspace.py` 无锁异步 IO + 短锁落盘；

4. **阶段 4：建立“真实世界坑点”回归靶场 + 多栈实测验收**
