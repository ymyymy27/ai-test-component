# AI 主导合同冲突修订（2026-11-07）

## 1 触发与范围

设计草案 `docs/项目文档/一期/设计文档/03-AI主导与非开发者体验设计草案.md` 第 13 节列出与现行合同的冲突。本次按最小合同改动处理：

- 不新增 FR/AC 编号，一期仍为 17 FR / 35 AC，总计 25 FR / 52 AC；
- 只修订文本、判定公式和验收场景，不升级任何验收结论；
- 不同步实现代码；合同要求与当前代码行为不一致处，在验收登记中保持 blocked / untested / not_verified。

## 2 决策

| 冲突 | 决策 |
| --- | --- |
| `P1-AC20` 运行中修订 | 采用方案 A：`full` 运行中拒绝任何计划修改；运行中修订仅适用于 `on_demand`，只影响未执行步骤 |
| `P1-AC31` 逐动作确认 | 一次计划确认生成独立 `PlanExecutionGrant`；每个副作用动作仍保留 `ActionAuthorization` 记录；计划内且许可内自动执行，越界动作逐项确认；计划确认不替代授权记录 |
| `P1-AC24` 模板漏项 | 扩展为业务功能清单、`unknown`/未支持、功能×必要维度覆盖门禁；模板项改为提醒项处置 |
| `P1-FR04` 模板必测 | 模板项是提醒，不是固定必测清单；新增项目理解与业务功能清单；必要新增按覆盖缺口判定 |
| `P1-FR06` 计划覆盖 | 用例关联业务功能与必要维度；功能级覆盖由维度汇总；必要/可选新增分别进入 `full` / `on_demand` |
| 模板下限 `T` | 判定公式中的 `T` 替换为业务功能×必要维度集合 `B`；`M` 是覆盖 `B` 的冻结用例集；模板不构成下限 |

## 3 逐项变更

### 3.1 `P1-AC20`

- 场景改为：完整验证运行中尝试修改计划；另以按需自测修改未执行用例。
- 预期改为：
  - `full` 运行中拒绝任何计划修改，提示新建 `on_demand`，原运行保留为历史；
  - `on_demand` 允许在步骤边界修改未执行用例，运行中修订只影响未执行步骤；
  - 正在执行的步骤任何档位都拒绝修改；
  - 依据失效时暂停、列出需重跑用例，历史结论保留；
  - 删除必测或弱化断言仍被拒绝。

同步位置：需求文档 `P1-FR07` 运行中修订条、功能文档第 2/4 节、架构 01 §4、架构 05 验证矩阵、设计 02 §4.2.1。

### 3.2 `P1-AC31`

- 场景改为：一次计划确认后集中授权、许可内自动执行、越界动作逐项确认。
- 预期改为：
  - 一次计划确认生成独立 `PlanExecutionGrant`；
  - 每个副作用动作保留 `ActionAuthorization` 记录；
  - 计划内且许可内动作自动执行，越界动作逐项确认；
  - 授权来源区分 `plan_grant` 与 `human_confirmation`；
  - 计划确认不替代授权记录；输入/目标/凭据范围变化原授权失效。

同步位置：需求文档 §7 产品使用合同、功能文档第 10.7 节、架构 02 §6、架构 05 §9、面板与工作台设计。

### 3.3 `P1-AC24`、`P1-FR04`、`P1-FR06`

- `P1-FR04` 增加项目理解与业务功能清单；模板项逐项给出 `included`/`not_applicable`/`unsupported`，不能静默删除；清单缺 `unknown`、未支持或功能×必要维度缺口时阻止 `full`。
- `P1-FR06` 增加业务功能 × 必要维度覆盖；用例发布时关联业务功能与维度；AI 新增检查按是否填补覆盖缺口判定必要/可选。
- `P1-AC24` 场景与预期加入业务功能清单、`unknown`/未支持、功能×维度未覆盖；功能级“已验证”只在全部必要维度有效时成立。
- 能力与模板清单同步：模板项不是必测集合；`full` 覆盖 AcceptanceScope 内全部适用业务功能×必要维度。

### 3.4 判定公式

功能文档第 3 节：

- 旧：`T` 为模板适用必测条目映射的用例集，`full` 要求 `T⊆M`，统计“模板覆盖”。
- 新：`B` 为冻结范围内全部适用业务功能×必要维度对；`M` 为覆盖 `B` 的冻结必测用例集；`full` 要求 `M⊆S` 且每个 `b∈B` 至少一条 `M` 内用例有有效证据和独立核验；统计“业务功能覆盖”。
- 模板项只作提醒，不构成 `T` 或必测下限。

同步位置：功能文档第 3 节、架构 01 §4、架构 05 验证矩阵、设计 01 面板来源表。

### 3.5 架构与报告

- 架构 05 §9 增加 `PlanExecutionGrant`：计划内动作生成 `ActionAuthorization(source=plan_grant)`；越界动作仍需 `ApprovalChallenge` 和 `ConfirmationRecord`；许可撤销/过期/上游修订变化后未执行动作回到待授权。
- 架构 02 §6 明确每个动作仍逐项保存授权，计划驱动不新增无范围、无记录或永久的集合授权。
- 架构 03 报告快照增加授权来源、可信度；新增 `BusinessFunctionCoverage` 记录。
- 架构 00/06、设计 01/02 的主流程从“集中逐项授权”改为“计划级许可（越界逐项授权）”。
