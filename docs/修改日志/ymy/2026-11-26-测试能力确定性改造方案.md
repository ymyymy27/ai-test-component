## 0. 目标与边界

### 0.1 核心目标

> 在声明支持的能力与本次验收范围内，给出可信、可核对、不夸大的结论。

### 0.2 四个目标的分层

| 层级 | 目标 | 可验收定义 |
| --- | --- | --- |
| 核心结果（P0） | 不误测 | 声明支持范围内 `false_pass = 0`；环境/前置问题不判产品失败；可判定的弱断言不发布 |
| 结果质量（P1） | 覆盖透明 | 每个验收项有覆盖账本；未覆盖/不支持显式列出；不承诺绝对“不漏” |
| 默认路径约束（P1） | 插件级 | 默认不启动服务、不装浏览器、不跑容器、不常驻；深能力显式升级 |
| 实现策略（P2） | 复用经济 | 协议/引擎/项目产物优先复用；重型依赖不进默认路径 |

优先级：

> **不误测 > 覆盖透明 > 插件级（默认路径约束） > 多复用**

解释：

- 不误测是红线，宁可不判通过，也不猜；
- 覆盖透明是可验收的“不漏测”：缺口可以存在，但必须可见；
- 插件级约束默认路径，不能阻止用户显式升级去换覆盖；
- 多复用是手段，不是产品承诺。

### 0.3 结论必须可核对

每条结论必须同时具备：

- 证据（请求/响应/日志/截图）；
- 范围（`S/M`、未覆盖清单）；
- 来源（invariant/recipe/model/engine、事实来源）；
- 未知（`unknowns/unsupported`）。

四者缺一，不得写成“通过”。

### 0.4 两种“新问题”必须分开

| 类型 | 含义 | 处理 |
| --- | --- | --- |
| 被测项目的新缺陷 | 插件发现目标产品的真实 bug | 产品价值，越多越好 |
| 插件自身的新缺陷 | 假通过、误失败、误阻塞、计划失败、报告错误 | 本方案要收敛的对象 |

### 0.5 成功标准

1. 新项目首次运行：0 假通过、0 误阻塞、0 新增 C1；环境类失败必须先 blocked/复核，不得直接计入 failed；
2. 新发现只允许是 `unsupported`（能力未识别）或 `coverage gap`（覆盖不足）；
3. 每个 correctness 缺陷都有 fixture，CI 能拦住；
4. 加一个新栈只需 adapter/配方/fixture，不改判定核心；
5. 连续 3–5 个新项目不再产生新的 correctness 类。

## 1. 问题定义

### 1.1 插件缺陷反复出现的根因

| # | 根因 | 典型表现 |
| --- | --- | --- |
| G1 | 事实靠猜 | DRF router 漏路由、模板 baseURL 丢失、封装 fetch 跳过 |
| G2 | 生成靠模型 | 空 `http:`、`{var,path}`、FIRST_SUPERUSER、缺 status 断言 |
| G3 | 校验只查形状 | 负向 setup、凭证混入、错误结构被放行 |
| G4 | 判定可被改写 | 负向 401 被补认证改成通过、failed 被改成 blocked |
| G5 | 发现不沉淀 | 只修当前项目，没有类级机制与回归夹具 |

### 1.2 必须保持的产品硬约束

- 业务结论只有 `passed / failed / incomplete / not_applicable`；
- 未执行、未知、阻塞不得汇总成通过；空分母不显示 100%；
- 报告固定展示 `S/M` 与未覆盖清单；
- 判定只在 core 计算一次，面板/报告只读取；
- 凭据落盘前过滤，不进入日志、报告、导出；
- 旧计划/旧记录不静默迁移；
- 不引入常驻服务、数据库、消息队列。

## 2. 总体架构

```text
事实层
  ├─ 默认：静态读取（代码图、配置、README）+ 复用已运行服务
  └─ 升级：运行时内省（OpenAPI/resolver/url_map/router）
            + Playwright 抓包 + 契约/流量引擎（需用户确认）

生成层
  ├─ 不变量（CRUD/auth/状态码）
  ├─ 配方（高频形态）
  └─ 模型（业务特有语义）

约束层
  ├─ 五条红线
  ├─ 断言强度
  └─ 基线 gate

验证层
  ├─ 覆盖账本（advisory）
  ├─ 项目测试交叉校验（advisory）
  └─ fixture zoo + 固定项目组合

复用层
  ├─ 协议：OpenAPI / Playwright；GraphQL/gRPC 暂为实验性
  └─ 引擎：Schemathesis / RESTler 思路 / mitmproxy
```

原则：

- 事实、生成、判定、验证解耦；
- 栈相关逻辑只进适配器/配方，不进判定核心；
- **默认不改变环境**：不启动、不安装、不常驻；缺事实时问一次；测试本身仍可能写业务数据；
- 深度能力是动作，不是模式；
- 复用成熟引擎执行，自建层只做验收语义与结论。

### 2.1 默认行为与升级

不设“简单/完整”用户模式，只定义默认行为和升级动作：

| 场景 | 行为 |
| --- | --- |
| 打开项目 | 只读文件/配置；已有服务在跑则复用，不重复启动；用例仍可能写业务数据 |
| 缺事实且影响验收 | 提示一次：“允许启动服务读取真实接口吗？” |
| 用户拒绝/启动失败 | 回退静态，标 `unknown/uncovered`，不猜 |
| 需要浏览器/契约 fuzz | 用户点击“深度发现”，显式确认后执行 |
| 切换后 | 重新生成计划（新 revision），重新确认 |

T1–T4 是支持级别，可在概览/报告展示，但不作为用户可选模式；界面不提供模式选择。

### 2.2 AI 能力边界

AI 做五类事：

| 角色 | 任务 | 产物 |
| --- | --- | --- |
| 理解助手 | 拆验收项、识别歧义、建议覆盖维度 | clarification |
| 设计助手 | 写不变量/配方未覆盖的业务用例，并对已覆盖项提出非重复业务增强 | suggestion / case_proposal |
| 评审助手 | 弱断言、范围不匹配、负向凭证 | review_finding |
| 解释助手 | 失败假设、配置说明、报告叙述 | hypothesis |
| 执行助手 | 生成结构化动作/流程（环境修复、诊断、前端流程），受控执行 | action_proposal / frontend_flow |

AI 不允许：

- 决定路由、字段、认证、状态码；
- 判 `passed/failed`；
- 计算 `S/M`、覆盖率；
- 静默修改脚本语义；
- 决定唯一数据/隔离；
- 直接执行 shell、浏览器或全局安装，代替人确认。

关闭 AI 后，确定性链路必须仍能完整运行。

### 2.4 AI 参与增强（执行版）

本节是 §2.2/§2.3 的展开，不改变“AI 不判结论”的边界；新增的是 AI 工作台、工件生产、受控动作与质量评估。

#### 2.4.1 原则

1. **AI 提议，确定性层验收。**
2. **增加工件，不增加决定权。**
3. **没有证据就是 `unknown`。**
4. **风险分级授权：只读、项目内可逆、项目内执行、系统级、结论级。**
5. **动作必须可回滚；修复必须复测。**
6. **AI 产出必须去重，人工审核有预算。**
7. **所有 AI 能力先过 golden set，再进产品路径。**

#### 2.4.2 AI 工作台

```text
事实层（确定性）
  ├─ 路由/字段/认证/服务/依赖
  ├─ 探针、日志、证据
  └─ 四值结论、S/M、覆盖率、可信度

AI 工作台
  ├─ Context Builder：代码、日志、截图、验收项、历史运行
  ├─ Proposal Engine：用例、数据、补丁、诊断动作、环境动作、前端流程、报告草稿
  ├─ Validator：schema、证据、断言强度、去重、策略、风险、预算
  ├─ Human Gate：采纳/驳回/应用/批量决策
  ├─ Executor：runner / action engine / Playwright
  └─ Contribution Ledger：AI 生成了什么、被采纳多少、覆盖提升多少
```

工件生命周期：

```text
proposed → validated → accepted/rejected → applied → verified/rolled_back
```

所有 AI 工件统一带：

- `model`
- `prompt_version`
- `input_hash`
- `evidence`
- `confidence`
- `requires_user_confirmation`

统一输出结构：

```json
{
  "kind": "suggestion|clarification|hypothesis|review_finding|case_proposal|disposition|action_proposal|frontend_flow",
  "scope": {"project_id": "...", "task_id": "...", "case_id": "..."},
  "statement": "...",
  "evidence": ["..."],
  "confidence": "high|medium|low",
  "requires_user_confirmation": true
}
```

本节与 §4.7 是同一契约，以 §4.7 为唯一 schema 来源；新增 `action_proposal`/`frontend_flow` 已同步到 §4.7。

#### 2.4.3 能力矩阵

| 能力 | AI 产出 | 确定性验收 | 风险 | 优先级 |
| --- | --- | --- | --- | --- |
| 验收项抽取/歧义 | 可观察验收项、歧义、覆盖维度 | 原文引用、可观察性检查、人确认 | 低 | P1 |
| 既有测试映射 | 验收项 → 项目测试 | 测试存在、路径有效、去重 | 低 | P1 |
| 业务用例（缺口+增强） | 缺口用例 + 已覆盖项的非重复增强用例 | plan validation、断言强度、去重签名 | 中 | P1 |
| 数据构造器 | fixture/builder/清理脚本 | 唯一数据、隔离、清理可执行 | 中 | P1 |
| 计划评审补丁 | finding + 可应用 patch | schema、lint、diff 可读、人采纳 | 低 | P1 |
| 失败分诊 | 假设、证据、下一步 | 证据引用、结论词过滤 | 低 | P2 |
| 诊断动作 | 查日志、重放请求、加探针 | 动作白名单、只读优先、人确认 | 中 | P2 |
| 脚本/选择器修复 | 修复 diff | AST、断言不减弱、重跑 | 中 | P2 |
| 环境依赖修复 | 结构化动作：argv/cwd/env/rollback | 项目内、lockfile、确认、回滚、复测 | 高 | P3 |
| 前端流程 | Playwright 流程/选择器 | localhost、隔离数据、确定性断言、截图/trace | 高 | P4 |
| Mock 真实性 | 真/Mock/混合/unknown + 依据 | 读取预算、证据、unknown 降级 | 中 | P2 |
| 报告/问题/交付 | 事实草稿 | 事实-only、结论词过滤、人编辑 | 低 | P5 |
| 贡献统计 | 生成/采纳/覆盖提升/修复结果 | 只统计，不改结论 | 低 | P5 |

#### 2.4.4 用例生成策略

```text
验收项
  → 不变量/配方生成结构用例
  → AI 读取“已覆盖结构 + 未覆盖维度 + 业务语义”
  → AI 生成缺口用例 + 非重复增强用例
  → AI 数据构造器
  → AI 评审 patch
  → 去重签名
  → plan validation
  → 人确认
  → 运行
```

规则：

- **缺口必补 + 已覆盖项的非重复业务增强**；不要求 AI 全覆盖。
- 去重签名：`item_id + scenario_type + assertion_target + data_shape`。
- AI 用例必须引用验收项原文；引不上标“未证实”。
- AI 用例带 `generation.source=model`；配方/不变量不重复生成。
- 弱断言 HTTP 用例不发布；脚本弱断言只作 advisory。
- 数据构造器必须唯一、可清理、可隔离。
- 未覆盖项进 `coverage_ledger`，不能靠 AI 猜一条补上。

#### 2.4.5 关键闭环

**计划闭环**

```text
验收项 → 不变量/配方 → AI 缺口+增强用例 → 数据构造器
→ AI 评审 patch → 去重 → plan validation → 人确认 → 运行
```

**失败闭环**

```text
失败 → AI 分诊 → 假设 + 证据 → 诊断动作/修复补丁
→ 策略校验 → 人确认 → 执行 → 重跑原失败用例
→ 通过记录；失败回滚/保留假设
```

- AI 不返回 verdict；`inconclusive` 收敛为 `incomplete`。
- 修复最多 1–2 次；断言不能减少/放宽；原始失败证据保留。

**环境修复闭环**

```text
doctor/失败 → AI 判断缺包/版本/端口/环境变量/服务
→ 结构化动作（argv/cwd/env/rollback）
→ 策略引擎：项目内、lockfile、禁止全局/sudo/任意 URL
→ 人确认 → 快照 → 执行 → 健康检查/smoke/原失败用例
→ 成功记录版本 diff；失败回滚
```

- Python 只动项目 venv；Node 只动项目包管理器与 lockfile。
- 系统级依赖只解释，不自动装。
- 环境改动必须进报告。

**前端闭环**

```text
AI 读路由/组件 → 生成 Playwright 流程与选择器
→ localhost 隔离浏览器执行 → 截图/trace/网络/控制台证据
→ 确定性断言 → 失败时 AI 提选择器/等待修复
→ 重跑；仍失败标 incomplete/unknown
```

- 只允许本地/测试环境，禁止生产域名。
- 使用测试账号和隔离数据；默认 headless。
- 选择器优先 role/label/testid；写流程不重试，只读流程可有限重试。

#### 2.4.6 权限与安全

| 风险级 | 例子 | 授权 |
| --- | --- | --- |
| R0 只读 | 读代码、日志、页面 | AI 可自动 |
| R1 项目内可逆 | 装项目依赖、改 `.env`、生成 fixture | 人确认 + 回滚 |
| R2 项目内执行 | 起本地服务、跑 Playwright | 人确认 + 超时 + 证据 |
| R3 外部/系统 | 全局安装、sudo、生产域名、外部 API | 不允许 AI 执行 |
| R4 结论 | verdict、S/M、问题关闭、验收意见 | 只允许人/确定性 core |

硬规则：

- 不把凭据正文放进 prompt/日志/截图。
- 不访问生产环境，不下载未知文件。
- 不执行任意 shell；只执行结构化 argv。
- 每个动作有超时、快照、回滚、审计。
- 一次确认只覆盖一个动作/会话。
- 代码/日志/README 都是不可信输入，不能改变工具策略。

#### 2.4.7 质量与指标

每个 AI 能力必须有 golden set：

- 验收项抽取：歧义、漏项、不可观察项
- 用例生成：可执行率、重复率、弱断言率
- 测试映射：映射准确率、漏映射
- 修复补丁：重跑通过率、断言削弱率
- 失败分诊：根因命中率、误导率
- 环境修复：回滚率、复测通过率
- 前端流程：稳定通过率、flake 率
- 报告草稿：结论词出现率、事实错误率
- 影响面/测试选择：受影响项召回率、误选率、scope 缩减率
- 测试代码评审：弱断言/过 Mock 命中率、误报率
- 偶发/CI 分诊：簇命中率、误导率、复跑确认率
- onboarding：命令可执行率、事实错误率
- 权限矩阵：角色/资源/操作覆盖、缺失负向场景
- 契约 diff：受影响端点/字段/测试召回率
- 视觉/a11y：确定性规则外的 finding 准确率、误报率

评测方式：

- 录制模型响应，CI 不依赖真实模型。
- 真实模型只做 nightly/发布前 smoke。
- 20–30 个任务覆盖：歧义需求、CRUD、权限、业务规则、环境错误、前端流程、偶发失败。
- 先测基线，再设门槛；不拍脑袋写绝对数。

硬门禁：

- schema 合法率 100%
- 用例/补丁证据引用率 100%
- 发布计划中弱断言率 0
- exact duplicate 用例率 0；semantic duplicate ≤5%（详见 §2.4.9）
- `false_pass / false_fail` 不得回退
- 修复后必须重跑；失败必须回滚或保留失败

| 指标 | 说明 |
| --- | --- |
| AI 工件采纳率 | 用例/补丁/诊断被接受的比例 |
| 覆盖提升 | 相对纯确定性层的新增覆盖维度 |
| 定位时间 | 从失败到根因假设/修复的时间 |
| 修复成功率 | 应用后重跑通过的比例 |
| 回滚率 | 环境/脚本修复失败回滚比例 |
| 假通过/误失败 | 不因 AI 参与而回退 |
| AI 弃权率 | 标 unknown/inconclusive 的比例 |
| 人工修改率 | AI 产出被人改动的比例 |
| 审核负载 | 每任务 AI 提案数、处理时长 |

AI 工件存储：

- 计划建议：`plan.ai_expectations`、`plan.ai_reviews`；
- 运行假设：`run.ai_hypotheses`；
- 决策：`run.ai_decisions`、`Confirmation.ai_decisions`；
- 数据构造器/修复补丁/诊断动作/环境动作/前端流程：计划阶段进 `Plan.ai_artifacts`，运行阶段进 `Run.ai_artifacts`；审计明细写 `plans/<plan_id>/revisions/<revision>/ai/` 或 `runs/<run_id>/ai/`；带状态、证据、执行结果；不进业务结论字段；
- 贡献统计：由报告从上述记录计算，不另存业务结论。

#### 2.4.8 不做什么

- 不让 AI 判结论、算覆盖、关问题。
- 不让 AI 直接执行 shell、全局安装、sudo、访问生产。
- 不让 AI 代替确认、服务启动、依赖安装许可。
- 不让 AI 生成无证据的用例/补丁/报告。
- 不让 AI 无限修复、静默重跑、放宽断言。
- 不用 AI 调用次数冒充参与度。

#### 2.4.9 工件、动作与预算契约

**通用工件对象**

```text
AIWorkItem
  work_id, kind, scope{project_id,task_id,run_id,case_id},
  input_facts, proposal, evidence[], confidence, risk,
  requires_user_confirmation, status,
  model, prompt_version, input_hash, created_at
  kind = suggestion|clarification|hypothesis|review|case|data_builder|patch|diagnostic|environment|frontend|report|impact|test_review|onboarding|permission_matrix|contract_diff|flaky|ci_triage|visual_review

AIActionProposal
  action_id, work_id, target, argv[], cwd, env{non-secret only},
  timeout_seconds, expected_effect, risk,
  rollback{argv[],cwd,snapshot}, network_policy,
  idempotency_key, requires_user_confirmation, status
  target = python_venv|node_modules|service|browser|config|data

AIArtifact
  artifact_id, work_id, kind(case|data_builder|patch|diagnostic|
  environment|frontend|report|impact|test_review|onboarding|
  permission_matrix|contract_diff|flaky|ci_triage|visual_review),
  case_ids[], content, evidence[], validator_result, applied_at, result, rollback_ref

AIContribution
  task_id, run_id, cases_generated, cases_accepted,
  coverage_lift{}, reviews_accepted, reviews_rejected,
  hypotheses_confirmed, repairs_applied, repairs_rolled_back,
  actions_applied, actions_rolled_back, time_observed{}
```

状态机：

```text
proposed → validated → accepted/rejected
  → applied → verified
  → failed → rolled_back
```

存储：

- `Plan.ai_artifacts`：计划阶段生成的 data_builder/patch/frontend flow 等，可选，旧计划默认 `[]`；
- `Run.ai_artifacts`：运行阶段生成/应用的工件，可选，旧运行默认 `[]`；
- `AIWorkItem`/`AIActionProposal` 审计记录写 `plans/<plan_id>/revisions/<revision>/ai/` 或 `runs/<run_id>/ai/`；
- 所有工件带 `evidence`；没有证据不能进 `accepted`。

**数据构造器生命周期**

```text
DataBuilder
  builder_id, case_ids[], language, setup{argv,cwd,env},
  cleanup{argv,cwd,env}, unique_prefix, resources[], evidence[],
  status(proposed|validated|accepted|applied|cleaned|cleanup_failed)
```

规则：

1. `plan.generate` 把 AI 数据构造器写入 `Plan.ai_artifacts`，并绑定 `case_ids`。
2. 计划确认时人确认数据构造器；未确认不执行。
3. `run.start` 把计划工件复制到 `Run.ai_artifacts`；worker 在该用例执行前运行 `setup`，执行后运行 `cleanup`。
4. `unique_prefix` 必须由确定性层生成或校验；禁止生产数据。
5. 写用例清理失败：该用例标 `incomplete`，后续写用例不再执行；报告显示 `cleanup_failed`。
6. 只读用例不要求清理；数据构造器不能修改项目源码或全局环境。
7. 数据构造器失败不影响未依赖它的用例；依赖它的用例标 `incomplete`。

**计划评审 patch 的应用路径**

```text
review_plan
  → plan.ai_reviews（status=pending，带 patch）
  → 人逐条采纳/驳回
  → plan.update(patch.cases + ai_review_decisions)
  → 服务端校验 patch
  → 接受 patch 应用，拒绝写 reason
  → 新 revision
  → 重新确认
```

规则：

- `plan.generate` 只写 `pending`；应用 patch 时由 `plan.update` 生成新 revision，并清空 `ai_reviews`/`ai_expectations`，同时清空绑定被改用例的 `ai_artifacts`（无法判断时全部清空）；决策明细写 `AIWorkItem` 审计，不把 `accepted/rejected` 写回计划字段（避免悬空）。
- 多条 patch 批量成一次 `plan.update`，避免 revision 抖动。
- 新 revision 必须重新确认；旧运行仍引用旧 revision。
- 不改变计划的评审决策可以留在 `run.ai_decisions` 作为审计；**应用 patch 必须走 `plan.update`**，不能借 `run.start` 改计划。

**环境/前端动作执行契约**

- 每个工作空间同一时间只允许一个**写动作**（环境修复、前端执行、修复补丁）；只读诊断可并行，但每任务有上限。
- `action_id` 是幂等键；相同 `target + argv + cwd + env` 重复提交返回已有结果，不重复执行。
- 动作状态：`proposed|validated|confirmed|running|succeeded|failed|rolled_back`。
- 每个动作必须有 `timeout_seconds`、`rollback`、`network_policy`、审计日志。
- 执行前做快照；执行后跑健康检查/smoke/原失败用例；失败回滚。
- 动作结果写入 `Run.ai_artifacts` 或 `plans/<plan_id>/revisions/<revision>/ai/`，报告可查。

**前端 flow 工件**

```text
FrontendFlow
  flow_id, base_url(localhost only), auth_ref,
  steps[{action,selector,value,wait,assert}],
  data_namespace, evidence[], max_repairs, status
```

规则：

- 只允许 localhost/测试环境；`base_url` 不在 allowlist 直接拒绝。
- `auth_ref` 只引用配置/SecretStorage，不写凭据正文。
- 选择器优先 role/label/testid；禁止依赖 nth-child 的脆弱选择器。
- 断言必须包含页面状态/文本/网络/控制台中的至少一项；找不到元素不能算通过。
- 选择器修复最多 2 次；仍失败标 `incomplete/unknown`。
- 写流程不重试；只读流程可有限重试。

**预算与配置**

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `model.ai.mode` | `assist` | `off` 走确定性；`legacy` 仅兼容；不暴露 UI |
| `model.ai.max_review_items` | 20 条/任务 | 按 severity/confidence 排序；超出截断并标 `truncated`；支持批量决策 |
| `model.ai.max_repairs` | 2 次/用例 | 脚本/选择器修复上限；超过保留失败证据 |
| `model.ai.max_tokens_per_task` | 继承模型预算 | 超预算降级确定性路径 |
| `evidence.mock.max_files` | 40 个文件 | 默认读取预算；可显式调高；报告记录实际值 |
| `evidence.mock.max_depth` | 3 层 | 超出标 `unknown`，不允许静默放宽 |
| `model.ai.action_parallelism` | 1 | 写动作串行；只读诊断可另行配置 |

配置落点：

- AI 配置落 `model.ai`（`mode`、`max_review_items`、`max_repairs`、`max_tokens_per_task`、`action_parallelism`、`model_tier`），不新增顶层配置段；
- Mock 读取预算落 `evidence.mock.max_files`/`max_depth`；当前实现为 240/3/120，P2 调为默认 40/3，`per_component_files` 受总预算约束；
- 旧配置缺段/缺键时使用默认值；`model.ai.mode` 只允许后端/项目配置，不暴露 UI；
- 配置值在 `project.config` 更新时校验类型和范围；非法值返回 `INVALID_REQUEST`；
- 配置变化不自动重跑，下一次计划/运行动作生效。

patch 格式：

- `AIReview.patch` 统一为 `{cases: [...]}`，内容是候选用例的完整对象，不使用 unified diff；
- `plan.update` 入参扩展为 `{plan_id, patch:{cases}, ai_review_decisions, expected_revision}`；
- `ai_review_decisions` 为 `[{review_id, decision: accepted|rejected, reason}]`；
- 服务端只接受计划中存在的 `review_id`；未知/重复 ID 返回 `INVALID_REQUEST`；
- 接受的 patch 合并进 `patch.cases`；拒绝只记录 reason，不改 cases；
- 新 revision 仍走 `plan.update` 的 `PLAN_STALE` 和任务契约校验。

动作策略覆盖：

- `DataBuilder.setup/cleanup` 和 `FrontendFlow.steps` 不能绕过策略引擎；它们必须分别包装成 `AIActionProposal`，走同一套白名单、超时、幂等、回滚、网络策略。
- 数据构造器只允许项目内测试数据操作；前端只允许 localhost/测试环境。
- 例外必须显式列入 allowlist，并在报告标“策略例外”。

审计存储：

- 计划阶段：`plans/<plan_id>/revisions/<revision>/ai/`；
- 运行阶段：`runs/<run_id>/ai/`；
- 每个审计文件带 `schema_version=1`、`model`、`prompt_version`、`input_hash`；
- 审计文件随计划/运行记录保留；`data.cleanup` 只清理临时材料，不删除业务证据；
- 写入前脱敏；`AIArtifact.content` 默认上限 256 KB，超出截断并标 `truncated`；`evidence` 只保留引用，不复制正文。

质量阈值：

- exact duplicate 用例率必须为 0；semantic duplicate 目标 ≤5%；
- 发布计划中弱断言率 0；
- AI 用例/补丁证据引用率 100%；
- schema 合法率 100%；
- `false_pass / false_fail` 不得因 AI 参与回退；
- 未达阈值时只允许 advisory，不允许进入 `accepted`。

`model.ai.mode=off` 的计划语义：

- 允许生成“零 AI 用例”的计划用于查看缺口；选中项全部进 `coverage_ledger` 的 `missing`；
- `run.start` 仍按空 S/无用例拒绝启动，不因 `off` 放松；
- 有确定性/显式用例时正常生成；没有时计划可存在，但不能执行。

Playwright 依赖：

- Playwright 与浏览器二进制只作为 P4 可选依赖，不进默认 wheel/VSIX；
- 未安装时 `propose_frontend_flow` 返回 `unsupported`，不阻塞确定性链路；
- 离线环境必须显式安装或跳过前端流程；报告标注“前端未执行”。

**AI 模式与降级**

- 默认 `assist`：AI 参与，但不改结论。
- `off`：不调用模型；计划由不变量/配方/显式 cases 生成，缺口进 ledger；`judge_failure` 走确定性规则；`judge_mock` 全 `unknown`；`summarize_report` 不生成；`repair_script` 不修。
- `legacy`：仅用于迁移旧行为，不作为新功能路径。
- 模型不可用：AI 建议为空；确定性链路继续；不能因 AI 不可用伪造用例或通过。
- 不提供用户可见的 `ai.mode` 模式选择。

**模型成本与隐私**

- 任务分级：分类/摘要/映射可用便宜模型；用例/补丁/环境/前端用强模型；可配置 `model.ai.model_tier=auto`。
- 按 `input_hash` 缓存；同一输入不重复调用。
- 单任务 token 预算；超预算降级确定性路径。
- 代码/日志/截图进 prompt 前脱敏；不发送凭据正文。
- 明确供应商数据保留策略；支持本地/企业模型选项；发送运行日志需用户同意。
- 记录模型名、prompt 版本、输入哈希，支持回放与对比。

**AI 贡献统计**

- 只统计被采纳的工件、覆盖提升、修复成功/回滚、定位耗时；不计调用次数。
- `time_observed` 只记录可观测时间，不做主观估算。
- 被拒绝/截断的提案不计入正向贡献，但计入审核负载。

#### 2.4.10 扩展 AI 能力（第二批）

这些是讨论过、但不属于 P0–P4 主线的 AI 能力。默认不阻塞主线，按优先级逐步接入。

| 能力 | 方法 | 输入 | AI 输出 | 确定性验收 | 风险 | 优先级 |
| --- | --- | --- | --- | --- | --- | --- |
| 变更影响/测试选择 | `analyze_change_impact` | diff、代码图、测试映射、验收项 | 受影响模块/测试/验收项 + 证据 | 依赖图/测试发现；不自动取消测试 | 中 | P1 |
| 测试代码评审 | `review_tests` | 测试文件、断言、验收项、运行历史、PR diff | 弱断言、过度 Mock、共享状态、负向认证问题 | lint、证据；不自动改项目测试 | 低 | P1 |
| 项目 onboarding | `onboard_project` | README、配置、测试、目录 | 启动/测试/环境/风险说明 | 文件引用、命令存在；不执行 | 低 | P1 |
| 权限矩阵提案 | `propose_permission_matrix` | 角色、认证、路由、验收项 | 角色×资源×操作矩阵 + 缺失负向场景 | plan validation；不自动发布 | 中 | P2 |
| 契约/schema diff | `analyze_contract_diff` | OpenAPI/schema diff、路由、测试 | 受影响端点/字段/测试 + 证据 | 解析器/diff；人工确认 | 低 | P2 |
| 偶发/多服务归因 | `analyze_flaky`、`cluster_failures` | 多次运行、服务日志、request id | 失败簇、假设、下一步 | 复跑/日志关联；不返回 verdict | 中 | P2 |
| CI 失败分诊 | `triage_ci_failure` | CI 日志、测试输出 | 失败簇、假设、下一步 | 复跑/证据；不返回 verdict | 低 | P2 |
| 视觉/无障碍 | `review_visual_a11y` | Playwright 截图、DOM | 视觉/a11y findings | 确定性 a11y 规则优先；advisory | 中 | P4 |

**变更影响/测试选择**

```text
diff → 依赖图/测试发现 → AI 语义映射 → 人确认范围 → 运行
```

- AI 可以建议“哪些测试/验收项受影响”，不能自动取消测试。
- 用户确认后写入本次 scope；空 S 仍按现有规则拒绝启动。
- 结果写入 `Plan.ai_artifacts`，报告展示“为什么选这些测试”。

**测试代码评审**

```text
测试文件/断言 → AI findings → 确定性 lint → 人编辑/采纳
```

- 不自动修改项目测试代码；只出 finding 或建议 patch。
- 重点：只断言 200、过度 Mock、共享测试污染、负向用例补认证。
- 结果用于计划评审/报告，不直接改结论。

**偶发失败与多服务日志**

```text
多次运行/服务日志/request id → AI 聚类 → 确定性复跑/关联 → suspected/incomplete
```

- AI 只给簇和假设；是否不稳定由复跑和证据决定。
- 多服务日志先按 request id/时间窗确定性关联，AI 只做归因说明。

**项目 onboarding**

```text
README/配置/测试/目录 → AI onboarding 卡 → 人查看
```

- 输出：怎么跑、测试命令、环境缺口、建议先测什么、风险点。
- 只读，不启动服务、不安装依赖。
- 由 `project.map.refresh` 生成 `projects/<project_id>/ai/onboarding.json`；`project.snapshot` 读取 optional `ai_onboarding`，不新增项目字段。

**权限矩阵提案**

```text
角色/认证/路由/验收项 → AI 矩阵 → plan validation → 人确认
```

- AI 提议角色×资源×操作矩阵和缺失的负向场景。
- 矩阵必须经计划校验；不自动发布、不自动补认证。

**契约/schema diff**

```text
OpenAPI/schema diff → AI 影响说明 → 确定性 diff/测试映射 → 人确认
```

- 输出受影响端点、字段、测试；证据引用 diff 行。
- 不自动改计划；需要时走 `plan.update`。

**视觉/无障碍**

```text
Playwright 截图/DOM → AI findings → 确定性 a11y/断言 → advisory
```

- 视觉问题只作 advisory；a11y 先跑确定性规则。
- 无确定性证据时标 `unknown/incomplete`，不能算通过。

**CI 失败分诊**

```text
CI 日志 → AI 聚类/假设 → 复跑/证据 → 不返回 verdict
```

- 只用于定位；不自动关问题、不改结论。

存储与 UI：

- 计划类：`impact_analysis`、`test_review`、`permission_matrix`、`contract_diff` 进 `Plan.ai_artifacts`；
- 运行类：`flaky_analysis`、`ci_triage`、`visual_review` 进 `Run.ai_artifacts`；
- 项目级 onboarding：`projects/<project_id>/ai/onboarding.json`，由 `project.snapshot` 返回 optional `ai_onboarding`；
- UI：范围页/计划页 `AIImpactPanel`/`AITestReviewPanel`/`AIPermissionMatrixPanel`/`AIContractDiffPanel`；结果页 `AIFlakyPanel`/`AICITriagePanel`/`AIVisualReviewPanel`；概览 `AIOnboardingCard`；报告页统一汇总；
- 所有扩展能力都走 `AIWorkItem` 审核/证据/预算，不新增独立工作台。

扩展执行路径：

- **影响面/测试选择**：主入口在 `ScopeView.vue`；AI 建议受影响验收项/测试，人确认后更新本次 scope，再 `plan.generate`。已有计划时应用建议会重新生成计划并重新确认；不自动取消测试。
- **测试代码评审**：在计划页展示 finding；不自动改项目测试；需要改用例时走 `plan.update`。
- **权限矩阵**：`AIPermissionMatrixPanel` 输出矩阵 + case proposals；人确认后作为 `plan.generate` 的显式 cases 或 `plan.update` patch，`generation.source=model`，新 revision 重新确认。
- **契约 diff**：只出 finding/受影响测试；需要改计划时走 `plan.update`，不自动改 scope。
- **CI 分诊**：CI 日志通过 `evidence.add` 挂到 run（或 `analysis.run` 的 `ci_log_ref`/`ci_log_text`）；`AICITriagePanel` 读取证据，输出 `Run.ai_artifacts`，不返回 verdict。
- **视觉/a11y**：Playwright 截图/trace 进 run evidence + `Run.ai_artifacts`；`AIVisualReviewPanel` 用 `EvidenceDialog` 打开；Playwright 不可用时标 `unsupported`。

## 3. 事实层

### 3.1 运行时内省

| 栈 | 运行时事实 |
| --- | --- |
| FastAPI | `/openapi.json`（路由、方法、参数、schema、状态码） |
| Django / DRF | URL resolver + `router.register` 展开 |
| Flask | `app.url_map` |
| Express | `app._router.stack`（应用可导出时） |
| Spring / Nest | OpenAPI / Swagger 端点 |
| 前端 | Playwright 跑主流程，抓真实网络请求 |

### 3.2 协议适配器

| 协议 | 覆盖的栈 | 能力 |
| --- | --- | --- |
| OpenAPI/Swagger | FastAPI、DRF Spectacular、Spring Boot、NestJS、.NET、Go、Rails、Laravel | 路由、方法、schema、必填、状态码 |
| GraphQL introspection（实验性） | Apollo、Hasura、graphene、Strawberry | query/mutation、字段、类型；尚无 fixture |
| gRPC reflection（实验性） | Go/Java/Python/C# gRPC | 方法、消息结构；尚无 fixture |
| Playwright 网络抓包 | 任意 Web 前端 | 真实请求、认证头、封装调用 |

### 3.3 静态兜底与未知

- 运行时不可用 → 静态提取；
- 静态也拿不到 → 记入 `unknowns`；
- `unknowns` 不允许当作“已通过”或“已覆盖”；
- 报告与计划确认页必须展示。

### 3.4 支持矩阵（支持级别）

| 级别 | 含义 | 典型栈 | 承诺 |
| --- | --- | --- | --- |
| T1 完整 | 运行时发现 + 路由/schema + 认证 + 不变量 + fixture | FastAPI、Django+DRF、Flask；Express 仅当 app 可导出 router（候选）；React/Vue 仅当有 Playwright UI fixture（当前未达） | 路由/字段/认证/CRUD/负向可确定性覆盖 |
| T2 协议导入 | 有 OpenAPI/Swagger 可导入路由、方法、schema、负向 | Spring Boot、NestJS、.NET、Rails、Laravel、Go | 完整性取决于规范，缺失进 unknown；启动与认证需配置；由 openapi_generic fixture 验证 |
| T3 静态部分 | 只能静态提取 | 无 schema 的 Python/Node 项目 | 只承诺静态事实，未知显式 |
| T4 明确不支持 | 不假装支持 | 当前不支持：移动端、桌面端、WebSocket 推送、消息队列 | 报告列出，未覆盖 |

规则：

- T1 必须有对应栈 fixture；T2 由通用 OpenAPI fixture 验证协议导入；GraphQL/gRPC 在 fixture 落地前只标实验性，不写进 T1/T2；
- 新增技术栈只加协议/启动/认证适配器 + fixture，不改判定核心；
- T1–T4 只用于框架/协议；依赖/外部/宿主用 D1–D4；
- 不维护“支持 50 个框架”的营销清单；条件不满足时按 T3 处理。

### 3.5 启动与认证适配器

| 类型 | 解决 | 例子 |
| --- | --- | --- |
| 启动适配器 | 项目怎么跑、健康检查 | Python venv + uvicorn/flask/django；Node npm/pnpm；Java mvnw/gradlew；.NET dotnet run；Go go run |
| 认证适配器 | 登录与凭证注入 | JWT Bearer、Session Cookie、API Key、OAuth client credentials、无认证 |

### 3.6 用户确认

计划确认页展示：

- 已识别的路由/认证/服务；
- `unknowns` 与 `unsupported`；
- 端点/认证/凭据修正沿用现有 `project.config`，在发现前完成；确认页表单不在本轮 S0–S7，另行追加 S2c；
- 修正结果通过重新生成计划进入快照，后续复用。

### 3.7 发现阶段的副作用

- 运行时内省/浏览器/引擎需要启动或访问服务，必须显式确认；
- 不能静默启动；
- 优先复用现有服务启动流程与日志；
- 服务起不来时回退静态，并写入 `unknowns`。

### 3.8 能力快照

```json
{
  "capabilities": {
    "backend": ["django"],
    "router": ["drf"],
    "auth": ["jwt"],
    "frontend_calls": ["axios-template"],
    "services": ["backend", "frontend"],
    "dependencies": [{"type": "redis", "level": "D1", "source": "docker-compose"}],
    "external_systems": [],
    "hosts": ["browser"],
    "level": "T1",
    "unknowns": ["frontend_wrapper"],
    "unsupported": ["drf_custom_action"],

```

画像随计划保存，不新建独立画像服务、缓存或数据库。

### 3.9 适配类型全景

“类型”不只指依赖。除应用框架外，还会遇到协议、依赖、外部系统、宿主环境和质量维度。方案把它们统一成“适配类型”，但只对能验证的给承诺。

#### 3.9.1 类型分组

| 大类 | 例子 | 分级 |
| --- | --- | --- |
| 运行时/框架 | Flask、Django、Express、Spring、React、Next、Electron | T1–T4 |
| 协议/接口 | REST/OpenAPI、GraphQL、gRPC、WebSocket/SSE、MQTT、Webhook | T1–T4 |
| 依赖/基础设施 | SQL、Redis、MongoDB、Kafka、S3、Mailpit、Vault | D1–D4 |
| 外部系统 | 支付、邮件/SMS、地图、AI/LLM、KYC、CDN | D1–D4 |
| 宿主/客户端 | 浏览器、移动端、桌面、容器、Serverless | D1–D4 |
| 质量维度 | 安全、性能、可靠性、一致性、a11y/i18n、合规 | 无级别，入覆盖账本 |

完整类型表见附录 C。

#### 3.9.2 分级 D1–D4（依赖/外部/宿主）

| 级别 | 能力 | 承诺 |
| --- | --- | --- |
| D1 完整 | 识别 + 启动/健康 + 复位/隔离 + 状态探针 + fixture | 可确定性覆盖依赖状态 |
| D2 基本 | 识别 + 启动/健康 + 复位 | 可隔离，但不能断言依赖内部状态 |
| D3 只识别 | 识别 + 连接，不可复位/探针（如托管云服务） | 只能靠唯一数据，报告标限制 |
| D4 不支持 | 不识别或不处理 | 报告列为 unsupported |

范围：D1–D4 只用于依赖/外部系统/宿主；框架与协议用 T1–T4；质量维度不评级，只进覆盖账本。

规则：

- D1/D2 必须有 fixture 或项目证据；没有不算；
- 默认只识别，不启动依赖；启动/复位需显式确认；
- 依赖不可用 → 相关用例 `blocked`，不判产品失败；
- 不能复位时，必须用唯一数据/命名空间，并在报告标“隔离受限”。

#### 3.9.3 控制面

不为每个产品写适配器，按控制面归类：

| 控制面 | 覆盖类型 | 操作 |
| --- | --- | --- |
| 数据库协议 | SQL/NoSQL/时序/图 | 连接串、迁移/清表、查询 |
| Redis 协议 | 缓存/KV | `redis-cli`、FLUSHDB/前缀 |
| 队列管理 API | Kafka/RabbitMQ/SQS | 清空、积压、死信 |
| 对象存储 API | S3/MinIO | bucket/前缀、HEAD、清理 |
| 邮件 API | Mailpit/MailHog | 收件箱查询/清空 |
| Mock HTTP | 第三方 API | WireMock/Prism/Mockoon |
| WebSocket/SSE | 实时 | Playwright/ws 客户端 |
| Appium/Playwright | 移动/桌面/SSR | UI 驱动 |

#### 3.9.4 复位与隔离

| 类型 | 推荐策略 |
| --- | --- |
| SQL | 迁移 + 种子/清表；唯一数据库或 schema；避免共享库 |
| Redis | `FLUSHDB` 或 key 前缀；不要 `FLUSHALL` 共享实例 |
| 队列 | 唯一队列/topic、清空、consumer group 隔离 |
| 对象存储 | 唯一 bucket/前缀，用例后清理 |
| 邮件 | Mailpit/MailHog API 清空收件箱 |
| 搜索 | 唯一索引/前缀 |
| 外部 HTTP | WireMock/Prism 场景复位 |
| 宿主 | 设备/容器/浏览器上下文隔离 |

#### 3.9.5 优先级

| 优先级 | 类型 |
| --- | --- |
| 高（首批） | Redis、SQLite（Postgres/MySQL 待 fixture） |
| 中（次批） | S3/MinIO、Mailpit、WebSocket/SSE、第三方 HTTP mock；fixture 落地前按实验性 |
| 低（后续） | 向量库、时序库、图数据库、工作流引擎、移动/桌面、支付 webhook |
| 不做 | 专有云服务、硬件、OS 级、K8s 全量编排 |

#### 3.9.6 对测试的影响

适配类型不直接生成业务用例，但会影响：

- 覆盖账本增加“缓存/异步/依赖状态”维度；
- 数据隔离与复位；
- 基线 gate（依赖/宿主可用性）；
- 用例排序（先读后写，写后复位）；
- 证据（key、行、消息、文件、邮件、WS 帧）。

Redis 示例：

- 创建后读：缓存未命中 → 回源 → 正确；
- 更新后读：缓存必须失效/更新；
- 删除后读：不能返回旧对象；
- TTL：过期后行为；
- 用例间：`FLUSHDB` 或 key 前缀隔离。

## 4. 生成层

### 4.1 不变量优先

由真实路由 + schema 直接生成，不调用模型：

| 不变量 | 期望 |
| --- | --- |
| 创建→读取 | 字段一致、id 一致 |
| 更新→读取 | id 不变、字段已更新 |
| 删除→读取 | 404 |
| 不存在资源 PUT/DELETE | 404 |
| 缺必填字段 | 400 |
| 未认证 | 401 |
| 无权限 | 403 |
| 列表包含新对象 | 包含 |
| Content-Type | application/json |
| 状态化序列 | create→update→delete 全链同一对象 |

这些覆盖 flask-vue-crud 暴露的 5 个真实缺口，不需要模型参与。

### 4.2 数据驱动配方

配方放 `src/aitest/resources/recipes/<id>/<version>.json`，与现有“检查模板”完全分开：

- 检查模板：咨询性清单，不进 S/M，继续保留；
- 用例配方：生成可执行用例，直接影响 S/M；
- 不共用 schema、不共用 `plan.templates` 字段、不共用结论语义。

首期配方：

| 配方 | 覆盖 |
| --- | --- |
| `rest-crud` | 列表/详情/创建/更新/删除 + 404 |
| `rest-validation` | 缺必填 400、类型错误 400 |
| `jwt-login` | 登录取 token、token 注入、非法 token 401 |
| `negative-auth` | 未带凭证 401、无权限 403 |
| `multi-service` | 前后端分离探针目标与健康 |

配方匹配只使用画像事实；匹配不上就不生成，进入未覆盖清单，不回退猜测。

### 4.3 模型只补业务语义

模型负责：

- 业务特有验收项（如“库存从 10 变 7”）；
- 不变量覆盖不到的流程；
- 复杂数据构造与业务断言；
- 已覆盖项的非重复业务增强（并发、幂等、跨租户、状态组合等），前提是去重签名不重复、断言强度合格。

模型不得负责：

- 决定有没有某条路由；
- 发明环境变量或凭据；
- 决定负向用例是否补认证；
- 决定预期是什么；
- 为满足覆盖率硬造用例。

Prompt 约束：

- 注入画像 facts、`unknowns/unsupported`、允许的验证方式；
- 输入包含“已覆盖结构 + 未覆盖维度”，不只喂缺口清单；
- 凭据来自 README/.env/配置默认值；
- 负向鉴权不得包含会被拒绝的 setup；
- `extract` 必须是 `{变量名: 响应体路径}`；
- 业务项一律 L2。

### 4.4 验收映射与来源

- 每条用例必须有 `expectation_source`；
- 引不上验收项原文的标“预期未证实”；
- 计划展示 `S/M` 与未覆盖清单；
- 用例标记来源：`invariant / recipe / model / engine`，记录配方 id/version；
- 报告可按来源筛选。

### 4.5 可执行验收样例

预期来源优先级：

1. 用户提供的可执行输入/输出样例；
2. 验收项原文；
3. 用户确认过的冻结预期；
4. AI 建议（只作候选，不能直接冻结）。

规则：

- 业务项有样例/原文 → 可执行；
- 只有 AI 建议 → 存 `plan.ai_expectations`，标“AI 建议，未证实”；
- 用户确认后 → 才能进入本次运行的冻结预期；用户拒绝 → 本次不采用，不进入计划；
- 确认界面：确认页逐条展示 AI 预期建议，标“未证实”；决策随 `run.start` 写入 `Run.ai_decisions`/`Confirmation.ai_decisions`，不改计划 revision；计划里的 `plan.ai_expectations.status` 只保留生成时的 `suggested`；
- 未确认的 AI 预期 → 只能标“预期未证实”，不进入通过；
- 都没有 → 标“预期未证实”，最多算 incomplete，不硬判通过；
- AI 不替用户定义业务真相。

### 4.6 状态与权限矩阵

- 数据状态：空、单条、多条、重复、边界、并发；
- 权限：角色 × 资源 × 操作，至少覆盖“无权”和“跨租户”；
- 状态流转：创建→更新→删除、重复提交、幂等。

按项目画像决定适用维度，不强制所有项目全量覆盖。

### 4.7 AI 输出契约

所有 AI 输出统一结构（`case_proposal`/`disposition` 用于计划用例与模板处置，其余方法用 suggestion/clarification/hypothesis/review_finding）：

```json
{
  "kind": "suggestion|clarification|hypothesis|review_finding|case_proposal|disposition|action_proposal|frontend_flow",
  "scope": {"project_id": "...", "task_id": "...", "case_id": "..."},
  "statement": "...",
  "evidence": ["验收项原文/文件:行/响应片段"],
  "confidence": "high|medium|low",
  "requires_user_confirmation": true
}
```

规则：

- 必须引用验收项原文或证据；
- 禁止 `passed/failed/confirmed/suspected`；
- 禁止 `S/M`、覆盖率、通过率；
- 禁止凭据正文；
- 检测到结论词 → 整段不采用；
- 无证据 → 降级为 `unknown`。

存储位置：

- `plan.ai_reviews`：评审建议，生成时 `status=pending`；接受/驳回决策随 `run.start` 写入 `Run.ai_decisions`，不改计划 revision；
- `plan.ai_expectations`：生成时 `status=suggested`；确认/拒绝同样写入 `Run.ai_decisions`；
- `run.ai_hypotheses`：失败假设；
- 建议不写入业务结论字段。

## 5. 约束层

### 5.1 五条红线

| # | 红线 | 行为 |
| --- | --- | --- |
| 1 | 负向鉴权不补认证 | 验收项要求 401/403 时，assert 阶段不得带凭证；禁止把 401 改写成带凭证通过 |
| 2 | setup 只能期望成功 | setup 请求的 expect 不得出现 4xx/5xx；负向断言不得放 setup |
| 3 | 状态码必须断言 | 验收项写了 400/401/404 等，assert 阶段必须有 `path=status` |
| 4 | 结果与可信度分离 | 完成执行的断言失败保持 `failed`；AI 只给假设，最终由确定性规则定档；裁判不确定只影响 `suspected`，不得改成 `blocked` |
| 5 | 未知/未覆盖不算通过 | 空 `http:`、`unknowns`、未覆盖验收项不得计入通过；空 S 不得启动 |

实现：

- 直接写在 `plan_validation.py` / `lifecycle.py`；
- 只自动修复结构（extract 形态、status 断言、变量顺序），不修业务语义；
- 自动修复写入计划提示/警告；
- 不建守卫注册表、不建自动修复账本。

#### AI 假设 → 确定性定档

| 证据组合 | 结论 |
| --- | --- |
| 断言失败 + 断言与验收项一致 + 无脚本假设/环境/依赖异常 | `failed`（confirmed） |
| setup/服务/依赖不可用 | `incomplete`（blocked） |
| 脚本语法/导入/前置错误 | `error`，可修 |
| 断言失败 + 存在环境/依赖异常 | `incomplete`（blocked），不判产品失败 |
| 断言与验收项不一致，或 AI 指出的脚本假设有证据 | `error` 或 `incomplete`，不得 `failed confirmed` |
| AI 假设多解 + 无确定性证据 | `incomplete`（unknown），不猜 |

顺序要求：先排除脚本假设/断言不匹配/环境异常，再确认产品失败；AI 假设不能绕过这个顺序。

AI 的 `hypotheses` 只用于补充 `next_check`，不直接改上表结果。

### 5.2 断言强度 lint

- http 用例必须断言 `status` + 至少一个业务字段/状态；
- 负向用例必须断言状态码，不能只断言 `error` 存在；
- 脚本用例必须包含针对响应/状态/业务字段的 assert；
- 禁止“只要 200 就算通过”；
- 断言目标必须能映射到验收项原文。

输出：

- http 可判定的弱断言 → 计划警告/拒绝发布；
- 脚本只能静态判断到“疑似弱断言” → advisory，不静默通过；报告标“未证实”。

### 5.3 基线 smoke gate

按当前事实来源执行：

- 默认：项目可读、配置完整、可生成计划；已有服务只读可用则复用；
- 升级后：服务健康、登录/匿名访问、关键只读接口；
- 深度发现：再加前端首页/关键流程可达。

基线失败 → 本次 `blocked`，不进入产品失败判定。

### 5.4 数据隔离与波动控制

- 写用例使用唯一数据（uuid/时间戳）；
- 创建后清理或依赖服务 reset；
- 只读用例可重试；写用例不重跑；
- 两次结果不一致标“疑似不稳定”，两次证据都保留；
- 固定时钟/随机种子（可配置）；
- 依赖按 §3.9 的 D1–D4 处理：D1/D2 复位或隔离，D3 用唯一数据并标“隔离受限”，D4 标 unsupported。

## 6. 验证层

### 6.1 覆盖账本（advisory）

每个验收项按需标记：

| 维度 | 例子 |
| --- | --- |
| 正向 | 合法请求成功 |
| 负向 | 400/401/403/404 |
| 权限 | 无权限、跨租户 |
| 边界 | 缺字段、超长、类型错误、空值 |
| 状态流转 | 创建→更新→删除、重复提交、幂等 |
| UI | 页面/流程可达 |
| 跨服务 | 服务依赖、部分失败 |
| 缓存/异步 | 更新后缓存失效、队列消息、TTL |
| 依赖状态 | 数据库行、Redis key、对象文件、邮件 |
| 安全 | 认证、授权、CSRF、CORS、上传、限流 |
| 性能 | 响应时间、并发、限流、超时 |
| 可靠性 | 重试、幂等、补偿、断线重连 |

规则：

- 从验收项文本 + 用例覆盖推断“应覆盖维度”；
- 文本明确要求 401/404/400 → 负向必须覆盖；
- 提到角色/权限 → 权限维度；
- 提到必填/长度/类型 → 边界维度；
- 出现认证/授权/CSRF/CORS/上传/限流/注入 → 安全维度；
- 出现并发/超时/响应时间/吞吐 → 性能维度；
- 出现重试/幂等/补偿/死信/断线 → 可靠性维度；
- 没提到的标“未要求”，不扣分；
- 无法判断标 `unknown`，不强行判缺失。

展示：

```text
验收项：PUT /books/{id} 更新后保持原 id
正向 ✓  负向 404 ✓  权限 ✗（未要求）  边界 ✗（未要求）  状态 ✓
```

账本是 advisory：明确要求但缺失 → 列入未覆盖；未要求的不影响结论。

### 6.2 路由/流程覆盖

- 每个检测到的路由/方法至少一条用例，或显式排除；
- UI 关键流程同理；
- 覆盖不到 → `uncovered` 清单；
- 覆盖报告不作为硬门槛。

### 6.3 与项目自带测试交叉校验

- 只对失败用例跑其映射的既有测试；
- 结果只作为证据提示，不自动改判；
- 项目测试通过、插件失败 → 报告提示“需人工确认”；
- 没有映射测试 → 跳过。

### 6.4 Fixture Zoo（静态 / 集成两层）

```text
tests/fixtures/zoo/
  static/            # 离线，每次提交
    flask_decorator/
    fastapi_router/
    django_drf_router/
    express_router/
    axios_template_base/
    fetch_wrapper/
    openapi_generic/
  integration/       # 本地服务/Redis，发布/夜间
    jwt_negative_401/
    multi_service/
    redis_cache/
```

每个 fixture：

- 几十行源码；
- `expected.json`：画像、路由、前端调用、配方匹配、守卫结果、执行结论；
- `static`：不启动服务、不调模型；
- `integration`：只起本地服务/Redis，不访问外网；模型路径用录制响应回放；
- 两层都不访问外部网络。`openapi_generic` 使用仓库内固定的 OpenAPI 文件，不启动服务。

### 6.5 固定回归组合（Portfolio）

现有 5 个项目，按“角色”而不是“数量”使用：

| 项目 | 角色 | 栈 | 基线 |
| --- | --- | --- | --- |
| rbac-demo | 权限/多租户 baseline | Python 标准库 JSON API + 静态 Web | 8/8 缺陷检出，0 误报 |
| flask-rbac | 组织隔离 baseline | Flask + SQLite | 7/7 缺陷检出，0 误报 |
| flask-vue-crud | 全栈 CRUD baseline | Flask + Vue/Vite | 5/5 缺口检出，0 误报 |
| django-react-crud | 干净对照 + T1 协议栈 | Django + DRF + SQLite + React/Vite | 0 失败，0 误报 |
| store-pos | 大项目 + JWT/负向鉴权 | Express + sql.js + JWT + React/TS | 全部通过，0 误报 |

#### 运行时机

| 时机 | 跑什么 |
| --- | --- |
| 每次提交 | 单测 + `zoo/static` + 合同测试（离线、确定性） |
| 发布/夜间 | `zoo/integration` + Portfolio；按改动范围选子集，发布跑全量 |
| 改动仅涉及提取器 | 每次提交：只跑受影响 fixture；发布/夜间：fixture + 对应项目 |
| 改动涉及判定/红线 | 跑全量 Portfolio |

#### 判定标准

不是“全部通过”，而是“与基线一致”：

- 有缺陷项目：已知缺陷仍然检出；
- 干净项目：仍然 0 误报、0 误失败；
- 无新增 C1（假通过/误失败/误阻塞）；
- 探针/覆盖没有退化；
- 证据齐全。

#### 基线维护

- 每个项目有 `tests/portfolio/<project>/expected.json`：任务、计划、已知缺陷、误报、误失败、C1、探针；
- 基线变化必须附证据，不允许静默改写；
- 环境失败 → `blocked`，不算基线回归；
- 新项目加入条件：覆盖新轴、目标用户主流栈、或暴露新 C1；数量控制在 6–7 个以内。

### 6.6 新发现处理流程

```text
发现 → 归类（C1 correctness / C2 coverage / C3 UX）
     → 最小 fixture 复现
     → 类级修复（adapter / 红线 / 不变量）
     → fixture 进 zoo
     → 固定组合回归
     → 发布门槛
```

分类定义：

- C1 correctness：假通过、误失败、误阻塞、结论错；
- C2 coverage：未覆盖、未知、不支持；
- C3 UX：面板、报告、交互问题。

### 6.7 停止规则

- 连续 3–5 个新项目不再产生新的 C1 类，只产生 C2，说明体系收敛；
- 进入维护模式，不再为单个项目改核心。

### 6.8 合同测试

每次提交的“合同测试”指：

- CLI 命令名、`{"command","payload"}` envelope、错误码；
- Plan/Run/Report 必填字段与枚举；
- 面板 DTO 与后端字段映射；
- 旧计划读取兼容（新增字段可选）。

位置：`tests/contract/`；不启动服务、不调真实模型。

## 7. 插件级：默认不改变环境

### 7.1 默认行为

- 只读项目文件/配置；
- 已有服务在跑则复用，不重复启动；
- 不装浏览器、不跑容器、不新增常驻进程/端口；
- 缺事实 → `unknown`，不猜；
- 测试仍可能写业务数据：写用例必须唯一数据并有清理/reset；用户不需要额外配置。

### 7.2 升级动作

- 缺事实且影响验收 → 提示一次：“允许启动服务读取真实接口吗？”；
- 需要浏览器/契约 fuzz → 用户点击“深度发现”，显式确认；
- 升级后重新生成计划（新 revision）并重新确认；
- 失败/拒绝 → 回退默认，保留已获得的事实。

### 7.3 依赖预算

- 核心：Python 标准库 + requests；
- 可选：Schemathesis、Playwright、mitmproxy、Testcontainers；
- 可选组件只在深度发现时按需加载，不随默认包分发；
- 不可用时降级，不阻塞默认路径。

### 7.4 UI

- 项目概览：能力画像卡，显示本次用了哪些事实来源；
- 计划页：来源构成 + 未覆盖/未知；
- 确认页：只展示未知/不支持/未覆盖/副作用；
- 不显示“模式选择”；
- 不做指标看板、不做配置向导；
- 未知默认折叠；
- AI 工件以提议卡展示：证据、风险、回滚、采纳/驳回；低价值默认折叠，支持批量决策；
- 环境/前端动作单独确认，不与执行前主 checkbox 混用；
- AI 贡献统计放报告章节，不做独立经营看板。

### 7.5 缓存与复用

- 画像按源码/配置指纹缓存；
- 计划按任务/规则缓存；
- 只跑失败项、断点续跑。

## 8. 复用经济

### 8.1 协议复用

OpenAPI/Swagger、Playwright 网络抓包为主；GraphQL introspection、gRPC reflection 暂列实验性，fixture 落地前不承诺。

### 8.2 引擎薄封装

主路径两个：Schemathesis、Playwright；其余为借鉴/可选，不算入口。先不抽象统一接口：

| 能力 | 采用/借鉴 | 说明 |
| --- | --- | --- |
| OpenAPI 契约/边界/负向 | Schemathesis | 有 spec 时直接作为 runner |
| 浏览器/网络抓包 | Playwright | 抓真实请求，替代静态猜封装 |
| 状态化 CRUD 序列 | RESTler 思路 | 借 create→update→delete 序列，不重写状态机 |
| 流量回放 | mitmproxy | 可选；跨平台 |
| 依赖/环境 | Testcontainers + 原生客户端 | DB/Redis/队列的启动、复位、探针；可选 |

可选、非核心：Qodo Cover/Pynguin/EvoSuite（单元测试覆盖率）、Pact（双方契约）。这些不进入验收主路径，只在明确需要时接入。

RESTler 只借序列思路；mitmproxy/Testcontainers 可选。只有接入第三个引擎时，再抽统一适配接口。

### 8.3 结果归一化

外部引擎结果不能直接当验收结论，必须：

- 映射到路由/用例；
- 映射到验收项；
- 经过五条红线；
- 生成证据；
- 去重/归一化签名。

### 8.4 项目产物复用

- OpenAPI/GraphQL/gRPC schema；
- 项目自带测试；
- README/配置中的默认凭据；
- CI 命令、迁移、种子数据。

### 8.5 许可与平台

- 只嵌入 Apache/MIT 等可分发组件；
- Linux-only（Keploy）标可选；
- 商业工具只借鉴思路，不嵌入。

### 8.6 不重复造

不造：API fuzzer、浏览器录制器、流量代理、单元测试生成器、容器编排、自愈 locator。

只造：验收映射与 S/M、四值判定、五条红线、证据链、插件体验。

### 9.2 四个概念必须分清

| 概念 | 含义 | 是否算通过 | 展示位置 |
| --- | --- | --- | --- |
| failed | 执行完成且断言失败 | 否 | 结果/问题/报告 |
| blocked | 前置、环境或服务未就绪 | 否 | 结果/报告 |
| unsupported | 插件没有该能力 | 否 | 概览/确认页/报告 |
| uncovered | 有能力但本次没覆盖 | 否 | 计划/报告未覆盖清单 |

映射到业务四值：

| 情况 | 业务结论 |
| --- | --- |
| 执行完成且断言失败 | `failed` |
| 前置/环境/服务未就绪 | `incomplete`（原因 blocked） |
| 插件不支持该能力，但验收项适用 | `incomplete`（原因 unsupported） |
| 有能力但本次没覆盖 | `incomplete`（原因 uncovered） |
| 验收项本身不适用于本项目 | `not_applicable` |

`blocked / unsupported / uncovered` 是原因，不是第五种结论；`not_applicable` 只能用于“验收项本身不适用”，不能用来掩盖“插件没能力”。

新项目出现更多 `unsupported/uncovered` 不是退步，而是把“原来会猜错/假通过”的部分变成了明确缺口；缺口可以后续加适配器或配方消掉，假通过不能。

### 9.3 降级

- 运行时内省失败 → `source=static, degraded`；
- 概览/确认页/报告明确显示“降级”；
- 未知项增多，计划来源更多是 model；
- 不把降级结果写成“全部通过”。

### 9.4 首次与后续

- 首次：可能多一次服务启动确认、多几条未知/未覆盖；
- 用户修正端点/认证/凭据通过现有 `project.config` 完成，重新生成计划后进入快照；
- 后续项目复用画像，不再重复问同类问题。

| 问题页 | 仅真实失败，附证据；未知/未覆盖不入问题 |

### 9.6 前端改造方案（面板与 Trae）

前端不新起一套 AI 视觉语言，复用现有面板的页面头、摘要条、双栏工作台、卡片、抽屉、确认块和证据弹窗。

#### 9.6.1 设计原则

1. **不新增独立 AI 工作台大屏**：AI 工件以现有页面内的提议卡、抽屉、弹窗呈现。
2. **复用现有布局与组件**：
   - 页面头：`PageHeader`
   - 计划摘要：`plan-summary-strip` + `CoverageRuler`
   - 双栏工作台：`workbench-split` + `workbench-sticky`
   - 内容卡片：`elevated-panel` + `section-title` + `stack`
   - 状态标记：`badge is-info/is-warn/is-neutral`、`StatusMark`
   - 空/错/载入：`EmptyState`、`ErrorState`、`LoadingState`
   - 确认：`ConfirmDialog`、`ConfirmationPanel` 的 `confirm-block` 风格
   - 证据：`EvidenceDialog`
   - 抽屉：`drawer-backdrop` / `drawer-panel`
3. **中文标签沿用现有术语**：计划、验收项、用例、运行、报告、问题；AI 统一标“建议/假设/草稿/待确认”。
4. **不新增全局 CSS 体系**：优先复用现有 `styles/*` 与原子类；只在现有 token 下加局部类，不引入新的颜色/间距/字体体系。
5. **面板不重算结论**：四值、`S/M`、覆盖率、可信度只读 CLI；AI 产出只做展示与决策。
6. **AI 决策走业务记录**：预期决策走 `run.ai_decisions`/`Confirmation.ai_decisions`；评审 patch 决策走 `AIWorkItem`/`plan.update`；sidecar 只存 UI 状态。
7. **旧数据兼容**：所有新字段 optional；旧计划/旧运行/旧报告走 `normalizePlan`/`normalizeReport`，缺字段显示“未知/未启用”，不崩。
8. **不新增模式开关**：不出现 `ai.mode` 选择、不出现“简单/完整”模式。

#### 9.6.2 页面级改动

**范围页 `ScopeView.vue`**

- 增加 `AIImpactPanel`：读取 diff/代码图/测试映射，给出受影响验收项/测试建议。
- 人确认后更新本次 scope，再 `plan.generate`；不自动取消测试。
- 已有计划时应用建议会重新生成计划并重新确认。

**计划页 `PlanView.vue`**

- 摘要条增加：

- 检查清单 `PlanLedger`：
  - 每条用例显示 `generation.source`、配方版本、断言强度
  - AI 用例加“AI 建议”徽章；未证实预期加“待核实”
  - 支持按来源筛选：全部 / 不变量 / 配方 / AI / 显式
- 右栏确认区上方增加 `AIReviewPanel`：
  - finding 列表：severity、statement、evidence
  - patch 预览：改为哪些用例、改什么断言
  - 采纳/驳回；低置信度默认折叠

**确认页 `ConfirmationPanel.vue`**

- `aiExpectations`：AI 预期建议

- AI 预期逐条“确认/拒绝”，默认折叠低置信度。

**报告页 `ReportView.vue`**

**概览 `ProjectOverview.vue`**

- 无计划时显示“未生成画像/未生成 onboarding”。

#### 9.6.4 数据流

```text
CLI DTO (snake_case)
  → host/dto.ts（optional 字段）
  → host/map.ts（防御式映射，旧字段兜底）
  → domain/types.ts
  → Pinia workspace/ui
  → View/Component
```

写操作：

```text
View → workspace action
  → HostRepository / LocalStorageRepository
  → host/commands.ts
  → Trae bridge → CLI
  → refreshProject / plan.show / run.status
```

必须同步：

- `dto.ts`：Plan/Run/Report/Case 新字段；`project.snapshot.ai_onboarding`；`AIArtifact`/`AIWorkItem`/`AIActionProposal` 视图 DTO
- `map.ts`：`mapPlan`、`mapPlanCase`、`mapRun`、`mapRunCase`、`mapReport`、`mapAIArtifact`、`mapAIAction`、`mapOnboarding`
- `commands.ts`：`discoverProject`、`generatePlan` 传 capabilities/facts、`updatePlan` 传 `ai_review_decisions`、`startRun` 传 flags/decisions
- `ProjectRepository.ts` / `HostRepository.ts` / `LocalStorageRepository.ts`
- `workspace.ts`：AI action、决策、刷新、轮询
- `sidecar.ts`：只存 UI 折叠/选中，不存业务决策
- `integrations/trae/src/ext_commands.ts`：白名单、confirmable、超时
- `panel/src/host/bridge.ts`：超时、长任务、活动观察

所有新字段 optional；旧计划/旧运行/旧报告缺字段时显示“未启用/未知”，不报错。

#### 9.6.5 交互规则

- AI 建议卡默认按 severity/confidence 排序；低置信度折叠；超过 `max_review_items` 显示“已截断”。
- 采纳/驳回必须可批量；驳回可填原因。
- AI 预期未决策时，不阻塞启动；对应用例只能“未证实”。
- 计划评审 patch 不应用不影响启动；应用 patch 后生成新 revision，必须重新确认。
- 服务/依赖许可单独确认；环境/前端动作再次单独确认。
- 动作卡显示：目标、命令/步骤、风险、回滚、超时、证据。
- 运行中动作可取消；取消后显示“已取消”，不显示“失败”。
- 回滚后显示原始失败证据和新状态；不能把回滚写成通过。
- 所有 AI 文本必须标“建议/假设/草稿”，不出现“已通过/已确认缺陷”等结论词。
- 证据统一走 `EvidenceDialog`；截图/trace 不直接嵌大图，先缩略图+打开。
- 键盘/ARIA 沿用现有 `ConfirmDialog`/`drawer-panel` 焦点管理；新增卡片必须有可访问名称。

#### 9.6.6 Trae 扩展

- 新命令/动作必须同步：
  - `PANEL_COMMANDS`
  - `CONFIRMABLE_COMMANDS`
  - `COMMAND_TIMEOUT_MS`
  - `extension.ts` confirm 门禁
  - `panel/src/host/bridge.ts` 超时/长任务
  - `integrations/trae/README.md` 命令表
- AI 环境/前端动作若新增命令，默认 confirmable；不能复用 `run.start` 的确认代替动作确认。
- 面板不能直接调未登记命令。

## 11. 兼容性与合同

- `plan.templates` 继续只存检查模板，语义不变；
- 旧计划可读，不静默迁移；需要新能力时重新生成计划（新 revision）；
- 不引入常驻服务、数据库、消息队列；
- 结论仍是四值，S/M 口径不变，证据与凭据约束不变；
- 运行时内省/深度发现必须显式确认，不能静默启动服务。

## 12. 实施

### 12.1 MVP（约 4–6 周）

- 五条红线补全 + 单测；
- HTTP 断言强度 lint；
- 基线 smoke gate；
- 覆盖账本（advisory）；
- 默认不改变环境行为 + 一次确认升级；
- OpenAPI 适配；
- 7 个静态 fixture（`zoo/static`）；
- 5 个现有项目基线校准（发布/夜间跑）。

验收：

- 新项目不再出现假通过/误阻塞；
- 每个 C1 类有静态 fixture；
- 未识别能力、未覆盖维度可见；
- 现有项目基线不回归。

### 12.2 第二阶段（约 2–3 周）

- Playwright 网络抓包；
- `zoo/integration`：`jwt_negative_401`、`multi_service`、`redis_cache`；
- 依赖适配器：Redis + SQLite 的识别/复位/探针；Postgres/MySQL 待 fixture 后升级；
- S3/MinIO、Mailpit、WebSocket/SSE、第三方 HTTP mock：fixture 落地前只标实验性；
- Schemathesis 可选 runner。

验收：

- 真实服务/依赖类 fixture 可重复；
- 缓存/队列/存储类未覆盖能力在报告可见。

### 12.3 后置（按需）

- mitmproxy/Testcontainers；
- 次批/后续类型：MongoDB、Elasticsearch、RabbitMQ/Kafka、工作流、SSR、GraphQL、向量/时序/图、移动/桌面、支付 webhook；
- 权限/状态矩阵扩展；
- 变异/覆盖充分性抽样；
- 引擎统一适配接口（接第三个引擎时再抽）；
- 更多 fixture 与项目组合。

触发条件：

- 出现新的 C1 类；
- 某个栈的 T2 覆盖率不足；
- 用户明确需要深度发现。

### 12.4 AI 接入顺序

| 阶段 | 内容 |
| --- | --- |
| P0 | AI 工作台契约、AIWorkItem/AIActionProposal/AIArtifact/AIContribution、`model.ai`/`evidence.mock` 配置、预算默认值、审计、golden harness；无行为变化 |
| P1 | 验收抽取、测试映射、业务用例（缺口+增强）、数据构造器、评审补丁、影响面/测试选择、测试代码评审、onboarding |
| P2 | 失败分诊、诊断动作、脚本/选择器修复补丁、偶发/多服务归因、CI 分诊、权限矩阵、契约 diff |
| P3 | 项目内环境依赖修复（确认、快照、回滚、复测） |
| P4 | 本地前端 Playwright 流程（localhost、隔离数据、截图/trace）、视觉/a11y |
| P5 | 报告/问题/交付草稿 + 贡献统计 |
| P6 | 受控自动修复循环（策略内重试，高风险仍需人确认） |

说明：

- P0–P2 是主线可信结论的增强，优先做；
- P3/P4 用户感知强，但风险高，必须在 P2 的动作策略、回滚、复测稳定后再做；
- 环境修复和前端流程都不是“模型能力问题”，核心是策略引擎、沙箱、证据和回滚；
- AI 接入不改变主线的五条红线和四值结论。

| F4 | 报告页 AI 贡献、能力/覆盖、AI 工件索引、影响面/测试评审/flaky/契约/权限摘要 | 导出 Markdown 同步；旧报告可读 |
| F5 | 环境/前端动作工作台：diff、风险、进度、取消、回滚、证据 | 动作必须走 `AIActionProposal`；回滚可复测 |
| F6 | Playwright flow 查看/授权/执行/截图/trace/选择器修复 | localhost、隔离数据、确定性断言；最多 2 次修复 |
| F7 | Trae 白名单/confirm/超时 + E2E/a11y | 新命令可调用；确认不被丢弃；E2E 全链路通过 |

依赖：

```text
F0 → F1 → F2 → F3 → F4
          ↘ F5 → F6
F7 随 F1–F6 同步
```

F5/F6 的真实执行分别依赖后端 P3/P4；UI 可以先行，但未接后端时只能显示“未启用”，不能给出可执行按钮。

前端执行接口、组件 props/emits 与测试清单见[改造施工图](2026-11-26-改造施工图.md) §7。

## 14. 风险与取舍

| 风险/冲突 | 处理 |
| --- | --- |
| 覆盖透明 vs 默认路径 | 默认不启动；缺事实问一次；拒绝则标未知 |
| 覆盖透明 vs 不误测 | 宁可不判通过，也不猜；未知/未覆盖不算通过 |
| 复用 vs 不误测 | 复用引擎执行，结论由守卫与映射层产生 |
| 复用 vs 插件级 | 外部引擎可选、按需加载；核心不依赖 |
| 运行时内省有副作用 | 显式确认；失败回退静态并标 unknown |
| 无 OpenAPI/服务起不来 | 静态兜底；T3/T4 明示 |
| 模型业务断言不可靠 | 样例/交叉校验；静态+模型不写“全部通过” |
| AI 环境/前端动作有副作用 | 结构化动作、人确认、快照、回滚、复测；系统级只解释 |
| AI 修复掩盖缺陷 | 断言不减弱、限制修复次数、保留原始失败证据、复测 |
| AI 审核疲劳 | 按 severity/confidence 排序、默认折叠、批量决策、每任务提案上限 |
| 前端 AI 区块过多 | 不新增独立工作台；内联提议卡+抽屉；低价值默认折叠 |
| 旧计划/旧报告缺 AI 字段 | optional + `normalizePlan`/`normalizeReport`；缺字段显示未知，不崩 |
| 动作确认与执行确认混淆 | 服务/依赖/环境/前端动作单独确认，不与主 checkbox 合并 |
| AI 供应链/提示注入 | 项目内/lockfile/禁止任意 URL；代码/日志视为不可信输入 |
| fixture 维护成本 | 每个只测一个维度；新发现才加 |

## 16. 完成定义

1. 每次提交 `zoo/static`/单测/合同测试通过；发布/夜间 `zoo/integration` + Portfolio 与基线一致；
2. C1（假通过/误失败/误阻塞/结论错）新增为 0；
3. 新项目首次运行只产生 C2/C3，不产生 C1；
4. 未识别能力、未覆盖维度、事实来源在报告首页可见；
5. 加一个新栈只加 adapter/配方/fixture；
6. 五条红线、断言强度、基线 gate 全部有单测；
7. 默认路径不启动服务/浏览器/容器；写操作有数据副作用提示；
8. 已实现适配类型（Redis/SQLite）有 D 级、复位/隔离策略与证据；S3/MinIO/Mailpit/WebSocket/SSE/外部 mock 在 fixture 落地前标实验性；其余明确列出未支持项；
9. AI 只输出 suggestion/clarification/hypothesis/review_finding/case_proposal/disposition/action_proposal/frontend_flow，无结论词、无 S/M；
10. `generate_cases` 做“缺口必补 + 非重复业务增强”；`judge_failure` 不再直接给 verdict；`freeze_expectations` 只写建议；`repair_script` 只出受控补丁；
11. AI 工件有 schema、证据、置信度、去重签名、golden set；环境/前端动作有确认、快照、回滚、复测；
12. 关闭 AI 后，确定性链路可完整运行；
13. 前端 AI 工件/决策/动作可见；旧计划/旧报告兼容；E2E“计划→AI 建议→确认→结果→报告”通过；新增控件有可访问名；
14. 扩展 AI 能力（影响面/测试评审/flaky/CI/权限矩阵/契约 diff/视觉 a11y/onboarding）有 golden set、证据、门禁；默认 advisory，不阻塞主结论。

## 20. 附录 D：AI 任务明细

### D.1 任务清单

| 任务 | 输入 | 输出 | 约束 |
| --- | --- | --- | --- |
| 验收项拆解 | 验收项原文、目标、画像 | 维度建议、澄清问题、候选样例 | 只建议，不直接改预期 |

| 前端流程 | 路由、组件、页面 | Playwright 流程/选择器 | localhost、隔离数据、确定性断言 |
| 报告/问题撰写 | 证据、用例、运行 | 标题/步骤/摘要 | 只写事实，过滤结论词 |

评审：


```json

  ]
```

### D.3 评测

- 录制模型响应，CI 不依赖真实模型；
- golden tests 覆盖：schema、结论词过滤、证据引用、无证据降级；
- 人工标注 20–30 条验收项，评估歧义识别率；
- 统计建议采纳率与驳回原因；
- 真实模型只做 nightly/发布前 smoke。

### D.4 迁移与回退

- 后端内部配置 `model.ai.mode=legacy|assist|off`，不暴露用户可见模式；
- 新字段全部可选：`plan.ai_reviews`、`run.ai_hypotheses`、`case.generation.source=model`；
- 旧计划可读；
- AI 不可用 → 建议为空，确定性链路继续；
- AI 建议不得写入业务结论字段。
