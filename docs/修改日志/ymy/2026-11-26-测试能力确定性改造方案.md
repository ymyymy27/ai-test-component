## 0. 目标与边界

### 0.1 核心目标

> 在声明支持的能力与本次验收范围内，给出可信、可核对、不夸大的结论。

### 0.2 四个目标的分层

| 层级 | 目标 | 可验收定义 |
| --- | --- | --- |
| 核心结果（P0） | 不误测 | 声明支持范围内 `false_pass = 0`；环境/前置问题不判产品失败；可判定的弱断言不发布 |
| 结果质量（P1） | 覆盖透明 | 每个验收项有覆盖账本；未覆盖/不支持显式列出；不承诺绝对“不漏” |
| 默认路径约束（P1） | 插件级 | 默认不启动服务、不装浏览器、不跑容器、不常驻；深能力显式升级 |
| 实现策略（P2） | 复用经济 | 协议/引擎/项目产物优先复用；重型依赖不进默认路径 |

优先级：

> **不误测 > 覆盖透明 > 插件级（默认路径约束） > 多复用**

解释：

- 不误测是红线，宁可不判通过，也不猜；
- 覆盖透明是可验收的“不漏测”：缺口可以存在，但必须可见；
- 插件级约束默认路径，不能阻止用户显式升级去换覆盖；
- 多复用是手段，不是产品承诺。

### 0.3 结论必须可核对

每条结论必须同时具备：

- 证据（请求/响应/日志/截图）；
- 范围（`S/M`、未覆盖清单）；
- 来源（invariant/recipe/model/engine、事实来源）；
- 未知（`unknowns/unsupported`）。

四者缺一，不得写成“通过”。

### 0.4 两种“新问题”必须分开

| 类型 | 含义 | 处理 |
| --- | --- | --- |
| 被测项目的新缺陷 | 插件发现目标产品的真实 bug | 产品价值，越多越好 |
| 插件自身的新缺陷 | 假通过、误失败、误阻塞、计划失败、报告错误 | 本方案要收敛的对象 |

### 0.5 成功标准

1. 新项目首次运行：0 假通过、0 误阻塞、0 新增 C1；环境类失败必须先 blocked/复核，不得直接计入 failed；
2. 新发现只允许是 `unsupported`（能力未识别）或 `coverage gap`（覆盖不足）；
3. 每个 correctness 缺陷都有 fixture，CI 能拦住；
4. 加一个新栈只需 adapter/配方/fixture，不改判定核心；
5. 连续 3–5 个新项目不再产生新的 correctness 类。

## 1. 问题定义

### 1.1 插件缺陷反复出现的根因

| # | 根因 | 典型表现 |
| --- | --- | --- |
| G1 | 事实靠猜 | DRF router 漏路由、模板 baseURL 丢失、封装 fetch 跳过 |
| G2 | 生成靠模型 | 空 `http:`、`{var,path}`、FIRST_SUPERUSER、缺 status 断言 |
| G3 | 校验只查形状 | 负向 setup、凭证混入、错误结构被放行 |
| G4 | 判定可被改写 | 负向 401 被补认证改成通过、failed 被改成 blocked |
| G5 | 发现不沉淀 | 只修当前项目，没有类级机制与回归夹具 |

### 1.2 必须保持的产品硬约束

- 业务结论只有 `passed / failed / incomplete / not_applicable`；
- 未执行、未知、阻塞不得汇总成通过；空分母不显示 100%；
- 报告固定展示 `S/M` 与未覆盖清单；
- 判定只在 core 计算一次，面板/报告只读取；
- 凭据落盘前过滤，不进入日志、报告、导出；
- 旧计划/旧记录不静默迁移；
- 不引入常驻服务、数据库、消息队列。

## 2. 总体架构

```text
事实层
  ├─ 默认：静态读取（代码图、配置、README）+ 复用已运行服务
  └─ 升级：运行时内省（OpenAPI/resolver/url_map/router）
            + Playwright 抓包 + 契约/流量引擎（需用户确认）

生成层
  ├─ 不变量（CRUD/auth/状态码）
  ├─ 配方（高频形态）
  └─ 模型（业务特有语义）

约束层
  ├─ 五条红线
  ├─ 断言强度
  └─ 基线 gate

验证层
  ├─ 覆盖账本（advisory）
  ├─ 项目测试交叉校验（advisory）
  └─ fixture zoo + 固定项目组合

复用层
  ├─ 协议：OpenAPI / Playwright；GraphQL/gRPC 暂为实验性
  └─ 引擎：Schemathesis / RESTler 思路 / mitmproxy
```

原则：

- 事实、生成、判定、验证解耦；
- 栈相关逻辑只进适配器/配方，不进判定核心；
- **默认不改变环境**：不启动、不安装、不常驻；缺事实时问一次；测试本身仍可能写业务数据；
- 深度能力是动作，不是模式；
- 复用成熟引擎执行，自建层只做验收语义与结论。

### 2.1 默认行为与升级

不设“简单/完整”用户模式，只定义默认行为和升级动作：

| 场景 | 行为 |
| --- | --- |
| 打开项目 | 只读文件/配置；已有服务在跑则复用，不重复启动；用例仍可能写业务数据 |
| 缺事实且影响验收 | 提示一次：“允许启动服务读取真实接口吗？” |
| 用户拒绝/启动失败 | 回退静态，标 `unknown/uncovered`，不猜 |
| 需要浏览器/契约 fuzz | 用户点击“深度发现”，显式确认后执行 |
| 切换后 | 重新生成计划（新 revision），重新确认 |

T1–T4 是支持级别，可在概览/报告展示，但不作为用户可选模式；界面不提供模式选择。

### 2.2 AI 能力边界

AI 只做四类事：

| 角色 | 任务 | 产物 |
| --- | --- | --- |
| 理解助手 | 拆验收项、识别歧义、建议覆盖维度 | clarification |
| 设计助手 | 只写不变量/配方未覆盖的业务用例 | suggestion |
| 评审助手 | 弱断言、范围不匹配、负向凭证 | review_finding |
| 解释助手 | 失败假设、配置说明、报告叙述 | hypothesis |

AI 不允许：

- 决定路由、字段、认证、状态码；
- 判 `passed/failed`；
- 计算 `S/M`、覆盖率；
- 静默修改脚本语义；
- 决定唯一数据/隔离。

关闭 AI 后，确定性链路必须仍能完整运行。

## 3. 事实层

### 3.1 运行时内省

| 栈 | 运行时事实 |
| --- | --- |
| FastAPI | `/openapi.json`（路由、方法、参数、schema、状态码） |
| Django / DRF | URL resolver + `router.register` 展开 |
| Flask | `app.url_map` |
| Express | `app._router.stack`（应用可导出时） |
| Spring / Nest | OpenAPI / Swagger 端点 |
| 前端 | Playwright 跑主流程，抓真实网络请求 |

### 3.2 协议适配器

| 协议 | 覆盖的栈 | 能力 |
| --- | --- | --- |
| OpenAPI/Swagger | FastAPI、DRF Spectacular、Spring Boot、NestJS、.NET、Go、Rails、Laravel | 路由、方法、schema、必填、状态码 |
| GraphQL introspection（实验性） | Apollo、Hasura、graphene、Strawberry | query/mutation、字段、类型；尚无 fixture |
| gRPC reflection（实验性） | Go/Java/Python/C# gRPC | 方法、消息结构；尚无 fixture |
| Playwright 网络抓包 | 任意 Web 前端 | 真实请求、认证头、封装调用 |

### 3.3 静态兜底与未知

- 运行时不可用 → 静态提取；
- 静态也拿不到 → 记入 `unknowns`；
- `unknowns` 不允许当作“已通过”或“已覆盖”；
- 报告与计划确认页必须展示。

### 3.4 支持矩阵（支持级别）

| 级别 | 含义 | 典型栈 | 承诺 |
| --- | --- | --- | --- |
| T1 完整 | 运行时发现 + 路由/schema + 认证 + 不变量 + fixture | FastAPI、Django+DRF、Flask；Express 仅当 app 可导出 router（候选）；React/Vue 仅当有 Playwright UI fixture（当前未达） | 路由/字段/认证/CRUD/负向可确定性覆盖 |
| T2 协议导入 | 有 OpenAPI/Swagger 可导入路由、方法、schema、负向 | Spring Boot、NestJS、.NET、Rails、Laravel、Go | 完整性取决于规范，缺失进 unknown；启动与认证需配置；由 openapi_generic fixture 验证 |
| T3 静态部分 | 只能静态提取 | 无 schema 的 Python/Node 项目 | 只承诺静态事实，未知显式 |
| T4 明确不支持 | 不假装支持 | 当前不支持：移动端、桌面端、WebSocket 推送、消息队列 | 报告列出，未覆盖 |

规则：

- T1 必须有对应栈 fixture；T2 由通用 OpenAPI fixture 验证协议导入；GraphQL/gRPC 在 fixture 落地前只标实验性，不写进 T1/T2；
- 新增技术栈只加协议/启动/认证适配器 + fixture，不改判定核心；
- T1–T4 只用于框架/协议；依赖/外部/宿主用 D1–D4；
- 不维护“支持 50 个框架”的营销清单；条件不满足时按 T3 处理。

### 3.5 启动与认证适配器

| 类型 | 解决 | 例子 |
| --- | --- | --- |
| 启动适配器 | 项目怎么跑、健康检查 | Python venv + uvicorn/flask/django；Node npm/pnpm；Java mvnw/gradlew；.NET dotnet run；Go go run |
| 认证适配器 | 登录与凭证注入 | JWT Bearer、Session Cookie、API Key、OAuth client credentials、无认证 |

### 3.6 用户确认

计划确认页展示：

- 已识别的路由/认证/服务；
- `unknowns` 与 `unsupported`；
- 端点/认证/凭据修正沿用现有 `project.config`，在发现前完成；确认页表单不在本轮 S0–S7，另行追加 S2c；
- 修正结果通过重新生成计划进入快照，后续复用。

### 3.7 发现阶段的副作用

- 运行时内省/浏览器/引擎需要启动或访问服务，必须显式确认；
- 不能静默启动；
- 优先复用现有服务启动流程与日志；
- 服务起不来时回退静态，并写入 `unknowns`。

### 3.9 适配类型全景

“类型”不只指依赖。除应用框架外，还会遇到协议、依赖、外部系统、宿主环境和质量维度。方案把它们统一成“适配类型”，但只对能验证的给承诺。

#### 3.9.1 类型分组

| 大类 | 例子 | 分级 |
| --- | --- | --- |
| 运行时/框架 | Flask、Django、Express、Spring、React、Next、Electron | T1–T4 |
| 协议/接口 | REST/OpenAPI、GraphQL、gRPC、WebSocket/SSE、MQTT、Webhook | T1–T4 |
| 依赖/基础设施 | SQL、Redis、MongoDB、Kafka、S3、Mailpit、Vault | D1–D4 |
| 外部系统 | 支付、邮件/SMS、地图、AI/LLM、KYC、CDN | D1–D4 |
| 宿主/客户端 | 浏览器、移动端、桌面、容器、Serverless | D1–D4 |
| 质量维度 | 安全、性能、可靠性、一致性、a11y/i18n、合规 | 无级别，入覆盖账本 |

完整类型表见附录 C。

#### 3.9.2 分级 D1–D4（依赖/外部/宿主）

| 级别 | 能力 | 承诺 |
| --- | --- | --- |
| D1 完整 | 识别 + 启动/健康 + 复位/隔离 + 状态探针 + fixture | 可确定性覆盖依赖状态 |
| D2 基本 | 识别 + 启动/健康 + 复位 | 可隔离，但不能断言依赖内部状态 |
| D3 只识别 | 识别 + 连接，不可复位/探针（如托管云服务） | 只能靠唯一数据，报告标限制 |
| D4 不支持 | 不识别或不处理 | 报告列为 unsupported |

范围：D1–D4 只用于依赖/外部系统/宿主；框架与协议用 T1–T4；质量维度不评级，只进覆盖账本。

规则：

- D1/D2 必须有 fixture 或项目证据；没有不算；
- 默认只识别，不启动依赖；启动/复位需显式确认；
- 依赖不可用 → 相关用例 `blocked`，不判产品失败；
- 不能复位时，必须用唯一数据/命名空间，并在报告标“隔离受限”。

#### 3.9.3 控制面

不为每个产品写适配器，按控制面归类：

| 控制面 | 覆盖类型 | 操作 |
| --- | --- | --- |
| 数据库协议 | SQL/NoSQL/时序/图 | 连接串、迁移/清表、查询 |
| Redis 协议 | 缓存/KV | `redis-cli`、FLUSHDB/前缀 |
| 队列管理 API | Kafka/RabbitMQ/SQS | 清空、积压、死信 |
| 对象存储 API | S3/MinIO | bucket/前缀、HEAD、清理 |
| 邮件 API | Mailpit/MailHog | 收件箱查询/清空 |
| Mock HTTP | 第三方 API | WireMock/Prism/Mockoon |
| WebSocket/SSE | 实时 | Playwright/ws 客户端 |
| Appium/Playwright | 移动/桌面/SSR | UI 驱动 |

#### 3.9.4 复位与隔离

| 类型 | 推荐策略 |
| --- | --- |
| SQL | 迁移 + 种子/清表；唯一数据库或 schema；避免共享库 |
| Redis | `FLUSHDB` 或 key 前缀；不要 `FLUSHALL` 共享实例 |
| 队列 | 唯一队列/topic、清空、consumer group 隔离 |
| 对象存储 | 唯一 bucket/前缀，用例后清理 |
| 邮件 | Mailpit/MailHog API 清空收件箱 |
| 搜索 | 唯一索引/前缀 |
| 外部 HTTP | WireMock/Prism 场景复位 |
| 宿主 | 设备/容器/浏览器上下文隔离 |

#### 3.9.5 优先级

| 优先级 | 类型 |
| --- | --- |
| 高（首批） | Redis、SQLite（Postgres/MySQL 待 fixture） |
| 中（次批） | S3/MinIO、Mailpit、WebSocket/SSE、第三方 HTTP mock；fixture 落地前按实验性 |
| 低（后续） | 向量库、时序库、图数据库、工作流引擎、移动/桌面、支付 webhook |
| 不做 | 专有云服务、硬件、OS 级、K8s 全量编排 |

#### 3.9.6 对测试的影响

适配类型不直接生成业务用例，但会影响：

- 覆盖账本增加“缓存/异步/依赖状态”维度；
- 数据隔离与复位；
- 基线 gate（依赖/宿主可用性）；
- 用例排序（先读后写，写后复位）；
- 证据（key、行、消息、文件、邮件、WS 帧）。

Redis 示例：

- 创建后读：缓存未命中 → 回源 → 正确；
- 更新后读：缓存必须失效/更新；
- 删除后读：不能返回旧对象；
- TTL：过期后行为；
- 用例间：`FLUSHDB` 或 key 前缀隔离。

## 4. 生成层

### 4.1 不变量优先

由真实路由 + schema 直接生成，不调用模型：

| 不变量 | 期望 |
| --- | --- |
| 创建→读取 | 字段一致、id 一致 |
| 更新→读取 | id 不变、字段已更新 |
| 删除→读取 | 404 |
| 不存在资源 PUT/DELETE | 404 |
| 缺必填字段 | 400 |
| 未认证 | 401 |
| 无权限 | 403 |
| 列表包含新对象 | 包含 |
| Content-Type | application/json |
| 状态化序列 | create→update→delete 全链同一对象 |

这些覆盖 flask-vue-crud 暴露的 5 个真实缺口，不需要模型参与。

### 4.2 数据驱动配方

配方放 `src/aitest/resources/recipes/<id>/<version>.json`，与现有“检查模板”完全分开：

- 检查模板：咨询性清单，不进 S/M，继续保留；
- 用例配方：生成可执行用例，直接影响 S/M；
- 不共用 schema、不共用 `plan.templates` 字段、不共用结论语义。

首期配方：

| 配方 | 覆盖 |
| --- | --- |
| `rest-crud` | 列表/详情/创建/更新/删除 + 404 |
| `rest-validation` | 缺必填 400、类型错误 400 |
| `jwt-login` | 登录取 token、token 注入、非法 token 401 |
| `negative-auth` | 未带凭证 401、无权限 403 |
| `multi-service` | 前后端分离探针目标与健康 |

配方匹配只使用画像事实；匹配不上就不生成，进入未覆盖清单，不回退猜测。

### 4.3 模型只补业务语义

模型负责：

- 业务特有验收项（如“库存从 10 变 7”）；
- 不变量覆盖不到的流程；
- 复杂数据构造与业务断言。

模型不得负责：

- 决定有没有某条路由；
- 发明环境变量或凭据；
- 决定负向用例是否补认证；
- 决定预期是什么。

Prompt 约束：

- 注入画像 facts、`unknowns/unsupported`、允许的验证方式；
- 凭据来自 README/.env/配置默认值；
- 负向鉴权不得包含会被拒绝的 setup；
- `extract` 必须是 `{变量名: 响应体路径}`；
- 业务项一律 L2。

### 4.4 验收映射与来源

- 每条用例必须有 `expectation_source`；
- 引不上验收项原文的标“预期未证实”；
- 计划展示 `S/M` 与未覆盖清单；
- 用例标记来源：`invariant / recipe / model / engine`，记录配方 id/version；
- 报告可按来源筛选。

### 4.5 可执行验收样例

预期来源优先级：

1. 用户提供的可执行输入/输出样例；
2. 验收项原文；
3. 用户确认过的冻结预期；
4. AI 建议（只作候选，不能直接冻结）。

规则：

- 业务项有样例/原文 → 可执行；
- 只有 AI 建议 → 存 `plan.ai_expectations`，标“AI 建议，未证实”；
- 用户确认后 → 才能进入本次运行的冻结预期；用户拒绝 → 本次不采用，不进入计划；
- 确认界面：确认页逐条展示 AI 预期建议，标“未证实”；决策随 `run.start` 写入 `Run.ai_decisions`/`Confirmation.ai_decisions`，不改计划 revision；计划里的 `plan.ai_expectations.status` 只保留生成时的 `suggested`；
- 未确认的 AI 预期 → 只能标“预期未证实”，不进入通过；
- 都没有 → 标“预期未证实”，最多算 incomplete，不硬判通过；
- AI 不替用户定义业务真相。

### 4.6 状态与权限矩阵

- 数据状态：空、单条、多条、重复、边界、并发；
- 权限：角色 × 资源 × 操作，至少覆盖“无权”和“跨租户”；
- 状态流转：创建→更新→删除、重复提交、幂等。

按项目画像决定适用维度，不强制所有项目全量覆盖。

### 4.7 AI 输出契约

所有 AI 输出统一结构（`case_proposal`/`disposition` 用于计划用例与模板处置，其余方法用 suggestion/clarification/hypothesis/review_finding）：

```json
{
  "kind": "suggestion|clarification|hypothesis|review_finding|case_proposal|disposition",
  "scope": {"project_id": "...", "task_id": "...", "case_id": "..."},
  "statement": "...",
  "evidence": ["验收项原文/文件:行/响应片段"],
  "confidence": "high|medium|low",
  "requires_user_confirmation": true
}
```

规则：

- 必须引用验收项原文或证据；
- 禁止 `passed/failed/confirmed/suspected`；
- 禁止 `S/M`、覆盖率、通过率；
- 禁止凭据正文；
- 检测到结论词 → 整段不采用；
- 无证据 → 降级为 `unknown`。

存储位置：

- `plan.ai_reviews`：评审建议，生成时 `status=pending`；接受/驳回决策随 `run.start` 写入 `Run.ai_decisions`，不改计划 revision；
- `plan.ai_expectations`：生成时 `status=suggested`；确认/拒绝同样写入 `Run.ai_decisions`；
- `run.ai_hypotheses`：失败假设；
- 建议不写入业务结论字段。

## 5. 约束层

### 5.1 五条红线

| # | 红线 | 行为 |
| --- | --- | --- |
| 1 | 负向鉴权不补认证 | 验收项要求 401/403 时，assert 阶段不得带凭证；禁止把 401 改写成带凭证通过 |
| 2 | setup 只能期望成功 | setup 请求的 expect 不得出现 4xx/5xx；负向断言不得放 setup |
| 3 | 状态码必须断言 | 验收项写了 400/401/404 等，assert 阶段必须有 `path=status` |
| 4 | 结果与可信度分离 | 完成执行的断言失败保持 `failed`；AI 只给假设，最终由确定性规则定档；裁判不确定只影响 `suspected`，不得改成 `blocked` |
| 5 | 未知/未覆盖不算通过 | 空 `http:`、`unknowns`、未覆盖验收项不得计入通过；空 S 不得启动 |

实现：

- 直接写在 `plan_validation.py` / `lifecycle.py`；
- 只自动修复结构（extract 形态、status 断言、变量顺序），不修业务语义；
- 自动修复写入计划提示/警告；
- 不建守卫注册表、不建自动修复账本。

#### AI 假设 → 确定性定档

| 证据组合 | 结论 |
| --- | --- |
| 断言失败 + 断言与验收项一致 + 无脚本假设/环境/依赖异常 | `failed`（confirmed） |
| setup/服务/依赖不可用 | `incomplete`（blocked） |
| 脚本语法/导入/前置错误 | `error`，可修 |
| 断言失败 + 存在环境/依赖异常 | `incomplete`（blocked），不判产品失败 |
| 断言与验收项不一致，或 AI 指出的脚本假设有证据 | `error` 或 `incomplete`，不得 `failed confirmed` |
| AI 假设多解 + 无确定性证据 | `incomplete`（unknown），不猜 |

顺序要求：先排除脚本假设/断言不匹配/环境异常，再确认产品失败；AI 假设不能绕过这个顺序。

AI 的 `hypotheses` 只用于补充 `next_check`，不直接改上表结果。

### 5.2 断言强度 lint

- http 用例必须断言 `status` + 至少一个业务字段/状态；
- 负向用例必须断言状态码，不能只断言 `error` 存在；
- 脚本用例必须包含针对响应/状态/业务字段的 assert；
- 禁止“只要 200 就算通过”；
- 断言目标必须能映射到验收项原文。

输出：

- http 可判定的弱断言 → 计划警告/拒绝发布；
- 脚本只能静态判断到“疑似弱断言” → advisory，不静默通过；报告标“未证实”。

### 5.3 基线 smoke gate

按当前事实来源执行：

- 默认：项目可读、配置完整、可生成计划；已有服务只读可用则复用；
- 升级后：服务健康、登录/匿名访问、关键只读接口；
- 深度发现：再加前端首页/关键流程可达。

基线失败 → 本次 `blocked`，不进入产品失败判定。

### 5.4 数据隔离与波动控制

- 写用例使用唯一数据（uuid/时间戳）；
- 创建后清理或依赖服务 reset；
- 只读用例可重试；写用例不重跑；
- 两次结果不一致标“疑似不稳定”，两次证据都保留；
- 固定时钟/随机种子（可配置）；
- 依赖按 §3.9 的 D1–D4 处理：D1/D2 复位或隔离，D3 用唯一数据并标“隔离受限”，D4 标 unsupported。

## 6. 验证层

### 6.1 覆盖账本（advisory）

每个验收项按需标记：

| 维度 | 例子 |
| --- | --- |
| 正向 | 合法请求成功 |
| 负向 | 400/401/403/404 |
| 权限 | 无权限、跨租户 |
| 边界 | 缺字段、超长、类型错误、空值 |
| 状态流转 | 创建→更新→删除、重复提交、幂等 |
| UI | 页面/流程可达 |
| 跨服务 | 服务依赖、部分失败 |
| 缓存/异步 | 更新后缓存失效、队列消息、TTL |
| 依赖状态 | 数据库行、Redis key、对象文件、邮件 |
| 安全 | 认证、授权、CSRF、CORS、上传、限流 |
| 性能 | 响应时间、并发、限流、超时 |
| 可靠性 | 重试、幂等、补偿、断线重连 |

规则：

- 从验收项文本 + 用例覆盖推断“应覆盖维度”；
- 文本明确要求 401/404/400 → 负向必须覆盖；
- 提到角色/权限 → 权限维度；
- 提到必填/长度/类型 → 边界维度；
- 出现认证/授权/CSRF/CORS/上传/限流/注入 → 安全维度；
- 出现并发/超时/响应时间/吞吐 → 性能维度；
- 出现重试/幂等/补偿/死信/断线 → 可靠性维度；
- 没提到的标“未要求”，不扣分；
- 无法判断标 `unknown`，不强行判缺失。

展示：

```text
验收项：PUT /books/{id} 更新后保持原 id
正向 ✓  负向 404 ✓  权限 ✗（未要求）  边界 ✗（未要求）  状态 ✓
```

账本是 advisory：明确要求但缺失 → 列入未覆盖；未要求的不影响结论。

### 6.2 路由/流程覆盖

- 每个检测到的路由/方法至少一条用例，或显式排除；
- UI 关键流程同理；
- 覆盖不到 → `uncovered` 清单；
- 覆盖报告不作为硬门槛。

### 6.3 与项目自带测试交叉校验

- 只对失败用例跑其映射的既有测试；
- 结果只作为证据提示，不自动改判；
- 项目测试通过、插件失败 → 报告提示“需人工确认”；
- 没有映射测试 → 跳过。

### 6.4 Fixture Zoo（静态 / 集成两层）

```text
tests/fixtures/zoo/
  static/            # 离线，每次提交
    flask_decorator/
    fastapi_router/
    django_drf_router/
    express_router/
    axios_template_base/
    fetch_wrapper/
    openapi_generic/
  integration/       # 本地服务/Redis，发布/夜间
    jwt_negative_401/
    multi_service/
    redis_cache/
```

每个 fixture：

- 几十行源码；
- `expected.json`：画像、路由、前端调用、配方匹配、守卫结果、执行结论；
- `static`：不启动服务、不调模型；
- `integration`：只起本地服务/Redis，不访问外网；模型路径用录制响应回放；
- 两层都不访问外部网络。`openapi_generic` 使用仓库内固定的 OpenAPI 文件，不启动服务。

### 6.5 固定回归组合（Portfolio）

现有 5 个项目，按“角色”而不是“数量”使用：

| 项目 | 角色 | 栈 | 基线 |
| --- | --- | --- | --- |
| rbac-demo | 权限/多租户 baseline | Python 标准库 JSON API + 静态 Web | 8/8 缺陷检出，0 误报 |
| flask-rbac | 组织隔离 baseline | Flask + SQLite | 7/7 缺陷检出，0 误报 |
| flask-vue-crud | 全栈 CRUD baseline | Flask + Vue/Vite | 5/5 缺口检出，0 误报 |
| django-react-crud | 干净对照 + T1 协议栈 | Django + DRF + SQLite + React/Vite | 0 失败，0 误报 |
| store-pos | 大项目 + JWT/负向鉴权 | Express + sql.js + JWT + React/TS | 全部通过，0 误报 |

#### 运行时机

| 时机 | 跑什么 |
| --- | --- |
| 每次提交 | 单测 + `zoo/static` + 合同测试（离线、确定性） |
| 发布/夜间 | `zoo/integration` + Portfolio；按改动范围选子集，发布跑全量 |
| 改动仅涉及提取器 | 每次提交：只跑受影响 fixture；发布/夜间：fixture + 对应项目 |
| 改动涉及判定/红线 | 跑全量 Portfolio |

#### 判定标准

不是“全部通过”，而是“与基线一致”：

- 有缺陷项目：已知缺陷仍然检出；
- 干净项目：仍然 0 误报、0 误失败；
- 无新增 C1（假通过/误失败/误阻塞）；
- 探针/覆盖没有退化；
- 证据齐全。

#### 基线维护

- 每个项目有 `tests/portfolio/<project>/expected.json`：任务、计划、已知缺陷、误报、误失败、C1、探针；
- 基线变化必须附证据，不允许静默改写；
- 环境失败 → `blocked`，不算基线回归；
- 新项目加入条件：覆盖新轴、目标用户主流栈、或暴露新 C1；数量控制在 6–7 个以内。

### 6.6 新发现处理流程

```text
发现 → 归类（C1 correctness / C2 coverage / C3 UX）
     → 最小 fixture 复现
     → 类级修复（adapter / 红线 / 不变量）
     → fixture 进 zoo
     → 固定组合回归
     → 发布门槛
```

分类定义：

- C1 correctness：假通过、误失败、误阻塞、结论错；
- C2 coverage：未覆盖、未知、不支持；
- C3 UX：面板、报告、交互问题。

### 6.7 停止规则

- 连续 3–5 个新项目不再产生新的 C1 类，只产生 C2，说明体系收敛；
- 进入维护模式，不再为单个项目改核心。

### 6.8 合同测试

每次提交的“合同测试”指：

- CLI 命令名、`{"command","payload"}` envelope、错误码；
- Plan/Run/Report 必填字段与枚举；
- 面板 DTO 与后端字段映射；
- 旧计划读取兼容（新增字段可选）。

位置：`tests/contract/`；不启动服务、不调真实模型。

## 7. 插件级：默认不改变环境

### 7.1 默认行为

- 只读项目文件/配置；
- 已有服务在跑则复用，不重复启动；
- 不装浏览器、不跑容器、不新增常驻进程/端口；
- 缺事实 → `unknown`，不猜；
- 测试仍可能写业务数据：写用例必须唯一数据并有清理/reset；用户不需要额外配置。

### 7.2 升级动作

- 缺事实且影响验收 → 提示一次：“允许启动服务读取真实接口吗？”；
- 需要浏览器/契约 fuzz → 用户点击“深度发现”，显式确认；
- 升级后重新生成计划（新 revision）并重新确认；
- 失败/拒绝 → 回退默认，保留已获得的事实。

### 7.3 依赖预算

- 核心：Python 标准库 + requests；
- 可选：Schemathesis、Playwright、mitmproxy、Testcontainers；
- 可选组件只在深度发现时按需加载，不随默认包分发；
- 不可用时降级，不阻塞默认路径。

### 7.4 UI

- 项目概览：能力画像卡，显示本次用了哪些事实来源；
- 计划页：来源构成 + 未覆盖/未知；
- 确认页：只展示未知/不支持/未覆盖/副作用；
- 不显示“模式选择”；
- 不做指标看板、不做配置向导；
- 未知默认折叠。

### 7.5 缓存与复用

- 画像按源码/配置指纹缓存；
- 计划按任务/规则缓存；
- 只跑失败项、断点续跑。

## 8. 复用经济

### 8.1 协议复用

OpenAPI/Swagger、Playwright 网络抓包为主；GraphQL introspection、gRPC reflection 暂列实验性，fixture 落地前不承诺。

### 8.2 引擎薄封装

主路径两个：Schemathesis、Playwright；其余为借鉴/可选，不算入口。先不抽象统一接口：

| 能力 | 采用/借鉴 | 说明 |
| --- | --- | --- |
| OpenAPI 契约/边界/负向 | Schemathesis | 有 spec 时直接作为 runner |
| 浏览器/网络抓包 | Playwright | 抓真实请求，替代静态猜封装 |
| 状态化 CRUD 序列 | RESTler 思路 | 借 create→update→delete 序列，不重写状态机 |
| 流量回放 | mitmproxy | 可选；跨平台 |
| 依赖/环境 | Testcontainers + 原生客户端 | DB/Redis/队列的启动、复位、探针；可选 |

可选、非核心：Qodo Cover/Pynguin/EvoSuite（单元测试覆盖率）、Pact（双方契约）。这些不进入验收主路径，只在明确需要时接入。

RESTler 只借序列思路；mitmproxy/Testcontainers 可选。只有接入第三个引擎时，再抽统一适配接口。

### 8.3 结果归一化

外部引擎结果不能直接当验收结论，必须：

- 映射到路由/用例；
- 映射到验收项；
- 经过五条红线；
- 生成证据；
- 去重/归一化签名。

### 8.4 项目产物复用

- OpenAPI/GraphQL/gRPC schema；
- 项目自带测试；
- README/配置中的默认凭据；
- CI 命令、迁移、种子数据。

### 8.5 许可与平台

- 只嵌入 Apache/MIT 等可分发组件；
- Linux-only（Keploy）标可选；
- 商业工具只借鉴思路，不嵌入。

### 8.6 不重复造

不造：API fuzzer、浏览器录制器、流量代理、单元测试生成器、容器编排、自愈 locator。

只造：验收映射与 S/M、四值判定、五条红线、证据链、插件体验。

### 9.2 四个概念必须分清

| 概念 | 含义 | 是否算通过 | 展示位置 |
| --- | --- | --- | --- |
| failed | 执行完成且断言失败 | 否 | 结果/问题/报告 |
| blocked | 前置、环境或服务未就绪 | 否 | 结果/报告 |
| unsupported | 插件没有该能力 | 否 | 概览/确认页/报告 |
| uncovered | 有能力但本次没覆盖 | 否 | 计划/报告未覆盖清单 |

映射到业务四值：

| 情况 | 业务结论 |
| --- | --- |
| 执行完成且断言失败 | `failed` |
| 前置/环境/服务未就绪 | `incomplete`（原因 blocked） |
| 插件不支持该能力，但验收项适用 | `incomplete`（原因 unsupported） |
| 有能力但本次没覆盖 | `incomplete`（原因 uncovered） |
| 验收项本身不适用于本项目 | `not_applicable` |

`blocked / unsupported / uncovered` 是原因，不是第五种结论；`not_applicable` 只能用于“验收项本身不适用”，不能用来掩盖“插件没能力”。

新项目出现更多 `unsupported/uncovered` 不是退步，而是把“原来会猜错/假通过”的部分变成了明确缺口；缺口可以后续加适配器或配方消掉，假通过不能。

### 9.3 降级

- 运行时内省失败 → `source=static, degraded`；
- 概览/确认页/报告明确显示“降级”；
- 未知项增多，计划来源更多是 model；
- 不把降级结果写成“全部通过”。

### 9.4 首次与后续

- 首次：可能多一次服务启动确认、多几条未知/未覆盖；
- 用户修正端点/认证/凭据通过现有 `project.config` 完成，重新生成计划后进入快照；
- 后续项目复用画像，不再重复问同类问题。

## 11. 兼容性与合同

- 新增字段全部可选：`plan.capabilities`、`plan.recipes`、`plan.coverage_ledger`、`plan.ai_expectations`、`plan.ai_reviews`、`run.ai_hypotheses`、`run.ai_decisions`、`Confirmation.ai_decisions`、`Case.generation`、`Case.assertion_strength`；具体 schema 见[改造施工图](2026-11-26-改造施工图.md) §1；
- 不使用 `Case.template_id` 作为新契约；检查模板仍只存 `plan.templates`，配方存 `plan.recipes`；
- `run.ai_hypotheses` 是新结构化字段；`Analysis.candidate_causes` 只读兼容，新运行不再写入；
- AI 预期/评审决策走 `run.start` 的 `ai_decisions`，写入 `Run.ai_decisions`/`Confirmation.ai_decisions`，不改计划 revision；
- `plan.templates` 继续只存检查模板，语义不变；
- 旧计划可读，不静默迁移；需要新能力时重新生成计划（新 revision）；
- 不引入常驻服务、数据库、消息队列；
- 结论仍是四值，S/M 口径不变，证据与凭据约束不变；
- 运行时内省/深度发现必须显式确认，不能静默启动服务。

## 12. 实施

### 12.1 MVP（约 4–6 周）

- 五条红线补全 + 单测；
- HTTP 断言强度 lint；
- 基线 smoke gate；
- 覆盖账本（advisory）；
- 默认不改变环境行为 + 一次确认升级；
- OpenAPI 适配；
- 7 个静态 fixture（`zoo/static`）；
- 5 个现有项目基线校准（发布/夜间跑）。

验收：

- 新项目不再出现假通过/误阻塞；
- 每个 C1 类有静态 fixture；
- 未识别能力、未覆盖维度可见；
- 现有项目基线不回归。

### 12.2 第二阶段（约 2–3 周）

- Playwright 网络抓包；
- `zoo/integration`：`jwt_negative_401`、`multi_service`、`redis_cache`；
- 依赖适配器：Redis + SQLite 的识别/复位/探针；Postgres/MySQL 待 fixture 后升级；
- S3/MinIO、Mailpit、WebSocket/SSE、第三方 HTTP mock：fixture 落地前只标实验性；
- Schemathesis 可选 runner。

验收：

- 真实服务/依赖类 fixture 可重复；
- 缓存/队列/存储类未覆盖能力在报告可见。

### 12.3 后置（按需）

- mitmproxy/Testcontainers；
- 次批/后续类型：MongoDB、Elasticsearch、RabbitMQ/Kafka、工作流、SSR、GraphQL、向量/时序/图、移动/桌面、支付 webhook；
- 权限/状态矩阵扩展；
- 变异/覆盖充分性抽样；
- 引擎统一适配接口（接第三个引擎时再抽）；
- 更多 fixture 与项目组合。

触发条件：

- 出现新的 C1 类；
- 某个栈的 T2 覆盖率不足；
- 用户明确需要深度发现。

### 12.4 AI 接入顺序

| 阶段 | 内容 |
| --- | --- |
| 0（1 周） | AI 输出契约、后端内部配置 `ai.mode=legacy|assist|off`（不暴露 UI）、结论词过滤、golden harness |
| 1（2–3 周） | 计划生成拆分、计划评审、歧义检测 |
| 2（2 周） | `judge_failure` 改假设、确定性定档、配置/数据建议 |
| 3（后置） | UI 探索、离线 adapter/配方/fixture 草稿 |

AI 接入不改变主线的五条红线和四值结论。

## 13. 指标与发布门槛

| 指标 | 目标 |
| --- | --- |
| 声明支持范围内 false_pass | 0 |
| 误失败（false_fail） | 持续下降；环境类由基线 gate 拦截；确认属于插件误判的计入 C1 |
| 未覆盖/未知 | 每次发布可见 |
| 新增栈改动 | 只加 adapter/配方/fixture |
| 每次发布新增 correctness 类 | 0 |
| 默认路径副作用 | 不启动服务/不安装/不常驻；业务写操作有提示 |
| 已实现适配类型 | 有 D 级、复位/隔离、证据 |
| AI 建议采纳率 | 统计 `accepted / (accepted + rejected)`，不设硬目标 |
| AI 错误断言率 | 持续下降 |
| CRUD/负向用例 AI 参与比例 | 接近 0 |
| AI 调用次数/项目 | 只与未覆盖业务项相关 |
| 关闭 AI 后的确定性链路 | 完整可运行 |

发布门槛：

- 每次提交：五条红线单测 + `zoo/static` + 合同测试全过；
- 发布/夜间：`zoo/integration` + Portfolio 与基线一致（含证据）；
- 新增 C1（假通过/误失败/误阻塞）为 0。

## 14. 风险与取舍

| 风险/冲突 | 处理 |
| --- | --- |
| 覆盖透明 vs 默认路径 | 默认不启动；缺事实问一次；拒绝则标未知 |
| 覆盖透明 vs 不误测 | 宁可不判通过，也不猜；未知/未覆盖不算通过 |
| 复用 vs 不误测 | 复用引擎执行，结论由守卫与映射层产生 |
| 复用 vs 插件级 | 外部引擎可选、按需加载；核心不依赖 |
| 运行时内省有副作用 | 显式确认；失败回退静态并标 unknown |
| 无 OpenAPI/服务起不来 | 静态兜底；T3/T4 明示 |
| 模型业务断言不可靠 | 样例/交叉校验；静态+模型不写“全部通过” |
| fixture 维护成本 | 每个只测一个维度；新发现才加 |

## 15. 非目标

- 不追求“测遍所有技术栈”；
- 不为每个框架写专用执行引擎；
- 不重写 API fuzzer、浏览器录制器、流量代理、单元测试生成器；
- 不引入常驻服务/数据库/指标看板；
- 不承诺“任何项目都绝对不漏”；
- 不用“提高覆盖”为理由放松不误测红线。

## 16. 完成定义

1. 每次提交 `zoo/static`/单测/合同测试通过；发布/夜间 `zoo/integration` + Portfolio 与基线一致；
2. C1（假通过/误失败/误阻塞/结论错）新增为 0；
3. 新项目首次运行只产生 C2/C3，不产生 C1；
4. 未识别能力、未覆盖维度、事实来源在报告首页可见；
5. 加一个新栈只加 adapter/配方/fixture；
6. 五条红线、断言强度、基线 gate 全部有单测；
7. 默认路径不启动服务/浏览器/容器；写操作有数据副作用提示；
8. 已实现适配类型（Redis/SQLite）有 D 级、复位/隔离策略与证据；S3/MinIO/Mailpit/WebSocket/SSE/外部 mock 在 fixture 落地前标实验性；其余明确列出未支持项；
9. AI 只输出 suggestion/clarification/hypothesis/review_finding，无结论词、无 S/M；
10. `generate_cases` 只处理未覆盖业务项；`judge_failure` 不再直接给 verdict；
11. 关闭 AI 后，确定性链路可完整运行。

| 浏览器 | Chrome、Firefox、Safari | 兼容性、localStorage、Cookie、IndexedDB |
| 移动设备 | iOS、Android | 权限、通知、离线 |
| 桌面 | Windows、macOS、Linux | 安装、文件系统、进程 |
| 容器/编排 | Docker、K8s | 启动、健康、网络 |
| Serverless | Lambda、Cloud Functions | 冷启动、超时、事件 |
| 反向代理/CDN | Nginx、Traefik、Cloudflare | 路由、TLS、缓存 |

### C.6 质量 / 测试维度

这些不是“技术栈”，但属于覆盖类型：

| 维度 | 关注点 |
| --- | --- |
| 安全 | 认证、授权、CSRF、CORS、注入、文件上传、速率限制 |
| 性能 | 响应时间、并发、限流、超时 |
| 可靠性 | 重试、幂等、补偿、死信、断线重连 |
| 数据一致性 | 缓存与 DB、跨服务、最终一致 |
| 可访问性/国际化 | a11y、i18n、时区 |
| 合规 | 审计日志、PII、删除权、保留期 |

质量维度按验收项适用，不默认全部纳入覆盖账本；适用时由账本标记。

## 20. 附录 D：AI 任务明细

### D.1 任务清单

| 任务 | 输入 | 输出 | 约束 |
| --- | --- | --- | --- |
| 验收项拆解 | 验收项原文、目标、画像 | 维度建议、澄清问题、候选样例 | 只建议，不直接改预期 |
| 歧义检测 | 验收项、任务 | 澄清问题、候选样例 | 无法澄清标“预期未证实” |
| 业务用例设计 | 未覆盖业务项、画像 | 业务 cases | 必须绑定验收项原文 |
| 计划评审 | 计划、验收项、画像 | review_finding | 不直接改计划/结论 |
| 失败归因 | 用例、响应、日志、证据 | hypotheses + next_check | 不直接给 verdict |
| 测试数据 | 业务字段、约束 | 数据建议 | 唯一性/隔离由确定性层做 |
| 配置推断 | README/.env/CI/配置 | 启动/端口/认证建议 | 给来源，用户确认 |
| 报告/问题撰写 | 证据、用例、运行 | 标题/步骤/摘要 | 只写事实，过滤结论词 |

### D.2 输出示例

澄清：

```json
{
  "kind": "clarification",
  "item_id": "ai_...",
  "statement": "“管理”具体指哪些操作？",
  "suggested_dimensions": ["positive", "negative", "auth"],
  "requires_user_confirmation": true
}
```

评审：

```json
{
  "kind": "review_finding",
  "case_id": "case_...",
  "severity": "high",
  "statement": "只断言 status=200，未验证字段更新",
  "suggestion": "增加 body.title/author/read 断言",
  "evidence": ["验收项原文", "case.expected"]
}
```

归因：

```json
{
  "kind": "hypothesis",
  "case_id": "case_...",
  "hypotheses": [
    {"cause": "产品未保持原 id", "evidence": "...", "next_check": "GET /books 响应体"},
    {"cause": "脚本按错误字段查询", "evidence": "...", "next_check": "检查脚本字段名"}
  ]
}
```

### D.3 评测

- 录制模型响应，CI 不依赖真实模型；
- golden tests 覆盖：schema、结论词过滤、证据引用、无证据降级；
- 人工标注 20–30 条验收项，评估歧义识别率；
- 统计建议采纳率与驳回原因；
- 真实模型只做 nightly/发布前 smoke。

### D.4 迁移与回退

- 后端内部配置 `ai.mode=legacy|assist|off`，不暴露用户可见模式；
- 新字段全部可选：`plan.ai_reviews`、`run.ai_hypotheses`、`case.generation.source=model`；
- 旧计划可读；
- AI 不可用 → 建议为空，确定性链路继续；
- AI 建议不得写入业务结论字段。
