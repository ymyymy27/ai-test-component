### 4.1 接入前勘定：解释器核对的值从哪来（只读核对，未改代码）

动手前先核对主责合同，得到三条会改变实现方式的事实：

1. **冻结的解释器身份不在 `ExecutionSourceBinding` 里**。合同（架构01 第 12 节）说 prepare 冻结「解释器/可执行文件身份、…、已登记入口与参数、…、适配器版本」，但实测该绑定字段为 `registered_entry`／`entry_arguments`／`cwd_mapping`／`allowed_env_keys`／`secret_refs`／`test_config_ref`／`adapter_versions`／`resolved_input_digest`——**含解释器字段：False**。解释器身份在环境分支：`EnvironmentRefFact.interpreter_identity` 与 `EnvironmentResolutionFact`（`executable_path`／`executable_digest`／`interpreter_version`／`base_executable_path`／`base_executable_digest`／`probe_prefix`／`base_prefix`）。即 prepare 的冻结由「绑定 + 环境引用」**两处共同承载**，实现时不能只在 binding 里找。
2. **`prepared` 里这条路径是可达的**：`action_resolver._environment_resolution(prepared)` 读 `prepared["environment"]["resolution"]` 并构造 `EnvironmentResolutionFact`。因此 `frozen_interpreter` 可取该事实的 `executable_path`（prepare 时由核心观测载体记录的路径），无需新增端口。
3. **`observed_executable` 必须来自一次新的探测**。`require_interpreter` 比较的是 `Path(...).resolve()` 后的**路径**（口径对齐 `source_checks._derive_state` 的 `actual_interpreter_mismatch` 分支，不自行发明身份摘要）；start 时的"实际值"只能由 `PythonLoadSourceProbe` 现场 probe 得到——而该探针在默认装配里**被构造却从未被调用**。这才是解释器核对接不上的直接原因。

**口径已结清（无需再裁定）**：上一段曾把它列为待确认，随后在**被引为权威的实现**里找到了答案。`source_checks._derive_state` 第 182–186 行：

```python
if (
    request.expected_interpreter_ref and observation.observed_interpreter_ref
    and Path(request.expected_interpreter_ref).resolve()
    != Path(observation.observed_interpreter_ref).resolve()
):
    return SourceVerificationState.MISMATCH, ("actual_interpreter_mismatch",)
```

即主责口径就是**解析后的路径一致**，不是摘要身份比对；第 212–218 行另外要求 observed 侧必须存在、为绝对路径且是文件（否则记 `actual_interpreter_missing`／`actual_interpreter_path_unverified`）。`EnvironmentRefFact.interpreter_identity` 是**环境修订的身份**，不参与这个比较。因此 `admit_start` 的两个参数映射为：`frozen_interpreter = request.expected_interpreter_ref`（取自冻结环境事实的 `executable_path`），`observed_executable = observation.observed_interpreter_ref`（来自 start 时的新探测）。**不需要为此改合同或改口径，也不需要引入字节级摘要比对**——若要更强的字节级身份，那是另一个需求，不应借本次接入顺带改变既有口径。

### 4.2 第 1 步收尾的前置：项目选择走目录绑定，而 `bind_project` 不可派发

面板的**业务动作区**要能用，前置是"选定项目"（写动作的 `Command` 还要求 `intent_id` + `expected_revision`）。**本节先给过一次不准确的表述（写作"入口无法枚举项目"），随后核对合同更正如下。**

合同把"项目选择"定义为**目录绑定**：架构05 第 3 节〔目录绑定：规范化当前目录、**选择/建立稳定项目**，取得 `binding_revision`；多目录显式选择，**显示名不是键**〕；设计文档也要求「当前项目选择器始终可见…多目录工作区由用户明确选择绑定」。因此合同机制**不是**"列出所有项目"。

核对实际动作面：

| 动作 | 状态 |
| --- | --- |
| **`bind_project`**（合同定义的项目选择动作，在动作表与 `HUMAN_ACTIONS` 中） | **声明了但默认不可派发** |
| `save_binding` | **已注册**，但**不在一期动作表内**（表外动作） |

即：**合同定义的项目选择动作不可用，可用的绑定动作不在合同表里**。这是动作面与合同的不一致，需要人来裁定（把 `bind_project` 接上，还是把 `save_binding` 纳入合同），不应由实现方单方选定。

补充实测（说明为什么不能用别的动作凑合）：`query` 强制 `project_id`，不带则 `B_INVALID_PARAMETER`，只能查单项目；`events` 作为工作空间级只读动作能间接看到 `project_id`（实测见到 `project-a`、`project-b`），但受**事件窗口与 `limit`** 限制，项目在该窗口内无事件就不会出现——**不能**当作项目清单（否则会把"没查到"显示成"不存在"）。两者都不是合同定义的目录绑定机制。

### 6.1 结清一个未解释疑点：mypy 报的文件数

会话中 `mypy` 的成功行一开始报 228 个源文件，后段变成 227，而 `src/` 下始终恰好 **213** 个 `.py`（全部位于 `src/aitest`）。为了确认不是**源文件被静默跳过**，做了受控实验：

1. 在 `src/aitest/` 下临时新增一个带真实类型错误的文件（返回 `str` 而声明 `-> int`，**不加** `type: ignore`）→ mypy 报 `error: Incompatible return value type ... [return-value]`，计数变为 228；
2. 删除该文件 → 计数回到 227，无错误。

结论：**`src/aitest` 的每一个文件都在 mypy 覆盖内**（计数随新增文件同步，且真实错误被报出）。228 与 227 的差异来自 mypy 通过导入关系额外跟进的文件数，不是静态门禁的覆盖缺口。第一次实验我误在错误行上写了 `# type: ignore[return-value]`，把错误压掉、得到"通过"的假象——已重做并记录。

### 6.2 本机改文件的一个坑：不要用 PowerShell 往返写 UTF-8 源码

做上一条的受控漂移验证时，我用 `Get-Content -Raw` 读、`Set-Content -NoNewline` 写 `integrations/trae/src/core-bridge.ts`，结果中文注释被按控制台编码重写，文件变成**非法 UTF-8**，随后“还原”又写坏一次。已用 `git checkout --` 恢复并复核无残留差异。教训：这类仓库里改文件一律走编辑工具或 Python 显式 `encoding="utf-8"`，不要用 PowerShell 的文本 cmdlet 做读写往返。

### 6.3 新增守卫：编辑器入口的只读白名单不得漂移

`core-bridge.ts` 的 `READ_ONLY_ACTIONS` 是**手工复制**的 `contracts.commands.READ_ACTIONS`，它决定面板能派发什么，属安全边界，此前无测试守着（本会话刚修过一次同类脱节：MCP relay 的 `_QUERY_FIELDS`）。新增 `tests/unit/test_trae_read_only_allowlist.py`：要求二者**完全相等**（不是包含即可——两个漂移方向都有害），并单独锁定白名单与全部写动作交集为空。已受控验证非空转：注入 `publish_plan` 后两条断言均失败并精确报出违规动作与两侧对称差。
