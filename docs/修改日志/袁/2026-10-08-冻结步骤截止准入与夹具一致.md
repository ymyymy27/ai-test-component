# 冻结步骤截止准入与夹具一致（C-12）

基线 `d7b821b`，`fix`；C-12，主责[一期架构01第1节](../../项目文档/一期/架构文档/01-项目与计划.md)环境冻结属性与[架构02第10节调度控制](../../项目文档/一期/架构文档/02-执行与证据.md)，FR09/10、AC19/23/34；ABC 仍 21 整项。

## 1. 根因（已复现）

`EnvironmentRef` 声明 `request_timeout_seconds` / `step_timeout_seconds`，合同把“请求与步骤超时配置”列为**运行冻结属性**；`Attempt.timeout_ms`、`ExecutionRequest.timeout_ms` 与真实命令适配器的截止计时（`command.py`：`request.timeout_ms is not None` 才启动计时）都依赖它。但执行链从不消费该声明：`ExecutionAuthorizationService.prepare` 直接接受注入的动作解析器返回的截止，既不核对冻结环境，也不要求“未声明即无截止”。于是：

- 环境已冻结 120 秒步骤截止时，解析器仍可用**任意**截止（或无截止）冻结执行依据；
- 无截止的步骤可以无限等待，与 C-12“默认业务执行截止、不靠无限等待规避”相悖；
- 共享夹具在环境记录里声明 `step_timeout_seconds=120`，解析器却给出别的截止，夹具本身即是不一致的依据。

## 2. 源码修改

[authorization.py](../../../src/aitest/application/execution/authorization.py)：

- 新增 `_frozen_step_deadline_ms(prepared)`：按冻结准备的 `environment_id`/`revision` 精确读取 environment 记录，核对封套；`step_timeout_seconds` 必须是**非 bool 正整数**，缺失返回 `None`（可读历史，但没有冻结截止）；无法读取或形状不符一律 `ApprovalRequired`。
- 新增 `_require_frozen_step_deadline(prepared, resolved)`：`resolved.request.timeout_ms` 必须等于声明值 ×1000；未声明时必须为 `None`——不允许自报未冻结的截止。
- 在 `prepare` 的冻结依据核对之后（解析器返回同一冻结基础之后）调用，先于任何授权/确认记录写入。

## 4. 边界

生产装配（`bootstrap.assemble_workspace_core`）仍**未注入可信动作解析器**（`execution_action_resolver` 默认 `None`），因此本核对目前只在已注入解析器的组件/宿主路径生效；默认真实执行截止、真实宿主交互与长步骤验收仍缺，C-12 整项不闭合，真实 AC 仍 0 verified，未用组件结果代填。
