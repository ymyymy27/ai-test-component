# 测试 flaky 根因（WorkspaceInUse 非锁冲突）与面板三段信息区的阻断

文档基线 `c785d8c`（分支 `fix`）。本文记录 2026-10-12 的第三批：把「全量跑暴露的 6 项 `WorkspaceInUse`」追到**启动等待超时**这一真正根因并修掉（只改测试侧），以及为面板三段信息区（一期 P1-FR17／P1-AC26/27）查出的**只读项目身份来源缺失**这一阻断。

## 1 `WorkspaceInUse` 的真正根因

全量 5011 项跑出 6 项 `WorkspaceInUse`，分布在 4 个真实起核心的测试文件里。**它不是锁文件冲突**：

```
interfaces/local/editor_host.py:104   WorkspaceInUse("核心启动后在限定时间内不可连接")
interfaces/local/editor_host.py:60    wait_timeout_seconds: float = 5.0
bootstrap.py:156                      _DEFAULT_WAIT_TIMEOUT_SECONDS = 5.0
```

`EditorHost.acquire` 给出一个**有界的等待期限**：真实核心进程要在 5 秒内启动并可连接。对单文件运行足够；但全量跑时机器持续满负荷（大量真实装配、真实文件提交、真实子进程），冷启动超过 5 秒即报此错。

**这类假失败有实际危害**：会让「改了代码、旧断言变红」被当成噪声忽略——正是 `AGENTS.md` 第 5.5.4 条要防的事。查证过程中的两次经验也印证了它：`test_editor_host_ownership.py` 在全量复跑附近失败一次、单独复跑即通过。

## 2 裁定：只改测试侧，不改生产默认

**5 秒是有界且如实的失败**（设计文档要求「如实报不可用、不伪装成功」），合同也**没有**规定该期限（全库检索「等待核心／启动超时／不可连接 + 秒」无结果）。为了让测试变绿而调大生产默认，等于**改变产品语义**——不做。

做法：新增 `tests/support/core_wait.py`（`REAL_CORE_WAIT_SECONDS = 30.0`，远小于 `_wait_seconds` 的 60 秒上限，**仍有界**），把用**默认值**起真实核心的 9 处调用显式传它：

| 文件 | 处数 |
| --- | --- |
| `tests/unit/test_mcp_stdio_read.py` | 3 |
| `tests/unit/test_mcp_stdio_write.py` | 2 |
| `tests/unit/test_json_unicode_boundaries.py` | 1 |
| `tests/unit/test_mcp_default_reuse_inspection.py` | 1 |
| `tests/unit/test_cli_core_forwarding.py` | 1 |
| `tests/unit/test_editor_host_ownership.py` | 1 |

**同时确认**：更重的真实核心用例（`test_a_a02_core_dispatch`、`test_a_a10_connection_recovery`、`test_a_bootstrap_acquire`）**本就显式传了 8.0 秒**，全量跑里也没失败，故不动它们。这次只补「完全没传期限」的那些——正好就是全量跑失败的那几个文件。

**过程留痕（一次自己踩坑并纠正）**：第一版脚本粗暴处理跨行调用，把 `test_a_a02_core_dispatch.py` 的缩进改坏。没有硬修，而是 `git checkout -- tests` **全量回退**，改成「只替换单行、跨行一律跳过并报告」的安全版本，并实测确认那些跨行调用都已显式带 8.0 秒。

## 3 面板三段信息区：缺一个只读的项目身份来源

设计文档《01-面板与工作台》把**面板骨架与三段信息视图**定为一期 **P1-FR17（P1-AC26/27）**：运行前「这次到底要检查什么」、运行时「现在到哪了、有哪些缺漏」（核心价值是缺漏五类计数常驻）、运行后给结论／计数／证据充分性。

**实测阻断**：

- 业务/缺口数据只能走 `query`：`QuerySpec` 承载 `reports.latest`／`reports.by_id` 与 `issues.list`（含 `blocking` facet），`ReportSnapshot` 已提供 `business_outcome`／`evidence_grade`／`primary_gap`。
- 但 `QuerySpec.project_id` **必填**（`contracts/queries.py:63`）。
- 而**没有任何只读动作能列出或解析项目**：`list_projects`／`projects_list`／`current_project` 全不存在。`Command.project_id` 虽可选，对 `query` 无济于事——参数里那份 `QuerySpec` 仍要真实项目号。
- 面板当前也没有项目身份，只接 `ensure-core` 与工作空间级只读派发。

**结论**：面板三段业务字段卡在「缺一个只读的项目身份来源」。这与 `backup`／`migrate` 卡在「工作空间级维护写动作该携带何种身份」是**不同**问题：那一处缺身份口径，这一处缺**一个只读动作**。

**未做的事及原因**：**没有**加「让用户手输项目号」的输入框。设计文档里面板显示的是**由核心给出的当前项目与计划**；手输等于把事实来源搬到界面上，且会绕开「界面点击不等于用户确认」的边界。这属合同/设计裁定。建议由合同在只读面补一个项目枚举／当前项目动作，或明确 `query` 在无项目时的合法语义。已记入交接说明 §9.2。
