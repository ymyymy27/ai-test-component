## 2. 当前 CI 是否合理

| 项目 | 判断 | 本次处理 |
| --- | --- | --- |
| Windows + Python 3.13、锁文件、版本/ruff/mypy/Schema/pytest | 与一期工程配置相符；Windows CI 不是 Windows 11/真实 Trae 验收 | 保留；不恢复二期跨系统矩阵 |
| 日常不运行面板/Trae | 是提交 `7b925b0`（PR #14）明确采用的 Python 日常检查范围 | 保留；不以普通 CI 成功表示前端验收通过 |
| 缺 `check_peer_identity` 导致收集失败 | 合理暴露“测试要求接口但源码没有实现”，不是应豁免的 CI 误报 | 不改测试、不忽略文件、不用 continue-on-error；仍应失败 |
| 收集错误让其他测试不执行 | 默认行为合理，但当前阶段诊断信息不足 | 改为 `--continue-on-collection-errors`，继续运行可收集测试并保留 error 与非零退出码；`always()` 上传 JUnit，报告存 runner.temp/14 天 artifact |
| Schema 只用 git diff | 不包含新生成而未追踪的文件 | 改为限定 Schema 目录的 `git status --porcelain --untracked-files=all`，任意变更都失败 |
| tag 制品打包没有 npm ci/共享面板构建 | 干净 runner 没有 tsc/esbuild/vsce 依赖和 panel/dist/index.js；这是实际缺口 | 仅 tag 分支补 setup-node@v6 / Node 24、两份锁文件 npm ci、先构建共享面板再打包扩展和 wheel |
| develop 保护规则没有必须成功的 status check | CI 当前提供检查结果，未充当成功合并门禁；这与“CI 绿灯”是不同事实 | 本次不改服务端保护规则；修复基线失败后应由项目维护者决定是否启用成功检查要求 |

参数语义核对[pytest 官方参考](https://docs.pytest.org/en/stable/reference/reference.html#command-line-flags)，Node/npm 准备方式核对[setup-node 官方说明](https://github.com/actions/setup-node)。未发 tag、未创建 release、未扩大日常 Node 检查范围。发布门仍依赖所有 Python 检查成功，因此现有产品失败时不会进入发布。
