# 冻结截止守卫暴露的长步骤夹具不一致

基线 `46a3d7a`，`fix`。修正 3 个因 C-12 冻结步骤截止守卫而失败的旧夹具（解析器自报 10 分钟，夹具环境只声明 120 秒），不放松守卫本身。

## 1. 发现（六路文件分块回归）

把 `tests/unit` 的 260 个文件按轮转分成 6 批并行运行（`-v --tb=line`），除已修的陈旧夹具外，暴露 3 项与守卫直接冲突的失败：

- `tests/unit/test_default_active_control.py::test_default_long_step_pause_resume_and_actual_cancel`
- `tests/unit/test_default_active_control.py::test_default_new_core_and_adapter_use_saved_stop_without_inventing_exit_code`
- `tests/unit/test_default_live_output.py::test_default_active_large_output_stays_running_and_preserves_pause`

三者都经 `LongCommandResolver`（`timeout_ms=600000`，命令 `time.sleep(300)`）走真实 `prepare_execution`，而共享夹具环境在 [2026-10-08 的截止准入](../../../src/aitest/application/execution/authorization.py) 之后声明 `step_timeout_seconds=120`：

```
aitest.domain.approvals.ApprovalRequired: resolved execution must use the frozen step timeout,
not an unfrozen deadline
```

即：守卫本身工作正常，**旧夹具声明与用例真实需要的步骤截止不一致**。

## 2. 修正

- [test_authoritative_preparation.py](../../../tests/unit/test_authoritative_preparation.py)：夹具体改为 `_authoritative(tmp_path, *, step_timeout_seconds=120)` 上下文管理器；`authoritative` 保持默认 120 秒（既有用例不变），新增 `authoritative_long_step`（600 秒）供真实长步骤用例声明其实际需要。
- `test_default_active_control.py`、`test_default_live_output.py`：上述 3 个用例改用 `authoritative_long_step`，其解析器 600000ms 与冻结声明一致。
- 未改产品代码，未放松守卫：解析出的执行请求仍必须等于冻结环境声明的步骤截止。

- 六路分块回归仍在继续（每批 43–44 个文件，含单项 setup 30–110 秒的真实文件事务用例）；本文件记录的是截至 04:00 的结果，剩余批次结果在后续批次登记，不用旧全量顶替。
- 生产装配仍未注入可信动作解析器，本守卫目前只在已注入解析器的组件/宿主路径生效；C-12 整项不闭合，真实 AC 仍 0 verified。
