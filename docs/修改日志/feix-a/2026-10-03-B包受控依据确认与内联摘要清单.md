## 2 新增动作 `confirm_assertion_basis`（动作表 17 → 18）

**调用方只能声明"我核对了哪个用例的哪一版依据"**：

| 参数 | 说明 |
| --- | --- |
| `case_id` | 确认必须绑定具体用例 |
| `case_revision` | **准确**用例修订，不接受"最新" |
| `basis_text_digest` | 调用方**宣称**核对的依据摘要；必须与那份用例记录一致 |

**系统派生、调用方不得自称**：

| 字段 | 派生方式 |
| --- | --- |
| `basis_revision` | 取自已按准确修订读回的用例的 `assertion_basis.revision` |
| `confirmation_id` | `confirmation-{case_id}-r{basis_revision}` |
| `confirmed_at_commit` | **保存之前**取的 `next_commit_seq()` |

## 3 接入时发现并堵住的两个缺口（**实测**）

| # | 缺口 | 实测证据 |
| --- | --- | --- |
| 1 | **可以确认一个不存在的依据** | `ConfirmationRecord(basis_revision=999, basis_text_digest='sha256:bogus')` **构造成功**；领域只校验非空与 `>= 1`。若不比对，会记下一条"确认了不存在的依据"的记录——将来永远匹配不上任何依据，却看起来像已确认 |
| 2 | **`confirmed_at_commit` 由调用方给** | 领域只校验非空 → 调用方可声称"我在某次提交时确认的"。改为保存前取 `next_commit_seq()` |

**为什么必须在保存前取**：既有 `_stage_result` 的说明写明"`save_*` 自带 `open`/`commit`
并只返回 `StagedRevision`，**提交序号在返回时已经前进**，事后补读会拿到**下一次**的序号"。

**为什么 `confirmation_id` 不能含提交序号**：确认是**追加**记录（`save_confirmation` 无
`expected_revision`），既有约定是"同一 `confirmation_id` 再登记一次**冲突而不是静默覆盖**"。
标识只由被确认的事实决定，才能保证"同一事实重复确认 = 冲突"、"依据修订变化 = 新记录"。

## 4 内联摘要 vs 对象引用清单（`AB-001` 第 8.18 节）

**根因（实测定位）**：A 的 `infrastructure/file_store/integrity.py`

- 第 27 行 `_DIGEST_RE` 匹配 `^sha256:[0-9a-f]{64}$`；
- 第 73—86 行 `_iter_digest_refs()` **递归收集任意位置**的这种形状字符串，
  **只看值、不看键名与记录类别**；
- 第 300 行对 `referenced - object_digests` 报 `unreachable object reference`。

**实测复现**：写入带 `content_digest` 的 `generated_content` 与带 `payload_hash` 的
`preparation_record` 后运行 `check_workspace()`：

```
完整检查 ok = False
  error: unreachable object reference: sha256:bbbb…（64 个 b）
  error: unreachable object reference: sha256:cccc…（64 个 c）
```

**内联摘要清单（8 个字段，不是对象引用）**：`content_digest`、`payload_hash`、
`error_detail_digest`、`projection_digest`、`basis_text_digest`、`published_digest`、
`digest`、`observed_resolved_input_digest`。

**真正的对象引用（必须可达）**：`content_ref`、`output_object_digest`、`replaced_object_ref`。

**B 侧保证**：B **不会**为上述任何内联摘要字段在 `objects/` 下写 blob；它们全是自包含字符串。
