## 1 六条缺陷与修法

### B-12 项目、正文、模型策略的归属未统一校验

**症状**（照抄检查文档）：默认 `LocalAPI` 接受 envelope-project 下保存 payload-project
的项目；保存的 `Delivery` 正文没有 `project_id`，随后 `load_delivery(foreign-project)`
可读取；真实模型编排在内存外部端口下接受 `project-ticket` 的策略为 `other-project`
准备请求。

**本轮实测到一条比原描述更具体的根因**（这一条解释了为什么"正文没有项目"会变成
"任意项目都能读"）：`usecase_registry` 的 `handle_save_delivery` 先
`delivery_from_payload(payload)` 得到 `Delivery`（**`Delivery` 领域对象不带项目字段**），
再调用 `save_delivery(delivery, project_id=命令项目)`——写入用的是**命令的项目**，
正文里调用方声明的项目被静默丢弃。于是"命令项目 A + 正文项目 B"会落成 A 的记录，
而记录正文里根本没有项目可供事后核对。

**修法（四处）**：

| 位置 | 改动 |
| --- | --- |
| `application/usecase_registry.py` | 新增 `_require_owned_by_command()`：正文自带 `project_id` 就必须与命令项目一致，否则 `B_INVALID_PARAMETER`。`save_delivery`、`save_task` 在构造领域对象**之前**调用它 |
| `application/project/serialization.py` | `delivery_to_payload()` 新增**必填**关键字参数 `project_id`，把项目写进正文（与 `case` / `acceptance_scope` / `rule_draft` 同一做法） |
| `application/project/persistence.py` | 新增 `_verify_payload_project()`：**缺失与不符都拒绝**；`_load_payload()` 与 `_stage_and_commit()` 共用它。过去只在 `stored_project is not None` 时比较 |
| `application/planning/model_orchestration.py` | `request_model_draft()` 在准入之前比对 `policy.project_id` 与 `project_id`，不一致即 `blocked`（**不调用供应方、不落出站记录**） |

**边界**：检查文档要求"B 校验正文/引用/策略归属，**A 同时守住持久命名空间**"。
本轮只做 B 侧；底层跨项目归属（**A-11**）不在本包职责内。

### B-13 交付方自填 `verified_in_scope` 即成为"已验证交付"

**症状**：默认 `save_delivery` 接受未登记 `task_id` 和调用方填写的
`verified_in_scope=[all-required]`，没有执行记录或证据，读回 `Delivery.is_verified` 为真。

**修法**：`save_delivery()` 对非空 `verified_in_scope` 抛错，并在消息里指向
`unverified_scope`（那本来就是声明字段）。入口把该 `ValueError` 翻成
`B_INVALID_PARAMETER`（新增 `try/except`），不再落到 `INTERNAL_ERROR`。

**为什么是"拒绝"而不是"改成派生"**：从执行事实派生已验证范围需要 C 的运行事实与 D 的
判定链，当前默认装配未接通。先把"自报即为真"这条通道关上；
**派生本身仍未实现**（见第 3 节未做到）。

### B-14 发布忽略调用方预期修订，旧编辑可继续发布

**症状**：真实默认 `HUMAN_UI` 接口依次发布 original / new edit / stale edit，
三个 `Command.expected_revision` 都是 `0`，全部 `published=true`，
`rule_version` 产生三份正文历史。

**根因**：`publish_rules()` / `publish_plan()` 自己调 `_current_revision()` 读当前修订，
再把它当作 `expected_revision` 交给 `tx.stage_record()`。等于**替调用方接受最新基线**，
底层的乐观锁只能保护"读取之后"那一小段窗口。

**修法**：

1. 两个发布函数新增 `expected_revision` 参数（默认 `None`，与"新建"同义）；
2. 新增 `publish._revision_to_stage()`：读当前修订、与调用方声明的修订比对
   （`None` 与 `0` 都表示新建，`0 == 当前 0` 通过），不符即 `ConcurrentEditError`
   （带 `aggregate_kind` / `record_id` / `expected_revision` / `current_revision`）；
   检查与 `tx.stage_record()` 在**同一次事务内**；
3. 入口新增 `_expected_revision_or_none()`：只认 `Command.expected_revision`，
   **不回退**到草稿/计划自己的修订号——那仍然是替调用方猜基线。

`ConcurrentEditError` 经既有 `_guard` 变成 `B_REVISION_CONFLICT`，调用方能拿到当前修订。

### B-15 运行修订允许替换掉必测验收关联，且未校验计划完整身份

**症状**：必测 Case 的验收关联从 `{AC-A,AC-B}` 改为 `{AC-A,AC-C}` 被 `accepted`；
同修订号但 `plan_id=unrelated-plan` 的计划也被接受。

**根因**：适用性检查写的是
`next_case.links.acceptance_item_ids < current.links.acceptance_item_ids`
（Python 集合的**真子集**运算符）。两个互不包含的集合比不出真子集关系，
所以"替换"既不小于也不大于，直接漏检。计划检查只比 `plan.revision` 与
`facts.plan_revision_no`，从不看 `plan_id`。

**修法**：

1. 改为**差集判定**：`current - next` 非空即 `APPLICABILITY_WEAKENED`，
   并在 detail 里列出被丢弃的具体 ID（验收项与关键链路各一组）。
   "只增加"仍然通过（差集为空）；
2. `RuntimeRevisionRequest` 新增 `base_plan_revision_id`（必填）与
   `base_plan_revision_digest`（可选）；与 `plan.plan_id`、事实的
   `plan_revision_id` / `plan_revision_digest` 逐项核对，不符即
   `PLAN_REVISION_MISMATCH`。

**摘要为什么是可选的**：不给就是没核对。不拿计划自己的内容**猜**一个摘要来比——
那样等于自己跟自己比，看着通过、其实什么也没验。真实调用方应当给出
（C 的事实里本来就有 `plan_revision.digest`）。

### B-16 目录移动沿用旧确认和内容摘要

**症状**：`confirmed=true`、`manifest_digest=sha256:old` 的 `C:/old` 绑定移动到
`C:/new` 后，修订增加到 2，但仍 `confirmed=true` 并继承原摘要。

**根因**：`move_binding()` 把 `binding.confirmed` 与 `binding.manifest_digest`
原样传给 `create_binding()`。

**修法**：新修订一律 `confirmed=False`；摘要**不继承**，新增可选参数
`manifest_digest` 由调用方在核对完新位置内容后显式传入。
`plain` 形态没给摘要时按既有领域口径返回 `missing_environment_carrier` 缺口
（**给缺口而不是给一个继承来的摘要**）。
`git` 形态本就不许带清单摘要，省略后行为不变。

### B-17 合法单模块无依赖项目被判为阻塞缺口

**症状**：一个有职责/输入输出的模块、匹配项目的无边依赖图和有效环境输入，
`detect_context_gaps()` 返回阻塞 `missing_dependency_registration`。

**根因**：`if graph.modules and not graph.dependencies` ——
"有模块但没有边"被直接读成"漏登记"，无法区分**已明确没有依赖**与**还没登记**。

**修法**：在图上把这件事变成**可落盘的事实**，而不是靠"有没有边"猜：

1. `domain/project/context.py` 的 `ModuleDependencyGraph` 新增
   `edges_declared: bool = False`（默认 `False` = 无法证明边已登记）；
2. `application/project/context.py` 的 `register_graph()` 产出
   `edges_declared=True`：调用方明确给出了边集合（哪怕是空集合），
   **"没有边"就是已声明的结论**；
3. `detect_context_gaps()` 只在 `graph.modules and not graph.edges_declared` 时报缺口；
4. `serialization.py` 的 payload 带 `edges_declared` 键并读回。
   **旧记录**缺该键时按 `True` 读回——沿用它们原来的语义，
   不顺手把历史记录变成阻塞项。

**本执行环境的 7 failed / 214 errors 已实测查明是执行环境限制，不是产品缺陷**，
**且同一提交在远端 CI 上 1204 项全部通过**：

- **214 errors 同一根因**：`_pytest/pathlib.py` 的
  `os.scandir('<TEMP>\dsh-jixPre\pytest-of-LENOVO')` 报 `PermissionError: [WinError 5]`，
  即本执行环境**禁止枚举 pytest 临时基目录**，所有 `tmp_path` 用例在**夹具阶段**失败。
  实测排除：目录**存在**；.NET `Directory.GetFileSystemEntries` 枚举**同样被拒**；
  工作区内既有的 `--basetemp` 目录（`.pytest-tmp`、`.basemp`）**同样被拒**。
- **7 failures** 全在被禁用的操作系统能力上：`test_a_pipe_host`（3，命名管道
  `PipeUnavailable: 连接客户端失败`）、`test_command_adapter`（3）与
  `test_execution_adapters`（1）（子进程/输出捕获 `couldn't create signal pipe, Win32 error 5`）。
- **判定依据**：① 涉及模块是 A 的 `interfaces/local/pipe.py` 与 C 的
  `infrastructure/adapters/execution/*`，与本轮 8 个 `application/`、`domain/` 产品文件
  **零重叠**；② 失败点在 `_pytest` 临时目录机制与管道/子进程创建上，
  **不进入本轮改动的任何函数**；③ **同一提交在远端 CI 干净环境上 1204 项全部通过**，
  说明上述失败只在本执行环境出现。

> 原计划的"改动前基线对拍"（`pytest` → `git stash push` → `pytest` → `git stash pop`）
> **已无必要**：CI 全绿比本机基线对拍更权威。

**证据来源口径**：本节数字取自 `py -3.13 -m uv run --frozen ...`
（与 CI 同一套命令）与远端 CI 的 JUnit 制品。执行环境在缓存目录 ACL 损坏时会报
`Failed to initialize cache`（`os error 5`）；改用新建的空缓存目录后命令正常，
**正式结果一律以 `uv run` 与远端 CI 为准**。

**仍需补齐（一项）**：上述 7+214 的**"改动前基线"尚未实测**。
本执行环境拒绝写 `.git`（`git stash` 报 `index.lock: Permission denied`、
`git worktree add` 报 `.git/worktrees: Permission denied`），无法自动切到基线代码。
补齐命令见第 5 节；补前只声称"失败点与本轮改动无关"，**不声称"基线数字完全相同"**。
