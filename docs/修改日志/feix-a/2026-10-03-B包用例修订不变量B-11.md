## 1 缺陷

**检查文档原文**：合法 `Case.revision=9` 被保存为仓储修订 1、2；准确读取 `@1`/`@2`
均返回 `Case@9`，正文与记录修订不一致（反例 `B-REVISION-01-payload-storage`）。

**本轮用真实文件存储复现**，结果与原文一致：

```
save_case(case.revision=9, expected_revision=None)
  → staged record revision = 1
  → 记录 revision=1  payload revision=9
  → load @1 → 正文 revision=9
  → load @2 / @9 → ValueError: unknown revision
```

即：**记录修订与正文修订分叉**。按记录修订 `@1` 读回得到正文 `@9`；
按正文修订 `@9` 又读不到东西。

## 2 根因

`application/planning/persistence.py` 的两半各自"说自己的话"：

- `_stage_and_commit()` 把 `expected_revision` 原样交给底座，由底座分配**仓储修订**
  （`None`/`0` = 新建 → 分配 1；否则分配 `expected_revision + 1`）；
- `case_to_payload()` / `acceptance_scope_to_payload()` 把对象自己的 `revision`
  写进 payload。

两者从不比对，于是"新建一条 `revision=9` 的用例"落成"记录 `@1`、正文 `@9`"。

## 3 修法

**不变量**：`正文修订 == 这次会分配的仓储修订 == (expected_revision or 0) + 1`。

| 项 | 做法 |
| --- | --- |
| 校验位置 | `_stage_and_commit()` 新增 `revision_carrying_key`；给出时在**事务内部**、`stage_record` **之前**调用 `_require_revision_matches_assignment()`。放在事务内是为了让底座的**并发校验先生效**，本核对只处理"修订号本身的错配"，避免用修订号的错配去掩盖并发冲突 |
| 拒绝方式 | 抛 `ConcurrentEditError`（携带 `expected_revision` 与**将要分配的修订**），入口经既有 `_guard` 翻成 **`B_REVISION_CONFLICT`** |
| 适用对象 | `save_case()`、`save_acceptance_scope()`（检查文档点名的 "Case/Scope 同类路径"） |
| 不适用 | `save_rule_draft()`、`publish_plan` 的 `plan` 记录——理由见第 5 节 |

**为什么选择"拒绝"而不是"按正文修订分配仓储修订"**：后者会让"记录修订"不再是
"调用方声明的业务修订"，也会让并发校验（`expected_revision`）失去可比对的基准；
检查文档的完成条件写的正是"拒绝旧修订/跳号错配"。

## 5 未纳入 `rule_draft` 的理由（如实登记）

`save_rule_draft()` 有**同样的现象**（实测：`RuleDraft.revision=9` → 记录 `@1`、正文 `@9`），
但本轮**故意不改**：

- `rule_draft` 的修订号在**导入**路径上来自外部规则包：
  `portable.import_rule_payloads()` 按文件里的 `revision` 原样还原
  （`portable.py` 第 158—163 行）。强制"正文修订 = 仓储修订"会与
  "导入保真外部规则编号"冲突；
- 检查文档 B-11 的完成条件把规则路径列为"**同类路径验证**"，
  而"规则修订与仓储修订应否一致"属**需要先定口径**的设计问题
  （涉及导入语义与 `publish_rules` 里 `rule_version` 的记录语义），
  按第③级"改契约字段/语义先确认"不在本轮擅自决定。

**待定问题（供组内裁定）**：`rule_draft` 的仓储修订与正文修订是否需要一致？
若需要，需先决定"外部规则修订号如何映射到本地编排修订"。

`publish_plan` 的 `plan` 记录同理：其 payload 修订来自计划对象、仓储修订是独立序号，
与 `rule_version` 同类；本文不改变其发布语义。
