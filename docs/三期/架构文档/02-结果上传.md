# 三期架构02：结果上传

版本：2.6  
更新日期：2026年9月21日  
状态：修订基线，待实现与实测；文档不代表产品已通过验收。

仅上传侧ResultSubmitterPort，不提供接收端实现。业务合同在平台确定后映射为单次或prepare/upload/query/finalize等流程；分块大小与网络字段随平台能力定，不提前约束平台内部架构。

## 1 本地提交与候选

本地事实成功提交后，DeliveryCandidate按已提交序号和记录修订引用产生；登记候选失败可由持久游标补建，不能回滚本地事实。未登录/平台失联保留候选，明确尚未核实账号或目标；用户关联并核实后生成冻结Submission。候选仅订阅允许运行/步骤/证据/问题/报告的业务提交，不订阅候选、提交、回执或游标自身的写入，避免循环。以来源实例、项目、记录类型/ID/修订为候选去重键；候选登记与游标推进在同一工作单元提交，队列满时候选仍登记或游标停留，不能先推进再丢材料。

三种身份独立：运行键=(来源实例,本地项目,run_id)，目标映射另存；提交键=submission_id，固定账号/目标/内容；请求键=request_id，关联一次传输尝试。同一运行可有多内容修订，不与“同提交异内容”混淆。

## 2 投影与摘要

先按类型白名单投影运行、证据、报告和本地问题；禁止源码正文、GitHub Issue/PR。日志/截图中可能包含路径或源码，不能仅靠类型认定安全：无法生成满足策略的投影则排除并明确上传缺口，不宣称完整。

入队时冻结投影字节，记录source_digest（本地原对象）与upload_digest（实际上传字节）、投影策略版本和大小。路径/文件名开关作用所有字段与正文，默认去除；本地绝对路径不作为隐含来源字段发送。显式开启仅加入合同允许信息，不放开源码正文。

清单采用RFC8785规范化JSON，顶层schema_version、report_hash（有报告时）、对象数组；对象含object_id、record_type、content_revision、upload_digest、size、projection_policy_version及策略允许元数据。数组按(type,id,revision,digest)确定排序，拒绝重复对象键；缺省/空值、整数类型和UTF-8编码按Schema固定。SHA-256取规范字节，小写hex并加sha256:前缀。禁止换行拼接自制编码。

report_hash单独对冻结的可上传报告投影计算，包含报告ID/修订、来源修订、判定策略、结论、证据上传摘要清单；独立本地复核作为明确关联记录，不暗中写入原正文。任何投影字节或材料/投影策略变化产生新提交，不在发送阶段二次改写字节。

合同测试向量覆盖顺序变化、中文/换行、空值、省略字段、重复键、数值类型、原始与脱敏摘要不同。双方对拍成功后才声明可互通。[RFC8785规范](https://www.rfc-editor.org/rfc/rfc8785.html)

## 3 状态与重试

PENDING→SENDING；请求超时/失联→UNKNOWN；UNKNOWN先按原号查，存在缺口→INCOMPLETE补缺，完整且匹配→ACKNOWLEDGED；认证/参与/冲突/重试耗尽→PAUSED。只有用户明确选择“放弃提交”并确认，才追加AbandonDecision并显示ABANDONED；暂停本份、退出/切账号、关闭自动同步只撤销对应许可并暂停后续网络动作，不生成放弃决定。材料均永久保留。AbandonDecision是发送控制决定，接收状态独立记录：放弃后迟到的完整有效回执仍登记为已送达，并保留放弃决定，不恢复自动发送；迟到失败不覆盖放弃决定。暂停或许可撤销后，在原因已解决并重新确认许可时可继续原提交，沿用最近接收事实；UNKNOWN先查询、INCOMPLETE只补缺、已ACKNOWLEDGED不再发送。ABANDONED再次发送须显式新建关联提交，先查询原号并展示已接收情况，不能用重新登录自动复活。

未知查询遵守一期connectivity同一有界失败周期，不存在无限查询豁免；重启不重置次数。重登原账号不自动重置失败周期；用户明确恢复且原暂停原因已解决、发送许可有效时可开新周期；参数/目标变化不得沿用原提交。原提交仍允许发送且平台明确不存在原提交时，才能按同号同内容重新发送，不重新执行业务。

完整回执校验账号/目标、submission_id、manifest_hash、接收修订、对象集合/数量、每项upload_digest和完整性。对象缺失为INCOMPLETE；摘要错误/多余冲突对象/修订归属错误为PAUSED，不标送达。回执摘要只能证明双方声明一致，不宣称防止恶意平台篡改。

ACKNOWLEDGED保存不可变回执历史；后续对账异常新增冲突状态记录，不删除原收到的回执。相同原结果修订与投影在平台可关联原记录，不能产生重复业务执行。

## 4 容量与不干扰本地

待发送逻辑占用与全部历史物理占用分开。逻辑队列拒绝新提交时本地事实/候选不丢，显示待处理；显式放弃停止自动发送、释放逻辑待发送量但不删永久材料。无足够物理空间时按本地存储规则拒绝需新增字节的操作，不能承诺无限容量。

发送在事务外，不占执行通道，不因网络失败锁死本地写入。原始对象、冻结投影、回执永久保存；只有上传形成的冗余临时副本在确认安全后回收，不把唯一上传投影叫临时副本删除。

验收P3-AC03—06：断网/重启/回执丢失、同运行新修订、重绑新目标、真实脱敏摘要、UNKNOWN耗尽、队列满/放弃、本地保存成功但候选尚未登记即崩溃。

## 5 策略门禁与冻结预览

SendPolicy由核心保存，按账号/目标/项目和材料类别修订，manual默认；新增save_send_policy、preview_submission、confirm_submission动作，发送循环使用同一门禁。候选持久化独立于模式；on_run_end等待运行终止修订，per_step按步骤提交，避免状态写入自触发。关闭自动同步撤销当时未完成许可并停止后续自动网络请求；之后可显式重授单份送达许可或手动查询一次，见第9节。

预览读Submission已经冻结的安全投影，不读取动态原对象替换字节；用户确认绑定manifest_hash/策略修订。首次、目标/类别变化或关键投影缺口要求显式确认，后者PAUSED带projection_review_required原因；恢复发送核对确认记录，不能被普通重试绕过。已发送提交内容不可改。

EvidenceDeliveryCoverage与清单一起冻结，记录预期证据ID、包含/排除/缺失及原因；对象全部接收只驱动接收状态，不能抹掉覆盖缺口。平台合同不支持完整业务标记时不自行制造。脱敏投影预览、发送和回执核对使用相同摘要；本地证据包不跳过上传白名单。

## 6 记录、请求与回执字段

| 记录 | 必需内容 |
| --- | --- |
| DeliveryCandidate | 来源实例/本地项目/类型/ID/修订、提交序号、目标关联状态和候选去重键 |
| Submission | submission_id、精确账号、来源/目标、binding_revision、Run/Step/Attempt、源码身份/环境、内容与策略修订、冻结清单/投影引用 |
| 投影对象 | object_id/type/revision、source_digest本地追溯、upload_digest、实际大小、策略、包含或排除原因 |
| 传输尝试 | request_id、原提交、动作、会话/绑定上下文、最后确认状态、失败周期/次数、结果或错误 |
| Receipt | 原提交/账号/项目、manifest_hash、接收记录及内容修订、每个对象ID/upload_digest、完整性、平台给出的接收信息 |
| AbandonDecision/覆盖 | 操作者、提交、明确放弃确认及原因；预期证据、实际包含、排除/缺失和原因独立保存 |

平台给出的接收时间只用于接收信息，不替代本地提交序号或证明测试执行顺序。运行身份与提交身份分开，同一Run新内容修订可独立提交；同submission_id不能改账号、目标或字节。

## 7 上传端口行为映射

下表是插件所需能力，不要求平台必须提供同名四个接口，更不要求插件实现接收端。

| 所需能力 | 插件发送/核对 | 失败处理 |
| --- | --- | --- |
| 准备/协商 | 冻结清单、账号/目标、能力及已存在对象 | 保存原提交，不能把准备成功当完整回执 |
| 对象传输 | 指定对象及实际upload_digest；支持分块时按确认偏移与摘要续传 | 失联结果未知先查，不能假定未写入 |
| 原号查询 | 原账号/项目下的submission_id | 得缺口则补交；仍未知受统一有界周期控制 |
| 最终核对 | 清单、接收内容修订、完整标志、对象集合与逐项摘要 | 缺项INCOMPLETE；多余冲突/错摘要/错归属PAUSED |

若平台采用单次提交，也必须表达原号查询、幂等与完整回执。若支持分块，分块大小/偏移语义由双方合同确定；重复同块不能产生新的业务结果。网络动作均在事务外，本地先保存发送意图，响应再经工作单元追加。

## 8 中断与冲突决策

| 情形 | 处理 |
| --- | --- |
| 本地事实提交后、候选写入前崩溃 | 从已提交游标重扫允许类型；候选去重与游标同事务，不漏结果 |
| 预览后原记录变化 | 旧预览/旧提交字节不变；新来源修订另建候选与提交 |
| 发送已成功但本地未收回执 | 原号查询，核对完整回执后登记；不再次执行业务 |
| 平台明确无原提交 | 仅在原提交仍允许发送时同号同字节重发；放弃/策略撤销不能自动恢复 |
| 同号不同内容或目标 | CONTENT_CONFLICT/PAUSED；保留原记录，新提交关联旧提交 |
| 同运行新报告修订 | 新submission_id，不误判为同Run冲突，不覆盖旧报告回执 |
| 退出/换账号后回执迟到 | 校验原账号/绑定/请求，只追加原提交接收事实 |
| 放弃后完整回执迟到 | 记录真实已送达，同时保留AbandonDecision，不恢复发送循环 |
| 已送达后对账冲突 | 新增冲突记录，旧收到的回执不可删除；本地测试结论不变 |

发送循环仅处理策略允许的提交；不监听自身状态写入重新造候选。队列压力只影响待发送逻辑量，物理空间不足按本地存储守卫处理；不能靠放弃删除唯一冻结材料。合同对拍用明确样例验证规范JSON、对象排序、空值/省略、中文换行及脱敏前后不同摘要，真实平台未通过前保持未验证状态。

## 9 送达许可与恢复守卫

SubmissionDeliveryGrant字段为grant_id/revision、submission_id、manifest_hash、账号/目标、binding_revision、发送控制/材料策略/投影修订、allowed_operations、confirmation_ref或approved_policy_ref、active/revoked/completed、失败周期引用和撤销原因。它作为delivery中的提交控制记录，沿用工作单元保存；不另建调度器。confirm_submission在核心校验人工确认来源及挑战后创建许可，自动模式只按已批准策略创建匹配许可；存在撤销/暂停记录的原提交不能由扫描循环自动再授许可，必须显式人工确认，不能以重登或重复候选扫描绕过停止决定。

发送循环每次取许可→核对当前会话/参与/策略和冻结摘要→在短事务记录传输意图→事务外请求→追加响应。原号查询和补交也经过该门禁；单次手动查询的许可不含补交。错误恢复先匹配reason，认证重登不自动解除冲突或投影确认门禁。许可失效不改冻结字节，重新人工确认可对未放弃的原提交建立新许可；材料/投影策略或内容变化仍需新提交；仅mode及启停控制修订不改冻结材料，可按当前门禁重授原提交许可。

关闭同步、暂停、退出按功能第7节撤销相关许可；与新发送意图串行裁决，已在途可能完成，回执仍登记。重启读取原许可和已消耗失败周期，不重新授权或清零。ACKNOWLEDGED结束该许可；ABANDONED不因重登恢复。按钮含义、单份恢复范围及P3-AC03/04/07预期由需求维护。

## 10 控制动作与接收事实对应（2.6）

接收事实、控制状态、许可状态独立保存；PAUSED/ABANDONED是控制呈现，不覆盖最后接收事实。控制状态为ready/paused/abandoned，沿用提交控制记录，不另建状态服务。

| 用户动作/事件 | 控制与许可 | 原提交后续 |
| --- | --- | --- |
| 暂停本份、退出/切账号、关闭同步 | 对应提交paused、许可revoked；保存原因，不写AbandonDecision | 人工重授且原因守卫满足后ready；按原接收事实查询/补缺 |
| 明确放弃提交并确认 | abandoned、许可revoked，保存AbandonDecision | 原提交不恢复发送；再次发送须新关联提交并先查原号 |
| 暂停/放弃后收到完整有效回执 | 保存ACKNOWLEDGED并结束传输；保留控制决定 | 展示已送达及原暂停/放弃决定，不因回执重开自动发送 |
| 只查询一次 | 仅授只读查询，不改变既有暂停/放弃决定 | 发现缺项也不补交；用户另行确认送达才允许后续写请求 |

恢复先读接收事实再决定动作，不能把UNKNOWN或INCOMPLETE重置为PENDING后盲发。已送达提交只允许按合同查询，不因重授按钮重复发送。界面“暂停”“关闭同步”“放弃提交”用不同动作名和确认文案；放弃确认不能由通用停止动作隐式触发。与功能第7节单份许可规则一起验收。
