# 一期真实 Trae 入口验证：步骤与证据模板（2026-10-11）

> 本目录是**真实环境验收**的落点，不是组件级测试记录。组件级证据（本机的真实核心进程、真实子进程、面板渲染）**不能**填进这里冒充真实环境验收——见 `AGENTS.md` 第 5.5 条与 [项目现状](../../现状.md)。

## 1. 这一步要证明什么

一期要求「Windows 11 x64 + Python 3.13 + **Trae** 上的本地测试闭环」。到 2026-10-11，代码侧已接通：

| 能力 | 现状 | 组件级证据 |
| --- | --- | --- |
| 扩展经既有 CLI／命名管道连同一核心 | 已实现 | 本机 Node 侧对真实核心派发 `doctor`/`storage_usage` 成功 |
| `ensure-core` 发现或启动核心 | 已实现 | 本机真实进程验证（含不存在路径被拒且不建目录） |
| 面板呈现 `supported_actions` 与回执 | 已实现 | Playwright 2 条（含注入真实回执的正向路径） |
| 只读白名单拦截写动作 | 已实现 | 有守卫测试，且注入写动作时必失败 |

**缺的只有一件事：这些在真实 Trae 里是否成立。** 本目录就是为它准备的。

## 2. 前置条件（逐项记录版本，缺一不可）

| 项 | 记录内容 |
| --- | --- |
| 操作系统 | Windows 版本与构建号（`winver`） |
| Trae | 版本号与发行版（国内版／国际版，**两者扩展 API 可能不同**） |

## 3. 步骤

### 3.1 构建扩展与面板

```powershell
npm --prefix src/aitest/resources/panel run build
npm --prefix integrations/trae run build
npm --prefix integrations/trae run package   # 产出 dist/aitest-trae.vsix
```

记录 `dist/aitest-trae.vsix` 的 SHA256 与构建时间。**注意**：`dist/` 不受版本控制，必须现场构建。

### 3.2 安装并配置

1. 在 Trae 里安装该 VSIX（命令面板 → 从 VSIX 安装）。
2. 设置两项配置（**这是最容易配错的地方**）：
   - `aitest.pythonPath`：能 `import aitest` 的解释器（本仓库用 `.venv/Scripts/python.exe`）。
   - `aitest.workspaceRoot`：**用户数据工作空间**根目录，**不是**被打开的源码目录。留空会被如实拒绝。
3. 确认工作区已信任（未信任时扩展会拒绝打开面板）。

### 3.3 打开面板并连接核心

1. 命令面板执行 `AI Test: 打开一期面板（核心只读入口）`。
2. 点「**连接核心**」→ 期望状态行出现核心 `READY` 与身份（`workspace_id`/`instance_id`），且**不**创建缺失的工作空间目录。
3. 点「**刷新核心状态**」→ 期望「核心能力（真实回执）」区列出 `supported_actions`，实际动作集合与[现行动作库存](../../现状.md#3-默认动作库存与缺依赖)核对（条件依赖变化如实登记，不用历史数量倒推）。

### 3.4 只读派发与安全边界

1. 点「空间诊断」→ 期望「最近回执」区出现**原样 JSON**（字段名与核心回执一致，不应被面板改写）。
2. 点「事件续读」→ 同上。
3. **反向验证**：确认写动作在面板里**不可发起**（业务动作按钮为 disabled），且扩展侧白名单会拒绝写动作（可用开发者工具查看扩展日志中是否出现 `ENTRY_ACTION_NOT_ALLOWED`）。

### 3.5 故障与恢复（一期明确要求）

逐项做并记录实际现象：

| 场景 | 期望 |
| --- | --- |
| 关掉核心进程后再点「刷新核心状态」 | 如实报不可用，**不**伪装成功 |
| 再点「连接核心」 | 重新发现或启动核心并回报身份 |
| 填一个不存在的工作空间路径后重开面板 | 如实报 `WORKSPACE_NOT_FOUND`，且**目录未被创建** |
| 未信任工作区打开面板 | 拒绝并提示先信任工作区 |

## 4. 证据要求（放进本目录）

- **日志**：`<step>-<场景>.log`（扩展宿主日志、核心 stderr、或操作记录）。
- **截图**：面板各状态的截图（连接前／后、回执区、写动作禁用、故障态）。命名 `<step>-<场景>.png`。
- **版本**：`versions.json`，内容为第 2 节各项的**实际取值**与 VSIX 的 SHA256。
- **一句话结论**：`RESULT.md`，逐条写「预期 / 实际 / 是否通过 / 证据文件」。

**不要**把组件级测试输出（pytest、Playwright、本机 Node 探针）放进这里当真实环境证据。

## 5. 通过后如何登记

只有对应 AC 的**完整需求场景**实际通过且全部满足，才可以改 `tests/acceptance/p1/status.json`；本目录只读入口验证只是部分前置，不能凭这些步骤直接把 AC26/27 或其他完整 AC 登记通过：

1. `result = "verified"`；
2. `evidence.path` 指向**本目录内的具体文件**（非空）；`evidence.method` 另记实测方法；
3. 该行要求的**真实环境已验证**为真（即上表场景在真实 Trae 内实测通过）。

且：登记里的 `scenario`/`expected`/`related_frs` **逐字取自需求文档第 5 节**，只在需求文档改动后同步——不得为了迁就实测结果改写它们。

## 6. 已知限制（如实写明，不得含糊）

- 扩展是**候选实现**：Trae 各发行版的扩展 API 兼容性未验证。
- 本次接通的是**只读**入口；面板的**业务动作区未接线**（写动作必须经受控用户入口并携带授权，界面点击不等于用户确认）。
- 来源核验目前覆盖 L1 的「语法」与「加载来源」，**不覆盖**「适用构建」与 `MINIMAL_START`。
- 真实供应商（模型／HTTP）与**物理掉电**恢复不在本目录范围，各有独立验收项。
