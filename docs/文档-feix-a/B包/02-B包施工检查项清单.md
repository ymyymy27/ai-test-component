   产品路径只接受已解析的事实对象。理由：安装包里没有 `docs/`；`CD-001` 第 7 节禁止
   "直接读取未发布的 spool 文件或以文件名推断证据"，同一条理由适用于夹具。
2. **领域层镜像 C 的状态枚举**（`StepRuntimeState` / `AttemptRuntimeState` / `RunRuntimeState`）：
   `domain/` 不得 import `contracts/`，而门禁必须点名 `running`、`pending_verification` 等取值。
   取值集合由 `tests/contracts/test_runtime_vocabulary.py` 锁定（与 `CaseLayer` 的双层声明同一做法）。
   备选是"应用层把 C 的枚举压成三态再传入"，代价是"哪些取值算正在执行"这条规则离开领域层。

### 28.3 规则清单（16 条拒绝码）

| 拒绝码 | 触发条件（全部来自事实或内容，不解析调用者文案） |
| --- | --- |
| `plan_not_published` | 计划不是 `published` |
| `plan_revision_mismatch` | 计划修订 ≠ C 事实的计划修订，或请求声明的基准修订对不上 |
| `stale_snapshot` | 决策读到的 `snapshot_cursor` ≠ 已提交事实的游标（不许在混合快照上决策） |
| `run_not_active` | 运行态为 `not_started`／`cancel_requested`／`cancelling`／三个终态 |
| `driver_expansion` | 驱动反向扩大（`stepwise → planned`）：拒绝并置 `new_run_required` |
| `frozen_case_not_provided` | 改动的用例不在冻结计划里 |
| `frozen_case_revision_mismatch` | 未提供冻结修订的用例对象（或修订号不符） |
| `case_revision_not_advanced` | 新用例修订没有超过冻结修订 |
| `mandatory_case_removal` | 请求把必测项移出必测 |
| `applicability_weakened` | 必测用例丢验收项或关键链路关联（变更适用性规避门禁） |
| `assertion_weakened` | 依据改回 `missing`，或三态降级 |
| `independent_verification_removed` | 原来有独立核验方式，新修订删掉 |
| `step_is_executing` | 该用例有步骤正在执行（步骤 `running`，或当前尝试在 `intent_recorded`…`collecting`） |
| `step_not_in_case` | 点名的步骤不属于该用例 |
| `step_facts_already_recorded` | 点名要改的步骤已产生事实（完成／取消／执行错误／待核实） |
| `no_unexecuted_step` | 该用例没有尚未执行的步骤——运行中修订不能回改历史 |

派生规则（不是拒绝，而是交接）：

- **只影响未执行步骤**：`affected_step_ids` 取 `NOT_STARTED`，`preserved_step_ids` 取
  `FACTS_RECORDED`；`invalidated` 的步骤按 C 的判定归入"尚未执行"（它要重跑，不是历史事实）。
- **依据变化**：文本变了但同级不降级 → 不算弱化，按依据变化处理；若该用例已有产生事实的步骤，
  则置 `pause_required`、列出 `invalidated_basis_step_ids`（交 C 失效，含它自己的传递失效）
  与 `rejudge_case_ids`（交 D 重新判定）。若一步都还没跑，不产生失效与重判清单。
- **确认态一律派生**：请求里写 `confirmed` 不算数，只有绑定了**新**依据修订与文本摘要的
  `ConfirmationRecord` 才算；否则进 `confirmation_required_case_ids`。
- **整体拒绝**：任一拒绝码出现即整次修订不产生，不留"一半生效"的序列。

### 28.4 夹具使用与**覆盖缺口**

用的是 C 的公共副本 `docs/接口对接/进行中/CD-001-ExecutionFacts/fixtures/*.json`

（`tests/contracts/fixtures/execution_facts/` 的 4 份同样如此）。本轮因此从 `failure.json`

"派生结果不冒充交付夹具"。**这不是产品缺陷，是夹具覆盖缺口**：建议 C 交付一份
`running.json`（运行中、含一个 `running` 步骤与一个未开始步骤）。

### 35.2 为什么用规范 JSON 而不是 Markdown

架构文档把"规则 Markdown 导入导出"记为待实现能力，但**没有定义 Markdown 方言**。
在方言未定的前提下做 Markdown 导出会引入两个问题：

1. **无法逐字节往返**：`unknown_extension_fields`（来源里未识别的执行字段）与多行文本
   在 Markdown 里没有约定的转义规则，导出再导入会丢信息；
2. **等于另立一套格式合同**：格式一旦被外部文件引用就变成事实契约，而它没走合同流程。

因此导出的是**按生成 Schema 的规范 JSON**（键排序、紧凑分隔符、`ensure_ascii`）：
可逐字节往返、可核对摘要、未知字段原样保留。**Markdown 方言一旦定下来**，
可以在 `portable.py` 的导出函数旁再加一个渲染器，规范 JSON 仍是往返与校验的基准。

模板的导出形态与已安装资源 `<template_id>/<version>.json` **同一形状**——
测试里逐字节比对了六个内置模板，因此导出结果可以直接落回资源目录。

### 35.3 导入的两条硬约束

1. **导入只得到草稿**：导入产出的永远是 `confirmed=False` + `enablement=DISABLED`；
   来源里写 `confirmed` / `enablement` 也会被**忽略**（它们不在可携带字段集合里）。
   出口测试里有一条可执行证据：**导入的草稿直接发布会被门禁拒绝**。
2. **未知字段不混进步骤**：`unknown_extension_fields` 与 `steps` 分开存放，
   往返后仍不重叠——"未识别字段被当成可执行步骤"这条路径不被打开。

### 36.2 逐条改法与依据

**B-12（项目归属统一校验）**

1. **写入侧统一拒绝**：`usecase_registry` 新增 `_require_owned_by_command()`，
   `save_delivery`、`save_task` 在构造领域对象**之前**比对正文 `project_id` 与命令项目，
   不一致即 `B_INVALID_PARAMETER`。过去只有依赖图、环境个别动作比过，其余动作直接
   用命令项目覆盖正文项目——调用方以为存的是 B 的记录，实际落成了 A 的。
2. **`Delivery` 正文带项目**：`delivery_to_payload()` 新增必填关键字参数 `project_id`
   （与 `case` / `acceptance_scope` / `rule_draft` 的既有做法一致）。
3. **读侧缺失即拒绝**：`persistence._verify_payload_project()` 对**缺失与不符都拒绝**，
   不再把"正文没有项目"读成"任何项目都能读"；写入前也走同一函数。
   依据是检查文档"旧记录归属未知应显式阻塞或迁移"。
4. **模型策略归属**：`request_model_draft()` 在准入之前比对 `policy.project_id` 与
   `project_id`，不一致直接 `blocked`，**不调用供应方、不落出站记录**。

**B-13（拒绝自报验证）**

`save_delivery()` 对非空 `verified_in_scope` 抛错并指明改用 `unverified_scope`
（自述字段），入口把它翻成 `B_INVALID_PARAMETER`。验证范围只能由后续执行/核验事实
投影产生——`Delivery.is_verified` 不再能由提测者一句话置真。

**B-14（发布核对调用方预期修订）**

1. `RuntimeRevisionRequest.base_plan_revision_id` / `base_plan_revision_digest` 补齐后，
   `publish_rules()` 与 `publish_plan()` 新增 `expected_revision` 参数；
2. 新增 `_revision_to_stage()`：在**同一次事务内**把"调用方所见修订"与当前修订对上，
   不符即 `ConcurrentEditError`（携带当前修订），入口翻成 `B_REVISION_CONFLICT`；
3. 入口**不回退**到草稿/计划自己的修订号——那仍然是替调用方猜基线，正是本项要消除的行为。
   `_expected_revision_or_none()` 只认命令给的 `expected_revision`（`0` = 新建）。

**B-15（必测关联只增不减 + 冻结计划完整身份）**

1. 适用性检查从 `next < current`（真子集）改为**差集判定**：
   `current.acceptance_item_ids - next...` 或关键链路出现被丢弃项即
   `APPLICABILITY_WEAKENED`。这样 `{AC-A,AC-B}` → `{AC-A,AC-C}` 的**替换**会被抓住，
   而"只增加"仍然通过。
2. `RuntimeRevisionRequest` 新增 `base_plan_revision_id`（必填）与
   `base_plan_revision_digest`（可选），与 `plan.plan_id`、C 事实的
   `plan_revision_id` / `plan_revision_digest` 逐项核对，不符即 `PLAN_REVISION_MISMATCH`。
   摘要**只在调用方给出时**核对：不给就是没核对，不拿计划内容猜一个来自比。

**B-16（移动不继承旧确认与旧摘要）**

`move_binding()` 新修订一律 `confirmed=False`，且**不继承** `manifest_digest`；
新增可选参数 `manifest_digest`，调用方核对完新位置的内容后显式传入。
`plain` 形态没给摘要时按既有口径返回 `missing_environment_carrier` 缺口
（**给缺口而不是给一个继承来的摘要**）。

**B-17（区分"已明确无依赖"与"未登记"）**

1. `domain/project/context.py` 的 `ModuleDependencyGraph` 新增 `edges_declared: bool`
   （默认 `False` = 无法证明边已登记）；
2. `register_graph()` 产出的图一律 `edges_declared=True`：调用方明确给出了边集合
   （哪怕是空的），**"没有边"就是已声明的结论**；
3. `detect_context_gaps()` 只在 `graph.modules and not graph.edges_declared` 时报
   `missing_dependency_registration`；
4. 该事实随 payload 落盘（`edges_declared` 键）并读回。**旧记录**没有这个键时按 `True`
   读回——沿用它们原来的语义，不顺手把历史记录变成阻塞项。
