## 3 数据模型与不变量

### 3.1 `InputRevisions`（输入修订载体）

架构文档第 11 节原文：**"提交时校验项目、绑定、计划、规则、模板、环境修订及准备请求是否仍有效。"**
需求 P1-FR07：**"准备运行生成持久 intent_id，绑定项目、源码、环境、计划、规则、模板和动作。"**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `project_revision` | `int` | 项目修订 |
| `binding_revision` | `int` | 绑定修订 |
| `snapshot_revision` | `int` | 源码快照修订 |
| `environment_revision` | `int` | 环境修订 |
| `plan_revision` | `int` | 计划修订 |
| `rules_revision` | `int` | 规则修订 |
| `template_revision` | `int` | 模板修订 |
| `scope_revision` | `int` | 验收范围修订 |

**不变量**：每一项 `>= 1`。分册说"校验……是否仍有效"，`0` 不是合法修订，用 `0` 表示"无"会
与"修订从 1 起"的既有约定冲突。

**为什么用一个值对象承载，而不是八个位置参数**：`input_revisions` 要参与相等与摘要比较，
散成八个参数会让"哪一项变了"无法在类型层面表达，`changed_inputs()` 也无从实现。

### 3.2 `PreparationRequest`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `project_id` | `str` | 业务身份之一 |
| `client_id` | `str` | 客户端持久身份 |
| `prepare_request_id` | `str` | 一次明确的准备请求 |
| `payload_hash` | `str` | **业务输入摘要**，见 3.4 |
| `input_revisions` | `InputRevisions` | 本次解析到的各来源修订 |

**不变量**：前四项非空；`payload_hash` 建议带 `sha256:` 前缀（与仓库既有摘要写法一致）。

**三个身份键的次序固定为 `(project_id, client_id, prepare_request_id)`**（架构文档第 11 节原文）。

### 3.3 `PreparationRecord`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `request` | `PreparationRequest` | 已登记的准备请求 |
| `intent_id` | `str` | **与准备记录同一次提交**的业务意图身份 |
| `created_at_commit` | `str` | 登记时的提交序号；业务顺序据此判断 |
| `cancelled` | `bool` | 客户端取消只记录取消，**不自动创建新意图** |

**不变量**

1. `intent_id`、`created_at_commit` 非空。
2. **`intent_id` 不能等于任何 `request_id`**：这是"不以新入口的 `request_id` 替代业务身份"的落点。
   类型层面两者都是 `str`，因此由**规则**保证——`intent_id` 由应用生成，不接受调用方传入的传输号。
   测试用"`intent_id` 不得等于 `prepare_request_id`"断言这一点。
3. `cancelled=True` 的记录**保留**，仍可被查询命中（重传返回取消事实，不静默新建意图）。

### 3.4 `payload_hash()`（业务输入摘要）

架构文档第 8 节：**"`prepare_run` 解析已发布计划/环境/所选源码，保存 `intent` 与 `payload_hash`"**；
第 11 节：**"输入摘要不同返回冲突"**。

```python
def payload_hash(payload: Mapping[str, object]) -> str:
    """对业务输入计算规范摘要；键排序、紧凑分隔符，与调用方字典次序无关。"""
```

**规则**

1. **只对业务输入计算**：不得把 `request_id`、传输时间、重试次数、接收时间一类**传输层参数**纳入，
   否则"同号重传"会被判成"输入不同"，与"重传不变"直接矛盾。
2. **与字典次序无关**：内部按键排序后序列化，同一组输入无论构造顺序如何都得到同一摘要。
3. **不参与业务身份**：`payload_hash` 的取值不构成业务主键（主键是三个身份键）。

**这是本部分最容易写错的地方**，测试对第 1、2 条各有一条反例。

### 3.5 `decide_preparation()`（四态判定）

```python
def decide_preparation(
    request: PreparationRequest,
    existing: PreparationRecord | None,
) -> PreparationLookup: ...
```

| # | 条件 | 结果 | 依据 |
| --- | --- | --- | --- |
| 1 | 无记录 | `NEW` | 首次准备 |
| 2 | 有记录，`payload_hash` 不同 | `CONFLICTED` | 架构文档第 11 节：「**输入摘要不同返回冲突**」 |
| 3 | 有记录，摘要相同，`input_revisions` 不同 | `NEEDS_REPREPARE` | 架构文档第 11 节：「**同请求期间源码已变则返回原意图及"依据需重新准备"，不能把新字节塞进旧意图**」 |
| 4 | 有记录，摘要与修订都相同 | `REUSED` | 「同请求同输入**幂等**返回」 |

**判定次序是硬性的**：第 2 条先于第 3 条。因为"输入摘要不同"是**冲突**，而
"同一批输入但来源修订已变"才是"需重新准备"；把次序颠倒会把冲突误报成可重试。

`PreparationLookup` 还带 `intent_id`（仅 `REUSED` 时有值）与 `changed_inputs`（仅
`NEEDS_REPREPARE` 时非空），让调用方能直接给出"哪一类来源变了"的提示，而不是只说"失败了"。

### 3.6 取消语义

需求 P1-FR07：**"同一次准备的客户端取消只记录取消，不自动创建新意图"**。

| 情况 | 判定 |
| --- | --- |
| 记录 `cancelled=True`，重传**同摘要同修订** | `REUSED`（返回原记录，含取消事实） |
| 记录 `cancelled=True`，摘要或修订不同 | 走 3.5 的第 2／3 条，**不因取消而特判** |

即：**取消不改变幂等键的行为**，只是记录里的一个事实位。测试覆盖这两种情况。

### 3.7 序列化层：不适用键真正省略

`LocalProjectBinding` 的领域不变量（Sprint 1 已实现）：

- `git` 形态：`repository_id` / `branch` / `base_commit` 必填，`manifest_digest` 必须为 `None`；
- `plain` 形态：前三者必须为 `None`，`manifest_digest` 必填。

**序列化层的责任**（施工清单第 2 节遗留项）：上述"必须为 `None`"的字段，
在写出的 payload 里要**真正不出现这个键**，而不是出现且为 `null`。
需求 P1-AC25 的原文是"界面与报告中**不出现**仓库、分支、提交、远端任何内容，
**也不显示为空值或"未知"**"——空值出现在存储 payload 里，下游投影就很容易把它渲染成空值。

`to_payload()` 规则：

| 形态 | payload 中的键 |
| --- | --- |
| `git` | `binding_id`、`binding_revision`、`project_id`、`canonical_path`、`binding_form`、`repository_id`、`branch`、`base_commit`、`local_owner`（可选）、`confirmed`、`schema_version` |
| `plain` | `binding_id`、`binding_revision`、`project_id`、`canonical_path`、`binding_form`、`manifest_digest`、`local_owner`（可选）、`confirmed`、`schema_version` |

`repository_id` / `branch` / `base_commit` / `manifest_digest` 四个键中，
**只有该形态适用的那些出现**。`from_payload()` 反向解析，且**缺键与值为 `null` 同等拒绝**——
这样"存进去时省略、读出来时补 `null`"这条错误路径也会被抓到。

## 4 设计决定

| # | 决定 | 依据 | 备选与代价 |
| --- | --- | --- | --- |
| 1 | 判定规则放 `application/planning/preparation.py`，不放 `domain/` | 它描述的是**用例层的幂等与冲突处理**，不是纯业务不变量；`domain/` 里也没有"记录"这一层概念 | 备选：放领域层。代价：领域层会出现"登记/重传"这类用例词汇 |
| 2 | 用 `InputRevisions` 值对象而不是八个参数 | 需要参与相等比较与差异报告 | 备选：裸参数。代价：`changed_inputs()` 无法实现，消息只能笼统说"来源变了" |
| 3 | `payload_hash` 由**应用**计算，不接受调用方传入 | 架构文档第 8 节："`prepare_run` 解析……保存 `intent` 与 `payload_hash`" | 备选：由客户端传入。代价：客户端可以伪造"相同输入"绕过冲突检测 |
| 4 | 判定次序：摘要冲突 > 来源变化 > 幂等复用 | 架构文档第 11 节把三句话分开写，"冲突"对应摘要不同 | 备选：先比修订。代价：把冲突误报为可重试，用户会反复"重新准备"却一直失败 |
| 5 | `cancelled` 不改变幂等判定 | 需求 P1-FR07："取消只记录取消，不自动创建新意图" | 备选：取消即失效、允许新意图。代价：与"不自动创建新意图"矛盾 |
| 6 | 序列化只覆盖 `LocalProject` 与 `LocalProjectBinding` | 键存在性随形态变化的只有绑定 | 备选：为全部领域对象写序列化。代价：多半是无意义的扁平映射，且覆盖面越大越容易与 A 的存储格式冲突 |
| 7 | `from_payload` 把"缺键"与"`null`"同等拒绝 | 防止"存时省略、读时补空"的错误路径 | 备选：宽容读取。代价：状态不一致会被静默吞掉 |
| 8 | 不实现 `register_preparation` 的真实调用 | 端口无签名 | 见第 1.2 节 |

## 5 验证设计

`tests/unit/test_preparation.py`（新增），每条不变量一条测试，规则分支全覆盖。

| 测试组 | 覆盖 |
| --- | --- |
| 输入修订 | 八个字段均须 `>= 1`；相等比较按值 |
| 请求 | 四个非空字段；三个身份键的组合唯一性；`payload_hash` 前缀 |
| `payload_hash` | 同输入不同字典次序**摘要相同**；**`request_id` 等传输参数不进摘要**；不同输入摘要不同；`intent_id` 不等于 `prepare_request_id` |
| 判定四态 | `NEW`／`REUSED`／`CONFLICTED`／`NEEDS_REPREPARE` 逐条；**摘要冲突优先于来源变化** |
| 取消语义 | 取消后同摘要同修订 → `REUSED`；取消后摘要不同 → `CONFLICTED` |
| `changed_inputs` | 逐字段可变；多字段同时变化时全部列出，且顺序稳定 |
| 序列化 | `git` 形态不含 `manifest_digest`；`plain` 形态不含 `repository_id`/`branch`/`base_commit`；**键真正不存在**（`not in payload`，不是 `is None`）；往返一致；缺键与 `null` 同等拒绝 |

`tests/unit/test_binding_serialization.py` 或并入上表同一文件——实现时按行数决定。
