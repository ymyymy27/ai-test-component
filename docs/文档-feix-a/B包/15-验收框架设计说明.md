# B 包一期验收框架设计说明（Sprint 7）

版本：0.1
日期：2026-09-28
用途：定义 `tests/acceptance/p1/status.json` 的字段、取值与对账规则，使一期 35 项验收场景"条件到位即可填"。

依据：`docs/项目文档/一期/需求文档/01-需求文档.md` 第 5 节（验收场景唯一维护点）、根 `AGENTS.md` 第 5.3／5.5 条、《一期工程四部分拆分与低对接实施方案》第 5 节（验收牵头包）、`docs/文档-feix-a/B包/01-B包一期实施计划.md` 第 4 节 Sprint 7。

---

## 1 本框架解决什么

实施方案把 35 项 AC 的**牵头包**只指定一次，但"牵头"此前没有落地形式：谁填哪一行、填什么、缺什么算缺、什么时候可以写"通过"，都没有机器可检查的载体。本框架给出一处**登记 + 对账**位置，使：

- 每项 AC 的**场景与预期原文**直接对齐需求文档第 5 节，不靠人工转抄，也不允许改写；
- B 牵头的 8 项 AC（AC01、AC03、AC12、AC17、AC20、AC30、AC31、AC32）写明**前置条件、缺什么、卡在谁那里**；
- 断言不能只检查"调用成功"：`result` 的取值与 `verification.method` 强制绑定；
- 文档一致、测试通过、夹具通过，都**不能**得到 `verified`（第 6 节）。

**本框架不产生验收结论。** 它只登记"要跑什么、缺什么、谁负责、证据放哪"，以及在条件满足后如实记录实际结果。

## 2 `status.json` 字段定义

顶层：

| 字段 | 含义 |
| --- | --- |
| `version` | 框架版本，本文件与代码同版本 |
| `updated_at` | 本文件最后修订日期（不作为业务时间依据） |
| `baseline_commit` | 填写或校对本文件时 `develop` 的提交号；条件变化后应重新核对 |
| `scope` | 固定说明本文件不是脚手架测试清单，而是产品验收登记 |
| `update_rules` | 可机读的更新边界，见第 5 节 |
| `results` | 35 项登记，按 AC 编号升序，**不得缺项、不得多项** |
| `cases` | 保留的旧字段名镜像（仅为兼容既有引用），与 `results` 同源同序 |

每项登记：

| 字段 | 取值要求 |
| --- | --- |
| `id` | `P1-AC01`—`P1-AC35` |
| `owner` | 牵头包，取值 `A`／`B`／`C`／`D`；由实施方案第 5 节确定 |
| `result` | `untested`／`verified`／`not_verified`／`blocked` |
| `scenario` | **逐字**取自需求文档第 5 节"场景"列 |
| `expected` | **逐字**取自需求文档第 5 节"预期结果"列 |
| `related_frs` | 需求文档第 5 节"关联功能"列，按原顺序 |
| `prerequisites` | 跑该项所需输入、事实与环境；`null` 表示尚未分析 |
| `artifact_versions` | 软件与制品版本（提交号、模板修订、计划修订、依赖版本等）；`null` 表示尚未记录 |
| `actual` | 实际结果；未执行时必须为 `null`，不得写推测值 |
| `evidence` | `{path, description, method}`；未执行时 `path` 为 `null` |
| `unverified_reason` | 未验证原因（含缺什么、卡在谁的哪项交付） |
| `blockers` | 结构化阻塞项清单，每项含 `kind`／`detail`／`resolved_by` |
| `real_environment_verified` | 是否已在目标环境（Windows 11 x64／Python 3.13／选定 Trae 版本）取得真实证据 |

`blockers[].kind` 取值与含义：

| 取值 | 含义 |
| --- | --- |
| `package_port` | 等待 A 的端口方法签名 |
| `real_storage` | 等待真实文件存储（单写锁、不可变历史、索引） |
| `execution_facts` | 等待 C 的真实运行事实 |
| `user_entry` | 等待 D 的入口（Trae／CLI／MCP／面板） |
| `decision` | 等待归属或口径裁定（如 `SourceSnapshot` 归属） |
| `environment` | 目标环境或目标宿主版本不具备 |
| `protocol` | 对接口径未定（如 GitHub 只读获取方式） |

**`result` 与 `real_environment_verified` 的关系**：`result = verified` 要求 `real_environment_verified = true` 且 `evidence.path` 非空。用内存替身、假仓储或合同夹具得到的结论只能支撑 `not_verified`，并在 `unverified_reason` 中写明"仅通过静态·单元·合同检查"。

## 3 B 牵头 8 项 AC 的前置条件结论

逐项明细见 `tests/acceptance/p1/README.md`（与 `status.json` 同步维护）。结论概览：

| AC | 当前状态 | 已具备（本包） | 尚缺 |
| --- | --- | --- | --- |
| P1-AC01 | `not_verified` | 交付说明必填校验、任务不得推进为可验收的纯规则（`domain/project`、`application/project`） | 真实存储落盘（A 端口）；入口提示（D） |
| P1-AC03 | `not_verified` | 单模块项目、依赖图传播、跨模块"不适用 + 原因"的纯规则 | 真实存储落盘（A 端口）；适用检查的实际执行（C） |
| P1-AC12 | `not_verified` | 规则／用例修订只追加不覆盖、计划冻结准确修订、草稿定向失效 | 真实存储的历史保留（A 端口）；"新执行绑定新版本"的运行事实（C） |
| P1-AC17 | `not_verified` | 六模板结构一致、来源标注、上下文缺口阻塞、未确认草稿不进入执行 | `SourceSnapshot` 归属裁定；真实存储落盘（A 端口） |
| P1-AC20 | `blocked` | 运行中修订只影响未执行步骤、删必测／弱化断言拒绝、反向驱动拒绝的纯规则 | 步骤执行事实与运行中修订序列（C）；A 端口 |
| P1-AC30 | `not_verified` | 最小输入、无模型人工建计划、显式分析固定选定内容、分析后源码变化提示 | `SourceSnapshot` 归属裁定；`SourceSnapshotPort`；D 的入口 |
| P1-AC31 | `not_verified` | 档位／范围门禁、计划确认与逐项授权分离、每动作独立确认的规则面 | D 的确认记录与 MCP relay；C 的副作用动作；A 的记录落盘 |
| P1-AC32 | `not_verified` | 出站策略修订、`source_snippets` 默认关闭、改动后重新确认、关闭 AI 的准入规则与请求编排 | `ProjectionPort`／`SecretPort`／`ModelProvider`（A 端口）；D 的入口与展示 |

**没有任何一项可以现在填 `verified`**：8 项全部要求真实存储、真实执行事实或真实入口中的至少一项，而这些都尚未交付。

## 4 对账规则（可机读）

`tests/unit/test_acceptance_status.py` 锁定下列不变量：

1. `results` 恰好 35 项，编号为 `P1-AC01`—`P1-AC35`，升序且不重复；
2. `scenario` 与 `expected` 与需求文档第 5 节**逐字一致**；需求文档改动而未同步本文件即失败；
3. `related_frs` 与需求文档一致；
4. `owner` 与实施方案第 5 节的牵头包一致；
5. `result ∈ {untested, verified, not_verified, blocked}`；`result = verified` 必须有非空 `evidence.path` 且 `real_environment_verified = true`；
6. `result = untested` 必须 `actual = null`；
7. 非 `untested` 必须有非空 `unverified_reason` 或 `actual`；
8. `blockers[].kind` 取值在上述枚举内；未分析的项允许 `blockers = null`；
9. `cases` 与 `results` 的编号与 `result` 一致；
10. `update_rules` 中声明 B 只更新自己牵头条目的可分析字段，不改写他人条目结论。

**为什么把这些做成测试**：需求文档是"唯一维护点"，但唯一维护点只有在能被机器对账时才真正唯一。此测试把"转抄失真"和"悄悄改预期"变成 CI 可见失败。

## 5 更新边界（谁改哪一行）

| 内容 | 谁可以改 |
| --- | --- |
| B 牵头 8 项的 `prerequisites`／`artifact_versions`／`actual`／`evidence`／`unverified_reason`／`blockers`／`real_environment_verified`／`result` | B |
| 非 B 牵头 27 项的上述字段 | 各自牵头包；B 不代填结论 |
| `scenario`／`expected`／`related_frs` | **无人**：只在需求文档第 5 节改动后同步 |
| `owner` | 只在实施方案第 5 节改动后同步 |
| 顶层 `version`／`updated_at`／`baseline_commit`／`scope`／`update_rules` | 维护本框架者 |

---

## 6 不做什么

- **不产生验收结论**，也不把 `not_verified` 说成"通过"或"失败"；
- **不把静态检查、单元测试、合同夹具、生成 Schema 一致写成真实环境验收**（根 `AGENTS.md` 第 5.5 条）；
- **不代其他包填结论**，即使看起来能推断；
- **不在本框架里再造一套判定规则**：判定、统计与证据等级只在 D 的领域规则中计算一次；
- **不改写需求文档第 5 节的场景与预期**；发现分册冲突按根 `AGENTS.md` 第 1.3 节登记，不在代码里选一种解释。
