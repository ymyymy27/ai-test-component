# 计划发布请求形状草案（B 内部）

日期：2026-10-02
包：B（项目与计划）
用途：给 `publish_plan` 的**请求形状**定下来，使"计划发布入口"从"没定形状"变成可实施。
性质：**B 内部的入口形状**，不是跨包合同；`Plan` 与 `AcceptanceScope` 的领域语义仍以
`docs/项目文档/一期/架构文档/01-项目与计划.md` 为准。

---

## 1 为什么不能直接镜像内部 `Plan`

`application/planning/publish.py` 的 `publish_plan(plan, *, project_id, cases, ...)` 收的是
一个**已经构造好的 `Plan`**。把内部 `Plan` 直接当请求体镜像出去会有三个问题：

| 内部字段 | 直接镜像的问题 |
| --- | --- |
| `status` | 是**发布结果**，不是请求内容。让调用方传 `status` 等于允许"自报已发布" |
| `confirmation_id` | 由发布时**本次提交的提交序号**给出，不接受调用方传入（架构文档第 8 节） |
| `case_revisions[].digest` | 是**内容身份**，必须由服务端按用例内容算出；让调用方传等于允许伪造身份 |

`plan_id` 与 `revision` 属人工给定的业务身份（与 `rule_version` 的 `rule_id` / `revision`
同一处理方式），由调用方给出；其余由服务端**派生或校验**。

## 2 请求形状

动作名：`publish_plan`（写动作，需 `project_id` / `intent_id` / `expected_revision`）。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `plan_id` | string | 是 | 计划业务标识；同一 `plan_id` 的修订递增追加 |
| `revision` | int ≥ 1 | 是 | 本次发布的计划修订号 |
| `scope` | object | 是 | 验收范围，形状见第 2.1 节 |
| `cases` | array | 是 | 计划冻结的**实际用例全文**；每项形状与 `case` 记录的落盘形状一致 |
| `rule_revisions` | array | 否 | `[{rule_id, revision}]`；`digest` 由服务端按已发布的 `rule_version` 记录填写 |
| `template_versions` | array | 否 | `[{template_id, version}]`；`digest` 由服务端按已安装模板资源填写 |
| `run_tier` | `quick` / `on_demand` / `full` | 否 | 缺省 `full`（发布完整范围时的默认档） |
| `initial_driver` | `planned` / `stepwise` | 否 | 缺省 `planned` |

**服务端派生或校验**：

| 结果字段 | 怎么来 |
| --- | --- |
| `case_revisions[].digest` | 按请求里 `cases` 的**内容**计算，不接受调用方传入 |
| `status` | 恒以草稿进入门禁；门禁通过后由发布动作置为已发布 |
| `confirmation_id` | 取**本次提交的提交序号**，不接受调用方传入 |

### 2.1 `scope` 的形状

与 `AcceptanceScope` 的字段一一对应：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `scope_id` | string | 是 | 范围业务标识 |
| `revision` | int ≥ 1 | 是 | 范围修订 |
| `name` | string | 是 | 范围名称 |
| `required_case_ids` | array[string] | 是 | 必测集合 `M` |
| `template_case_ids` | array[string] | 是 | 模板适用必测 `T`；必须 `T ⊆ M` |
| `objective` | string | 否 | 范围目标 |
| `excluded_case_ids` | array[string] | 否 | 显式排除 |
| `exclusion_reasons` | array[[case_id, reason]] | 否 | 排除理由；**有排除就必须每项有理由** |
| `dependency_closure_ids` | array[string] | 否 | 依赖闭包纳入的用例 |
| `applicability_exclusions` | array[[case_id, reason]] | 否 | 不适用项与理由；不适用项**不计入分母** |

## 3 三条设计决定（需保持）

1. **用例全文随请求一起给，而不是只给 `case_id` 与修订号。**
   门禁要检查"冻结必测里有没有依据缺失的用例""冻结用例有没有独立核验方式"，
   只给标识就得回读记录；而"回读什么"取决于发布者看到的是哪一份用例——
   让请求自带全文，门禁检查的对象与发布者看到的是**同一份字节**。
   同时这些用例经 `save_case` 落盘后，历史修订仍可独立读回。

2. **身份摘要服务端算，调用方只给标识与修订。**
   与 `ConfirmationRecord` 不接受"自报确认"同一条原则：内容身份由服务端按字节算，
   调用方报了也没用，因此**不给这个入口**。

3. **`status` / `confirmation_id` 不进请求。**
   发布是人工动作，但"已发布"这个事实由动作本身与本次提交序号产生。

## 4 与现有代码的衔接

| 现有入口 | 衔接方式 |
| --- | --- |
| `publish_plan(plan, *, project_id, cases, unit_of_work, reader, context_gaps)` | 请求经适配层构造 `Plan` 与 `cases` 后原样调用；**不改它的签名与门禁** |
| `plan_builder.py`（当前为空壳） | 本草案的"由请求构造 `Plan`"就是它的第一段职责；实现时把构造逻辑放这里，而不是塞进动作表 |
| `save_case` / `save_acceptance` | 发布前先用它们落盘独立用例与范围；发布本身只落 `plan` 记录 |
| `application/planning/serialization.py` | `cases` 与 `scope` 直接复用同一套 `from_payload`，不另写第二套形状 |

## 5 两个身份摘要的取法（已定）

| 摘要 | 取法 |
| --- | --- |
| `rule_revisions[].digest` | 按 `rule_id` + `revision` 读 `rule_version` 记录，用 `RuleRevisionRef.from_version()` 取该版本的 `digest`（领域已提供该入口）。**记录不存在时拒绝**，不填占位值 |
| `template_versions[].digest` | 按 `template_id` + `version` 装载已安装模板资源，对其内容用与草稿正文**同一套**规范 JSON 摘要（`draft.template_draft_text()` + `draft.text_digest()`）。**模板不存在时拒绝** |

为什么模板摘要这样取：`TemplateVersionRef` 在一期**没有任何构造点**，
因此"模板版本的 digest 是什么"此前没有口径。选"模板内容的规范 JSON 摘要"是因为
它与计划里 `template_versions` 的用途一致（核对"这份计划绑的是哪一版模板内容"），
且与草稿正文共用同一套序列化，不引入第二种表示。

## 6 未定项（实施前需要有结论）

1. **`cases` 与已落盘 `case` 记录的关系**：请求里的用例与 `case` 记录不一致时以哪一份为准？
   本草案取"以请求为准，并核对记录存在且内容一致；不一致则拒绝"，但这条是**我的取舍**，
   若与检查方或对方的预期不同，以检查方口径为准。
2. **`run_tier` 的缺省值**：本草案取 `full`（发布完整范围的默认档）。
   若更希望"必须显式给出档位"，删掉缺省即可，属一行改动。
