## 1 要解决的问题（实测原文）

`AB-001` 第 8.9 节的原文：

> B 的用例**进入产品统一入口**还缺装配点改造——`bootstrap.CoreBootstrap.create()`
> 目前只把 `FileUnitOfWork` 交给 `LocalAPI(transaction_port=...)`，
> `register_use_cases` 注册的 handler 拿不到工作单元与只读仓储
> （`Handler = Callable[[Command], Mapping]`，没有依赖注入）。
> 装配点归 A；本包不修改该文件。

实测佐证（本轮复查）：`git grep register_use_cases src tests` **全仓零调用**——
注册窗口存在，但没有任何包真的注册过动作。所以"B 的用例通了"此前只在**单元测试里**
成立，**产品入口上不成立**。

## 2 约束（决定了方案只能怎么选）

| 约束 | 出处 | 对方案的影响 |
| --- | --- | --- |
| `Handler = Callable[[Command], Mapping]`，没有依赖参数 | `interfaces/local/api.py`；A 的交付说明 | 不能在 handler 调用时注入依赖 |
| B/C/D **只能提交用例注册表**，A 统一装配，不由各包修改组装点 | 《一期工程四部分拆分与低对接实施方案》第 2 节；`bootstrap.py` 模块 docstring | B 不能改 `bootstrap.py` |
| `application/` 不得 import `infrastructure` / `interfaces` | `tests/architecture/test_boundaries.py` | 动作表不能放在会 import `bootstrap` 的位置 |
| 动作名是跨包词汇，归 `contracts/commands.py` 的一期动作表 | `contracts/commands.py` | B 不能自造动作名 |

## 3 选定方案：**注册时把依赖闭包进 handler**

```
装配点 / 测试
   │  构造 BUseCaseDependencies(unit_of_work, reader, clock)
   ▼
interfaces/local/b_registration.register_b_use_cases(api, deps)
   │  显式 cast：Command → B 的结构化 handler
   ▼
application/usecase_registry.build_b_use_case_registry(deps)
   │  每个 handler 在**闭包里**持有 deps
   ▼
LocalAPI.handlers["save_context"] = entry   ← 形状与 Handler 完全一致
```

三点理由：

1. **不需要 A 先改签名**：`Handler` 的形状不变，装配点也就没有"必须先改"的理由；
   B 的阻塞项因此从"等 A"变成"B 自己能做完的部分已做完"。
2. **不越界**：新增的两个文件分别在 B 自己的 `application/` 与 `interfaces/local/`；
   `bootstrap.py` 一行未动。
3. **将来可替换**：若 A 的装配点改成支持依赖注入，B 只需把"注册时闭包"
   换成"装配时注入"，**动作表与合同测试都不用改**。

### 3.1 为什么不是"在用例里加 try/finally 收尾"

不在本设计范围（那是 B-Q10），但记一条原则：这类横切收尾属于端口层职责，
零散加在用例里会让"谁保证收尾"变得不可核对。

## 4 文件与职责

| 文件 | 层 | 职责 | 不做什么 |
| --- | --- | --- | --- |
| `src/aitest/application/usecase_registry.py` | application | 依赖包、动作表、参数与错误的翻译 | 不 import `bootstrap`/`interfaces`/`infrastructure` |
| `src/aitest/interfaces/local/b_registration.py` | interfaces | 把动作表并进 `LocalAPI.handlers`；`Command` ↔ 结构化 handler 的一次显式 cast | 不构造也不替换 `LocalAPI` |

`application` 侧的 handler 只按**结构化字段**读命令（`action` / `project_id` /
`expected_revision` / `parameters`），不认识 `contracts.Command`。这样做的好处是
`application` 不必依赖入口层的传输模型；代价是两边对接处需要一次显式 cast，
因此**必须**有一条用真实 `Command` 驱动的合同测试来锁死形状（见第 6 节）。

## 5 已暴露的动作与结果形状

| 动作 | 语义 | 记录类别 | 是否要求写身份 |
| --- | --- | --- | --- |
| `save_context` | 保存项目（模块随项目一起） | `project` | 是 |
| `save_binding` | 保存 Git/plain 绑定 | `binding` | 是 |
| `save_environment` | 保存环境引用 | `environment` | 是 |
| `save_dependency_graph` | 保存模块依赖图 | `dependency_set` | 是 |
| `save_acceptance` | 保存验收范围（含排除理由与适用范围排除） | `acceptance_scope` | 是 |
| `save_case` | 保存一条用例的某个修订 | `case` | 是 |
| `save_task` | 保存一个任务（验收项随任务一起） | `task` | 是 |
| `save_delivery` | 保存一份交付说明 | `delivery` | 是 |
| `generate_draft` | 应用模板生成草稿；**缺口非空即阻塞且不生成**；生成成功时**正文与摘要一起落盘** | `generated_content` | 是 |
| `publish_rules` | 发布规则草稿为 `RuleVersion` | `rule_version` | 是 |
| `publish_plan` | 发布计划（请求形状见 [17-计划发布请求形状草案](17-计划发布请求形状草案.md)） | `plan` | 是 |
| `prepare_run` | 编排一次准备，产出 `PreparedRun` | `preparation_record` | 是 |
| `query` | 有界查询 | — | 否（读动作） |

`generate_draft` 的缺口是**正常结果**（返回 `blocked=true` 与缺口清单），不是错误。
`publish_rules` 沿用 `PublicationResult` 的不变量：**要么得到已发布版本、要么得到阻塞原因**，
响应里用 `published` 区分两者，因此不会出现"既发布又报阻塞"的形态。

写身份（`project_id` / `intent_id` / `expected_revision`）由 `Command` 自身校验，
**不通过就不进 handler**——这是合同层的事，不在 handler 里重复校验。

### 5.0 计划域材料的落盘形状

`Case` / `AcceptanceScope` / `ConfirmationRecord` 由
`application/planning/serialization.py`（形状）与
`application/planning/persistence.py`（事务与记录标识）负责：

| 对象 | `aggregate_kind` | `record_id` | 修订 |
| --- | --- | --- | --- |
| `Case` | `case` | `case_id` | `case.revision` |
| `AcceptanceScope` | `acceptance_scope` | `scope_id` | `scope.revision` |
| `ConfirmationRecord` | `case_link` | `confirmation_id` | 1（确认只追加） |

与 `rule_version` 用 `rule_id` 当记录标识是同一模式：**同一对象的修订递增追加，
历史修订永不覆盖**。三个约定值得记下来：

1. **集合写成排序数组**：同一集合的不同书写顺序必须得到同一字节，
   否则"同一份材料"会因为 dict/set 的遍历顺序而产生不同摘要；
2. **可省略字符串写 `null`**：`independent_verification` 与 `no_critical_path_reason`
   为 `None` 时写 `null`，不写空串——空串是有内容的字符串，二者语义不同；
3. **确认只追加**：`save_confirmation()` **不接受** `expected_revision`，
   给它一个"我看到的修订"就等于允许覆盖历史确认；更正走"登记新确认"。

读回时**缺字段一律抛错**（与 `preparation_record_from_payload()` 同一原则）：
把读不懂的记录当成"没有记录"，会让同键异输入覆盖既有材料。

`publish_plan` 落在 `plan` 记录里的是**用例摘要**（`case_id`、修订、层级、依据三态、
独立核验、是否在范围内），足以核对"计划当时冻结了哪些用例"；
需要按准确修订读回**完整用例内容**时走 `case` 记录——两者用途不同，不是重复。

### 5.1 模板草稿的**正文**是什么

`apply_template()` 产出的是"应用了哪个模板的哪一个版本"的**草稿元数据**，
模板的可核对内容就是它自己声明的检查项、必测项、关键链路与样例。
因此 `generate_draft` 落盘时：

- **正文** = 模板内容按 `TemplatePack` 生成 Schema 的规范 JSON 形态
  （键排序、紧凑分隔符、`ensure_ascii`），因此**可复现**：同样输入两次生成，
  正文与 `content_digest` 逐字节一致；
- **正文与摘要一起落盘**（`draft.generated_content_payload()`），
  只存元数据会让"到底产出了什么"没有可核对的字节；
- 正文**完全来自已安装的模板资源**，不编造检查内容；模板里没有的东西不会出现；
- 模板草稿与模型草稿**共用这一份落盘形状**，避免两条路径各写一套。

### 5.2 `publish_rules` 的一处实测事实

`publish_rules` 要读 `rule_version` 的**当前修订**，走的是有界查询：
索引文件不存在时按合同报 `B_INDEX_MAINTENANCE_REQUIRED`，**不会隐式全表扫描**。
新工作空间在第一次提交后索引文件就已存在（行数为 0），因此正常链路不受影响；
测试里显式建一份空索引来复现该形态，而不是让实现偷偷回退。

### 5.3 三处刻意的取舍（写给下一个接手的人）

1. **写动作成功结果不报提交序号。**
   `application/project/persistence.py` 的 `save_*` 自带 `open`/`commit` 并只返回
   `StagedRevision`；返回时提交序号已经前进，事后补读会拿到**下一次**的序号。
   报一个错的序号比少报一个字段更糟，所以只报 `aggregate_kind` / `record_id` / `revision`。
   若将来需要随写返回提交序号，接口形态要改（由拥有 `save_*` 语义的一方决定），
   B 不在本轮自行发明。
2. **`query` 在索引缺失时返回 `B_INDEX_MAINTENANCE_REQUIRED`，不返回空列表。**
   `PortsRecordReader.query()` 把 A 的 `status=maintenance_required` 翻成
   `IndexMaintenanceRequired`；直接透传会变成 `INTERNAL_ERROR`，调用方无法把
   "索引待重建"与"真的没有数据"分开——这正是"不把未知状态静默解释为成功或空结果"。
3. **"不报提交序号"只适用于 `save_*` 那四个动作。**
   `prepare_run` 与 `publish_rules` **需要**在提交前读到提交序号，因此它们
   **依赖** `AB-001` 第 8.8 节的三个只读方法；缺少注入时按第 8.8 节抛
   `SubstrateContractError`，**不用默认值顶替**。这一点已登记在合同第 8.11 节。

## 7 未做（如实登记）

1. **跨进程唯一核心的装配点接线**：产品路径是 `CoreBootstrap.create()` 一次性装配；
   要让 B 的动作在真实核心进程里生效，仍需装配点把依赖包交给 `register_b_use_cases()`。
   **本包不修改 `bootstrap.py`。**
2. **`publish_plan` 与模型出站类动作未接**：

   | 记录类别 | 写入点 | 是否已注册 |
   | --- | --- | --- |
   | `project` / `binding` / `environment` / `dependency_set` | `application/project/persistence.py` | **是** |
   | `rule_version`（规则发布） | `application/planning/publish.py` | **是**（`publish_rules`） |
   | `preparation_record` | `application/planning/substrate_adapter.py` | **是**（`prepare_run`） |
   | `generated_content`（模板草稿元数据） | `application/planning/draft.py` | **是**（`generate_draft`） |
   | `plan` | `application/planning/publish.py` | 否（`publish_plan` 未注册） |
   | `model_outbound_request` / `generated_content`（模型出站） | `application/planning/model_orchestration.py` | 否 |

   **`publish_plan` 未接的理由**：它的输入是 `Plan`（10 字段）**加** `Case` 列表
   （每项 14 字段，含嵌套 `CaseLink`、`AssertionBasis` 与三个枚举）。给这些领域对象定 JSON 形状
   等于**另立一套合同**；按设计原则应由**拥有该语义的主责合同**定义形态，
   再写参数适配层。因此它单列一个批次，不在动作表里临时拼。
   **模型出站未接的理由**：依赖 A 的 `ModelProvider` / `SecretPort` 与运行时凭据，
   属"等 A"的部分。
3. **没有真实 Trae 宿主证据**：全部证据是合同测试与真实**文件系统**集成测试。
4. **`A` 侧三个只读方法仍未冻结**（`current_revision` / `commit_seq` / `next_commit_seq`）：
   除 `prepare_run` 与 `publish_rules` 已依赖提交序号（见 5.2 第 3 条）外，其余动作不依赖它。
