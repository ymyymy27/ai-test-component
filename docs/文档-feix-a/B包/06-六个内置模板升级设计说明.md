## 1 目的与现状

### 1.1 现状（实测）

六个模板已存在，但内容为占位。实测每个模板的条目数与形态：

| 模板 | 条目数 | 必测 | 关键链路 | 样例 | 状态字段 |
| --- | --- | --- | --- | --- | --- |
| `python-library` | 4 | 4 | **0**（有 `no_critical_path_reason`） | 3 | `scaffold` |
| `python-service` | 4 | 4 | 1 | 3 | `scaffold` |
| `http-workflow` | 4 | 4 | 1 | 3 | `scaffold` |
| `manual-web-workflow` | 3 | 3 | 1 | 3 | `scaffold` |
| `agent-workflow` | 3 | 3 | 1 | 3 | `scaffold` |
| `ticket-workflow` | 6 | 6 | 1 | 3 | `scaffold` |

**存在的三个问题**：

1. `implementation_status` 被合同锁死为 `Literal["scaffold"]`，模板永远无法标记为已发布。
2. 条目的 `objective` / `expected` 是通用占位（如"正常输入独立预期比对符合用户确认的验收条件"），未表达对应业务类型下的**具体必测与不可省核验**。
3. 缺"漏项拒绝案例"——需求明确要求每个模板都要有。

## 2 合同变更

### 2.1 `implementation_status` 由固定值改为三态枚举

```python
class TemplateImplementationStatus(StrEnum):
    DRAFT = "draft"          # 内容仍在补齐，不得作为完成依据
    RELEASED = "released"    # 内容已定稿，可生成草稿供用户补齐与确认
    DEPRECATED = "deprecated"  # 保留历史引用，新计划不再选用
```

`TemplatePack.implementation_status` 类型由 `Literal["scaffold"]` 改为该枚举。

**取值语义**（必须与"草稿只生成草稿"这条边界一致）：

| 取值 | 含义 | **不表示** |
| --- | --- | --- |
| `released` | 模板**自身内容**已定稿，可用它生成项目草稿 | ❌ 不表示项目草稿已确认，❌ 不表示可以执行 |
| `draft` | 模板内容仍可能变化 | — |
| `deprecated` | 历史引用仍可读，新建计划不再选用 | ❌ 不表示已删除（模板不设删除路径） |

**为什么需要三态而不是布尔**：与隔离方式同理——"模板没写完"和"模板已废弃"是两件事，布尔无法区分。

### 2.2 断言依据文案保持不变（记录一处易误判点）

现状六个模板的 `assertion_basis` 均为：

> "待用户补齐并确认，模板不是断言依据"

**这不是占位缺失，是正确设计，本 Sprint 不改。** 依据：

- 需求 P1-FR04："模板只能生成草稿"，"缺字段阻止发布"
- 架构文档《01-项目与计划》第 3 节：断言依据由用户对**准确修订**确认，模板不能代填
- 功能文档第 10.4 节：模板版本冻结的是必测 ID 与关键链路要求，不是某项目的断言依据

**因此模板的 `assertion_basis` 必须显式写明"由用户补齐并确认"，不得填具体业务断言。**
本条件将作为回归测试的一条断言，防止后来者误以为它该被"补全"。

### 2.3 条目字段保持现有形状

`TemplateItem` 的字段不变。需求第 4 节要求的六个字段组与现有合同对应关系：

| 需求要求的字段组 | 现有承载 |
| --- | --- |
| 身份与来源 | `schema_version`、`template_id`、`version`、`name`、`source`、`applicability` |
| 条目 | `item_id`、`layer`、`objective`、`preconditions`、`input_fields`、`entry_type`、`expected`、`assertion_basis`、`verification`、`evidence_requirements` |
| 适用性 | `applicability`（本次升级为按条件分述） |
| 必测和关键链路 | `required_item_ids`、`critical_paths`（含 `real_dependencies`、`required_verification`）、`no_critical_path_reason` |
| 草稿样例 | `examples`（`normal` / `boundary` / `error`，合同强制三类齐全） |

**结论：字段无需新增。本 Sprint 只升级内容，不改条目结构。**

## 3 六个模板的内容要求

内容依据功能文档《02-能力与模板清单》第 2 节的"必测与关键核验"与"适用边界"两列。

### 3.1 `python-library`（Python 库／纯函数）

| 项 | 内容 |
| --- | --- |
| 适用边界 | 无持久化时不要求数据库核验；**独立预期比对仍必测** |
| 必测 | 适用语法/加载；正常/边界/异常输入；**预期独立比对** |
| 关键链路 | 无跨系统链路 → 保留 `no_critical_path_reason` 并写明"独立预期比对仍必测" |
| 不可省核验 | 纯函数预期比对（不得用"运行成功"代替） |

### 3.2 `python-service`（Python 服务）

| 项 | 内容 |
| --- | --- |
| 适用边界 | **仅实际服务项适用，库项目不强套** |
| 必测 | 适用构建/加载/**最小启动**；健康与关键入口；依赖失败；**状态变化核验** |
| 关键链路 | 服务启动 → 关键入口 → 状态变化的真实链路 |
| 不可省核验 | 最小启动的真实进程事实；状态变化需独立读取，不采信进程自报 |

### 3.3 `http-workflow`（API 流程）

| 项 | 内容 |
| --- | --- |
| 适用边界 | 鉴权/会话/持久化**按适用条件**；**必须真实链路，不以 Mock 顶替** |
| 必测 | 同对象请求串联；字段/业务断言；错误路径；**持久化独立核验** |
| 关键链路 | 写请求 → 独立只读查询同一业务对象 |
| 不可省核验 | **成功 HTTP 状态码不能代替持久化证据**；写请求恢复须有端点幂等合同 |

### 3.4 `manual-web-workflow`（人工页面验收）

| 项 | 内容 |
| --- | --- |
| 适用边界 | **无页面不适用**；**尚不支持不等于不适用**（两者必须区分） |
| 必测 | 业务路径；适用按钮/分页/跳转/表单/滚动/鼠标/异常提示；**刷新后核验** |
| 关键链路 | 页面操作 → 刷新/重进后同一业务对象的独立核验 |
| 不可省核验 | 刷新后的持久状态；不包含浏览器录制回放 |

### 3.5 `agent-workflow`（智能体评价）

| 项 | 内容 |
| --- | --- |
| 适用边界 | **无采集则列缺口，不采信 AI 自述** |
| 必测 | 实际输入/工具调用/结果；**发布评价规则**；随机输出**默认重复三次分别留存** |
| 关键链路 | 智能体调用 → 实际工具事件采集 → 业务观察 |
| 不可省核验 | 实际工具事件；随机输出的三次独立留存；**不得以文字自述补造证据** |

### 3.6 `ticket-workflow`（工单贯通示例）

| 项 | 内容 |
| --- | --- |
| 适用边界 | **联调示例，不代表所有业务**；复用 HTTP／人工能力，不引入专用执行引擎 |
| 必测 | 创建取 ID → 分页找到同 ID → 详情 → 改状态 → 刷新/重进 → **独立持久化核验** |
| 关键链路 | 同一工单 ID 贯穿创建 → 查询 → 改状态 → 复查询 |
| 不可省核验 | 全程同一业务对象标识；改状态后的独立持久化证据 |

### 3.7 六个模板共同的必测下限原则

每个模板的 `required_item_ids` 必须**覆盖该模板适用边界下的最小必测集合**，且：

1. **不得通过删除必测项规避门禁**（需求 P1-FR07）；
2. 模板**只能生成草稿**，`released` 不改变这一点；
3. 条目的 `item_id` 稳定，升级内容**不改变既有 `item_id`**——已引用旧 ID 的计划不受影响。

> **本次升级不新增也不重命名任何 `item_id`**，只在必要时追加。理由：`PreparedRun` 以准确修订引用模板，重命名会破坏既有引用。

## 4 漏项拒绝案例

需求第 3 节："每个模板须有……**漏项拒绝案例**"。

**当前实现方式**：由 `tests/contracts/test_templates.py` 的 `test_invalid_packs_cannot_be_used` 覆盖五类非法输入（缺字段、重复 ID、悬空引用、空关键链路无理由、未知执行字段）。

**本 Sprint 的处理**：**不把"漏项拒绝案例"塞进模板 JSON**，理由：

1. `TemplatePack` 的 `extra="forbid"` 会在 JSON 中拒绝任何未知字段，加一个 `rejection_examples` 字段需要改合同；
2. 需求第 4 节把它列在**草稿样例**行，指的是"验证缺字段等输入被拒绝"的**校验行为**，不是模板数据的一部分；
3. 现有五类拒绝测试已覆盖该要求，本次**扩展为逐模板覆盖**（每个模板各验一次五类拒绝）。

**这是本 Sprint 唯一一处与需求字面表述可能不同的处理，理由如上，记录在此备查。**

| 断言 | 原状态 | 改为 |
| --- | --- | --- |
| `assert all(p.implementation_status == "scaffold" for p in packs)` | 锁定 scaffold | **改为锁定 `released`**（六个模板本次升级后即定稿） |

> **改既有断言的说明**（项目协作规则第 3 条、B 包规则第 4 节要求）：
> 该断言原意是"模板尚未定稿，不得当完成依据"。本次升级后该前提不再成立，
> 因此**改其取值而非删除**，并保留"必须是一个合法状态值"的校验意图。

### 5.2 新增内容回归测试（`tests/contracts/test_template_content.py`）

逐模板断言需求里的可检查项（**不重复合同已保证的结构校验**）：

| 断言 | 依据 |
| --- | --- |

| `python-service` / `http-workflow` / `manual-web-workflow` / `agent-workflow` / `ticket-workflow` 各至少一条 `critical_paths`，且含 `real_dependencies` 与 `required_verification` | 需求第 2、4 节 |

| 六个模板的 `item_id` 集合与升级前一致（无重命名） | 第 3.7 节 |
