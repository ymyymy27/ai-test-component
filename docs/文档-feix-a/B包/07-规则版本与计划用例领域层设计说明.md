## 3 数据模型与不变量

### 3.1 规则：`RuleDraft` → `RuleVersion`

架构文档第 3 节：**"`RuleDraft` 发布 `RuleVersion` 不可变"**；需求 P1-FR05：**"正文说明、结构化规则和发布状态分开"**、**"导入只创建草稿，不执行其中命令"**、**"往返保留编号、来源与未识别扩展字段，未知执行字段不得静默启用"**。

#### `RuleDraft`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `rule_id` | `str` | 稳定规则编号 |
| `revision` | `int` | 草稿修订，从 1 起 |
| `scope` | `str` | 适用范围 |
| `text` | `str` | 面向人的正文说明 |
| `steps` | `tuple[str, ...]` | 结构化步骤 |
| `evidence_requirements` | `tuple[str, ...]` | 证据要求 |
| `source` | `str` | 来源（人工／导入）；导入必须保留来源 |
| `enablement` | `RuleEnablement` | 启用状态；**草稿未发布不生效** |
| `unknown_extension_fields` | `tuple[str, ...]` | 往返保留的未识别扩展字段 |
| `confirmed` | `bool` | 是否已确认；未确认不得发布 |

**不变量**

1. `rule_id`、`scope`、`text`、`source` 非空；`revision >= 1`。
2. **`unknown_extension_fields` 只做保留，不得进入 `steps` 或被执行。** 领域层提供 `executable_steps()` 只返回已识别的 `steps`；测试断言未知字段不出现在其中。
3. `enablement` 为 `enabled` 时 `confirmed` 必须为 `True`（未确认不生效）。

#### `RuleVersion`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `rule_id` | `str` | 同草稿 |
| `revision` | `int` | 发布后的修订号，**与草稿修订独立递增** |
| `scope` / `text` / `steps` / `evidence_requirements` | 同草稿 | 冻结内容 |
| `source` | `str` | 保留来源 |
| `confirmation_id` | `str` | 发布确认记录标识 |
| `digest` | `str` | 内容摘要，供 `PreparedRun` 按准确修订引用 |

**不变量**

1. `revision >= 1`；`confirmation_id`、`digest` 非空。
2. **`RuleVersion` 不可变**（`frozen=True`），发布后不提供任何修改路径。
3. **发布是独立动作**：`RuleDraft` 不提供"自动发布"方法；`RuleVersion` 只能由显式的发布用例构造（本 Sprint 只提供构造函数与守卫）。

**新测试使用新版本、历史保留原版**：`RuleVersion` 以 `(rule_id, revision)` 标识，`PlannedRuleSet` 按准确修订引用。

### 3.2 断言依据三态与派生有效状态

架构文档第 3 节：

> 确认依据使用既有 `ConfirmationRecord` 绑定准确 Case/依据修订与摘要，**不改写冻结 Plan 或原 Case 字节**；
> 应用读取该精确依据的有效确认记录派生 `effective_assertion_basis_state`，**生成新的判定/报告修订，不能将文本已改变的旧确认带到新依据**。

#### `AssertionBasis`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `state` | `AssertionBasisState` | **Case 修订保存时的冻结值** |
| `text` | `str` | 依据文本 |
| `revision` | `int` | 依据修订，从 1 起 |
| `text_digest` | `str` | 依据文本摘要 |

**不变量**：`state == MISSING` 时 `text` 必须为空；`state != MISSING` 时 `text`、`text_digest` 必须非空。

#### `ConfirmationRecord`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `confirmation_id` | `str` | 确认标识 |
| `case_id` | `str` | 被确认的用例 |
| `basis_revision` | `int` | **绑定的准确依据修订** |
| `basis_text_digest` | `str` | **绑定的准确依据文本摘要** |
| `confirmed_at_commit` | `str` | 确认时的提交序号（业务顺序以此判断） |

**不变量**：均非空；`basis_revision >= 1`。

#### 派生函数（本 Sprint 的核心）

```python
def effective_assertion_basis_state(
    basis: AssertionBasis,
    confirmations: Sequence[ConfirmationRecord],
) -> AssertionBasisState:
    """派生当前有效状态；不回写冻结 Case。"""
```

**规则（逐条对应架构文档与需求原文）**：

| 输入条件 | 派生结果 | 依据 |
| --- | --- | --- |
| `basis.state == MISSING` | `MISSING` | 缺失无法被确认补齐 |
| 存在确认记录，且 `basis_revision` 与 `basis_text_digest` **都**匹配当前依据 | `CONFIRMED` | "绑定准确依据修订与摘要" |
| 有确认记录但修订或摘要**不匹配**（依据文本已变） | `PRESENT_UNCONFIRMED` | "不能将文本已改变的旧确认带到新依据" |
| 无匹配确认记录且 `basis.state != MISSING` | `PRESENT_UNCONFIRMED` | 已填未确认 |

**三条硬性不变量**：

1. **依据文本变化后旧确认失效**：摘要不匹配即回到 `PRESENT_UNCONFIRMED`。
2. **不回写**：本函数不修改 `basis` 或 `case`；派生值不写进冻结对象。
3. **补充确认不增加已验证数**：本函数**只返回状态**，不返回任何计数；领域层不提供"确认数 +1"的路径。

> **为什么把 `ConfirmationRecord` 放进领域层**：架构文档称其为"既有"记录，但其字段全是纯值。
> 本 Sprint 只定义其**领域表示与匹配规则**，持久化与编排仍属应用用例（等 A 的端口）。

### 3.3 `Case` 与发布门禁

需求 P1-FR06 的用例字段：**层级、前置条件、输入、步骤、预期结果、验证方法、允许的 Mock 范围、重要性、断言依据**。

#### `Case`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `case_id` | `str` | 稳定编号 |
| `revision` | `int` | 从 1 起 |
| `layer` | `CaseLayer` | 层级 |
| `objective` | `str` | 目标 |
| `preconditions` | `tuple[str, ...]` | 前置条件 |
| `inputs` | `tuple[str, ...]` | 输入 |
| `steps` | `tuple[str, ...]` | 步骤 |
| `expected` | `str` | 预期结果 |
| `verification_method` | `str` | 验证方法 |
| `independent_verification` | `str \| None` | **独立核验方式**；发布必填 |
| `mock_scope` | `tuple[str, ...]` | 允许的 Mock 范围 |
| `importance` | `CaseImportance` | 重要性 |
| `assertion_basis` | `AssertionBasis` | 断言依据（含冻结三态） |
| `links` | `CaseLink` | 关联 |

**不变量**

1. `case_id` 非空；`revision >= 1`。
2. `objective`、`expected`、`verification_method` 非空。
3. **`preconditions` 与 `steps` 均非空** —— 需求："没有预期结果或前置条件不得标为可直接验收的完整用例"。
4. **`expected` 为空时不得构造** —— 同上。
5. `mock_scope` 中的每一项非空；`mock_scope` 非空时**不因此降低证据要求**（领域层不做降级）。

#### `CaseLink`

架构文档第 3 节：`CaseLink` 关联**验收项、模块、检查内容、适用环境**；需求："发布时必须把用例关联到适用关键链路条目，并登记该用例的独立核验方式"。

| 字段 | 类型 |
| --- | --- |
| `acceptance_item_ids` | `frozenset[str]` |
| `module_ids` | `frozenset[str]` |
| `environment_ids` | `frozenset[str]` |
| `critical_path_ids` | `frozenset[str]` |
| `no_critical_path_reason` | `str \| None` |

**不变量**

1. **`critical_path_ids` 为空时 `no_critical_path_reason` 必须非空** —— 需求："确无适用链路时保存明确空集合及理由；缺清单字段仍阻止发布"。
2. `acceptance_item_ids` 非空 —— 需求："用例关联验收项……是关联链的起点"。
3. 各集合元素非空字符串。

#### 发布门禁（纯函数）

```python
def validate_case_publication(case: Case) -> None:
    """不满足则抛 ValueError，并指出具体缺失字段。"""
```

| # | 门禁 | 依据 |
| --- | --- | --- |
| 1 | 无预期结果或前置条件 → 拒绝 | 需求 P1-FR06 异常处理 |
| 2 | 缺 `independent_verification` → 拒绝 | "发布必填；缺失时该用例不得计入已验证" |
| 3 | 无验收项关联 → 拒绝 | "关联链的起点" |
| 4 | 关键链路为空且无理由 → 拒绝 | "缺清单字段仍阻止发布" |
| 5 | **`assertion_basis.state == MISSING` 时不拒绝发布，但该用例不得进入 `full` 必测** | 架构文档第 3 节：missing 禁止进入 full 必测，未说禁止发布 |

**第 5 条是易错点**：`missing` 依据阻止的是**进入 full 必测**，不是**发布**。需求原文：
"缺失时不可进入完整验证必测项"，而发布状态与依据状态"独立记录，不与发布确认混同"。

### 3.4 `AcceptanceScope` 扩展与 `Plan`

架构文档第 3 节：

> `Plan`：计划编号、修订、冻结的规则版本与用例修订、必测项集合、档位、驱动、结论上限。
> 约束：计划发布固定**精确**用例与规则修订。

现有 `AcceptanceScope` 已有 `scope_id` / `revision` / `name` / `required_case_ids` / `template_case_ids`，本次**扩展**（不重命名既有字段）：

| 新增字段 | 类型 | 依据 |
| --- | --- | --- |
| `objective` | `str` | 需求 P1-FR06："AcceptanceScope 含目标" |
| `excluded_case_ids` | `frozenset[str]` | "包含/排除及原因" |
| `exclusion_reasons` | `tuple[tuple[str, str], ...]` | 同上；**排除必须给原因** |
| `dependency_closure_ids` | `frozenset[str]` | "依赖闭包" |
| `applicability_exclusions` | `tuple[tuple[str, str], ...]` | "适用性"；不适用项必须给理由 |

**不变量（新增）**

1. `excluded_case_ids` 中每一项必须在 `exclusion_reasons` 里有原因。
2. `applicability_exclusions` 的每一项必须带非空理由；**不适用项不计入分母**（由 D 计算，领域层只保证理由存在）。
3. **`T ⊆ M`**：`template_case_ids ⊆ required_case_ids`（既有不变量，保留）。

#### `Plan`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `plan_id` | `str` | 计划编号 |
| `revision` | `int` | 从 1 起 |
| `scope` | `AcceptanceScope` | 冻结的验收范围 |

| `rule_revisions` | `tuple[RuleRevisionRef, ...]` | **按准确修订**冻结的规则 |
| `template_versions` | `tuple[TemplateVersionRef, ...]` | 模板版本 |

| `status` | `PlanPublicationStatus` | `draft` / `published` |
| `confirmation_id` | `str \| None` | 发布确认；`published` 时必填 |

**不变量**

1. `plan_id` 非空；`revision >= 1`。
2. **按准确修订引用**：`CaseRevisionRef` / `RuleRevisionRef` / `TemplateVersionRef` 均含 `revision` 或 `version` 与 `digest`，**不得出现"最新"语义**。
3. `status == PUBLISHED` ⇒ `confirmation_id` 非空。
4. **发布在人工动作下完成**：`Plan` 不提供"自动发布"路径（`publish_plan` 属 `HUMAN_ACTIONS`，见 `contracts/commands.py`）。

## 4 五处设计决定

| # | 决定 | 依据 | 备选与代价 |
| --- | --- | --- | --- |
| 1 | 领域层提供 `effective_assertion_basis_state` **派生函数**而非字段 | 架构文档第 3 节："应用读取该精确依据的有效确认记录派生" | 备选：在 `Case` 上存派生值。代价：违反"不改写冻结 Case 字节" |
| 2 | `RuleDraft` 不提供任何自动发布方法 | 需求 P1-FR05："导入只创建草稿"；`publish_rules` 属人工动作 | 备选：提供 `publish()`。代价：AI／MCP 可绕过人工确认 |
| 3 | `missing` 依据**不阻止发布**，只阻止进入 full 必测 | 架构文档第 3 节；需求"发布状态与依据状态独立" | 备选：missing 直接拒绝发布。代价：与"已发布但依据待确认不退回草稿"矛盾 |
| 4 | `Plan` 不含 `conclusion_ceiling` 字段 | 架构文档第 4 节："只由档位派生" | 备选：冻结时存一份。代价：出现两个真值来源 |
| 5 | `ConfirmationRecord` 的领域表示进领域层，持久化仍属应用用例 | 架构文档第 3 节称其"既有"，字段全为纯值 | 备选：整个放应用层。代价：派生规则无法纯测 |

## 5 验证设计

`tests/unit/` 新增／扩展，**每条不变量一条测试，合法与非法都覆盖**。

| 文件 | 覆盖 |
| --- | --- |
| `tests/unit/test_rules.py`（新增） | 规则字段必填；未确认不得启用；**未知扩展字段不得进入可执行步骤**；发布版本不可变；按准确修订引用 |
