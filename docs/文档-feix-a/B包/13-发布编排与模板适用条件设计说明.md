## 3 三条硬约束的落点

| 约束 | 落点 | 依据 |
| --- | --- | --- |
| **发布是人工动作，不接受"自报确认"** | `confirmation_id` 取**本次提交的提交序号**，不由调用方传入；本模块无"自动发布"路径 | `contracts/commands.py` 把 `publish_rules` / `publish_plan` 列为 `HUMAN_ACTIONS` |
| **失败可说明，不抛栈** | 门禁不通过或上下文有**阻塞级**缺口时返回 `PublicationResult(value=None, blocked_by=(...))` | 发布是用户触发的动作，失败要能向用户说明原因 |
| **写入失败不得显示为已保存** | 提交异常**向上抛**，不吞掉 | 根 `AGENTS.md` 第 3 节 |

### 3.1 只有**阻塞级**缺口才拦发布

`detect_context_gaps()` 返回两级缺口（见 `12-...设计说明.md` 第 2 节）。
发布只被**阻塞级**拦住；提示级（如盘符类型未知）不拦。
有测试分别覆盖两种情况。

### 3.2 已发布的计划**不原地再发布**

`Plan` 不可变，历史运行仍引用原修订。因此 `publish_plan()` 对
`status == published` 的输入直接拒绝并提示"发布新修订"。
**不是因为技术做不到，而是因为"历史运行仍引用原版"这条产品约束。**

## 4 实现中发现的一处真实缺陷（值得记录）

**现象**：同一规则的**第二次发布**被薄底座拦下，报
`ConcurrentEditError: rule_draft rule-1: expected revision None but current is 1`。

**原因**：`publish_rules()` 最初一律传 `expected_revision=None`（语义是"新建"）。
第一次发布确实在新建，第二次则是在既有记录上加修订——
底座正确地拒绝了"以新建语义覆盖已有记录"。

**修正**：发布前先从只读侧读**当前修订**，把实际值传给底座：

```python
expected_revision=_current_revision(
    reader, project_id=project_id, aggregate_kind="rule_draft", record_id=draft.rule_id
)
```

`publish_plan()` 同样处理。

**为什么值得记**：这条缺陷若未发现，"规则改版后重新发布"这条**正常业务路径**会完全不可用，
而单元测试不跑编排就看不出。它也说明薄底座的"不自动覆盖"守卫确实在起作用。

## 5 模板适用条件

需求 P1-FR04 异常分支："项目上下文缺失时列出缺什么并保持阻塞"；
施工清单要求"**不适用项给出原因**"。

因此 `assess_template()` 返回**逐项缺失的能力名**，而不是一个布尔：

| 语义 | 判定 |
| --- | --- |
| **适用** | `applicable=True`，`missing` 为空 |
| **不适用** | `applicable=False`，`missing` 逐项列出 |

**三项语义不得混同**（施工清单第 3 节"尚不支持"与"不适用"不得混用）：

- **适用**：模板要求的能力项目都具备；
- **不适用**：模板要求某项能力而项目没有 —— 本函数判定；
- **尚不支持**：能力清单里该技术栈尚未实现 —— **不在本函数范围**，由调用方另行声明。

`ApplicabilityAssessment` 在构造期拒绝"既适用又有缺失"与"不适用但没说缺什么"两种自相矛盾状态。
