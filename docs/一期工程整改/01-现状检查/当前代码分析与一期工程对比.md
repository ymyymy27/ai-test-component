## 3. 新增缺陷与已知产品阻断

### C-15：默认快照身份/字段与执行目录接错（已复现默认阻断）

- 真实 B `analyze_project` 保存业务 `source-*`，记录另有技术 `pinned_snapshot_id=snap-*`。`SnapshotRef` 保存 `source_snapshot_id`；默认 `SavedActionResolver._snapshot` 把业务 ID 直接交 `StartMaterializer`/`FileSourceSnapshotStore`，后者只接受技术 snap-ID，报 `SnapshotError: pinned source snapshot identity is invalid`。
- 用真实核心/UOW/固定字节、已有受控材料/环境夹具执行 prepare_run→register_run→未替换的默认解析器：准备状态为 prepared，但 prepare_execution 即失败，未启动业务。这是默认装配级证据，未冒充真实 Trae 人工验收。
- 绕过前一层单独核对 provider：它读取 `snapshot.snapshot_id`，正式 DTO 实际是 `source_snapshot_id`；真实 verify_pinned 返回技术清单，没有 provider 要求的 `content_identity`。两个不匹配分别复现。
- 同族静态缺陷：解析器虽计算 `workdir`/`cwd`，`ExecutionRequest.materialized_snapshot_ref` 却填 snapshot_id；默认 RegisteredEntryExecutionAdapter 将其当文件目录。此项当前被前置阻断遮挡，不宣称真实 start 已执行。需统一准确业务记录→技术清单/内容身份→实际固定 cwd 的端到端来源，不能关闭来源核验来绕开。

### C-16：来源核验丢弃失败事实，SYNTAX 未实际检查（边界反例已复现）

为检查被 C-15 遮挡的逻辑，反例显式使用兼容字段替身；真实 blob 固定/物化和 Python 子进程仍执行。不得把该替身当已修生产桥接。三个反例分别为：平铺 entry.py 语法错误；一个正常包加一个导入 SyntaxError 的包；命名空间包内子文件语法错误加正常包。三组都返回 `verified`、空 gap。

根因是无模块时仅核摘要/文件存在而未 compile；有模块时只取第一个非空 `item.file`，丢弃其他模块 `load_error`/无文件/摘要、probe_error 和实际解释器事实，且没有逐模块比较冻结内容。PythonLoadSourceProbe/evaluate_source_binding 组件存在并不表示 provider 消费了全部结果。关闭条件须覆盖语法、全部登记模块和入口的实际来源/摘要、失败分类以及永久原始输出。
