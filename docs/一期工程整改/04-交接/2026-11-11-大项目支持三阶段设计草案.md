# 大项目支持三阶段设计草案

- 状态：**已评审，已同步到 `docs/项目文档/`；阶段 A 后端已开始，A3/真实 Trae/AC 未验收。**
- 日期：2026-11-11
- 范围：一期 P1-FR10、P1-FR12、P1-FR14、P1-FR15、P1-FR17 的大项目适配。
- 结论：**不新增 FR/AC，不新增第七个模板，不引入用户分组；采用 scope-first、原生 pytest、JUnit 永久证据、验收项级独立核验。**

---

## 1 背景

当前向导和计划链路只适合单入口、单文件、纯函数场景：

- 向导固定使用 `python-library` 模板；
- 入口必须是项目内的 `.py` 文件；
- 执行源只有一个 `registered_entry`、一组 `entry_arguments`；
- `cwd_mapping` 只校验、不生效；
- 纯函数核验要求 stdout 是单个 JSON 对象；
- 没有 pytest 发现、JUnit 解析或多包测试范围；
- 问题、报告、导出已有实现，但部分投影仍有缺口。

大项目通常有多个包、多个测试目录、成百上千个测试。  
如果按“一个 node ID 一个 case”设计，会出现计划爆炸、AI 枚举不可靠、参数上限、问题列表爆炸。

因此本设计采用 **scope-first**：

> AI 选择真实测试范围（阶段 A/B 为文件/目录/marker；单个 node ID 放到阶段 C），pytest 执行范围，JUnit 展开到每个测试，报告按“验收项 → 范围 → 测试结果”展示。

---

## 2 设计目标与非目标

### 2.1 目标

1. 多包项目可以发现真实测试。
2. AI 只能从真实测试清单中选择范围，不能编造测试节点或范围。
3. 用户只确认目标和计划，不确认分组。
4. 测试在物化副本中执行，不修改被测仓库。
5. 原始 stdout/stderr 与 JUnit XML 都永久保存。
6. pytest 结果只作为断言结果，独立核验单独表达。
7. 失败测试生成问题草稿，复用现有问题、修复、回归、关闭流程。
8. 报告和导出复用现有服务，补足追溯字段。
9. 模型不可用时仍可手工选择范围、执行、看证据、处理问题。
10. 每个阶段独立验收，不越级声称。

### 2.2 非目标

- 不实现平台上传、跨账号、服务端协作。
- 不新增二期/三期能力。
- 不把 AI 分组做成用户确认项或独立合同。
- 不在阶段一/二声称 L3 完成。
- 不把 pytest 通过等同于业务正确。
- 不自动关闭问题。
- 不删除原始证据或 JUnit。

### 2.3 与一期产品目标的对应

三阶段全部完成后，覆盖产品目标；阶段 A/B 单独完成时，不宣称一期产品目标全部满足。

| 产品目标 | 设计覆盖 | 完成阶段 |
| --- | --- | --- |
| 嵌入 Trae、本地执行与存储、可选模型出站 | 现有 Python 核心、Trae 扩展、面板；模型只做草稿 | 已有，A/B 继续复用 |
| 不部署服务、不登录、不上传、不跨账号 | 明确非目标；全部记录在本机工作空间 | 全阶段 |
| 理解项目上下文 | `analyze_project`、源码快照、项目理解 | A |
| 组织测试 | 六个业务模板 + `RuleVersion` + Test Inventory + scope-first 计划 | A |
| 调用模型辅助分析 | AI 从真实 Inventory 选择范围、起草预期、解释失败 | A/B |
| 收集原始证据 | 原始 stdout/stderr + JUnit 附件；JUnit 不删除 | A |
| 发现问题所在 | `failure_frame` + `suspect_source_frame` + 失败类别、消息、堆栈、证据；找不到位置标 `location_unknown`；AI 根因只作候选 | A（详情）、B（问题） |
| 形成问题清单并跟踪修复 | 失败签名簇 → 问题草稿（内部列失败测试）→ 确认 → 修复 → 回归 → 关闭 | B |
| 链路检查是插件的一项能力 | 沿用现有 HTTP workflow / trace / 人工关联；不重做、不删除 | 已有，B/C 报告保留 |
| 测试规范 | 计划继续绑定 `TemplatePack`、`RuleVersion`、断言依据 | A |
| 分层执行 | L1 现有源码检查；L2 pytest；L3 在 C 完成 | A（L1/L2）、C（L3） |
| 问题反馈 | 问题草稿、确认、修复、回归、关闭 | B |
| 本地报告导出 | `SavedReportService`、`SavedExportService` | B |
| 验收项/用例/执行/证据/问题可追溯 | `CaseLink`、`ExecutionFacts`、`ReportSnapshot.issue_revisions`、导出 | B |
| 分别表达源码可运行/模块正确/完整业务 | 报告分层；L1/L2 在 A，L3 在 C；不互相替代 | C |
| 实际执行、开发说明、Mock 声明、AI 候选分开 | 执行事实、交付说明、Mock 声明、AI 草稿/假设分别保存 | A/B |
| 模型不可用时保留证据并人工处理 | 手工选范围、手工预期；执行/证据/报告/问题继续 | A/B |

结论：

- **三阶段全部完成后，符合产品目标。**
- **阶段 A 满足“发现、L1/L2 执行、证据、基础报告”**，不满足问题闭环、L3、Mock 真实性、依赖影响。
- **阶段 B 满足问题、追溯、报告、导出、Mock 候选**，仍不满足 L3 和依赖影响。
- **阶段 C 完成后才可声称分层业务和完整产品目标覆盖。**

## 3 关键设计决策

### D1 scope-first，而不是 node-first

一个 case 代表一个验收目标或一个测试范围：

```text
case: 订单创建主流程
  inputs: ["pkgA/tests/test_order.py"]
  steps: ["运行该测试范围并核对结果"]
  verification_method: "pytest-junit"
```

JUnit 展开：

```text
pkgA/tests/test_order.py::test_create  passed
pkgA/tests/test_order.py::test_cancel  failed
pkgA/tests/test_order.py::test_refund  skipped
```

优点：

| 维度 | node-first | scope-first |
| --- | --- | --- |
| AI 选择 | 枚举大量 node ID | 只选范围 |
| 计划大小 | 几千 case | 几十 case |
| 参数限制 | 容易超 64 | 一个范围一个参数 |
| 参数化/重命名 | 计划大量失效 | 范围仍有效 |
| 问题粒度 | 每个 case 一个问题 | 每个失败签名簇一个问题（内部列失败测试） |
| 大项目可用性 | 差 | 好 |

默认范围粒度：

1. 测试文件；
2. 测试目录/包；
3. marker（可选）；
4. 单个 node ID 只放到阶段 C 的定向补充，阶段 A/B 不做。

阶段 A/B 以文件和目录为主，避免一开始就引入 node ID 级别的计划与参数复杂度。

### D2 保留六个模板，使用现有 `entry_type`

不新增 `python-pytest` 模板。

- 六个业务模板继续负责提醒项、覆盖、关键链路；
- 模板项使用现有 `entry_type` 字段声明执行方式；
- 新增 `entry_type = "pytest"`，由执行源选择 pytest 路径；
- 以后 unittest 也走 `entry_type`，不新增模板。

这样不破坏“六个模板”的合同，也不把业务模板和执行框架混在一起。

### D3 默认不新增 `PlanProposal 1.2`

优先复用现有字段：

```json
{
  "inputs": ["pkgA/tests/test_order.py"],
  "steps": ["运行该测试范围并核对结果"],
  "verification_method": "pytest-junit"
}
```

`test_target` 由 `inputs[0]` 派生，不新增字段。

只有评审明确要求 UI 区分“测试范围”和“普通输入”时，才新增：

```text
PlanProposal 1.2
  case.test_target: str
```

不新增 `package` 字段；包名从路径派生，只做报告标签。

### D4 原生 `python -m pytest`，不注入桥接器

执行形态：

```text
python -m pytest
  --junitxml=<workdir>/evidence/pytest.xml
  --rootdir=<package-root>
  <scope-or-node>
```

不新增 `pytest_bridge.py`，避免：

- 新执行入口；
- 原始输出被改写；
- harness 身份/摘要问题；
- 与“登记入口/来源可核对”合同冲突。

需要补的是：

1. 向导允许 pytest 入口，不再强制 `.py`；
2. `cwd_mapping` 生效，或明确使用 `--rootdir`；
3. 执行适配器采集 JUnit 文件作为证据附件。

### D5 原始输出与 JUnit 都永久保存

```text
attempt
  ├─ stdout        原始 pytest 输出
  ├─ stderr        原始 pytest 错误
  ├─ pytest.xml    JUnit 结构化结果（永久）
  └─ derived       解析后的 outcome/计数（可重算，不替代原始）
```

规则：

- JUnit XML 不解析后删除；
- 派生结果只做展示和核验输入；
- 证据保存后才允许回收 workdir；
- 原始输出按现有凭据过滤合同处理。

### D6 pytest 结果 = 断言结果，独立核验另算

| 情况 | 报告写法 |
| --- | --- |
| pytest 通过，有独立核验 | 断言通过 + 已独立验证 |
| pytest 通过，无独立核验 | 断言通过 + **未独立验证** |
| pytest 失败 | 断言失败 |
| 跳过/收集错误 | 未完成 |
| Mock 未核验 | 断言通过 + **Mock 未核验** |

独立核验粒度：**每个验收项至少一条**，不是每个测试一条。

独立核验方式：

- 纯函数独立预期比对；
- 只读业务查询；
- 已有的外部核验能力。

没有独立核验时，不判完整通过。

### D7 Test Inventory 绑定源码快照

`discover_tests` 的结果形成 Test Inventory：

- 绑定 `source_snapshot_id`；
- 记录文件级摘要：路径、测试数、marker、收集错误；
- 不保存全量 node ID；
- 有摘要，可复取；
- AI 只能从 Inventory 的树形投影中选择范围；
- 源码变化后 Inventory 失效，重新发现。

Inventory 是**派生缓存**，不是永久业务记录，不需要用户确认；可随时从源码快照重新生成。

选择文件/目录时不需要 node ID 清单；JUnit 执行结果会给出实际测试节点。

### D8 问题按失败签名簇生成，内部列失败测试

- 失败签名 = 异常类型 + 归一化后的首条消息 + 首个项目源码帧；
- 同一 scope 内同签名合并为一个问题草稿；
- 不同签名分开生成问题；
- 草稿内部列出全部受影响测试、失败位置和证据；
- 关联 case、run、attempt、JUnit 节点、证据、验收项；
- 用户可以在问题详情中拆分、合并或只针对单个测试建子问题；
- 草稿状态为 `draft`，用户确认后才 `confirmed`；
- 修复/回归/关闭复用现有 `SavedDefectManagement`。

这样：

- 一个 `ImportError` 导致 20 个失败 → 1 个问题；
- 同一文件 3 个不同断言失败 → 3 个问题；
- 不丢失任何失败测试。

归一化只处理临时路径、内存地址、随机 ID、时间戳和参数化实例编号；不改业务数值和断言值。

### D9 包只做报告标签，不做身份

- 包名从 node ID/文件路径派生；
- 不进入用户确认；
- 不进入计划身份；
- 模块映射仍使用项目已登记模块和 `CaseLink.module_ids`；
- 无法映射时标“未登记模块/缺口”，不让 AI 分组替代模块登记。

### D10 面板复用现有三入口

- 项目页：项目、包、pytest、测试发现；
- 计划页：测试范围、预期、Mock、验收项；
- 工作台：执行、证据、结果；
- 问题/报告继续用现有页面。

“测试发现”是项目/计划里的动作，不新增页面结构。

### D11 AI 只输出选择单，服务端生成 Case

AI 不再生成完整 Case，只输出内部选择草稿：

```json
{
  "schema_version": "aitest.test-selection/1.0",
  "goal": "验证订单创建、取消、退款",
  "selections": [
    {
      "acceptance_item_ids": ["AC-ORDER-01"],
      "scope": {"kind": "file", "value": "pkgA/tests/test_order.py"},
      "expected": "all_pass",
      "mock_scope": "unknown",
      "rationale": "覆盖订单创建与取消"
    }
  ]
}
```

说明：

- `1.0` 是 GeneratedContent 的内部草稿格式，不是新的公共业务合同；
- 阶段 A/B 的 `kind` 只支持 `file`、`dir`、`marker`；
- 单个 `node` 选择放到阶段 C；
- 服务端校验 scope 存在于 Inventory；
- 服务端生成 Case ID、修订、内容摘要；
- 写入 `inputs`、`steps`、`verification_method`、`links`；
- 不存在、空 scope、验收项无链接：拒绝发布。

AI 仍然写预期，但预期写在选择项上，不写整个 Case 结构。

### D12 多包按包隔离执行

每个测试范围单独启动 pytest：

```text
python -m pytest
  --import-mode=importlib
  --rootdir=<package-root>
  --junitxml=<workdir>/evidence/pytest.xml
  <scope>
```

规则：

- 一个 scope 一个 pytest 进程；
- 使用 `--import-mode=importlib` 避免同名测试模块冲突；
- `--rootdir` 指向包根，不依赖当前目录；
- 一个 prepare 只绑定一个解释器；
- 不把多个包的测试塞进一个 pytest 进程。

多解释器项目在阶段 A/B 先按包拆成多次 run，不做项目级自动聚合；项目级聚合放到阶段 C。不要为了首版同时解决多解释器和跨包报告而增加调度复杂度。

### D13 JUnit 附件有大小预算，原始证据优先

- JUnit XML 压缩保存；
- 设置单附件大小上限；
- 超限时保留：完整摘要、失败节点、每个失败测试的类型/消息/堆栈前 N 行、原文件摘要和引用；
- 原始 stdout/stderr 仍按现有证据规则保存；
- 截断必须标 `truncated`，不能当完整证据；
- 派生结果不替代原始证据。

### D14 失败必须可定位，不能只写“失败”

这是本设计的硬要求。发现问题所在，不是只给一个红色状态。

每条失败分三层：

| 层 | 含义 | 是否证据 |
| --- | --- | --- |
| `failure_frame` | 断言/异常实际发生的位置，通常是测试代码 | 是，来自 JUnit/traceback |
| `suspect_source_frame` | traceback 中最后一个**项目源码、非测试、非 fixture** 的帧 | 是，但只标“可疑位置”，不证明根因 |
| `root_cause_hypothesis` | AI 对根因的解释 | 否，阶段 B 可选，只是候选 |

JUnit 每条失败至少提取：

- `node_id`；
- `classname` / `name`；
- `file` / `line`（JUnit 有则用）；
- `failure@type` / `failure@message`；
- stack trace；
- `system-out` / `system-err` 中的该测试片段；
- 失败类别：断言失败、setup/teardown 错误、收集/导入错误、超时、进程异常。

如果 JUnit 缺少位置：

- 解析 Python traceback；
- `failure_frame` 取异常发生的帧；
- `suspect_source_frame` 取最后一个项目源码帧，排除测试目录、fixture、venv、site-packages；
- 核对文件确实存在于源码快照；
- 找不到时写 `location_unknown` 和解析依据，不猜路径。

问题草稿必须包含：

- 实际失败测试列表；
- 每个测试的失败类型、`failure_frame`、`suspect_source_frame`、函数名；
- 断言消息或错误消息；
- 预期/实际（能从断言消息提取则填，否则写 unknown）；
- 复现命令、node ID、环境、源码身份；
- JUnit、stdout、stderr 证据引用；
- 同一签名簇合并到一个问题，但测试逐条列出。

报告和面板必须能展开到：

```text
scope
  -> testcase
      -> failure type
      -> failure_frame
      -> suspect_source_frame (or location_unknown)
      -> message
      -> evidence
```

不允许：

- 把多个失败压成一句“运行失败”；
- 把测试断言行冒充产品源码根因；
- 用 AI 根因假设替代原始 traceback；
- 找不到位置时编造文件/行号；
- JUnit 缺失或截断时仍判通过；
- 测试数少于 Inventory 预期时仍判完整；
- 全部测试 skipped 仍判通过；
- pytest 退出码与 JUnit 结果冲突时仍判通过。

### D15 选择完整性只做“可见”，不做复杂证明

计划发布前检查：

**阻止发布：**

- scope 不存在于 Inventory；
- scope 没有任何测试；
- 选择项没有验收项链接。

**警告但允许发布：**

- 某个验收项没有选中任何 scope；
- 选中测试数明显少于 Inventory；
- 选中范围里跳过比例过高。

规则：

- 不自动补选；
- 不自动分组；
- 不声称“已覆盖全部业务”；
- 未选测试、空验收项、跳过比例写入报告；
- `full` 档位才要求完整覆盖，阶段 A/B 只做 `on_demand`。

这是可见性检查，不是覆盖证明。

## 4 端到端流程

```text
选择项目
  -> 源码快照/项目分析
  -> discover_tests
       -> Test Inventory（绑定快照）
       -> AI 只看到树形投影（包/目录/文件/计数/样例）
  -> AI 输出选择单（验收项 + scope + expected + mock_scope）
  -> 服务端生成 Case（范围 + 预期 + Mock + 验收项）
  -> 用户评审/修改/确认
  -> 冻结计划
  -> 物化副本 + 每个 scope 单独 pytest
  -> 原始 stdout/stderr + JUnit
  -> JUnit 展开测试结果
  -> 失败定位（测试、类型、文件:行号、消息、堆栈）
  -> 验收项级独立核验
  -> 证据/判定
  -> 失败签名簇 -> 问题草稿（内部列失败测试）
  -> 确认问题 -> 修复 -> 回归 -> 关闭
  -> 报告
  -> 本地导出
```

## 5 阶段 A：发现与执行闭环

### 5.1 目标

让多包项目可以：

1. 发现真实测试；
2. AI 选择真实范围；
3. 冻结计划；
4. 继续复用现有 L1 源码检查；
5. 物化副本执行 pytest；
6. 保存原始输出和 JUnit；
7. 解析测试结果；
8. 做验收项级独立核验；
9. 生成基础报告。

阶段 A 只支持 `on_demand`，不支持的 `full`；报告明确“L3 未执行、Mock 未核验、依赖影响未计算”。

阶段 A 继续复用现有：

- `TemplatePack` 与 `RuleVersion`：计划仍绑定模板、规则和断言依据；
- L1 源码检查：报告分列 L1/L2，L3 标未执行；
- HTTP workflow / trace：链路检查仍是插件能力，不重做、不删除；
- `GeneratedContent` / AI 草稿：AI 分析只作为候选和假设，不与 Attempt、Evidence 混存；
- `CaseLink`：测试范围仍关联验收项、模块、环境。

阶段 A 不创建问题记录。失败测试只展示失败详情、JUnit 节点和证据，并提供“复制失败摘要”；完整问题草稿、确认、修复、回归、关闭从阶段 B 开始。

### 5.2 用户流程

1. 选择项目。
2. 点击“分析项目”。
3. 点击“发现测试”。
4. 选择目标。
5. AI 生成测试范围计划。
6. 用户评审/修改/确认。
7. 发布计划。
8. 准备执行。
9. 逐范围执行。
10. 查看测试结果、证据、未验证项。
11. 生成基础报告。

### 5.3 后端流程

```text
analyze_project
  -> source_snapshot
  -> project_understanding

source_checks (L1)
  -> 复用现有语法/加载/最小启动检查
  -> 与 L2 pytest 分列

discover_tests
  -> TestInventory（文件级摘要，不存全量 node ID）
  -> 文件/目录/marker/测试数/收集错误
  -> AI 只看到树形投影（包/目录/文件/计数/样例）

generate_draft (draft_kind=test_selection)
  -> AI 输出选择单：验收项 + scope + expected + mock_scope + rationale
  -> scope 只支持 file/dir/marker
  -> 服务端校验 scope 存在于 Inventory
  -> 服务端生成 Case（ID/修订/摘要/inputs/steps/links）
  -> 不存在/空 scope/无验收项链接：拒绝发布
  -> 验收项无范围/漏选测试/跳过比例高：警告并写入报告

save_case / save_acceptance / publish_plan
  -> 冻结计划

prepare_run
  -> 物化副本
  -> 解析解释器
  -> pytest 可用性检查

start_run / execute_step
  -> 每个 scope 单独进程
  -> python -m pytest --import-mode=importlib --rootdir=<package-root> --junitxml

collect
  -> stdout/stderr
  -> JUnit 附件（压缩 + 大小预算）
  -> 失败节点、文件、行号、类型、消息、堆栈、失败类别

verify_pending
  -> JUnit 解析
  -> 测试结果
  -> failure_frame + suspect_source_frame
  -> 验收项独立核验

create_report
  -> 基础报告
  -> scope -> testcase -> failure type -> failure_frame -> suspect_source_frame -> evidence
```

### 5.4 数据与合同

新增/调整：

1. **`discover_tests` 动作**
   - 只读；
   - 不创建业务记录；
   - 返回 Inventory 摘要和 AI 投影。

2. **Test Inventory 派生缓存**
   - `inventory_id`；
   - `source_snapshot_id`；
   - `pytest_version`；
   - `summary`：文件数、测试数、失败收集数；
   - `files[]`：`path`、`test_count`、`markers`、`collection_error`；
   - `collection_errors[]`；
   - `digest`；
   - 不保存全量 node ID。

3. **Test Inventory 投影**
   - AI 不接收全量 node ID；
   - 只接收树形投影：包/目录/文件/测试数/marker 统计/少量文件样例；
   - 服务端只校验 scope 路径和测试数，不展开 node ID 列表；
   - 实际 node ID 由 JUnit 执行结果给出；
   - 投影有摘要，绑定 Inventory 修订。

4. **`aitest.test-selection/1.0`**
   - 复用现有 `generate_draft`，增加 `draft_kind=test_selection`，不新增生成动作；
   - AI 只输出验收项 + scope + expected + mock_scope + rationale；
   - 阶段 A/B 的 scope 只支持 `file`、`dir`、`marker`；
   - 服务端验证 scope 存在、验收项链接完整；
   - 服务端生成 Case、ID、修订、摘要、`inputs`、`steps`、`links`；
   - AI 不写 Case ID、不写 node ID 列表、不写执行入口。

5. **`entry_type = "pytest"`**
   - 使用现有模板字段；
   - 不新增模板。

6. **执行附件**
   - `ExecutionCollectionResult` 增加 `artifact_refs`；
   - 或 `Attempt` 增加 `artifact_refs`；
   - JUnit 使用通用 `artifact` 证据类型，媒体类型标记 `application/xml; profile=junit`；
   - 不新增 pytest 专用证据类型，避免以后 unittest/覆盖率报告重复扩展；
   - JUnit 压缩保存，超限标 `truncated`，原始 stdout/stderr 优先；
   - 具体字段由架构分册确认。

7. **pytest 核验**
   - JUnit 解析为派生结果；
   - 测试结果映射 `passed/failed/skipped/error`；
   - 独立核验读取验收项级依据。

8. **失败定位**
   - JUnit `testcase` 的 `classname`、`name`、`file`、`line`；
   - `failure@type`、`failure@message`、stack trace、`system-out`、`system-err`；
   - 失败类别：断言失败、setup/teardown 错误、收集/导入错误、超时、进程异常；
   - `failure_frame`：异常发生帧；
   - `suspect_source_frame`：最后一个项目源码、非测试、非 fixture 帧；
   - 阶段 A 不做 AI 根因假设；阶段 B 可选，且只作候选；
   - JUnit 缺位置时解析 traceback，核对文件存在于源码快照；
   - 找不到写 `location_unknown`，不猜；
   - 失败测试数少于 Inventory 预期时标不完整，不判通过。

### 5.5 面板

- 项目页：显示包、测试文件、pytest 版本、发现按钮。
- 计划页：显示测试范围、测试数、预期、Mock、验收项。
- 工作台：按范围显示进度；展开后显示每个测试结果。
- 结果页：断言通过/失败/跳过/错误；独立验证状态；证据。
- 失败详情：测试节点、失败类型、`failure_frame`、`suspect_source_frame`、消息、堆栈、预期/实际、证据。
- 点击失败位置：优先打开 `suspect_source_frame`；没有时打开 `failure_frame`；都不能定位时显示 `location_unknown` 和解析依据，不猜路径。
- 失败范围：显示该范围全部失败测试；阶段 B 支持按失败签名拆分/合并问题。

不出现：

- 分组确认；
- 包选择必填；
- 手工 wrapper；
- 复杂配置。

### 5.6 阶段 A 验收

必须通过：

1. 单包项目发现/计划/执行/报告。
2. 多包项目：两个包、两个测试文件、同名函数。
3. 通过、失败、跳过、收集错误、超时。
4. JUnit XML 可重读，原始 stdout/stderr 可重读。
5. 不修改被测仓库。
6. 模型关闭时手工选范围并执行。
7. 重复执行同一意图不重复启动。
8. 中断后可恢复，未知副作用不自动重放。
9. 没有独立核验时显示“未验证”。
10. L1 源码检查结果与 L2 pytest 结果分列，L1 通过不替代 L2。
11. 计划仍绑定模板、规则和断言依据；AI 分析只出现在草稿/假设区。
12. 链路检查沿用现有 HTTP workflow / trace，不被 pytest 改造破坏。
13. 阶段 A 不创建问题记录，只提供失败详情与复制摘要。
14. 报告明确 L3、Mock、依赖未完成。
15. 断言失败：报告能给出具体测试、`failure_frame`、`suspect_source_frame`、断言消息和证据。
16. 导入/收集错误：能给出错误文件、错误类型和收集阶段；`suspect_source_frame` 指向导入位置。
17. setup/teardown 错误：能区分夹具错误与断言失败。
18. 多失败范围：所有失败测试逐条列出，不压成一句“运行失败”。
19. 无位置信息：标 `location_unknown` 和解析依据，不编造文件/行号。
20. JUnit 缺失/截断/测试数少于 Inventory 预期：标不完整，不判通过。
21. 同名测试模块：`--import-mode=importlib` 后两个包都能执行，不互相污染。
22. 选择完整性：不存在/空 scope/无验收项链接阻止发布；验收项无范围、漏选测试、跳过比例高只警告。
23. 全部测试 skipped：标未完成，不判通过。
24. pytest 退出码与 JUnit 结果冲突：标不完整，不判通过。
25. 阶段 A 不展示 AI 根因结论；如需根因假设，阶段 B 单独标为候选。

不声称：

- L3；
- Mock 真实性；
- 问题闭环；
- 依赖影响；
- 完整通过。

## 6 阶段 B：问题、追溯与报告闭环

- 失败签名簇 → 问题草稿（内部列全部失败测试）；
- 确认 → 修复 → 回归 → 关闭；
- 验收项 → 范围 → 测试 → 证据 → 问题追溯；

- 报告/导出；
- 面板投影修复；
- 模型不可用降级。

### 6.2 用户流程

1. 查看测试结果。
2. 失败签名簇自动生成问题草稿，内部列失败测试、位置和证据。
3. 用户确认问题，必要时拆分/合并。
4. 开发修复。
5. 用户选择回归范围。
6. 重新执行。
7. 新证据满足条件后关闭。
8. 生成报告。
9. 本地导出。

### 6.3 后端流程

复用现有：

- `SavedDefectManagement`；

- `SavedExportService`；
- `DeliveryVerificationReader`；
- `CaseLink`；
- `ExecutionFacts`；
- `ReportSnapshot.issue_revisions`。

补充：

1. **问题草稿**
   - 从失败签名簇生成，而不是每个测试一条，也不是整个 scope 一条；
   - 内部列全部受影响测试：node ID、失败类型、`failure_frame`、`suspect_source_frame`、函数、消息、堆栈摘要；
   - 关联验收项、case、run、attempt、JUnit 节点、证据；
   - 字段按现有功能文档补齐：标题、级别、影响范围、验收项、用例/步骤/尝试、版本与环境、复现步骤、预期/实际、频率、证据、事实/假设、责任人；
   - 预期/实际能从断言消息提取则填，不能则写 `unknown`；
   - 失败位置来自 JUnit 或 traceback；找不到写 `location_unknown`；
   - 只创建 `draft`，不自动确认；
   - 支持按失败签名聚合，也支持用户拆分/合并；
   - AI 根因假设单独字段，标为候选，不写入证据。

2. **追溯**
   - `CaseLink.acceptance_item_ids` 已有；
   - 报告冻结 `issue_revisions`；
   - 导出读取精确修订；
   - 修复面板 `issue_revisions` 数组解析 bug；

   - 扫描测试源码中的 `unittest.mock`、`pytest-mock`、fixture；

5. **模型不可用**
   - 手工选择范围；
   - 手工填写预期；
   - 执行、证据、报告、问题、导出继续可用；

## 7 阶段 C：L3、依赖与多框架

### 7.1 目标

- L3 完整业务流；

1. 报告分层显示 L1/L2/L3。
2. 用户选择业务目标。
3. 创建 L3 case：同一业务对象、完整步骤、最终核验。
4. 变更后计算直接影响/间接受影响模块。

6. 用户调整并确认。
7. 多框架项目选择 pytest/unittest。

1. **L3**
   - 复用 `CaseLayer`、`StepLevel`、`SavedManualEvidenceCapture`、`SavedBusinessVerification`；
   - 补分层统计；
   - 补同一业务对象校验；

   - 接线 `regression_graph.py`；
   - 读取 `dependency_set` 精确修订；
   - 匹配 `CaseLink.module_ids`；
   - 生成回归建议；
   - 记录人工增减理由。

3. **多框架**
   - `entry_type = "unittest"`；
   - 独立发现/执行/核验；
   - 不新增业务模板。

4. **多解释器聚合**
   - 每个包/解释器一个 run；
   - 项目级报告按验收项、包、run 聚合；
   - 不把不同解释器的结果混成一次 run。

5. **基线对比**
   - 记录同 scope 的上一次结果；
   - 新 run 对比新增失败/既有失败/已修复；
   - 默认只为新增失败生成问题草稿；
   - 既有失败仍展示，不制造新问题噪音。

6. **定向 node ID**
   - 在文件/目录范围之外，允许手工补充单个 node ID；
   - 必须存在于 Inventory 或重新收集确认；
   - 不把 node ID 作为默认计划粒度。

7. **服务/数据库**
   - 服务启动/健康检查；
   - 数据库迁移/测试数据；
   - 环境失败保留证据，不伪造通过。

### 7.4 阶段 C 验收

## 9 验收与验证计划

### 9.1 阶段 A

- 多包夹具：`pkgA/tests/test_order.py`、`pkgB/tests/test_order.py`、同名测试函数。
- AI 选择单只能选 Inventory 中存在的 scope；不存在的 scope 被拒绝。
- 空 scope、无验收项链接被拒绝；验收项无范围、漏选测试、跳过比例高只警告。
- AI 不输出 Case ID；Case 由服务端生成，字段和链接一致。
- 通过、失败、跳过、收集错误、超时。
- 断言失败夹具：在已知测试文件/行号触发 `AssertionError`，报告必须给出 `failure_frame`；若 traceback 有产品源码帧，`suspect_source_frame` 必须指向产品源码，否则 `unknown`。
- 导入/收集错误夹具：报告必须给出错误文件、错误类型和收集阶段。
- setup/teardown 错误夹具：必须区分夹具错误与断言失败。
- 多失败夹具：同一文件 3 个失败，必须逐条列出，不能压成一句“运行失败”。
- 无位置夹具：JUnit/traceback 都没有位置，必须标 `location_unknown`，不能编造。
- 阶段 A 不出现 AI 根因结论；只显示失败事实和可疑源码位置。
- JUnit 截断/测试数少于 Inventory：必须标不完整，不能判通过。
- JUnit 可重读，stdout/stderr 可重读。
- 不修改源目录。
- 模型关闭时手工范围。
- 重复意图不重复执行。
- 中断恢复。
- 报告显示未验证项。

### 9.2 阶段 B

- 失败签名簇 → 问题草稿，内部列每个失败测试的 `failure_frame`、`suspect_source_frame`、类型、消息、证据。
- 同签名合并，不同签名分开。
- 确认 → 修复 → 回归 → 关闭。
- 旧证据不能关闭。
- `location_unknown` 在问题、报告、导出中保留。
- AI 根因假设只作候选，不进入证据。
- 报告/导出追溯。
- Mock 未核验。
- 模型关闭。
- 面板投影。

### 9.3 阶段 C

- L3 完整业务流。
- 分层统计。
- 依赖影响/回归建议。
- unittest。
- 服务/数据库。

## 10 评审决定（采用建议）

以下 12 项按建议定稿，后续同步项目文档时照此执行。

| 问题 | 决定 | 理由 |
| --- | --- | --- |
| AI 输出 | **selection-first**：AI 只输出验收项 + scope + expected + mock_scope + rationale；服务端生成 Case；选择草稿是内部 GeneratedContent 格式 | 减少编造、降低 token、统一 Case 结构；不增加公共 Schema |
| 范围粒度 | 阶段 A/B 默认**测试文件**和**测试目录/包**；`marker` 可选；单 node ID 放到阶段 C。一个 case 一个范围 | 覆盖大项目主场景，避免计划爆炸；node ID 不进入首版复杂度 |
| `test_target` 是否显式 | **不新增 PlanProposal 1.2**；`inputs[0]` 承载测试范围，`steps` 一步，报告派生 `test_target`。只有 UI 评审明确要求区分时才加 1.2 的单字段 `test_target` | 复用现有合同，减少 Schema/测试/文档变更；`package` 永远不做字段 |
| 独立核验粒度 | **每个验收项至少一条独立核验**；case 可共享；没有独立核验的 case 显示“未验证” | 大项目无法逐测试写独立核验；验收项是业务追溯的最小单位 |
| 问题粒度 | **一个失败签名簇一个问题草稿**；同签名合并，不同签名分开；内部列全部失败测试 | 避免 ImportError 产生几十个重复问题，也不把不同根因混成一个 |
| 多包执行 | 每个 scope 单独 pytest 进程；`--import-mode=importlib`、`--rootdir=<package-root>`；一个 prepare 一个解释器；多解释器项目在阶段 C 才做项目级聚合 | 同名测试模块、src 布局不互相污染；首版不同时解决多解释器调度 |
| JUnit 证据类型 | 使用**通用 `artifact`**，媒体类型 `application/xml; profile=junit`；不新增 pytest 专用证据类型；压缩保存，超限标 `truncated` | 以后 unittest、覆盖率、日志包可复用同一通道 |
| 阶段 A 是否包含问题草稿 | **不包含完整问题记录**。阶段 A 只展示失败测试详情、JUnit 节点、证据，并提供“复制失败摘要”；问题草稿、确认、修复、回归、关闭从阶段 B 开始 | 阶段 A 聚焦发现/执行/证据/核验；避免半成品问题字段进入正式记录 |
| 失败定位 | **三层**：`failure_frame`、`suspect_source_frame`、可选 `root_cause_hypothesis`；前两层是证据，AI 假设只是候选；找不到写 `location_unknown` | 只写“失败”无法修复；测试断言位置不等于产品根因 |
| 选择完整性 | 不存在/空 scope/无验收项链接阻止发布；验收项无范围、漏选测试、跳过比例高只警告 | 可见性检查，不做自动补选或覆盖证明；on_demand 允许部分覆盖 |
| 包与模块映射 | 包名不替代模块；只映射到项目已登记模块和 `CaseLink.module_ids`；未登记时标“未登记模块/缺口”，不自动用 AI 分组补全 | 模块/依赖是 P1-FR01 的用户登记事实，AI 分组不能成为权威 |
| `full` 档位 | **阶段 A/B 只支持 `on_demand`**；`full` 需要完整覆盖契约、L3、独立核验和分层统计，放到阶段 C 完成后启用 | 避免用 pytest 子集冒充完整通过 |

### 10.1 已移除或降级的过度设计

| 原设计 | 处理 | 原因 |
| --- | --- | --- |
| Inventory 保存全量 node ID | 改为文件级摘要 + 计数 + 错误 + 摘要 | 大项目列表巨大；scope 执行不需要全量 node ID；JUnit 会给实际节点 |
| 阶段 A/B 支持单 node ID 选择 | 降到阶段 C | 首版先文件/目录，减少计划和参数复杂度 |
| 阶段 A/B 做多解释器项目级聚合 | 降到阶段 C | 首版一次 run 一个解释器；不引入跨包调度 |
| 选择完整性阻止所有未覆盖 | 只阻止不存在/空 scope/无验收项链接；其余警告 | 避免把 on_demand 做成 full 门禁；用户可能只想测一部分 |
| 阶段 A 生成 AI 根因结论 | 删除；阶段 B 可选且只作候选 | 根因不能被 traceback 自动证明；先显示失败事实和可疑位置 |
| 每个测试一个问题 | 改为签名簇 | 避免问题爆炸，同时不把不同根因混在一起 |
| 每个测试一条独立核验 | 改为每个验收项一条 | 大项目不可行；验收项是业务追溯单位 |
| 新增第七个模板 | 复用六个模板 + `entry_type` | 模板是业务提醒，执行框架是适配器 |
| 新增 PlanProposal 1.2 | 复用 `inputs`；必要时只加 `test_target` | 减少合同/Schema/测试变更 |
| 核心桥接器输出 JSON | 原生 pytest + JUnit 附件 | 保留原始证据和执行入口合同 |
| 复杂失败消息归一化 | 只归一化临时路径/地址/随机 ID/时间戳 | 过度归一化会合并不同 bug |
| 阶段 A/B 做基线对比 | 放到阶段 C | 依赖历史结果和稳定 Inventory |
| 自动补选/自动分组 | 不做 | 分组不准确；选择必须可解释、可评审 |

## 11 实施顺序

评审通过后：

1. 同步项目文档和 Schema。
2. 实现 Test Inventory（文件级摘要）+ `discover_tests` + AI 投影。

6. 实现 pytest 结果解析、失败类别、`failure_frame`、`suspect_source_frame`、traceback 定位。
7. 实现验收项级独立核验。
8. 实现基础报告、失败详情、选择完整性警告。
9. 阶段 A 验收。
10. 实现失败签名簇问题草稿、追溯、Mock 候选、导出、面板修复。
11. 阶段 B 验收。
12. 实现 L3、依赖/回归、unittest、多解释器聚合、基线对比、node ID、服务/数据库。
13. 阶段 C 验收。

每一阶段结束都要更新：

- 修改日志；
- 验证批次；
- `docs/现状.md`；
- `tests/acceptance/p1/status.json`（只有真实证据才登记）。
