# 0.4.3 计划、执行、独立核验与报告操作

> 当前鉴权、动态对象 ID 与安装包版本见[0.4.4 增量指南](0.4.4-鉴权与动态对象核验.md)。本文保留基础操作步骤，文中的无凭据/固定 ID 限制仅描述 0.4.3。


此版增加按步骤填写的入口、从准确已保存记录准备运行、宿主独立 HTTP 查询登记与默认解析。运行结果仍由核心产生；未完成步骤如实出现在报告中。真实 Trae 安装、人类确认、物理故障恢复与完整一期验收尚未完成。准确检查范围见[本批记录](../../validation/p1-workflow-20261015/README.md)，当前状态见[项目现状](../../现状.md)。

## 安装与前提

核心 wheel：`dist/ai_test_component-0.4.3-py3-none-any.whl`；扩展：`integrations/trae/dist/aitest-trae.vsix`。在安装核心的 Python 3.13 环境安装 wheel，在 Trae 安装 VSIX，配置独立用户数据工作空间和明确项目编号。已有核心须安全排空后重启，不能让旧核心加载新界面后误认为配置已生效。

项目创建与真实 Python 载体登记沿[0.4.2 操作步骤](0.4.2-项目创建与Python环境登记.md)。开始前须保存项目、源码绑定、环境、验收范围、用例，并通过 `analyze_project` 的 `purpose=prepare` 固定选定源码。绑定和环境仍须核心原生确认，登记解释器不代替真实环境观察。

范围与用例正文目前仍通过既有受控 JSON 入口保存（save_acceptance / save_case）；本版没有把全部计划编辑器、数据导入和错误修复做成图形向导。已有记录可通过 query 读取，不能用模型猜测的修订/摘要替代回执。

## 独立 HTTP 核验登记

在宿主维护独立配置文件，填写真实地址。示例的地址只说明形状，不能原样用于验收：

```json
{
  "schema_version": "aitest.business-queries/1",
  "queries": [{
    "query_method": "demo:read-order",
    "target_deployment_ref": "deployment-v1",
    "url_template": "https://your-test-service.example/orders/{business_object_id}",
    "object_id_field": "object_id"
  }]
}
```

将绝对路径填入机器级设置 `aitest.businessQueriesFile`；CLI 启动核心时使用环境变量 `AITEST_BUSINESS_QUERIES`。配置只在核心装配时读取，修改后须安全重启。不从被测源码自动发现，不接受命令覆盖地址。登记名格式为 `<project_id>:<名称>`，两段均非空且不含冒号。当前入口仅登记无需凭据的独立 GET；需要鉴权、数据库和纯函数核验的项目仍有适配缺口，不可声称已经支持。

该用例的 `assertion_basis.text` 使用明确的结构化依据，原文完整摘要仍通过现行依据规则生成和确认：

```json
{
  "schema_version": "aitest.business-query-basis/1",
  "business_object_id": "order-1",
  "query_method": "demo:read-order",
  "target_deployment_ref": "deployment-v1",
  "expected_facts": {"paid": true},
  "query_interval": "configured",
  "deadline_condition": "immediate"
}
```

对象标识必须属于本次实际操作；此版不从执行输出自动提取动态对象 ID。应在操作前明确稳定对象标识与独立预期，不能用刚看到的实际值倒填预期。自由文本不会被猜成核验规则。查询响应须是完整 JSON 对象且 `object_id` 与原对象相同；不匹配、无结果、查询错误分别留存。轮询可显式选择既有 `poll_interval_ms:N` / `poll_deadline_ms:N`，仍受核心上限约束。

## 面板操作顺序

每一步先点“准备本步骤操作”，核对下方输入，再点“请求核心确认并提交”。只有核心真实窗口里的确认才能授权；面板不会自动连点、代签或根据 HTTP 成功重算业务通过。

| 顺序 | 输入和操作 | 回执与下一步 |
| --- | --- | --- |
| 确认依据 | confirm_basis：准确用例/依据修订、依据原文摘要 | 保存 confirmation_id、case_id、basis_revision、confirmed_at_commit；这是依据确认，不是执行或核验 |
| 1 发布计划 | 计划编号/新修订、已保存范围和完整用例 JSON、模板版本数组、档位与驱动 | 只有 published=true 才发布成功；报告需要冻结的真实模板版本，不应遗漏模板输入 |
| 2 准备运行 | 项目/绑定/计划/源码快照/环境的准确修订、持久 client_id、本次 prepare_request_id、执行入口、所选用例和准确确认引用 | 核心读取完整记录并生成 PreparedRun；status=prepared 才能登记；blocked/needs_reprepare 必须先处理原因 |
| 3 登记运行 | prepared_run_id，首写修订 0 | 回执提供真实 run_id 与步骤列表；登记没有执行任何步骤 |
| 4 解析步骤动作 | run_id、step_id 与本次执行稳定意图 | 返回 execution_action_id；核对解析出的动作与源码/环境 |
| 5 授权步骤 | 同一步骤、动作编号，沿用第 4 步意图 | 核心展示准确保存材料并确认；授权不等于执行 |
| 6 执行步骤 | 同一动作、步骤和第 4 步意图 | 查看真实 Attempt、退出事实、完整性、依赖和 execution_facts；未知结果不能直接重跑 |
| 7 独立核验 | 新的核验意图，run_id、step_id、当前 attempt_id、准确 base_snapshot_commit_id | 从准确 Case 依据解析并独立 GET，先保存查询材料，再发布 Verification；matched 不等于整轮通过 |
| 8 保存报告 | 新报告意图、run_id、report_id、关联问题编号数组 | 保存不可变报告修订，未执行/未验证范围和问题如实保留 |
| 9 导出报告 | report_id、markdown_summary 或 evidence_bundle、明确复核编号数组 | 保存实际制品与摘要；缺附件仍登记缺口，不用“导出成功”表示证据齐全 |

解析/授权/执行三步必须沿用同一业务意图；切到其他动作时表单清空意图，避免误复用。回执超时或丢失时保留原意图/准备编号，先取回原结果；只有明确的新尝试才用新意图。跨工作空间或项目变化会清空输入，旧排队操作不得进入新上下文。

“从本次成功回执填入记录编号”只复制回执明确给出的编号，不选择步骤、不自动提交、不推断通过。登记运行后从返回步骤列表选定准确步骤；在宿主设置更新当前 runId 后可读取运行/面板 DTO。

执行入口 JSON 示例（参数必须适用于实际项目，不能猜入口）：

```json
{
  "registered_entry": "python-main",
  "entry_arguments": ["main.py"],
  "cwd_mapping": "workdir:.",
  "allowed_env_keys": [],
  "secret_refs": [],
  "test_config_ref": "your-saved-test-configuration",
  "adapter_versions": {"command": "command/1.0"}
}
```

便捷表单让核心生成 resolved_input_digest，不要求用户填写观察摘要。确认引用数组仅引用真实回执；没有确认填 `[]`，不会获得有效验证资格。运行依赖、必测范围、来源、证据和判定门禁保持不变。

## 仍须现场验证

组件链包含真实 Python 子进程、独立 HTTP 读取、持久记录和重启回读；受控人类事件仍使用明确夹具；两条组件主链已通过，其中一条使用真实宿主登记 venv 及实际环境解析器。报告和 ZIP 字节均在重启后回读一致。它不能代替真实 Trae、完整全部步骤、鉴权目标、纯函数核验、动态 ID、运行中修订和恢复的产品验收。三个期次验收登记不因本次实现或测试自动改为 verified。
