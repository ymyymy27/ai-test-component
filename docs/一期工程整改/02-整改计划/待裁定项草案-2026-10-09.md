## 1. `cwd_mapping` 的解析语法

现状：`ExecutionSourceBinding.cwd_mapping` 是 `str`（min_length=1），合同只说"工作目录映射"，未定语法；start 需要在固定 workdir 内解析出实际工作目录。

- 方案 A（推荐）：形如 `workdir:<relative>` 的受限前缀语法，`relative` 必须是安全相对路径（非绝对、不含 `..`、不含盘符），解析结果必须落在 workdir 内。优点：显式、可校验、与既有"物化目标不得经过链接"口径一致。
- 方案 B：允许 `{project_root}`/`{workdir}` 占位符的模板串，解析后再做同一套越界校验。表达力更强，但需要定义占位符集合与转义。
- 影响面：字段语义（AB-001 §3.4 需补语法）、start 解析实现与反例（越界/绝对/盘符/链接祖先拒绝）、B 侧生成夹具。

## 2. `entry_arguments` 与用例输入的合并

现状：`entry_arguments` 是冻结的字符串元组；用例输入的代入规则未定。

- 方案 A（推荐）：**不代入**。`entry_arguments` 即最终参数序列，用例输入只作为计划/断言依据，执行命令始终是冻结序列。优点：零歧义、不可能被正文/模型拼成 shell。
- 方案 B：在冻结参数中允许 `{input:<name>}` 占位符，由用例输入展开；需要定义缺失/类型/转义与长度上限规则。
- 影响面：`resolved_input_digest` 覆盖内容、执行请求构造、反例（缺失输入、超长、注入字符）。

## 3. 适配器选择依据

现状：一个步骤可能对应命令/Python/HTTP/导入等适配器；`RegisteredEntryRef.adapter_kind` 需由某处决定。

- 方案 A（推荐）：由 `ExecutionSourceBinding.adapter_versions` 的**键**决定（当前唯一键即所选适配器），键多于一个时拒绝并要求重新 prepare。优点：与已冻结字段同源，不新增字段。
- 方案 B：在 `PreparedRun` 增加显式 `adapter_kind` 字段（需要 BC-001 版本提升与 B 侧实现）。
- 影响面：合同字段（方案 B）、prepare 校验、start 解析、默认装配注入。

## 4. 失败回执分类与按动作降级

现状：入口缺失/来源不符/环境未登记/物化失败都可能在 start 前发生；A-10 要求"按实际动作依赖降级"，但四类失败到错误码的映射未定。

- 方案 A（推荐）：全部映射为不可重试的**阻塞**（`SOURCE_BINDING_UNVERIFIED` / `CAPABILITY_DEGRADED` 视来源），并在运行事实中登记 `source_unverified` 缺口；只有"登记/查询/模板/本地保存"等不依赖该动作的能力保持可用。优点：与新实现的 `SourceBindingUnverified` 直接对应。
- 方案 B：区分"可重试的物化失败"（存储瞬时问题）与"不可重试的来源不符"，前者给 `retryable=true`。
- 影响面：错误码与 `next_step` 文案、A-10 动作级门禁、AC19/23 的失败回执证据。

## 5.（追加）`source_checks` 的期望摘要字段语义

现状（2026-10-09 复核，**已定性**）：全仓文档与接口合同检索 `SourceCheckRequest` / `expected_source_binding_digest` / `observed_source_digest` **零命中**——两个类型（请求与探针观察）是**代码内类型、无合同条目**；其中字段名 `expected_source_binding_digest` **复用了 [BC-001 第 6 节](../../接口对接/进行中/BC-001-PreparedRun/contract.md) 已定义术语**（那里指 C 在 start 计算的"期望→实际路径映射"摘要），而 [`_derive_state`](../../../src/aitest/application/execution/source_checks.py) 实际把它当作**来源内容摘要**与探针的单值 `observed_source_digest` 比较。因此这是**确认存在的口径/命名不一致**（同一术语两义），不是误读；`SourceCheckRequest` 目前**只有测试构造、无生产装配**，尚未产生线上误判。

- 方案 A（推荐）：把该内部字段改名（如 `expected_source_content_digest`）并注明它**不等于** BC-001 的 `source_binding_digest`；映射级比较继续由 start 准入（`admit_start` 的摘要重放核对）承担。
- 方案 B：保持名字与映射摘要含义，探针改为逐项返回期望→实际映射，`_derive_state` 改映射级比较。
- 影响面：字段注释/夹具；**接线前必须完成**（当前无生产构造点，改动成本最低）。

**裁定后的动作**：合同先行 → 改 `source_checks`/探针 → 补反例（摘要不符、映射缺项、单值 vs 映射混用）→ 再评估启动前来源核验的默认接线。



## 6.（追加）"解释器身份"与"实际可执行文件"的比较口径 —— **已对齐既有实现，无需新裁定**

结论（2026-10-09 复核）：[`source_checks._derive_state`](../../../src/aitest/application/execution/source_checks.py) 对解释器已有明确口径——`Path(expected_interpreter_ref).resolve() != Path(observed_interpreter_ref).resolve()` 即 `actual_interpreter_mismatch`。因此本会话的 `require_interpreter` 已改为**同一 `resolve()` 路径口径**，不自行发明"身份摘要"或字符串精确匹配（先前的逐字比较写法已修正）。

仅剩**数据来源**问题（非语义裁定）：冻结侧应取环境记录的 `EnvironmentRefFact.resolution.executable_path`，在解析器/默认装配接线时确定；届时两侧都按同一路径口径比较。
