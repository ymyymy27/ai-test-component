# 运营阶段 · 效果检测与数据采集

- 目的：定义"这个产品到底有没有效果"的可核对指标，并说明数据只能从哪些本地材料来。
- 前提：本产品**不收集用户数据**，没有遥测、没有上报接口、没有账号体系；所有指标由维护者在本地读取仓库与工作空间材料得出。
- 现状数字只在[项目现状](../../../现状.md)维护；本文件定义口径，不复制结论。

## 1 指标定义

| 指标 | 定义 | 数据口径 | 不能说明什么 |
| --- | --- | --- | --- |
| 验收通过率 | `verified` 项数 / 当期登记 AC 总数 | 逐项读 `tests/acceptance/p{1,2,3}/status.json` 的 `result`；`verified` 还须 `evidence.path` 非空且 `real_environment_verified=true` | 不等于产品可用度；不覆盖未登记范围；分母为 0 时不显示 100% |
| 测试节点 | pytest 收集或执行的用例节点数 | `pytest --collect-only -q` 的输出行数；执行结果取 JUnit XML 的 `tests` 属性 | 收集数不等于通过数；分块数字相加不等于全量 |
| 批次结果 | 一次验证批次的整体结论 | `docs/validation/<批次>/README.md` 的范围、提交、命令、退出码、失败与跳过、证据路径；以 JUnit/回执文件为准 | 单批通过不推广到同 FR 的其他 AC；历史批次不累加成"全量通过" |
| 失败簇 | 同一批次内按失败签名归并后的簇数 | 失败签名 = 异常类型 + 首个业务帧 + 所属测试模块；同签名多次失败计 1 簇，另记出现次数 | 簇少不代表质量好（可能只跑了少量节点）；面板里的"失败签名簇"是产品功能，不是运营指标 |
| 诊断状态 | 每个工作空间核心的就绪与依赖状态 | `doctor` 回执的 `status`（`READY`/`NOT_READY`）、`supported_actions`、`dependencies`；启动失败读 `core/startup-diagnostic.json`；恢复结论读 `diagnostics/recovery/` 的 `healthy/repaired/blocked` | `READY` 只说明核心可用；`unknown` 不能当健康 |

补充口径：

- 验收通过率按**期次**分开算，不跨期合并成"整体完成度"；一期 35 项、二期 9 项、三期 8 项的登记结构不同，分母不可互换。
- 只有 `verified` 计入分子；`not_verified`、`blocked`、`untested` 都不计入，也不因"接近通过"折算。
- 测试节点只统计当次真实执行的范围；中断、超时、未跑完按"未完成"记录，不按通过计。
- 批次结果的四种取值沿用验收登记：`passed`（退出 0 且失败逐条解释）、`failed`、`blocked`（环境/入口不可用）、`incomplete`（未跑完）。

## 2 数据从哪来

| 来源 | 具体位置 | 采集方式 |
| --- | --- | --- |
| 验收登记 | `tests/acceptance/p1|p2|p3/status.json` | 直接读 JSON；逐项字段 `result`、`evidence.path`、`real_environment_verified`、`unverified_reason` |
| 验收对账 | `tests/unit/test_acceptance_status.py`、`tests/unit/test_acceptance_status_phases.py` | 运行测试；失败即说明场景/预期与需求文本不一致 |
| 验证批次 | `docs/validation/<批次>/README.md` 与同目录回执、JUnit、`artifacts.json` | 逐批读 README 的"实际结果"与"边界"；制品核对看 `docs/validation/artifacts.json`（版本、sha256、scope） |
| CI 基本检查 | `.github/workflows/ci.yml` 的 `basic-checks`（Windows，20 分钟上限） | 读 Actions 运行结论与 artifact `pytest-windows`（JUnit XML，保留 14 天）；覆盖 contracts/architecture/recovery/acceptance/integration 与指定 unit |
| CI 夜间全量 | `.github/workflows/nightly.yml` 的 `full-python`（Windows，360 分钟上限，`-n 8 --dist loadfile`，默认 `develop`） | 读 Actions 运行结论与 artifact `pytest-full-windows`；定时为 02:00（Asia/Shanghai） |
| 发布制品 | `.github/workflows/release.yml` 的 tag 构建 | 读 `dist/*`、`integrations/trae/dist/*.vsix`、`SHA256SUMS`、`docs/validation/artifacts.json` |
| 运行时诊断 | `doctor` / `ensure-core` / `restart-core` 的 stdout JSON；`core/startup-diagnostic.json`；`core/connection-ledger.jsonl` | 直接执行命令并保存回执；不解析人读文本 |
| 恢复与维护 | `diagnostics/recovery/`、`maintenance/audit.jsonl` | 只读取证；`healthy/repaired/blocked` 原样记录 |

采集命令（本地，等价于 CI 口径）：

```powershell
aitest doctor --workspace "C:\本地用户数据\aitest"
python -m pytest --collect-only -q            # 收集节点数，不等于通过数
python -m pytest -p no:cacheprovider --import-mode=importlib -n 8 --dist loadfile -ra tests
```

## 3 采集边界

1. **本地优先**：指标全部由维护者在本地读文件、跑命令得出。仓库没有服务端、没有数据库、没有本地 HTTP 服务，也没有把指标写到远端的代码路径。
2. **无遥测**：源码中没有任何 telemetry/analytics 上报实现（`grep -ri telemetry src integrations` 只命中面板 `node_modules` 里的第三方依赖）。不自动发送崩溃、使用次数、功能点击或机器标识。
3. **凭据不外发**：报告、导出、诊断、备份都只接纳落盘前已过滤的字节；凭据正文不进配置、日志、面板、导出或上传。指标侧同样不采集任何凭据或凭据引用。
4. **源码不外发**：模型出站策略默认关闭源码片段，首次使用需显式确认；三期上传在平台合同确定前不实现，不存在"顺手把源码或证据传出去"的采集动作。
5. **指标可复算**：任何数字都要能由 `status.json`、批次 README、JUnit XML 或命令回执重算；无法复算的数字不写进汇报。
6. **CI 只跑仓库代码**：GitHub 托管的 Windows 运行器只检出本仓库、执行测试与构建；不接触用户工作空间，因此 CI 通过不能当作本地工作空间的诊断结果。

## 4 报告节奏

- **按批次，不按日**：每完成一个验证批次（定向/回归/全量/宿主/真实环境）写一份 `docs/validation/` 记录，并在其中给出该批的五项指标；没有批次就没有新指标。
- **按里程碑汇总**：M0 准备、M1 本地闭环、M2 真实宿主、M3 发布门禁、M4 交付验收各汇总一次，口径见[交付计划](../01-项目/03-交付计划.md#3-里程碑)。
- **不设日报/周报**：没有稳定流量与用户，按日统计只会制造噪声；也不设实时看板——仓库没有指标服务。
- **发布前一次总账**：以[验收台账](../05-测试验收/02-验收台账.md)与 `status.json` 对账后的数字为准，同时列出未验证项与失败簇，不做"通过率上升"式宣传。
- 报告必须同时写：批次名、提交、版本、命令或界面动作、节点数、耗时、退出码、失败与跳过原文位置、证据路径、未验证原因。

## 5 不采集什么及原因

| 不采集 | 原因 |
| --- | --- |
| 用户使用行为、功能点击、活跃时长 | 产品无遥测实现；内部工程工具也不需要此类指标 |
| 机器标识、用户名、绝对路径清单 | 与验收无关，且属于用户环境信息；导出材料只保留可移植相对路径 |
| 崩溃自动上报、后台心跳 | 无上报端点与账号体系；三期平台侧尚未实现，不得先行设计 |
| 被测源码正文、提示词与模型响应正文 | 源码默认不出站；模型响应只在本地用于确认，不作为指标原料 |
| 凭据、令牌、连接串 | 落盘前即过滤；任何指标都不得引用其正文 |
| 第三方分析脚本、广告或统计 SDK | 面板与扩展只依赖构建所需包，不引入分析 SDK |

原因归结为一条：**本产品不收集用户数据**。需要出站的能力（模型调用、三期平台上传）都是显式、按材料类别授权、可关闭的动作，不是后台采集。

## 6 偏差记录

| 位置 | 旧表述 | 现行事实 |
| --- | --- | --- |
| 部分汇报口径 | 把 `4 verified / 35` 说成"一期完成度 11%" | 这是**登记完成度**，不是功能完成度；31 项未 verified 中有 25 项未实测、5 项前提不足、1 项阻塞 |
| 历史全量记录 | "6,104 passed"当作当前全量 | 该数字只对应 2026-11-11 的提交；当前全量须重跑，收集数（6,167）不能替代通过数 |
| `ci.yml` 注释 | 把 6,104 节点的全量记为"2026-11-10" | [项目现状第 4 节](../../../现状.md#4-规模与门禁2026-11-12)记为 2026-11-11（1:14:58）；以现状与当次 JUnit 为准，注释日期不作指标时点 |
| `docs/validation/README.md` | 新批次命名 `p1-<主题>-<YYYYMMDD>/` | 2026-11-13/14 的实际批次为 `<YYYY-MM-DD>-p1-*`；按实际路径采集，不重命名历史批次 |
| 早期材料 | "面板/CI 会自动统计验收通过率" | 无此类代码；通过率需人工按 `status.json` 复算 |
| 三期相关材料 | 暗示上传回执可作运营指标 | 三期全部 `untested`，平台合同未定；不得以本地桩件或模拟回执产生指标 |
