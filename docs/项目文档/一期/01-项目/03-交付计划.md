## 5 关键路径与依赖

```text
D1 需求 → D2 契约 → D4 技术 → WP2 运行时 → WP4 宿主/面板
                                      ↘ WP5 适配器 → WP8 验收 → M4
```

| 依赖 | 前置 | 断裂后果 | 可并行 |
| --- | --- | --- | --- |
| 契约稳定 | D1/D2 | 扩展与 CLI 各说一套，结论不可对账 | 文档措辞与示例 |
| 运行时可靠 | WP2 | 运行目录、锁、备份不可信 | 面板文案与错误态 |
| 宿主可用 | WP4 | 只有 CLI 证据，M2 不成立 | 适配器与备份演练 |
| 真实证据 | WP5/WP8 | 无证据的条目只能登记 `untested` | 测试补齐与文档同步 |

- 关键路径上的变更先改契约再改实现；实现中发现契约问题，先改契约并留记录。
- 可并行的只有不共享判定口径的工作；适配器失败不得阻塞本地记录、证据与报告。

## 6 变更控制

1. **范围/FR/AC 变更**：同步需求规格、功能清单、`status.json` 与测试计划，再改本文件第 1 节。
2. **契约变更**：命令名、字段、错误码、枚举只改一处主责文档，并同步 `models.py`、扩展与契约测试。
3. **工作包调整**：只改目标、输出与完成证明，不引入日期或人天；调整写入 `docs/修改日志/<作者>/`。
4. **登记冲突**：先改 `status.json` 与文档事实，再改叙述；不得用文档迁就未验证实现。
5. **发布物变更**：wheel/VSIX 重新构建后，M0 与 M3 的相关检查必须重跑，旧结论不对新产物有效。

## 7 完成定义

一期可交付必须同时满足：

1. 17 FR 在现行文档与代码中都有落点，31 条 AC 均有登记结果；
2. `verified` 项同时具备非空证据路径与 `real_environment_verified=true`；
3. 真实 Trae 的安装、绑定、确认、执行、导出有宿主侧证据；
4. GitHub 只读与链路导入的成功、缺失、失败路径均有记录；
5. 备份可创建、可校验、可恢复到空目录，缺证据时如实显示；
6. 模型、`gh`、链路不可用时，本地项目、计划、证据、报告仍可用；
7. 交付说明分四栏：已实现、静态/单元/合同通过、真实环境通过、未验证。

- 不以“全量测试通过”“文档一致”“面板能打开”替代上述任一条。
- 第 3、4 项尚未完全满足：完整宿主闭环（含导出与逐项安装/绑定记录）与 GitHub 成功路径仍待补；M4 只表示登记退出条件已满足，不等于本节的交付定义全部满足。
- 未验证项必须写缺什么、补完后登记到哪；不要求指定负责人，空着不算完成。
