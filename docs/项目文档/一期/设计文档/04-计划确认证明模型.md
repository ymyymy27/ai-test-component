# 一期设计04：计划确认证明模型

版本：0.2；日期：2026-11-09
状态：**核心已实现，界面与真实宿主验收未完成**。本文件定义“一次计划确认如何同时证明计划、执行许可和逐条断言依据”。不替代现行需求、功能、架构分册；不把单元/合同测试写成真实 Trae 或验收通过。

## 1. 问题

现有审批链是**逐动作**的：

- `ApprovalChallenge` 绑定一个动作、一个目标、一个输入摘要；
- `ActionConfirmation` 证明这一次用户交互；
- `BasisConfirmationService` 每条依据要求独立 challenge；
- `ControlledWriteService` 发布计划时要求 `publish_plan` challenge，并在计划记录写 `approval_confirmation_id`、`approval_commit_seq`。

设计要的是**一次计划确认**同时产生：

```text
PlanConfirmation
+ PlanExecutionGrant
+ 每条 Case 的 AssertionBasisConfirmation
```

直接把 `publish_plan`、`create_plan_grant`、`confirm_basis` 顺序调用不能满足：

- 计划记录没有受控发布元数据，`FrozenRunPlanReader` 拒绝；
- 逐条依据没有 `approval_confirmation_id`，`SavedCaseBasisReader` 拒绝；
- 不是一个用户交互，无法证明“人只确认了一次”。

## 2. 目标模型

### 2.1 `PlanConfirmation`

复用现有 `ApprovalChallenge` / `ActionConfirmation`，**动作仍是 `publish_plan`**：

```text
PlanConfirmation（= publish_plan 的 ActionConfirmation 视图）
  confirmation_id                 # ActionConfirmation.confirmation_id
  plan_id
  plan_record_revision
  plan_digest
  scope_digest
  grant_scope                     # 可选，冻结在 approval_parameters.plan_grant
  basis_digests[]                 # 每条 case 的 case_id/revision/basis_revision/basis_text_digest
  origin_session_id
  origin_entry_kind
  interaction_id
  confirmed_at_commit
```

它不是新聚合，而是 `ActionConfirmation` 的受控视图。`confirmation_id` 仍由核心生成。
不新增 `confirm_plan` 动作：`publish_plan` 已经是唯一受控的人工计划发布入口；再加一个动作会多一次交互，违背“人只确认一次”。

### 2.2 计划记录

受控发布计划记录：

```text
approval_action = "publish_plan"
approval_confirmation_id = PlanConfirmation.confirmation_id
approval_commit_seq = PlanConfirmation.confirmed_at_commit
approval_parameters = 冻结的 plan/cases/scope + 可选 plan_grant 摘要
```

`FrozenRunPlanReader`、`SavedRuntimeRevisionReader` 继续读 `approval_commit_seq` 与 `approval_action="publish_plan"`，无需改读取语义。

### 2.3 逐条依据确认

`CaseLink` 记录增加 plan proof 形状（替代逐用例 `approval_confirmation_id`）：

```text
plan_confirmation_id
plan_id
plan_revision                   # 计划记录修订
```

`confirmation_id` 仍按 case 生成稳定值；`confirmed_at_commit` 取计划记录的 `approval_commit_seq`。

`SavedCaseBasisReader` 接受两种 proof：

1. 旧的 `approval_confirmation_id`（逐用例 `confirm_basis`）；
2. 新的 `plan_confirmation_id` + plan 记录验收。

两种形状互斥：plan proof 不再携带 `approval_confirmation_id`，避免同一记录出现两个“确认来源”。

### 2.4 `PlanExecutionGrant`

许可绑定：

```text
plan_id / plan_revision(记录修订) / scope_digest
understanding_revision
grant_scope_digest
allowed_action_classes / credential / environment / risk / 预算 / 主机 / 时间窗
```

许可由同一 `publish_plan` 确认派生；`ActionAuthorization(source=plan_grant)` 仍逐动作保存。
`plan_grant` 进入受控发布的 `parameters`，因此计划确认的输入摘要已经覆盖许可范围；调用方不能在确认后偷偷扩大许可。

## 3. 一次确认的时序

```text
1. 客户端提交 plan/cases/scope + 可选 plan_grant
2. 核心生成规范 plan_digest、scope_digest、grant_scope
3. 核心生成一个 ApprovalChallenge(action=publish_plan, target=plan_id, input_digest=上述摘要)
4. 用户在一个确认页确认一次
5. 核心在同一工作单元保存受控 Plan 记录
   （approval_confirmation_id / approval_commit_seq / approval_parameters.plan_grant）
6. 核心派生（可重放，不要求新的用户手势）：
   a. 为每条 case 追加 CaseLink（带 plan_confirmation_id / plan_id / plan_revision）
   b. 最后创建 PlanExecutionGrant
7. 返回 plan_revision、plan_confirmation_id、grant_id、basis_confirmation_ids、coverage_receipt
```

第 5 步是单次原子提交。第 6 步的派生记录都以稳定业务意图幂等：

- 重传同一计划确认读回原记录，不重复写入；
- 依据先写、许可最后写，因此不会出现“有许可、无依据”的可用状态；
- 任一派生失败时，计划仍是已确认的不可变事实；重试同一意图继续补齐，不要求第二次确认。

这里与 0.1 草案的差别：不再声称计划、许可、依据必须在**同一个**提交批次。计划发布本身是一个批次；许可与依据是可重放的派生批次。若未来要把三者合并成单一批次，需要扩展 `ControlledWriteService` 的批次布局并重做恢复测试，不属于当前实现范围。

## 4. 校验规则

### 4.1 Challenge

- `action == "publish_plan"`
- `target == plan_id`
- `input_digest` 覆盖：plan + scope + cases + `plan_grant`（若提供）
- `origin_session_id` / `origin_entry_kind` 必须是受控用户入口
- `agent_relay` 不能确认

### 4.2 Plan

- `plan_id/revision/plan_digest` 与 confirmation 一致
- scope/cases 与冻结摘要一致
- 发布门禁（模板项处置、业务功能×维度、依据、独立核验）全部通过
- `approval_confirmation_id` 必须等于 `PlanConfirmation.confirmation_id`

### 4.3 Basis

- 每条 case 的 `case_revision`、`basis_revision`、`basis_text_digest` 必须出现在 `approval_parameters.cases`
- case 仍在当前修订
- 不能少一条，不能多一条
- 旧 `approval_confirmation_id` 路径继续有效

### 4.4 Grant

- `plan_id/revision/scope_digest/understanding_revision` 由服务端从刚发布的 plan 计算，客户端不能自报
- `understanding_revision` 从 v1.1 `CoverageContract` 取；旧计划没有契约时才允许由 `plan_grant` 显式提供
- `allowed_action_classes`、credential、environment、risk、预算/主机/时间窗按现有 `PlanExecutionGrant` 校验
- `grant_scope_digest` 由服务端计算

## 5. 兼容与迁移

- 不带 `plan_grant` 的 `publish_plan` 完全保持旧行为；
- 旧 `publish_plan` + 逐条 `confirm_basis` + 独立 `create_plan_grant` 路径保留；
- 旧 `CaseLink` 没有 `plan_confirmation_id` 时按旧 proof 读取；
- 新 `CaseLink` 有 `plan_confirmation_id` 时不再要求逐用例 `approval_confirmation_id`；
- 旧计划记录没有 `approval_confirmation_id` 时仍按旧受控发布路径读取，不能强行升级。

## 6. 失败语义

- challenge 过期/输入变化：拒绝，不写任何记录；
- plan 门禁失败：不写计划，不产生 confirmation/grant/basis；
- grant 参数非法：计划确认本身可能已保存；派生拒绝，重试需修正输入并生成新的计划修订/意图；
- basis 缺失或多余：拒绝该次派生，不创建许可；
- 核心崩溃：按现有 WU 恢复；未提交的计划批次不产生部分记录；已提交计划可按幂等意图重试派生；
- 重传同一 intent：返回同一 `PlanConfirmation` / plan / grant / basis 结果，不重复写入。

## 8. 非目标

- 不改变 `ActionAuthorization` 的逐动作记录；
- 不取消越界动作的逐项确认；
- 不把 AI 生成内容当作用户确认；
- 不实现平台上传、并行执行或真实宿主验收；
- 不新增 `confirm_plan` 动作或第二个人工手势。

## 9. 实施状态

已实现（核心）：

1. `ApprovalService.validate_plan_basis_confirmation`：按计划记录核对 confirmation、commit 与 case/basis 摘要；
2. `BasisConfirmationService.confirm_with_plan`：逐条依据引用同一计划确认；
3. `SavedCaseBasisReader`：同时接受旧 proof 与 plan proof；
4. `PlanConfirmationService.derive`：计划发布后派生逐条依据与许可，重放幂等；
5. `publish_plan` 可选 `plan_grant`：确认输入覆盖许可范围，发布后返回 `plan_confirmation_id`/`grant_id`/`basis_confirmation_ids`。

已实现（向导 v1.1）：

- 项目阶段先执行 `analyze_project` 并返回持久化 `ProjectUnderstanding`；审阅与模型生成都能使用同一份 understanding revision；
- 提交阶段不再生成逐条 `confirm_basis`，改为 `publish_plan` 携带 `plan_grant`；用户只面对一次计划发布确认；
- 复核页显示模板覆盖收据，有 `coverage_preview` 时显示功能×维度表；
- 覆盖契约随 `publish_plan` 提交，核心按 `understanding_ref` 读取已保存 understanding 并逐项核对功能、必要维度、测试意图、用例与 `full` 全功能覆盖；
- 准备阶段从发布回执的 `basis_confirmations` 组装确认引用。

未实现（不得写成通过）：

- 真实 Trae/Tk 人工确认与整批派生；
- 真实宿主下的掉电/重启恢复与验收登记。

## 10. 当前结论

“一次计划确认”可以由现有 `publish_plan` challenge 承担，无需新增动作。核心证明链、派生链、向导 v1.1 一次确认与项目理解→覆盖契约发布已实现并通过单元/合同测试；真实宿主验收与掉电恢复仍未完成，不能据此登记 AC 通过。
