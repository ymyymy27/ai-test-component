# 一期设计04：计划确认证明模型（草案）

版本：0.1；日期：2026-11-09  
状态：**合同设计草案，未实现**。本文件定义“一次计划确认如何同时证明计划、执行许可和逐条断言依据”，用于替换 `confirm_plan` 当前无法执行的编排。不替代现行需求、功能、架构分册。

## 1. 问题

现有审批链是**逐动作**的：

- `ApprovalChallenge` 绑定一个动作、一个目标、一个输入摘要；
- `ActionConfirmation` 证明这一次用户交互；
- `BasisConfirmationService` 每条依据要求独立 challenge；
- `ControlledWriteService` 发布计划时要求 `publish_plan` challenge，并在计划记录写 `approval_confirmation_id`、`approval_commit_seq`。

设计要的是**一次计划确认**同时产生：

```text
PlanConfirmation
+ PlanExecutionGrant
+ 每条 Case 的 AssertionBasisConfirmation
```

直接把 `publish_plan`、`create_plan_grant`、`confirm_basis` 顺序调用不能满足：

- 计划记录没有受控发布元数据，`FrozenRunPlanReader` 拒绝；
- 逐条依据没有 `approval_confirmation_id`，`SavedCaseBasisReader` 拒绝；
- 不是一个用户交互，无法证明“人只确认了一次”。

## 2. 目标模型

### 2.1 `PlanConfirmation`

复用现有 `ApprovalChallenge` / `ActionConfirmation`，但动作是 `confirm_plan`：

```text
PlanConfirmation
  confirmation_id
  plan_id
  plan_revision
  plan_digest
  scope_digest
  grant_scope_digest
  basis_digests[]        # 每条 case 的 case_id/revision/basis_revision/basis_text_digest
  origin_session_id
  origin_entry_kind
  interaction_id
  confirmed_at_commit
```

它不是新聚合，而是 `ActionConfirmation` 的一个受控视图。`confirmation_id` 仍由核心生成。

### 2.2 计划记录

受控发布计划记录增加：

```text
approval_action = "confirm_plan"
approval_confirmation_id = PlanConfirmation.confirmation_id
approval_commit_seq = PlanConfirmation.confirmed_at_commit
approval_parameters = 冻结的 plan/grant/basis 摘要
```

`FrozenRunPlanReader` 继续读 `approval_commit_seq`，无需改读取语义。

### 2.3 逐条依据确认

`CaseLink` 记录增加：

```text
plan_confirmation_id
plan_id
plan_revision
plan_digest
```

`confirmation_id` 仍按 case 生成稳定值；`confirmed_at_commit` 取 `PlanConfirmation.confirmed_at_commit`。

`SavedCaseBasisReader` 接受两种 proof：

1. 旧的 `approval_confirmation_id`；
2. 新的 `plan_confirmation_id` + plan 记录验收。

### 2.4 `PlanExecutionGrant`

许可绑定：

```text
plan_id / plan_revision / scope_digest
understanding_revision
plan_confirmation_id
grant_scope_digest
allowed_action_classes / credential / environment
```

许可由同一 `PlanConfirmation` 派生；`ActionAuthorization(source=plan_grant)` 仍逐动作保存。

## 3. 一次确认的时序

```text
1. 客户端提交 plan/cases/scope + grant 参数 + basis 列表
2. 核心生成 plan_digest、scope_digest、grant_scope_digest、basis_digests
3. 核心生成一个 ApprovalChallenge(action=confirm_plan, target=plan_id, input_digest=上述摘要)
4. 用户在一个确认页确认一次
5. 核心在同一工作单元：
   a. 消费 challenge，保存 PlanConfirmation
   b. 保存受控 Plan 记录（带 approval_confirmation_id/commit_seq）
   c. 保存 PlanExecutionGrant
   d. 为每条 case 保存 CaseLink（带 plan_confirmation_id）
   e. 保存 acceptance scope / cases（若尚未保存）
6. 返回 plan_revision、grant_id、basis_confirmation_ids、coverage_receipt
```

第 5 步必须是一个工作单元。任何一个记录失败，整批回滚；不能返回“计划成功、许可失败”的 partial。

## 4. 校验规则

### 4.1 Challenge

- `action == "confirm_plan"`
- `target == plan_id`
- `input_digest` 覆盖：plan_digest + scope_digest + grant_scope + basis_digests
- `origin_session_id` / `origin_entry_kind` 必须是受控用户入口
- `agent_relay` 不能确认

### 4.2 Plan

- `plan_id/revision/plan_digest` 与 confirmation 一致
- scope/cases 与冻结摘要一致
- 发布门禁（模板项处置、业务功能×维度、依据、独立核验）全部通过
- `approval_confirmation_id` 必须等于 `PlanConfirmation.confirmation_id`

### 4.3 Basis

- 每条 case 的 `case_revision`、`basis_revision`、`basis_text_digest` 必须出现在 `PlanConfirmation.basis_digests`
- case 仍在当前修订
- 不能少一条，不能多一条
- 旧 `approval_confirmation_id` 路径继续有效

### 4.4 Grant

- `plan_id/revision/scope_digest` 由服务端从刚发布的 plan 计算，客户端不能自报
- `understanding_revision` 从 v1.1 proposal/coverage contract 取
- `allowed_action_classes`、credential、environment、risk、预算/主机/时间窗按现有 `PlanExecutionGrant` 校验
- `grant_scope_digest` 由服务端计算

## 5. 兼容与迁移

- 旧 `publish_plan` + 逐条 `confirm_basis` + 独立 `create_plan_grant` 路径保留；
- 新 `confirm_plan` 只对 `PlanProposal v1.1` / `CoverageContract` 计划启用；
- 旧 `CaseLink` 没有 `plan_confirmation_id` 时按旧 proof 读取；
- 新 `CaseLink` 有 `plan_confirmation_id` 时不再要求逐用例 `approval_confirmation_id`；
- 旧计划记录没有 `approval_confirmation_id` 时仍按旧受控发布路径读取，不能强行升级。

## 6. 失败语义

- challenge 过期/输入变化：拒绝，不写任何记录；
- plan 门禁失败：整批回滚，不产生 confirmation/grant/basis；
- grant 参数非法：整批回滚；
- basis 缺失或多余：整批回滚；
- 核心崩溃：按现有 WU 恢复；未提交的 batch 不产生部分记录；
- 重传同一 intent：返回同一 `PlanConfirmation` / plan / grant / basis 结果，不重复写入。

## 7. 需要修改的合同

| 合同 | 修改 |
| --- | --- |
| `P1-AC31` | 明确 `confirm_plan` 一次确认可以派生逐动作 `ActionAuthorization`，计划确认仍不替代动作记录 |
| `P1-FR07` | 计划确认与执行许可的绑定 |
| 架构 05 §9 | PlanConfirmation、受控计划发布、plan proof |
| 架构 01 §3/§4 | 计划记录的 `approval_confirmation_id`/`approval_commit_seq` 来源 |
| 架构 02 §6 | `SavedCaseBasisReader` 接受 plan proof |
| 报告/证据 | 计划确认来源、grant 来源、basis 来源 |
| 验收 | 新增“一次确认 → 计划/许可/依据同批保存”的场景；不能复用旧 AC 文字 |

## 8. 非目标

- 不改变 `ActionAuthorization` 的逐动作记录；
- 不取消越界动作的逐项确认；
- 不把 AI 生成内容当作用户确认；
- 不实现平台上传、并行执行或真实宿主验收；
- 不在本设计未批准前改 `confirm_plan` 代码。

## 9. 实施顺序

1. 领域/合同：`PlanConfirmation` 视图、`CaseLink` plan proof 字段、校验规则；
2. 应用：`confirm_plan` 单工作单元编排、plan 受控发布、grant、basis；
3. 读取：`SavedCaseBasisReader`、`FrozenRunPlanReader`、`validate_basis_confirmation`；
4. 测试：一次确认、整批回滚、重传幂等、旧路径兼容、relay 拒绝；
5. UI：确认页只显示覆盖收据并提交一次 challenge；
6. 验收：真实 Trae/Tk 后才能登记。

## 10. 当前结论

`confirm_plan` 不能在证明模型未定时实现。先批准本合同的字段和整批语义，再写代码；否则会生成准备/执行链拒绝的记录。
