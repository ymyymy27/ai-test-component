## 1. 背景与共同约束

本文件记录后端优化的三项设计方向：

1. **AI 主导测试**：用户建立项目并输入测试目标后，由 AI 生成计划、执行并产出结果，人的介入作为可选项。
2. **非开发者界面**：用户可见的术语、字段、流程与错误提示应能被非开发者理解，而不是暴露测试工程内部概念。
3. **模板项与模板合集**：按被测项目种类选择模板；没有对应模板时使用通用模板；每个模板说明该类项目的通用测试内容。

当前工作树基线：

- 分支：`后端优化`
- 提交：`6b88d42`（结构化提案与集中授权实现）、`2718be8`（真实 DeepSeek 冒烟记录）
- 验证记录：[p1-ai-plan-review-20261106](../../../validation/p1-ai-plan-review-20261106/README.md)
- 当前状态：[项目现状](../../../现状.md)

三项设计共同受以下约束：

- 人工确认、逐项授权、证据留存与报告来源不可被 AI 或 MCP 替代。
- 不得把“AI 已生成”写成“用户已确认”；不得把“策略授权”写成“人工确认”。
- 不得把“未支持”写成“不适用”；不得用空集合或通用模板掩盖覆盖缺口。
- 模板项、用例、计划、范围、授权、证据等级等术语沿用现行合同定义，不另起定义。
- 本草案不修改 FR/AC；正式落地前需按阅读索引更新主责分册与验收映射。

## 2. 第一项：AI 主导测试

### 2.1 目标形态

```text
用户建立项目、输入测试目标
→ AI 生成结构化计划
→ 用户一次审阅（可改）
→ 发布、准备、逐项授权
→ 计划驱动自动执行
→ 自动核验与报告
→ 用户可选复核
```

### 2.2 当前已实现（路线 A）

| 能力 | 当前实现 | 证据 |
| --- | --- | --- |
| 结构化计划提案 | `aitest.plan-proposal/1.0` 解析、模板覆盖校验、Case/Scope 物化 | `src/aitest/contracts/plan_proposal.py`、`src/aitest/application/planning/proposal.py` |
| 模型结构化输出 | `output_schema`、system prompt、JSON mode | `src/aitest/application/planning/model_ports.py`、`src/aitest/infrastructure/adapters/model.py` |
| 一屏审阅与提交 | 向导 `review`/`commit` 阶段、全字段审阅页 | `src/aitest/application/project/onboarding.py`、`src/aitest/resources/panel/src/onboarding.ts` |
| 普通写入通道 | 非人工动作不弹原生窗口 | `integrations/trae/src/core-bridge.ts`、`src/aitest/resources/panel/src/index.ts` |
| 集中逐项授权 | 一个原生窗口、每项独立确认 | `src/aitest/interfaces/local/native_confirmation.py` |
| 计划驱动启动 | 授权列表、`start_run`、刷新 | `src/aitest/resources/panel/src/run-authorization.ts` |

当前验证边界：真实 DeepSeek 冒烟 5 次核心路径 4 次成功、1 次 `blocked`；真实 Trae、真实 Tk 批量窗口、计划驱动全链路仍未验证。面板 Playwright 23 passed / 7 failed。

### 2.3 尚未实现（路线 B）

- 真正的 `auto` 驱动：AI 在策略内自动发布计划、自动确认依据、自动授权动作。
- `AutomationPolicy`：一次性批准范围、动作类型、凭据、副作用、模型出站、失效条件。
- 策略授权来源：`human_confirmed` / `policy_authorized` / `ai_generated` 三种来源的逐项 provenance。
- 策略授权下的证据等级语义：是否允许 A 级，如何标注“未经人工确认”。
- 运行时才解析的动作在策略内的自动执行边界。

### 2.4 待决策

| 编号 | 决策 | 选项 | 影响 |
| --- | --- | --- | --- |
| D1 | 副作用动作的授权模型 | 逐项人工确认 / 首次逐项确认后同范围复用 / 策略预授权 / 全自动 | 决定合同、AC、报告来源与安全边界 |
| D2 | 策略授权能否取得 A 级 | 可以但降级标注 / 只允许 B 以下 / 单独等级 | 决定证据等级口径 |
| D3 | 计划发布与依据确认是否允许 AI 自动完成 | 只允许人工 / 策略内自动 / 首次人工后自动 | 决定 P1-AC31/32 的扩展方式 |
| D4 | 运行时动态动作 | 越界暂停 / 策略内自动 / 一律人工 | 决定 `waiting_authorization` 的频率 |
| D5 | 模型输出失败的回退 | 失败即回退手动/模板 / 自动重试一次 / 自动修补 | 决定可靠性与不可信输出处理 |

**建议**：D1 优先采用“策略预授权 + 越界暂停”，D5 保持“失败即回退”，不允许自动修补。

## 3. 第二项：非开发者界面

### 3.1 目标用户

目标用户为业务测试人员、产品、运营等非开发者：

- 能描述业务目标、判断业务结果；
- 能完成项目选择与确认；
- 不要求理解 Python 入口、虚拟环境、JSON、断言依据、证据等级、修订号、摘要。

若目标用户是“会一点 Python 的测试工程师”，本项范围可相应收窄。

### 3.2 当前界面评估

| 界面 | 当前内容 | 非开发者可读性 | 主要差距 |
| --- | --- | --- | --- |
| 首次向导 | 项目目录、Python 入口、测试目标、数据隔离 | 部分 | 需要理解“入口”与 Python 文件 |
| 模型配置 | 端点、模型名、超时、API Key | 部分 | 端点/模型名需要技术知识 |
| AI 计划审阅 | 范围、用例、模板项 ID、断言依据、独立核验、链接、Mock、高级 JSON | 低 | 测试设计语言与工程标识过多 |
| 启动前授权 | 步骤/用例 ID、副作用类别、入口、参数、超时、输入摘要 | 低 | 缺少“会做什么、影响什么”的业务说明 |
| 运行/报告 | 业务结论、证据等级 A—D、覆盖、缺口、提交号、事件边界 | 部分 | 等级与缺口缺少解释 |
| 设置/诊断 | Python 路径、工作空间、项目编号、载体文件、原始 JSON | 低 | 应自动探测或折叠到高级视图 |
| 错误提示 | `B_INVALID_PARAMETER`、`INTENT_CONFLICT` 等 | 低 | 缺少原因、下一步与结果影响 |

### 3.3 目标设计

#### 3.3.1 简单模式与高级模式

- **简单模式（默认）**：只显示检查项目标、范围、影响、结论与下一步。
- **高级模式**：显示模板项 ID、用例 ID、入口、参数、修订、摘要、原始 JSON。

两种模式共享同一核心事实，不产生第二套判定。

#### 3.3.2 业务语言映射

| 工程术语 | 用户可见表达 |
| --- | --- |
| 模板项 `boundary` | 边界值检查 |
| 断言依据 | 为什么这条检查能证明目标 |
| 独立核验 | 如何用另一条路确认结果 |
| 副作用类别 | 这一步会不会改动业务数据 |
| 证据等级 A—D | 这个结论有多可靠、还缺什么 |
| 覆盖/缺口 | 测了什么、没测什么 |
| `AWAITING_USER_CONFIRMATION` | 这件事需要你本人确认后才能继续 |

#### 3.3.3 默认值与自动探测

非开发者不应手填解释器、虚拟环境、入口、工作空间、项目编号、模型端点。应由插件探测或给出推荐值，用户只确认“是否为本项目”。

#### 3.3.4 授权窗口

授权窗口应优先说明：

- 这一步会做什么；
- 会影响什么；
- 为什么需要确认；
- 允许/不允许的影响。

技术字段保留在“查看技术细节”中，不作为默认内容。

#### 3.3.5 报告结论卡

报告首屏应回答四个问题：

1. 通过了吗；
2. 哪些没测到；
3. 为什么可信或不可信；
4. 下一步做什么。

技术标识、提交号、事件边界、覆盖计数折叠到详情。

#### 3.3.6 错误提示格式

每个错误应包含：

- 原因；
- 用户可执行的下一步；
- 是否影响已有结果；
- 是否需要重新准备或重新授权。

### 3.4 不可简化的内容

- 人工确认与逐项授权；
- 证据来源与 provenance；
- 未执行、未验证、未覆盖范围；
- 结论不确定性；
- 失败与问题处置。

简化的是表达与操作，不是事实与门禁。

### 3.5 用户验证指标

- 无指导完成“建项目 → 提交 → 授权 → 读取报告”的比例；
- 需要人工解释的次数；
- 关键术语误解次数；
- 误操作率；
- 从开始到拿到报告的时间。

## 4. 第三项：模板项与模板合集

### 4.1 当前设计

模板由 `TemplatePack` 定义，位于 `src/aitest/resources/templates/<template_id>/<version>.json`。

主要字段：

- `template_id`、`version`、`name`、`source`
- `applicability`、`delivery_method`、`implementation_status`
- `items[]`：`item_id`、`layer`、`objective`、`preconditions`、`input_fields`、`entry_type`、`expected`、`assertion_basis`、`verification`、`evidence_requirements`
- `required_item_ids`、`critical_paths`、`no_critical_path_reason`
- `examples`

当前六套模板：

`python-library`、`python-service`、`http-workflow`、`manual-web-workflow`、`agent-workflow`、`ticket-workflow`。

模板项不是用例、不是断言、不是执行脚本。它只定义“必须检查什么”，项目特定的输入、预期、依据与核验方式由 `Case` 补充。

### 4.2 原始设想

- 先判断被测项目种类；
- 在模板合集里找对应模板；
- 没有对应模板时使用通用模板；
- 每个模板是一份文档，写明该类项目的测试内容。

### 4.3 对比

| 维度 | 结构化 `TemplatePack`（现有） | 整篇文档合集（原始设想） |
| --- | --- | --- |
| 机器校验覆盖率 | 强 | 弱 |
| 版本与摘要冻结 | 强 | 弱 |
| 防止 AI 漏项/改项 | 强 | 弱 |
| 人类阅读与培训 | 中 | 强 |
| 业务背景说明 | 弱 | 强 |
| 作者编写成本 | 中 | 低 |
| 内容漂移风险 | 低 | 高 |
| `full` 门禁可执行性 | 强 | 弱 |
| 跨项目复用 | 强 | 中 |
| 非开发者可读性 | 弱 | 强 |

### 4.4 建议形态

> **结构化模板包作为唯一权威来源；由它生成面向人的模板指南；增加通用回退模板与项目类型推荐；文档不单独维护第二套内容。**

#### 4.4.1 术语修正

“写明该类项目的全部测试内容”应修正为：

> 该类项目的**通用必测骨架、适用条件、已知不适用项、执行方式与证据要求**。

模板项是下限，不是完整测试套件；项目范围仍由 `AcceptanceScope`、`M`、`S` 决定。

#### 4.4.2 模板项扩展

建议在 `TemplateItem` 增加：

- `display_name`：业务可读名称；
- `business_description`：业务含义；
- `why_required`：为什么必测；
- `not_applicable_hint`：何种条件下可不适用；
- `limitations`：本项已知限制。

`item_id` 保持稳定，仅用于机器引用。

#### 4.4.3 通用回退模板

新增 `generic` 模板：

- 适用范围：无法匹配任何专用模板的项目；
- 内容：保守的 L1 加载/入口检查、基础 L2 可执行检查、可用的独立核验；
- 明确声明不覆盖项目特定业务规则；
- 报告中标注“使用通用回退模板”并列出未覆盖范围；
- 不得把“没有专用模板”写成“不适用”。

#### 4.4.4 项目类型识别与模板推荐

建议增加用例：

```text
analyze_project
→ 识别技术栈、交付方式、持久化、页面、智能体等信号
→ 推荐模板（含置信度与理由）
→ 用户确认
→ 无匹配时推荐 generic，并列出缺口
```

推荐结果应显示推荐模板、版本、理由、不匹配信号、需补充信息与通用回退代价。

#### 4.4.5 面向人的模板指南

每个模板生成一份 Markdown 指南，包含：

- 项目类型说明；
- 适用/不适用条件；
- 必测项清单；
- 关键链路；
- 执行方式；
- 证据要求；
- 正常/边界/异常示例；
- 项目需补充字段；
- 已知限制。

指南由模板生成，不手工维护。

#### 4.4.6 模板覆盖视图

显示：

```text
使用模板：python-library 1.0.0
必测项：4
已覆盖：4
不适用：0（附理由）
未支持：0
项目补充项：2
```

报告保留同一份模板覆盖事实。

#### 4.4.7 版本与迁移

- 模板版本不可变；
- 新增、删除、改义条目必须显式记录；
- 旧计划继续引用旧版本；
- 模板升级不自动改写旧计划；
- 迁移生成新计划修订。

### 4.5 待决策

| 编号 | 决策 | 选项 | 影响 |

| D6 | 模板指南的维护方式 | 由模板生成 / 手工维护 / 混合 | 决定内容漂移风险 |
| D7 | 通用模板的覆盖范围 | 仅 L1 / L1+基础 L2 / 可配置 | 决定回退时的结论强度 |

## 5. 三项之间的关系

| 项 | 核心问题 | 依赖 |
| --- | --- | --- |
| 第一项：AI 主导 | 谁做决定、谁执行 | 授权模型、模板骨架 |
| 第二项：非开发者界面 | 用户看到什么、需要决定什么 | 模板项业务名称、信息分层 |
| 第三项：模板项 | 检查内容如何组织 | 项目类型识别、模板指南 |

建议实施顺序：

1. **模板项内容模型**：先补齐通用回退、业务名称与版本说明，为 AI 提案与界面提供稳定骨架。
2. **AI 主导授权模型**：确定策略授权、provenance 与证据等级语义。
3. **非开发者界面**：在稳定骨架与授权语义之上做简单/高级模式、默认值与解释层。

三项可以并行设计，但正式落地时以上述依赖为准。
