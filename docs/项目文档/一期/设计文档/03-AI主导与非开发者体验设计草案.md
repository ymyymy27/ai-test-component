## 0. 一页结论

最简流程：

```text
建项目
→ （可选）说目标
→ AI 理解项目并给出目标候选
→ 用户选目标
→ AI 生成计划
→ 用户确认一次
→ 计划驱动自动执行
→ 报告
```

六个关键设计：

1. **一次项目理解**：复用现有 `ProjectContext`，产出 `BusinessFunctionCatalog`、`TestIntent`、`GoalCandidate`；同一个 understanding 修订，不另造一套项目模型。
2. **目录与覆盖分开**：`BusinessFunction` 是稳定目录，`FunctionCoverage` 是每次计划/运行的投影；覆盖事实不反写目录。
3. **清单回答“有没有漏”**：模板只做提醒；`full` 门禁看业务功能×必要维度；模板项拆成“适用性×覆盖”，不再用一个三态混住两件事。
4. **目标按风险选**：问“最近改了什么、坏了最疼什么、哪里最常出问题”，候选按变更×影响×历史排序，并显示推荐理由。
5. **用户只确认一页**：范围、覆盖收据、已知限制、执行影响、执行方式；`full` 不可编辑，修改转 `on_demand`。
6. **一次确认产生三类记录 + 能力信封**：计划确认、`PlanExecutionGrant`（含预算/时间窗）、逐条依据确认；计划内自动执行，越界暂停；报告给覆盖收据和每项可信度，不只是一个总等级。

一期不做：

- AI 直接操作浏览器/桌面/工具；
- 全项目一次性全量覆盖；
- 并行/分布式执行；
- 平台上传。

合同状态：`P1-AC20`、`P1-AC31` 已按 13.1 修订；`P1-AC24`、`P1-FR04`、`P1-FR06` 已扩展；未新增 FR/AC 编号，验收结果不升级。详见 13.1。

## 1. 文档定位

### 1.1 目的

本文件描述一期后端优化的目标形态：

- AI 主导测试：用户建立项目后，由 AI 理解项目、给出目标候选、生成计划；
- 非开发者体验：用户只确认计划及其影响，不需要理解测试工程细节；
- 模板与业务功能：模板作为提醒，业务功能清单作为完整性依据。

三项不是三个独立产品，而是同一流程的三个层面：

```text
业务功能清单（内容）
→ AI 生成计划（自动化）
→ 用户确认（体验）
```

```text
SourceSnapshot
→ ProjectUnderstanding（ProjectContext + BusinessFunctionCatalog + TestIntent + GoalCandidate）
```

## 2. 目标、角色与原则

### 2.1 产品目标

```text
用户建立项目（可输入目标，也可不输入）
→ 一次项目理解
→ AI 给出目标候选
→ 用户选择或确认目标
→ AI 生成最终计划
→ 用户确认计划及执行影响
→ 计划驱动自动执行
→ 自动核验与报告
→ 用户可选复核
```

### 2.2 用户角色

| 角色 | 关心什么 | 默认看到什么 |
| --- | --- | --- |
| 业务用户 | 这次测什么、能不能证明业务正确、还差什么 | 目标候选、计划确认页、运行状态、报告结论 |
| 测试工程师 | 计划、用例、证据、授权、诊断 | 技术详情、用例编号、授权范围、原始材料 |
| 审计/复核 | 谁批准了什么、证据在哪 | 技术详情、授权来源、证据引用 |

业务用户不需要理解代码结构、测试设计语言或内部标识。

### 2.3 设计原则

1. **全局设置只做一次，项目流程可重复。**
2. **全局只配“怎么连模型”，不配“怎么测项目”。**
3. **AI 负责起草和适配，人负责决定和确认。**
4. **用户确认后果，不确认技术机制。**
5. **默认只显示业务语言，技术详情折叠。**
6. **不隐藏未支持、未覆盖、`unknown`。**
7. **`full` 不可编辑；修改转 `on_demand`。**
8. **AI 不能自证通过；执行结果仍需独立核验。**

### 2.4 不可简化的边界

- 人工确认计划；
- 计划级执行许可；
- 证据来源与 provenance；
- 未执行、未验证、未覆盖、未支持范围；
- 结论不确定性；
- 失败与问题处置。

简化的是表达与操作，不是事实与门禁。

## 3. 端到端流程

### 3.1 首次使用

首次启动只配置插件级设置，不创建项目：

```text
插件设置

模型配置
  配置名称：[默认]
  供应商：[DeepSeek]
  API 地址：[https://api.deepseek.com]
  模型：[deepseek-flash]
  API Key：[安全保存到系统凭据管理器]
  超时：[60] 秒

[测试连接]

高级（默认折叠，仅诊断时展开）
  Python 3.13 路径（自动探测）
  用户数据根目录
  诊断与兼容性

[保存并开始使用]
```

要求：

- 模型连接配置一次，长期复用；
- API Key 只进系统凭据管理器；
- 可以跳过模型配置，模板/人工流程仍可用；
- 测试连接失败时允许保存，但标记“未验证”；
- 界面不显示“载体登记文件”“业务查询文件”等内部名称；这些只在诊断页和技术详情中出现，正常流程自动生成。

### 3.2 建立项目

```text
新建测试

项目目录：[选择目录]
项目名称：[自动带出目录名]
测试数据：[隔离/复位说明]

模型：
  [使用默认配置档]
  [选择其他配置档]
  [不使用模型]

模型材料范围：
  [x] 项目名称和测试目标
  [x] 模板骨架
  [ ] 源码片段（敏感，默认关闭）

[开始理解项目]
```

用户不需要填写入口、解释器、虚拟环境、工作空间、项目编号或 API Key。

### 3.3 项目理解

- 每个源码版本、每个测试范围只做一次完整扫描；
- 发生在建立项目之后、生成目标之前；
- 输入：源码快照、选定范围、排除规则；
- 处理：全范围确定性扫描 + AI 语义补充；
- 输出：`ProjectUnderstanding`，包含现有 `ProjectContext`、`ProjectSignals`、`BusinessFunctionCatalog`、`TestIntent`、`GoalCandidate`、`CapabilityGap`。

`ProjectUnderstanding` 是唯一版本入口：三者共用 `understanding_id`、`revision`、`source_snapshot_id`、`scope` 和 `digest`，不分别维护画像、清单、目标候选的修订号，避免三者不同步。

“完整读源码”指全范围扫描，不是把全部字节发给模型：

| 任务 | 靠什么 |
| --- | --- |
| 发现有哪些业务功能 | 全范围扫描：路由、CLI、页面、事件、定时任务、状态字段、领域模型 |
| 理解某个功能细节 | 读取该功能的局部源码片段 |
| 证明没有漏功能 | 业务功能清单 + `unknown` 桶 + 覆盖门禁 + 用户确认 |

局部源码发现清单外功能时，必须补入清单或标为 `unknown`，不能忽略。

### 3.4 目标确定

```text
最近改了什么？
  [订单状态] [支付回调] [权限]

如果坏了，最疼的是什么？
  [下错单] [收不到货] [看不到订单]

哪里最常出问题？
  [取消订单] [分页] [权限]

推荐验证（按 变更 × 影响 × 历史 排序）：
  1. 订单状态修改
     最近改动 + 下错单影响最大
  2. 取消订单权限
     历史问题 + 越权影响
  3. 订单查询分页
     最近改动 + 看不到订单影响

其他范围：
  完整验证当前范围
  自定义
  让 AI 选择
```

规则：

- 用户不需要从零写目标；先回答三个业务问题，而不是直接选测试项；
- 目标候选由业务功能清单与 `TestIntent` 生成；
- 排序依据是 `变更 × 影响 × 历史风险`，每个候选显示“为什么推荐”；
- “完整验证当前范围”只有在清单完整、无 `unknown` 时才可选；
- 界面文案用“完整验证当前范围”，副标题写明“覆盖当前范围内的全部适用业务功能，不等于全项目所有代码”；避免用户理解成“整个项目 100% 通过”；
- 目标候选都不合适时，可以补充说明后重新理解；
- 目标绑定 `ProjectUnderstanding` 修订；`GoalCandidate` 只是 `TestIntent` 的界面投影，不是第二套验收对象。

### 3.5 计划生成

- 复用同一次项目理解，不重新全量读源码；
- 模板作为提醒清单，AI 逐项给出处置；
- AI 可以新增项目检查；
- 最终计划内所有检查项平级；
- `full` 只包含证明目标所需的最小充分集。

### 3.6 计划确认

用户只确认一个页面：

```text
本次验证范围
覆盖收据（预览）
  将验证：4 个功能 × 6 个维度
  将不验证：1 个功能（插件暂不支持）
  未识别：1 个
已知限制
执行影响
执行方式
需要你确认
```

覆盖收据是计划冻结的 `FunctionCoverage` 预览，不是报告；用户确认后按同一收据生成报告，避免确认页和报告各说一套。

`full` 下：

- 所有检查项平级、全部必测；
- 用户只能整体确认；
- 修改即转 `on_demand`；
- 原 `full` 计划保留为候选。

一次确认产生三类记录：

1. 计划确认；
2. `PlanExecutionGrant`；
3. 每条用例的断言依据确认。

这三类记录共享同一次用户交互，但各自独立保存：一次点击，不是三次点击；每条用例仍有自己的依据确认，不是用计划确认代替。

### 3.7 执行

- `planned` 驱动自动推进；
- 计划内、许可内动作自动执行；
- 越界动作暂停确认；
- 用户可暂停、取消、重试、补证、核实；
- `full` 运行中不允许修改计划。

### 3.8 报告

- 业务结论与可信度分开；
- 显示业务功能覆盖；
- 显示未支持、未覆盖、不适用、`unknown`；
- 写明“完整验证只对本次范围成立”；
- 技术标识折叠到技术详情。

### 3.9 退出与恢复

- 关闭编辑器不等于取消；
- 核心继续管理运行；
- 重开回到同一运行、同一状态；
- 暂停不被自动解除；
- 未知副作用先核实，不自动重放。

## 4. 项目理解与业务功能清单

### 4.1 一次项目理解

- 每个源码版本、每个范围只做一次；
- 源码快照固定在前，AI 分析在后；
- AI 输出只是草稿，后端负责校验；
- 源码变化时重新理解，旧结果保留为历史；
- 不把“模型读完了所有代码”当作完整性证明。

`ProjectUnderstanding` 的输入、范围和摘要一次固定；清单修正也生成新的 understanding 修订，旧修订保留。计划、目标、授权只引用 understanding 修订，不分别引用画像或清单修订。目录修正生成新的 understanding；覆盖事实不写回目录。

### 4.2 ProjectUnderstanding、ProjectContext 与 CapabilityGap

`ProjectUnderstanding` 顶层字段：

| 字段 | 含义 |
| --- | --- |
| `understanding_id` / `revision` | 一次项目理解的稳定身份与修订 |
| `source_snapshot_id` | 依据的源码快照 |
| `scope` | 本次扫描范围 |
| `project_context_ref` | 复用现有 `ProjectContext`（模块、依赖、入口） |
| `signals` | 项目信号（入口候选、技术栈、能力、风险信号） |
| `inventory` | `BusinessFunctionCatalog` |
| `test_intents` | `TestIntent` 集合 |
| `goal_candidates` | 目标候选，`TestIntent` 的界面投影 |
| `capability_gaps` | 插件能力缺口 |
| `unknown_areas` | 未识别/待确认区域 |
| `model_profile_ref` | 使用的模型配置档 |
| `material_policy_digest` | 材料范围摘要 |
| `digest` | 整体摘要 |

`ProjectSignals` 字段：

| 字段 | 含义 |
| --- | --- |
| `detected_stack` | 语言、框架、包管理器、运行时 |
| `entry_candidates` | 可能的入口、命令、模块 |
| `capabilities` | HTTP、数据库、页面、智能体、外部服务等 |
| `risk_signals` | 数值输入、状态迁移、持久化、权限、并发、异常路径等 |
| `confidence` | 每个信号的置信度 |
| `evidence_refs` | 指向源码快照中的文件/位置 |
| `origin` | deterministic / ai_suggested / user_corrected |

`CapabilityGap` 字段：

| 字段 | 含义 |
| --- | --- |
| `gap_id` | 稳定标识 |
| `scope` | 受影响的功能、维度或入口 |
| `missing_capability` | 插件/适配器缺少的能力 |
| `capability_revision` | 产生该缺口的适配器/能力修订 |
| `reason` | 为什么当前做不到 |
| `workaround` | 可接受的人工/外部替代（如有） |
| `blocks_full` | 是否阻止 `full` |
| `source_refs` | 依据来源 |

不再定义 `ProjectProfile`；模块、依赖、入口字段来自现有 `ProjectContext`。`CapabilityGap` 表达的是“插件暂时做不到”，不是“项目没有这个能力”；适配器能力升级后按 `capability_revision` 重算缺口，不必重新扫描项目。

### 4.3 BusinessFunctionCatalog

业务功能指“用户或外部系统可触发的、有明确业务结果的能力”，例如：

- HTTP 端点 + 业务对象 + 动作 + 预期结果；
- 页面操作流程；
- CLI 命令；
- 智能体工具调用；
- 业务状态迁移；
- 业务计算规则。

不包含每个内部私有函数或纯技术辅助代码；否则“所有业务功能”会退化为代码覆盖率。

```text
业务域
└── 业务功能（capability）
      ├── 业务流程（flow）
      └── 操作（operation）
            └── 业务规则（rule）
```

### 4.4 BusinessFunction、FunctionCoverage 与 TestIntent

`BusinessFunction` 是稳定目录，只描述“项目能做什么”：

| 分组 | 字段 | 含义 |
| --- | --- | --- |
| 身份 | `function_id` | 稳定标识 |
| 身份 | `name` | 业务名称 |
| 身份 | `parent_function_id` | 父功能 |
| 身份 | `function_kind` | capability/flow/operation/rule |
| 身份 | `canonical_function_id` | 去重后的主功能 |
| 身份 | `aliases` | 同一功能的其他入口 |
| 业务语义 | `trigger` | HTTP/页面/CLI/智能体/事件/定时任务/状态迁移 |
| 业务语义 | `business_object` | 作用的业务对象 |
| 业务语义 | `expected_outcome` | 预期业务结果 |
| 业务语义 | `conditions` | 角色、租户、环境、功能开关等适用条件 |
| 覆盖契约 | `required_dimensions` | 该功能必须覆盖的维度 |
| 来源 | `source_refs` | 源码/需求证据 |
| 来源 | `origin` | deterministic/ai_suggested/user_confirmed |
| 来源 | `confidence` | 置信度 |
| 来源 | `review_state` | unreviewed/confirmed/needs_review |
| 版本 | `source_snapshot_id` | 依据的源码快照 |
| 版本 | `understanding_revision` | 依据的项目理解修订 |

`FunctionCoverage` 是每次计划/运行的投影，不写回目录：

| 字段 | 含义 |
| --- | --- |
| `coverage_id` | 稳定标识 |
| `function_id` | 对应业务功能 |
| `plan_revision` / `run_id` | 本次计划或运行 |
| `coverage_by_dimension` | 每个必要维度的状态（已覆盖/部分/未覆盖/不适用/未支持） |
| `overall_coverage` | 由维度汇总，不手填 |
| `case_ids` | 对应用例 |
| `evidence_refs` | 已保存证据 |
| `verification_refs` | 独立核验记录 |
| `gap_reason` | 缺口原因 |
| `updated_at` | 投影更新时间 |

`TestIntent` 把“为什么测”固定下来：

| 字段 | 含义 |
| --- | --- |
| `intent_id` | 稳定标识 |
| `statement` | 业务目标/风险陈述 |
| `risk` | 失败影响 |
| `function_ids` | 关联业务功能 |
| `required_dimensions` | 本次意图要求覆盖的维度 |
| `acceptance_condition` | 什么算验证成立 |
| `rationale` | 变更/影响/历史依据 |
| `origin` | user/ai_suggested |
| `confidence` | 置信度 |
| `understanding_revision` | 依据的项目理解修订 |

`CoverageClaim` 是 intent × function × dimension 的连接记录：`claim_id`、`intent_id`、`function_id`、`dimension`、`plan_revision`、`status`（proven/partial/not_proven/unsupported）、`case_ids`。

`TestIntent` 与现有 `AcceptanceItem` 同构，是面向用户的业务视图，不新增第二套验收对象；`GoalCandidate` 只是 `TestIntent` 的界面投影。`FunctionCoverage` 是报告/门禁的投影，不是目录的一部分。

### 4.5 覆盖维度

不能只要求“一条 L3”，应要求“功能 × 必要维度”：

| 维度 | 说明 |
| --- | --- |
| `normal` | 正常路径成功完成 |
| `boundary` | 极值、空集合、分页边界 |
| `error` | 非法输入、依赖失败、超时 |
| `permission` | 角色、未授权、越权 |
| `state_transition` | 合法迁移、非法迁移、重复提交 |
| `persistence` | 最终写入、刷新后仍正确 |
| `dependency_failure` | 外部服务不可用、降级 |
| `concurrency` | 仅在该功能确有并发/幂等要求时 |

每个功能声明 `required_dimensions`；每个必要维度至少一条有效证据和独立核验；维度不适用需理由和证据。

必要维度不由 AI 自由决定，先按规则派生，再允许有理由的补充：

| 功能属性 | 默认必要维度 |
| --- | --- |
| 所有功能 | `normal`、`error` |
| 有输入边界 | `boundary` |
| 改变业务状态 | `state_transition`、`persistence` |
| 有角色/权限要求 | `permission` |
| 依赖外部服务 | `dependency_failure` |
| 声明并发或幂等 | `concurrency` |

`FunctionCoverage.overall_coverage` 由 `coverage_by_dimension` 汇总，不允许手填一个“已覆盖”掩盖某个维度缺口；`BusinessFunction` 目录本身不保存覆盖状态。维度确认不适用时记为 `not_applicable`，汇总时忽略；全部维度都不适用时功能级为 `not_applicable`。

AI 可以补充维度，但必须说明理由；用户可以覆盖，覆盖也要理由。最终 `required_dimensions` 写入清单并参与 `full` 门禁，不由模型在每次计划生成时临时决定。

### 4.6 与验收项的双向映射

```text
AcceptanceItem / TestIntent（为什么测）
  ↕
BusinessFunction（项目能做什么）
  ↕
CoverageClaim（本次承诺覆盖什么）
  ↕
Case / Evidence / Verification（怎么证明）
```

规则：

- 每个 `TestIntent` 至少映射一个业务功能与必要维度；
- 每个范围内业务功能至少映射一个 `TestIntent`，或明确标记“范围外”；
- 每个 `CoverageClaim` 至少映射一条用例/证据；没有 claim 的功能不能算“已覆盖”；
- 没有功能支撑的验收项不能算“完整验证”；

`CoverageContract` 冻结 `coverage_claims`；每条 claim 的 `function_id`/`dimension` 必须出现在 `function_requirements` 中，`case_ids` 非空。发布门禁用 claim 校验每个适用 `b∈B` 至少一条用例，而不是只看功能名是否出现。
- 业务功能清单不替代 `AcceptanceScope`，它是完整性检查。

### 4.7 完整性审计

清单不能只靠 AI 生成。建议多源交叉：

1. 路由/端点扫描；
2. CLI 命令注册；
3. 页面入口/菜单/表单；
4. 事件消费者、定时任务、Webhook；
5. 状态机/状态字段；
6. 领域模型/业务规则；
7. AI 语义补充；
8. 用户确认清单完整性（不只是确认计划）。

未识别的部分进入 `unknown` 桶，不能默认“没有”。`full` 前必须由用户确认“清单完整、unknown 数已知”，不能只靠 AI 自述。清单输出完整性声明：

```text
已识别 N 个业务功能；
来源：路由、CLI、页面、事件、状态机；
未识别/待确认：K 个；
本次范围：M 个。
```

### 4.8 去重与版本

- 规范化键：`business_object + action + trigger`；
- `aliases` 记录同一功能的其他入口；
- `canonical_function_id` 指向主功能；
- 避免同一能力被重复计数为多个“已覆盖”；
- 清单绑定 `understanding_id`、`understanding_revision`、`source_snapshot_id`；
- 源码、范围或清单修正都生成新的 understanding 修订；旧修订保留，不能直接沿用 `full`；
- `BusinessFunctionCatalog` 随 understanding 版本化；`FunctionCoverage` 随计划/运行版本化；覆盖不修改目录。

### 4.9 完整验证当前范围

对外文案统一用“完整验证当前范围”；“完整测试项目”只作为历史称呼，不作为界面文案。

“完整验证当前范围”指覆盖当前项目范围内全部适用业务功能，不是读取全部代码行；它与“全项目所有代码都通过”不是一回事：

- 前提：`BusinessFunctionCatalog` 完整、无 `unknown`；
- 每个适用功能 × 必要维度都有 `FunctionCoverage` 证据；
- 不适用有理由；未支持为缺口；
- 存在缺口时不能判完整通过，只能转为按需验证或补齐能力；
- 大型项目按模块/服务/业务域分范围。

### 4.10 大型项目

- 先按模块/服务/业务域生成子清单；
- 支持增量刷新；
- `full` 只对当前范围的子清单负责；
- 并行、分片、CI 导入作为后续优化；
- 不因大型项目暂不支持而放弃业务功能完整性。

## 5. 计划生成

### 5.1 模板作为提醒清单

模板不是定死的清单，而是 AI 制定计划时的提醒：

- 提醒 AI 不要忘记某些通用风险；
- AI 读源码后可以新增项目检查；
- AI 对模板项逐项给出适用性（applicable/not_applicable/unknown）与覆盖（covered/uncovered/deferred），并给出理由和证据；
- 不允许静默删除模板项；
- 模板不是“重要项清单”，所有进入最终计划的检查项平级。

### 5.2 模板项处置

模板项拆成两个正交轴，不再用一个三态混住“项目是否需要”和“本次是否覆盖”：

| 轴 | 取值 | 含义 |
| --- | --- | --- |
| 适用性 | `applicable` / `not_applicable` / `unknown` | 项目是否需要这项检查 |
| 覆盖 | `covered` / `uncovered` / `deferred` | 本次计划是否已有用例、证据和独立核验 |

派生处置：

| 适用性 | 覆盖 | 处置 | `full` |
| --- | --- | --- | --- |
| `applicable` | `covered` | `included` | 允许 |
| `applicable` | `uncovered` | `uncovered` | 阻止 |
| `applicable` | `deferred` | `deferred` | 阻止 `full`，转 `on_demand` |
| `not_applicable` | — | `not_applicable` | 允许，需理由与证据 |
| `unknown` | — | `needs_review` | 阻止，先补清单 |

`unsupported` 不是独立轴，而是 `applicable` + `CapabilityGap.blocks_full=true` 的派生结果；对外仍可投影为“已知限制”。

`not_applicable` 如果与项目信号冲突，转为 `needs_review`。缺失任一轴都算处置不完整，阻止 `full`。

### 5.3 AI 新增检查

- 模板缺口、项目特有风险可以由 AI 新增检查；
- 所有新增必须有预期、断言依据、独立核验和证据要求；
- 来源（模板/AI/用户）不默认展示，技术详情可查。

必要性按覆盖缺口判定，不由模型自报：

| 类型 | 判定 | 去向 |
| --- | --- | --- |
| 必要新增 | 填补某个适用功能 × 必要维度的缺口，或某个 `applicable` 模板项没有对应检查 | 进入 `full`，与模板项平级 |
| 可选新增 | 不填补上述缺口，只是更细或更多组合 | 进入 `on_demand` 建议清单，不进入 `full` |

这样 AI 不能通过“多生成检查”把计划撑大，也不能用无关检查抵消漏项。

### 5.4 最小充分计划

- 每条检查必须映射到业务功能 × 必要维度，或一个模板提醒项；
- 不允许重复检查；
- 超出必要维度的检查是可选补充；
- `full` 只包含证明目标所需的最小充分集；
- 用户可把可选检查提升为必测，但那是 `on_demand` 或新计划。

### 5.5 计划校验

计划按顺序校验，后面的项不能抵消前面的缺口：

1. **业务功能 × 必要维度覆盖**（硬门禁）：每个适用 `b∈B` 至少一条用例、有效证据和独立核验；
2. **模板项适用性/覆盖审计**：`unknown`、`uncovered`、缺失处置阻止 `full`；`deferred` 转 `on_demand`；
3. **关键链路覆盖**：必须真实的依赖和不可省核验没有缺口；
4. **断言依据/独立核验**：缺失依据不能进入 `full` 必测；
5. **不静默删除**：不在 `full` 中删除必测或弱化断言。

模板项审计只做补充检查，不能覆盖或抵消第 1 项的功能×维度缺口。

### 5.6 模板质量与演进

- AI 反复新增的检查 → 模板候选；
- 模板项频繁不适用 → 模板评审；
- 未支持项集中 → 能力建设优先级；
- 模板 lint：可判定、有证据要求、不含项目特定值；
- 模板版本不可变；旧计划引用旧版本；迁移生成新计划修订。

## 6. 计划确认与执行授权

### 6.1 确认页

前端默认只保留一个确认页：

```text
本次验证范围
覆盖收据（预览）
  将验证：4 个功能 × 6 个维度
  将不验证：1 个功能（插件暂不支持）
  未识别：1 个
已知限制
执行影响
执行方式
需要你确认
```

覆盖收据是计划冻结的 `FunctionCoverage` 预览，不是报告；用户确认后按同一收据生成报告，避免确认页和报告各说一套。

执行方式显示：

```text
执行方式
  - 插件执行：3 步
  - 人工执行：1 步
  - AI 辅助决策：2 步（AI 决定参数，插件执行）
```

一期不包含 AI 直接操作工具。

不默认显示：

- 模板项、模板版本；
- AI 新增标记；
- 常规“不适用”清单；
- 用例 ID、步骤 ID、输入摘要、修订号。

### 6.2 full 不可编辑

`full` 下用户不能修改范围、检查项、预期、断言依据、执行影响和许可范围；只能确认、取消、改为按需验证或展开技术详情。

任何修改都转 `on_demand`，原 `full` 计划保留为候选。

### 6.3 已知限制与 full 可用性

| 情况 | 是否允许 `full` | 前端 |
| --- | --- | --- |
| 项目没有该能力（不适用） | 允许 | 默认不显示 |
| 项目有该能力，插件不支持（未支持） | 不允许 | 显示“已知限制” |
| 范围内业务功能未覆盖 | 不允许 | 显示缺口 |
| 清单存在 `unknown` | 不允许 | 显示“需要补充” |
| 无上述缺口 | 允许 | 显示“完整验证覆盖本次范围” |

如果存在缺口：

```text
完整验证暂不可用：
  - 取消订单：插件暂不支持
  - 定时对账任务：未识别

你可以：
  [补充项目说明]
  [缩小到已识别范围]
  [改为按需验证]
  [重试生成计划]
```

不能出现“有缺口但还能确认完整验证”的按钮。

### 6.4 PlanExecutionGrant

采用计划级执行许可，保留授权事实，删除许可内的逐动作交互：

- 用户确认计划时，后端分别记录计划确认、`PlanExecutionGrant`、每条用例的断言依据确认；
- 许可绑定：计划修订、understanding 中与本次范围相关的部分、范围、允许的动作类别、凭据范围、环境、风险等级、副作用预算、允许主机、时间窗、失效条件；
- 计划内、许可内动作自动执行，记录 `authorization_source=plan_grant`；
- 计划外、许可外、新凭据、扩大范围、运行动态动作：暂停，逐动作确认；
- 新 Attempt 是否复用许可，按同一计划/许可/动作类别判断；输入或目标变化则暂停；
- 失效按影响判断：计划、范围、动作类别、凭据、环境变化 → 失效；understanding/源码变化若影响本次计划的功能、维度或动作 → 失效；无关变化记录但不撤销；无法判断影响时按失效处理；
- 报告区分授权来源 `human_confirmation` / `plan_grant`；AI 生成的分析单独标 `ai_generated`，不作为授权来源；
- `plan_grant` 可以作为 A 级证据的授权来源，但报告必须标注授权来源。

`PlanExecutionGrant` 不是无限授权，而是带预算的能力信封：

| 字段 | 作用 |
| --- | --- |
| `grant_scope_digest` | 计划、understanding 相关部分、范围、动作类别、凭据、环境的摘要 |
| `risk_class` | low / medium / high |
| `max_side_effect_actions` | 本次许可最多允许的副作用动作数 |
| `max_data_mutation` | 最多允许修改的业务对象/行数 |
| `allowed_hosts` | 允许访问的目标主机 |
| `time_window` | 许可有效时间窗 |
| `budget` | 其他资源上限（如外部调用次数） |

`PlanExecutionGrant` 保存计划的 `scope_digest`；`grant_scope_digest` 是上述字段的组合摘要，写入 `ActionAuthorization`，不重复存一份。`allowed_hosts` 由动作解析层核对实际目标；`grant_allows` 只做计划级的动作类别/凭据/环境/时间窗匹配。副作用次数、数据变更量和预算由执行层累计，超出后暂停。

已实现动作类别、凭据、环境、时间窗、失效、`max_side_effect_actions` 与 `max_data_mutation` 累计拦截、HTTP entrypoint 的 `allowed_hosts` 核对。一期动作还没有独立的“业务数据变更量”声明，`max_data_mutation` 按非只读动作保守计数（`unknown` 也计入）；该口径不改变 `P1-AC31` 的硬断言。

`PlanExecutionGrant` 不替代 `ActionAuthorization`，而是授权来源：

| 层 | 记录 | 作用 |
| --- | --- | --- |
| 计划确认 | `PlanConfirmation` | 人确认计划及影响 |
| 计划许可 | `PlanExecutionGrant` | 绑定计划、understanding 相关部分、范围、动作类别、凭据、环境、能力信封 |
| 动作授权 | `ActionAuthorization`（每个副作用动作一条） | 记录该动作被许可；`source=plan_grant` 或 `human_confirmation`；带 `grant_id`/`grant_scope_digest` |
| 人工交互 | `UserInteraction` / `ConfirmationRecord` | 仅越界动作需要新的交互 |

动作执行前，核心解析动作摘要、类别、凭据、环境；与许可匹配则生成或复用 `ActionAuthorization(source=plan_grant)`；不匹配则 `waiting_authorization`。这样“每个动作有记录”和“人不逐动作点击”可以同时成立。

断言依据确认同样按用例逐条记录，但共享同一次计划确认交互；不是逐用例点击。

### 6.5 越界动作确认

以下情况才弹确认窗口：

- 计划外动作；
- 许可外动作；
- 新凭据；
- 访问生产环境；
- 扩大范围；
- 删除数据；
- 运行时才解析且超出许可类别的动作。

窗口内容：

```text
这一步会做什么
会影响什么
为什么需要确认
允许/不允许的影响
```

### 6.6 记录与 provenance

- 计划确认、执行许可、依据确认分开保存；
- 每个动作记录授权来源、`grant_id` 与 `grant_scope_digest`；
- `plan_grant` 不等于“每个动作都人工确认”；
- AI 生成的分析是假设，不是结论；
- 报告可追溯到准确计划、清单、许可、能力信封和证据。

### 6.7 AI 在执行中的角色

| 角色 | 谁执行 | 一期 |
| --- | --- | --- |
| AI 规划，核心执行 | AI 生成计划；核心跑命令/HTTP/人工步骤 | 已支持 |
| AI 辅助决策 | AI 决定下一步/参数；插件执行 | 目标形态 |
| AI 直接操作工具 | AI 自己点击、调用浏览器/桌面/HTTP | **不在一期** |
| AI 分析 | AI 只分析失败和证据 | 已支持 |
| 被测对象是 AI | 记录被测 Agent 的工具调用 | 已支持（agent-workflow） |

一期采用“AI 辅助决策 + 插件执行”，不包含 AI 直接操作工具。

## 7. 执行与运行

### 7.1 档位、驱动与许可

| 概念 | 决定什么 |
| --- | --- |
| 档位 `RunTier` | 跑什么范围、能不能判完整通过、是否打分 |
| 驱动 `RunDriver` | 怎么推进、确认节奏 |
| 执行许可 `PlanExecutionGrant` | 哪些动作已被授权 |

- 现行驱动只有 `planned` / `stepwise`，没有 `auto`；
- `planned` 是“自动推进”，不是“自动授权”；
- 最简 AI 主导组合：`full` + `planned` + `PlanExecutionGrant`；
- `stepwise` 是可选的人工介入方式；
- `on_demand` 是用户修改计划或范围后的档位；
- 档位/驱动按运行选择，不进入全局配置。

### 7.2 自动执行

- 计划内、许可内动作自动执行；
- 运行时才解析、且属于许可声明类别的动作自动执行；
- 超出许可类别、新凭据、扩大范围、计划外动作暂停逐动作确认；
- 许可撤销/过期后暂停，重新确认。

### 7.3 人工介入

| 介入 | 何时可用 | 语义 | 对结论的影响 |
| --- | --- | --- | --- |
| 暂停 | 运行中 | 步骤边界生效；正在执行的步骤先收尾 | 不改变已执行事实 |
| 恢复 | 已暂停 | 从未执行步骤继续 | 不重跑已完成步骤 |
| 取消 | 运行中 | 先登记取消意图；确认停止后才算已取消 | 未确认保持“取消中/待核实” |
| 重试 | 步骤失败/完成 | 创建新 Attempt，立即成为当前；旧尝试保留 | 新尝试失败不退回旧通过 |
| 退回阶段 | 步骤失败/需要重做 | 创建新 Attempt，并把下游标为需重跑 | 旧证据保留，不记为已重跑 |
| 补证 | 任意步骤 | 登记人工材料，关联准确 Attempt | 补证不等于通过 |
| 核实未知 | 结果未知 | 查询原执行/业务对象，确认是否发生 | 未核实前不重跑 |
| 继续人工步骤 | 待你操作 | 用户实际执行，记录步骤与证据 | 不录制回放 |
| 收窄驱动 | 步骤边界 | `planned → stepwise` | 不改变结论口径 |
| 撤销许可 | 运行中/暂停 | 撤销 `PlanExecutionGrant` | 后续动作暂停 |

`full` 运行中不允许修改计划：

- 只能暂停、取消、重试、补证、核实、收窄驱动；
- 任何范围、预期、依据变化，都新建 `on_demand` 运行；
- 原 `full` 运行保留为历史，不删除、不改写；
- `full` 的收窄驱动记录为无 `step_changes` 的 `RunPlanRevision`；它是控制变更，不是计划内容修改。

### 7.4 未知结果

- 先核实执行与业务对象；
- 不自动重试、不新建意图；
- 未确认停止前显示“取消中/待核实”；
- 不能显示“已取消”或“已通过”。

### 7.5 退出与重开

- 关闭编辑器不等于取消；
- 核心继续管理运行；
- 重开回到同一运行、同一状态；
- 暂停不会被自动解除；
- 未知副作用先核实，不自动重放。

## 8. 报告与可信度

### 8.1 业务结论

业务结论只使用：

- 通过；
- 失败；
- 未完成；
- 不适用。

业务结论与证据等级、可信度分开。

### 8.2 可信度

默认显示“可信度：高/中/低”，但它只是汇总，不是单一事实：

| 可信度 | 判定规则 |
| --- | --- |
| 高 | `full`；所有适用功能 × 必要维度有有效执行与独立核验；无 `unknown`/`unsupported`；证据完整 |
| 中 | 真实执行且结论为通过/失败，但存在证据或核验缺口；或 `on_demand` 但范围内完整 |
| 低 | 未完成、结果未知、关键依赖未确认；或存在未支持/未覆盖导致结论不完整 |

每个功能/维度还要有独立状态：

| 状态 | 含义 |
| --- | --- |
| `proven` | 有效执行 + 有效证据 + 独立核验 |
| `partial` | 部分维度有效，仍有明确缺口 |
| `not_proven` | 未执行、结果未知或证据无效 |
| `unsupported` | 插件当前做不到，已登记 `CapabilityGap` |
| `unknown` | 清单未识别或待确认 |
| `planned` | 计划已承诺、尚未执行；只用于确认页预览，不等于已验证 |
| `not_applicable` | 该维度已确认不适用，需理由与证据；汇总时忽略 |

功能级汇总优先级：`unsupported` > `unknown` > 任一 `not_proven` > 全部 `planned` > `partial` > `proven`；`not_applicable` 不计入汇总，全部维度都不适用时功能级为 `not_applicable`。已知能力缺口或未识别区域不能被 `planned`/`partial` 掩盖。

可信度由领域规则计算一次，不由 AI 打分。A—D 放到技术详情，供测试工程师查看。

### 8.3 业务功能覆盖收据

```text
覆盖收据
业务功能        必要维度                 状态       缺口
订单创建        normal/boundary/error    proven     —
订单查询        normal/error             proven     —
取消订单        normal/permission        partial    permission 未覆盖
定时对账        —                        unknown    未识别

汇总
  功能：4 个；功能×维度：12 个
  proven：9；partial：1；unsupported：0；unknown：2（定时对账未识别，按 2 个维度计）
```

功能级“已验证”只在所有必要维度都有效时成立；只覆盖部分维度时显示“部分覆盖（缺：permission）”，不能把功能级数量当成维度级完整。

并写明：

```text
完整验证只对本次范围成立。
```

### 8.4 证据与导出

- 原始证据保留；
- 摘要与证据包分开；
- 导出不含凭据；
- 缺附件列缺口；
- 永久保留，不提供删除；
- 技术标识折叠到技术详情。

### 8.5 下一步

报告首屏回答：

1. 通过了吗；
2. 哪些没测到；
3. 为什么可信或不可信；
4. 下一步做什么。

## 10. AI 不确定与失败

### 10.1 失败分类

| 情况 | 处理 | 是否允许 `full` |
| --- | --- | --- |
| 模型不可用（无凭据/网络/超时/限流） | 阻塞；回退人工/模板；不自动修补 | 否 |
| 非法 JSON / Schema 不符 | 保存原始响应；`structured_output_invalid`；用户重试或人工 | 否 |
| 计划缺少业务功能或必要维度 | 返回覆盖缺口；补范围或转 `on_demand` | 否 |
| 清单不完整 | 进入 `unknown` 桶；显示“需要补充” | 否 |
| 业务规则不明确 | 向用户提问；不编造预期 | 否 |

| AI 置信度低 | 标记“需要重点核对” | 视缺口而定 |
| 源码变化 | 计划过期；重新理解、重新生成 | 否 |
| AI 生成过多检查 | 只保留最小充分集；额外检查转可选 | 是，若最小充分集完整 |
| 模型输出含敏感材料 | 落盘前过滤；无法安全处理则登记缺口 | 否 |

### 10.2 用户可见行为

只显示三件事：

```text
现在卡在哪
为什么
你可以做什么
```

缺少业务规则时直接提问，例如：

```text
订单状态是否允许从“已创建”直接变为“已发货”？
  [允许]
  [不允许]
  [只在特定角色下允许]
```

### 10.3 重试与记录

- 不自动重试；
- 用户显式重试时创建新的生成意图，旧响应保留；

- 不暗中切换供应商；
- 源码变化后旧计划标记过期，不能强行确认；
- 重试成功生成新的计划修订。

### 10.4 执行阶段不受影响

- 计划确认后执行使用冻结计划；
- 模型失败不影响原始证据和报告；
- 运行时缺凭据、未知副作用暂停核实。

### 12.4 模板与业务功能

| 编号 | 决策 | 结论 |
| --- | --- | --- |
| TPL-01 | 模板定位 | 提醒清单；AI 逐项处置；不能静默删除 |
| TPL-02 | AI 新增检查 | 必要新增与模板项平级；可选新增不进 `full` |
| TPL-03 | 模板项两轴 | 适用性（applicable/not_applicable/unknown）× 覆盖（covered/uncovered/deferred）；派生 included/uncovered/needs_review/unsupported |
| TPL-04 | 业务功能粒度 | 业务能力，不是内部代码函数 |
| TPL-05 | 业务功能层级 | 业务域 → 功能 → 流程 → 操作/规则 |
| TPL-06 | 覆盖方式 | `BusinessFunction` × 必要维度；`FunctionCoverage` 记录本次覆盖 |
| TPL-07 | 验收项映射 | `TestIntent` ↔ 业务功能 ↔ `CoverageClaim` ↔ 用例/证据 |
| TPL-08 | 清单作为门禁 | 业务功能清单作为 `full` 覆盖依据 |
| TPL-09 | 完整性审计 | 多源扫描 + AI + 用户确认 + `unknown` 桶 |
| TPL-10 | 清单版本 | `BusinessFunctionCatalog` 绑定 `source_snapshot_id`、`understanding_revision`；`FunctionCoverage` 绑定计划/运行；覆盖不反写目录 |
| TPL-11 | 去重 | `business_object + action + trigger`；`aliases`/`canonical_function_id` |
| TPL-12 | 清单与范围 | 清单不替代 `AcceptanceScope`，只做完整性检查 |
| TPL-13 | 完整验证当前范围 | 覆盖范围内全部适用业务功能；有缺口不得判完整通过 |
| TPL-14 | 大型项目 | 先按模块/服务/业务域；并行/分片后续 |
| TPL-15 | 合同更新 | “所有业务功能”需要新增/更新 FR/AC |
| TPL-16 | 模板演进 | 反复新增的检查 → 模板候选；频繁不适用 → 模板评审 |
| TPL-17 | 新增必要性 | 按覆盖缺口判定，不由模型自报；必要进 `full`，可选进 `on_demand` |
| TPL-18 | 维度派生 | 先按功能属性规则派生，AI/用户补充需理由，结果写入 `BusinessFunction` 并参与门禁 |
| TPL-19 | 完整性的确认 | `full` 前用户确认“目录完整、unknown 数已知”；不能只靠 AI 自述 |
| TPL-20 | 覆盖 claim | `CoverageContract` 冻结 `coverage_claims`；每个功能×必要维度至少一条 claim，claim 用例必须在冻结集合内 |
| TPL-21 | 覆盖状态 | `FunctionCoverage` 支持 `not_applicable`；汇总优先级 `unsupported > unknown > 全部 proven > 全部 not_proven > partial` |

## 附录 A 术语表

| 术语 | 含义 |
| --- | --- |
| 项目理解 | 一次源码/范围扫描产生的 `ProjectContext`、项目信号、业务功能目录、业务意图、目标候选与能力缺口，统一修订 |
| 业务功能目录 | 稳定的 `BusinessFunction` 集合，只描述“项目能做什么” |
| 功能覆盖 | `FunctionCoverage`，每次计划/运行的功能×维度覆盖投影，不反写目录 |
| 业务意图 | `TestIntent`，固定“为什么测、要证明什么”，是 `AcceptanceItem` 的业务视图 |
| 覆盖主张 | `CoverageClaim`，连接 intent × function × dimension 与用例/证据 |
| 能力缺口 | `CapabilityGap`，插件/适配器暂时做不到的部分，不是项目属性 |
| 必要维度 | 该功能必须验证的维度，先按规则派生，允许有理由的补充 |
| 计划修订 | 不可变的计划、用例、覆盖契约与断言依据集合 |
| 执行许可 | 计划级 `PlanExecutionGrant`，绑定计划、理解相关部分、范围、动作类别、凭据、环境与能力信封 |
| 越界动作 | 不在许可内的动作，需要新的确认 |
| 覆盖收据 | 确认页预览和报告中的功能×维度状态清单，说明验证了什么、没验证什么 |
| 完整验证当前范围 | 覆盖当前范围内全部适用功能 × 必要维度，不等于全项目所有代码 |
| 可信度 | 高/中/低，由领域规则计算，不由 AI 打分；下面还有每项 `proven/partial/not_proven/unsupported/unknown` |
| 模板项 | 提醒 AI 的通用检查提示，不是必测清单；按“适用性×覆盖”处置 |
