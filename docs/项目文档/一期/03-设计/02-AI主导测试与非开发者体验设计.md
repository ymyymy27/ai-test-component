# AI 主导测试与非开发者体验设计

> 适用期次：一期；主责：产品形态、角色与体验原则、端到端流程、配置分层、AI 失败表达；状态：设计基线。实现与验收状态以[项目现状](../../../现状.md)和[验收台账](../05-测试验收/02-验收台账.md)为准，本册不登记通过。

本册把归档的《AI 主导与非开发者体验设计草案》中转正的设计内容收敛为现行基线，并说明《计划确认证明模型》在现行合同中的落点。字段、枚举、状态迁移和校验仍由[业务方案](../02-需求/01-业务方案.md)、[需求规格](../02-需求/02-需求规格.md)、[功能清单](../02-需求/03-功能清单.md)与[架构分册](../04-架构/01-架构总览.md)主责；页面与文案见[产品方案与界面设计](01-产品方案与界面设计.md)。

## 1 一页结论

```text
建项目
→ （可选）说目标
→ AI 理解项目并给出目标候选
→ 用户选目标
→ AI 生成计划
→ 用户确认一次
→ 计划驱动自动执行
→ 报告
```

六项设计：

1. **一次项目理解**：同一修订产出项目上下文、业务功能目录、测试意图与目标候选；不另造第二套项目模型。
2. **目录与覆盖分开**：业务功能是稳定目录，覆盖是每次计划/运行的投影；覆盖事实不反写目录。
3. **清单回答“有没有漏”**：模板只做提醒；完整验证门禁看业务功能 × 必要维度；模板项拆成“适用性 × 覆盖”。
4. **目标按风险选**：候选按变更 × 影响 × 历史排序，并显示推荐理由。
5. **用户只确认一页**：范围、覆盖收据、已知限制、执行影响、执行方式；完整验证不可编辑，修改转按需执行。
6. **一次确认产生三类记录 + 能力信封**：计划确认、计划级执行许可、逐条断言依据确认；计划内自动执行，越界暂停；报告给覆盖收据与逐项可信度。

一期不做：AI 直接操作浏览器/桌面/工具、全项目一次全量覆盖、并行/分布式执行、平台上传。

## 2 角色与设计原则

| 角色 | 关心什么 | 默认看到什么 |
| --- | --- | --- |
| 业务用户 | 这次测什么、能否证明业务正确、还差什么 | 目标候选、计划确认、运行状态、报告结论 |
| 测试工程师 | 计划、用例、证据、授权、诊断 | 技术详情、用例编号、授权范围、原始材料 |
| 审计/复核 | 谁批准了什么、证据在哪 | 技术详情、授权来源、证据引用 |

业务用户不需要理解代码结构、测试设计语言或内部标识。

设计原则：

1. 全局设置只做一次，项目流程可重复。
2. 全局只配“怎么连模型”，不配“怎么测项目”。
3. AI 负责起草和适配，人负责决定和确认。
4. 用户确认后果，不确认技术机制。
5. 默认只显示业务语言，技术详情折叠。
6. 不隐藏未支持、未覆盖、未知。
7. 完整验证不可编辑；修改转按需执行。
8. AI 不能自证通过；执行结果仍需独立核验。

不可简化的事实边界：人工确认计划、计划级执行许可、证据来源、未执行/未验证/未覆盖范围、结论不确定性、失败与问题处置。简化的是表达与操作，不是事实与门禁。

## 3 端到端体验

### 3.1 首次使用与建项目

首次只配置插件级设置：模型配置档（名称、供应商、地址、模型、Key 引用、超时）、默认配置档、Python 路径、用户数据根目录；不创建项目。

现行向导把项目创建并入六步（选择项目、准备环境、发现测试、生成计划、核对发布、准备运行），首步承接“首次设置”的模型连接；完整步骤与失败处理见[产品方案与界面设计 §2](01-产品方案与界面设计.md#2-首次向导)。本册保留的原则是：模型连接配置一次长期复用；Key 只进系统凭据管理器；可跳过模型配置，模板/人工流程仍可用；测试连接失败允许保存但标“未验证”；正常流程不显示载体登记、业务查询等内部名称。

### 3.2 项目理解

每个源码版本、每个测试范围只做一次完整扫描，发生在建项目之后、生成目标之前。输入是源码快照、选定范围与排除规则；处理为全范围确定性扫描加 AI 语义补充；输出为同一 `understanding` 修订下的项目上下文、信号、业务功能目录、测试意图、目标候选与能力缺口。

“完整读源码”指全范围扫描，不是把全部字节发给模型：

| 任务 | 靠什么 |
| --- | --- |
| 发现有哪些业务功能 | 全范围扫描：路由、CLI、页面、事件、定时任务、状态字段、领域模型 |
| 理解某个功能细节 | 只读该功能的局部源码片段 |
| 证明没有漏功能 | 业务功能目录 + 未知桶 + 覆盖门禁 + 用户确认 |

局部源码发现目录外功能时，必须补入目录或标为未知，不能忽略。目录与覆盖的字段合同见[项目与计划 §3—4](../04-架构/02-项目与计划.md#3-项目理解与业务功能目录)，覆盖判定口径只在[功能清单 §3](../02-需求/03-功能清单.md#3-判定与统计唯一口径)。

### 3.3 目标确定

先问三个业务问题，而不是让用户选测试项：最近改了什么、坏了最疼什么、哪里最常出问题。目标候选由业务功能目录与测试意图生成，按“变更 × 影响 × 历史风险”排序，并显示推荐理由。

“完整验证当前范围”只有在目录完整、无未知区域时才可选；文案要写明“覆盖当前范围内的全部适用业务功能，不等于全项目所有代码”，避免被理解为整个项目 100% 通过。目标绑定项目理解修订；目标候选只是测试意图的界面投影，不是第二套验收对象。

### 3.4 计划生成

复用同一次项目理解，不重新全量读源码。模板作为提醒清单，AI 逐项给出“适用性 × 覆盖”处置；AI 可以新增项目检查；最终计划内所有检查项平级；完整验证只包含证明目标所需的最小充分集。模板项处置与覆盖门禁见[功能清单 §7.3](../02-需求/03-功能清单.md#73-模板项处置与覆盖)。

### 3.5 计划确认与执行

用户只确认一个页面：本次验证范围、覆盖收据预览、已知限制、执行影响、执行方式、需要确认的后果。覆盖收据是计划冻结时的覆盖投影，不是报告；确认后按同一收据生成报告，避免确认页与报告各说一套。

完整验证下所有检查项平级且全部必测，只能整体确认；修改即转按需执行，原计划保留为候选。

一次确认产生三类记录：计划确认、计划级执行许可、每条用例的断言依据确认。三者共享同一次用户交互，但各自独立保存；一次点击不是三次点击，每条用例仍有自己的依据确认。默认在宿主面板内确认；CLI 等非面板入口回退到核心原生窗口。证明链、派生顺序、校验与失败语义见[计划确认证明模型](../04-架构/06-Trae接入.md#7-计划确认证明模型)。

执行期：已发布计划驱动自动推进；计划内且许可内动作自动执行；越界动作暂停确认；用户可暂停、取消、重试、补证、核实；完整验证运行中不允许改写计划。

### 3.6 报告与退出恢复

报告把业务结论与可信度分开，显示业务功能覆盖，显示未支持、未覆盖、不适用与未知，写明“完整验证只对本次范围成立”，技术标识折叠到技术详情。

关闭编辑器不等于取消；核心继续管理运行；重开回到同一运行与同一状态；暂停不被自动解除；未知副作用先核实，不自动重放。

## 4 配置模型

配置按“全局 / 项目 / 运行”三层分开，避免把项目选择塞进全局：

| 层 | 内容 | 规则 |
| --- | --- | --- |
| 全局 | 模型配置档、默认配置档、Python 路径、用户数据根目录、语言与通知偏好 | 一次配置长期复用；不放假位、驱动、材料范围或项目路径 |
| 项目 | 项目目录与名称、入口/解释器/虚拟环境探测、数据隔离与复位、模型配置档、模型材料范围、源码片段开关 | 换配置档或改材料范围要重新确认；源码片段默认关闭 |
| 运行 | 测试目标、档位、驱动、范围 | 每次运行选择；范围由目标与计划确定 |

模型配置档与凭据：全局可存多个档；项目选择使用哪个；Key 只存引用、不显示正文；显示“已配置/未配置”；支持更换、测试连接与失效提示；Key 轮换不影响已有报告。

材料范围是项目级安全决定：默认允许项目名称/目标和模板骨架；默认关闭源码片段；不发送 Key、业务系统凭据或完整源码仓库；开启源码片段后只发送相关片段；材料范围变化要重新确认。这是模型出站，不是三期平台上传。

默认值与自动探测：入口、解释器、虚拟环境、工作空间、项目编号、模型端点优先自动探测。环境异常时用业务语言说明（Python 版本、多个入口、找不到入口、数据目录不可写、非 Git 项目不显示仓库字段），不默认显示绝对路径。

项目列表显示项目、上次运行相对时间与状态，提供新建、继续上次、打开报告；运行中/待操作/待核实显示在侧栏，完成或阻塞给通知；记录永久保留，不提供删除，只提供导出/备份与隐藏项目。

## 5 AI 不确定与失败

| 情况 | 处理 | 是否允许完整验证 |
| --- | --- | --- |
| 模型不可用（无凭据/网络/超时/限流） | 阻塞；回退人工/模板；不自动修补 | 否 |
| 非法 JSON / Schema 不符 | 保存原始响应，标结构化输出无效；用户重试或人工 | 否 |
| 计划缺少业务功能或必要维度 | 返回覆盖缺口；补范围或转按需执行 | 否 |
| 目录不完整 | 进入未知桶，显示“需要补充” | 否 |
| 业务规则不明确 | 向用户提问，不编造预期 | 否 |
| 项目有该能力、插件不支持 | 标已知限制 | 否 |
| AI 置信度低 | 标“需要重点核对” | 视缺口而定 |
| 源码变化 | 计划过期，重新理解、重新生成 | 否 |
| AI 生成过多检查 | 只保留最小充分集，额外检查转可选 | 是，若最小充分集完整 |
| 模型输出含敏感材料 | 落盘前过滤；无法安全处理则登记缺口 | 否 |

用户可见行为只回答三件事：现在卡在哪、为什么、可以做什么。缺业务规则时直接提问并给业务选项（允许/不允许/只在特定角色下允许），不要求用户理解测试术语。重试沿用同一业务意图，不重复写记录；失败与原始响应留痕，不自动修补成“成功”。

## 6 非开发者界面细则

- 业务语言优先：结论只用通过、失败、未完成、不适用；证据等级带中文含义或“本轮未评级”，等级不是放行按钮。
- 不写百分比、分数或通过率；覆盖写成“必测 12 项，已执行 11 项”这类带分母计数。
- 执行完成、有效验证、有效通过/失败分列，不合并成“完成率”。
- 按钮用明确动词（开始执行、确认并授权、核验这次执行结果、复制复测简报）；错误必须给可执行的下一步。
- 状态不只靠颜色表达；主要动作可键盘完成；对话框关闭后焦点回到触发按钮。
- 技术详情折叠：用例编号、原始材料、授权来源、诊断原文只进技术详情，不出现在业务主路径。
- 页面状态、空态与禁用文案的完整清单见[产品方案与界面设计 §6](01-产品方案与界面设计.md#6-状态空态与文案)。

用户验证指标（设计目标，不是已验收数据）：业务用户能在不理解测试工程术语的情况下完成一次计划确认；确认页能说清“测什么、不测什么、代价是什么”；报告能回答“还差什么”；失败时用户知道下一步，而不是只看到错误码。

## 7 关键决策记录

| 决策 | 结论 | 理由 |
| --- | --- | --- |
| 项目理解与模板/计划的关系 | 一次 understanding，模板与计划都引用同一修订 | 避免画像、目录、目标各维护一套修订而不同步 |
| 目录与覆盖 | 目录稳定，覆盖是投影 | 覆盖变化不应改写业务功能身份 |
| 模板项处置 | 适用性 × 覆盖两轴，不再用一个三态混住两件事 | 让“不适用”和“未覆盖”可分别审计 |
| 完整验证可否编辑 | 不可编辑，修改转按需执行 | 防止静默缩小范围规避门禁 |
| 计划确认动作 | 复用 `publish_plan`，不新增 `confirm_plan` | 人只确认一次；新增动作会多一次交互 |
| 计划、许可、依据是否同批 | 计划发布是一个原子批次；许可与依据是可重放派生批次 | 派生失败不要求第二次确认；恢复按幂等意图补齐 |
| 越界动作 | 仍逐项确认并逐动作记录 | 计划许可不代表每个动作都可免记录 |
| AI 与人工边界 | AI 起草，人工确认；AI 不能自证通过 | 结论必须有独立证据与核验 |

## 8 实施状态与未实现

已落地（以代码与验收台账为准，本册不重复登记）：项目理解与业务功能目录、目标候选与选择、模板项两轴处置、覆盖契约与完整验证门禁、目录完整性确认、一次计划确认派生依据与许可、覆盖收据、模型配置档与最近项目。

未实现或未验证：

- 大型项目分片与完整大型项目覆盖；
- 模板反馈闭环；
- 真实 Trae/Tk 人工确认、真实宿主掉电/重启恢复与验收；
- 三期平台上传与对拍。
