# 报告与缺陷

本册覆盖 P1-FR14—P1-FR15：报告如何冻结与导出、本地复核如何与正文分离、问题如何统一编号与流转、关闭依据如何校验。业务结论、覆盖集合、证据等级与失败优先级的**唯一口径在[功能清单 §3](../02-需求/03-功能清单.md#3-判定与统计唯一口径)**，本册不重写公式，只写这些结论如何被快照、查询与呈现。

代码落点：领域 `src/aitest/domain/review/reports.py`（判定输入输出、报告快照、复核、导出键）与 `defects.py`（问题状态、关闭守卫、有效阻塞）；应用 `application/review/saved_reports.py`、`saved_defects.py`、`saved_exports.py`、`repair_brief.py`；只读 DTO 在 `interfaces/dto.py`。面板、MCP 与导出都读同一份已保存记录，不各自重算。

## 1 报告快照与不可变

`ReportSnapshot` 是一次判定的不可变冻结体，字段如下。

| 字段 | 代码事实 |
| --- | --- |
| `report_id` / `content_revision` | 报告编号与内容修订；同一编号的修订从 1 递增，不能改编号或换项目 |
| `context` | `ReportContext`：`project_id`、`run_id`、`run_revision`、`plan_revision_refs`、`scope_revision`、`scope_name`、`source_identity`、`environment_ref`、`rules_revision`、`acceptance_revision`、`template_revision`、`policy_version` |
| `decision` | `DecisionResult`：`business_outcome`、`evidence_grade`（仅 `full` 有值）、`primary_gap`、`gaps`、`decisive_failures`、`coverage`、`policy_version`、`case_ids_revision`、`source_commit`、`snapshot_commit_id`、`snapshot_cursor` |
| `evidence_refs` / `evidence_revisions` | 证据编号列表，以及编号→保存时冻结的证据修订；修订键必须是已声明证据的子集，读取方不得猜修订 |
| `issue_revisions` | `(issue_id, revision)` 对，按问题去重；报告只引用精确修订 |
| `created_at` | 本机记录时间（`Clock`）；没有开始/结束/采集时间字段 |

保存时的 payload 另有 `published_sequence`、`reuse`（候选数、计入用例、具名拒绝原因）、`execution_snapshot_ref`、`blocking_issue_ids`、`pytest_failures`、`pytest_baseline`、`layers`，以及 `decision.confidence`（高/中/低：`incomplete` 为低；功能覆盖出现 `unsupported/unknown/not_proven` 为低；A 级且全部 `proven/not_applicable` 为高；其余为中）。覆盖集合里还嵌入 `function_coverage` 收据（见 §4）。

不可变规则：

- 同一 `report_id` 的旧修订永不改写；新的有效证据、当前尝试或问题修订改变结论时，`create_report_revision` 生成 `content_revision + 1`。
- 生成前核对 `expected_revision` 是否等于当前修订，不等抛 `ReportRevisionConflict`；读取输入期间提交序号变化抛 `ReportGuardRefused`，调用方重新取同一已提交边界，不拼接不同时刻的“最新字段”。
- 报告的 `policy_version` 必须与上下文一致，且必须是当前默认策略版本，否则拒绝保存。
- 证据正文不复制进报告：只保存编号与修订，正文按引用读取。外部删除或损坏只形成证据缺口，不篡改历史正文。

### 当前结论与历史事实

报告冻结的是一份判定输入，不等于“当前结论”。当前结论键由项目、源码身份（含未提交差异或 plain 内容清单及排除规则）、适用范围、环境修订、规则/验收/模板修订与 `policy_version` 共同决定；同提交不同 diff 不合并，历史分组与当前结论键是不同用途。

- `quick` 与 `on_demand` 报告标“未打分”，只附覆盖摘要，不升级为完整通过，也不覆盖已有 `full` 结论。
- 新的 `full` 开始后显示“重新验证”；终止、取消或结果未知时不回退到旧绿灯。历史报告仍可查，但标为历史，不能当作当前通过依据。
- 报告页首固定范围名称与本轮结果，不能把局部验收描述成全项目已通过；`DecisionDTO` 与 `ReportSnapshot` 各自带范围、环境事实与证据缺口，环境类型本身不触发降级。
- 报告是本地过程记录与自检依据，不引入签名、防篡改组织认证或平台审核保证。

### 生成顺序

生成报告只有一条路径：固定输入修订集合（计划与运行修订、各 Step 当前 Attempt、被消费的上游 Attempt 与条件事实、依据确认、问题修订、来源绑定有效性）→ 纯判定器计算 `DecisionResult` → 经工作单元在同一提交保存报告、业务变更索引与幂等结果。判定不在面板、MCP 或导出器里第二次计算；任何一处显示的结论与保存的 `decision` 不一致都算缺陷。

- 报告只读取已提交事实：当前尝试、证据索引与问题修订；不修改执行记录，不复制证据正文。
- 上游 Attempt 发布后，下游旧通过不能继续作为当前依据；新报告修订列出受影响步骤与原因，历史报告与原断言不改。
- 采集安全状态随证据引用一起进入报告：来源未核实或凭据过滤影响必要核验时，报告列缺口，不把“采集成功”写成“业务通过”。

## 2 修订与复核

| 记录 | 最小字段 |
| --- | --- |
| `LocalReview` | `review_id`、`project_id`、`report_id`、`report_revision`、`reviewer`、`conclusion`、`explanation`、`recorded_at` |
| `ReportExport` | `export_id`、`key`（见 §3）、`artifact_ref`、`artifact_digest`、`created_at` |

- 复核绑定**精确报告修订**：`validate_reviews_for_report` 要求同一项目、同一报告编号、`report_revision` 等于该快照的 `content_revision`，复核编号不得重复。
- 复核是独立记录：不写报告正文、不改变 `content_revision`、不改变测试事实，也不能把失败或缺证据改成通过。
- 新增复核只新增 `LocalReview`；需要把复核带进导出时创建新的导出记录（§3），旧正文与旧导出保留。
- 复核人身份是本地责任人，不等于平台已验证身份；平台审核不属于本册承诺。
- 新报告修订的常见触发：出现新的有效证据、当前尝试被替换、问题修订或有效人工确认变化、上游 Attempt 发布导致下游依据过期、依据或源码身份变化。触发后旧报告的正文、旧复核与旧导出均保留。
- 读取旧报告时按它冻结的精确修订展开证据与问题；这些对象的**当前**修订可能已经更新，两者的差异就是“报告说当时如此”与“现在如何”的差异，界面分别呈现。

## 3 导出

`ReportExportKind` 只有两个值：`markdown_summary` 与 `evidence_bundle`。导出键 `ReportExportKey` =（`report_id`、`report_revision`、排序后的 `review_ids`、`kind`、`redaction_policy_version`、排序后的 `attachment_refs`）。键相同则复用同一产物；键相同但产物摘要不同直接拒绝，不允许“同名重导”。脱敏策略当前只接受 `aitest.redaction/1.0`，其他取值拒绝。

导出顺序（与代码一致）：生成内容 → 永久对象库先保存（落盘前过滤凭据，摘要基于过滤后字节）→ 交付副本写事务临时位置、核对摘要后发布 → 再次核验制品摘要 → 才提交导出记录。任一步失败都不报成功；临时产物未登记不得当作已导出。

- `markdown_summary`：Markdown 正文加声明“证据正文不内联，附件不随本文件交付”，并列证据索引（编号、类型、大小、摘要；缺失项标注原因）。
- `evidence_bundle`：ZIP，含 `report.md`、`manifest.json` 与 `evidence/<sha256(evidence_id)>.bin`。成员路径必须是规范相对路径，拒绝绝对路径、盘符、`..`、重复覆盖、符号链接与控制字符；`manifest.json` 必须存在且与成员一一对应。
- 包清单 `manifest.json` 记录：`format_version`（`aitest.evidence-bundle/1.0`）、报告与复核精确修订、范围、投影策略、`files`（路径/摘要/大小）、`attachments`、`excluded`、`missing`、`generated_at`；摘要按实际导出字节计算，与本地对象摘要分开。
- 坏材料或不可安全投影的材料进入 `excluded`/`missing` 并说明原因，不生成伪装成有效证据的空附件；空字节附件标 `projected_placeholder`。
- 复制修复说明（`copy_repair_brief`）复用同一脱敏投影，从指定问题与尝试生成文本，位置未知保持未知，不把原始日志或密钥写入剪贴板。
- 交付副本（`artifacts/reports/<report_id>/<kind>-<摘要前16位>.<md|zip>`）只是交付物；权威副本是对象库中登记的对象。包是只读交付物，本期不提供导入恢复或可执行安装。
- 导出中断或失败：临时目录可能残留半成品，但“已发布文件”与“已登记导出记录”是两个分别核对的事实；未登记成功不得对用户报成功。重新导出时按同一导出键先核对已发布产物摘要，一致则幂等复用并登记，不一致则拒绝覆盖。
- 导出包验收在**新的空目录**解压，检查 `report.md` 的相对链接、清单全部摘要、排除/缺失原因与复核集合；普通 Markdown 与附件应脱离插件可读。迁移到空目录只验证相对链接，不要求安装插件。
- 跨目录写入不假设与工作空间同一原子事务；出现孤立文件（有产物、无登记）时不当作已成功导出，按恢复规则处理。
- 二期附件的图定义与图修订只能按用户选择的精确修订引用；布局更新只提示可选新图，不自动刷报告，用户选新图才生成新报告修订。

## 4 覆盖与缺口 DTO

领域 `Coverage` 只持有集合：S=`selected`、M=`required`、E=`executed`、R=`reused`、V=`verified`、P=`passed`；构造时强制 `E∩R=∅`、`E∪R⊆S`、`V⊆E∪R`、`P⊆V`，失败集 `V−P` 与未验证集 `S−V` 都是派生属性，不单独存事实。

`CoverageDTO` 是**扁平**计数，不含双摘要：

| 字段组 | 字段 |
| --- | --- |
| 分母 | `selected_applicable_count`、`required_applicable_count`、`required_verified_count` |
| 集合计数 | `executed_count`、`reused_count`、`verified_count`、`passed_count`、`failed_count`、`unverified_count` |
| 功能收据 | `function_coverage`（`function_id`、`dimensions`、`overall_status`、`gap_reason`、`case_ids`、`evidence_refs`、`verification_refs`） |

双摘要属于 `DecisionDTO`（`schema_version = aitest.decision/1.0`）：`selected_summary` 与 `required_summary`，类型 `CoverageSummaryDTO`，同构字段为 `scope_kind`、`case_ids_revision`、`denominator`、`executed_count`、`reused_count`、`verified_count`、`passed_count`、`failed_count`、`unverified_count`、`decisive_failure_count`、`decisive_failures`、`source_commit`、`policy_version`。运行视图 `RunViewDTO` 同样带这两组摘要与扁平 `CoverageDTO`。

- 决定性失败 H 由 `FailureCandidate` 六项守卫同时成立才派生：当前有效尝试、必要断言失败、依据已确认、失败核验有效、来源身份一致、依赖有效。`decisive_failure_count` 按 `case_id` 去重；整用例失败数 `failed_count` 与 H 不可相加，H 不要求属于 V。
- 功能级汇总由 `derive_overall_coverage` 派生，七种状态：`proven/partial/not_proven/unsupported/unknown/not_applicable/planned`；`not_applicable` 不计分母，`unsupported` 优先于 `unknown`，`planned` 只在没有其他缺口时单独成立。
- 缺口记录 `ReviewGap(code, safe_reason, subject_id)`。等级映射固定：D 级为 `source_identity_mismatch`、`no_valid_execution_basis`；B 级为 `assertion_basis_unconfirmed`、`noncritical_unknown`、`noncritical_verification_gap`；其余（含来源未核实、必测缺口、关键链路、环境证据、outdated_basis、`unclassified_gap`）为 C 级。`primary_gap` 按等级、枚举顺序与 `subject_id` 取最小。
- 缺字段一律显式未知，不补零；`verified_count = passed_count + failed_count` 由集合关系保证，不由界面计算。
- 步骤进度另存 `automatic_step_count` 与各层计数，不能当作用例分母；`layers` 冻结 L1/L2/L3 的 `total/completed/blocked/failed/pending_verification`，三层互不替代。

### S/M 与复用的报告合同

`DecisionInput` 冻结 M、S、当前 Attempt 与复用引用及其有效性，以及源码/环境/验收/模板/规则/策略修订；`DecisionOutput` 同时给出本轮 S 的 E/R/V/P/失败/未验证计数与完整 M 覆盖。补充用例参与 S 的业务结论；历史复用不伪造本轮执行，修复关闭仍要新证据。新 Attempt 只撤销该用例的旧复用资格，不回退旧 R 的事实记录；跨运行继承不得与本轮部分执行拼成整用例 E/R/V。

报告标题保留 `AcceptanceScope` 名称与 partial 上限；计划补充项可另列，不能抵消必测遗漏。确认依据后必须重检实际核验证据，不能只改计数；独立核验缺失时该检查标为未验证。来源未核实、凭据过滤影响必要核验、依赖过期三类缺口分别列出，不能用执行退出成功、投影成功或证据文件存在代替业务通过。

## 5 问题投影与状态机

`IssueRecord` 是人与 AI 共用的唯一记录：`issue_id`、`project_id`、`revision`、`title`、`status`、`severity`（P0—P3，可为空）、`disposition`、`owner`、`confirmed_by`、`disposition_reason`、`canonical_issue_id`、`fix_version`、`regression_method`、`closure_criteria`、`regression_request_id`、`evidence_refs`、`evidence_revisions`、`attempt_ids`。缺陷单、面板、MCP 与 Markdown 都读同一编号与修订，不建 AI 副本。

状态机只有下表一份（不再另画一份图）：

| 迁移 | 校验条件 |
| --- | --- |
| 草稿 → 待确认 | `draft → awaiting_confirmation`；至少一条证据引用 |
| 待确认 → 已确认 | 用户给出级别、责任人；`confirmed_by` 取自受控交互会话 |
| 已确认 → 处理中 | 仅从 `confirmed` 迁移 |
| 处理中 → 待复测 | 同时登记 `fix_version`、`regression_method`、`closure_criteria`，缺一拒绝 |
| 待复测 → 已关闭 | 必须满足 §6 的全部关闭守卫；修复说明或 AI 判断不替代 |
| 待复测/已关闭 → 处理中 | 复测失败：保留原失败与修复记录，清空处置回到 `active` |

不属于缺陷、重复、暂缓是**处置**而非状态：它们不改写原断言，也不删除记录。归并拒绝自指与环；撤销处置（`undo_disposition`）回到待确认，清空确认人、处置理由、主问题与修复三元组，已有级别与责任人保留、需重新确认。

问题列表行 `IssueListRowDTO` 字段：`issue_id`、`content_revision`、`module_ids`、`layers`、`severity`、`workflow_state`、`review_state`、`disposition`、`blocking`、`canonical_issue_id`、`updated_sequence`、`gap_reason`。

- `review_state` 三值（小写）：`unreviewed`、`reviewed`、`unknown`，含义限定为“当前问题事实是否已有有效人工核对记录”，独立于流程状态、报告 `LocalReview` 与平台审核。当前实现写入固定为 `unreviewed`（独立问题事实确认记录尚未实现），`unknown` 用于旧材料或字段无法判定的情形。
- 双未知：`module_ids`、`layers` 不得为空，未知写 `unknown`；`severity`、`workflow_state`、`disposition` 用 `null` 表示未知；`blocking` 为 `blocking/non_blocking/unknown`，`unknown` 必须带可见 `gap_reason`，不得被界面隐藏。
- 无法核实的定位写明未知及原因，不从文件名或 AI 推测补齐。

问题身份与失败细节由核心从已保存 JUnit 重算：调用方只提交 `run_id`/`step_id`/`signature`，核心校验簇存在、`issue_id` 等于服务端派生身份，并把完整簇冻结在 `links.pytest_cluster`；不接受调用方自报节点、位置、消息或证据。旧问题记录没有该键时按空读取。拆分只接受源问题与节点编号，子草稿使用独立身份并写 `split_from`，源问题不改写。AI 根因假设单独保存为候选，不进入证据、不自动关闭问题、不替代人工确认。

## 6 处置与阻塞

`IssueDisposition` 五值：`active`、`fixed`、`non_defect`、`duplicate`、`deferred`。守卫与状态联动：

- `duplicate` 必须给 `canonical_issue_id`，同项目、禁止自指、禁止环；解析失败或主问题缺失时保留 `unknown` 阻塞并显示缺口。
- `non_defect` 与 `duplicate` 必须已关闭、带理由与确认人；`fixed` 必须已关闭、具备修复三元组，并已有级别、责任人与确认人；`deferred` 必须保持未解决（已关闭 + 暂缓被拒绝）。
- 有效阻塞只算 P0/P1：`effective_blocking_issue_ids` 沿重复链取最终主问题，主问题处置为 `active`/`deferred` 时计入一次阻塞；链上取最强已确认级别，归并不能静默降级。`fixed`/`non_defect` 不阻塞。
- 任何处置都不改原断言与原始失败；处置变化触发受影响投影与新报告修订，报告继续冻结其原精确修订。

重算触发：主问题重开、重复关联变更、非缺陷处置撤销、级别变化、问题修订、有效人工确认变化都会重新计算当前阻塞与受影响索引键；报告冻结它生成时解析出的问题与处置修订，不用“当前主问题”覆盖旧报告。AI 只提供处置建议，处置生效仍需核心人工确认记录。

修复关闭守卫（`close_issue` 与 `SavedDefectManagement._closure_evidence` 逐项核对，缺一拒绝）：

1. 指定 Attempt 属于该用例、是该 Step 的**当前**尝试，状态 `completed`，采集完整，无依赖失效；
2. 断言编号属于该 Step，来源身份为 `matched`，断言依据已确认；
3. `closure_criteria` 必须等于保存的断言依据文本；`fix_version` 必须出现在无缺口、`verified` 的 `observed_source_digest` 集合中；
4. 存在权威断言核验（同一 Attempt/断言/用例），并由领域判定确认该用例进入 P；调用方自报通过与核验不符时拒绝；
5. 原失败 Attempt 不能用于关闭，需新的实际回归证据。

大项目 pytest 失败按**失败签名簇**：签名 = 异常类型 + 归一化首条消息 + 首个项目源码帧（无帧时为 `location_unknown`）；簇身份为 `(step, attempt, signature)`，同一执行范围内同签名合并。问题草稿只从每步当前 Attempt 的失败簇生成，被替代的历史失败保留在事实中但不重复成簇。冻结字段为 `pytest_failures`（`node_id`、`failure_type`、`message`、`file`、`line`、`suspect_file`、`suspect_line`、`location_unknown`、`stack`）；`pytest_baseline` 只与同一 `decision.coverage.selected` 的上一份已保存报告比较（`new_node_ids`/`existing_node_ids`/`fixed_node_ids`），基线只作变化说明，不证明修复关闭，无可比报告或旧报告无该字段时保持未知。问题记录把完整簇冻结在 `links.pytest_cluster`；拆分只接受 `source_issue_id` 与 `node_ids`，源问题不改写。

项目级汇总 `aggregate_project_runs` 只读已保存报告：按运行列环境、计划修订、S/E/V/P 计数与 pytest 失败数，并按验收项展开为逐运行行；不重跑、不重算、不合并不同解释器或不同运行，未映射到验收项的用例显式返回。

## 7 查询入口（引用）

问题列表、报告列表与报告编号查询的**掩码、排序、游标、允许组合与索引键只在[存储与恢复 §4](05-存储与恢复.md#4-有限查询与索引键) 展开**，本册只声明读取语义：

- `issues.list`：`view=OPEN|ALL`，14 种筛选掩码；列表每个问题只返回当前修订，历史修订走详情；`OPEN` 包含 `active`/`deferred`，以及解析到未解决主问题的 `duplicate`；`fixed`/`non_defect` 与主问题已解决的重复只出现在 `ALL`；无法解析的重复保留在 `OPEN` 并显示缺口。
- `reports.latest` / `reports.by_id`：报告“状态”指 `business_outcome`，不是执行状态或有效性；`reports.latest` 折叠同一 Run 的旧修订，`reports.by_id` 按报告或运行编号直达最新摘要；历史修订按 `content_revision` 降序读取。
- 索引缺失或损坏返回可重建要求，界面显示暂不可用；不回退全历史扫描，不把“查不到”当成“已通过”。

## 8 偏差记录

| 旧说法 | 代码事实 |
| --- | --- |
| `ReportSnapshot` 保存“断言可信度（已确认／总数）”与“授权来源（human_confirmation／plan_grant）” | 无这两个字段；payload 只有三档 `confidence`，没有确认计数与授权来源 |
| 存在 `OutdatedBasis` 记录（原依据、原因、来源、标记时间） | 无该记录实体；只有 `ReviewGapCode.OUTDATED_BASIS` 缺口与依赖失效事实，报告不保存“原依据行” |
| `pytest_failures` 用 `suspect_source_frame` | 保存的是 `file`/`line`/`suspect_file`/`suspect_line`/`location_unknown`/`stack`；`failure_frame`、`suspect_source_frame` 只存在于 JUnit 解析结果 |
| “`CoverageDTO` 固定定义 `selected_summary` 与 `required_summary` 两个同构摘要” | `CoverageDTO` 是扁平计数（含 `required_verified_count`、`function_coverage`）；双摘要在 `DecisionDTO`，类型为 `CoverageSummaryDTO` |
| `review_state` 取 `UNREVIEWED`/`REVIEWED`/`UNKNOWN`，事实变化会回到未复核 | 枚举为小写；生产写入固定 `unreviewed`，独立问题事实确认记录未实现，`reviewed` 暂无写入者 |
| 投影字段为 `layer`，`severity`/`disposition` 必填 | 投影为多值 `layers`；`severity`、`workflow_state`、`disposition` 可空；`module_ids`/`layers` 不得为空（未知写 `unknown`） |
| 关闭只需 `fix_version` 等于来源摘要 | 还需 `closure_criteria` 等于保存的断言依据文本、当前且完成的回归尝试、采集完整、无依赖失效、权威断言核验且用例进入 P |
| 报告保存“必要追溯时间戳（开始、结束或采集时间）” | 只有 `created_at` |
| 证据包附件为 `evidence/相对路径` | 附件名为 `evidence/<sha256(evidence_id)>.bin` |
| 状态机同时给 ASCII 图与迁移表 | 本册只保留迁移表一份；以代码守卫为准 |
