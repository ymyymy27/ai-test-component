# 执行与证据（一期）

> 状态：2026-11-16 设计基线（D4），2026-11-17 按代码事实核对。字段见[CLI 与数据契约](../03-设计/03-CLI与数据契约.md)；运行目录见[存储与备份](04-存储与备份.md)。本文不登记验收结论；完整宿主闭环与试点项目仍待验证。

## 1 运行状态

```text
run.start
  → running
      ├─ 正常结束 → completed
      ├─ 取消确认 → cancelled
      ├─ PID 不在且心跳超过 5 秒 → interrupted；PID 存活不判死
      └─ 执行异常/worker 异常退出 → execution_error
```

- 状态由 CLI/worker 写，面板只读；
- 业务结论在运行结束后由 core 派生，与状态分开。

## 2 启动

```text
run.start(payload)
 1. 校验计划已发布、范围非空；`intent=smoke` 的项目快速检查可以没有验收项范围
 2. 重算计划来源签名：项目/交付提交/任务契约/规则/服务/L1/运行器/根目录；不一致 → PLAN_STALE
 3. 校验确认记录或 --confirm；无 --confirm 时只复用同计划版本、同范围、同指纹的确认记录，否则 CONFIRMATION_REQUIRED
 4. 校验同一项目无活动运行
 5. 创建 runs/<run_id>/，写 plan.json（计划快照）与 task.json（任务修订 + 验收项快照）
 6. 写 run.json：running、started_at、heartbeat_at、frozen scope；worker 启动后补写 pid
 7. detached 启动 worker
 8. 返回 run_id
```

任一步失败即返回对应错误码，不留下可误认为有效的运行。

### 2.1 快速检查

```text
run.quick(payload)
 1. 校验项目存在、同一项目无活动运行
 2. 校验 --confirm
 3. 生成不含业务用例的项目级计划
 4. 创建 runs/<run_id>/，写 run.json（kind=project_check）与计划快照
 5. 启动 worker，返回 run_id
```

- 不建任务、不选验收项；`task=null`、`task_snapshot=false`；
- L1 只执行项目配置里的构建命令与入口导入；未配置的项不执行，也不合成额外的最小测试命令；
- 报告 `0/0`，L1 单独展示；L1 失败只让快速检查失败，不产生验收项通过结论；
- 业务用例只能走 `run.start`。

## 3 worker 循环

```text
for case in plan.cases:
  if cancel.requested: 剩余用例标 not_run，退出为 cancelled
  检查 depends_on：build/service 未满足 → blocked
  执行用例：
    L1 → 构建/语法/入口加载
    L2 → pytest/命令/HTTP
    L3 → 生成并执行脚本，或标 manual_pending
  写结果、证据引用、心跳
结束：
  派生结论与计数
  写 run.json completed/cancelled/execution_error
  同一 worker 进程内同步后处理：失败分析、问题草稿、Mock 判定、报告（completed/cancelled/execution_error）
  报告写 generated_at，并把 latest_report_id 写回 run.json
  后处理完成后再退出；后处理异常写 postprocess-error.txt，不回改运行状态
```

- 单个用例失败不终止整个运行；
- 依赖失败的用例按 `depends_on` 阻塞；
- 命令用例的失败输出显示第三方模块缺失时，不自动安装：用例按阻塞记录，并保存“缺失模块 + 建议包 + 来源”的依赖建议。建议优先取项目 test extras、requirements-dev 或 requirements-test 的声明版本；没有声明时才由内置映射/模型给出包名。用户在结果页确认后执行 `run.repair`，记录安装版本、日志、确认人与安装前后环境指纹，再重跑未完成项；命令不存在或数据库/服务连接失败直接按阻塞记录，不记为产品失败；缺失的是项目自身模块时仍按失败处理；
- 运行开始记录环境指纹（解释器路径、Python 版本、项目 venv、Node 版本、工作目录），并在开测前执行 `preflight` 环境安检门（服务拓扑序、端口复用/冲突、环境变量与工具体检）；执行免 AI 确定性硬探针（前后端契约对账、静态资产全 200 与 MIME、路由边界及按需 `LivePageProbe` 真页面活 DOM/控制台巡检），命中错题本 `conventions` 自动降噪豁免；
- 运行环境沿用宿主非凭据变量，剔除宿主模型/GitHub 凭据；加载项目根 `.env`、`.env.local`、`.env.test` 并按 `${VAR}` 展开，已有变量不被覆盖；默认 `PYTHONUTF8=1`、`PYTHONIOENCODING=utf-8`，避免中文 Windows 的 GBK 解码把 UTF-8 项目误判为失败。项目 `.env` 中 secret 命名字段加入证据脱敏集合，不写入项目配置或报告；运行子进程额外注入 `AITEST_PROJECT_ROOT`，生成脚本应以项目根为 cwd，不用 `__file__` 推导项目路径；
- 盲写预期隔离：计划生成第 1 步仅凭需求、前端 API 调用与 OpenAPI 契约冻结预期，不暴露后端实现源码；跑前通过 `ScriptLinter` AST 安检拦截空断言、退化断言、吞异常及无写后读回水脚本；执行阶段分离 `setup`/`verify`（`setup` 失败判 `blocked` 避免跨模块连坐），截取窗口期服务日志捕获表面 200 下的静默 `Traceback`/500；首次失败触发干净防抖重跑与独立裁判复核，派生三档可信度（`confirmed` / `suspected` / `blocked`）并按用例 Checkpoint 支持稳定通过用例的断点续跑；
- 用例级状态隔离：配置 `data.snapshot_files` 时，每个用例开始前还原声明的本地数据文件，避免前序用例修改共享状态导致后序用例级联失败；未配置时不启用，按原顺序执行；
- 同一层、同一命令、同一预期与依赖的重复命令用例在计划生成时合并，相关验收项绑定到同一用例并写警告；执行阶段对相同命令复用第一次结果；
- 用例结果独立写入，worker 崩溃时已完成部分可读；
- 计划用例带 `coverage_kind` 与 `test_nodes`：只有指向真实测试函数的 `direct` 证据能在执行通过后计为验收项通过；文件级 `file`、共用节点 `shared`、无法定位的 `unverified` 即使命令退出 0 也按 `blocked` 计，避免一个测试文件冒充多个逐项断言。
- 模型生成的 `script:` 脚本含真实断言时与既有测试同样计为 `direct`；无断言的脚本记 `unverified`。`http:`/`junit:` 计直接证据，`sql:` 记 `unverified`。401/403 且未带凭据按 `blocked` 记录；只由弱证据覆盖的验收项按 `blocked` 展示。
- 生成脚本失败后自动把失败输出回传给模型修复并重跑，最多 2 次；`http:` 用例失败时改写为等效脚本再跑。修复只影响当前用例，不重新生成整套计划；
- 脚本不得删除或修改种子账号（`FIRST_SUPERUSER`）；检测到同时对种子账号和 `/users/me`、`reset-password` 的修改/删除时，先让模型改用一次性用户，修不好按 `blocked` 阻止执行，避免破坏共享数据库状态；
- 生成脚本的失败按原因区分：缺认证、账号密码不成立、服务未启动、页面定位歧义、命令不在当前环境（需 `uv run`/`poetry run`/`bun`）等前置条件问题按 `blocked`；断言失败按 `failed`；语法/导入错误按 `error`。

## 4 服务生命周期

```text
读取 services 配置
 → 探测健康地址
   ├─ 已通：不接管
   └─ 未通：执行 start，轮询健康检查
         ├─ 通：继续
         └─ 超时：标 blocked，保留启动日志
运行结束：
  keep_on_failure=false → 执行 stop
  keep_on_failure=true 且存在失败 → 保留
```

- 只停止自己启动的服务；start/stop 使用与用例相同的过滤后运行环境：项目 venv 的 PATH、`AITEST_RUN_ID`、`AITEST_DATA_PREFIX`，不继承模型/GitHub 密钥；
- 写操作（POST/PATCH/PUT/DELETE）默认排在只读用例之后，其中 PATCH/PUT/DELETE 排在 POST 之后；服务配置了 `reset` 命令时，在每个写操作用例后执行一次重置命令，日志写入 `service-<name>-reset.log`；未配置 `reset` 且服务由本次运行启动时，默认在每个破坏性用例（PATCH/PUT/DELETE）后重启服务，`restart_on_mutation=false` 可关闭；命令类测试按测试输入识别写状态，无法证明只读时按写状态处理；
- 未配置 `services` 且计划含端到端、脚本或 `http:` 用例（访问本机端口或 `BACKEND_BASE_URL` 之类的本机地址）时，按识别的 Compose（含 `compose.override.yml` 等覆盖文件）、Postgres、Mailpit、`backend` FastAPI 和 `frontend` Vite 自动生成服务；按 db → mailpit → backend → frontend 顺序启动，使用专用端口 `18000`/`15173`，避免误用本机已有服务；
- Compose 服务在运行结束时执行 `docker compose ... stop <服务>`（不删数据卷），进程服务按进程树清理；已存在且未接管的服务直接复用并在运行记录里体现 `service_started=false`，不保证环境由本次运行建立；
- 端到端命令（Playwright/Cypress）在未配置服务、服务未就绪且没有 `PLAYWRIGHT_BASE_URL` 时直接按阻塞记录，不启动浏览器等待；`npm/pnpm/yarn/bun run dev` 这类长驻开发服务命令同样不执行，直接按阻塞记录；
- 端口冲突/启动失败不强行杀进程；
- 停止命令失败只记录，不影响结论。

## 5 测试文件

- 生成到 `runs/<run_id>/generated/`；
- 文件头标 `# generated by aitest`（脚本类用 `// generated by aitest`）；
- 生成后扫描危险操作（`rm -rf`、`DROP TABLE`、`git push`、`format`、写系统目录），计划生成阶段返回 `INVALID_REQUEST`，启动阶段返回 `SCRIPT_REJECTED`；
- 缺依赖：执行前确认页列出依赖；确认后 worker 用项目解释器执行 `pip install`，失败时相关用例标 `blocked`；
- 脚本自身语法/导入错误标 `error`，不算产品失败；
- `junit:` 只接受本次命令 stdout 中的 XML，或本次命令新写/更新的 `junit.xml`；仓库里或上一用例遗留的旧报告不会被复用。

## 6 L3

| 载体 | 执行 | 证据 |
| --- | --- | --- |
| 前端 UI | Playwright 脚本 | 截图、脚本；视频/trace 当前未自动采集，需手工 `evidence.add` 或另行实现 |
| 接口/命令 | 请求/命令序列 + 最终查询 | 请求/响应、查询结果、脚本 |

- 不可自动化 → `manual_pending`，worker 继续后续用例；
- 人工记录逐条落盘，未记录计入未完成；
- 不做 AI 临场自主操作。

## 7 取消与中断

取消：

```text
run.cancel → 写 cancel.requested
worker 在用例边界检查；正在执行的 command/script/pytest/junit/playwright/sql
会收到取消信号，进程树被终止，当前用例按阻塞记录
  ├─ 已停：status=cancelled，剩余用例 not_run
  └─ worker 异常退出：status=execution_error + 原因
```

中断：

- worker 每约 3 秒刷新 `heartbeat_at`；PID 不在且心跳超过 5 秒即接管，PID 存活时不因心跳单独判死，无 PID 时 120 秒兜底；
- `run.status`/`run.list` 发现 `running` 且心跳超过阈值、PID 不在 → 标 `interrupted`；
- 保留已完成用例、证据与未完成清单；
- 不自动重跑，不补造结果。

## 8 并发

- 同一项目同时只允许一个运行；第二个 `run.start` 返回 `RUN_ACTIVE` 与现有 `run_id`；
- 不同项目可并行；
- 运行内跨用例串行；
- 一期 runner 只执行单条声明命令，不支持 `parallel`/`args` 等并行参数；需要并行时先补结构化结果契约。
- 并行不改变结论与计数口径。

## 9 证据

| 类型 | 限制 |
| --- | --- |
| 单文件 | 20MB 截断，标注原始大小 |
| 单次运行媒体 | 软上限 500MB |
| 超限顺序 | 通过用例截图只留最后一张 → 跳过通过用例的新证据 → 失败用例证据不跳过；没有“压缩截图”步骤 |
| 视频 | 默认关闭 |
| 截图 | 失败用例全留；通过用例留最后一张 |
| 历史 | 不自动删除 |

证据只存相对路径、摘要、大小、media type；正文放证据目录。

## 10 AI 调用

| 调用 | 时机 | 失败处理 |
| --- | --- | --- |
| 目标候选 | 进入项目 | 返回空候选 + 自定义入口 |
| 验收项提取 | 建任务 | 人工填写 |
| 交付说明 | 提测 | 标未生成 |
| 计划生成 | 选范围后 | 人工编写/导入 |
| 测试脚本 | 执行前 | `blocked` |
| Mock 判定 | 运行结束 | 全部 `unknown` |
| 失败分析 | 运行结束且有失败 | 标未生成 |
| 问题起草 | 运行结束 | 不建问题，保留失败 |
| 报告摘要 | 生成报告 | 只输出事实 |

所有调用带超时与输出校验；网络错误不自动重试，避免重复计费；不合格输出不进入结果。

## 11 Mock 判定

- 输入：测试配置、测试代码、客户端初始化、地址来源、本次请求/响应/日志/DB；
- 预算：按组件计算，默认每组件 120 文件/3 层、单次总计 240 文件；任一组件或总计超出即 `unknown`；
- 输出：`real/mock/mixed/unknown` + 依据 + 读过的文件清单；
- 判不出即 `unknown`，不默认真实；
- `unknown` 或未识别 Mock 的用例不能获得“真实链路通过”。

## 12 结论派生

```text
S = 本次范围；M = 适用验收项
for item in S:
  取该验收项下所有用例最差结果
结论：
  有失败 → failed
  无失败但有阻塞/未知/未执行/manual_pending → incomplete
  全部通过 → passed
  S 无适用检查 → not_applicable
```

- 未选验收项不属于本次范围；
- 报告必须同时展示 `S/M` 与未覆盖清单；
- L1 单独统计，不计入验收项覆盖；项目级检查失败/未完成会使运行结论为 failed/incomplete；
- `intent=smoke` 且任务没有适用验收项时允许空范围：此时没有 `S/M` 覆盖分母，只做项目级检查，结论只对 L1 成立；任务仍有适用验收项（M>0）时，空范围仍返回 `SCOPE_EMPTY`；
- 独立快速检查使用 `run.kind=project_check`，不经过任务和验收项；优先级高于 smoke 空范围路径，避免为快速检查建任务。
