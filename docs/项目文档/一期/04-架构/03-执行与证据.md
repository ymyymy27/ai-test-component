本册覆盖 P1-FR08—13：执行如何被调度与适配、请求与句柄合同、输出如何被耐久采集、证据对象如何绑定事实、失败如何分类。业务结论 `passed/failed/incomplete/not_applicable`、覆盖集合与证据等级的**唯一口径在[功能清单 §3](../02-需求/03-功能清单.md#3-判定与统计唯一口径)**，执行聚合与依赖失效见[功能清单 §4](../02-需求/03-功能清单.md#4-执行证据与聚合)，本册不重写公式。

代码落点：领域 `src/aitest/domain/execution/`（运行、步骤、尝试、请求句柄、输出、来源核对）与 `domain/evidence/`（证据、链路、Mock、核验、脱敏摘要）；应用 `application/execution/`（runner、recovery、step_execution、runtime_source、facts）、`application/evidence/`；端口 `application/ports.py`；适配器 `infrastructure/adapters/execution/`；spool 与脱敏实现 `infrastructure/file_store/spool.py`、`infrastructure/adapters/execution/redaction.py`。

## 1 调度与适配器

三层调度自下而上固定：`Run`（档位、驱动、结论上限、范围与环境）→ `Step`（依赖、登记入口、断言、证据要求、`StepRevisionRef`）→ `Attempt`（一次真实业务尝试）。

| 记录 | 代码事实 |
| --- | --- |
| `Run` | `run_id`、`project_id`、`origin_workspace_id`、`intent_id`、`driver`、`run_tier`、`conclusion_ceiling`、`environment_ref`、`rules_revision`、`revision` |
| `Step` | `step_id`、`run_id`、`ordinal`、`case_id`、`level`、`step_revision_ref`、`required_for_case`、`state`、`input_refs`、`dependency_edges`、`registered_entry_ref`、`assertion_refs`、`evidence_requirements`、`current_attempt_id` |
| `Attempt` | `attempt_id`、`attempt_index`（从 1 起）、`resolved_input_digest`、`step_revision_ref`、`source_binding_digest`、`side_effect_class`、`adapter_kind`/`adapter_version`、`state`、授权与幂等键引用、`transport_retry_count`、句柄/游标/块/附件引用、`exit_fact_ref`、`capture_completeness` |

`AdapterKind` 七值：`python_checks`、`command`、`http`、`verification`、`manual_evidence`、`agent`、`external_result`。`SideEffectClass` 四值：`read_only`、`idempotent_write`、`non_idempotent_write`、`unknown`；`unknown` 按最严处理。

| 适配器 | 职责与输出 |
| --- | --- |
| `python_checks` | 语法、适用构建、加载或最小启动，保存 `SourceCheckResult` 及 `failure_class` |
| `command` | 既有 pytest/命令入口、输出与退出结果；按范围执行并采集 JUnit 附件 |
| `http` | 登记目标、凭据引用、请求关联、变量提取；输出事实供领域断言 |
| `verification` | 同对象的独立只读接口或可选数据库驱动，不作为插件存储 |
| `manual_evidence` | 页面操作类型、人工来源、步骤、截图附件与业务对象 |
| `agent` | 实际工具调用与逐次业务评价，不接受文字自述替代 |
| `external_result` | 格式、来源、附件、幂等校验及可独立重算的断言 |

`ExecutionPort` 只有四个方法：`start(request) -> ExecutionHandle`、`inspect(handle) -> ExecutionInspectionResult`、`collect(handle, cursors=None) -> ExecutionCollectionResult`、`request_stop(handle) -> StopRequestResult`。适配器只返回实际句柄、结构化结果与停止确认，不写业务记录、不自行改变断言规则、不另建调度或重试循环。

一期串行执行：上游失败只阻塞依赖步骤，不把阻塞当断言失败。若启用并行，须无共享写冲突且无依赖，并在全组边界处理暂停/修订/驱动切换。层级分工：L1 记源码失败、环境阻塞、工具异常与不适用子项；L2 分别判定响应、持久化结果与 Mock 范围；L3 绑定同一业务对象并保存完整流程与最终状态证据。L1 通过不能替代 L2/L3 业务核验。

### 意图、启动与控制

- 启动前提交 Attempt 意图、输入摘要、幂等键与副作用类别；提交后调用外部执行，返回句柄再记录。
- 意图已提交但句柄未保存时崩溃，不能推断未执行：以执行身份或业务幂等关联核实；有副作用且无法核实则未知。
- 句柄仍活且身份匹配时重新关联并继续采集，保留原 Attempt，禁止重复启动。
- 关闭编辑器不改变执行归属；重新打开按 `workspace`/`run` 恢复状态。
- 取消先保存取消意图再请求停止，未确认保持取消中/未知；不以窗口关闭生成已取消记录。
- 暂停只在步骤边界生效，正在执行的步骤先收尾；恢复从未执行步骤继续。

## 2 执行请求与句柄

| 合同 | 代码事实 |
| --- | --- |
| `ExecutionRequest` | 项目/`run_id`/`step_id`/`attempt_id`、`intent_id`、`resolved_input_digest`、`registered_entry`（`RegisteredEntryRef`）、`materialized_snapshot_ref`、`environment_ref`、`source_binding_digest`、`authorization_ref`、`side_effect_class`、`timeout_ms`、`expected_plan_revision_ref`、`source_capture` |
| `ExecutionHandle` | `handle_id`、`adapter_kind`、`adapter_version`、`real_execution_id`、`process_start_identity`、`workdir_ref` |
| `ExecutionInspectionResult` | `handle_id`、`state`、`process_reachable`、`identity_matches`、`stop_confirmed`、`observed_at`、`unknown_reason` |
| `ExecutionCollectionResult` | `attempt_id`、`output_blocks`、`captured_blocks`、`output_cursors`、`artifacts`、`exit_fact_ref`、`structured_result_ref`、`capture_completeness`、`error_ref`、`complete`、`runtime_source` |
| `StopRequestResult` | `handle_id`、`stop_confirmed`、`observed_state`、`unknown_reason` |

`ExecutionInspectionState` 为 `running`／`exited`／`stopped`／`lost`／`unknown`。只用 PID 认领进程不够：`process_start_identity` 与 `real_execution_id` 必须同时匹配，否则按“未知”处理。

启动顺序固定：先提交 Attempt 意图、输入摘要、幂等键与副作用类别，再调用外部执行，返回句柄后记录。意图到句柄之间崩溃不能推断未执行；有副作用必须查业务事实，无法确认时按未知/执行异常记录。授权引用在提交时一并保存，实际调用前再核对动作摘要、目标、凭据范围与计划修订。

`expected_plan_revision_ref` 把这次执行钉在精确计划修订上：`Attempt` 上保存，授权核对与提交时都要求它与运行当前引用的计划修订一致，不一致即拒绝。`timeout_ms` 同样随请求冻结，超时只体现在 `timed_out` 与终止原因上。

## 3 采集与输出

输出流按 Attempt 分块保存。每块是 `OutputBlockRef`：`block_id`、`attempt_id`、`stream_name`（`stdout`／`stderr`）、`block_index`、`offset`、`length`、`digest`、`complete`、`capture_source`、可选 `redaction_summary_id`。适配器回传的 `CapturedOutputBlock` 带 `run_id`/`step_id`/`attempt_id`/`stream_name`/`block_index`/`offset`/`content`，由核心校验归属与摘要后认领为永久证据。

游标 `OutputCursor` 记录 `attempt_id`、`stream_name`、`offset`、`last_block_index`、`last_committed_digest`、`durable`。核心拒绝推进到没有完整前缀的位置：`require_saved_output_cursors()` 要求每个流的块序号从 0 连续、`offset` 首尾相接、`cursor.offset` 等于前缀总长、`cursor.last_committed_digest` 等于最后一块摘要，且 `durable` 必须为真。游标只是进度标记，不是内容——不能把游标当成“已经持久化的输出”。

- 只读已封口的块：未封口尾部即使通过了过滤，也必须标“未持久化”，不得计入完整证据。
- 跨流不能凭采集时钟推断业务因果；因果只能来自真实请求号、trace/span 父子关系或明确业务关联。
- 块中途写入中断或磁盘不足时保留可识别字节与缺口，请求受控停止；不能补造缺失尾部。
- 采集停止且必要证据发布前不得清理 workdir。

### pytest 范围执行与 JUnit 证据

pytest 走既有 `command` 入口，不新增桥接器或专用执行引擎：

- 每个范围单独启动 `python -m pytest --import-mode=importlib --rootdir=<package-root> --junitxml=<workdir>/pytest.xml --tb=long <scope>`；`node` 范围把完整 node ID 作为最后一个参数。
- 不把多个包的测试塞进一个进程；同名测试模块由 `--import-mode=importlib` 隔离。一个 prepare 只绑定一个解释器。
- 原始 stdout/stderr 按 §3、§7 保存；JUnit XML 作为通用 `artifact` 附件（媒体类型 `application/xml; profile=junit`），不新增 pytest 专用证据类型；超限标 `truncated`。
- `ExecutionCollectionResult.artifacts` 携带附件，`Attempt.artifact_refs` 是 spool 附件引用；发布后由通用 `EvidenceKind.ARTIFACT` 证据引用，不能把 spool 引用当永久对象引用。
- 原始证据优先，派生结果不替代原始证据；证据保存后才允许回收 workdir。
- pytest 结果只用于断言结果；独立核验按验收项单独登记，不能拿 pytest 通过冒充独立核验。
- 从 JUnit/traceback 提取 `failure_frame`（断言/异常位置）与 `suspect_source_frame`（最后一个项目源码、非测试、非 fixture 帧）。JUnit 缺位置时解析 traceback 并核对文件存在于源码快照；`location_unknown` 只在完全没有失败帧时写，有失败帧但无法映射时保留已知位置并另记可疑位置缺口，不猜路径。
- 比较 `expected_test_count`／`expected_outcome`：`business_fact_mismatch:<field>` 是明确比较结果，按决定性失败处理；`business_fact_missing`／`business_fact_filtered` 等核验缺口不产出通过或失败。
- JUnit 缺失/截断、测试数少于 Inventory、全部 skipped、退出码与 JUnit 冲突时标不完整，不判通过。AI 根因假设只作候选，不进入证据。

规则：

- `code_identity` 按绑定形态给值：git 必须有 `commit_id`，plain 必须有 `file_manifest_digest`，没有就构造失败，不用空值占位。
- 调用关系只在真实采集到请求号、trace/span 父子关系或明确业务关联时建立；仅凭相近时间或 AI 推断不得生成已发生调用。
- 独立核验用本次业务对象编号与隔离测试数据，不拼接进原应用调用链；无请求号或关键结构化日志时降级为人工关联，记录 `evidence_level` 与缺口，既不判通过也不视为产品缺陷。
- `MockDeclaration` 不可原地覆盖：新结论是新内容修订；声明来源为 `development_declaration`／`runtime_config`／`static_candidate`，静态候选只形成风险提示，不证明 Mock 真实。
- 关键真实依赖缺口不被普通响应成功覆盖；关键链路清单里未覆盖的条目必须进入报告警告与等级判定。

### 外部结果导入

导入格式 `aitest.external-result/1.0` 包含层级、源码快照、运行与尝试、实际输出、Mock 与附件引用。旧格式由迁移适配器转换；未知来源不补造身份或快照。同一来源编号同内容导入幂等并返回原记录，异内容报冲突；来源始终保留为 `EXTERNAL_IMPORT`，不升级成插件实际采集。已核验、未核验与自述内容分开保存。附件路径必须受控并校验长度、摘要与项目关系；未知格式拒绝，不猜测转换。

## 5 spool 与退出事实

spool 布局按 Attempt 隔离：

```text
<workspace>/spool/<attempt_id>/stdout.log
<workspace>/spool/<attempt_id>/stderr.log
<workspace>/spool/<attempt_id>/.capture-<stream>.lock
```

写入器（`_FileSpoolStreamWriter`）在构造时取得该流的采集互斥锁，读取既有清单决定续写边界与下一个块序号，随后逐次 `append(bytes)`：过滤后的字节先落盘并 `flush`，块满则 `fsync` 并封口返回 `OutputBlockRef`。`close(complete=...)` 封口尾部；`abort()` 释放采集租约但保留未确认输出供恢复。

- 未决尾部留在内存，不落盘。超出内存预算（`max_pending_bytes`）时抛 `UnsafeMaterialError` 并把流标为失败，此后 `append` 继续抛错——**不降级写未过滤内容**。
- 封口时校验：块内容仍含已知凭据则拒绝发布。块归属必须共享 `run_id`/`step_id`/`attempt_id`，偏移与序号必须是精确整数。
- 写入器只写本 Attempt 的 spool 事实，不持工作空间业务写锁，不发布业务结论；核心校验块摘要与归属后经工作单元认领一次。

`ExitFact` 记录真实退出：`attempt_id`、`startup_token`、`process_start_identity`、`real_exit_code`（不可得时为空，不补造）、`last_block_index_by_stream`、`saved_bytes_by_stream`、`capture_completeness`、`termination_reason`、`timed_out`、`published_at`。`ProcessTerminationReason` 为 `natural_exit`／`timeout`／`confirmed_stop`／`executor_lost`／`capture_failure`／`unknown`。退出码非零是执行事实，不直接等同业务断言失败；`saved_bytes_by_stream` 表示**安全捕获流**字节数，执行退出与采集完整性分开记录。

| 故障情形 | 恢复规则 |
| --- | --- |
| 核心退出，包装器与子进程仍活 | 按真实启动身份重新连接，继续读已封口块，不重启命令 |
| 核心退出期间子进程已结束且 ExitFact 完整 | 核对标记与输出，恢复终态并独立评价业务断言 |
| 包装器失效、子进程可能存活或退出码不可得 | 保存可验证输出为部分证据，结果未知；不声称重新获得旧匿名管道，不补造 `real_exit_code` |
| 块中途写入/磁盘不足 | 保留可识别部分与缺口，请求受控停止；未知副作用不自动重放 |
| 清理 workdir | 必须先核实全组结束、输出已认领且必要源码对象已保存 |

被测命令产生后台子进程时，必须用已验证的受控进程组/作业机制登记归属，不能把父进程退出等同全组停止。

### 暂停、取消与恢复

| 动作 | 机制 |
| --- | --- |
| 暂停 | 在步骤边界生效；`暂停中` 与 `已暂停` 分别记录 |
| 取消 | 先登记取消意图，再请求执行器停止；确认停止后才记 `cancelled`，未确认保持取消中并记录执行异常 |
| 重试 | 产生新尝试并立即成为当前，`attempt_index` 递增，保留旧尝试与结果 |
| 恢复 | 对仍存活的句柄重新关联；对已完成句柄补取输出；已有落盘块的步骤按块恢复；明确未执行的步骤可继续 |

检查点 `RecoveryCheckpoint` 内容：`last_committed_stage`、`output_cursors`、`output_block_refs`、`resolved_input_digest`、`side_effect_class`、`execution_handle_ref`、`checkpoint_revision`。检查点在单写锁下先核实进程身份与存活，再抢救 spool 输出并校验归属与摘要，最后提交恢复事实；不可归属的材料保留待处理。保存检查点不代表能安全重放任意业务操作。

## 6 传输重试

三种动作严格分开，身份与授权各不相同：

| 动作 | 身份与记录 | 授权与恢复 |
| --- | --- | --- |
| 原结果查询/已知句柄重关联 | 原 `Attempt`，追加只读查询与采集事实 | 不新执行被测业务；查询目标与凭据仍须在允许范围 |
| 同一业务请求的传输重试 | 原 `Attempt`、相同业务幂等键/输入/目标，新的传输请求号 | 只有端点明确保证同号重传不产生第二次业务执行时才可按有界策略恢复 |
| 重新执行业务步骤 | 新 `Attempt` 立即成为当前，保留旧尝试 | 副作用步骤需新人工授权；只读步骤可按已登记规则与有效授权范围重试 |

有界策略的唯一实现是 `application/connectivity.py` 的 `retry_delay(retries_completed, *, read_only, idempotency_proven)`：不满足 `read_only or idempotency_proven` 或已完成 3 次即返回 `None`（不再重试），否则返回 `2`／`5`／`10` 秒。该函数只给资格与间隔，不睡眠、不执行。

HTTP 方法名、成功响应或“通常幂等”都不证明端点支持上述恢复合同。进程命令重启属于新 `Attempt`，不能伪装成传输重试；连接层不得自行重发未声明恢复语义的写请求。业务幂等键在同一 `Attempt` 首次请求前持久化；各传输请求保留独立结果，`transport_retry_count` 与 `attempt_index` 分别计数。被测智能体按用例设计的三次执行是三次计划执行，不算传输重试。

新副作用 `Attempt` 即使业务端支持幂等也不继承原授权；结果未知且无法核实时保持未知，不用新增 `Attempt` 掩盖。

## 7 采集安全与原始证据语义

本合同覆盖命令 stdout/stderr、HTTP 与核验响应、模型响应、人工与外部导入及诊断。文中的“原始输出/日志/响应”统一指**经过不可关闭的落盘前凭据过滤、但未被 AI 总结或业务改写的捕获流**；不承诺它与含凭据的外部原字节完全相同。原始源码对象另按来源排除规则处理，不能把凭据文件当必要源码保存。

| 边界 | 必须行为 | 不允许的替代 |
| --- | --- | --- |
| 解析凭据 | `SecretPort` 按用途在受控进程内提供值；过滤材料只走受限本地内存通道，凭据不进命令行、普通临时文件或检查点 | 先写文件再在导出时删除 |
| 采集入口 | 过滤已解析凭据的精确值、策略明列的编码变体与标准认证字段；stdout/stderr 共用同一流式过滤器，匹配缓冲跨块保留 | 按封口块分别过滤导致跨块漏出；未过滤尾部直接展示 |
| 未决尾部 | 留在受控内存直到可安全输出；异常终止时不能确认安全的尾部不落盘，保存采集缺口 | 把未决缓冲转储到 spool 或调试文件 |
| 封口与摘要 | 只对可保存的过滤后字节计算 `offset`/`length`/`digest`/块序号/游标，与 `RedactionSummary` 一起提交 | 保存低熵密钥的独立摘要或未过滤片段“帮助复原” |
| HTTP/模型 | 结构化移除认证头与凭据字段；响应正文仍经采集过滤，禁止整包认证调试转储 | 假设响应一定不会回显凭据 |
| 导入与二进制附件 | 导入前校验类型与已知敏感项；无法安全检查或转换的疑似敏感附件不入默认证据库，登记缺口并允许重新提供安全材料 | 原样保存后只在上传阶段排除 |
| 后续投影 | 面板、复制、报告、模型出站、导出、上传在安全捕获流上继续按各自策略投影 | 把落盘前过滤当成所有隐私、路径与源码外发规则已满足 |

`RedactionSummary` 字段：`policy_version`、`applied_rule_categories`、`filtered_streams`、`filtered_ranges`、`replacement_count`、`completeness`、`gap_reasons`、`created_at`。它不含凭据值，也不含任何可逆恢复信息。

- 凭据或过滤器不可用时暂停采集、请求受控停止并记录输出缺口，不把未过滤输出降级写盘。
- 保证范围仅限插件管理且已知的凭据值、明确认证字段与已登记过滤模式；不能保证识别任意未知或任意变形的秘密。输入/输出合同禁止夹带未登记凭据；检测到疑似敏感但无法安全处理的内容，阻止保存并提示安全补证，不能只显示“已脱敏”。
- 该边界不承诺隔离同一 OS 用户下的恶意进程。
- 过滤不能偷偷改变业务判定：若必要断言或真实性核验依赖被过滤字段，按已发布的非敏感验证事实判断；没有可用事实则标未核实/证据缺口，不能用替换标记判通过。

验证覆盖跨块匹配、HTTP 回显、模型响应、导入、异常终止、恢复、备份与所有外发投影；使用虚构凭据构造，实际产品通过须保留对应制品与证据。

## 8 失败分类

| 枚举 | 取值与含义 |
| --- | --- |
| `FailureClass` | `source_error`（源码错误）、`dependency_missing`（依赖缺失）、`environment_unreachable`（环境不可达）、`tool_failure`（工具失败）、`passed`（检查通过） |
| `CaptureCompleteness` | `complete`／`partial`／`gap`／`unknown`，默认 `unknown` |
| `TransportErrorClass` | `network`／`authentication`／`rate_limit`／`input_limit`／`response_truncated`／`schema_error`／`unknown` |
| `AttemptState` | `intent_recorded`／`starting`／`running`／`stop_requested`／`collecting`／`completed`／`cancelled`／`execution_error`／`invalidated`／`unknown` |

`failure_class` 只描述源码/环境/工具层面的检查结论，业务断言由领域判定器独立计算：`passed` 不等于业务通过，`source_error` 也不代替断言失败。传输错误归一到统一枚举后由 `connectivity` 决定是否重试与降级；网络、认证、限流、输入限制、响应截断、结构错误分别处理，失败时不悄悄换模型或供应商。

超时只表示等待截止（`timed_out` + `timeout` 终止原因），继续核实执行与业务结果，不宣称回滚。取消先登记取消意图再请求停止；未确认停止保持取消中并记录执行异常，不得伪造 `cancelled`。进程退出、编辑器关闭与网络断开都不等同于停止。

恢复与重试是不同动作：恢复同一已知句柄不新造业务执行，显式重试才产生新尝试。新尝试失败/阻塞/取消时它仍是当前尝试，不回退旧通过。

已确认失败与未完成的边界：上游必要断言已有有效失败、下游因此阻塞时，仍保留该失败并按 `failed` 附未完成范围，不因整用例不计已验证而改成只有 `incomplete`。上游新尝试、证据失效或依据变化只让受影响失败退出当前判定；独立分支的有效失败保留。聚合与依赖失效在同一业务提交发布，调度不把阻塞当失败，也不为消除未完成而自动重放副作用。
