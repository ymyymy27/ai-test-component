# 项目与计划

本册覆盖 P1-FR01—07，并为 P1-FR08 提供执行来源。业务结论、覆盖集合与证据等级的**唯一口径在[功能清单 §3](../02-需求/03-功能清单.md#3-判定与统计唯一口径)**，档位语义见[功能清单 §2](../02-需求/03-功能清单.md#2-运行档位驱动与结论上限)，本册只写这些事实如何被建立、冻结与核对，不重写公式。

代码落点：领域 `src/aitest/domain/project/context.py`（项目、绑定、模块、环境、源码清单）、`domain/planning/plans.py`（档位、用例、范围、计划）、`domain/planning/grants.py`（计划许可）；应用 `application/project/*`、`application/planning/*`；契约 `contracts/prepared_run.py`、`contracts/templates.py`、`contracts/plan_proposal.py`、`contracts/schemas/*.json`。依赖方向固定为 `application → domain`，外部能力一律经 `application/ports.py` 的端口。

## 1 项目与绑定

`LocalProject` 用稳定 `local_project_id` 标识；对外 DTO 的 `project_id` 与它是**同一值**，不是第二个编号。路径只是绑定属性，显示名或路径变化都不改变历史身份。

| 记录 | 代码事实 |
| --- | --- |
| `LocalProject` | `local_project_id`、`workspace_id`、`name`、`goal`、`created_at_commit`、`revision`（默认 1）、`modules`、`schema_version` |
| `LocalProjectBinding` | `binding_id`、`binding_revision`、`project_id`、`canonical_path`、`binding_form`、`repository_id`/`branch`/`base_commit`/`manifest_digest`（仅 git 形态）、`local_owner`、`confirmed` |
| `BindingForm` | `git`／`plain` 两值。由绑定是否含仓库标识决定，**不靠“取不到值”判断**，界面按形态渲染 |
| `Module` | `module_id`、`project_id`、`name`、`responsibility`、`interface_note`、`inputs`、`outputs`、`implementation_status`、`owner`、`revision`、`source_paths` |
| `Dependency` | `consumer_module_id` → `provider_module_id`，`origin` 为 `registered`／`inferred`，带 `source` 与 `revision` |
| `ModuleDependencyGraph` | `project_id`、`modules`、`dependencies`、`edges_declared` |

`canonical_path` 校验很严：必须是绝对 Windows 路径，且不得含 `.`／`..` 段。plain 形态完全省略仓库字段，不用空值假装仓库存在；`INFERRED` 依赖边必须在界面标“推导结果，可能不完整”，不能与已登记边等义。绑定与项目身份分离，移动目录或改变形态创建新修订，重新确认后才继续使用。

`ImplementationStatus` 为 `unimplemented`／`partial`／`complete`／`deprecated`，默认 `unimplemented`：登记模块不等于已实现。模块依赖允许循环，传播遍历须去重（`affected_modules` 负责反向闭包）。

工作空间位置拒绝给出原因而不只给布尔值：`DriveKind` 为 `fixed`／`removable`／`network`／`sync_folder`／`unknown`，`WorkspaceLocationRejection` 为 `network_drive`／`sync_folder`。拒绝登记来源不可靠的目录，而不是事后补救。

## 2 环境与来源快照

环境与源码是两类不同事实，分别冻结。

| 记录 | 代码事实 |
| --- | --- |
| `EnvironmentRef` | `environment_id`、`revision`、`interpreter_requirement`、`dependency_declaration`、`isolation_mode`、`isolation_confirmed`、`data_isolated`、`data_reset_policy`、`target_deployment_identity`、`request_timeout_seconds`、`step_timeout_seconds`、`network_targets`、`secret_refs`、`revision_note` |
| `IsolationMode` | `venv`（默认）／`none`／`unmanaged`；`none` 是用户显式选择不隔离，是合法事实，不是缺配置 |
| `SecretRef` | `purpose`、`env_key`、可选 `ref`；凭据按用途分列（模型／HTTP／数据库核验／GitHub），不能只允许模型密钥 |
| `ResolvedEnvironment` | `environment_id`、`revision`、`isolation_mode`、`interpreter_identity`、`dependency_set_digest` |

`EnvironmentRef` 缺解释器或依赖载体一律阻塞，但显式 `none` 不降级也不阻塞。超时值是运行冻结属性，改了就是新修订。

源码侧分成两条记录，职责不同：

| 记录 | 代码事实 |
| --- | --- |
| `SourceManifest` | `source_scope`、`source_form`（`git`／`plain`）、`manifest_digest`、`git_base_commit`、`git_diff_digest`、`files`（`SourceFileDigest`：`relative_path`／`size`／`content_digest`／`mtime_hint`）、`exclusion_rules`、`refetch_dependencies`、`refetch_scope` |
| `SourceSnapshot` | `snapshot_id`、`project_id`、`purpose`、`binding_revision`、`files`、`content_identity` |

`SourceForm` 与 `BindingForm` 取值集合相同但**各自声明**：绑定与源码快照是不同记录，任一方扩展不应牵连另一方。`source_content_identity()` 由 `SourceManifest` 计算内容身份，mtime 只作变化提示。

快照作用：显式 `analyze_project`、计划确认与启动运行读取选定范围源码；元数据变化只提示，不证明内容未变。未保存缓冲区必须先由用户保存，或明确“以磁盘版本运行”，决定要进记录。

物化始终在 `workdirs/<run_id>`（应用层 `application/execution/start_materialization.py` 校验单段安全标识，拒绝越界）：包含所选模块依赖闭包、入口、共享配置与必要资源，排除凭据与生成物。venv 用原位复用或重建，不搬移现有环境。物化副本不进永久对象库，执行停止且证据保存后才回收。

Git 提交标识只证明复取依赖仓库对象可用，不保证删除仓库后永久恢复；需离线复现的选定内容按摘要留存。plain 保留必要文件与差异，缺复取范围显式报告。一期面板只读最近固定快照并说明当前目录未重新核实。

## 3 模板与用例

`resources/templates` 是唯一模板来源，代码不另存一份必测清单。

```text
src/aitest/resources/templates/
  python-library/1.0.0.json
  python-service/1.0.0.json
  http-workflow/1.0.0.json
  manual-web-workflow/1.0.0.json
  agent-workflow/1.0.0.json
  ticket-workflow/1.0.0.json
```

每个 JSON 是一份 `TemplatePack`（schema `aitest.template/1.0`），字段：`template_id`、`version`、`name`、`source`、`applicability`、`delivery_method`、`implementation_status`、`items`、`required_item_ids`、`critical_paths`、`no_critical_path_reason`、`examples`。`items` 至少一项，`item_id` 必须唯一。模板项是提醒，不是必测 ID；缺处置字段阻塞发布，明确不适用才记录理由与依据。

| 记录 | 代码事实 |
| --- | --- |
| `TemplateVersionRef` | `template_id`、`version`、`digest` |
| `TemplateDisposition` | `template_item_id`、`applicability`、`coverage`、`reason`、`evidence` |
| `TemplateApplicability` | `applicable`／`not_applicable`／`unknown` |
| `TemplateCoverage` | `covered`／`uncovered`／`deferred` |
| `GeneratedContent` | 生成编号、任务类型、实际输入修订集合、模板/策略/模型修订、来源、草稿确认与过期状态 |
| `RuleDraft` → `RuleVersion` | 稳定规则编号、适用范围、步骤与证据要求、版本、发布状态 |

用例与关联：

| 记录 | 代码事实 |
| --- | --- |
| `Case` | `case_id`、`revision`、`layer`（`L1`/`L2`/`L3`）、`objective`、`preconditions`、`inputs`、`steps`、`expected`、`verification_method`、`links`、`assertion_basis`、`independent_verification`、`mock_scope`、`importance`（`P0`/`P1`/`P2`，默认 `P1`）、`template_item_id`、`data_mutation_units` |
| `CaseLink` | `acceptance_item_ids`、`module_ids`、`environment_ids`、`critical_path_ids`、`no_critical_path_reason`、`function_ids` |
| `AssertionBasis` | `revision`、`state`、`text`、`text_digest` |
| `ConfirmationRecord` | `confirmation_id`、`case_id`、`basis_revision`、`basis_text_digest`、`confirmed_at_commit` |
| `AcceptanceItem` | 验收项编号、目标、可观察且可验证的条件、版本、本地责任人、状态 |

断言依据三态不可合并（`AssertionBasisState`）：`missing` 禁止进入 `full` 必测；`present_unconfirmed` 可执行、保留分母但不计已验证；`confirmed` 仍须实际证据或独立核验有效才计已验证。`Case` 保存的是该修订保存时的状态，当前有效状态由核心按精确 `ConfirmationRecord` 派生，AI 只能起草。发布状态与依据确认分别校验：草稿未发布不能执行，两个状态不能互相顶替。

生成流程只有一条：选取模板 → 读取项目上下文 → 生成草稿（规则／验收项／用例／检查项）→ 用户增删改 → 确认发布为不可变版本。人工编辑不被再次生成覆盖；迟到模型结果只挂原来源并标过期。

## 4 计划与验收范围

| 记录 | 代码事实 |
| --- | --- |
| `Plan` | `plan_id`、`revision`、`scope`（`AcceptanceScope`）、`case_revisions`、`rule_revisions`、`template_versions`、`run_tier`、`initial_driver`、`status`、`confirmation_id`、`record_revision`、`coverage_contract` |
| `AcceptanceScope` | `scope_id`、`revision`、`name`、`required_case_ids`、`template_case_ids`、`objective`、`excluded_case_ids`、`exclusion_reasons`、`dependency_closure_ids`、`applicability_exclusions` |
| `CaseRevisionRef` | `case_id`、`revision`、`digest`，逐项固定被冻结的用例修订 |
| `CoverageContract` | `contract_id`、`understanding_revision`、`function_requirements`、`template_dispositions`、`critical_path_ids`、`coverage_claims` |

`PlanPublicationStatus` 只有 `draft`／`published`：草稿不能执行。计划发布固定精确用例与规则修订；必测集合由 `scope.required_case_ids` 承载，缺断言依据不能进入 `full` 必测。计划本身**不保存结论上限**，上限由档位派生（§5），避免两处口径。

范围排除必须成对给出原因（`excluded_case_ids` ↔ `exclusion_reasons`），适用性排除同理。缺 `CaseLink` 覆盖保持缺口，不能用新增无关用例抵消。跨用例修改必须比对 `expected_revision`；来源过期或并发编辑冲突返回当前修订与差异提示，不自动覆盖用户编辑。

发布、授权、执行、复核分别持久化，不合并成一个确认标记。

### 发布、准备与启动的次序

1. `project/context` 保存项目、绑定与最小环境；任务与交付按当前操作所需校验，正式提测和 `full` 分别施加对应门禁。
2. 用户可显式 `analyze_project`：先固定 analysis 来源，再按 `ModelOutboundPolicy` 投影；也可导入或编辑已保存草稿。
3. `plan_builder` 读取已保存上下文、验收与模板修订生成草稿；用户修改不被后续生成覆盖。发布时校验 `CaseLink`、适用性、预期、核验方式与范围，写不可变 `Plan`。
4. `prepare_run` 解析已发布计划/环境/所选源码，保存 `intent_id` 与 `payload_hash`。源码读取与摘要计算在短事务外完成；提交时校验项目、绑定、计划、规则、模板、环境修订与准备请求是否仍有效。
5. `start_run` 先按意图去重，再核对物化字节与冻结摘要；启动阻塞如实保存，不能换输入复用原意图。运行、授权与意图关联经同一工作单元发布。
6. 新需求、源码或环境产生相关新修订；未执行步骤可按守卫修订，已完成依据只标过期，不追认旧执行。

并发完成同一准备请求时只能发布一条 `PreparationRecord`，其余取得已发布结果。

### 派生物与失效

缓存键由每个派生物的实际依赖决定：源码、上下文、验收、规则、模板、环境或生成策略发生相关变更才定向失效，不做全量清空。派生物包括上下文摘要、检查与用例草稿、已执行检查复用、回归范围与证据分析；任一依赖不能证明一致即不复用。迟到模型结果只挂原来源并标过期，不覆盖当前人工版本。

回归建议是只读动作 `suggest_regression`：输入 `graph_revision`、已发布计划的 `plan_id`/`plan_revision` 与 `changed_files`，按准确的依赖集修订做反向传播，返回直接变化模块、受影响模块、未登记模块，以及与 `CaseLink.module_ids` 相交的建议用例。未登记模块显式返回，不猜影响面；该动作不写计划、不创建运行。

## 5 档位与驱动

三个枚举，冻结在运行上，语义与判定唯一的正文见[功能清单 §2](../02-需求/03-功能清单.md#2-运行档位驱动与结论上限)。

| 枚举 | 取值 | 代码约束 |
| --- | --- | --- |
| `RunTier` | `quick`／`on_demand`／`full` | 决定检查范围与结论上限 |
| `RunDriver` | `planned`／`stepwise` | `narrow_driver()` 只允许 `planned → stepwise`，反向抛错 |
| `ConclusionCeiling` | `partial`／`passable` | 只由档位派生，与覆盖率、驱动方式无关 |

`conclusion_ceiling_for(tier)` 是唯一边界：`full → passable`，`quick`/`on_demand → partial`，未知档位抛错。`on_demand` 即使把冻结范围全部选上也仍是 `partial`；要判通过必须新建一次 `full` 运行。判定入口只接受 `ConclusionCeiling`，不接受“覆盖了多少”作为放宽依据。

编排上驱动只能收窄授权，不能反向扩大；`full` 运行中拒绝修改计划内容，驱动收窄仍允许。

## 6 修订与身份

运行中修订不是“改计划”，而是新建一条绑定生效边界的事实。

`RunRevisionRecord`（schema `aitest.run-plan-revision/1.0`，`application/execution/runtime_revision.py`）字段：`record_id`、`project_id`、`origin_workspace_id`、`run_id`、`intent_id`、`input_digest`、`revision_no`、`previous_revision_ref`、`initial_plan_ref`、`base_snapshot`／`result_snapshot`（`SnapshotContentRef`：`snapshot_commit_id`／`snapshot_cursor`／`digest`）、`request_payload`、`confirmation_ids`、`effective_case_refs`、`step_changes`、`invalidated_basis_step_ids`、`invalidated_consumer_attempt_ids`、`pause_required`、`effective_driver`、`created_at`。

- `StepContentChange` 记录 `step_id` 与 `previous_ref`／`next_ref` 两个 `StepRevisionRef`；每步绑定其执行时的计划修订，继承的已完成步骤额外标“沿用上次证据，本次未重跑”。
- `full` 只接受无 `step_changes` 的驱动收窄记录；内容修订只属 `on_demand`，且只作用于尚未执行的步骤。
- 受影响的下游依据列入 `invalidated_consumer_attempt_ids`，历史断言不修改，但不得参与当前通过。
- 内容修订需要 `pause_required` 时在边界暂停，不在执行中途改写。

业务身份分五层，不可混用：

| 身份 | 创建范围 | 冻结与恢复 |
| --- | --- | --- |
| `client_id` / `prepare_request_id` | 客户端持久身份 / 一次明确的“准备运行” | 重传、重连、取回丢失响应都用原号；只有明确新准备才换号 |
| `intent_id` | 应用创建，绑定项目/动作/实际输入摘要及各来源修订 | 与准备记录同提交；跨入口启动沿用 |
| `run_id` | `start_run` 按 `(project_id, action, intent_id)` 取得或创建 | 与启动意图、授权及幂等结果同提交 |
| `attempt_id` / `attempt_index` | 步骤内真实业务尝试，序号从 1 起 | 网络恢复不新增业务尝试；新副作用尝试重新授权 |
| `request_id` | 接口一次传输尝试 | 只用于传输去重与响应匹配，**不代替 `intent_id`** |

跨入口恢复通过 `intent_id` 或准备查询取得已有意图，不用新入口的 `request_id` 顶替业务身份。同一意图输入摘要不同返回冲突；同请求期间源码已变则返回原意图并提示“依据需重新准备”，不能把新字节塞进旧意图。源码物化与意图不匹配拒绝启动，重新准备并核对计划级许可与越界授权。

### 合法复用与当前尝试

`ReuseReference`（schema `aitest.reuse-reference/1.0`）是已有运行记录之间的引用关系，不创建虚假 Attempt，也不新增执行器或独立服务。字段：`target_run_id`、`case_id`、`source_run_id`、`source_step_id`、`source_attempt_id`、`source_attempt_by_step`、`source_plan_revision_digest`、`source_content_identity`、`environment_revision_digest`、`entry_input_digest`、`rules_revision_digest`、`adapter_digest`、`evidence_refs`、`validity_checked_at_commit`、`verification_basis`。

准备运行时逐项验证：来源已完成、内容身份/范围与实际环境状态一致、证据仍可读、断言依据仍有效。任一项不能证明一致则不复用；不能证明环境未变时重新核验，不只比名称。首次启动本轮新 Attempt 即撤销对应整用例的复用资格并保留引用历史；新 Attempt 失败、取消或阻塞都不回退旧结果。

复用规则与整用例聚合的唯一正文见[功能清单 §5](../02-需求/03-功能清单.md#5-复用与验证资格)：`E` 只为本轮执行、`R` 为有效复用、`V` 取自当前有效的 `E/R`；本轮所选 `S` 与完整必测 `M` 分别投影。缺陷修复关闭只接受新的实际执行，不能用复用补齐关闭条件。复用来源损坏或失效时生成新的判定/报告修订，旧报告不原地修改。

## 7 计划许可与确认

`PlanExecutionGrant`（`domain/planning/grants.py`）是一次受控发布确认派生的**能力信封**，只回答“允许哪些动作类别、在哪个凭据/环境下、带多少预算”。字段：`grant_id`、`plan_revision`、`understanding_revision`、`scope_digest`、`allowed_action_classes`（非空）、`credential_scope_ref`、`environment_id`、`risk_class`（`low`/`medium`/`high`）、`max_side_effect_actions`、`max_data_mutation`、`allowed_hosts`、`time_window_start`/`time_window_end`、`budget`、`status`、`created_at`、`revoked_at`。

- `GrantStatus` 为 `active`／`revoked`／`expired`；`GrantInvalidationReason` 为 `plan`／`understanding`／`scope`／`credential`／`environment`／`revoked`／`expired`。
- 预算按动作累计（`stage_action_usage`）：只读动作不消耗预算；`idempotent_write`／`non_idempotent_write`／`unknown` 都按会改业务数据计入，`unknown` 按最严。任一预算超限抛 `PlanGrantRejected`。旧 usage 记录缺数据变更字段时，以历史副作用次数补齐，避免升级后低估已用预算。
- 撤销或过期后未执行动作回到待授权，逐动作 `ActionAuthorization` 仍单独保存（来源 `plan_grant`），不因有许可就免逐项记录。

`publish_plan` 带可选 `plan_grant` 时走受控发布：`PlanConfirmationService.derive()` 从**已保存**记录的 `approval_parameters.plan_grant` 读范围，不从调用方参数再取一次——确认后无法改写许可。它同时写出逐条依据确认与计划级许可，并把派生状态记到 `plan_confirmation_state`（schema `aitest.plan-confirmation-state/1.0`，状态含 `ready`／`derivation_failed`）。派生幂等，重放得到同一结果。

不带 `plan_grant` 时保留旧的逐条 `confirm_basis` 路径。两条路径都不把 AI 生成内容当作用户确认；发布确认、动作授权、断言依据确认、实际执行与独立核验是五种不同事实，任何一种都不能替代另一种。

## 8 执行来源与物化边界

物化摘要只证明已固定的文件内容；**执行来源合同再证明已登记的入口确实使用了该范围**。两项同时满足，才能说“源目录后续编辑不影响本次执行”。venv 只隔离依赖包，不承担源码来源或安全沙箱保证。

`ExecutionSourceBinding`（`contracts/prepared_run.py`）作为 Run/Attempt 已有输入的组成保存，不新增服务：`registered_entry`、`entry_arguments`、`cwd_mapping`、`allowed_env_keys`、`secret_refs`、`test_config_ref`、`adapter_versions`、`resolved_input_digest`、`source_checks`。`prepare` 冻结这些约束，`start` 在固定 workdir 中解析实际路径并保存期望→实际映射与 `source_binding_digest`，跨入口重传读同一冻结结果。

`source_checks` 是 `build`／`minimal_start` 两类显式登记（`SourceCheckPlans`）。缺省**不是“不适用”**：服务模板要求的两项检查缺失时准备阶段阻塞；库模板默认不适用，由核验侧带原因记录。

模块模式（如 `python -m pytest <scope>`）的入口可以是目录 scope，不要求单个文件：实际入口必须落在固定 workdir 内，目录入口只要其下有已观察到的项目文件，即判入口已观察。准入阶段若冻结参数给不出该目录而回落为同一 workdir 内首个文件，运行时目录入口与准入文件入口视为一致；解释器仍须与准入事实精确相同。目录入口不把 scope 外被导入的项目文件排除在来源观察之外。

| 来源 | 核对与失败处理 |
| --- | --- |
| 解释器与工具 | 核对真实可执行文件、版本与环境身份；复用环境的依赖变化则原绑定失效，不能只检查进程能启动 |
| editable/`.pth` 与导入配置 | 识别本项目的开发目录引用、`PYTHONPATH`、site 与测试配置，映射到冻结物化范围；无法映射或验证则阻塞该入口 |
| 绝对命令参数与 cwd | 源码/配置路径必须在允许物化范围内；必要外部资源单列依赖及其内容与版本身份，不能把原仓库路径当固定副本 |
| 实际加载来源 | 在适配器支持的加载边界记录本项目模块实际来源、入口与核对结果；无法证明的部分标 `source_unverified` 并形成证据缺口 |
| 写入位置 | 运行缓存、测试输出与生成物写明确输出子目录，不作为冻结源码；需改写输入源码时显式登记，改变后停止沿用原来源判定 |

`SourceVerificationState` 为 `verified`／`mismatch`／`unverified`／`blocked`／`unknown`；`SourceCheckType` 为 `syntax`／`applicable_build`／`load`／`minimal_start`，结果单独保存为 `SourceCheckResult`。每个步骤启动前核对它实际依赖的来源与环境状态；验证方式可复用受控且仍有效的内容身份，不能只看 mtime。`verified` 只覆盖已证明的来源范围，不承诺追踪恶意同用户进程或未声明的动态代码。

预期绑定不符时拒绝启动并保存阻塞事实；已执行后才发现来源不符，则保留执行与输出、标 `source_unverified`／依据过期并重新判定，不冒充未执行、不改写旧报告。扩大范围、修改输入或重新安装导致绑定变化时重新 prepare，并按现有许可与越界授权守卫核对。

## 9 模型提案

模型可按 `aitest.plan-proposal/1.0` 或 `1.1` 返回完整计划提案，但只是草稿。

| 版本 | 边界 |
| --- | --- |
| `1.0` | 沿用模板骨架；`coverage_contract` 物化被拒绝（要求 `1.1`） |
| `1.1` | 模板当提醒清单：每个模板项有且只有一条两轴处置（适用性 × 覆盖），`not_applicable`／`unknown` 必须给理由，不能静默删除模板项 |

`PlanProposal` 字段：`schema_version`、`template_id`、`template_version`、`scope`、`cases`、`understanding_revision`、`goal_intent_ids`、`coverage_claims`、`template_dispositions`。`ProposalCase` 的 `template_item_id` 可为空、`origin` 为 `template`／`ai`／`user`；`1.1` 允许 AI 新增检查，但必须通过 `coverage_claims`（`intent_id`／`function_id`／`dimension`／`case_ids`）填补业务功能×必要维度缺口。

服务端校验模板项处置完整性、功能×维度覆盖、必填字段、链接、断言依据文本、独立核验方式与 scope 一致性；用例修订、内容摘要、环境链接与项目身份由服务端生成，模型不能提交。`full` 发布必须有覆盖契约：缺契约、出现 `unknown` 适用性、`applicable` 未覆盖或推迟、understanding 的未知区域或 `blocks_full` 能力缺口都拒绝。没有 understanding 的导入/编辑路径只能走 `quick`/`on_demand`。

解析失败返回 `structured_output_invalid`，原始响应仍按 `generated_content` 保存；不自动修补、不二次调用，由用户重新生成或编辑已保存提案。审阅页可编辑范围与用例全部字段，提交走 `save_case`、`save_acceptance`、`publish_plan`。初始驱动默认 `planned`；启动前逐步骤 `prepare_execution`，原生窗口逐项 `authorize_step`，`start_run` 只推进已授权步骤；运行时才解析出的动作停在 `waiting_authorization`，补充授权后继续。

模型出站另有策略：`ModelOutboundPolicy` 由项目配置用例保存，`ModelProvider` 只接收经策略校验的脱敏投影；代码分析授权不等于允许外发代码，`source_snippets` 默认关闭，不能经日志或另一字段夹带。

## 10 pytest 范围选择

`discover_tests` 是只读发现动作，不创建业务记录，结果为绑定 `source_snapshot_id` 的 Test Inventory 派生缓存：`inventory_id`、`source_snapshot_id`、`pytest_version`、`digest`、`summary`（文件数／测试数／收集失败数）、`files[]`（`path`、`test_count`、`markers`、`collection_error`、`mock_candidates`、`nodes`）。`mock_candidates` 只是静态提示，不证明存在 Mock；`nodes` 供定向选择校验，但不随材料发给模型。

AI 只接收树形投影，输出内部草稿 `aitest.test-selection/1.0`（不是新的公共业务合同）：`goal` 与 `selections`；每项含 `acceptance_item_ids`（至少一个）、`scope`、`expected`（仅为 `all_pass`）、`mock_scope`、`module_ids`、`rationale`。`scope.kind` 为 `file`／`dir`／`marker`／`node`，`value` 必须是快照内 POSIX 相对路径、不含控制字符、不越出快照；阶段 A/B 默认只用前三类，阶段 C 增 `node` 且必须精确存在于该文件的 `nodes` 中，找不到时拒绝而不是猜。`module_ids` 为空表示“尚未映射模块”，**不得读成“不覆盖任何模块”**。

服务端校验 scope 存在于 Inventory，生成 Case ID、修订、摘要、`inputs`、`steps`、`links`；`module_ids` 原样冻结到 `CaseLink.module_ids` 供回归建议求交。AI 不写 Case ID、node ID 列表或执行入口。不存在、空 scope、无验收项链接阻止发布；验收项无范围、漏选测试、跳过比例高只警告并进入报告。

计划复用现有字段：`inputs[0]` 承载测试范围，`steps` 为一步“运行该范围并核对结果”，`verification_method="pytest-junit"`，断言依据文本为 `aitest.pytest-basis/1`（scope、expected_test_count、expected_outcome）。不新增 `PlanProposal` 版本，也不新增 `package` 字段，包名只作报告标签。

模型关闭时提供基于 Test Inventory 的手工范围选择页，勾选文件生成同一选择单，不退化为四项独立检查。每个范围单独启动 pytest（`--import-mode=importlib`、`--rootdir=<package-root>` 与 JUnit 附件）；一个 prepare 绑定一个解释器和一个已登记入口，多解释器项目按包拆 run。独立核验按验收项登记，pytest 结果只是断言结果。
