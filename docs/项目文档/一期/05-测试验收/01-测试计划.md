# 测试计划（一期）

> 期次：一期；主责：验证范围、测试分层、批次与通过标准；状态：计划，不代表已通过
> 预期唯一来源：[需求规格](../02-需求/02-需求规格.md) 第 6 节（P1-AC01—35）。本计划只安排"怎么测、在哪一层测、什么算通过"，不改写任何 AC 的场景与预期；"当前登记"列引自 [status.json](../../../../tests/acceptance/p1/status.json)，不是本计划的判定结论。

## 1 目的与范围

本计划为一期 17 个 FR、35 个 AC 安排可执行的验证路径。它回答四个问题：每条 AC 至少在哪一层取得证据、用什么样例和环境、按什么批次进入与退出、证据达到什么程度才可登记为验收结果。

本计划不回答"是否已通过"。任何进度、通过数与缺口以[项目现状](../../../现状.md) 第 7.1 节和 `tests/acceptance/p1/status.json` 为准；本文件中的"当前登记"只是引用，不构成新的状态口径。

范围边界：

- 只覆盖一期：Windows 11 x64、Trae 稳定版、Python 3.11+，本地测试闭环与本地导出。
- 不覆盖二期源码定位、依赖图、其他宿主与系统组合；不覆盖三期上传、回执与平台合同。出现相关异常时只记录为一期边界之外，不据此扩展验收范围。
- 不实现、不验证服务端、账号、自动录制回放、跨语言静态影响分析与生产部署。
- 被测仓库只读；证据与运行数据写入操作系统用户数据工作空间，不写入安装包、被测源码或 `src/`。

验收口径（与 [AGENTS](../../../../AGENTS.md) 第 5.5 节一致）：AC 成立必须同时具备真实输入、真实执行、可核对的预期对照和非空证据位置。文档一致、单元或合同测试通过、夹具通过、组件级真实进程通过，均不能单独构成 AC 通过。

## 2 测试分层与责任

| 层 | 目录或手段 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| 单元 | `tests/unit/`（含 `tests/architecture/test_boundaries.py` 依赖方向） | 领域规则、判定与等级、状态迁移、幂等与失效在夹具下成立；被改动路径的既有行为未回归 | 真实入口、真实执行、持久化落盘、宿主呈现 |
| 契约 | `tests/contracts/` 与 `tests/contracts/fixtures/`、六主题接口夹具 | DTO、动作、枚举、入口参数与冻结合同一致；非法输入与越界动作被拒 | 产品界面文案与交互、真实业务结果、跨进程时序 |
| 集成 | `tests/integration/`（`assemble_workspace_core` 临时工作空间）、`tests/recovery/` 故障注入 | 真实核心进程内的用例链、报告、问题、导出与恢复分支可完成 | 真实 Trae、真实业务数据、物理掉电与跨机搬运 |
| 宿主 | 面板 Playwright（`src/aitest/resources/panel/tests/`，4 个 spec）、扩展 `node --test tests/*.test.mjs`（3 个文件） | 面板与扩展的消息、渲染、七类页面操作、错误提示与无删除入口 | 真实 Trae 版本兼容、安装后 VSIX 全流程、真实用户操作 |
| 真实环境 | 真实核心 + 真实 Trae + 真实样例项目/仓库 + 人为故障（强杀、掉电、跨机） | AC 所要求的真实输入、真实执行、原始证据与恢复事实 | 本期未列出的宿主、系统与平台组合 |

分层使用规则：

1. 每条 AC 的"最低测试层"是可产出该 AC 决定性证据的最低层；低层可以做前置回归与反例，但不能替代 AC。
2. 只有真实环境层可以支撑 `verified` 登记；真实 Trae、恢复与跨机类 AC 即使已有组件测试，也必须在真实环境重做。
3. 依赖方向、生成 Schema 与接口夹具属于单元/契约门禁，不单列验收层。
4. 任何一层不得重算业务结论、覆盖、证据等级或问题关闭依据；各层只读取核心派生事实。

## 4 异常与边界清单

| 异常/边界 | 触发方式 | 对应 AC | 判定要点 |
| --- | --- | --- | --- |
| 凭据或认证字段扩散 | 在源码、响应回显、采集异常、spool 与导出中注入已知凭据 | AC07、AC16、AC29、AC35 | 落盘前过滤；过滤前字节不得进入 spool、对象、诊断或备份；无法处理登记缺口，不假报核验通过 |
| 掉电或强杀 | 在活动执行、发布、导出中终止核心或宿主，重启后核对 | AC19、AC28、AC13 | 不自动重放未知副作用；保留可抢救输出与原始证据；不伪造终态；报告如实显示缺口 |
| 执行器未确认停止 | 暂停或取消后断开执行器，再查询运行状态 | AC19 | 保持"取消中/未知"，不重跑、不判通过；恢复后重新核对活动执行 |
| 未知活动执行 | 迁移、备份或重启前存在不确定 Attempt | AC19、AC28 | 先核实活动执行与可抢救材料；有未核实执行器不得切换；永久材料缺口阻止完整迁移 |
| 依赖过期 | 重试上游并产生新 Attempt，下游已引用旧输出 | AC19、AC20、AC24 | 下游旧依据立即过期并需重跑；即使新输出等值也不自动复活；历史保留 |
| 运行中修订与驱动切换 | 在半程运行中改未执行用例、改正在执行用例、切换驱动 | AC20、AC24 | 完整验证拒绝任何计划修改；按需只允许步骤边界改未执行步骤；已完成步骤绑定原修订；反向切换拒绝 |
| 断言依据已填未确认 | 12 项执行完成、2 项依据未确认，随后补确认 | AC21、AC22、AC24 | 未确认不从分母移除、不计已验证；补确认须重新评价既有核验材料；发布与依据确认分别判定 |
| 空分母与全不适用 | 单模块跨模块传播、无前端网页项、S 为空 | AC03、AC04、AC18、AC25 | 不显示 100%；不适用须有理由；空分母不等于通过，也不隐藏非空范围结果 |
| 快查/按需勾满 | 按需自测把冻结范围全部勾满并全部通过 | AC18、AC21、AC23 | 不派生证据等级、不判完整通过；报告标"未打分"并给覆盖摘要 |
| Mock 与真实性冲突 | 未声明模拟、静态候选命中、声明真实但只拿到 Mock 证据 | AC05、AC06、AC22 | 静态候选只作风险提示；证据冲突以证据为准并标混合/未知；该范围不得给真实链路通过 |
| 接口成功但业务未写入 | HTTP 200 但独立数据断言失败 | AC02、AC07 | 不以调用成功判通过；保留业务失败，展示两类检查区别 |
| 环境不可达与来源不明 | 环境不可达；用 venv editable、PYTHONPATH 或绝对入口指向原仓库 | AC13 | 启动前核对实际来源，不符则阻塞；执行后来源不明保留事实并标证据缺口；不以 workdir 复制成功判源码通过 |
| 范围仍有未关闭 P1 | 构造未关闭 P1、重复归并、核实非缺陷、主问题重开与暂缓 | AC14 | 阻止该范围通过并显示关联问题；归并无环且只计一次；暂缓不能放行；非缺陷确认不改原失败断言 |
| 权限拒绝与路径越界 | 只读目录、无权限文件、绝对路径、盘符、`..`、符号链接、同步盘/网络盘 | AC07、AC13、AC35；跨盘拒绝无独立 AC，随 AC25、AC30 的绑定步骤记录 | 结构化拒绝并说明原因；不创建越界产物；可安全排除的附件列缺口，整体失败不发布成功产物 |
| 模型或平台不可用 | 断网、错误端点、空凭据、关闭 AI；三期平台未接入 | AC10、AC15、AC30、AC32；平台不可用无一期 AC | 本地信息、人工结论与导出仍可用；AI 辅助显示不可用；不补造根因或结论；平台策略不替代模型策略 |
| dirty 缓冲区 | 编辑器有未保存改动 | 一期无对应 AC（二期源码定位能力） | 一期只认物化来源与磁盘文件；不得把未保存内容当作当前已核实源码，也不自动保存 |
| 时间与历史 | 修改系统时间；尝试删除报告或证据；间隔很久后回看最早期运行 | AC28、AC34 | 无删除入口；不按可调系统时间选最新；按提交序号排序；历史正文不回改，当前有效性单独显示缺口 |

## 5 测试样例与环境

样例项目优先使用最小可判定结构；每个样例只引入验证该 AC 所需的复杂度。

| 样例 | 形态 | 主要用途 | 构造要点 |
| --- | --- | --- | --- |
| 纯函数库 | 单文件函数 + pytest | AC05、AC06、AC22、AC30 | 固定输入输出，可注入 Mock 与未声明模拟；不索要数据库或平台账号 |
| HTTP 服务 | 本地 HTTP 端点 + 独立数据核验 | AC07、AC09、AC13、AC30 | 返回成功但可不写数据；可回显凭据；可制造不可达与错误端点 |
| 单模块项目 | 一个模块 + 自身测试 | AC03、AC23、AC24 | 依赖图只有一个模块，跨模块传播应为不适用并给原因 |
| 无 Git 目录 | plain 目录 + 文件清单摘要 | AC25、AC35 | 不初始化 Git；源码变化以文件摘要与差异快照判定；导出中不得出现仓库字段 |
| 两后端无前端 | 两个后端模块，无页面 | AC04 | 网页项标不适用；模块入口与接口检查仍须完成 |
| 工单管理试点 | 创建、查询、分页、详情、状态修改 | AC08、AC26、AC34 | 页面七类操作各一条；可制造分页或滚动后失效；用于 L3 与缺陷草稿 |
| 失败与问题样例 | 断言失败、修复后仍失败、未关闭 P1 | AC02、AC11、AC14、AC15 | 保留原失败断言与复测记录；问题簇可重复、可归并、可重开 |

环境与记录要求：

| 项 | 要求 | 记录内容 |
| --- | --- | --- |
| 操作系统 | Windows 11 x64 | 版本与补丁级别 |
| Python | 3.11 及以上（工程约束 `>=3.11,<3.14`） | 实际解释器路径、版本与来源 |
| 核心 | 由 `bootstrap` 装配的真实核心进程 | 包版本、仓库提交、工作空间 ID、实例 ID |
| Trae | 稳定版，隔离 profile | 实际版本、VSIX 摘要、安装与重载时间 |
| 面板 | 构建后的面板产物 + Playwright chromium | 产物摘要、浏览器通道、失败截图与 trace |
| 源码控制 | 本地 Git；GitHub 只读凭据可选 | 仓库、分支、提交；无凭据时不得写成 GitHub 检查通过 |
| 模型 | 可选；无模型是 AC30、AC32 的必测分支 | 端点类别、凭据引用名（不记录正文）、超时与错误分类 |
| 数据与目录 | 独立用户数据工作空间与临时样例目录 | 路径、盘类型、是否同步盘；不写入被测仓库 |

模型、GitHub 与网络均不是所有 AC 的前置条件。缺少凭据时按对应 AC 的"无模型/无远端"分支执行；不得用模拟结果替代真实出站证据。

## 6 批次计划

| 批次 | 进入条件 | 覆盖路径 | 证据要求 | 退出条件 |
| --- | --- | --- | --- | --- |
| 定向 | 改动路径明确；`git status --short` 已检查并保留他人未提交成果 | 改动模块的单元、契约与相关集成用例；至少覆盖被改动路径的既有用例 | 命令、提交、节点数、失败原文、环境 | 目标用例全部通过；失败与跳过逐条说明；不据此登记 AC |
| 回归 | 定向通过；改动涉及共享领域规则、默认装配或合同版本 | 受影响包的单元 + 契约 + 集成；接口夹具对拍 | 同上，附受影响 AC 清单与未覆盖项 | 受改动路径无回归失败；合同夹具通过；仍不等于全量或 AC |
| 全量 | 回归通过；无并发重测试任务 | `pytest tests`（当前收集 5,278 个节点；耗时以实际为准） | 完整日志、开始与结束时间、节点统计、退出码、失败与跳过清单 | 退出 0 且失败逐条处理；不得用分块数字相加冒充全量，也不得把未跑完写成通过 |
| 宿主 | 面板或扩展改动；面板已构建 | 面板 4 个 Playwright spec；Trae 扩展 3 个 node 测试 | 产物摘要、spec 名称、截图/trace、失败原文 | 目标 spec 通过；真实 Trae 相关结论留给真实环境批次 |
| 真实环境 | 定向与回归通过；对应 AC 的入口、样例和环境就绪 | 按 AC 逐项执行；真实 Trae、真实业务、恢复与跨机单独成批 | 每个 AC 一份记录：输入、版本、提交、命令或操作步骤、预期、实际、证据路径、未验证原因 | 证据路径非空且真实环境已验证；经对账后更新 `status.json`；否则保持 untested、not_verified 或 blocked |

批次执行约束：

- 全量运行期间不并发跑其他重测试命令，避免负载导致的假失败与超时。
- 每批必须覆盖被改动路径的既有用例；只跑新增用例不足以证明没有回归。
- 真实环境批次按 AC 拆分，不把一次成功运行推广到同一 FR 的其他 AC。
- 批次记录写入 `docs/validation/<日期>-<主题>/README.md`；历史结论不搬入本计划。

## 7 通过标准与证据要求

分三层判定，不得跳层：

1. **命令层**：目标测试命令退出 0，无未解释的失败或跳过；全量还须报告真实节点统计。
2. **合同层**：DTO、动作、枚举、边界反例与冻结合同一致；夹具与生成 Schema 对拍通过。
3. **AC 层**：在真实输入上完成操作，按需求第 6 节的预期逐项对照，证据可回读。

AC 证据必须包含：AC 编号；核心与插件版本、仓库提交；样例项目与工作空间标识；输入与操作步骤；执行命令或界面动作；预期（引用需求原文）；实际结果；证据文件路径；环境（系统、Python、Trae、模型/远端是否可用）；未验证原因（若有）。

判定规则：

- `verified`：证据位置非空且真实环境已验证，二者缺一不可。
- `not_verified`：已实测但前提不足，须写明缺什么；不得用组件通过补齐。
- `blocked`：无法构造输入或入口不可用，须写明阻塞类型与解除条件。
- `untested`：未实测。未跑、未跑完、只做了准备或只看了文档，都只能是 `untested`。
- 业务结论、证据等级与执行/验证计数分别记录；A 级不等于业务通过，`quick` 与 `on_demand` 不派生等级，空分母不显示 100%。
- 失败先修代码或补证据；不得通过改写预期、缩小范围、归并问题或改写历史报告来变绿。

## 9 计划维护

1. AC 文本只在[需求规格](../02-需求/02-需求规格.md) 第 6 节维护。需求变更后先改需求与 `status.json` 的 `scenario`/`expected`/`related_frs`，再同步本矩阵；本计划从不先行改写预期。
2. 新增或删除 AC 时，同步覆盖矩阵、异常清单、样例用途、批次范围与 `tests/unit/test_acceptance_status.py` 的对账；不得用重编号掩盖变化。
3. 新增测试层、目录或入口时更新第 2 节；新增样例或环境组合时更新第 5 节。
4. 每批验证完成后先写 `docs/validation/` 记录，再按证据更新 `status.json`；本计划只登记"当前登记"引用，不复制数字作为结论。
5. 默认装配、执行端口、合同版本或支持宿主发生变化时，重新评估受影响的 AC 与批次，已失效的旧证据只保留追溯，不迁移结论。
6. 本计划的修改不改变任何 AC 的验收范围；如发现计划与分册冲突，按根 [AGENTS](../../../../AGENTS.md) 第 1 节定位主责合同后同步修正。
