## 1 目的与范围

为一期 18 FR、32 AC 安排可执行的验证路径：每条 AC 至少在哪一层取得证据、需要什么输入与环境、按什么批次执行、证据达到什么程度才能登记。

## 2 测试分层

| 层 | 测什么 | 典型证据 | 不算通过的情况 |
| --- | --- | --- | --- |
| 单元 | 规则、范围、计数、状态、文件读写 | pytest 输出、覆盖报告 | 只有实现存在、没有断言 |
| 合同 | CLI 命令、字段、错误码、状态枚举、数据版本 | 契约测试、快照、金样 | 字段对不上仍放行 |
| 集成 | CLI + 文件工作空间、worker、取消、中断、备份 | 临时目录运行记录、日志 | 用 mock 替代真实文件 |
| 真实 CLI | 本机 CLI + 文件工作空间 + 真实进程/模型/日志 | run.json、报告、证据、命令回执 | 只跑单元/夹具，或用面板组件测试代替 |
| 真实宿主 | Trae 安装、绑定、执行、导出 | 截图、录屏、运行目录、报告 | 模拟器或组件测试 |
| 真实项目 | 试点项目的 L1/L2/L3、GitHub、链路 | 代码版本、运行 ID、证据路径 | 文档一致或接口定义 |

单元、合同、集成通过都不能替代真实 CLI、真实 Trae 与真实项目验收。`real_cli` 只覆盖 expected 为 CLI 行为的 AC；面板/宿主交互必须另有 `real_trae_panel` 证据，试点项目与 GitHub 成功路径不能由 `real_cli` 自动满足。

2026-11-21 自动化基线：后端 pytest 341 个节点、面板 vitest 120 项、扩展 node test 94 项；制品版本 0.5.0。这些结果只说明对应层通过，不替代真实 Trae、真实项目或平台对拍。

## 5 通过标准

- 每条 AC 的 `scenario` 与 `expected` 与需求规格逐字一致；
- `result=verified` 必须同时有证据路径、真实环境标记和与本 AC 要求层相符的证据；
- 单元、合同、集成通过只能登记为“已测”，不能登记为真实验收；
- 本轮新增行为必须逐项覆盖：取消（含最后用例取消）、L1 四类检查与 smoke、JUnit 旧报告、data.cleanup、HTTP 重定向、证据脱敏、备份限制、link.import/assert、project.config 各段；只靠单元测试不能写成宿主可用；
- 未跑、缺环境、无法构造输入分别记 `untested / blocked`；已测但前提不足记 `not_verified`，并写清缺什么；
- 阻塞项写清缺什么、由谁解决。

## 6 回归与质量

- 每个 WP 完成跑受影响的单元、合同、集成测试；
- 关键路径保留故障注入：写入中断、损坏 JSON、worker 被杀、备份恢复；
- 快测保持顺手；全量按批次执行，结果如实记录到 `tests/acceptance/p1/status.json`；
- 不以“全量通过”代替真实 Trae 验收。

## 7 证据要求

- 每次真实执行记录：软件与制品版本、输入、步骤、预期、实际、证据位置；
- 证据保存在运行目录与验收台账；
- 截图、日志、报告引用具体路径，不写“已验证”而无位置。
