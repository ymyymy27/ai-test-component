# 功能清单（一期）

> 适用期次：一期；主责：功能行为、判定与统计唯一口径、能力与模板；状态：合同有效，验收未完成

一期共 **17 项功能（P1-FR01—P1-FR17）**，对应 **35 项验收（P1-AC01—P1-AC35）**。验收场景、预期结果与"关联功能"列只在需求文档 §5 维护；本册给功能行为、判定口径与可观察的成功条件，不复制场景正文。

一期是纯本地插件：不登录、不上传、不跨账号协作，不监听 TCP，全部记录保存在本机文件工作空间。被测目录是 Git 仓库或普通目录、项目只有单模块或多模块，都必须能完成适用的 L1／L2／L3 检查与本地导出。

本文中"原始输出、原始日志、原始响应"指**落盘前已完成不可关闭凭据过滤、未被 AI 总结或业务改写**的捕获材料；已知凭据、认证字段和登记模式按架构·执行与证据 §13 处理。无法识别任意未知秘密的限制如实声明；疑似敏感且不能安全处理的材料不保存，登记为证据缺口。面板、复制、导出与上传各自使用安全投影；过滤影响必要核验时不能用替换标记判通过。

阅读分工：功能范围与入口见 §1—§2；判定、覆盖与等级**只在 §3 定义**；执行事实与聚合见 §4；复用资格见 §5；报告与问题见 §6；能力、模板与适配器见 §7—§8；逐功能成功条件见 §9；不做的事见 §10。其他小节出现结论性描述一律写"判定见 §3"。

## 2 运行档位、驱动与结论上限

一次运行固定两项互相独立的属性：**档位**决定跑到什么程度、这次能不能判通过；**驱动**决定谁推进，不改变范围与结论口径。两者都是运行的冻结属性。

### 2.1 档位

| 档位 | 跑什么 | 结论上限 | 证据等级 |
| --- | --- | --- | --- |
| `quick` 快速检查 | 固定跑 L1 ＋ 本次改动涉及模块的关键 L2 ＋ 按已发布保守规则适用的独立核验（纯函数预期比对或业务数据核验）；范围来自已发布保守规则与关键链路清单，不需要勾选；模板项只作提醒 | `partial`，只代表所选范围，不判完整通过 | 不打分，只给覆盖摘要 |
| `on_demand` 按需自测 | 运行时自选检查集，可只选某一层（如只跑 L2）、某个模块或某个环节；**只有本档由用户选择范围** | `partial`，只判所选范围，不判完整通过；未选与未执行项逐条列出 | 不打分，只给覆盖摘要 |
| `full` 完整验证 | **没有选择，全部执行**：冻结计划内该范围全部适用业务功能 × 必要维度对应的必测项，跳过项必须为 0 | 证据与 P0／P1 条件满足时可判通过；可按 §5 复用有效检查 | **A—D**，唯一打分的档位 |

**结论上限只由档位决定，不由覆盖多少或执行方式决定。** 快速检查与按需自测即使把冻结范围全勾满并全部跑完，仍只判所选范围的结果，不能判完整通过；需要完整通过必须新建一次完整验证运行。执行方式（驱动）同样不改变结论上限。

未选与未执行项一律记为"未执行"并写明原因，**不能当作不适用**。按需自测允许只选下层（例如只跑 L2），此时上层未执行按阻塞或未验证展示，不因此阻止该范围自身的判定。缺少独立核验的检查显示"未验证"，不判通过。

档位不足时可扩展新档位，但新增档位必须同时定义适用场景、必测范围、统计分母与结论上限，不能只增加名称。

### 2.2 驱动与切换

| 驱动 | 行为 | 适用 |
| --- | --- | --- |
| `planned` 计划驱动（默认） | 按已授权计划连续推进，不逐步询问；同类且无副作用的连续步骤不重复弹窗 | 计划已确认，范围、凭据与副作用均已授权 |
| `stepwise` 逐步驱动 | 每步确认后执行，可查看中间结果、随时补证、修改后续步骤或退回 | 首次接触被测系统、步骤有副作用、需要边看边判断 |

逐步驱动的确认表示"允许进入下一步"，**不重新判定断言、不改变结论上限**；连续多个同类且无副作用的步骤可合并为一次确认；**有副作用的步骤必须单独确认**。

**驱动可单向切换**：运行中允许在步骤边界从计划驱动切到逐步驱动（收窄授权）；**不允许**反向切换（逐步切计划），需要放宽授权时应新建运行。原始驱动、生效驱动与切换记录都保存。两种驱动使用同一套三层判定标准、同一模板版本与统一问题清单；遇到扩大范围、新凭据、明显副作用都必须暂停等待确认，不静默跳过。

每次运行固定展示三项：**档位 · 驱动 · 覆盖范围与跳过项**，例如"完整验证／计划驱动／必测 12 项，跳过 0 项"。

### 2.3 三类确认与断言依据

三类确认不可混用：**计划确认**绑定 Plan 修订；**执行授权**绑定实际动作与输入；**结果复核**绑定已有 Attempt／报告修订。计划确认不确认未来执行结果，也不自动设置人工复核。

一次计划确认生成 `PlanExecutionGrant` 作为授权来源；计划内且许可内的动作仍逐项保存 `ActionAuthorization`（`source=plan_grant`），越界动作清单式逐项确认，未解析值待执行前确认；不做无范围、无记录或永久的集合授权。授权绑定 `intent_id`／计划步骤、`input_digest`、目标与凭据范围；输入、目标或凭据范围变化使原授权失效，副作用的新 Attempt 须重新授权。重复传输不重复询问，执行前再核对实际输入。

| 断言依据状态 | 含义 | 对执行与统计的影响 |
| --- | --- | --- |
| `missing` | 没有可解析的依据修订 | 阻止该用例进入 full 必测 |
| `present_unconfirmed` | 已填写但未经人工确认 | 可运行，计入分母与未核实，不计已验证，并降低证据等级 |
| `confirmed` | 已确认并绑定准确依据修订 | 仍须实际核验证据才计已验证；补确认不产生新执行 |

依据确认与实际独立核验各自记录。未发布用例不执行，不等于"已发布但依据未确认"；两者的处置与展示必须区分。

### 2.4 运行中修订的边界

| 规则 | 内容 |
| --- | --- |
| 生效范围 | **仅按需自测**：修改形成运行中修订，只对尚未执行的步骤生效，从当前步骤边界起按新修订执行；快速检查无计划可改 |
| 完整验证 | **运行中拒绝任何计划修改**，须新建按需自测运行；原运行保留为历史 |
| 已完成步骤 | 绑定其执行时的计划修订，**不回改、不重判、不重跑**，已有证据继续引用 |
| 记录 | 按需自测同时保留基础计划修订与运行中修订序列；完整验证只保留基础计划修订；报告展示最终范围与每次修订原因 |
| 重新确认 | 修改扩大范围、新增凭据或引入新副作用时，必须先暂停并等待用户确认 |
| 并发防护 | 不允许修改正在执行的步骤；修改后当前步骤按新修订重取输入并说明变更内容 |

判定与统计见 §3；控制动作与失效机制的实现口径见 §4。

## 3 判定与统计唯一口径

本节是业务结论、覆盖、计数与证据等级的唯一正文。面板、报告、MCP、导出只读取核心派生结果，不在别处另算，也不允许把本节公式复制到实现或其它文档形成第二份定义。

### 3.1 业务结论

| 结论 | 成立条件 |
| --- | --- |
| `passed` | full 档、本轮所选范围内无决定性失败、无未验证，且 §3.3 门禁全部满足 |
| `failed` | 存在本轮所选范围内当前有效的决定性失败（H_S 非空）；**同时列出未完成范围** |
| `incomplete` | H_S 为空，但存在未完成、阻塞、取消、未知、依据未确认或证据缺口 |
| `not_applicable` | 本轮 S 为空且无适用检查；不显示 100% |

尚未确定、阻塞、取消或未知**不被当成失败证据**；已有明确失败时仍判 `failed`，不得因存在未完成项退回 `incomplete`。业务失败以 H_S 判断，不以 F_S 为空推断"没有失败"。

### 3.2 集合、计数与决定性失败

- **B**：冻结验收范围内全部适用业务功能 × 必要维度对。
- **M**：覆盖 B 所需的冻结必测用例集合（每个 b∈B 至少一条映射用例）。
- **S**：本轮实际选择的用例，含被选择的补充用例。
- full 要求 **M⊆S**，且 B 中每个功能 × 维度至少一条 M 内用例有有效证据和独立核验；`quick` 由已发布保守规则确定 S，`on_demand` 由用户选择 S。
- 模板项只作提醒，**不构成 T 或必测下限**；运行中不得通过缩减 M 或弱化预期美化结果。

对任一统计集合 X（本轮结果取 S，完整覆盖取 M）：

- **E_X**：X 中全部必需步骤的当前有效 Attempt 均在本轮实际完成且输出已保存的用例。
- **R_X**：X 中经完整复用守卫验证、且未被本轮新 Attempt 取代的复用用例；**E_X∩R_X=∅**。
- **V_X ⊆ E_X∪R_X**：依据已确认、所需证据/核验有效且断言明确通过或失败者。
- **P_X** 有效通过、**F_X** 有效失败，**V_X=P_X∪F_X**，**U_X=X−V_X**。
- 失败可计入 E 与 V；依据未确认可以在 E 但不在 V；执行异常、取消、阻塞或未知不计 E/V。**按用例统计，步骤进度独立计数。**
- **H_X**：X 中存在当前有效决定性失败的用例 ID 集合（守卫见下）。

H 的守卫：已发布的必要业务断言**已明确失败**，且其依据确认、所需失败核验证据、执行来源与所消费依赖均有效，足以否定该用例的必要验收条件；引用准确的 `case_id`、`step_id`、`attempt_id`、断言/依据修订与证据。整用例有效失败 F_X 必属于 H_X；后续必需步骤未完成时，H_X 可以包含尚不在 V_X 的用例，**但不能因此增加 E/V 或移出 U**。合法整用例复用中仍有效的失败按同一守卫计入 H；一旦新 Attempt 替代复用或失败依赖过期，旧失败只留历史。普通执行异常、阻塞、取消、未知结果、未确认依据、无效证据和非必要观察**均不能进入 H**。

H 仅是现有事实的领域派生结果，不新增可手工修改的业务状态，也不由 AI 意见或界面点击生成。H 按用例去重，多条失败证据保留引用但不重复计数；S/M 两组分别派生；旧报告保持当时输入与策略，不按新规则回写。界面把 H 显示为"已确认失败用例"，F 保留"整用例已验证失败"。

### 3.3 full 完整通过门禁

同时满足才给 `passed`：

- full 档；业务功能 × 必要维度覆盖完整（M⊆S）；所有适用必测有效通过；**跳过为零**。
- 无未知或过期依据；所需真实链路有证据；源码与执行对应。
- 无关联的有效 P0/P1 阻塞问题（处置规则见 §6.5）。
- 所有适用必测项的断言依据已确认，且有满足原验收条件的实际核验证据；**补充确认不替代实际核验**。
- 所选补充项没有失败或未验证。

低等级本身不改业务结论；依赖环境方式不直接决定等级或是否通过。环境与数据问题按具体无效证据或验收失败判定：证据完整的非虚拟环境可得 A，venv 也不保证证据齐全。

### 3.4 证据等级（仅完整验证打分）

仅 full 计算证据等级，取命中条件最严重者；同严重度按下表顺序给出**一条主要缺口**，全部缺口保留。

| 等级 | 显式条件 | 不表示什么 |
| --- | --- | --- |
| D 无有效依据 | 源码身份与执行不一致；或整轮无任何有效执行依据 | 不把可信的业务失败证据作废 |
| C 关键证据不足 | 所需源码无法核实；关键链路缺失/Mock/未知；必需证据缺失/损坏；必测阻塞、取消、未执行，或执行结果/必要核验证据未知（不含仅断言依据确认缺失）；相关依据过期；环境问题导致必需核验缺失/失效；实际覆盖低于业务功能 × 必要维度要求 | 不由字母替代真实业务结论 |
| B 局部不足 | 没有 D/C，存在非关键局部未知、非关键核验缺口，或执行及必要核验材料齐全但断言依据已填未确认 | 不表示可提测/可放行 |
| A 证据充分 | 无上述缺口，且所有适用判定有完整可追溯证据、关键真实路径已核验、依据确认、源码对应 | 可以有充分证据证明业务失败；A 不等于通过 |

补充规则：有效 R 引用的原执行证据属于有效执行依据；本轮 E 为空不自动判 D，但 R 失效且无其他有效依据仍按 D/C 守卫处理。P0/P1 控制业务放行，**不把证据自动降为 D**。无法归类的缺口保守给 C 并说明原因，不进入默认 A；A 的主要缺口为"无"。`quick`／`on_demand` 等级为 `null`，显示"未打分"与相同事实缺口。等级是对状态的派生投影，不参与断言判定，不改变结论上限。

### 3.5 统计呈现

| 统计 | 规则 |
| --- | --- |
| 本轮执行/复用/验证 | `count(E_S)/count(S)`、`count(R_S)/count(S)`、`count(V_S)/count(S)`；复用不伪造本轮执行 |
| 完整必测覆盖 | 分列 `count(E_M)/count(M)`、`count(R_M)/count(M)`、`count(V_M)/count(M)` 及未验证 `count(U_M)`；未选、跳过、未执行仍在 M |
| 业务功能覆盖 | 满足有效证据与独立核验的 b∈B 数 ／ count(B)；缺任一必要维度即缺口；无关新增用例不能抵消 |
| 本轮用例通过 | `count(P_S)/(count(P_S)+count(F_S))`，仅表示整用例已验证部分；同时显示 H_S 与 U_S；H_S 非空仍业务失败，不替代完整通过门禁 |
| 关键链路覆盖 | 满足实际核验条件的适用条目 ／ 适用关键链路；缺项列明并触发必测覆盖率警告 |
| 断言依据确认 | 已确认依据的参与用例 ／ 全部参与判定用例，与独立核验分开，不冒充已验证数 |
| 零分母 | 不适用或暂无有效验证，不显示 100%；M 为空不隐藏非空 S 的结果 |

本轮结果覆盖 S 中的全部所选项（含补充用例）：H_S 非空则本轮失败并列未验证范围；H_S 为空且有未验证才为未完成。full 还须 M 全部有效通过、补充项无失败或未验证，并满足源码、范围、关键真实路径、无过期依据与有效 P0/P1 门禁。`quick`／`on_demand` 无论 S 覆盖多少，都只显示所选范围结果、等级 `null`，不升级 full。

示例（同一冻结集合）：M=S 共 12 项，本轮执行 10 项并有效复用 2 项，则执行 10/12、复用 2/12、有效验证 12/12，其余门禁满足才完整通过。12 项本轮均执行但 2 项依据未确认，则执行 12/12、验证 10/12、未验证 2。按需只选 3 项非必测补充用例且通过、M 有 12 项，则本轮验证 3/3、必测验证 0/12，不能显示全范围通过。

### 3.6 判定样例

| 已知输入 | 执行/验证统计 | full 业务结论 | 证据等级 |
| --- | --- | --- | --- |
| 12 个适用必测均执行、必要核验齐全，其中 2 项仅依据确认缺失，其余有效通过 | E=12，V=10，U=2 | incomplete | B；另有关键缺口仍取 C/D |
| 11 项有效通过，1 项副作用执行结果未知 | E=11，V=11，U=1 | incomplete | C |
| 12 项均有充分有效证据，其中 1 项断言失败 | E=12，V=12，P=11，F=1 | failed | A；A 不代表放行 |
| 12 项全部满足合法复用守卫，无本轮新 Attempt，均有效通过 | E=0，R=12，V=12 | 其余 full 守卫满足时 passed | A；复用来源可追溯 |
| 无有效执行或复用依据 | E=0，R=0，V=0 | incomplete | D |

上表按同一冻结必测集合举例，实际 DTO 仍分别返回 S/M 两组。`quick`／按需无证据等级，所选通过不能替代完整验收通过。确认依据后必须重新评价已存在的实际核验材料，不能直接给已验证数加一。

### 3.7 分层与范围约束

L1/L2/L3 分层统计，上层失败只阻塞依赖它的步骤，独立用例可继续。任一适用必测层级失败、阻塞或未验证，不能显示全部通过。无前端只免网页交互，不免业务 L3（仍应通过接口/命令/智能体完成）。引用外部检查需与被测源码、环境和范围对应并可读原始结果，**绿色汇总不替代原始 L1 证据**。单模块项目仅跨模块传播项不适用并注明原因，本模块变化、用例映射与适用回归照常计入。按冻结范围与当前版本汇总，保留全部尝试，不删失败尝试美化报告。

## 4 执行、证据与聚合

### 4.1 状态维度

| 维度 | 状态 | 规则 |
| --- | --- | --- |
| 执行状态 | 未执行、排队中、执行中、暂停中、已暂停、取消中、已完成、阻塞、已取消、执行异常（10 值） | 表示运行过程；执行器异常与业务断言失败分开。取消后执行器未确认停止、或有副作用且结果无法确认时，按执行异常或阻塞记录并保留未知原因；不再设置独立的待核实状态与人工核实出口 |
| 断言结果 | 未判定、通过、失败、不适用（4 值） | 不适用需要原因；未判定不计为通过 |
| 依赖真实性 | 真实、Mock、混合、未知（4 值） | 可与断言通过同时存在，不能互相替代 |
| 人工复核 | 待复核、已确认、已驳回（3 值） | 保留复核人、时间与意见 |
| 计划发布确认 | 草稿、已发布 | 只绑定计划修订，不确认未来结果 |
| L1 失败类别 | `source_error`、`dependency_missing`、`environment_unreachable`、`tool_failure`、`passed`（5 值） | 区分源码错误、依赖缺失、环境不可达、工具失败与通过；缺依赖不算语法错误 |

示例：同一次模块测试可以是"已完成／断言通过／Mock／已确认"，其真实集成验证仍未完成。面板与报告必须分列这些维度，不允许用一个"未知"布尔值或一个不透明 status 合并。

### 4.2 Step 与 Attempt

Attempt 属于 Step；用例不以一个含糊的"当前 Attempt"代表多步过程。尝试序号从 1 起，**重试数 = 尝试数 − 1**（首次为 0），不用旧成功替代新尝试。新 Attempt 一旦建立立即成为当前，并取代该用例的旧复用资格；新 Attempt 失败、取消或阻塞**不能回退**旧通过或旧 R。副作用的新 Attempt 须重新授权；只读新 Attempt 仍受原允许范围与有界规则约束。传输次数与业务尝试次数分别记录。

### 4.3 证据

- 原始输出为凭据过滤后的捕获流；过滤前字节不得以"原始证据"名义保存在 spool、对象、诊断或备份中。
- 证据绑定运行/步骤/尝试、源码身份与采集来源；只纳入已可靠保存的必需证据，采集失败、缺失或待补的项不计完整。
- 每步结束与运行终止时**先可靠保存再进入下一步**；保存失败明确报错，不假装已完成。
- 失败、阻塞、取消同样保存，不改写为通过，也不因未导出而丢弃。
- 未采集与缺失分别注明；无法确认位置写未知及原因，不编造代码定位。

### 4.4 控制与修订

| 动作／情况 | 处理规则 |
| --- | --- |
| 暂停 | 在步骤边界生效，区分暂停中与已暂停 |
| 取消 | 确认执行停止后才标为已取消；未确认时保持取消中或**未知**，不得伪造已取消。关闭编辑器不等于停止或业务回滚 |
| 并行组边界 | 存在并行执行时"步骤边界"指组内所有活动步骤都到达可中断点；暂停、运行中修改与驱动切换只在组边界生效，正在执行的组内步骤拒绝修改。实现不支持组边界时，进入并行组即禁止运行中修改与驱动切换并说明原因 |
| 重试 | 产生新 Attempt 并立即成为当前；依赖旧 Attempt 的下游依据过期并列需重跑（见 §4.5） |
| 补证 | 关联准确 Attempt；文本确认不能当成功 |
| 退回阶段 | 形成新修订，将下游标为需重跑，旧记录可查，不伪造已重跑 |
| 源码／输入／规则变更 | 绑定新版本并新建运行；查看历史不改变当前结论 |
| 需求／验收项／用例变更 | 生成新修订，不改写冻结计划与已完成记录；受影响运行暂停并提示继续或新建；报告标注依据已过期并列出需重跑用例（复用 P1-FR03 的变更影响） |
| 进程或连接恢复 | 分别处理原句柄重新关联、可安全重试与需人工核实；有副作用且结果未知不得自动重放 |
| 状态展示 | 保留最近确认状态、缺失材料、重试次数与人工处理记录；连接故障不伪造测试终态 |

运行中修改的档位边界见 §2.4；是否通过、计入哪些集合见 §3。

### 4.5 聚合与依赖失效

用例聚合使用**冻结的必需步骤集合、每步当前 Attempt 及它实际消费的上游输出**。步骤输入绑定 `upstream_attempt_id`、`output_object_digest` 与 `value_ref`；控制/前置依赖同样绑定上游 Attempt 与相应条件事实，不能只登记有数据提取的边。

上游建立新 Attempt 时，在同一业务提交中替换该步当前尝试，并把依赖旧尝试的下游当前依据及其传递依赖标为 `OutdatedBasis`／需重跑；结论、覆盖与新报告修订随之更新。**即使新尝试后来输出同样的值，也不自动让旧下游恢复有效。** 无依赖的分支可继续有效；旧执行、输出、断言与报告保留为历史，不伪造新失败或重跑。退回阶段与普通上游重试使用同一失效机制。首发串行；若以后支持并行，存在受影响活动下游时不得直接替换上游，须先按全组边界停止并核实。

| 当前用例事实 | E/R/V 与用户提示 |
| --- | --- |
| 全部必需步骤均为本轮已完成当前 Attempt，依赖关联有效，输出已保存 | 可计 E；依据及必要核验有效且断言明确时才计 V，真实失败可计 F |
| 整个用例只有符合完整守卫的历史复用，本轮未启动该用例任何新 Attempt | 可计 R，按原有效性判 V/P/F，显示来源及本轮未重跑 |
| 已启动该用例任一步的新 Attempt | 立即取消该用例 R 资格；失败/取消/阻塞不得退回旧 R |
| 部分步骤本轮完成、其余只引用跨运行历史步骤 | 保留每步真实事实与复用来源，但不计整用例 E/R/V，列出待执行步骤 |
| 本轮先前步骤仍有效，仅重试其依赖下游 | 未受影响的本轮步骤可保持 E 聚合资格，不要求无关步骤重复执行 |
| 任一步执行异常、取消、阻塞、未知或依赖过期 | 当前用例不计 E/V；仍有效的决定性失败独立计 H，业务结论 failed 并列缺口；无 H 才 incomplete |

例：S1 创建订单 A，S2 核验 A 通过；重试 S1 建立新 Attempt 时，S2(A) 立即作为历史保留且当前依据过期；S1 得到 B 不能与 S2(A) 组合通过，需重新授权并执行适用下游核验。若另一分支 S3 不依赖 S1，其有效事实无需重跑。完成验证需要整用例合法复用，或使必需步骤全部具有本轮有效执行；模板不得把必需步骤改成可选以绕开聚合守卫。

### 4.6 记录、来源与幂等

记录均带 `schema_version`、项目、稳定编号、修订、来源与本机采集时间；**业务顺序以提交序号判断，不按可调整的系统时间选最新**。关键实体：LocalProject、LocalProjectBinding、Module、Dependency、Task、AcceptanceItem、Delivery、TemplatePack、RuleVersion、Case/CaseLink、Plan、Run、Step、Attempt、SourceSnapshot、EnvironmentRef、EvidenceRef、TraceNode、MockDeclaration、Verification、IssueRecord、ReportSnapshot、LocalReview、ReportExport。

用例链接验收项、模块、环境与关键链路；步骤绑定执行时计划修订；证据绑定运行/步骤/尝试、源码身份与采集来源；报告引用精确记录修订与判定策略。问题与缺陷单是同一 `issue_id`，不另建 AI 副本。生成缓存按实际依赖修订集合与生成策略版本失效，依赖变化定向失效。

`prepare_run` 冻结实际输入并产生 `intent_id`；`start` 对同 intent 原子取得既有 run 或建立一个 run；同 intent 异 `payload_hash` 冲突。重跑须显式准备新意图，跨入口恢复同一意图不重跑。`start` 物化摘要须匹配 prepare 冻结的源码；变化时旧意图不可启动，须重新准备并核对授权。导出键包含报告修订、所带复核集合、格式与脱敏策略，不能只用计划号去重。

### 4.7 模型接口与出站策略

| 项目 | 功能要求 |
| --- | --- |
| 接入 | 调用模型 API，默认 DeepSeek；配置地址、模型、密钥引用与超时，并提供连接检查 |
| 用途 | 生成项目摘要、检查内容与用例草稿、验收项建议、交付说明草稿与证据分析 |
| 保留记录 | 请求关联编号、模型配置、输入来源、原始输出与分析结果；与原始测试记录分开 |
| 异常 | 超时、限流或格式错误时 AI 步骤显示失败或未完成；原始证据可查看，人工处理可继续 |
| 编辑器 AI | 单独标明编辑器内建 AI 与插件直接调用模型 API，不混同调用记录或密钥 |

模型只输出草稿与假设，保留输入来源、模型配置修订、供应方请求标识（若有）、原始响应与错误；迟到响应须核对来源修订。模型不可用时原证据、人工处理与导出继续。仅发送选定脱敏材料，无法安全投影则排除并显示分析缺口。

## 5 复用与验证资格

复用与验证是两个不同资格，均按 §3 的集合定义参与统计。

| 资格 | 成立条件 |
| --- | --- |
| 整用例复用 R | 源码身份、环境动态状态、检查范围、入口参数、规则与适配器版本一致；检查已完成、仍有效、证据可读；未被本轮新 Attempt 取代 |
| 有效验证 V | 断言依据已确认、所需证据与独立核验有效、断言明确通过或失败 |
| 证据等级依据 | 仅 full 派生；有效 R 所引原执行证据属于有效执行依据 |

规则：

- 复用不能伪造本轮执行；报告必须显示复用来源与本轮未重跑。
- 新 Attempt 立即撤销该用例的旧复用资格；其失败、取消或阻塞不能回退 R 或旧通过。复用源与失效原因保留，来源修订与证据可查。
- 跨运行继承与本轮部分执行**不得拼成整用例 E/R/V**；界面保留步骤事实与待补执行。
- **复用不能替代缺陷关闭所需的新的实际执行证据**；修复关闭必须读取新回归 Attempt。
- 引用外部检查（含代码托管平台）须与被测源码、环境和范围对应并可读原始结果；绿色汇总本身不能证明 L1 通过。
- 复用资格不改变结论上限：`quick`／`on_demand` 即使大量复用仍只判所选范围。

## 6 报告、复核与问题闭环

### 6.1 报告冻结与当前结论

当前结论键 = 项目 ＋ 源码身份（Git 基准与 diff／非 Git 文件清单及排除规则）＋ 适用范围 ＋ 环境 ＋ 规则/验收/模板/判定策略修订。源码身份包含未提交差异，同提交不同 diff 不合并。

报告正文与等级随精确输入修订冻结，变化生成新内容修订；旧报告与其复核保留。新 full 启动即标"重新验证"，取消或未知不回退旧通过；`quick`／按需只作补充。缺失证据时保留旧历史结论并标当前有效性缺口，不改写旧正文。外部损坏只增加可用性缺口与当前有效性投影，不能继续称证据齐全。

### 6.2 报告内容与本地复核

| 项 | 内容 |
| --- | --- |
| 必需内容 | 范围名称与本轮结果、适用层级、分层统计、业务结论、未执行/阻塞项、Mock/未知、依据过期、证据索引、来源修订 |
| 完整验证专有 | 证据等级与主要（及全部）缺口、断言可信度（已确认／总数）、授权来源与可信度、必要追溯时间戳（开始、结束或采集时间之一） |
| 非完整验证 | 标注"未打分"并给覆盖摘要，同样展示断言可信度、检查配置、代码版本、环境、覆盖与时间戳 |
| 本地复核 | 独立记录：复核人、结论、说明、报告内容修订、时间；**不写入正文、不改变内容修订、不改变执行与断言事实**，不能把失败/阻塞/缺证据改成通过 |
| 状态标签 | 报告"状态"固定指业务结果 `business_outcome`，与 `execution_state`、当前有效性分别标注，不合并为不透明 status |

报告页首固定"范围名称＋本轮结果"，不能把局部验收描述成全项目已通过。面板实时投影与报告冻结快照分别标注。

### 6.3 导出

`ReportExport` 冻结 `report_revision`、附带 `review_ids`、格式、脱敏策略版本、产物摘要与位置。

| 类型 | 内容与边界 |
| --- | --- |
| `markdown_summary` | 声明附件未随文件交付；不含密钥；附证据索引 |
| `evidence_bundle` | ZIP，含 `report.md`、`manifest.json`、`evidence/` 相对路径附件；清单记录包格式版本、报告/复核精确修订、范围、投影策略、每项路径/大小/SHA-256 及缺失或排除原因 |
| 安全底线 | 所有路径为规范相对路径，拒绝绝对路径、盘符、穿越、重复覆盖与符号链接；不可安全处理的附件排除并说明；摘要按实际导出字节计算并与本地原始对象摘要区分 |
| 失败处理 | 只写事务临时位置，完成清单与对象校验后才发布并登记；失败不报成功；跨目录导出分别核对产物发布与工作空间登记 |
| 可读性 | 迁移到空目录后 Markdown 与普通附件应可脱离插件阅读，不依赖原工作空间链接 |

相同冻结输入复用已有产物；新增复核或改变复核集合、格式、策略须生成新导出，不改旧正文。

### 6.4 问题记录与状态

问题字段：标题、级别、影响范围、验收项、用例/步骤/尝试、版本与环境、复现步骤、预期/实际、频率、证据、事实/假设、责任人、修复/回归与关闭依据。事实与假设分段，位置未知保持未知。

状态流：草稿 → 待确认 → 已确认 → 处理中 → 待复测 → 已关闭；复测失败回处理中。严重程度与本地责任人由用户确认；AI 候选级别不能直接成为已确认 P0/P1。重复、非缺陷与暂缓保留原因，不删除。

| 级别 | 定义 | 处理规则 |
| --- | --- | --- |
| P0 | 系统核心能力全面不可用，或造成严重数据损坏等重大影响 | 阻止当前范围通过，立即指定本地责任人 |
| P1 | 关键业务流程不可用或核心结果错误，缺少合理替代路径 | 阻止受影响核心流程通过，修复后复测 |
| P2 | 局部功能异常，存在替代方式或影响有限 | 按范围确定修复计划与验收要求 |
| P3 | 轻微展示或体验问题，不影响主要任务完成 | 进入优化计划并保留记录 |

严重程度与开发排期不同；不将 P2/P3 一概视为满足对应验收项。修复关闭须在**原关闭标准**下有新的实际执行证据，且修复版本等于一次无缺口来源核验的实测源码摘要；修复说明、继承证据或 AI 判断不能替代，原失败 Attempt 不能关闭。

### 6.5 处置与有效阻塞

`IssueRecord` 的处理进度与 `disposition` 分开保存。`disposition` 5 值：`active`／`fixed`／`non_defect`／`duplicate`／`deferred`，均保存操作者确认、理由、证据及必要的 `canonical_issue_id`。

| 处置 | 必要条件 | 对 BlockingRule 的影响 |
| --- | --- | --- |
| `active` | 用户已确认问题与级别，尚未解决 | 关联范围内 P0/P1 阻塞 |
| `fixed` | 新实际回归满足原关闭标准 | 修复关闭；保留原失败与修复记录 |
| `non_defect` | 用户核实误报/脚本原因等，保存具体依据与理由 | 该问题不再作为产品缺陷阻塞；不改原执行、断言与证据有效性 |
| `duplicate` | 指向同项目有效主问题，核实重复依据；禁止自指、循环或悬空引用 | 沿最终主问题计算一次有效阻塞，范围取相关归并范围；不能借归并到低级别问题降低原已确认级别 |
| `deferred` | 用户记录暂缓原因 | 未解决的 P0/P1 继续阻塞，不等于关闭 |

重复链按稳定 ID 去重解析；主问题重开或处置撤销须重新派生阻塞，历史报告保持原修订。误报撤销只改变处置：原用例仍失败或依据失效时报告仍失败/未完成；测试脚本或断言修订后须建立新的有效执行证据才能给新范围通过，不能点击"非缺陷"使原失败变绿。处置不改变证据等级：P0/P1 阻止放行但不把充分失败证据降为 D。

### 6.6 查询合同

列表读摘要、详情按引用读取；所有入口调用同一核心查询，不得只过滤已加载页，也不得全扫历史兜底。

| `query_id` | 允许筛选与排序 |
| --- | --- |
| `reports.latest` | 按项目与冻结范围取最新已保存报告；报告修订折叠 |
| `reports.by_id` | 完整编号精确匹配，不暗示模糊检索 |
| `reports.revisions` | 同一 Run 的修订序列，按修订读取正文 |
| `issues.list` | `project` 必填；`view=OPEN/ALL`（默认 OPEN）；`facet` 为 `NONE/module/layer/review_state/workflow_state/disposition/blocking` 之一并给一个类型匹配的 `facet_value`；`severity` 可独立或叠加；排序固定 `updated_sequence` 降序、`issue_id` 升序 |
| `aggregate_project_runs` | 只读汇总；按已保存报告列出运行的环境、计划修订与计数，不重跑执行、不重算判定、不合并不同解释器结果 |
| `suggest_regression` | 只读，按精确 `dependency_set` 修订与已发布计划修订返回影响面；不创建运行 |
| `discover_tests` | 只读，产生 Test Inventory 投影，供选择 pytest 范围（见 §8） |

`issues.list` 固定 **14 种筛选掩码**：`NONE`、`severity`、`module`、`module+severity`、`layer`、`layer+severity`、`review_state`、`review_state+severity`、`workflow_state`、`workflow_state+severity`、`disposition`、`disposition+severity`、`blocking`、`blocking+severity`；各支持 OPEN/ALL，共 **28 种索引入口形态**。

- `OPEN` 包含 `active`、`deferred`，以及解析到仍未解决主问题的 `duplicate`；`fixed`、`non_defect` 与主问题已解决的 `duplicate` 只出现在 `ALL`。无法解析的重复关联保留 OPEN 并显示缺口。
- 未知是可见且可筛选的值（模块、层级、复核状态均有独立 UNKNOWN 分支），不混作"不筛选"；显式枚举值与字段缺失严格区分。
- 一次只选一个主筛选维度，可再叠加级别；首版不提供任意多维交叉表达式。切换主维度清除上一主维度条件并重新分页。
- 游标绑定 `query_id`／schema、条件摘要、`commit_id` 与末尾完整排序键；不同条件不可复用游标。跨条件或版本重用返 `QUERY_CURSOR_MISMATCH`，非法组合返 `QUERY_UNSUPPORTED_FILTER`，索引缺失/损坏返 `INDEX_REBUILD_REQUIRED` 并重建目标分片。
- 有 m 个已知模块的单条问题最多产生 **4m+24** 个入口记录（无模块按一个 UNKNOWN 分支计）；这是明确的写放大上界，不是新增实体。
- `review_state` 为 `UNREVIEWED`／`REVIEWED`／`UNKNOWN`，含义限定为"当前问题事实是否已有有效人工核对记录"，独立于处理进度、报告本地复核与平台审核；被核对事实变化会使当前投影回到 `UNREVIEWED`，原确认永久保留。

索引与游标的实现口径见架构·存储与恢复 §13；问题查询投影字段见架构·报告与缺陷 §14。

### 6.7 永久保留与面板

全部业务记录、证据、报告修订、导出、诊断与复核**永久保存**：无保留期、无自动删除、无删除入口。只回收证据已落盘且执行停止后的运行副本/运行临时文件/上传冗余临时副本，以及恢复确认的空对象和无有效内容的事务残留；已写入的输出先抢救为部分或完整证据，不能先清空。空间不足时停止接纳新增字节并按控制流程暂停/停止，**不驱逐历史**。空间统计不删除材料；材料缺失只产生可用性缺口，报告如实显示缺口且不改旧正文。

检查面板（P1-FR17）三段：运行前（范围、必测、跳过项、环境与源码）、运行时（进度、分项状态、可用动作及原因）、运行后（业务结论、证据等级、缺口、导航）。信息区只读，动作区提供开始/暂停/恢复/取消/导出与跳转；业务编辑位于计划、工作台、设置等子视图。统计与等级只读核心 DTO，full 才有等级；plain 不渲染仓库字段；一期缺口跳记录详情，不依赖二期源码标注与图。

当前检查按原因给出下一步：断言失败到证据/问题、环境阻塞到对应配置、依据未确认到依据核对、未知副作用到状态核实（不给直接重跑）；详情仍展示全部缺口。`copy_repair_brief` 从 Issue/Attempt 精确修订生成脱敏文本，事实与假设分段、位置未知不猜测、附复测入口；该动作不执行修复、不关闭问题，也不保证可调用编辑器聊天 API。项目隐藏/恢复偏好只记录展示选择，隐藏不停止运行、不删除业务数据或引用。

## 7 能力与内置模板

能力与模板是**必须实现并验证的交付清单**，不是已安装能力声明；能力只在适配器、模板与验收均有证据后才标"支持"，未测标"未验证"。

### 7.1 能力方式

| 能力 | 一期方式 | 必需输入及边界 |
| --- | --- | --- |
| Python 源码可运行 | 自动适配 | 解释器、范围、适用构建/加载/启动入口；不猜启动命令 |
| 既有 Python 测试 | 登记命令执行；大项目按 pytest 文件/目录/marker 范围 | 入口、预期、依赖环境、参数；JUnit 与原始输出；不自动知道全部业务需求 |
| HTTP 集成 | 已配置流程执行 | 目标、凭据引用、变量、断言、独立核验；远端版本未知不冒充源码一致 |
| 页面业务 | 人工步骤及证据 | 操作与最终核验，不录制回放 |
| 智能体业务 | 登记入口执行或导入实际工具记录，逐次评价 | 输入、实际调用与业务结果；不能凭自述证明执行 |
| 其他技术栈 | 外部格式导入 | 来源、源码身份、尝试、输出、附件；保留 `EXTERNAL_IMPORT` |
| 模型辅助 | 选定脱敏材料生成草稿/解释 | 出站策略、材料、模型；可关闭，不发布计划或伪造执行 |

### 7.2 六个内置模板

`template_id` 六值固定；模板是版本化数据，不新增第七个模板。

| `template_id` | 用途 | 提醒项与关键核验 | 适用边界 |
| --- | --- | --- | --- |
| `python-library` | Python 库/纯函数 | 适用语法/加载、正常/边界/异常输入、预期独立比对 | 无持久化不要求数据库 |
| `python-service` | Python 服务 | 适用构建/加载/最小启动、健康与关键入口、依赖失败、状态变化核验 | 仅实际服务项适用，库项目不强套 |
| `http-workflow` | API 流程 | 同对象请求串联、字段/业务断言、错误路径、持久化独立核验 | 鉴权/会话/持久化按适用条件；必须真实链路不以 Mock 顶替 |
| `manual-web-workflow` | 人工页面验收 | 业务路径及适用按钮/分页/跳转/表单/滚动/鼠标/异常提示，刷新后核验 | 无页面不应用；尚不支持不等于不适用 |
| `agent-workflow` | 智能体评价 | 实际输入/工具调用/结果、发布评价规则；随机输出默认重复三次分别留存 | 无采集列缺口，不采信 AI 自述 |
| `ticket-workflow` | 工单贯通示例 | 创建取 ID → 分页找到同 ID → 详情 → 改状态 → 刷新/重进 → 独立持久化核验 | 联调示例，不代表所有业务 |

模板包内容：`schema_version`、`template_id`/version、适用条件、稳定条目 ID、模板项集合、关键链路、输入字段、核验方式与样例夹具。**空关键链路须给不适用理由；缺字段不等于空集合。** 模板项是提醒项，不是固定必测清单，不静默删除。

| 字段组 | 必须表达 | 校验 |
| --- | --- | --- |
| 身份与来源 | `schema_version`、`template_id`/version、名称、来源、适用业务/技术栈 | 引用明确版本；未知结构不得自动当可执行模板 |
| 条目 | 稳定 `item_id`、层级、目标、前置、输入字段、步骤/登记入口类型、预期/依据、验证方法、证据要求 | ID 唯一、引用可解析，正文不是可执行 shell |
| 适用性 | 模块/前端/持久化等条件及理由 | 未满足能力不是不适用；无法判断先列待确认 |
| 模板项与关键链路 | 模板项 ID 与处置；关键链路 ID、必须真实依赖与不可省核验 | 缺处置字段阻塞；显式 `not_applicable` 须有理由与证据 |
| 草稿样例 | 正常/边界/异常输入与期望、生成来源、确认状态 | 期望不是实际结果，样例不冒充真实执行 |

### 7.3 模板项处置与覆盖

模板项处置 3 值：`included`／`not_applicable`／`unsupported`。`not_applicable` 必须给理由与证据；`unsupported` 作为已知限制保存，不等于不适用。缺处置字段阻塞发布。AI 逐项给出处置，不静默删除；必要新增按是否填补覆盖缺口判定——必要项进入 full，可选项只进入 `on_demand`。

业务功能清单是完整验证的覆盖依据：缺清单、含 `unknown`、含未支持范围或功能 × 必要维度未覆盖时**阻止 full**。同一模板处理两个项目应生成结构一致的草稿并标注来源；上下文缺失时列缺口并阻塞；未确认草稿不进入执行。发布与导入校验覆盖五类反例：缺模板项处置字段、重复 ID、悬空引用、显式不适用、尚不支持。

### 7.4 适配器最小交付

| 能力 | 最小执行机制与输入 | 实际输出/不支持条件 |
| --- | --- | --- |
| Python 源码检查 | 用户登记解释器及适用语法、导入、最小启动入口；通过共同命令执行器运行 | SourceCheckResult 及命令、退出事实、原始输出；未登记入口不猜命令，不将缺依赖当语法错误 |
| 既有测试命令 | 明确 argv、工作目录、环境修订、输入、预期及副作用授权 | Attempt 和输出块；未经登记的 shell 正文不能因来自模型而执行 |
| HTTP 流程 | 已登记目标、方法、凭据引用、字段提取、变量来源、关联业务对象与断言 | 响应事实与请求关联；领域统一评价断言；写请求恢复必须有端点幂等合同 |
| 独立核验 | 首发支持已配置只读 HTTP 查询与纯函数独立预期比对；输入同一业务对象标识与独立预期 | VerificationResult 含来源、对象、观察值、预期引用、证据与有效性；数据库驱动仅在安装清单明确列名且实测后可用，不声称通用数据库支持 |
| 人工页面 | 发布步骤清单、用户实际操作说明、附件及最终读取核验 | 人工来源、步骤/尝试关联与材料缺口；不含浏览器录制回放 |
| 智能体业务 | 登记入口调用，或导入实际工具事件；预先发布评价规则，随机输出按计划三次分别执行 | 每次输入/响应、实际工具事件与业务观察；缺工具采集保持缺口 |
| 外部结果导入 | `aitest.external-result/1.0` 结构及受控附件包 | 验证来源、关联与摘要，始终 `EXTERNAL_IMPORT`；未知执行字段不自动启用 |
| 可选模型 | 显式材料范围、ModelProfile 与出站策略，结构化草稿 Schema | 草稿/解释与来源修订；关闭或失败仍支持人工计划与报告 |

各适配器复用同一调度、授权、Attempt、采集、导入与错误处理组件，不创建六套执行引擎；首发串行执行依赖顺序。每种能力须有真实可执行成功样例、证据不足样例与不支持输入样例，另加安全采集、加载来源不符与依赖过期的反例。

### 7.5 外部结果与智能体事件

`ExternalResult` 必需字段：`schema_version="aitest.external-result/1.0"`、`source_system`、`source_result_id`、`source_revision`、`project_id`、`layer`、`source_identity`（未知为 `null` 并填 `reason`）、`attempt_ref`、`execution_facts`、`assertions`、`mock_declarations`、`attachments`。没有本地 Run/Attempt 映射时由导入用例创建外部记录并显式关联，不能借外部编号覆盖本地 Attempt。**幂等键为 (`project_id`, `source_system`, `source_result_id`, `source_revision`)**，冻结 `payload_digest`，同键异内容冲突。

- `execution_facts`：入口类型、输入摘要、真实开始/结束信息（缺失为 `null`）、执行状态、实际退出码/响应码与输出引用。
- `assertions`：已登记 `case_id`、依据引用、观察值、外部自报结论与可核验材料；**外部自报结论不直接成为本地有效验证**，能独立核验的重算。
- `attachments`：`attachment_id`、相对包内路径、媒体类型、`size`、`digest` 及完整性；解包拒绝绝对路径、链接逃逸、重复 ID 与摘要不符；未知扩展字段保留但不执行。

智能体工具事件包含 `event_id`、`source_result_id`、序号、`tool_name`、`call_id`、`parent_call_id`（可空）、参数安全投影、实际结果引用与采集来源。循环调用同一工具用不同 `call_id`；缺事件的工具调用保持未知。**工具调用只是证据**，仍须按发布规则核验最终业务对象；被测智能体只认实际采集的工具调用，文字自述不作调用证据。随机业务输出按发布规则逐次评价，默认重复三次属于测试设计，各次保留结果且每次都须满足必需业务断言。正常导入、重复导入、异内容、附件缺失、未知源码与仅有自述分别作为导入合同样例。

## 8 pytest 适配（唯一处）

本节是一期 pytest 适配的唯一正文；`entry_type=pytest` 仅表示执行方式，六个业务模板不变。除本节外不再另行描述 pytest 行为。

**范围与选择**

- 默认以测试文件或测试目录/包为选择粒度；`marker` 可选；单个 node ID 只作阶段 C 的定向补充。模块模式的入口可以是目录 scope；目录下至少一个文件被实际观察即可核对入口，解释器仍须精确匹配。
- `discover_tests` 产生文件级 Test Inventory 投影；AI 只从该投影中选择范围，不接收全量 node ID，不编造范围；选择草稿由服务端校验并生成 Case。
- 一个 case 一个测试范围、一个执行步骤；`inputs[0]` 承载范围，步骤说明"运行该范围并核对结果"，不新增 PlanProposal 字段。
- 包名只作报告标签，不替代模块；模块映射仍用已登记模块与 `CaseLink.module_ids`，未登记标缺口。
- 选择完整性：不存在、空范围、无验收项链接阻止发布；验收项无范围、漏选测试、跳过比例高只警告并进入报告，不自动补选或分组。

**执行**

- 每个范围单独启动 `python -m pytest --import-mode=importlib --rootdir=<package-root> --junitxml=<workdir>/pytest.xml <scope>`，不把多个包塞进一个进程。
- 一个 prepare 只绑定一个解释器；多解释器项目在阶段 A/B 按包拆 run，不做项目级自动聚合。
- JUnit XML 作为通用 `artifact` 证据永久保存（媒体类型 `application/xml; profile=junit`）；原始 stdout/stderr 按原证据规则保存。JUnit 可压缩并设大小上限，超限标 `truncated`；派生结果不替代原始证据。

**核验与失败定位**

- pytest 结果只作**断言结果**；独立核验按验收项单独登记，缺少独立核验的 case 显示"未验证"，不判完整通过。
- 失败必须给出 `failure_frame`（断言/异常位置）、`suspect_source_frame`（最后一个项目源码、非测试、非 fixture 帧）、失败类别、消息、堆栈与证据；JUnit 缺位置时解析 traceback。
- `location_unknown` 只在 traceback/JUnit **完全没有失败帧**时写；有 `failure_frame` 但无法映射到项目源码、或没有 `suspect_source_frame` 时保留已知断言位置，并另记"可疑位置未知"——不猜路径，也不把已知位置改写成 `location_unknown`。
- 核验比较 `expected_test_count` / `expected_outcome`：`matched` 只表示冻结预期满足；`mismatched` 且缺口为 `business_fact_mismatch:<field>` 时是明确业务失败，进入决定性失败。`business_fact_missing`／`business_fact_filtered`、位置未知等真实核验缺口不产出通过或失败；业务字段不匹配只留在核验事实，不把已完整保存的证据标成有缺口。
- JUnit 缺失/截断、测试数少于 Inventory、全部 skipped、退出码与 JUnit 冲突时标不完整，不判通过。

**失败族与问题草稿**

- 签名 = 异常类型 + 归一化后的首条消息 + 首个项目源码帧；同一 scope 内同签名合并，不同签名分开。
- 问题草稿只从每步**当前 Attempt** 的失败簇生成；被新 Attempt 取代的历史失败保留在事实中，不重复成簇。草稿只到 `draft`，用户确认后才 `confirmed`；AI 根因假设只作候选，不写证据、不自动关闭。
- 草稿身份与失败细节由核心从已保存 JUnit 重算：调用方只提交 `run_id`/`step_id`/`signature`，不能伪造节点、位置或证据；冻结的簇随问题记录保存并可读回。
- 用户可从冻结簇中勾选部分测试拆分为新草稿，核心校验节点全部属于源簇并写 `split_from`（子草稿身份 `issue:pytest:split:*`），源问题不变；合并仍走"重复问题"处置。

**面板与报告投影**

- 项目页提供"发现测试"；计划页显示范围/测试数/预期/Mock/验收项；工作台按范围显示进度并展开到每个测试的 `failure_frame` 与 `suspect_source_frame`；失败卡片可发送 `openSource` 打开发送方校验过的 workspace-relative 源码行，找不到位置显示 `location_unknown`。
- 运行视图同时给出 L1/L2/L3 步骤计数，步骤卡显示层级；报告页读取冻结的 `pytest_failures`（node ID、失败类型、消息、`file/line`、`suspect_source_frame`、`location_unknown`、堆栈片段）。失败区按签名簇显示"新增/既有"基线标记，并可生成服务端校验的问题草稿。
- 报告创建时还冻结 `pytest_baseline`（新增/既有/已修复节点），只说明变化，不证明修复或关闭；没有可比较报告或旧报告缺 `pytest_failures` 时保持未知。未核验 Mock 进入 `critical_mock` 缺口，报告不能写成模块正确。
- 工作台另有只读"回归建议"，按依赖图精确修订与已发布计划修订显示影响模块、未登记模块与建议用例，不改计划、不自动执行。不新增页面结构，不出现分组确认。

**阶段边界**

- 阶段 A 只支持 `on_demand`，不创建问题记录，只展示失败事实和可疑源码位置；AI 根因假设在阶段 B 才可选，且只作候选，不进入证据。
- 阶段 B 按失败签名簇生成问题草稿并复用现有问题闭环；阶段 C 补 L3、依赖/回归、多解释器聚合、基线对比与 node ID。定向 node ID 必须精确存在于 Inventory；项目级汇总按运行/验收项读取已保存报告，不合并不同解释器结果。
- 测试源码中的 `unittest.mock`、`pytest-mock`、fixture 只生成静态候选（Inventory 可带 `mock_candidates`）：出现 mock 字样不判假，没有字样也不判真；未核验的 Mock 触发 `critical_mock`，pytest 通过不能升级为真实业务通过。
- 不新增模板、不新增公共 Schema、不引入用户分组；六个业务模板与 `entry_type=pytest` 同时存在。

## 10 明确不做

- 不登录、不上传、不跨账号协作、不监听 TCP，不提供本地 HTTP 服务、数据库、消息队列或独立发送 Worker；平台侧能力不在一期。
- 不安装浏览器扩展，不实现自动录制回放；页面业务只有人工执行与证据关联。
- 不提供依赖/链路图、源码行内标注，也不把 dirty 缓冲区判为当前已核实源码（二期能力）。
- 不实现平台接收、审核、共享查询或宿主投影；不引入字节级对拍与平台回执（三期能力）。
- 不提供任何删除业务记录的入口、保留期或一键清理；空间不足不驱逐历史材料。
- 不新增第七个业务模板；pytest 只新增 `entry_type` 与执行方式。
- 不做多解释器项目级自动聚合、基线对比、按 node ID 全量选择与用户分组（阶段 C）。
- 不要求模板穷尽需求；AI 不自动发布计划、不自动授权、不自动确认依据、不自动处置或关闭问题、不替用户作出结论。
- 不提供任意多维交叉查询表达式，不以全历史扫描兜底查询，不把执行状态当业务结果过滤。
- 不因目录不是 Git 仓库而拒绝建立项目或降低检查范围；不因文档一致、单元/合同/夹具测试通过或组件级进程通过就写成真实验收通过。
