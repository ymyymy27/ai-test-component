> 适用期次：一期（P1-FR01—17 / P1-AC01—35，当前唯一交付范围）
> 主责：范围、FR 与验收预期
> 状态：合同有效，验收未完成——本文件只定义范围、规则与验收预期，不表示任一功能已实现或已通过真实环境验收。

本文件是「项目落地」生命周期中的需求规格：回答做什么、不做什么、凭什么价值做、拿什么预期验收。字段、枚举、判定公式与提交/恢复的技术合同由功能分册与架构分册维护，本文件不另起定义；当前实现与验收登记以[项目现状](../../../现状.md)为准。

## 1 产品目标与成功指标

### 1.1 产品目标

建设一个可嵌入 Trae、**本地执行与存储、可选模型出站**的 AI 辅助测试插件：理解项目上下文、组织测试、调用模型 API 辅助分析、收集原始证据、形成问题清单并跟踪修复。

一期不依赖插件平台服务端：不部署服务、不登录、不上传结果、不做跨账号协作。全部记录保存在本机文件工作空间。

插件以 Python 核心包、Trae 扩展和轻量面板交付。链路检查是插件的一项能力；项目上下文、测试规范、分层执行、问题反馈与本地报告导出共同组成完整产品。

目标分解：

- 用相同规范组织测试，使验收项、用例、执行、证据和问题可相互追溯。
- 分别表达源码可运行、模块功能正确和用户完整业务流程通过。
- 将实际执行结果与开发说明、Mock 声明、AI 候选分析分开保存。
- 模型接口不可用时仍能保留证据并继续人工处理。

### 1.2 成功指标

成功指标用于判断一期是否达成，不引入新阈值、不设百分比口径；每项仍以第 6 节对应验收场景的输入、步骤、版本与原始证据为准。

| 成功指标 | 合同判定要求 |
| --- | --- |
| 三层闭环 | 三层测试可闭环执行，问题可复现并回归 |
| 档位不越权 | 按需自测不产出完整通过结论，并如实标注未执行范围与原因；完整验证确认计划后推进，遇副作用、新凭据或范围扩大仍需对应授权；只有完成全部门禁才给完整通过 |
| 单模块可用 | 被测代码只有一个模块时仍可完成适用检查 |
| 可追溯 | 本地证据与版本可相互追溯，报告可在本地导出且不含密钥 |
| 结论分层 | 仅完整验证给证据等级与主要缺口，快查和按需未打分；业务结果与证据等级分别展示，面板读取同一判定 DTO，报告冻结来源修订 |
| 覆盖率真实 | 快速检查可在一次改动后给出可判定的结论与覆盖摘要（**不打分**），且不伪装成完整验证；完整验证的**适用**覆盖不低于当前范围内全部适用业务功能×必要维度与关键链路清单 |
| 鲁棒性 | 断网与重复运行不产生错误结论；模型不可用不影响原始证据查看与人工处理 |
| 永久保留可验证 | 全部记录、证据与报告永久保存、界面无删除入口、无到期清理；材料缺失时如实显示缺口（见 P1-AC28） |
| 复核独立 | 本地复核不写入报告正文、不改变报告内容修订，也不改变测试事实（见 P1-AC29） |
| 本地自治 | 本地核心、记录、人工处理与导出不依赖插件平台服务或平台登录；模型、可选 GitHub 与被测远端环境分别依赖其已配置的网络及凭据 |
| 技术侧可核对 | 模块契约、来源核验、文件一致性、崩溃恢复与真实编辑器接入均有对应验证 |

### 2.3 明确不做

- 不部署服务端，插件自身不监听任何网络端口。
- 不登录、不接入统一账号，不做结果上传、回执、共享查询与跨账号审核。
- 不做自动操作录制与回放、可视化流程图绘制、任意语言自动插桩。
- 不做自动处理合并冲突、无人确认自动修复发布、生产部署管理。
- 不修改被测仓库：GitHub 接入为只读，不通过 GitHub 自动发起测试、不处理 PR；本地测试由用户授权后执行。
- 不做跨语言静态影响分析（见第 7 节）。

### 2.4 单模块、无仓库与多模块

一期必须支持「被测代码只有一个模块」的情形：可完成该模块的 L1／L2／L3 适用检查并形成报告。

**一期必须支持「被测目录不是 Git 仓库」的情形**：全部检查、证据、报告与导出均可完成；凡与仓库、分支、提交、远端相关的内容一律不出现（不显示为空值、不显示「未知」），源码变化改以文件清单摘要与差异快照判定，结论口径不变。

跨模块依赖传播仅在登记两个及以上模块时适用；单模块仍须进行本模块变更映射、回归建议与快速检查，仅跨模块传播显示不适用，不作为失败或缺失。

### 2.5 试点场景

试点采用工单管理示例，验证创建、查询、分页、详情和状态修改的真实业务结果。三层测试分别评价，不能用 GitHub 绿色状态、接口成功响应或 AI 文字说明替代完整证据。

### 2.6 复用与读取边界

复用与增量处理用于减少重复工作，不得牺牲证据与判定口径。

- **复用优先**：各派生物保存实际依赖的源码、上下文、验收项、规则、模板、环境及生成策略修订集合；仅在实际依赖全部未变时复用，不重新调用模型。只重算受影响部分；单模块仍检查本模块变化，跨模块传播才是不适用。首次或映射不明使用已发布保守检查集合；无法确定时提示确认计划。
- **分析材料最小化**：模型只接收当前任务选定的脱敏结构、差异、证据摘要及必要代码片段，不发送全仓源码或整份日志。材料因供应方输入限制被截断时，标注「基于部分材料」及缺口。
- **源码读取边界**：一期在用户显式「分析选定项目内容」、计划确认与发起运行时读取所选范围源码；分析不要求已有计划，不等于发布或执行。面板、历史和进度读已保存记录，不自动扫描当前目录；运行前展示最近固定版本并提示「当前目录尚未重新核实」。二期显式跳转可先查目标元数据；打开历史快照优先，用户请求校验当前文件时允许只哈希目标文件，不遍历整仓。
- **源码固定**：首次固定须建立真实内容摘要。元数据只提示可能变化，不证明内容相同；物化时对实际复制字节计算摘要并核对复制期间变化。按所选模块、依赖闭包、配置和入口物化，运行副本为临时产物，执行停止且证据落盘后回收。
- **完整验证不可通过删减变轻**：同一已发布验收范围内的适用必测项不得通过运行中删减规避（见 P1-FR07）。
- **红线**：优化不得抬高通过结论、跳过独立核验、把未知当已知或少写证据。

### 2.7 未来期次

- **二期（展示与兼容增量）**：复用同一核心，增加非 Trae 编辑器、操作系统组合、源码定位与行内标注、依赖与链路图、能力诊断与面板增量；不重算一期的判定与统计。二期分册位于 `docs/90-未来期次/二期/`，本仓库当前尚未建立对应文档。
- **三期（账号关联与结果上传）**：使用平台提供的账号与项目身份，将已保存结果安全投影、冻结、出站发送并核对回执；不实现平台接收、审核、共享查询或宿主，不引入本地 HTTP 服务、数据库、消息队列或独立发送 Worker；平台不可用时，已具备的本地能力仍应可用。三期分册位于 `docs/90-未来期次/三期/`，本仓库当前尚未建立对应文档。

### 2.8 产品级使用与执行合同

以下合同约束多个功能，均落在既有 17 项 FR、35 项 AC 之内，不增加平台服务，不改变永久留存与产品分期。

#### 2.8.1 最小首次输入

适用于 P1-FR01/04/06/08/17：选择目录、检查目的、登记实际入口/解释器及该检查必需环境，确认计划摘要后运行。可由目录创建单模块草稿；仅快速/按需检查时，不要求填写无关上下游、完整交付表、数据库或模型凭据；正式提测仍遵守 P1-FR02，完整验证仍须完整验收依据。首次默认快速检查，范围由已发布保守规则与关键链路生成，人工也可配置；模板项只作提醒，不构成必测下限；无可用模板进入自建/导入，不擅自执行猜测命令。

#### 2.8.2 验收范围与结论上限

适用于 P1-FR06/07/14：计划发布前明确验收目标、包含/排除模块或业务目标及原因、依赖闭包、适用条件、模板修订；生成不可变 AcceptanceScope 修订。完整验证覆盖该范围全部适用必测，不表示自动覆盖整个项目；只有范围确为全项目才能如此展示。发布后不通过删必测或缩范围修饰原结论，范围变化建立新基线和运行。完整验证运行中不可修改计划；任何范围、用例、预期或依据变化都必须新建按需自测运行。结果标题、复核与导出均带范围。

#### 2.8.3 计划级执行许可与逐项记录

适用于 P1-FR07/09：一次计划确认生成独立 `PlanExecutionGrant`，绑定计划、understanding 修订、范围、动作类别、凭据范围与环境；计划内且许可内的副作用动作由核心生成逐动作 `ActionAuthorization` 记录（来源 `plan_grant`），不逐动作点击；越界动作仍集中列出并逐项确认，生成独立挑战/交互/确认记录。相同未执行动作的有效授权不重复询问；新尝试不自动继承副作用授权。不给无范围、无记录或永久的集合授权。

#### 2.8.4 模型出站

适用于 P1-FR04/06/17：模型配置独立于平台上传。首次出站确认项目、供应方/接收地址和材料类别，源码片段默认关闭；只发送显式选定脱敏材料，范围或目标变化重新确认。开启源码片段也不发送全仓。关闭 AI 阻止后续模型发送，已发请求不宣称已撤回；人工配置、证据和报告可用。平台上传策略不替代模型策略。

#### 2.8.5 主流程与历史查找

适用于 P1-FR17：主按钮标明「运行快速检查／运行所选检查／运行完整验证」；首屏展示范围、业务结果/未完成原因与下一步，等级/覆盖详情可展开。驱动为高级配置。动作区紧邻说明并调用核心用例；未知副作用先核实。

适用于 P1-FR14/16/17：一期按项目/业务结果/完整运行或报告编号筛选，修订折叠；隐藏项目仅默认列表偏好，可恢复，不删除、不影响活动任务；空间不足给组成和既有备份/迁移入口。二期才增加按源码分组的高级历史页。

#### 2.8.6 人工确认来源与重新执行

- 人工确认须来自核心认可的用户交互，MCP/非交互入口不能自报角色完成授权、发布、依据确认、处置或复核；重复确认幂等，输入变化重新确认。具体入口权限由一期接入分册第 9 节维护。
- 重新执行业务与原请求恢复分开；新副作用 Attempt 重新授权，同号幂等恢复须有端点合同且不产生第二次业务执行。

#### 2.8.7 统计、失败优先与依据确认

适用于 P1-FR06/07/09/14/17：沿用整用例 E/R/V/P/F/U，另由领域按判定与统计唯一口径派生当前有效决定性失败 H。所选 H 非空必须 failed 并同时列未完成范围；后续阻塞不使前步有效失败消失，也不能把阻塞本身算失败。失败所需依据确认、核验证据、来源及依赖必须有效；失效旧失败只保留历史。面板、报告、导出共享结果，分别标已确认失败与整用例验证失败，不相加、不改分母。

- 执行完成 E、有效验证 V、有效通过 P 分开，V_X⊆E_X∪R_X，E_X∩R_X=∅，分别对 X=S/M 统计；未确认依据只影响有效验证，不抹掉已执行事实。唯一集合定义见一期功能文档第 3 节。
- 后补依据确认按准确 Case/依据修订及 ConfirmationRecord 派生 `effective_assertion_basis_state`，不修改冻结 Case/Plan 或旧报告。12 项执行、2 项依据未确认时 E=12/V=10；补确认后只有实际核验仍有效才可 V=12，依据变化后旧确认失效。
- 问题修复关闭需要新回归证据；核实非缺陷、重复归并为独立处置，不改变原断言，暂缓继续阻塞。BlockingRule 按一期功能文档第 12.2 节计算有效问题。
- 复用与范围子场景（既有 AC 的边界）：P1-AC18 中按需 S 可包含非必测补充用例，以 S 展示本轮结论、同时展示 M 覆盖，不能升级 full；P1-AC21/27 中 10 项新执行加 2 项合法复用时执行 10/12、复用 2/12、验证 12/12，复用后新 Attempt 失败或取消不回退旧通过。

#### 2.8.8 视图快照、备份与迁移

- 视图快照与事件游标固定同一提交边界，订阅从其后重放，不能在两次读取之间跳过已提交事件。
- 备份覆盖所选边界前全部永久历史及引用闭包；在线备份明确活动材料不在范围，迁移须先完成受控收尾和完整备份。历史报告不依赖最新索引或外部导出副本才能恢复。
- P1-AC28 的迁移子场景：完整迁移保持严格闭包门禁；显式已知缺口迁移先确认 A/G、验证无新增损失、保留原目录及缺口，复制中新增丢失拒绝切换。

#### 2.8.9 执行正确性与轻量运行边界

| 确认语义 | 草稿未发布不能执行；已发布但依据待确认可执行但不计已验证；确认依据不替代业务执行/核验，也不改写冻结计划 | P1-AC17/21/32 |
| 关闭编辑器 | 有活动或已授权可推进的执行时核心保活并续行；仅暂停/人工待办等无可推进工作时持久化后可退出，重开恢复同一运行，不自动重放或解除暂停 | P1-AC19/34 |
| 日常读取 | 列表按有限查询索引分页，详情按引用取安全对象，普通查询不扫描全历史附件；索引损坏明确恢复，不靠隐式全扫伪装正常 | P1-AC27/28/34 |

上表是现有功能的确定性与异常守卫，不新增服务、平台功能、费用/资源预算或总执行时限；永久历史与证据保留不变，物化副本仍须在全部执行停止和证据保存后才可回收。

#### 2.8.10 报告查询、配置入口与问题筛选

- 报告查询：一期报告列表业务结果筛选使用 `reports.latest`，完整 Run/Report 编号精确匹配使用 `reports.by_id`，展开修订使用 `reports.revisions`；与存储分册的页面控件与 QuerySpec 固定目录一一对应，不扫描全部证据或仅筛当前页。界面标明业务结果，不与执行状态混称。
- 配置入口：设置可查看目录绑定并发起重新绑定，宿主负责目录选择、核心负责校验和形成绑定修订；取消选择不改变绑定。只有可靠已有记录可自动填入，实际入口、预期和授权仍按门禁确认，无法推断时显示未知。P1-AC30/32/34 覆盖这些入口、编号查询及索引状态。
- 问题筛选：P1-FR15 的问题列表须提供模块、层级、级别、人工复核及现有处理/处置/阻塞筛选；首版一次选择一个主维度并可叠加级别，提供未解决与全部问题范围。未知字段不能被隐藏或误作全部，问题关闭和复核规则保持独立。P1-AC08 在原场景基础上增加 `issues.list` 的 14 种掩码及 OPEN/ALL 覆盖，验证多模块问题单次查询不重复、同 commit 分页无漏重、筛选切换重置游标、归并主问题关闭/重开同步改变受影响投影、旧历史可读，以及索引异常明确提示而非全扫。

## 4 业务功能与价值判断

下表把 17 项功能按业务目录归位，说明各自解决的业务问题与结论所需的证据形态。它不新增功能编号，也不改变第 5 节的规则。

本表的“证据强度”指该功能结论所需的最低证据形态（合同要求），**不是已取得的证据等级**；证据等级 A/B/C/D 只由完整验证派生（见 5.7）。

| 业务功能目录 | 对应功能 | 用户价值 | 证据强度要求 |
| --- | --- | --- | --- |
| 项目上下文与源码基线 | P1-FR01 | 合并后的多个模块有同一份可追溯的项目与依赖视图 | 稳定项目编号 + 真实内容摘要；仓库可选，非 Git 目录不得降级 |
| 交付说明 | P1-FR02 | 分清开发者说完成了什么、测试验证了什么 | 开发自述与测试验证分列；AI 文字不作完成率 |
| 变更影响与回归建议 | P1-FR03 | 改动后知道该重跑哪些用例 | 依赖登记与用例关联的确定性匹配；推导须标“可能不完整” |
| 检查内容生成 | P1-FR04 | 不靠个人经验决定查什么 | 模板项逐项处置（included／not_applicable／unsupported）+ 业务功能清单 + 关键链路 |
| 测试规范版本 | P1-FR05 | 同一规范跨项目复用，历史结论可解释 | 不可变规则版本；导入未发布不生效 |
| 计划与用例 | P1-FR06 | 执行前就知道验收边界与断言依据 | 用例字段齐全 + 独立核验方式 + 断言依据状态 |
| 运行档位与驱动 | P1-FR07 | 快查不冒充满分，完整验证才谈证据等级 | 档位与驱动冻结；结论上限只由档位决定 |
| L1 源码可运行性 | P1-FR08 | 先排除“根本跑不起来” | 语法/构建/加载/最小启动的实际结果；无成功证据不得称可运行 |
| 引导式工作台 | P1-FR09 | 出错时能停在现场、补证、重试 | 每次尝试保留；阻塞原因可见 |
| L2 函数与模块 | P1-FR10 | 模块功能正确性可判定 | Mock 只覆盖声明范围，业务效果须独立核验 |
| L2 接口与集成 | P1-FR11 | 请求通了不等于业务对 | 业务断言 + 独立数据核验 + 数据来源与复位记录 |
| Mock 真实性 | P1-FR12 | 不被“看起来通过了”误导 | 真实／Mock／混合／未知由本次环境与证据决定，静态只给候选 |
| L3 业务场景 | P1-FR13 | 用户真正能完成业务流程 | 完整操作路径 + 最终持久化核对 + 操作证据 |
| 报告与导出 | P1-FR14 | 结论可带走、可复核、可对账 | 报告内容修订 + 证据索引 + 脱敏导出 |
| 缺陷与回归 | P1-FR15 | 问题有编号、有证据、有回归 | 关闭须新的实际执行证据 |
| 永久保留 | P1-FR16 | 早期证据不会因时间消失 | 无删除入口、无到期清理；缺口如实显示 |
| 信息面板 | P1-FR17 | 一眼看清这次检查要查什么、查成什么样 | 只读、与领域判定同一 DTO、实时值与快照值分别标注 |

## 5 功能需求（P1-FR01—17）

每条按「目标／输入／操作与规则／输出／异常分支」组织。规则按原文合并去重，字段、枚举与判定公式的技术定义仍由功能分册与架构分册维护。

### 5.1 P1-FR01 本地项目与模块上下文

- **目标**：建立本地项目与模块上下文，为计划、执行与结论提供稳定身份和可复取的源码基线。
- **输入**：本地项目根目录（Git 仓库或普通目录）、模块职责与输入输出、上下游依赖、接口说明、实现状态、排除规则。
- **操作与规则**：
  - **建立与标识**：建立本地项目并生成稳定的本地项目编号；绑定本地项目根目录，**仓库绑定是可选的**——目录可以是 Git 仓库，也可以是**普通目录（无版本库）**；路径解析为规范绝对路径。
  - **上下文内容**：登记模块职责、输入输出、上下游依赖、接口说明与实现状态；汇总为项目上下文。
  - **源码快照**：Git 保存基准提交、未提交新增/修改/删除内容及排除规则；非 Git 保存文件清单内容摘要、必要内容和差异。物化内容与执行身份一致。提交号不等于永久可复取：记录仓库、LFS/子模块等复取依赖和可复取范围，缺失则明确缺口；需离线复现的选定内容按摘要去重保存，不重复整仓留存。
- **输出**：本地项目记录（项目编号、绑定目录、可选仓库标识、排除规则）、模块登记与项目上下文、源码基线（提交与差异，或文件清单摘要与差异）、复取依赖与缺口清单。
- **异常分支**：
  - 目录移动或仓库变更：提示重新确认绑定，并保留原绑定记录；上下文缺失项保持可见。
  - **不得因为「不是 Git 仓库」而拒绝建立项目或降级检查范围。**
  - 工作空间若位于**同步盘／网络盘**（OneDrive、网盘映射、SMB 等）：启动时检测并**拒绝在该位置建立工作空间**并说明原因——同步器会破坏排他锁与原子替换语义，导致单写保护与崩溃一致性失效。

### 5.2 P1-FR02 标准交付说明

- **目标**：用结构化交付说明区分开发自述完成与测试验证完成，避免文字自述被当作验收结论。
- **输入**：原任务、完成与未完成项、变更模块、接口变化、运行方法、数据、依赖、Mock、已知问题和自测证据。
- **操作与规则**：按模板填写或由 AI 生成草稿，用户确认后提测；开发自述完成与测试验证完成分别展示。
- **输出**：结构化交付说明（自述栏与验证栏分列）、待补齐字段清单、可提测状态标记。
- **异常分支**：必填字段或可识别版本缺失时提示补齐；AI 文字不能作为完成率依据。

### 5.3 P1-FR03 变更影响与回归建议

- **目标**：按已登记依赖把改动映射到待回归用例，并保留旧版本结果。
- **输入**：需求、代码、接口或规则的变化；P1-FR01 登记的依赖边；P1-FR06 发布用例时登记的功能需求-模块关联。
- **操作与规则**：
  - **前提**：依赖边定义为「使用者 → 提供者」，依赖来自 P1-FR01 的登记；**用例与模块的关联**在 P1-FR06 发布用例时登记，是确定性匹配的最小依据。
  - **要求**：需求、代码、接口或规则变化时，按已登记依赖做确定性匹配，列出待回归用例及其变更依据；由用户启动测试。
  - **单模块**：保留本模块变化识别、变更映射与用例回归检查；仅跨模块（反向依赖）传播显示不适用并说明原因。首次或映射不足时使用已发布保守集合，无法确定则提示确认范围，不能解释为没有改动。
- **输出**：待回归用例清单、每条用例的变更依据、保守集合或「推导结果」标记。
- **异常分支**：映射缺失不能解释为没有影响；仅靠依赖图推导的影响须标注「推导结果，可能不完整」；跨语言静态影响分析不在一期。

### 5.4 P1-FR04 内置模板与检查内容生成

- **目标**：用版本化模板加项目理解生成检查内容草稿，使检查范围既有提醒项也贴合真实业务。
- **输入**：选定范围、项目上下文、内置模板包、业务功能目录候选、必要维度、人工编写内容。
- **操作与规则**：
  - **模板**：随插件提供版本化的通用模板包，按业务类型与技术栈组织。模板项是提醒项，不是固定必测清单；AI 结合项目理解逐项给出 `included`／`not_applicable`／`unsupported` 处置，不能静默删除；`not_applicable` 需理由与证据，`unsupported` 作为已知限制。
  - **项目理解与业务功能清单**：生成检查内容前，先对选定范围做一次项目理解，产出项目上下文与信号、业务功能目录、业务意图与目标候选，共用同一个 understanding 修订。业务功能目录按业务域→功能→流程→操作/规则组织，登记触发方式、业务对象、预期结果、必要维度、来源、置信度与 `unknown` 区域；目录是完整验证的覆盖依据，不替代 AcceptanceScope。
  - **关键链路**：模板还必须给出该业务类型与技术栈下的关键链路清单（哪些依赖必须真实、哪次核验不可省），条目标注适用条件（层级、模块类型、是否需要前端等）；应用模板时先按项目实际过滤出适用项；未覆盖的关键链路必须在报告中显示警告，并在完整报告的证据等级上体现。
  - **生成**：AI 结合项目理解、业务功能清单与模板提醒生成检查内容草稿，包含规则条目、验收项、用例与检查项；每条检查关联业务功能与必要维度；AI 新增检查按是否填补覆盖缺口判定必要/可选，必要新增进入完整验证，可选新增只进入按需自测。
  - **确认**：草稿未确认发布不生效；生成内容与人工编写内容分别标注来源；人工修订不被生成结果覆盖；确认页显示范围、已知限制与业务功能覆盖摘要。
  - **出站**：模型出站先确认项目、供应方/接收地址与材料类别（见 2.8.4），只发送显式选定的脱敏材料。
- **输出**：版本化模板应用结果与逐项处置、项目理解修订、业务功能目录（含 `unknown` 区域）、关键链路清单与适用项过滤结果、检查内容草稿及来源标记。
- **异常分支**：无匹配模板时提示自建或导入；项目上下文缺失时列出缺口并阻塞，不编造依赖与结论；业务功能清单存在 `unknown`、未支持范围或功能×必要维度缺口时阻止完整验证。

### 5.5 P1-FR05 测试规范与规则版本

- **目标**：把测试规范做成可分类、可修订、可复用的不可变规则版本。
- **输入**：面向人的步骤说明、AI 检查规则、证据要求、输出格式、待导入的 Markdown 规则文档。
- **操作与规则**：分类、修订、绑定项目；支持导入／导出 Markdown；确认后发布为不可变规则版本，新测试用新版，历史保留原版。
- **输出**：已发布规则版本及其绑定项目、导入结果与修订记录。
- **异常分支**：导入规则未确认发布不生效；文档正文不能自动触发新工具或补造上下文。

### 5.6 P1-FR06 测试计划与用例生成

- **目标**：生成可编辑的结构化用例，并在发布时固定验收范围、业务功能覆盖与断言依据。
- **输入**：业务功能清单与必要维度、关键链路清单、AI 建议的范围与用例、人工编辑结果、断言依据说明。
- **操作与规则**：
  - **用例字段**：层级、前置条件、输入、步骤、预期结果、验证方法、允许的 Mock 与重要性。
  - **生成与发布**：AI 建议范围与用例，用户编辑、删除、补充后发布；覆盖正常、边界、异常、依赖失败与会话差异等适用情况，并按业务功能清单逐项核对功能 × 必要维度。发布时必须把用例关联到适用关键链路条目、业务功能与必要维度，并登记该用例的**独立核验方式**；纯逻辑用例按其实际验证方法核验，不强行要求数据库。缺失关键链路清单会阻塞完整验证，确认无适用链路的显式空清单须附理由；缺失业务功能清单或维度映射时同样阻止完整验证。
  - **业务功能覆盖**：每个适用功能 × 必要维度至少一条用例和独立核验；功能级覆盖由维度汇总，不能用一条 L3 代替全部维度；AI 新增检查按是否填补覆盖缺口判定必要/可选，必要新增进入完整验证，可选新增只进入按需自测。
  - **断言依据**：每条用例必须登记「这条断言凭什么能证明对应验收项」（由 AI 起草、人工确认），状态区分缺失、已填写未确认、已确认。缺失时不可进入完整验证必测项；已填写未确认可执行并保留在分母，标为**断言未核实**、不得计入已验证，完整报告据此降低证据等级（非完整运行只标注「断言未核实」，不打分）；适用必测项仍有未确认依据时不能给完整通过。独立核验结果另存；确认依据不替代执行。
  - **状态独立**：发布状态与 `assertion_basis_state` 独立，已发布但依据待确认不退回草稿；依据是否确认单独记录，不与发布确认混同。
- **输出**：已发布计划与用例（含层级、步骤、预期、验证方法、允许的 Mock、重要性）、功能 × 必要维度覆盖映射、独立核验方式、断言依据状态与后续派生所用的 `effective_assertion_basis_state`。
- **异常分支**：未确认发布的用例保留草稿，不得作为已发布用例执行；没有预期结果或前置条件不得标为可直接验收的完整用例；业务功能清单缺失、存在 `unknown` 或未支持范围时阻止完整验证。

### 5.7 P1-FR07 运行档位与驱动配置

- **目标**：一次运行分别确定档位与初始驱动并冻结：**档位**决定检查范围和结论上限；**驱动**决定怎么推进。有效驱动仅可按下述规则单向切换，变化追加留痕，不覆盖初始值。
- **输入**：检查范围与已发布 AcceptanceScope、计划与用例、检查集选择、环境与隔离方式、模型与模板修订。
- **操作与规则**：
  - **快速检查**：固定执行适用 L1、改动模块关键 L2 与适用的独立核验；无需逐项勾选，不判完整通过、不派生等级。无持久化业务时按实际验证方法核验，不强行要求数据库。
  - **按需自测**：运行时由用户自选检查集，可只选某一层、某个模块或某个环节；只覆盖所选范围，**不判完整通过**，未选与未执行项逐条列出，**同样不打分**。**三档之中只有本档允许在已发布验收范围内选择本轮执行子集；计划发布前定义 AcceptanceScope 不受此限制。**
  - **完整验证**：开始前纳入当前范围全部适用业务功能×必要维度与关键链路；确认后只能整体确认，不能增删改；需要调整时新建按需自测运行。冻结档位与适用下限；跳过、失败、取消、阻塞不会把档位改成按需，仍保留完整验证意图并如实报告未通过或未完成；禁止获得完整通过。
  - **结论上限只由档位决定，不由覆盖多少或执行方式决定**：快速检查与按需自测即使把冻结范围全部勾满并跑完，也不能判完整通过；需要完整通过结论时必须新建一次完整验证运行。未选与未执行项一律记为未执行并说明原因，不能当作不适用。
  - **驱动**：计划驱动（默认，确认一次计划后连续执行，内容来源标记为计划生成）与逐步驱动（每步确认后执行，可查看中间结果、随时补证或退回）；两种驱动使用同一套三层判定标准、模板版本与问题清单。逐步驱动的确认只表示允许进入下一步，**不重新判定断言、不改变结论上限**；有副作用的步骤必须单独确认。
  - **驱动单向切换**：运行中允许从计划驱动切到逐步驱动（收窄授权）；不允许反向切换，需要放宽授权时新建运行。
  - **运行中修订只适用于按需自测**：按需自测只修改未执行步骤，生成运行修订并保留原因，已执行事实不回改；影响已完成依据时暂停、标记过期，当前结论不得使用失效依据。**完整验证运行中拒绝修改计划**；任何范围、用例、预期或依据变化都必须新建按需自测运行，原完整验证运行保留为历史，不改写、不删除。快速检查无计划可改。重跑需新运行或新的实际尝试，不伪装继承为本轮执行。
  - **需求或验收项变更**：一律生成新修订，不改写冻结中的计划与已完成记录；受影响的当前运行暂停并提示，报告中标注受影响步骤的依据已过期并列出需重跑的用例。
  - **约束**：任一驱动下遇到扩大范围、新凭据、明显副作用等情形都必须暂停等待用户确认；每次运行固定展示档位、驱动与覆盖范围及跳过项。
  - **同意图去重与明确重跑**：准备运行生成持久 `intent_id`，绑定项目、源码、环境、计划、规则、模板和动作。跨入口提交同 `intent_id` 返回同一运行；用户明确重跑生成新 `intent_id` 和 `run_id`。同键不同输入冲突；启动物化必须匹配准备意图冻结的源码摘要，不一致须重新准备并核对授权，不能执行新源码却沿用旧意图。导出按报告修订、复核集合、格式和脱敏策略去重。
  - **证据等级与业务结论分离**：仅完整验证派生 A 证据充分／B 局部不足／C 关键证据不足／D 无有效依据。业务结论单列通过、失败、未完成或不适用；A 可以对应有充分失败证据，不表示可放行。未知向下取最严重等级，不平均；快查和按需显示未打分。
  - **隔离与等级**：默认虚拟环境；显式选择不隔离冻结于运行，源码仍强制物化。依赖环境、业务数据隔离/复位、目标部署版本分别记录，venv 不代表外部数据隔离。依赖环境方式作为独立事实，不因未使用虚拟环境自动降级；只有具体环境问题使所需证据无效/缺失或不满足验收条件时，才按对应规则降级或阻塞。等级主要缺口可为「无」，全量缺口仍保留。
- **输出**：运行的冻结属性（档位、驱动、覆盖范围、跳过项）、`intent_id` 与 `run_id`、按档位得出的证据等级或「未打分」标记、运行中修订序列与原因、依赖环境与数据隔离记录。
- **异常分支**：扩大范围、新凭据、明显副作用 → 暂停等待用户确认；完整验证运行中修改计划 → 拒绝并提示新建按需自测运行；准备意图冻结的源码摘要与启动物化不一致 → 拒绝执行、重新准备并核对授权；同 `intent_id` 不同输入 → 冲突，不返回旧运行；依据失效 → 暂停并标记过期，当前结论不得使用失效依据。

### 5.8 P1-FR08 源码可运行性检查（L1）

- **目标**：确认被测源码在当前环境能真正加载或启动，并把失败按原因分类。
- **输入**：所选范围源码、构建与加载配置、实际入口与解释器、依赖环境。
- **操作与规则**：
  - **检查项**：语法检查、适用构建／编译、模块加载、最小启动；纯库或命令工具检查可调用入口。
  - **支持范围**：一期自动适配 Python；其他技术栈按标准格式导入，标明外部来源与未核实范围。
  - **判定**：L1 与业务结果分开判定；不适用子项给出原因；无成功证据不能声称可运行。
- **输出**：各子项的检查结果与判定、不适用子项及原因、失败分类（源码错误／依赖缺失／环境不可达／工具失败）。
- **异常分支**：区分源码错误、依赖缺失、环境不可达、工具失败与通过，不得把工具失败记为源码失败或通过。

### 5.9 P1-FR09 引导式测试工作台

- **目标**：让用户逐步执行并控制检查过程，任一时刻都能停下来看现场。
- **输入**：当前计划与步骤、环境与凭据、人工操作、工具结果、AI 分析。
- **操作与规则**：
  - **执行**：逐步查看与执行，记录人工操作、工具结果与 AI 分析。
  - **控制**：暂停、取消、重试、补证、退回阶段；暂停在步骤边界生效；取消需确认执行停止后才置为已取消。
  - **历史**：新尝试保留旧尝试并立即成为当前尝试；旧通过结果不因新尝试失败而回退显示。
- **输出**：逐步执行记录、每次尝试的历史、暂停/取消/退回操作记录、AI 分析及其待验证标记。
- **异常分支**：缺少环境、凭据、依赖或数据时显示阻塞及原因，不能跳过后汇总为通过。

### 5.10 P1-FR10 函数与模块测试（L2）

- **目标**：判定模块或函数功能是否正确，并把 Mock 覆盖限制在声明范围内。
- **输入**：项目既有测试命令／入口、输入、断言、上下游与允许的 Mock。
- **操作与规则**：
  - 运行函数／模块测试；AI 检查测试逻辑、建议补充用例并解释失败。
  - **判定**：Mock 结果只覆盖声明的局部范围，具体业务效果必须独立核验。
- **输出**：测试执行结果与断言判定、Mock 覆盖范围、未验证范围、独立核验记录。
- **异常分支**：成功提示或非空返回不能替代内容检查；真实依赖未接通时保留未验证范围。
- **大项目适配**：可按 pytest 文件/目录/marker 组织既有测试范围；范围由 AI 起草、用户确认；单个 node ID 只作阶段 C 的定向补充。该适配不新增 FR/AC，具体执行、证据与失败定位见功能与架构分册。

### 5.11 P1-FR11 接口与集成测试（L2）

- **目标**：按业务顺序串联接口请求，并核对业务结果而不仅是 HTTP 成功。
- **输入**：接口、环境参数、凭据引用、请求数据、响应断言与核验方式。
- **操作与规则**：
  - **串联与核对**：按业务顺序串联请求，提取上一步输出作为下步输入；核对响应、字段、业务规则与适用的数据结果。
  - **判定**：响应成功但字段错误或数据未写入时判为业务断言失败；缺独立核验能力时显示未完成。
  - **证据与数据**：执行前必须明确并记录**测试数据的来源、隔离与复位方式**；数据被上一轮污染时不得作为本轮结论的依据。
  - **证据链前置条件**：完整证据链要求被测应用提供请求标识与关键节点结构化日志；缺失时降级为人工关联证据并**显式标注证据级别与缺口**，不视为产品缺陷，也不因此判为通过。
- **输出**：请求串联记录、响应与业务断言结果、独立数据核验结果、证据级别与缺口、数据来源与复位方式。
- **异常分支**：不将接口状态等同于业务正确。

### 5.12 P1-FR12 Mock 声明与真实性核验

- **目标**：判定本次运行中链路是真实、Mock、混合还是未知，让缺口可见。
- **输入**：开发声明、运行配置、静态候选、依赖清单与实际运行证据。
- **操作与规则**：登记允许的 Mock；核对固定返回、内存替代持久化、测试替身、模拟接口与未接通依赖。
- **判定**：静态检查只给出候选；不能因出现 mock 字样判假，也不能因没有该字样判真。真实、Mock、混合与未知由本次环境与证据决定。
- **输出**：各关键节点的真实性判定（真实／Mock／混合／未知）、未声明 Mock 清单、缺口说明。
- **异常分支**：未声明 Mock、关键节点真实性未知或缺真实证据时，不给该范围真实链路通过。

### 5.13 P1-FR13 用户操作与业务场景测试（L3）

- **目标**：验证用户按真实操作路径能完成业务目标，并在最终持久化上核对结果。
- **输入**：用户业务目标、操作清单、测试数据、预期结果与证据要求。
- **操作与规则**：人工按步骤操作并关联证据；覆盖按钮、分页、跳转、表单、滚动、适用鼠标操作、异常提示与展示数据。
- **判定**：必需步骤失败、跳过或关键依赖未知时不能全流程通过；每个业务目标至少一条完整 L3；工单固定流程见功能分册。
- **输出**：逐步操作记录与证据关联、每类操作的覆盖记录、业务目标级判定。
- **异常分支**：操作正常但展示错误仍可建立缺陷；异常路径另按验收项验证。

### 5.14 P1-FR14 测试报告与本地导出

- **目标**：把一次检查的事实冻结为可追溯的报告修订，并以脱敏形式带出本机。
- **输入**：冻结计划与运行、源码与环境身份、规则/验收/模板修订、各层当前尝试、证据索引、问题修订、计算策略、导出选项与脱敏策略。
- **操作与规则**：
  - **报告**：固定范围、源码与环境、规则版本、各层当前尝试、证据索引、问题修订与计算策略；报告正文不可变，变化生成新内容修订。
  - **定位**：本地报告是过程记录与自检依据，不构成防篡改的组织结论；平台如何审核不属于插件交付承诺。
  - **结论取用**：以项目、源码身份（含未提交差异）、适用范围、环境、规则/验收、模板及判定策略修订为结论键。最新完整验证开始即显示重新验证；取消、未知不回退旧绿灯。旧报告仍可查但标为历史；快查和按需为补充，不覆盖完整验证。
  - **报告字段**：完整验证包含证据等级、主要/全部缺口、断言依据确认数；快查和按需标未打分并列覆盖摘要。保留本机采集、事件和复核时间用于追溯。
  - **导出**：支持 Markdown 摘要与可携带证据包（ZIP 内含 report.md、manifest.json 和脱敏附件）；摘要明确附件不随文件交付，证据包使用相对路径、摘要与缺口清单，在新目录解压可用；两者均不含密钥。
  - **复核**：本地复核是**独立记录**（复核人、结论、说明、所依据的报告内容修订、时间），不写入报告正文、不改变正文内容修订；复核不改变测试事实。
- **输出**：报告内容修订快照、判定与缺口摘要、Markdown 摘要、证据包（report.md、manifest.json、脱敏附件）、独立复核记录、报告列表查询结果。
- **异常分支**：源码、证据、当前尝试或问题影响结论时产生新报告修订，旧结论留在旧版；材料缺失时如实显示证据缺口、不宣称完整。

### 5.15 P1-FR15 缺陷管理与修复回归

- **目标**：用同一编号与字段管理人和 AI 发现的问题，并用新执行证据关闭。
- **输入**：失败尝试与证据、层级与模块、问题描述、预期与实际、已知位置或未知原因、AI 待验证假设。
- **操作与规则**：
  - **问题清单**：人和 AI 使用同一编号与字段；缺失信息标为未知。
  - **流程**：草稿 → 待确认 → 已确认 → 处理中 → 待复测 → 已关闭；不属于缺陷、重复、暂缓保留原因，不直接删除。
  - **关闭依据**：修复关闭必须有新的实际执行证据；修复说明或 AI 判断不能替代。核实非缺陷、重复归并是独立处置，按一期功能文档第 12.2 节处理，不把原失败断言改为通过；暂缓仍保留有效阻塞。
  - **修复交接**：问题详情提供「复制修复说明」，包含精确问题/尝试修订、预期/实际、脱敏证据、已知位置或未知原因、AI 待验证假设与复测入口；不自动调用编辑器聊天、不修改被测代码。
  - **筛选**：提供模块、层级、级别、人工复核及处理/处置/阻塞筛选；未知字段不得被隐藏或误作全部（见 2.8.10）。
- **输出**：统一编号的问题记录与状态流转、修复说明、回归与关闭依据、有效阻塞清单。
- **异常分支**：先区分产品、环境、数据与脚本原因；复测失败重新进入处理流程并保留原失败记录。

### 5.16 P1-FR16 永久保留与临时材料回收

- **目标**：业务记录与证据只增不减，同时把运行期临时产物与业务记录严格分开。
- **输入**：运行证据、报告修订、导出文件、诊断日志、业务元数据与复核记录；隔离物化副本、运行中的临时文件、上传完成后的临时冗余副本。
- **操作与规则**：
  - **永久保留**：**业务记录与证据**——运行证据、报告修订、导出文件、诊断日志，以及业务元数据与复核记录——**一律永久保存**；插件**不设保留期、不做自动清理、不提供删除入口**。运行期临时产物不属于本清单。
  - **不做清理**：插件不计算「可删除集合」、不因时间到期删除任何业务记录或证据、也不提供一键清理入口。**唯一的例外是运行期临时产物**：隔离物化副本、运行中的临时文件、上传完成后的临时冗余副本，在运行结束或终止且证据已落盘后回收（它们不是业务记录，不需要用户处理）；崩溃恢复先核实执行器与引用，区分事务目录、执行器 `spool` 与物化 `workdir`；抢救可验证输出并发布恢复记录后，才回收无活动引用的空对象及临时目录。非完整输出标为部分证据；存活执行器的目录与归属不明材料不得抢先清理。
  - **一致性**：材料缺失只可能来自外部破坏（用户手动删除、磁盘故障、迁移失败）或未完成提交；此时报告如实显示证据缺口、不宣称完整，**插件不得以「腾空间」为由改写结论**。
  - **时间来源**：记录时间取本机时间（经 `Clock` 端口）；因为不涉及到期判定，修改系统时间不触发到期删除；事件先后依单调提交序号，显示时间只用于本机溯源，不作为可信外部时间证明。
  - **空间与体积**：**记录与证据**只增不减，占用以证据为主（日志、截图、附件、原始输出，随运行轮次增长）；**源码不整仓复制**——Git 目录保存提交标识、未提交差异与复取依赖；离线复现所需的选定内容按摘要去重保存，外部仓库不可用且无保存对象时明确不可复取；非 Git 目录没有版本库可回取，需保留差异内容与必要文件内容（这是主要体积来源，报告会标注不可复取范围）。运行期物化副本用完即回收，不累积。插件只如实报告占用与缺口，业务记录与证据的清理由用户在插件之外自行处理。
- **输出**：永久保留清单与占用/缺口说明、崩溃恢复记录、临时产物回收记录、不可复取范围标注。
- **异常分支**：无法判断材料类别时**不删除**（本就不做自动清理）；发现材料缺失时按缺口如实呈现。

### 5.17 P1-FR17 检查信息面板

- **目标**：把一期已产生的事实按一次检查的生命周期分三段只读呈现，界面层不另算结论。
- **输入**：核心判定的结果 DTO、已保存的运行与证据记录、进度与缺口统计、报告快照。
- **操作与规则**：
  - **定位**：面板是插件主界面，**可操作**；其中的**信息面板**是只读信息区，把一期已经产生的事实按一次检查的生命周期分三段呈现（运行前／运行时／运行后）。**信息面板不新增判定、不写任何记录、不在信息区内放动作**；面板的动作限于发起与控制检查（开始检查／快速检查／暂停／取消／重跑／导出）与跳转，逐步执行仍在测试工作台，配置修改仍在配置页。
  - **运行前**：展示本次要检查什么（代码版本、隔离环境、计划与必测项、跳过项），**信息区只呈现，不放操作入口**；计划发布、范围选择与发起运行由独立操作区或工作台承载。
  - **运行时**：展示进度与发现的缺漏统计，可进入详情查看逐步状态与原始输出。
  - **运行后**：单独展示业务结论、证据等级（非完整运行未打分）、断言依据确认数及真实覆盖/缺口；一期跳转已保存的证据或链路详情，二期再增加图节点跳转。
  - **约束**：信息面板只读；展示的等级与统计必须与领域判定器的结果一致，不得在界面层另算；面板为实时值、报告为快照值，两处分别标明且口径一致。界面结构、每段显示内容、动作位置与空态由[检查面板设计](../03-设计/01-产品方案与界面设计.md)维护。
  - **目录形态**：目录不是 Git 仓库时，面板与配置页不出现仓库、分支、提交、远端相关内容，改为「本地目录模式」与文件清单摘要。
- **输出**：三段的只读展示（运行前清单、运行时进度与缺漏、运行后结论与等级）、跳转入口、空态与不可用提示。
- **异常分支**：记录缺失时三段各自显示空态与原因，不显示推测值；模型不可用时 AI 辅助显示为不可用，不影响本地信息与导出。
