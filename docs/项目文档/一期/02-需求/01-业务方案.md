# 业务方案（一期）

> 状态：2026-11-16 轻量插件重构基线。与[需求规格](02-需求规格.md)、[功能清单](03-功能清单.md)同源；出现分歧以需求规格与功能清单为准。

一期是 Windows 11 上的 Trae 插件：扩展调用本地 Python CLI，数据保存在用户级文件工作空间。正常路径上人的核心动作只有三项：确认目标（或选 AI 候选）、选范围、执行前确认；首次使用另需选目录与配置密钥。

## 1 角色与分工

| 角色 | 能做 | 不能做 |
| --- | --- | --- |
| 人 | 选项目目录；选/改/自定义目标；执行前确认；处理无法自动化的 L3；处理坏环境；发现明显错误时改范围或重跑 | 不直接修改运行结果、Mock 真实性、AI 分析内容 |
| AI | 生成目标候选、提取验收项、起草交付说明、生成并发布计划、生成测试脚本、判定 Mock、分析失败、生成问题与摘要、诊断环境 | 不判定 `passed/failed`；不改被测代码；不代替执行确认；不关闭问题；不写验收意见 |
| 模型 API | 提供上述 AI 能力 | 不可用时对应步骤标未生成，不阻塞本地流程 |
| GitHub（只读） | 提供提交、PR、检查、部署版本 | 不写、不接 Webhook；检查通过不改变业务结论 |
| 被测服务 / 数据库 | 提供接口、日志、查询结果 | 缺采集时标缺口，不补造 |

人工动作共八项：选目录、首次配置密钥、确认验证目标、选范围、执行前确认、处理不可自动化 L3、处理坏环境、纠正明显错误。正常主路径的核心是确认验证目标 → 选范围 → 执行前确认这三项；看报告与填写验收意见是可选项。

## 2 业务对象

| 对象 | 身份 | 生命周期 | 关系 |
| --- | --- | --- | --- |
| 项目 | 稳定项目编号 | 长期 | 挂模块、任务、运行、问题 |
| 模块 | 模块编号 | 研发登记，AI 可起草 | 依赖、接口、负责人、实现状态 |
| 任务 | 任务编号 + 修订 | 目标变化形成新修订 | 验收项、交付说明、计划 |
| 验收项 | 独立编号 | 需求变化保留历史 | 用例、执行、证据、问题 |
| 交付说明 | 与任务、提交关联 | 变化新建修订 | 运行输入 |
| 规则版本 | 规则编号 + 版本 | 新测试用新版本 | 计划、运行 |
| 计划 | 计划编号 + 修订 | 发布后冻结；改动新修订 | 运行引用 |
| 用例 | 用例编号 | 随计划修订 | 验收项、层级、预期、`depends_on` |
| 运行 | 运行编号 | 创建 → 执行 → 结束/中断/取消 | 冻结范围、环境、规则、提交 |
| 尝试 | 属于用例，从 1 起 | 重跑新建运行 | 输出、证据 |
| 证据 | 路径 + 摘要 | 永久保留 | 运行、用例、问题、报告 |
| 问题 | 问题编号 + 修订 | 四态流转 | 失败用例、证据、修复版本 |
| 报告 | 报告编号 + 修订 | 每次运行生成 | 结论、覆盖、问题、分析、验收意见 |

共同约定：

- 记录带项目编号、修订号、来源与时间；
- 路径与仓库是绑定属性，不是主键；
- 业务记录、证据、报告、问题永久保留；不做自动清理。

## 3 主流程

1. **选目录与建项目**：一个目录一个项目；monorepo 可登记多个子项目；根目录重叠需明确选择。
2. **选目标**：AI 给 3—5 条候选并附依据；无信号给通用目标；也可自定义。
3. **任务与验收项**：验收项必须可观察、有编号；写不出的标“待补充”并排除。
4. **交付说明**：AI 从提交与脚本起草；缺运行方式或版本标“不完整”。
5. **关联 GitHub**：只读提交、PR、检查、部署版本；固定被测提交。
6. **规则与模板**：绑定规则版本；模板作为预设检查清单。
7. **选范围**：按验收项勾选；全部适用或自选；显示 `S/M` 与未覆盖。模块筛选只作为 CLI/API 参数 `module_ids` 预留，面板固定传空数组；层级筛选未实现。
8. **生成计划**：AI 按验收项生成用例并发布初版；预期必须引用验收项原文。
9. **执行前确认**：展示范围、用例数、环境、凭据边界、副作用、将安装依赖、预计耗时；确认后启动。
10. **执行**：worker 顺序执行；按需启动服务；AI 生成测试脚本；L3 可自动化则跑，否则 `manual_pending`。
11. **失败分析与问题**：运行结束后自动生成四段分析（worker 退出前同步完成后处理）；按失败签名去重生成问题。
12. **重跑与回归**：按验收项新建运行；关闭问题必须有新证据。
13. **报告与备份**：core 生成结论与计数；AI 摘要只写事实；zip 备份默认不含证据。

## 4 业务规则

- **结论**：只有 `passed / failed / incomplete / not_applicable`，只对本次所选范围 `S` 成立；未选验收项不属于本次范围，不计未执行；报告必须同时显示 `S/M` 与未覆盖清单。
- **覆盖**：`S⊆M`；空 `S` 不发布、不运行，唯一例外是 `smoke` 目标且任务无适用验收项（只做项目级 L1，报告显示 `0/0`，不算验收项通过）；`S<M` 时不说“全部通过/完整通过”。
- **计数**：主表按验收项取所有用例最差结果（失败 > 阻塞/未知/未执行 > 通过）；用例明细附表；L1/L2/L3 按用例单独统计；各层不互相替代。
- **L1**：项目级检查，不计验收项覆盖；失败只阻塞 `depends_on=build` 的用例；服务启动失败只阻塞依赖 `service` 的用例。
- **Mock**：AI 判定真实/Mock/混合/未知并附依据；未声明或判不出即未知；未知不能获得“真实链路通过”。
- **问题**：失败签名去重；同一签名追加发生记录；不自动重试；结果不一致标疑似不稳定。
- **证据**：永久保留；单文件 20MB 截断；单次运行媒体软上限 500MB；失败证据不降级。
- **AI 边界**：分析、摘要、判定都带依据；AI 不改变业务结论、不改代码、不代确认。
- **服务与数据**：只接管自己启动的服务；默认运行后停止；测试数据带运行标记，默认不清理，`data.cleanup` 默认 dry-run。
- **并发**：同一项目同时只允许一个运行；不同项目可并行；运行内跨用例串行，runner 内部并行可选且需结构化输出。

## 5 异常处理

| 异常 | 行为 | 禁止 |
| --- | --- | --- |
| 模型不可用 | AI 步骤标未生成；本地测试、证据、导出继续 | 暗换供应方、把 AI 文字当执行结果 |
| GitHub 不可用 | 版本关联标缺口或未确认 | 用缓存冒充最新 |
| 链路缺口 | 明确标出未采集/无法关联 | 拼接为同一次调用 |
| 服务启动失败 | 标 `blocked` 并保留日志 | 强行杀进程、跳过阻塞后汇总通过 |
| 脚本自身错误 | 标 `blocked`/`error`，不算产品失败 | 判为产品缺陷 |
| worker 被杀 | 心跳超时且 PID 不在 → `interrupted`，保留已完成部分 | 自动重跑、补造结果 |
| 取消未确认停止 | 记 `execution_error` 并说明 | 伪造已取消 |
| 磁盘不足 | 停止写入并报错 | 驱逐已有证据 |
| 旧格式 | 拒绝并提示转换或重建 | 静默迁移、覆盖记录 |
