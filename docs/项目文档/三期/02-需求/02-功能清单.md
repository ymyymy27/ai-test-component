# 功能清单（三期）

> 适用期次：三期；主责：功能行为、展示状态唯一口径、发送策略与停止规则；状态：规划稿，验收未开始
> 三期共 **2 项功能（P3-FR01—P3-FR02）**，对应 **8 项验收（P3-AC01—P3-AC08）**。场景与预期只在[需求规格](01-需求规格.md) 第 6 节维护，本册不复制场景正文。
> **状态名只在本册第 2 节定义一次。** 架构分册只定义字段与取值，界面分册只引用展示态与文案，不得各自另立第三套。

三期只做上传：不接收别人的运行、不保存共享视图、不展示跨账号审核、不提供宿主子应用。一期与二期的判定口径、问题状态与导出字段继续有效，本册只增加协作相关的记录与规则。

## 2 展示状态：唯一口径

### 2.1 七个展示态

界面上关于"这份提交送到哪一步"只有以下 7 个展示态，均由核心派生的四组字段组合得到，不由界面自行推断：

| 展示态 | 含义 | 进入条件 | 允许的下一步 |
| --- | --- | --- | --- |
| 待发送 | 冻结已保存，尚未发送 | 提交已冻结，无在途请求，未暂停未放弃 | 有效许可与门禁满足后发送 |
| 发送中 | 请求已发出，等待受控截止 | 存在在途请求，尚未得到终态 | 等待截止，或按原号查询 |
| 结果未知 | 无法确定平台是否接收 | 请求超时、失联或结果无法确认 | 先查询原号，不直接重发 |
| 部分接收 | 已接收部分对象，仍有缺口 | 回执声明部分接收或缺对象 | 按缺失清单补交，不重新执行 |
| 已送达 | 完整回执与冻结清单一致 | 回执的账号/目标/修订/清单与每个对象摘要全部匹配 | 查看回执与覆盖缺口，不无限轮询 |
| 已暂停 | 当前失败周期耗尽或遇到需要人决定的问题 | 认证、参与、摘要冲突、投影复核或重试耗尽 | 按原因处理后明确恢复或重授许可 |
| 已放弃 | 用户明确放弃这份提交 | 存在放弃决定 | 查看接收情况；再次发送须新建关联提交并先查原号 |

派生优先级固定为：**控制决定优先于传输在途，传输在途优先于接收事实**。因此"已暂停"且此前已收到部分对象时，展示"已暂停"并同时列出已接收对象；不把接收事实重置为待发送。

### 2.2 三向映射表

本表是展示态与架构字段之间的**唯一定义处**。架构分册的字段取值以[结果上传](../04-架构/03-结果上传.md) 第 4 节为准；界面文案以本表与[产品方案与界面设计](../03-设计/01-产品方案与界面设计.md) 为准。

| 展示态 | receipt_state | transport_state | control_state | grant_state | 界面文案与允许动作 |
| --- | --- | --- | --- | --- | --- |
| 待发送 | PENDING | IDLE | ACTIVE | 无，或 active | "待发送"：有效许可与门禁满足后可发送 |
| 发送中 | PENDING 或 UNKNOWN | IN_FLIGHT | ACTIVE | active | "发送中"：只等待受控截止或查询，不重发 |
| 结果未知 | UNKNOWN | IDLE | ACTIVE | active | "接收结果尚未确定"：先查询原号 |
| 部分接收 | INCOMPLETE | IDLE | ACTIVE | active | "部分接收"：列出缺失对象，按清单补交 |
| 已送达 | ACKNOWLEDGED | IDLE | ACTIVE | completed | "已送达"：可看回执；业务证据缺口另行显示 |
| 已暂停 | PENDING/UNKNOWN/INCOMPLETE | IDLE | PAUSED | revoked | "已暂停：<原因>"：按原因处理，明确恢复原提交 |
| 已放弃 | 任意已记录值（含 ACKNOWLEDGED） | IDLE | ABANDONED | revoked | "已放弃"；若已收到完整回执则显示"已送达；此前已放弃" |

映射表使用规则：

1. **只有 7 个展示态。** 原设计稿里的"待关联""待确认/投影缺口""已送达但曾放弃"不是第 8、9 个状态："待关联"是候选尚未形成提交时的列表空态（没有 `receipt_state` 可言，文案为"需要确认账号和目标"）；"投影缺口"是"已暂停"且原因为 `projection_review_required`；"已送达但曾放弃"是"已放弃"行的文案变体。
2. 字段组合由核心派生并随 DTO 下发；面板、CLI、MCP 与报告只读，不重算、不把展示态回写到 `receipt_state`。
3. 新增展示态须同时给出四字段映射与文案，并在[需求规格](01-需求规格.md) 留下变更依据；不允许只加一个界面标签。
4. 架构分册不得出现展示态名称作为字段取值；界面分册不得出现四字段取值组合成的新状态名。

## 3 发送策略 SendPolicy

SendPolicy 按账号、平台项目、接收目标与材料类别保存发送修订；材料白名单与投影策略修订单独引用，二者不混用。

| 模式 | 行为 | 首次发送 | 边界 |
| --- | --- | --- | --- |
| manual（默认） | 不自动启动任何候选；用户逐份确认 | 须预览确认 | 手动确认仍可建立单份许可，不等于撤销过某次明确许可 |
| on_run_end | 运行终止修订形成最终候选后自动启动匹配提交 | 仍须首次预览确认 | 只在已批准范围内；新目标、新类别或关键缺口转待确认 |
| per_step | 按步骤提交结果自动启动匹配提交 | 仍须首次预览确认 | 状态写入不自我触发，不产生上传自身候选 |

- 仅切换模式或暂停/恢复不改变冻结投影，不强制新提交号；原提交保留创建时的策略来源，许可引用当前获确认的发送控制修订并核对材料策略仍适用。
- 账号、目标、材料类别或投影规则变化必须重新确认策略并新建提交。
- 关闭自动同步：改回 manual，撤销当时全部未完成许可，停止后续自动发送、补交与查询；候选、在途请求与接收事实保留，之后可再明确重授单份许可或"查询一次"。
- AI 工具调用不能自确认策略、不能自建许可；人工确认沿用一期入口权限。

### 3.1 首次预览与确认

- 首次发送、目标或材料类别变化、出现关键投影缺口时，必须预览确认；预览返回冻结投影、包含/排除清单及每项原因、接收方与材料范围，不展示原始密钥或原始敏感材料。
- 确认绑定准确的提交号与清单摘要；确认之后发送的字节必须与预览一致，发送阶段不重新读取最新原文。
- 关键材料无法安全投影时停在"已暂停"（原因 `projection_review_required`）；用户知情后可按合同发送部分材料，但界面同时显示业务证据缺口，不宣称齐全。
- 预览不等于送达许可：打开预览、查看安全正文都不产生许可，只有明确确认或已批准策略才建立许可。

## 4 单份送达许可与恢复

许可（`SubmissionDeliveryGrant`）是一份既有提交的确认元数据，不是新服务，也不另建调度器。它绑定提交号、清单摘要、账号与目标、投影与材料策略修订、当前发送控制修订与确认来源。

| 事件 | 许可与行为 |
| --- | --- |
| manual 下手动确认一份提交 | 可在有界失败周期内完成该份的首次发送、查询与补交，不发送其他候选 |
| 网络断开或核心重启 | 持久许可不扩大、不重置失败次数；会话/参与/目标/策略仍有效才续行 |
| 关闭自动同步 | 撤销当时未完成许可，停止后续自动网络动作；在途回执继续登记 |
| 暂停本份 / 退出 / 切账号 | 撤销对应许可；材料保留，重登只恢复会话，不复活许可 |
| 失败周期耗尽 | 转"已暂停"；显式恢复并确认原提交才开新周期，重启或重登不算 |
| 内容/目标/账号/投影策略变化 | 新建提交与新许可，不扩大也不覆盖原许可 |
| 明确放弃 | 撤销许可并进入"已放弃"；再次发送先查原号并新建关联提交 |
| 已完整送达 | 许可结束，保留回执；后续对账是单独允许的查询 |
| 仅查询一次 | 只读查询许可，不授权补交；也消耗其许可内的一次请求 |

撤销与发请求在核心内按提交串行裁决：撤销后不得再登记新发送意图，已登记的在途请求尽量停止但不承诺撤回；迟到结果一律按原归属核对。

## 5 暂停、关闭同步与明确放弃

| 用户动作 | 控制决定 | 接收事实 | 恢复方式 |
| --- | --- | --- | --- |
| 暂停本份 | 记暂停原因并撤销未完成许可 | 保留已收对象与"结果未知"/"部分接收" | 明确重授后先查原号，再只补缺 |
| 关闭自动同步 | 改回 manual 并撤销当时未完成许可 | 不重置、不删除 | 之后可重授单份许可或查询一次 |
| 退出或切换账号 | 撤销原会话关联未完成许可 | 冻结账号与目标不改 | 重登只恢复会话 |
| 明确放弃 | 记放弃决定，进入"已放弃" | 永久保留，迟到完整回执仍记真实送达 | 须新建关联提交并先查旧号 |
| 仅查询一次 | 只读查询许可 | 登记真实接收事实 | 发现缺项不自动补交 |

- 只有"明确放弃"产生放弃态；暂停、关闭同步、退出、切换账号都只撤销许可并保存原因，**不生成放弃决定**。
- 放弃决定与接收事实独立保存：放弃后迟到的完整有效回执仍登记为"已送达"，界面并列显示"此前已放弃"，且不恢复自动发送；迟到失败不撤销放弃决定。
- 恢复不得把"结果未知"或"部分接收"统一重置为"待发送"盲发：重授后先查原号，完整匹配则结束许可、部分则补缺；只有平台明确不存在原提交且当前许可有效时才允许同号同字节发送。
- 认证恢复不解除摘要冲突与关键投影复核要求；恢复按钮须按原因分别导航。

## 6 候选、游标与失联后先查

- 每步结束与运行终止后**先本地保存，再生成候选**；登记候选失败不回滚本地事实，可由持久游标补建。失败、阻塞、取消的运行同样保存并进入候选。
- 候选只订阅允许的业务记录修订（运行/步骤/证据/问题/报告），**不订阅候选、提交、回执与游标自身的写入**，避免自激。
- 候选登记与游标推进在同一工作单元提交；队列满时保留候选或停在原游标，不能先推进再丢材料。
- 未登录或无会话产生的候选保持"未关联"，不自动归到下次登录的账号；用户显式确认账号与目标后才冻结提交。
- 逻辑待发送占用与永久材料物理占用分别统计；放弃只释放逻辑占用，不删除历史材料。磁盘不能接纳新增字节时明确提示，不静默丢弃。

### 6.1 失联与重复投递的判定顺序

| 情形 | 处理 |
| --- | --- |
| 请求超时或断连 | 转"结果未知"，先按原编号查询，不直接重发 |
| 查询到缺口 | 转"部分接收"，按缺失清单补交；不重新执行被测业务 |
| 平台明确无原提交 | 原提交仍允许发送时才同号同字节重发 |
| 同号不同内容或不同目标 | 记为冲突并转"已暂停"，新提交关联旧记录 |
| 同运行产生新报告修订 | 新建提交，不误判为同号冲突，不覆盖旧回执 |
| 退出或换账号后回执迟到 | 核对原账号、绑定与请求，只更新原提交 |
| 预览后源记录变化 | 旧预览与旧提交字节不变，新修订另建候选与提交 |

### 6.2 接收进展与失败周期

- HTTP 成功不等于接收有进展。只有三类事实算真实进展：已完整接收对象集合严格增加、某个对象的可信连续偏移严格增加、完整匹配的回执到达"已送达"。
- 相同"结果未知"或相同缺失集合且无可信偏移增长的重复请求，计入**无进展周期**；正常分块偏移增长算进展，但真实进展也不重置周期的**总轮次**。
- 同一份提交的发送、查询、补交与完成确认共用一个周期；每个出站请求消耗一轮，重启与重登保留两类计数，不免费重试。
- 周期耗尽转"已暂停"（原因为重试耗尽或无进展）；只有用户明确恢复、原因可处理且许可有效才开新周期。平台无法确认可信块偏移时，不得宣称支持自动分块续传，只能使用已对拍的原子对象上传方式。

本节只给行为结论；周期字段、上限计算、偏移归一化与请求计划的唯一定义在[结果上传](../04-架构/03-结果上传.md) 第 7.2 节。

## 7 业务证据覆盖与不改变的本地结论

- 业务证据覆盖（`EvidenceDeliveryCoverage`）与清单一起冻结，记录预期证据、已投影、被排除、缺失及原因；它与接收状态分开保存、并列展示。
- 清单全部接收只驱动"已送达"，**不能抹掉覆盖缺口**：被脱敏排除的截图、未采集或损坏的材料仍是业务缺口。
- 上传成功、失败、被拒与回执不完整都不改变执行状态、断言结果、验收结论与问题状态；不自动确认缺陷、不关闭问题、不发布规则。
- 回执不完整或无法核对时显示"未送达"，不显示"已送达"；平台未支持完整业务完成标记时不自行制造。

## 9 可观察的成功条件

## 10 不做的事

- 不实现接收端、共享查询、跨账号审核、审核投影、宿主接收模块与远程 MCP，也不监听端口。
- 不新增数据库、消息队列、独立发送 Worker、调度器或本地 HTTP 服务；发送沿用一期有界恢复策略。
- 不上传代码正文、GitHub Issue、PR；GitHub 保持只读。
- 不把上传结果当作业务通过或"业务证据齐全"的依据。
