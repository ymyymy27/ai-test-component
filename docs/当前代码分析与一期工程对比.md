# 当前代码分析与一期工程对比

分析日期：2026年9月23日  
分析基线：`devlop`（仓库拼写为 `devlop`）与 `main` 的代码基线相同，均基于 `0120887`；当前工作分支包含仅更新文档的提交 `59b1b1f`。  
对照范围：[一期需求](项目文档/一期/需求文档/01-需求文档.md)、[一期功能](项目文档/一期/功能文档/01-功能文档.md)、[一期架构总览](项目文档/一期/架构文档/00-架构总览.md)及仓库当前实现。

## 1. 结论摘要

当前代码是一个边界清晰、以安全约束为先的一期工程骨架，尚未形成可供用户完成测试工作的产品闭环。核心 API 仅实现离线诊断和请求去重；项目、计划、执行、证据、报告等能力大多停留在领域模型、合同、接口占位或设计文档。CLI 的 `doctor` 明确返回 `NOT_READY`，其它未实现动作返回 `CAPABILITY_UNAVAILABLE`；MCP relay 明确不可用；Trae 面板只展示导航和未连接状态。README 也明确说明这次是骨架重建，不代表一期 35 项验收完成。

因此，当前适合用于继续开发、审查模块边界和验证基础工程约束，不适合宣称已具备一期测试执行、留证、判定、报告或缺陷管理能力。`tests/acceptance/p1/status.json` 中 P1-AC01—P1-AC35 全部为 `untested`，没有验收证据路径。

## 2. 当前代码结构与实际能力

仓库采用 `src/aitest` Python 包，分为 `domain`、`application`、`infrastructure`、`contracts`、`interfaces` 与打包资源；另有 TypeScript 面板和 Trae 扩展。`tests` 按 unit、contracts、architecture、recovery、acceptance 分类。结构与一期架构提出的依赖方向基本一致，但大部分业务模块还未连成可调用用例。

| 层/区域 | 当前实现 | 状态与边界 |
| --- | --- | --- |
| Domain | 项目/模块、任务/验收项、交付说明、计划范围、运行状态、源码快照、证据引用、问题及覆盖集合等不可变模型 | 有基础校验与部分判定规则；不是持久化业务系统，也没有完整的一期决策器 |
| Application | 规划、执行、复核等包结构；连接重试策略与受影响模块计算 | 多个关键用例是模块占位。例如 `execution/runner.py`、`review/reporting.py` 的正文说明尚未实现，`ports.py` 中多项端口只有协议说明 |
| Infrastructure | 原子 JSON 写入、OS 写锁等底层原语；模型、源码、执行、存储等适配器目录 | `atomic.py` 可完成单文件原子替换和有限瞬时错误重试；`locking.py` 提供锁原语。完整工作空间事务、记录仓储、恢复/备份、证据对象存储尚未接通 |
| Contracts/API | Pydantic 命令、响应、事件及模板合同；LocalAPI 对请求做会话内幂等缓存 | API 当前只真实处理 `doctor`；不执行或保存项目业务写入。未实现命令统一返回能力不可用 |
| CLI/Agent | `templates` 可列出随包模板；`doctor` 报告未就绪；relay 明确报错并退出 | 没有可用 MCP stdio 服务，也没有工作空间绑定和业务命令入口 |
| 面板/Trae | 共享 Webview 导航骨架；扩展要求工作区受信任并设置 CSP nonce | 无本地核心连接、业务 DTO、真实项目/计划/运行状态或动作。Trae 兼容性没有真实安装验证 |
| 模板/示例 | 六个模板 JSON、合同校验、示例项目 | 模板状态为 `scaffold`，输入与断言依据仍要求用户确认；模板条目不是运行证据。示例不代表测试引擎已可执行 |

## 3. 与一期目标的对照

一期需求覆盖 P1-FR01—P1-FR17，要求从本地项目与计划，经授权执行、证据采集和独立核验，到判定、报告、问题回归及永久留存。当前代码主要建立了模型、边界和个别规则，尚无可用的端到端用户路径。

| --- | --- | --- |

| FR04 模板/检查内容 | 包含六个版本化 JSON 模板、严格合同及模板列表 CLI | 可发现模板草稿；没有应用/生成/确认/发布流程或必测覆盖报告 |

## 4. 已有工程基础与边界

- **依赖方向**：`tests/architecture/test_boundaries.py` 静态检查领域层不依赖应用/基础设施/接口层，应用层不依赖基础设施和接口层，并约束若干后续阶段模块不出现在一期包中。这是工程边界检查，不是产品功能验收。
- **API 防误报**：`LocalAPI` 不把未实现动作伪装为成功；对重复 `request_id` 做内容指纹核对和会话内去重；Agent relay 不能执行需要人工确认的动作。
- **领域纯规则**：计划选择守卫、Coverage 集合关系、依赖环遍历、重试安全条件有针对性单元测试。
- **文件写入原语**：原子写 JSON 会 fsync 临时文件后替换目标；锁函数使用非阻塞 OS 锁。当前没有证明多对象事务、崩溃恢复及所有存储路径都已实现。
- **构建与质量门槛**：`pyproject.toml` 声明 Python 3.13、ruff、mypy、pytest；面板和扩展有 TypeScript 构建脚本。配置存在不代表本次分析已运行这些检查，也不代表真实编辑器兼容。
- **明确的产品边界**：代码和文档都说明不启动服务端、不开放业务网络入口、不伪造 MCP 消息或执行结果。这与一期本地优先设计一致。

## 5. 主要差距与交付风险

1. **没有可用业务闭环**：领域对象未通过应用用例连接到仓储和 API。用户无法通过 CLI、面板或 relay 建项目、发布计划、发起运行、留证和查看报告。
2. **执行/核验能力为空**：L1、命令、HTTP、人工操作适配器均有明确占位说明；运行器与报告流程也未实现。现有状态模型不能代替真实执行。
3. **数据可靠性能力只到原语**：需要的一致性提交、修订/事件目录、附件内容寻址、备份恢复、迁移和永久保留尚未形成整体存储实现。多进程锁和原子替换是必要组件，但不是完整事务保证。
4. **产品验收没有证据**：35 个 P1 验收用例在状态文件中全为未测试。现有 unit/contract/architecture 测试即使通过，也只能说明被覆盖的工程规则，不证明产品验收通过。
5. **宿主及运行环境未验证**：Trae 扩展使用 VS Code API 候选接口，README 明确尚未在目标 Trae 版本安装验证。Python/Node 构建可验证包，不足以验证真实 Webview、目录切换和宿主生命周期。
6. **设计规模与实现规模落差大**：一期文档已细化权限、脱敏、快照、授权、事件恢复、判定、查询和导出等约束；实现仍处骨架阶段。开发需按可验收的薄切片交付，不能从设计文档丰富程度推定对应功能已存在。

## 6. 建议的实现顺序

按一期架构中的本地闭环，先完成并验证单模块最小切片，再扩展完整验收范围：

1. **可恢复的本地工作空间**：路径/普通目录与 Git 可选绑定、单写生命周期、修订提交、事件和附件存储、重启后读取；先定义可验证的数据一致性合同。
2. **端到端项目与计划**：项目、模块、交付、规则/模板应用、验收项、计划发布及范围冻结；通过 LocalAPI 提供真实、受版本守卫的读写用例。
3. **受控执行与证据**：先实现 L1 与一种确定的执行类型，补齐逐项授权、尝试记录、超时/取消/待核实、原始输出采集和独立验证；然后扩展 HTTP、人工及业务场景。
4. **唯一判定、报告和问题回归**：把覆盖、真实性、证据缺口与结论上限放入领域判定；冻结报告修订、实现导出、问题确认/修复/回归。
5. **接入与验收**：面板/CLI/relay 作为同一用例的入口接入，补充事件续读及重启恢复，再在目标 Trae 环境验证；逐项执行 P1-AC01—35 并附真实证据。

每一步应从合同测试推进到存储/故障恢复测试和可重复的验收证据。分阶段发布时清晰标示尚未开放的动作，保持当前 API 对未实现能力的拒绝行为。
