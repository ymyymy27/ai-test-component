## 1. 产品目标与文档分工

### 1.1 产品究竟解决什么问题

开发者说“功能完成了”，接口返回“成功”，AI 说“没有问题”，都不能单独证明业务满足要求。本项目要帮助测试者把这些说法与实际执行、核验和证据分开。

主要问题包括：模块合并后不知道要检查哪些依赖；Mock 或固定返回掩盖真实结果；问题缺少版本和复现材料；AI 分析与实际事实混在一起。

因此，产品需要回答：测了什么，实际发生了什么，依据是否有效，结论覆盖多大范围，发现问题后怎样修复并复测。

以工单创建为例，先区分两个产品：

| 对象 | 职责 |
| --- | --- |
| 被测工单系统 | 接收工单数据，正确保存并提供业务操作 |
| 测试插件 | 组织已授权的测试，核验结果，保存证据并形成结论 |

测试插件的用户需求可以表述为：“测试者需要确认工单创建后确实保存且符合预期，并能识别成功响应与实际结果不一致的情况。”

### 1.2 四类文档的职责

| 文档 | 回答的问题 | 工单场景中的内容 |
| --- | --- | --- |
| 需求 | 用户需要什么，怎样验收 | 必须识别返回成功却没有保存的情况 |
| 功能 | 产品如何响应用户操作 | 创建后独立核验同一工单，分别处理失败和未知 |
| 架构 | 各部分如何配合保证行为 | 执行、核验、存储、统一判定分别承担职责 |
| 设计 | 用户如何理解和完成操作 | 显示结果、证据、缺口和下一步入口 |

FR 表示功能要求，AC 表示具体验收场景和预期。一个功能可以对应多个 AC，一个 AC 也可能同时检查多个功能。

例如 P1-FR11 是接口与集成测试要求；P1-AC07 包含“接口成功但未写入数据库”的业务子场景，同时还检查凭据过滤。讲解其中一个子场景，不等于缩减整个 AC 的范围。

### 1.3 三期边界

一期在 Windows 11 x64、Python 3.13、Trae 上完成本地测试闭环。二期扩展编辑器、操作系统、源码定位和展示。三期使用平台身份上传已经保存的结果。

一期 17 FR / 35 AC，二期 6 FR / 9 AC，三期 2 FR / 8 AC，合计 25 FR / 52 AC。讲义章节数量与功能编号无关。

本地核心和存储不依赖平台登录。调用模型、可选 GitHub 或远端被测系统时，仍需要对应网络与凭据。“本地运行”描述核心和数据归属，不能被理解为所有动作都不联网。

## 2. 整体架构、五层职责与调用流程

### 2.1 产品运行时的组成

用户通过 Trae 面板、命令行或 AI 工具入口提交操作。它们连接同一个本地核心，核心组织测试、管理状态、保存材料并生成结果。

~~~mermaid
flowchart TD
    U["用户"] --> E["Trae 面板／命令行／AI 工具入口"]
    E <--> C["同一个本地核心"]
    C <--> A["执行与核验能力"]
    A <--> T["被测项目"]
    C <--> S["本地工作空间：记录、证据、报告"]
    C <-->|可选调用| M["模型 API：草稿与辅助分析"]
~~~

图中的核心位于用户电脑。插件不部署本地 HTTP 服务、不监听 TCP 端口；本地入口通过进程间通信连接核心。外部模型或远端被测系统属于出站访问目标。

数据工作空间位于操作系统用户数据目录。被测源码目录、插件安装目录和运行数据目录各有用途，不能混为一个目录。

### 2.2 五层表示职责分工

| 层 | 主要职责 | 本项目中的边界 |
| --- | --- | --- |
| 入口层 | 接收操作、显示结果 | 面板、扩展、CLI、MCP relay 不直接写业务文件 |
| 接口层 | 检查格式、路由、版本与能力协商 | 不自行决定业务通过，也不替用户确认 |
| 应用层 | 编排准备、授权、执行、保存、恢复 | 管处理顺序、事务边界和持久业务意图 |
| 领域层 | 计算业务规则 | 统一判定、统计、复用资格和问题关闭条件，无外部 I/O |
| 基础设施层 | 执行具体外部操作 | 文件、进程、HTTP、模型、凭据及源码适配 |

五层不意味着五个独立服务。应用层回答“按什么顺序完成”，领域层回答“根据这些事实应得出什么结论”，基础设施提供实际操作能力。

### 2.3 端口、适配器与注入

端口是一份能力约定，明确输入、输出、错误和职责边界。这里的端口不是网络端口。

例如独立核验端口需要输入目标、业务对象编号和核验条件，返回观察结果、来源及证据或错误。适配器是具体工具，可以通过已配置的只读 HTTP 查询实现核验；数据库驱动只有在安装清单明确列名并实测后，才能声称可用。

注入表示系统装配时把选定工具交给应用层。应用层按能力约定工作，避免将某个供应商或文件后端的操作细节扩散到全部用例。

DTO 是按约定结构组织的数据对象，供各入口传递请求或展示结果。Schema 约束字段结构，能力协商说明当前支持哪些动作。结构正确不等于已授权或业务正确。

### 2.4 一次调用怎样经过这些部分

1. 面板提交项目、计划和动作参数。
2. 接口检查结构、会话和请求身份，交给应用用例。
3. 应用读取准确修订，使用领域规则检查运行条件，核对授权。
4. 应用经端口调用适配器，适配器执行已登记动作并返回事实。
5. 应用可靠保存材料，领域根据有效事实形成结论。
6. 接口返回 DTO，面板和报告读取同一结果。

依赖方向约束的是“谁依赖谁”，并不禁止结果返回。更换编辑器或模型时，领域判定仍复用同一规则；受影响的适配、接口和流程需要相应验证。

## 3. 数据关系、身份、修订与历史

### 3.1 主要记录及关联

| 记录 | 保存什么 | 关联意义 |
| --- | --- | --- |
| 项目及绑定 | 稳定项目身份、目录位置与环境 | 路径移动不改变历史项目归属 |
| 验收项 | 用户目标、范围和可验证条件 | 用例设计的起点 |
| 用例及计划 | 输入、步骤、预期、核验与准确修订 | 说明当时按什么要求测试 |
| Run | 一轮测试的冻结条件和运行事实 | 区分不同轮次 |
| Step | 具体动作、依赖和证据要求 | 表达顺序与进度 |
| Attempt | 某步骤一次尝试的身份、输入、执行状态与结果 | 区分首次执行和重试；Attempt 属于 Step，建立尝试不等于已经执行完成 |
| Evidence | 实际捕获材料及准确引用 | 将判定追溯到对应尝试 |
| ReportSnapshot | 基于特定事实的结论快照 | 保留当时的报告内容 |
| IssueRecord | 问题、修复与回归记录 | 跟踪处理和关闭依据 |

报告引用运行及准确证据；运行引用计划、源码和环境；证据绑定项目、运行、步骤和尝试。关联关系使人能从结论找到原始事实，不能仅靠时间相近猜测归属。

### 3.2 编号、修订和内容摘要

编号回答“它是谁”。项目改名或移动目录，稳定身份仍保留。目录位置是可修订的绑定属性。

修订回答“它当时是什么内容”。若工单状态预期由“待处理”改成“已受理”，新旧预期分别留存，原运行继续引用原修订。

摘要回答“内容是否与记录对应”。它按实际字节计算，用于校验变化、完整性和内容复用；摘要不能代替项目归属、授权或真实执行证明。

### 3.3 历史事实与当前依据

第一次成功、第二次结果未知，两次事实都保存。第二次已成为当前尝试时，不能回退第一次的成功显示当前绿灯。

后续查询若使用第一次创建返回的工单编号，必须记录其实际消费的上游尝试和输出。上游新尝试出现时，相关下游依据可能过期，但历史输出和历史断言不被篡改。

### 3.4 记录与证据内容分开

业务记录保存结构化信息和引用，日志、截图等较大内容作为对象保存。列表读取摘要，详情按引用读取附件；这样不需要每次打开运行列表就加载全部历史日志。

## 4. 测试准备：模板、规则、用例、计划和环境

### 4.1 从验收目标形成计划

| 对象 | 作用 | 例子 |
| --- | --- | --- |
| 验收项 | 说明用户要求 | 工单创建后可读到正确数据 |
| 模板 | 通用检查结构、适用条件、必测下限与关键链路 | 创建、查询、详情、状态修改和最终核验 |
| 规则 | 检查和证据要求 | 成功响应不能代替持久化核验 |
| 用例 | 一项具体检查 | 用指定数据创建，再查询相同编号 |
| 计划 | 固定范围、用例、规则和模板修订 | 对工单创建与查询范围完整验证 |

模板避免漏项，实际项目仍须提供入口、数据和明确预期。AI 或人工生成内容先是草稿，核对后发布；重生成不能覆盖人工编辑。

六类首发模板面向 Python 库、Python 服务、HTTP 流程、人工页面、智能体和工单贯通示例。模板存在不等于其适配器已支持或场景已实测。

### 4.2 适用性与范围

“不适用”表示对象没有这类要求；“尚不支持”表示要求存在但工具缺能力；“信息不足”表示无法确定。后两者不能变成不适用以降低分母。

验收范围说明目标、包含及排除内容和原因、依赖闭包、适用条件。完整验证覆盖这个范围的全部适用必测项，并不自动表示整个项目。

已发布范围不能通过删除失败必测项或弱化预期美化原运行；实质范围变化建立新基线和运行。

### 4.3 准备与启动分开

准备运行核对已发布计划、真实源码、入口、环境和范围，保存一次业务意图及冻结输入摘要。准备完成还不是实际执行。

启动前再核对实际物化内容与准备摘要，并核对授权。材料发生变化时旧意图不能悄悄换输入，须重新准备并检查相应授权。

### 4.4 源码快照与物化

快照记录选定内容身份、摘要和必要引用；物化将所选模块、依赖、入口和配置准备到本轮运行目录。

复制正确还要验证实际解释器、入口、加载路径和配置确实使用了这份内容。远端接口还须核对部署版本，本地固定不能证明远端一致。

普通目录也可测试，使用文件清单摘要和差异，不显示空的仓库字段。Git 项目需包含未提交变化；单有提交号不足以代表当前内容。

### 4.5 环境与最小配置

环境包含运行时、依赖、业务数据来源和隔离、复位、目标部署、网络、凭据用途和超时。虚拟环境隔离依赖包，不能保证数据库干净或远端版本正确。

首次纯函数检查不索要无关数据库、模型或 GitHub 凭据。正式提测、完整验证再检查对应交付信息和完整依据。无模型仍可人工建计划。

档位决定范围和结论上限，驱动决定推进方式。计划驱动按已授权步骤推进，逐步驱动在边界交互；可从计划驱动收窄为逐步驱动，反向扩大应新建运行。具体授权规则见第10章。

## 5. 执行与控制：状态、暂停、取消、恢复和重试

### 5.1 状态机是什么

状态机规定当前可以做什么、转换条件和需要保存的事实。它不是给按钮换一个名称。

计划状态、执行控制状态、业务结论、证据等级分别表达发布、推进、正确性和证据充分性，可以同时存在。运行已暂停也可能已发现有效业务失败。

### 5.2 L1、L2、L3

| 层级 | 评价什么 | 工单例子 |
| --- | --- | --- |
| L1 | 源码可运行性 | 语法、适用构建、加载或最小启动 |
| L2 | 模块与接口功能 | 创建工单并独立核验数据 |
| L3 | 完整业务目标 | 创建、分页查询、详情、改状态、刷新与最终核验 |

前一层通过不能替代后一层。无页面仅网页项不适用，仍可通过接口或命令完成适用 L3。上游失败阻塞依赖步骤，独立分支可以继续。首发先串行；并行须另行验证全组控制边界。

### 5.3 暂停、取消、超时

暂停在步骤边界生效，当前步骤先收尾；收到请求为暂停中，到达边界后为已暂停。

取消先保存意图再请求停止，确认后才记录已取消，未确认保持取消中或待核实。已停止也不能证明远端业务回滚。

超时表示等待达到截止条件。创建超时可能已产生工单，核验超时可能只是不知道结果，本地进程也可能仍存活。下一步须依据实际状态核实，不能无条件重发。

### 5.4 恢复、重试与重跑

| 动作 | 含义 |
| --- | --- |
| 恢复 | 重关联原执行、补取输出或从未执行步骤继续，不伪造新执行 |
| 重试某步骤 | 产生新 Attempt，立即成为该步骤当前尝试 |
| 明确重跑一轮 | 新建业务意图和运行，保留上一轮事实 |

副作用新尝试需要新授权。原请求的传输重试只能在端点明确保证同号重传不产生第二次业务执行时按合同恢复；方法名称或“通常幂等”不够。

### 5.5 运行中修改

修改形成运行中修订，只对尚未执行步骤生效；正在执行步骤拒绝修改。已执行步骤保留其当时修订，相关依据过期单列，不直接改旧事实。

删除必测、弱化断言或反向扩大驱动授权被拒绝。扩大目标、输入或凭据范围须重新核对授权，部分变化需要新建运行。

## 6. 可靠保存：单写、事务、幂等和恢复

### 6.1 单写与短事务

同一工作空间由一个核心持真实操作系统写锁。面板、CLI 和 MCP 不分别改业务文件。锁文件存在或过旧不能证明锁已释放，不能据此绕过活进程。

事务把相关记录、对象引用、索引、事件有效边界和幂等结果作为一次提交处理。材料准备和校验后发布，查询在发布前见旧完整状态，发布后见新完整状态。

外部执行、模型和网络等待在事务外。执行前保存意图，执行后收集材料，再以短事务发布结果。本地提交不能让远端业务与本地记录自动同时成功。

### 6.2 传输身份与业务意图

request_id 关联一次传输请求，intent_id 标识一次持久业务意图。重连或跨入口重传原意图，返回原结果或状态，不额外执行业务；同意图换输入属于冲突。

用户明确重跑才建立新意图。本地去重不能替被测接口证明幂等，未知副作用仍先查原结果。

### 6.3 输出与中断恢复

输出先以安全字节流进入可恢复采集区，保存块引用、摘要、序号和完整性；检查点保存最后提交阶段、真实执行身份和采集进度。只有游标、没有内容，无法抢救证据。

恢复依次核实已提交状态、活动执行、可抢救输出，再发布恢复事实。部分输出标为部分；不能先清空临时目录，也不能将未确认材料当完整证据。

PID 只是进程编号，恢复还须核对启动身份，避免把重用编号的其他进程认作原执行。

### 6.4 永久保留、备份与迁移

业务记录、证据、报告修订、导出、诊断和复核永久保留。临时运行副本等满足停止、证据可靠保存与恢复条件后才可回收；分类不明则保留待处理。

备份要包含所选已提交历史边界内的全部永久记录及其引用材料，包括早期报告、被替代修订、所有尝试和复核。只备份最新报告或索引不够。

迁移先处理活动执行和输出，再做可校验备份及引用校验。有已知缺口时，只能按合同明确确认缺口、验证无新增损失并保留原目录，不能称为完整迁移。

物理空间不足按控制流程暂停或停止并登记缺口，不静默驱逐历史。永久保留不保证外部删除、损坏永远不会发生。

### 6.5 查询与索引

列表按有限 QuerySpec 查询摘要，详情再取对象。分页固定筛选条件和提交快照，用户刷新才换新边界。索引损坏明确显示恢复状态，不伪装成空列表。

查询和小提交应只触及相关索引页和记录，不能每次遍历全部证据。这种效率约束保留全部历史，没有另设资源预算或总执行时限。

## 7. 判定与统计：怎样才能完整通过

### 7.1 先分清四种不同的问题

“操作执行完了”“验证过了”“业务通过了”“证据很完整”分别回答不同的问题。

| 问题 | 工单例子 |
| --- | --- |
| 执行是否完成 | 创建和查询这些必需步骤是否完成，输出是否可靠保存 |
| 是否有效验证 | 实际材料是否足以与有效、已确认的预期进行比较 |
| 业务是否通过 | 保存的工单内容是否满足要求 |
| 证据是否充分 | 来源、范围、关键链路、核验与材料是否可追溯 |

查询到了明确错误的工单状态，也可能是“执行完成、有效验证、业务失败”。查询超时，无法得知结果，则不能算有效验证，也不能用接口的成功响应补足。

本项目的业务结论是 passed、failed、incomplete、not_applicable。它们表示通过、失败、未完成、不适用。阻塞、取消、未知副作用等描述执行事实，不能随意冒充业务失败或业务通过。

### 7.2 用集合说明覆盖范围

集合可以理解为“带明确成员的名单”。用名单定义统计，是为了让每个数字都能查到具体用例，避免同一个页面说完成了，另一个页面却说没完成。

| 符号 | 名单的含义 |
| --- | --- |
| M | 当前已发布验收范围内，冻结的适用必测用例 |
| S | 本轮选中的用例，可能同时包含必测和补充用例 |
| E | 本轮有效完成全部必需步骤的整用例 |
| R | 本轮合法复用历史结果的整用例 |
| V | 有效验证的整用例 |
| P | V 中有效通过的整用例 |
| F | V 中有效失败的整用例 |
| U | 所选范围中尚未有效验证的用例 |
| H | 已有有效决定性失败依据的用例，按用例去重 |

公式只需要理解这些关系：

- E 与 R 不重叠。一个整用例不能同时算本轮新执行和整用例复用。
- V 包含在 E 与 R 的合集中，E 与 R 又包含在所选范围 S 中。
- V = P ∪ F，U = S − V。
- 完整验证要求 M ⊆ S，即所有必测项都被选中。

模板适用必测项还要准确映射到用例。只有“必测检查项”的文字，却没有对应可执行用例，不能当作已经纳入完整验证。

这些统计按整用例计算。一个用例有五步，完成三步，可以显示步骤进度三分之五，但不能因此把这个用例加入 E 或 V。

### 7.3 为什么还需要 H

假设一个用例要求创建、检查内容、变更状态三个步骤。第二步已经用可信证据证明“工单标题错误”，第三步没有执行。

此时整用例尚未完成，不能进入 E、V、F；但必要断言已经明确失败，也不能因为后续没执行就把整轮写成“只是未完成”。H 保留这个已确认失败的事实。

H 中的失败必须满足必要断言、准确且已确认的依据、有效来源与依赖、必要证据等守卫。普通报错、环境阻塞、未知结果、未确认的预期，都不能随便加入 H。

F 包含在 H 中。H 与 U 可以重叠，因此不能把“整用例已验证失败”和“已确认失败”直接相加。前者讲整用例验证完成情况，后者讲已经成立的决定性失败。

本轮存在有效 H，就派生业务失败，同时展示尚未完成的范围；没有有效失败但仍有未验证项，才是未完成。

### 7.4 覆盖与通过率分别表达什么

| 指标 | 计算方法 | 能说明什么 |
| --- | --- | --- |
| 本轮执行覆盖 | E 的数量 / S 的数量 | 本轮有效整用例执行了多少 |
| 本轮复用覆盖 | R 的数量 / S 的数量 | 合法复用了多少整用例 |
| 本轮有效验证覆盖 | V 的数量 / S 的数量 | 所选范围有多少得到有效验证 |
| 已验证部分通过率 | P 的数量 /（P 的数量 + F 的数量） | 已验证整用例中有多少通过 |

同时应展示相对 M 的必测覆盖。只显示 S 的百分比，会让“我只选了三项”看起来像“全部需求都测完了”。

零分母显示不适用或暂无有效验证，不能显示 100%。本轮 S 为空且没有适用检查时为 not_applicable；空选择不能让原有必测要求消失。“已验证部分通过率 100%”也不能遮住 H 或 U，更不能替代完整通过门禁。

三个例子：

| 冻结范围与实际事实 | 应当怎样显示 |
| --- | --- |
| M = S 共 12 项，执行全部完成，其中 2 项依据未确认 | 执行 12/12，验证 10/12，未验证 2；没有其他有效失败时为未完成 |
| M = S 共 12 项，全部有效验证，10 项通过、2 项失败 | 验证 12/12，业务失败；验证覆盖高说明检查充分 |
| M = S 共 12 项，新执行 10 项，合法整用例复用 2 项，全部有效通过 | 执行 10/12、复用 2/12、验证 12/12；其余门禁满足才可完整通过 |

如果 M 有 12 项，而按需只选三项非必测补充用例，即使三项全通过，也应同时显示本轮验证 3/3、必测验证 0/12。

### 7.5 完整通过是一组门禁

完整通过需要同时满足以下条件，具体字段和守卫仍按主责合同：

1. 本轮档位是 full，范围是准确的已发布验收范围，包含适用模板的最低必测要求。
2. 所有必测项有效通过；所选补充项也没有失败或未验证。
3. 没有跳过、待核实或过期依据；关键业务路径具有所要求的真实执行与核验。
4. 源码、实际执行来源、环境和预期依据相符，人工确认绑定准确修订，材料已可靠保存。
5. 没有与当前范围关联的有效 P0/P1 阻断问题。

补测十个无关用例不能抵消一个必测漏项。把失败项从名单删除，也不能获得完整通过。

quick 和 on_demand 分别用于快速检查与按需自测。它们只能表达所选范围结果，不派生完整报告证据等级，即使选中全部用例也不自动升级为 full。

完整通过只覆盖那次已发布验收范围。项目有两个独立验收范围，完成其中一个，界面应说明具体范围，不能写成整个项目通过。

### 7.6 A、B、C、D 是证据等级

证据等级只在 full 中派生，用来概括结论依据的充分程度。它不重新判断断言，也不替代业务结论。

| 等级 | 初学者可以怎样理解 |
| --- | --- |
| A | 没有触发更低等级缺口，结论有完整、有效、可追溯的依据 |
| B | 没有更严重缺口，但存在非关键部分缺口，或材料具备而准确依据尚未确认 |
| C | 关键来源待核实、关键真实链路缺失、必要核验证据缺失、必测未完成或依赖过期等 |
| D | 执行来源不匹配，或整轮没有有效证据等最严重情况 |

实际等级按合同列举条件从最严重情况向上判断，不能给多个维度取平均。无法归类的已知缺口，也要保守显示缺口及原因。

合法复用可以提供有效证据，所以“本轮没有新执行”不自动等于 D。使用虚拟环境也不自动得到 A；不使用虚拟环境但来源、数据与证据都有效，也不自动降级。

**A 级失败**完全成立：它表示有充分证据证明业务失败。工单确实没有正确保存，证据越完整，失败结论越可靠。

## 8. 复用、依赖失效与回归

### 8.1 复用解决什么问题

每次改动都从头生成内容、执行所有步骤，成本很高。复用允许在条件仍成立时使用既有成果，但必须知道成果依赖什么。

要分清两种复用：生成内容的复用，和测试结果的复用。旧用例文字仍可用，并不代表旧执行结果仍可用。

生成内容要核对来源、上下文、验收依据、规则、模板、环境以及实际采用的生成策略。只有受变化影响的内容才需要重新生成，人工修改不能被迟到的模型响应覆盖。

整用例结果复用还需要核对用例内容、执行入口与参数、范围、实际环境及业务数据状态、规则与适配器版本、材料可读取性、确认依据和依赖有效性。两个环境都叫“测试环境”，并不代表部署或数据相同。

### 8.2 新尝试为什么撤销旧复用

假设昨天的“创建并核验工单”是通过的，今天选择复用它，这个用例暂时属于 R。随后用户决定重新执行创建步骤，产生新的 Attempt。

一旦建立新 Attempt，整用例旧复用资格就撤销。新尝试失败、取消或阻塞，也不能退回昨天的绿色结果，让今天看起来通过。旧结果继续保留为历史。

跨运行的旧步骤与本轮的新步骤可以同时展示，但不能拼成一个本轮有效整用例 E、R 或 V。

同一轮中，未受影响且有效的上游步骤可以保留。只重试下游并不意味着无关步骤都要重跑，关键是依据关系仍成立。

### 8.3 依赖是结果之间的关系

工单用例的步骤可以是：

1. 创建工单，返回编号 A。
2. 查询编号 A，检查标题与状态。
3. 变更编号 A 的状态，再核验最终值。

第二、三步依赖第一步的实际输出。系统需要记录引用的 Attempt、输出摘要、取值及条件事实。

如果第一步重试后创建了 B，之前对 A 的查询就只能作为历史。即使重试仍返回 A，也不能只比较字面值就自动恢复下游有效性；执行身份和依赖依据已经改变，须按合同重新处理。

失效沿实际依赖传播，无关分支仍可有效。因此依赖记录同时避免了“错误沿用旧结果”和“所有步骤一律重跑”这两种浪费。

### 8.4 回归范围怎样产生

模块依赖的方向是“使用方指向提供方”。提供方改变时，要沿反方向查找可能受影响的使用方，再结合用例关联确定回归范围。

例如工单模块依赖用户模块，用户身份规则改变，就可能影响工单创建与权限检查。循环依赖需要去重，模块删除、重命名也要保持可追溯关联。

没有登记用例关联，表示影响映射有缺口，不能推断“不需要回归”。只有一个模块，也仍有本模块变化检查；不适用的只是跨模块传播部分。

关闭缺陷要求修复版本上的新实际执行及核验。历史复用可以辅助解释，但不能代替缺陷关闭所需的复测。

## 9. 证据可信性、Mock 与采集安全

### 9.1 什么才叫证据

证据是可以追溯到实际来源的材料，例如一次工具执行输出、HTTP 响应、独立查询结果、请求日志、人工操作截图和外部导入记录。

“AI 说已保存”“页面显示成功”“测试脚本退出码为零”都是观察，是否足以证明业务，还要看断言要求。

证据至少要关联项目、来源实例、运行、步骤、尝试、类型、内容摘要、大小和完整性。缺少这些关联，材料再多也难以知道是在证明哪次行为。

这里的原始输出指采集后、在落盘前过滤已知凭据的原始字节流。它保留真实观察，不经过 AI 改写；“原始”不意味着可以把密码原文永久保存。

### 9.2 独立核验必须对准同一业务对象

工单创建返回 A，后续必须核验 A，并核对实际目标部署、预期依据和查询策略。随便查询一条数据库记录，不能证明这次创建成功。

创建响应和核验结果应来自相应能力。项目的一期基线包括只读 HTTP 核验等方式；数据库核验依赖已安装、点名并实测的具体驱动，不能把“存在核验端口”理解成任何数据库都已支持。

如果要求直接确认数据库保存，就必须具备对应能力和授权。如果只有展示接口，应说明核验能力及其限制，不能把接口查询悄悄写成数据库核验。

最终一致系统可能稍后才可读，因此轮询间隔和核验截止条件应事先确定。超过核验期限而查询结果仍未知，记录为未完成及“查询结果超时”；查到明确不符合预期的结果，才按有效断言判断失败。若需求本身规定必须在某时间内完成，超时是否构成业务失败，要按那条已确认的时间要求判断。

### 9.3 链路关联不能靠猜

请求标识、Trace/Span 关系或明确的业务对象关联，能够连接“这次输入—执行—输出—核验”。

两个日志时间很接近、两个函数名称相似、AI 推断它们可能有关，都不能自动构成真实调用链。

缺少标识与结构化日志时，可以保留人工关联及说明，但必须标注证据性质和缺口。关联能力不足不自动证明产品有缺陷，也不能因此宣称关键真实链路完整。

### 9.4 Mock 为什么需要单独登记

Mock 用模拟行为替代真实依赖。例如用户接口不真正读取用户系统，而固定返回“用户有效”。它可以帮助验证本模块逻辑，但不能证明真实系统之间的集成成立。

本项目分别记录 Mock 声明、配置、静态候选和实际运行证据，再判断当前链路是 real、Mock、mixed 还是 unknown。

源码里出现 mock 一词，只能提示检查；源码没有该词，也不能证明没有模拟。最终以实际来源事实和执行材料为依据。

预先声明的 Mock 测试可以有局部价值。完整验证要求的关键真实路径，不能由 Mock 成功代替。

### 9.5 人工、智能体和外部导入

人工页面测试要保存具体操作顺序与结果。适用场景包括按钮、分页、跳转、表单、滚动、鼠标操作和错误展示。用户完成操作并不等于数据库结果已核验，仍须按业务要求补齐最终保存状态的证明。

一期的人工证据能力不能解释为已经具备自动录制与回放。

智能体测试应保存实际工具调用、每一步业务观察和必要核验。仅有“任务完成”的文字回答，不能证明外部动作成立。对于随机性输出，按预先发布的计划默认重复三次，分别保存实际输入、工具事件与结果，并逐次满足必要断言，不能用平均分遮住其中一次失败。

外部导入保留 EXTERNAL_IMPORT 来源。相同外部身份与相同内容可幂等处理；同身份不同内容须报告冲突。来源未知就保留未知，不能补造一次本地执行。导入中携带的命令或脚本也不会自动得到执行许可。

### 9.6 安全处理为什么必须在保存前

如果先把密码写进临时文件，再清理报告，密码仍可能进入采集区、备份和诊断。因此过滤必须覆盖 stdout、stderr、HTTP、模型响应、人工附件、外部导入等入口，在任何落盘之前完成。

已知凭据、授权字段、登记的模式及相应编码变体需要处理。跨输出块的凭据不能被拆开后漏掉，未能安全判断的尾部材料也不能原样转存，应保留采集缺口。

安全摘要和字节偏移对应过滤后的实际材料。过滤记录说明发生了什么，不保存凭据正文或可逆的替代信息。

凭据使用受控内存或安全后端引用，不进入普通配置、命令参数、日志、面板、导出或上传。

如果过滤掉了断言所需材料，应优先保存能够证明业务的非秘密事实；仍无法证明时就标出缺口，不能为了“证据完整”保留秘密。

这种设计能处理已知凭据和受控规则，不能保证识别任意未知、变形的秘密，也不承诺隔离同一操作系统用户下的恶意程序。这是设计边界，验收时应如实核对。

首次过滤后，模型外发、界面复制、报告导出和平台上传仍各有投影规则。本地安全保存不自动意味着任何材料都可以对外发送。

## 10. AI、人工确认与授权边界

### 10.1 AI 参与哪一部分

AI 可以协助生成用例草稿、解释缺口、整理问题描述和提出根因假设。实际执行、证据保存和最终判定由核心按合同处理。

“可能是事务没有提交”是待验证假设。只有具体执行与核验材料支持，才能成为事实说明；系统不应因为文字看起来专业，就自动确认问题、发布计划或关闭缺陷。

源码、项目文档、日志和模型输出都按不可信输入处理。它们可以提供待核对材料，但材料中的“忽略授权”“直接执行”不能变成新的权限。

本地核心的模型调用可以通过配置的模型 API 完成，与 Trae 内置聊天路径分开。MCP 提供 AI 工具接入，但一期仍须交付 CLI 与 stdio MCP 等约定入口，不能把接入合同省略为“以后再做”。

### 10.2 发给模型的材料要有明确范围

模型外发策略需要记录项目、接收方、地址、允许材料类别和策略修订。源码片段默认不允许外发，不能默认提交整仓库或全部日志。

变更接收方或扩大材料类别，需要重新确认。缩小范围立即生效；关闭 AI 阻止新的请求，但无法撤回已经发送到远端的字节。

请求只发送必要且处理过的材料。截断或省略应标注为部分材料，不能让 AI 基于一小段输出声称已经检查全部。

生成结果绑定当时的来源、策略和配置修订。用户已修改用例或来源已经变化，迟到响应只能按其真实来源处理，不能覆盖当前人工成果。

模型不可用时，人工整理、既有计划执行、材料查询等不依赖模型的本地动作仍应按各自条件工作。

### 10.3 “确认”至少有这些不同含义

| 确认或事实 | 表示什么 | 不能代替什么 |
| --- | --- | --- |
| 发布计划 | 接受这份范围与操作安排 | 具体副作用动作授权 |
| 确认断言依据 | 接受这一修订的预期判断依据 | 实际执行或独立核验 |
| 动作授权 | 允许对特定目标执行准确动作 | 其他输入、其他目标的新动作 |
| 实际执行 | 动作真正发生并有记录 | 业务正确 |
| 独立核验 | 真实结果与有效预期进行了比较 | 缺失的其他必测范围 |
| 本地报告复核 | 某人审阅了准确报告修订 | 修改执行与断言事实 |
| 模型外发策略确认 | 接受指定材料发送给指定模型 | 平台上传授权 |
| 上传许可 | 允许发送准确冻结提交 | 任意未来结果自动发送 |

这些事实分开，才能回答用户究竟同意了什么、系统实际做了什么。

例如补确认工单标题的预期依据，只会产生绑定准确依据修订的确认记录。它不改写冻结的用例、计划或旧报告，也不会伪造一次数据库查询。核心仍要核对已存在的真实材料，必要时重新执行核验。

### 10.4 副作用授权要绑定真实输入

创建工单、修改状态等会改变外部系统。授权应绑定业务意图、步骤、解析后的输入摘要、目标部署、凭据范围及相关修订。

上游还没有返回工单编号，下游实际输入就没有确定。不能用“同意整个计划”替代对未知实际动作的准确授权。

输入、目标或凭据范围改变，旧授权失效。新副作用 Attempt 要按合同建立相应授权；已明确幂等、属于原意图的恢复处理则按原许可边界判断。

### 10.5 AI 工具入口不能冒充用户

核心区分受控面板、交互式命令行和 agent_relay 等来源。调用者写一句“我是用户”或传入 user_confirmed=true，不足以成为人工确认。

需要确认时，核心生成准确的确认挑战，绑定动作、意图、输入摘要、目标、凭据范围、修订与来源会话。用户看到对应动作说明，受控入口完成核对后，核心保存确认事实并按许可推进。

重复提交同一确认返回原结果；错配挑战或输入变化不能沿用。不存在一个永久的“全部信任”开关来绕过这些合同。

MCP 可以查询、提交草稿或请求执行，并使用已经有效的授权。需要新的人工确认时，应返回待确认状态及用户入口，不能自己创建人工同意。

## 11. 报告、问题处理与安全导出

### 11.1 报告是冻结快照

报告要回答：“根据哪些范围、来源、环境、尝试、证据和规则，得出了这个结论？”

因此报告冻结准确输入修订，而非只保存一句结论。与判定相关的证据、依据或问题事实变化，就生成新的报告内容修订，旧报告继续保留。

面板的当前值可以变化，历史报告讲当时的事实。材料后来被外部删除，应在当前有效性与可用性中显示缺口，不能继续声称证据完整，也不能回改旧报告正文伪装成当时就知道缺失。

新的 full 开始时，当前范围进入重新评估。旧通过报告仍可查，但不能盖住新运行的取消、未知或未完成。quick 和 on_demand 结果只作为相应范围信息，不能替换完整验证结论。

源码变化、环境变化或规则变化，可能形成不同的当前检查依据。不能只按项目名称挑一份绿色报告作为“现在通过”。

### 11.2 报告复核独立保存

LocalReview 记录复核人、结论、说明、依据的报告内容修订和时间。复核不修改报告正文，也不改变实际执行与断言事实。

用户认为报告合理，不能把一个缺证据的结论改成通过。相关事实变化时生成新报告，新报告需要自己的复核依据。

导出会冻结所附复核集合。后来补一条复核，可以产生新导出，不会悄悄修改已经交付的旧导出。

### 11.3 问题如何从发现走到关闭

问题有稳定编号，保存预期、实际、复现步骤、来源与环境、用例及尝试引用、证据、严重程度和待验证假设。

基本处理过程如下，具体迁移守卫以问题合同为准：

~~~mermaid
flowchart LR
    A["草稿"] --> B["待确认"]
    B --> C["已确认"]
    C --> D["处理中"]
    D --> E["待复测"]
    E -->|新的实际复测通过| F["已关闭"]
    E -->|复测失败| D
~~~

问题可能属于产品、环境、数据或脚本。查询超时可以首先表现为未完成和阻塞原因，不能仅凭超时断定被测数据库存在产品缺陷。

P0/P1/P2/P3 用于表达严重程度。P0 对应核心不可用或重大损失，P1 对应关键功能错误，P2 是局部问题且有替代路径，P3 是较轻问题。是否阻断完整通过，还要核对人工确认、有效状态及与当前范围的关联。

AI 提出的 P1 草稿，不自动阻断所有项目。有效且关联当前范围的已确认 P0/P1，才按合同参与门禁。

重复、非缺陷、延期处理各有独立理由与追溯。延期不消除阻断；重复项跟随主问题处理且不能形成循环；被确认非缺陷时按合同解除相应阻断，但不篡改历史观察。

关闭问题必须依据修复版本上的新实际执行与核验，准确关联原验收条件和新来源。旧报告、复用结果或一句“开发已修复”，都不足以关闭。

### 11.4 修复说明怎样帮助开发

修复简报把问题编号、相关尝试、脱敏事实、复现步骤、预期与实际、待验证假设和复测入口整理在一起。

已知位置可给出准确来源引用，未知位置应保留未知，不能猜一行代码让用户误以为已经定位。

生成简报不等于自动改代码、自动执行修复或自动发消息给其他人。后续动作需要各自的操作入口和许可。

### 11.5 两种导出有不同价值

| 导出 | 用途 | 应明确说明 |
| --- | --- | --- |
| Markdown 摘要 | 阅读结论、范围、统计与缺口 | 没有随附证据时，不能声称可离线核验全部材料 |
| 可携带证据包 | 携带报告、清单和允许导出的证据 | 包含什么、缺失什么、排除了什么及实际文件摘要 |

证据包可使用 ZIP，包含 report.md、manifest.json 和相对路径证据文件。清单的摘要和大小对应实际导出字节，而不是简单照抄本地原对象摘要。

文件路径要避免目录穿越、重复覆盖和不安全引用，不能依赖接收者机器上的绝对路径。被安全规则排除或已经缺失的材料，要在清单中登记原因。

导出先生成并校验制品，再可靠发布成功记录。如果整体制品无法安全生成，就报告失败，不能只因为创建了一个空 ZIP 就提示成功。

可携带证据包用于阅读和核对，不自动具备完整恢复工作空间、导入后执行或平台审核的能力。

### 11.6 时间、摘要和信任边界

时间用于追溯开始、结束、采集和复核，并不单独证明跨系统的先后顺序。准确关系还要结合序号、关联身份和来源事实。

摘要可以检查内容是否与所引用材料一致，不能独自证明材料来自诚实执行。完整本地报告也不自动成为防篡改的组织审批或平台接收事实。

## 12. 面板、统一入口、诊断与生命周期

### 12.1 界面怎样帮助用户作出判断

面板的价值是让用户在合适的时刻看到足够的信息，并完成下一步操作。用户不需要先理解所有对象和内部字段。

| 阶段 | 主要信息 | 主要操作 |
| --- | --- | --- |
| 测试前 | 来源、环境、范围、档位、计划、阻塞原因 | 补配置、核对依据、发布计划、准确授权 |
| 测试中 | 当前步骤与尝试、实际进度、人工待办、暂停或未知原因 | 按守卫暂停、取消、核实、重试或修订未执行部分 |
| 测试后 | 业务结论、覆盖、证据与缺口、报告修订 | 查看证据、整理问题、复测、复核与导出 |

启动按钮应让用户知道是在快速检查、按需自测还是完整验证。高级驱动配置可以渐进展开，不能把普通测试变成填写全部内部字段。

下一步依据真实原因给出：断言失败去问题与证据，环境阻塞去对应配置，依据未确认去核对预期，未知副作用去核实原结果。界面也应保留其他缺口，不能只给一句泛泛的“请重试”。

隐藏一个项目只是视图偏好，不取消测试、不删除材料。用户查看历史时，新事件可以提示当前运行变化，但不应把正在阅读的历史报告自动切走。

### 12.2 面板为什么不能自己算结论

同一个运行，面板、CLI、MCP 和报告都读取核心产生的 DTO。业务统计、证据等级和问题阻断只计算一次。

界面可以转换展示方式，例如把 3/12 显示成进度，但不能重新扫描源码或按按钮颜色推断通过。信息区域读取事实；创建、确认、控制等动作通过核心用例提交，不能直接改业务文件。

共享面板保持一份源码，各编辑器由适配层提供宿主能力。这样能减少不同编辑器对同一结果解释不同的问题。

现行编辑器交互草案提出一个常驻面板和同容器详情等布局，属于 0.3 版讨论稿。学习时理解其信息组织理由，不应把草案里的布局当作已经实现或固定的最终界面。

### 12.3 快照与事件怎样接起来

假设面板先读取“已经完成两步”，随后订阅更新。如果第三步恰好在这两个动作之间完成，简单订阅“从现在开始的事件”就会漏掉第三步。

因此核心同时返回视图快照和属于同一提交边界的事件游标。面板先显示快照，再重放游标之后的事件，最后接入实时流。

游标需要区分同一提交里的多个事件。断线恢复允许重复投递，界面按事件身份和对象修订去重；不能只凭客户端时间判断哪个状态更新。

核心实例或写入代次变化，旧游标不能继续使用时，重新取得成对的快照与游标。跳到“最新位置”而不补齐中间事实，会把遗漏隐藏起来。

### 12.4 各入口如何共用一个核心

一期面板通过扩展和 Windows 本地命名管道连接核心；stdio MCP 的 relay 和 CLI 也转发到同一核心。

relay 可以理解为传话通道。它不拥有第二套业务存储、执行调度或判定逻辑。第二个编辑器窗口应核实并连接既有核心，不能创建第二个写入者抢写同一个工作空间。

本地通道限定当前用户及登录会话，核对工作空间、随机实例、启动身份和绑定。锁文件存在或某个 PID 存在，都不足以独自证明连接对象正确。

接口协商要区分协议版本和能力。主版本不兼容时拒绝相应写动作；不支持的动作明确返回能力不足。未知的关键字段或业务状态不能当零值处理，更不能默认通过。

### 12.5 健康状态与业务结果分开

| 健康状态 | 含义 |
| --- | --- |
| READY | 当前所需本地条件已就绪，能进入相应流程 |
| DEGRADED | 部分可选或可替代能力缺失，说明受影响动作及替代方式 |
| NOT_READY | 核心、写入或必需运行条件不可用，阻止受影响动作 |

READY 不代表被测产品通过。健康检查只说明产品自身是否能执行某个动作。

降级必须按动作的真实依赖判断：

- 模型不可用，影响需要模型的生成与分析，不自动阻止人工处理和已有计划执行。
- 宿主不能打开源码，可以显示位置文字或可用历史材料，不制造当前位置已验证。
- 工作空间不可写，阻止新运行和需要登记的新导出；核心仍可用且记录可读时，保留相应查询。
- 核心无法启动时，不能保证插件查询可用；用户可以用普通文件工具阅读已有导出产物。

诊断保存检查来源、修订、时间、已完成项、未检查项和原因。一次自检超时不应抹掉此前确认的结果；历史 READY 也不能绕过现在新出现的权限变化。

### 12.6 关闭窗口之后会怎样

窗口是入口，运行归核心管理。关闭窗口不等于取消业务，重新打开也不等于新建 Attempt。

| 核心所处情况 | 设计要求 |
| --- | --- |
| 仍有活动执行与输出采集 | 按合同继续保活，保存实际输出与状态 |
| 只有暂停、人工待办或没有已知活动执行的待核实结果 | 保存状态和恢复入口，安全收尾后可退出 |
| 有有效许可内的上传、查询、补缺或有限退避 | 完成本轮有界工作，再按其他条件收尾 |
| 只有未获许可的候选，没有可推进工作 | 保存材料，可安全退出 |
| 没有活动工作或未提交收尾 | 停止接纳新写动作，排空写队列后退出 |

核心不是永久系统服务，也不靠无人处理的空轮询一直保活。进入退出收尾时，新连接等待真实锁与发现状态后再连接，不能抢夺活动写锁。

活动执行身份不明时，先有限核实，保留目录与待核实记录；不能把核心进程退出当作外部业务一定停止。

“关闭编辑器后继续执行”需要在实际宿主和系统组合中验证进程组、句柄和退出行为。文档定义了要求，不等于已经证明该能力。

升级、卸载和维护也要遵守活动执行与输出收尾门禁，并保留业务数据，不能依赖编辑器停用回调一定执行。

## 13. 二期：兼容、源码定位和图

### 13.1 扩展哪些能力

二期继续使用一期核心，增加其他编辑器与操作系统组合、源码定位、依赖与链路图、能力诊断和面板增量。

变化的主要部分是宿主与系统适配，以及新增展示用例。原来的业务判定与统计保持统一，不能因为换了编辑器就重新定义“已验证”。

二期验收至少需要一个新增编辑器和一个新增操作系统组合的实测。这不等于已经支持所有编辑器与所有系统的任意组合。

进程、路径、锁、IPC 和宿主 API 在不同系统中可能不同。依赖方向、来源校验和恢复合同应保持相同，具体实现必须逐组合取证。

### 13.2 为什么“跳到代码”也要有可信状态

一份报告来自昨天的源码第 80 行。今天文件新增了十行，仍直接跳第 80 行，会让用户看见另一段内容。

源码定位需要回答两个问题：证据对应哪份历史内容，当前编辑器显示的内容是否就是那份内容。

| 状态 | 含义 | 界面应怎样理解 |
| --- | --- | --- |
| unknown | 来源或校验不足 | 说明未知原因，不宣称当前一致 |
| snapshot_verified | 冻结历史内容已校验 | 可以打开历史快照，不能据此断言当前文件相同 |
| metadata_match | 大小、时间等元数据匹配 | 只是候选一致，仍需显式内容校验 |
| current_verified | 当前磁盘与干净编辑器文档均完成对应内容和身份核对 | 可以按准确位置打开当前内容 |
| stale | 已证明当前内容不一致 | 提示历史快照或重新固定来源 |
| missing | 必要快照或路径不可用 | 展示缺口 |

未保存的编辑器缓冲区，即 dirty 文档，不能得到 current_verified。插件不替用户自动保存、回滚或改写代码。

显式校验只针对目标文件。核心核对磁盘内容及冻结来源，宿主核对文档会话、版本、显示内容及干净状态。校验期间编辑、关闭重开、绑定切换或迟到响应，都可能使结果失效。

宿主缺少可靠校验能力时，降级为历史快照或位置文字。“磁盘文件相同”不能冒充“编辑器正在显示的内容相同”。

### 13.3 两种图回答不同的问题

| 图 | 回答的问题 | 数据来源 |
| --- | --- | --- |
| 模块依赖图 | 哪个模块使用哪个模块，改变后可能影响谁 | 已登记的模块与依赖关系 |
| 实际链路图 | 某次执行具体经过哪些步骤和节点 | 真实执行、标识与业务关联事实 |

模块依赖图是结构信息，不能直接证明某次运行真的经过某条边。实际链路图也不能靠函数名相同或时间接近自动拼接。

重复调用同一个函数，仍可能是两个不同实际节点，不应合并后丢掉执行身份。

图的折叠、布局与说明是显示配置，独立保存修订。移动节点不改变执行事实，隐藏一条边不消除证据缺口。

图只投影已有事实，不产生新的通过结论。来源变化时，要标明图的依据是否过期。问题处理图等可能的后续扩展，也不能自动算作二期已约定交付。

### 13.4 历史分组不能混淆版本

历史记录可以按源码、改动和环境等依据分组。相同分支名称而实际改动不同，或者环境与范围不同，都不能被折叠成一份“当前绿色结果”。

展示便利必须建立在准确身份之上。用户展开分组后，应能查到每份运行、报告、范围和来源修订。

二期不引入三期的账号与平台上传。扩展阅读能力时，本地闭环仍应独立成立。

## 14. 三期：账号关联与结果上传

### 14.1 三期解决什么问题

三期让本地已经可靠保存的结果，按平台合同安全提交，并核对平台实际接收了什么。

可以把它理解为寄送一份封好的材料：先选收件方，确定包裹内容和清单，取得发送许可，再寄送并核对签收。寄送出问题不应让已经完成的本地测试消失。

插件负责账号关联、投影、冻结、发送与回执核对。平台接收、审核、共享查询和宿主属于平台职责。三期不额外引入本地 HTTP 服务、数据库、消息队列或独立发送 Worker。

### 14.2 账号身份和项目关联

账号身份使用平台确认的发行方与账号标识，不能只凭昵称或显示名称判断。同名用户可以是不同账号，未经平台约定也不能自行改写标识大小写。

本地项目绑定与平台项目绑定分开。缓存可以帮助展示，但发送时必须核对当前账号、参与关系、目标项目和绑定修订。

登录令牌通过凭据后端引用管理，不保存明文。退出或换账号应撤销相关许可并清理会话数据，保留原候选和冻结提交。

迟到回执归原账号与原提交，不能因为当前已换账号，就把原结果显示到新账号下。

没有 Git 的普通项目仍可按来源合同关联与提交，不必为了上传强行建立 Git 仓库。

### 14.3 候选与冻结提交是两个阶段

本地业务材料保存后，可以登记 DeliveryCandidate，表示存在可考虑上传的准确结果修订。未登录也可以保留候选；候选本身没有发送许可。

扫描以已提交业务变更为依据，有稳定的高水位和游标。候选引用与游标一起提交，失败后从原边界恢复，不能先跨过材料再慢慢登记。

上传自己的状态变化不应再次产生上传候选，否则会形成“上传状态又触发上传”的循环。空扫描也不应不断写新记录来保活。

队列或候选登记失败，保留恢复位置，不回滚已经保存的本地业务事实。

Submission 是准确冻结提交，绑定账号、目标、来源、材料修订、投影策略、实际安全字节与清单。材料或目标变化需要新提交；仅控制许可变化可以在合同允许时对原字节重新授予许可。

### 14.4 安全投影为什么要再做一次

本地材料已过滤凭据，不代表适合上传。日志或截图仍可能包含路径、源码和其他超出上传范围的信息。

三期按类型白名单投影运行、证据、报告与本地问题，禁止源码正文和 GitHub Issue/PR 等材料。默认移除路径信息；无法生成符合策略的材料时排除并保留缺口。

安全预览读取冻结后的材料，发送也用同一批字节，不能预览时很安全，发送时却重新读取最新原文。

本地源材料摘要与上传字节摘要分别保存。脱敏后字节变化，上传摘要必须按实际字节计算。

清单按项目约定的规范化 JSON 合同生成摘要，固定对象排序、类型、缺省与空值语义，拒绝重复对象键。不能用自制换行拼接代替双方约定字节。

算法样例和 Schema 可以帮助准备对接，但只有与真实平台进行字节级对拍，才能声明互通通过。

### 14.5 一份提交同时有四种状态

把所有事情塞进一个“上传中/完成/失败”状态，会混淆用户决定与平台事实。本项目分开保存：

| 维度 | 主要取值 | 表示什么 |
| --- | --- | --- |
| 接收状态 receipt_state | PENDING、UNKNOWN、INCOMPLETE、ACKNOWLEDGED | 平台实际接收的已知事实 |
| 传输状态 transport_state | IDLE、IN_FLIGHT | 当前有没有在途请求 |
| 发送控制 control_state | ACTIVE、PAUSED、ABANDONED | 用户及规则是否允许继续推进 |
| 许可状态 grant_state | active、revoked、completed | 准确许可当前是否有效 |

ACTIVE 不等于已经取得发送许可。安全预览、登录和项目绑定也不等于允许发送。

SubmissionDeliveryGrant 绑定准确提交、清单摘要、账号、目标、绑定与策略修订、允许操作以及相应人工确认或已批准策略。

用户只允许查询一次，就不能顺便补交缺失对象。暂停、关闭同步、退出或换账号撤销相关许可；仅用户明确放弃才产生 ABANDONED。

### 14.6 失联时为什么必须先查原编号

发送后超时，有两种可能：平台没收到，或者已经收到但回执丢了。直接创建新提交重发，会产生重复或冲突。

因此进入 UNKNOWN 后，在有效许可内先查询原 submission_id：

1. 完整收到且归属与摘要一致，保存 ACKNOWLEDGED。
2. 只收到部分，保存 INCOMPLETE，并在许可允许时补缺。
3. 平台明确没有原提交，原许可仍有效时，才可用同号同字节发送。
4. 归属、摘要或清单不符，保存冲突并暂停。

核对内容包括账号、项目、提交号、清单摘要、接收对象集合及每个对象的修订、大小和摘要。HTTP 成功只能说明请求得到了响应，不等于材料完整送达。

上传恢复只处理已经冻结的材料，不重新创建工单，也不重新执行业务测试。

### 14.7 暂停、放弃与迟到回执

用户暂停或放弃之后，之前在途请求可能已经被平台接收。不能宣称这些已发送字节被撤回。

迟到的完整有效回执仍按原归属保存接收事实，但不会解除暂停、撤销放弃决定或恢复发送许可。界面可以同时显示“已送达；用户此前已放弃”。

未放弃提交需要明确重授许可后恢复，并先查原号。被明确放弃的提交再次发送，需要显式建立关联的新提交并核对原接收情况；重新登录不能自动复活。

### 14.8 有界重试与正常分块

网络恢复需要有限失败次数、连续无进展次数和总请求轮次。这些记录持久保存，重启或重新登录不能清零。

HTTP 返回成功但一直 UNKNOWN，仍是无进展，不能无限查询。可信对象集合增加、确认连续字节偏移增加或完整回执到达，才算接收进展。

正常分块传输也需要多次请求，所以总轮次应由剩余正常请求计划 N 加有限额外恢复额度 R 确定。不能把“失败可重试三次”误用成“大文件最多发三个块”。

例如 100 MiB 对象用 10 MiB 块，平台约定一次准备、十次块传输、一次完成确认，正常计划就是 12 次。每次可信偏移增长都是进展，但总轮次仍有限；偏移到末尾也仍需完整接收确认。

达到失败、无进展或总轮次上限后保存原因并暂停。没有有效许可和可推进工作时，核心可以安全退出，无须另建长期 Worker。

平台不可用时，已具备的本地能力按自己的依赖继续工作。这种解耦不消除物理磁盘不足等真实限制。

## 15. 如何判断设计是否合理

### 15.1 从用户目标一路追到完成证明

评估设计时，可以沿着同一个用户场景，把四类文档和验收串起来。

~~~mermaid
flowchart TD
    A["用户目标：确认工单真正保存"] --> B["需求：明确应支持和应识别的场景"]
    B --> C["功能：输入、操作、输出、规则与异常"]
    C --> D["架构：职责、身份、核验、提交与恢复"]
    D --> E["界面：用户看见什么、能采取什么动作"]
    E --> F["验收：真实输入、实际观察与证据"]
~~~

这条链里，每一环都要保留原目标。“创建工单成功”不能在功能文档里变成“接口返回 200”，又在验收里变成“按钮可以点击”。

工单场景的完整对应关系如下：

| 层面 | 设计应给出的答案 |
| --- | --- |
| 用户价值 | 用户要知道数据真正保存且符合预期 |
| 需求 | 接口假成功能被识别，未知结果不能伪装成完成 |
| 功能 | 提交输入，保存对象编号，独立核验同一对象，输出结论及原因 |
| 架构 | 执行与核验端口、来源绑定、证据关联、统一判定、可靠保存 |
| 界面 | 分开显示响应、核验、业务结论和未完成原因，并给出合适入口 |
| 验收 | 用已知没有保存、保存错误和查询超时等真实场景核对结果 |

### 15.2 阅读设计时看这些方面

以下不是新增验收要求，而是理解现行设计的评估方法。

| 方面 | 应检查的内容 | 本项目中的具体意义 |
| --- | --- | --- |
| 目标与边界 | 服务谁，覆盖什么，依赖谁 | 测试插件与被测产品分开，三期与平台职责分开 |
| 输入与前置条件 | 输入来源、必填项、授权、环境是否明确 | 源码、范围、实际目标和断言依据不能含糊 |
| 完成定义 | 什么叫完成，什么只是进度 | 执行完成与有效验证分别统计 |
| 失败与未知 | 是否区分失败、阻塞、取消和未知 | 查询超时明确为未完成及原因 |
| 职责归属 | 规则有无唯一主责，模块能否替换 | 领域统一判定，适配器提供外部能力 |
| 身份与历史 | 当前依据与历史事实能否核对 | 来源实例、修订、Attempt 与证据引用明确 |
| 保存与恢复 | 中断后从哪里恢复，是否重复副作用 | 短事务、幂等意图、检查点与先查后恢复 |
| 依赖与复用 | 条件变化时旧结果是否失效 | 新 Attempt 撤销复用并传播实际依赖失效 |
| 安全与权限 | 秘密在哪处理，谁能授权什么 | 落盘前过滤，动作授权与上传许可精确绑定 |
| 用户理解 | 原因与下一步是否可理解 | 用真实原因引导操作，保留完整缺口 |
| 成本与维护 | 查询、材料保留、兼容的成本是否可控 | 有限索引查询、共享核心、历史备份与容量处理 |
| 完成证明 | 是否有真实环境、版本和证据 | 文档一致、模拟通过与真实验收分开报告 |

看到“自动恢复”时，继续核对恢复的是页面、核心事实、执行器还是外部副作用。看到“支持数据库”时，核对具体驱动与已验证组合。看到“实时”时，核对快照与事件之间是否可能遗漏。

这些词本身不能证明设计完整，具体输入、状态、关系和守卫才决定它们的含义。

### 15.3 这套架构的主要理由

**统一核心**让多个入口共用判定、统计和保存逻辑。它直接解决面板、AI、报告各说各话的问题。

**准确身份与不可变历史**让用户知道结果属于哪个版本、哪次尝试和哪份依据。新状态可以变化，过去发生的事实仍能追溯。

**副作用与独立核验分开**让“请求成功”和“业务成立”不被混淆。未知结果先核实，可以降低重复执行风险。

**保存与网络调用分开**让慢模型或慢平台不占据长写事务。本地闭环先成立，上传处理已保存材料。

**端口与适配器**使编辑器、系统和外部能力可替换。能力不足按动作降级，单个可选能力失效不会无依据地扩大为整个产品不可用。

这些理由与产品目标一致，因此架构方向有明确依据。具体方案是否在成本和可靠性上达标，还需要实现与相应验证支持。

### 15.4 同时需要承担的代价

| 设计选择 | 获得的价值 | 需要处理的代价 |
| --- | --- | --- |
| 多种身份、修订和独立确认 | 结果可追溯，授权准确 | 界面需渐进展示，避免用户被字段淹没 |
| 单写核心与文件存储 | 保持本地部署边界，统一提交 | 原子发布、锁与异常恢复必须在真实文件系统中验证 |
| 永久保留历史 | 原结论、尝试与问题可追溯 | 材料容量、备份耗时及外部损坏需要明确处理 |
| 精确副作用授权 | 用户清楚实际目标与输入 | 操作次数增加，应给清晰摘要并合理沿用仍有效许可 |
| 多宿主与多系统兼容 | 用户可在更多环境使用 | 每个组合都有 API、生命周期和能力验证成本 |
| 白名单冻结上传 | 降低泄露和内容漂移风险 | 投影可能排除材料，必须公开覆盖缺口 |

合理设计需要解释这些代价如何被管理。把代价隐藏在“自动完成”“安全可靠”等口号里，用户和开发者都难以判断风险。

本项目可以按内部里程碑逐步实施，但内部小闭环不能被写成一期完整交付。人工证据、外部导入、运行中修订、真实接入与故障恢复等仍属于约定范围。

### 15.5 文档一致与产品成立是不同证明

| 证明层次 | 可以说明什么 |
| --- | --- |
| 文档与静态一致性检查 | 名称、编号、字段、链接和规则没有已发现的冲突 |
| 领域、合同与应用检查 | 选定输入下，规则、接口与用例行为满足对应预期 |
| 故障注入与恢复检查 | 在指定中断位置，保存和恢复保持规定关系 |
| 真实宿主、系统、被测目标与平台验收 | 准确环境与版本下，外部边界实际成立并有证据 |

包能够构建，不证明 Trae 退出后进程仍存活。模拟平台确认摘要正确，不证明真实平台字节合同已经互通。清单里出现数据库驱动名称，也不证明实际连接与只读核验通过。

因此交付说明应分别列已实现、已通过检查、已通过真实环境验收和未验证。没有证据的部分保留未验证原因，不用“总体基本完成”混合表达。

### 15.6 几个重要场景如何对应验收

下表只是阅读定位，不替代完整 AC 原文，也不缩减复合场景。

| 设计主题 | 相关验收示例 |
| --- | --- |
| 接口成功但业务未成立、采集凭据过滤 | P1-AC07 |
| 暂停恢复、重试与依赖失效 | P1-AC19、P1-AC20 |
| 依据确认与执行/验证统计分离 | P1-AC21 |
| 模板门禁、独立核验、整用例聚合 | P1-AC24 |
| 面板、报告一致及快照事件衔接 | P1-AC27 |
| 永久保留、备份与迁移 | P1-AC28 |
| 独立本地复核 | P1-AC29 |
| 范围与准确授权、MCP 人工确认边界 | P1-AC31 |
| 配置与生成、问题处理、历史交互、安全导出 | P1-AC32—35 |
| 当前源码与历史定位保护 | P2-AC03、P2-AC04 |
| 平台失联恢复、许可、投影与回执 | P3-AC03—08 |

验收证据应能核对输入、软件及制品版本、预期、实际、材料位置和未验证原因。核对时从完整 AC 出发，不能只挑容易通过的子场景。

## 16. 贯穿示例：一次工单验证怎样完成

### 16.1 先把用户要求说准确

用户要求：“创建工单时，数据真正保存到数据库，内容与预期一致。如果查询超时，要如实说明未完成，原因是查询结果超时。”

这是被测工单产品的业务要求。测试插件负责组织验证并给出可信结论，不替工单产品保存它的业务数据。

本章是教学场景。假设项目已配置受支持、已验证的只读数据库核验能力，测试目标允许对应操作。它不表示当前工作区已完成这次实测。

### 16.2 准备范围、依据和环境

先确定这次验收范围是“工单创建与保存”。如果同时要验收分页、状态变更或权限，分别纳入范围与对应必测用例，不能运行到一半才把它们默认删除。

预期包括标题、发起人、初始状态等明确字段，并确认依据修订。测试数据需要能够识别本次对象，不能被已有同名工单干扰。

固定源码和实际执行来源，核对本地入口、解释器、加载来源与远端部署身份。虚拟环境只处理依赖等运行环境问题，不自动清空业务数据库。

选择 full 时包含全部适用必测项；只选择一个案例的 on_demand，只说明这个案例的范围结果。

### 16.3 发布计划与准确授权

计划定义创建输入、目标部署、核验方式、轮询策略、必要证据和依赖关系。

发布计划表示安排被接受。创建工单的具体副作用授权另外绑定准确输入、目标和凭据范围。未解析的下游输入留待上游结果产生后核对。

用例仍是草稿时不执行，依据未确认也不应悄悄从分母移除。需要人工处理的事项在启动前明确呈现。

### 16.4 实际执行与独立核验

基础检查可以确认入口和依赖可用，但这还没有证明工单正确保存。

创建步骤建立 Attempt，发出已授权请求并记录安全处理后的实际输出。假设响应返回工单编号 A。

核验步骤记录自己依赖哪个创建 Attempt，通过只读能力查询同一目标部署中的 A，按已确认预期检查数据。材料可靠保存后，核心才发布相应结果。

| 实际观察 | 核心应怎样处理 |
| --- | --- |
| 查到 A，必要字段与有效预期一致 | 该用例在其余条件满足时有效通过 |
| 查到 A，但标题或状态明确错误 | 按有效必要断言派生失败，并保留证据 |
| 创建响应成功，查询结果一直未知且达到核验期限 | 未完成；准确原因是查询结果超时 |
| 查询明确成功并确认对象不存在，且该观察满足已确认的保存时点要求 | 按该必要断言判断失败 |
| 查询到了另一条旧工单，无法证明与 A 对应 | 不能算完成核验，保留关联缺口 |
| 来源不匹配、必要证据损坏或查询能力不可用 | 按实际来源及能力缺口阻塞或判未完成，不能给通过 |

超时记录应说明哪个查询、目标、已知执行事实和最后确认位置。没有查到真实结果时，不编造“数据库没有写入”作为根因。

### 16.5 查询超时后怎样继续

创建动作可能已经产生 A，不能只因为核验超时就自动再创建一次。

先核实原业务对象和原查询状态。用户明确重试只读核验时，建立对应新尝试，并按合同判断哪些上游依据仍有效。

若用户改为重新执行创建，产生 B，则对 A 的旧查询只能作为历史，依赖新创建的下游需要重新核验 B。

如果此前是整用例历史复用，新 Attempt 建立后撤销旧 R。不能用昨天 A 的通过结果，加上今天 B 的创建响应拼出本轮整用例通过。

### 16.6 中断、保存与恢复

采集过程先处理已知凭据，再保存安全字节、关联引用和检查点。

编辑器意外关闭时，是否存在活动执行由核心和执行身份事实决定。重新打开先读取既有 Run；不自动建立新 Attempt，也不自动解除暂停。

核心中断后核实已提交状态、真实活动执行和可抢救输出。部分输出标部分，未知副作用先核实，不能清空工作目录再声称“恢复完成”。

### 16.7 形成报告与处理问题

核心按 S 和 M 分别计算覆盖，并根据有效事实派生业务结论。full 再派生证据等级及主要、全部缺口。

若查询超时且没有其他有效决定性失败，报告应为 incomplete，并保留未验证用例及查询超时原因。创建成功响应仍是证据之一，但不足以把该用例算入 V。

若已确认标题错误，即使还有后续必需步骤未完成，也保留 H 中的决定性失败，整轮为 failed，同时展示 U；不虚增 E 或 V。

问题记录保留预期、实际、准确版本、尝试及证据。把“可能是事务问题”作为假设，人工核对问题类别和严重程度后再处理。

### 16.8 修复与复测

修复产生新的源码或部署依据。测试者固定新来源，重新实际执行原失败条件和必要回归。

确认 A 已经存在，不能证明新版本不会再次丢失新工单。关闭缺陷要依据新实际执行与核验，不能复用原通过记录或只接受开发者口头说明。

复测通过后按守卫关闭问题，生成反映新事实的报告修订。旧失败报告、旧尝试和旧证据永久保留，形成可追溯修复过程。

本地复核另外绑定准确报告修订，不能回写旧执行事实。

### 16.9 导出与可选上传

用户可以导出摘要，或带安全证据和清单的证据包。清单核对实际导出字节，排除与缺失材料都给出原因。

三期还可以将已保存结果形成候选，按账号、目标和白名单生成冻结提交，预览后取得准确许可再发送。

发送超时先查询原提交号，核对实际回执；平台仅收到部分对象就按许可补缺。这个过程不会重新创建工单，也不会改变本地原测试结论。

这条路径把用户要求落实到准备、执行、核验、判定、保存、报告、修复和交付的每个环节。读懂架构，就是能够看出这些环节各自负责什么，以及它们怎样一起证明用户目标。

## 术语速查

| 术语 | 在本讲义中的含义 |
| --- | --- |
| FR / AC | 功能要求 / 验收场景与预期 |
| 合同 | 各模块和文档共同遵守的字段、规则、状态及行为约定 |
| 核心 | 共用的本地业务处理、判定、状态与保存能力 |
| 入口 | 面板、CLI、MCP 等用户或工具接入方式 |
| 领域规则 | 与外部设备和存储分离的业务判断规则 |
| 应用用例 | 为完成一次用户操作，组织规则、外部能力和提交 |
| 端口 / 适配器 | 业务所需外部能力的约定 / 实现该能力的具体连接方式 |
| DTO | 提供给入口或模块消费的数据视图 |
| Schema | 数据字段、类型和结构的约定 |
| 项目 / 用例 / 计划 | 被测对象组织 / 具体检查要求 / 一次检查的安排 |
| Run | 按准确计划和来源建立的一轮运行 |
| Step / Attempt | 用例中的步骤 / 某步骤的一次具体尝试 |
| 来源实例 | 本次记录绑定的准确来源身份，不只是一条分支名称 |
| 修订 revision | 同一对象内容或依据变化后形成的可追溯版本 |
| 摘要 digest | 用于核对准确内容的计算值，不独自证明来源诚实 |
| 快照 snapshot | 在确定边界冻结的内容或视图 |
| 断言 / 断言依据 | 对实际结果的检查条件 / 支持该预期的明确来源 |
| 副作用 | 创建、修改等会改变外部业务状态的行为 |
| 独立核验 | 用相应观察能力核对实际业务结果与有效预期 |
| 幂等 | 重复提交同一业务意图，保持约定结果而不重复产生副作用 |
| request_id / intent_id | 一次传输身份 / 一次持久业务意图身份 |
| 短事务 / 工作单元 | 一次可靠提交的边界 / 组织这次提交的机制 |
| 检查点 checkpoint | 支持中断恢复的已知执行与采集位置 |
| spool | 尚在采集和恢复过程中的安全输出材料区 |
| QuerySpec / 索引 | 有限查询条件 / 帮助定位相关记录的数据结构 |
| 游标 cursor | 查询或事件继续读取的准确位置 |
| epoch | 区分核心写入代次，避免沿用旧实例的状态 |
| Mock | 用模拟行为替代真实依赖 |
| 回归 | 变化后重新核对原有要求及受影响路径 |
| full / quick / on_demand | 完整验证 / 快速检查 / 按需自测 |
| E / R / V / H | 有效整用例执行 / 合法整用例复用 / 有效验证 / 已确认决定性失败 |
| 证据等级 | full 中对证据充分程度的派生概括，与业务结论分开 |
| LocalReview | 绑定准确报告修订的独立本地复核 |
| 安全投影 | 按指定策略选取、转换允许显示或外发的材料 |
| DeliveryCandidate | 已保存、可考虑上传的准确结果候选 |
| Submission | 绑定目标与准确安全字节、清单的冻结提交 |
| SubmissionDeliveryGrant | 针对准确提交及允许操作的发送许可 |
| 回执 | 平台提供的接收事实，须核对归属、集合与摘要 |
